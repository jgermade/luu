# Probing a destination before it is saved

Two threads were left open by
[`a-key-typed-into-the-form`](2026-10-20.a-key-typed-into-the-form.completed.md),
written earlier today, and they turn out to be one thread:

> **Nothing verifies the key before it is saved.** […] a key saved and a key
> that works are not the same fact, and the form currently claims the first
> while a person reads it as the second.

and, separately, Jesús's objection to the `Model` field:

> *¿por qué un proveedor debe especificar un modelo, en su lugar debe
> proporcionar una lista de los que ofrece?*

The second is half-answered already — the picker's second column *is*
`GET /v1/models`, so nothing in `config.toml` enumerates models and nothing
should. What is not answered is that the **form** asks for a model as free
text, before anything has spoken to the server, and then
[`provider.rs`](../crates/luu/src/provider.rs#L1191) floors it at a constant:

```rust
.unwrap_or_else(|| DEFAULT_MODEL.to_string()),   // "qwen2.5-coder:7b"
```

A profile with no model sends **a fact about one Ollama install** to whatever
it names. Against `api.minimax.io` that is a model the server has never heard
of, and the run dies at its first send with a message about a name nobody
typed.

Both failures have the same shape: **the form writes a destination it has never
spoken to.** A key that is wrong, a URL with a typo and a model that does not
exist are all discovered later, somewhere else, by a message that does not
mention the field that caused them.

## The proposal

A **Test** in the modal, against the candidate as typed — not against what is
saved, because what is saved is the thing being changed. `POST /api/providers/probe`
takes a backend, a URL and a key, builds a backend, calls `models()`, and
answers with the list or with the server's own refusal. **It writes nothing.**

On success the `Model` field stops being free text and offers what came back.
It stays *typable*, for the reason the existing route already gives: a model
that has not been pulled yet is a legitimate thing to write down, and a
provider that is simply off is the ordinary state on a laptop.

### Why a new route and not the one that exists

`GET /api/providers/{name}/models` resolves **through `config.toml`**. A
provider being added is not in it, and a provider being edited is in it with
the old URL and the old key — so the route would answer for the destination the
person is changing *away from* and call it a test. Saving first and probing
afterwards is the other way to get there, and it writes a broken profile to
disk in order to find out that it is broken.

### What crosses, and the commitment it touches

The probe makes an **outbound request to a host the person typed into a field
one second earlier**. That is local-first's own condition — *nothing leaves the
machine without the destination having been typed* — met in its strongest form:
not a profile typed weeks ago, but a URL still under the cursor. No prompt, no
file, no history crosses; the request is `GET /v1/models` with an
`Authorization` header and nothing else.

It is guarded like the writes are — `providers_editable`, loopback only. A
probe is not a write, but it spends the key, and "spends the key" is close
enough to "uses the credential" that it belongs behind the same door.

## What it costs

- **A route that reaches the network on behalf of the browser**, which none of
  the settings routes did before. It is bounded: one method, one URL shape, one
  timeout (`LIST_TIMEOUT`, the same the picker already uses).
- **The candidate key crosses again**, on a second route rather than only on
  the save. The exposure is the one already accepted earlier today and not a
  new one — loopback, no body in the log — but it is now two places rather than
  one.
- **A passing probe is not a passing turn.** `models()` says the endpoint
  answers and the key is accepted; it says nothing about whether the model
  named will take a `tools` field, or whether the window is what the profile
  claims. The button must say *what it checked*, not "OK".

## What was rejected

| | |
| --- | --- |
| Save, then probe the saved profile | Writes a broken profile to find out it is broken, and an edit would be tested after it had already replaced the thing it was being compared against. |
| Probing automatically as the URL is typed | A request per keystroke to a host that does not exist yet, and an outbound call nobody asked for. The button is the asking. |
| Dropping `model` from the profile entirely | It is not the list of what the provider offers — it is which model a *new session starts on*, and the three-step precedence (last used with this profile → the profile's → the first listed) already treats it as the preference it is. |
| Resolving the model by asking the provider at `resolve` time | `Resolved` is built without network, and `luu chat` would have to wait to learn where it is sending. The fix for the constant floor belongs in `BackendKind`, not in a round trip. |

## Still open

- **The constant floor is untouched by this.** `DEFAULT_MODEL` is still applied
  to every backend, so a profile saved without a model still sends
  `qwen2.5-coder:7b` to MiniMax. The probe makes it *unlikely* — the form now
  offers real names — and does not make it wrong. The floor wants to be the
  backend's own, or empty, and that is a change to resolution semantics with
  its own record to write.
- **Nothing probes `tool-calls`.** `native` against a server that will not take
  a `tools` field is refused at the first turn, which is exactly the class of
  late failure this record exists to move earlier.

## Appended 2026-10-20: the half the page sees

The route was built first and is as proposed. The form's half:

- **Test sits beside `Model`**, because the field it fills is the one it is
  about. It sends `backend`, the URL as typed, and the key as typed — or, with
  the key box empty, the `key-file`, so testing a saved provider retypes
  nothing.
- **On an answer the field becomes a select** of what came back, headed by
  *whichever the server picks*, and **nothing is chosen for the person**: a
  probe that lists one model still leaves the field as it was, because the
  field is what a session starts on and they may have meant another.
- **Any edit to what the answer was asked with throws it away** — backend,
  URL, key, key file. A list that outlived its URL would read as an answer
  for the new one, which is the stale-test failure this record started from.
- **A refusal is the server's own words**, `401 Unauthorized from …`, under
  the field. An answer with no models says that is ordinary — a server
  holding one — instead of looking like a failure.
- **The note under it says what was checked**: the endpoint answers and the
  key is accepted, not that a turn will succeed.

`tests/smoke/settings.spec.js` › *a destination is tested before it is saved,
and the test writes nothing* drives it against a stand-in `/v1/models` that
answers `401` to any key but one: the wrong key shows the refusal and keeps
the field free text, the right one offers both models with neither chosen,
editing the URL drops the list, and `config.toml` is byte-for-byte what it was
after both probes.

**Closed**: what this record planned is built. *Still open* above stands as
written — the constant floor is untouched and nothing probes `tool-calls`.
