# From tasks to jobs: uncrossing the terminology

**Status:** a proposal and the code it plans. It is marked `WIP` while waiting
for the implementation to land.

[`loude-design.md`](../loude-design.md) established the task lifecycle as the
core unit of scoping, permission, and forgetting:
> *A session is a sequence of tasks rather than a mode the agent is in. One
> boundary does three jobs — it is the cut point compaction takes, the scope
> permission is granted at, and the grouping the transcript shows.*

Up to now, that unit has been named `task`.

## The problem

Frontier models and agentic workflows (e.g. Qwen Coder, Claude, OpenAI) natively
think and communicate in terms of **task lists, checklists, or todo items**
(e.g., `- [ ] task 1`, or a sequence of subtasks emitted in reasoning/scratchpads).

When the outer boundary is named `task`, the vocabulary collides immediately:
1. Is a "task" the bounded operational container holding permissions, approvals,
   and summaries? Or is it one checklist item emitted by the model to complete
   that work?
2. In the planning block, the inner list was called `steps`:
   `{"objective": "...", "steps": [...], "files": [...]}`. Yet users and models
   naturally refer to these items as their "tasks".
3. When observing real model outputs, a model asked to perform work often outputs
   a list of "tasks" it will undertake, conflicting with the UI and protocol's
   use of `task` for the whole approval container.

## The proposal

Cleanly uncross the hierarchy by renaming the container to **`job`** and reserving
**`task`** for the model's checklist items:

```
Job (unit of scoping: objective, sandbox authority, gate approval, fold/summary)
 └── Tasks (checklist / plan steps returned by model or script)
      ├── Task 1: "read crates/agent-core/src/context.rs"
      ├── Task 2: "update select() signature"
      └── Task 3: "run cargo test"
```

### 1. Types and API
* `TaskId` $\to$ `JobId` (`pub type JobId = u64`)
* `TaskState` $\to$ `JobState` (`Proposed`, `Approved`, `Rejected`, `Closed`)
* `TaskView` $\to$ `JobView`
* `Authority::Task(TaskId)` $\to$ `Authority::Job(JobId)`
* `Context`:
  * `tasks` $\to$ `jobs`
  * `propose_task` $\to$ `propose_job`
  * `approve_task` $\to$ `approve_job`
  * `reject_task` $\to$ `reject_job`
  * `close_task` $\to$ `close_job`
  * `reopen_task` $\to$ `reopen_job`
  * `live_task` $\to$ `live_job`

### 2. Plan schema
In `Plan`:
```rust
#[derive(Debug, Clone, Default, PartialEq, Eq, Serialize, Deserialize)]
pub struct Plan {
    #[serde(default, alias = "steps")]
    pub tasks: Vec<String>,
    pub files: Vec<String>,
    pub writes: Vec<String>,
    pub commands: Vec<String>,
    pub closes_on: Option<String>,
    pub network: bool,
}
```
`alias = "steps"` ensures zero disruption for existing recordings, test fixtures,
or models that emit `steps`.

The `PLANNING` instruction updates to:
```
```plan
{"objective": "what this piece of work is", "tasks": ["what you will do"], ...}
```
```

### 3. Protocol (`protocol::VERSION` 3 $\to$ 4)
* `ClientMessage`:
  * `ApproveTask` $\to$ `ApproveJob`
  * `RejectTask` $\to$ `RejectJob`
  * `CloseTask` $\to$ `CloseJob`
  * `ReopenTask` $\to$ `ReopenJob`
* `ServerMessage`:
  * `JobProposed { job: JobId, objective: String, plan: Plan, source: PlanSource }`
  * `JobApproved { job: JobId, plan: Plan }`
  * `JobRejected { job: JobId }`
  * `JobClosed { job: JobId, summary: String, by: ClosedBy }`
  * `JobReopened { job: JobId }`
* `Refusal::Task` $\to$ `Refusal::Job` (with alias or fallback)

### 4. Record format (`record::FORMAT` 5 $\to$ 6)
* `job_proposed`, `job_approved`, `job_rejected`, `job_closed`, `job_reopened`.
* Existing format 5 readers check the number at `hello` / header.

### 5. Script directives
Task script parsing in `scripts/` supports:
* `## job: <objective>` (with `## task:` aliased for backward compatibility)
* `## task: <item>` (replaces `## step:`, with `## step:` aliased for backward compatibility)
* `## close`

### 6. SQLite store and Web UI
* SQLite table `jobs` stores `JobView`.
* Web debug client renders `Jobs` list with nested `Tasks` checklist.

## What it costs

* Protocol version bump to 4 and record format bump to 6.
* Full workspace rename across `agent-core`, `luu`, tests, and the web client.
* Backward compatibility layers (`alias`) in serde to preserve replay of older
  fixtures without breaking test suites.

## What was rejected

* **Keeping `task` and naming checklist items `steps` or `subtasks`:** Models
  naturally generate "Tasks" checklists, causing constant friction and cognitive
  overhead for users and documentation.
* **Partial rename (e.g. keeping wire protocol as `task` while calling it `job` in code):**
  A split vocabulary creates more confusion than a version bump. The protocol rule
  exists precisely to allow honest schema transitions.

## Still open

* Exposing granular task completion checkboxes (`[x] Task 1`) within the live Job
  in the Web UI as the model progresses.
