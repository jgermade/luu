# Session resume in SQLite: the inverse fold

**Status:** a proposal and the code it plans. It is the second half of item 2 of
[`ROADMAP/2026-09-01`](../ROADMAP/2026-09-01/README.md), spec'd in
[`session-store.md`](../ROADMAP/2026-08-31/session-store.md) and unblocked by
[`RECORD/2026-09-02.sessions-in-sqlite.completed.md`](2026-09-02.sessions-in-sqlite.completed.md).

[`sessions-in-sqlite`](2026-09-02.sessions-in-sqlite.completed.md) landed the store,
schema, and the parity test asserting that folding the record produces the same
`SessionView` as loading it from SQLite.

What it deliberately deferred was **session resume**: loading a stored view back into
a live `Context` (the write side), so that a server or CLI session can continue an
earlier conversation without re-running from scratch.

## The problem

`SessionView` is the read side — what a client browses. `Context` is the write side
— what the next prompt is built from.

To resume an active session:
1. `Context` needs its history (`turns`), its task state (`tasks`), its eviction
   watermark (`floor`), and its prefix blocks (`system`, `tools`, `map`).
2. Closed tasks must restore their summaries so that the compaction fold
   (`Item::Folded`) applies to history tokens identically.
3. The eviction floor must not reset: turns that left the window must stay out.

## The inverse fold

```
SessionView + TokenCounter + Prefix  --->  Context
```

### 1. The prefix
`Context::new(system)` with `tools` and `map`. When resuming in `luu serve` or `luu chat`,
the prefix comes from the current environment (or stored prefix tracker), keeping the
system invariants intact.

### 2. Task restoration
For each `TaskView` in `view.tasks`:
- `id`, `objective`, `plan`, `state`, `closed_by` are copied directly.
- If `task_view.summary` is present (i.e. task was closed), a `Summary` is
  reconstructed with `counter.count(&summary_text)` and `counter.id()`.
- If the task was `Approved` when saved, it resumes as `Approved`, restoring
  `context.live_task()`. If all tasks were `Closed`, `live_task()` is `None`.

### 3. Turn restoration
For each `TurnView` in `view.turns`:
- `prompt`: `turn_view.prompt`.
- `answer`: `turn_view.text`.
- `task`: `turn_view.task`.
- `steps`: each `ToolCallView` in `turn_view.tools` is reconstructed into a
  `ToolStep`:
  - `call`: `ToolCall { name, arguments }`
  - `outcome`: `ToolOutcome { verdict, output, truncated, error, command }`
  - `text`: reconstructed tool call fenced text:
    `"```tool\n" + serde_json::to_string(call) + "\n```"`
  - `duration_ms`: `duration_ms.unwrap_or(0)`
- `tokens`: recomputed by counting with the active `TokenCounter`.
- `counted_by`: `counter.id()`.

### 4. Eviction floor
A turn with `turn_view.evicted_by.is_some()` was dropped from the window before
the session ended.
`floor` is reconstructed as the count of leading evicted turns:
```rust
let floor = view.turns.iter().take_while(|t| t.evicted_by.is_some()).count();
```
The floor only ever moves forward, so turns that left the prompt stay dropped.

## Parity assertion

The acceptance test verifies that:
```rust
let resumed_context = Context::from_view(&view, system, tools, map, counter);
resumed_context.select(next_prompt, ...) == original_context.select(next_prompt, ...)
```
over real sessions recorded with tool steps, tasks and evictions.
