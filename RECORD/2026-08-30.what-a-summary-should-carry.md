# What a closed task's summary should carry: what it was shown, not only what it did

**Status:** proposal, no code yet. It answers the first row of the *still open*
table in [`2026-08-30.the-fold-probe-run.md`](2026-08-30.the-fold-probe-run.md),
which measured the fold and deliberately stopped short of proposing anything:
*what should a closed task's summary carry so turn 17/18 survive?*

## The problem, stated from the measurement

The probe run is the evidence and is not repeated here. In one line: two of the
three closed-task questions came back wrong after folding, and the reason is the
same in both — the summary is an account of what the task **did**, and the
questions ask for what the task **read**.

`task.rs` says as much in its own words. `summary_text` writes the objective, the
approved plan's steps, and then `evidence(steps)` — one line per distinct
`ToolStep`, each `name target — status`. A task whose grounding arrived as a
`## fragment:` ran no tools at all, so all three summaries in the tasks run
reduced to the same sentence:

```
no tools ran; 5 turn(s) folded, their text not kept
```

That sentence is true, and it is also the whole failure. `Turn.code_context`
holds the fragment that grounded the turn — path and text, structured, already
counted — and `Context::close_task` walks the task's turns to collect
`turn.steps` and never looks at the field beside it. Nothing was lost in a
lossy step: the content was in hand at the close and was not asked for.

There is a second, smaller effect worth naming, because it changes what a fix
has to do. Turn 18's tasks-run answer was *"I don't have access to the specific
sandbox policy details"* — a refusal, not a wrong guess. The summary told the
model that five turns had been folded and their text not kept, and the model
answered the question that sentence asks rather than the one the user asked.
A summary is not only storage; it is also an instruction about what may be
relied on.

## The proposal

**A closed task's summary carries what the task was shown, verbatim, under a
fixed token cap — and no model prose.**

Concretely, three changes to `summary_text` and its one call site:

1. **Provenance, always.** The fragments the task's turns were handed, by name
   and range, in order, deduplicated the way `evidence` already deduplicates
   tool lines. Nothing new has to be carried for this: `Fragment.path` is
   `Spec.source`, the string the person typed (`luu.toml:1-26`), kept that way
   on purpose so a prompt labels a fragment the way it was asked for.

2. **The bytes, while they fit.** Each named fragment is quoted verbatim into
   the summary, most recent first, until a per-task cap is reached. Anything
   past the cap is named and marked `not kept` — the honest half of what the
   current sentence says, kept for exactly the fragments it is true of.

3. **The no-tools sentence becomes accurate rather than discouraging.** With
   fragments quoted, "their text not kept" is false for the part that matters,
   and a model reading it refuses questions it could have answered.

Shape, for task 3 of the probe:

```
[task closed] work out what the sandbox policy grants
approved plan:
  - read the policy and answer from it
shown, from 5 turn(s):
  luu.toml:1-26 (26 lines, 285 tokens)
evidence: no tools ran
--- luu.toml:1-26
[sandbox]
paths = [...]
...
---
```

The cap is the same argument as `MAX_EVIDENCE_LINES` and should sit beside it:
the summary enters the write-once region every later call is built on, so its
size must be a function of the cap and not of how long the task ran. A
`MAX_QUOTED_TOKENS` counted with the session's own `TokenCounter` — the count
already happens at the close — is the mechanism; the number wants the probe to
choose it, not this file.

**Why verbatim and not a digest.** The one thing the design says about summaries
that is load-bearing is that they are *evidence, not narrative* — the same
sentence that governs the judge, for the same reason: a summary enters a region
that is never rewritten, so a wrong line in it is wrong for the rest of the
session and nothing later can contradict it. A file's own bytes cannot be a
hallucination. A model's one-line digest of them can, it costs a model call at
every close, and it makes the fold non-deterministic — three properties the fold
was specified not to have. The probe file's own suggestion was *"what the
fragments were and one line of what they said"*; this proposal takes the first
half and argues against the second.

## What it costs

Tokens, and only on later calls. A summary sits in the prefix from its close to
the end of the session, so quoting a fragment pays for it once per later call
rather than once. For the probe's three tasks, using the fragment sizes the
mock run measured (205, 230, 285 tokens, closing before turns 6, 11 and 16):

| | extra prompt tokens | total, all calls |
| --- | ---: | ---: |
| tasks, as run | — | 18 735 |
| tasks, quoting all three | ~6 800 | ~25 500 |
| plain (no fold) | — | 37 431 |

So roughly a third of the fold's token win goes back, and the fold still wins by
about a third against no fold. That is an estimate off the measured sizes, not a
measurement — it assumes the answers do not get longer, and it is exactly what
re-running the pair would settle.

Prefix reuse should improve rather than degrade: a summary is written once and
never edited, so the added tokens are stable-prefix tokens.

## What is rejected, and why

- **A model-written digest at close.** Above: prose in the write-once region,
  an extra call, and a non-deterministic fold. If the cap turns out to bind hard
  at 32K on real work, this comes back as its own proposal with the judge's
  shadow-mode framing — measured before it is trusted, not argued into place.
- **Keeping the fragment attached to later turns instead of quoting it in the
  summary.** That is relevance selection's question, and answering it here
  answers it wrong: "which turns does this file belong in" is not "the rest of
  the session".
- **Provenance alone, trusting the model to re-read.** Cheapest, and it fails
  the thing being measured: the fold is supposed to stand in for the turns, and
  a fold that converts an answer into a tool call has moved the cost, not kept
  the knowledge. The probe's last task says *"answer from the history alone"*
  for that reason. Re-reading stays available and stays the right move when the
  file has changed since; it is not the summary's answer.
- **Raising `MAX_EVIDENCE_LINES` instead.** Unrelated: the evidence lines were
  not truncated in this run, there were none.

## What changes when this is accepted

`loude-design.md`'s Tasks section, which currently says a closed task is
"replaced by a deterministic summary of the approved plan and what the tool
results reported". That sentence stays true of the mechanism and stops being the
whole of it: the summary is the plan, what the tools reported, **and what the
task was shown**. The measurement it rests on is the probe run; this file is the
decision it argued for.

Implementation is small and in one place: `Context::close_task` already walks the
task's turns to gather `steps`, and `Turn.code_context` is the field beside the
one it reads. `Task::close` grows a `fragments` argument and `summary_text`
grows the two blocks above. `Fragment` is unchanged — it already carries the
label and the text.

## Appended 2026-08-30, after building it: what the mock says it costs

Built as proposed, in the two places the file said it would be: `Task::close`
takes the fragments its turns were handed, `summary_text` writes a `shown, from
N turn(s):` block and quotes each kept fragment between `--- path` markers, and
`Context::close_task` gathers `turn.code_context` beside the `turn.steps` it
already gathered. `MAX_QUOTED_TOKENS` is **1024** to start with, counted with
the session's own counter; a fragment is kept whole or named `over the cap, not
kept`, and duplicates of the same spec are quoted once.

Task 3 of `grounded-tasks.txt` now folds to this, which is the point of the
change in one screen:

```
[task closed] work out what the sandbox policy grants
approved plan:
  - read the policy and answer from it
shown, from 5 turn(s):
  luu.toml:1-26 (26 line(s), 281 tokens)
no tools ran; the turns' own text is not kept
--- luu.toml:1-26
# Loude's own sandbox, for running the agent on this repository.
...
---
```

The numbers, both grounded scripts against the mock at `--context-limit 8192
--reserve 512`, summed over the twenty prompts with the approximate counter:

| | total prompt tokens | mean reuse, turns 2–20 |
| --- | ---: | ---: |
| tasks, before this change | 16 927 | 89.6% |
| tasks, quoting | 24 356 | 89.3% |
| plain, no fold | 30 682 | 93.9% |

The estimate above was ~6 800 extra tokens; the measurement is **7 429**, close
enough that the estimate's method was sound and far enough that it was an
estimate. Reuse is unchanged, as predicted — a summary is written once.

**Where the estimate was wrong is the ratio, and it is worth saying plainly.**
It said about a third of the fold's win goes back; on the mock, more than half
does — the fold's saving over no fold falls from 45% to 21%. The mock's answers
are one fixed sentence, so the prose the fold drops is much smaller here than
against a real model, where the same three quotes sat against 37 431 tokens of
real answers. The honest statement is that quoting costs a fixed ~7.4k on this
pair and the win it eats into is whatever the run's own prose is worth, which
only the M4 can say.

**What is now measurable and was not**: whether turns 17 and 18 come back right.
That is the same two scripts, the same pinned sampling (`--temperature 0 --seed
42`), the same tokenizer and model, and nothing else new. If they do, the first
row of this file's *still open* table closes and the second — the value of the
cap — becomes the only question the probe still has to answer for summaries.
