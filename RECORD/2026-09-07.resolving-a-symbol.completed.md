# Resolving a symbol: from what the model saw to where it is now

**Status:** a proposal, and one measurement it has to survive before any of it
is built.

It comes from outside the roadmap's table — like
[`naming-a-provider`](2026-09-07.naming-a-provider.completed.md), which came
from a *Still open* line rather than from an ordered item. The question is
narrow: the map and the selector hand the model a view of the tree that was true
*when the prompt was built*, and nothing in this repository can turn a symbol
the model then names back into a location that is true **now**.

## What is actually missing, which is less than it first looks

The proposal that started this said the provenance is discarded the moment the
view is rendered to plain text. That is not what the tree does, and the
correction decides how much there is to build:

- [`repo_map.rs`](../crates/agent-core/src/repo_map.rs) renders every entry as
  `line  signature`, 1-based, under the file's path — "meant to be followed by
  hand into the file", as its own doc comment says.
- [`select.rs`](../crates/agent-core/src/select.rs) computes `Chosen { path,
  lines: (start, end) }` per fragment — the matched definition, up to the line
  before the next one — and `Chosen::spec` round-trips it through the same
  `path:START-END` syntax `--fragment` parses.

So the path and the line range are **in the prompt already**, and a person can
follow them. Three things are missing, and only the third is interesting:

1. Nothing keeps the mapping after the render. `Chosen` is dropped once
   `Selection::render` has run; the next turn re-derives it from scratch.
2. Nothing is addressable by *name*. The model says `check_path`; the prompt
   says `crates/agent-core/src/sandbox/mod.rs:437-…`. Joining those two is a
   re-parse nobody performs.
3. **A captured range goes stale silently.** Any edit above line 437 moves
   `check_path`, and the range still parses, still passes the sandbox, and still
   returns a fragment — of the wrong lines. That is the one failure mode here
   with the shape this project cares about: it does not fail, it answers wrong.

## The proposal

A symbol index, built in the walk that already exists — `Walked` is produced
once at startup and shared by the map and the selector, so this adds a third
consumer rather than a second parse.

- **Identity:** `(path, qualified name)`. Not offsets, so an edit elsewhere in
  the file does not invalidate it. The path is part of the key because `new` is
  not unique in any Rust tree, this one included.
- **`resolve(id) -> Option<(path, range)>`** re-parses the file on demand and
  returns where the symbol is *now*, or `None`. Never a remembered range: the
  same posture as `check_path` re-resolving a path at the moment of the open
  rather than trusting an earlier check, one level up.
- **Nothing changes in the prompt.** The index lives beside the view, not in
  it; the model keeps naming symbols the way it already does.

What it buys, concretely: `edit_file(path, old_string, new_string)` makes the
model reproduce `old_string` from memory, and
[`fs.rs`](../crates/agent-core/src/tools/fs.rs) refuses it two ways — *is not in
the file*, and *appears N times; include more context*. A resolved symbol range
is `old_string` read off disk instead of transcribed.

## The honest scope, because the first draft overstated it

An id keyed on `(path, name)` survives **edits inside the file that shift line
numbers** — which is exactly what a captured range does not survive, and is the
whole of the win. It does not survive a rename, and it does not survive a move
to another file: both change the key. Claiming it survives moves would be
claiming the key is not the key.

It is also not a sourcemap. A v3 mapping is position↔position between two texts
and dies on any edit; this is symbol→location, re-derived on demand. A different
problem, and the comparison is only useful for naming which one is not being
built.

And it is **not selection**. The reference graph has lost three times as an
ordering — [`ranking-the-map`](2026-09-02.ranking-the-map.completed.md),
[`the-map-order-probe`](2026-09-03.the-map-order-probe.completed.md),
[`choosing-fragments`](2026-09-05.choosing-fragments.completed.md), the last one
on the question it was built for. Nothing here decides what enters the prompt. A
fourth attempt at selection still has to argue against that table; this does not
touch it.

## What has to be measured first, and it is not the overhead

The overhead is the easy half: the walk happens anyway, and an index of
`(path, name) -> range` over the 44 tagged files of this tree is small enough
that measuring it is a formality.

The hard half is that **this repository has no evidence the problem occurs.**
The corpus on disk — [`runs/2026-09-06.precision`](runs/2026-09-06.precision/) —
is 38 read-shaped questions and contains **zero `edit_file` calls**, so the
failure this proposal exists to remove has never been recorded here. Every
number this project trusts came from a run, and there is no run for this.

So the first step is not a prototype. It is a write-shaped corpus: prompts that
make the model edit what it was shown, scored on how often `edit_file` is
refused for *is not in the file* / *appears N times*, and how often a fragment
range captured at turn N points at the wrong lines by turn N+k. If those counts
are near zero the index is unmotivated and this record ends as a *no*, which is
a fine thing for a record to end as. If they are not, the prototype is the
`Walked` extension plus `resolve`, measured against the same corpus one flag
apart.

## Cost, and what it would break

- **A symbol can be gone by the time it is resolved** — the model edited it a
  step earlier in the same turn, or a person did. `resolve` returns `None` and
  the caller says so; nothing returns a stale range. The same rule as
  everywhere else: never fail quiet.
- **Re-parsing on demand is a filesystem read inside a turn**, which is the
  category of call the loop's clock exists for
  ([`a-clock-where-there-is-no-seam`](2026-09-05.a-clock-where-there-is-no-seam.completed.md)):
  it must not be an inline `std::fs` call in an `async` block, or the deadline
  beside it never fires.
- **Every read goes through the sandbox**, for the reason `select` already
  states: a path `read_file` would refuse must not become readable by being
  reached a different way. A symbol id is a different way.

## Still open

- Whether the write-shaped corpus is worth building for this alone. It is
  reusable — nothing scores editing at all today — which is an argument for it
  independent of this record.
- Whether `resolve` belongs to the selector or to the tools. `edit_file` is the
  caller that pays for it; `select` is where the ranges are already computed.
- What a rename should do. Returning `None` is correct and useless; matching by
  signature or by body similarity is a second mechanism and would need its own
  argument.

## 2026-09-07, later: the mechanism does not survive, and the bug it found is already in the tree

Written the same day, which is unusual and is the point: the record above
argued for a symbol index, and reading the code to schedule it found that the
index is answering a question the tree does not ask, while the failure it was
invented for is **live, today, and caused by something else**. Both halves
below are corrections to the proposal above, which stays as written.

### The failure is real, and it is a cache with no invalidation

`walk_sources` is called **once per process** — `serve.rs`'s `App` construction
and the chat/script loop in `lib.rs` — and `app.walked` is read on every turn
and never refreshed. The comment beside it said so, and drew the benign
conclusion:

> "A file written mid-session is therefore not selectable until a restart, which
> is the same staleness the map already accepts."

That sentence is wrong in the way that matters. An edited file does not become
unselectable: it stays in `walked` with its **startup line numbers**, `select`
turns those into `path:START-END`, and `crate::fragment` reads *the current
file* at them. The range parses, the sandbox allows it, a fragment comes back —
of the wrong lines, under the right path, presented as the definition the turn
asked about. Not selecting it would have been the safe failure; this is the
unsafe one, and it is the exact failure shape the proposal above was invented to
remove.

So the diagnosis in the proposal was right and its causal claim was not. Nothing
about symbol identity is required to fix this. A stamp per file — mtime and
length — and a re-walk that re-parses only what moved is the whole of it, and
`rewalk_sources` is that.

### The `edit_file` half would have removed a safety property

Point 4 of the proposal — derive `old_string` from the resolved range instead of
having the model transcribe it — is worse than unnecessary. `old_string` is not
a transcription tax, it is an **optimistic lock**, and `tools/fs.rs` says so
where it enforces it:

> `// Uniqueness is the safety property: a replacement that matched twice would
> // edit the one the model was not looking at, and it cannot see which.`

A model that saw version A of a file and writes an `old_string` from it fails
loudly against version B — *is not in the file*. Deriving `old_string` from the
current bytes makes the match unconditional, so the model's `new_string` is
applied on top of text it never read. It converts a loud failure into a silent
wrong write, invoking *never fail quiet* to do it.

### What is left of the index, which is not enough to build

Once the walk is re-stamped, the case the index was for — *the model names
`check_path`, give me where it is* — is answered by a range that is current.
What remains is resolving a symbol cited in an **earlier** turn against a tree
that has since moved, and `edit_file` already covers that by refusing. So the
index is a mechanism looking for the gap that the cheap fix closes. It is not
being built, and this record is the argument against it rather than for it.

The write-shaped corpus survives on its own terms — nothing scores editing today
— but it is no longer what blocks anything.

### What was built instead

- `repo_map::Stamp` (mtime + length), taken **before** the read. The order is
  the safety: a write between stamp and read leaves a stamp older than the
  bytes, so the next walk re-parses — one wasted parse. The other order records
  the new stamp against the old parse and keeps it, silently.
- `repo_map::rewalk_sources(sandbox, previous) -> Rewalked`, re-parsing only the
  files whose stamp moved, and counting `reparsed` / `added` / `dropped`.
- Called before scoring in `serve` and in the chat/script loop, on a blocking
  thread — a `std::fs` call inline in an `async` block never yields, so the
  loop's deadline above it never fires
  ([`a-clock-where-there-is-no-seam`](2026-09-05.a-clock-where-there-is-no-seam.completed.md)).
- Through the **agency's** sandbox, never the live job's. The walk is the
  session's cache, and refreshing it under a narrow plan would shrink it for
  every turn after; the narrowing belongs at the read, where `select` already
  applies it. Getting this backwards would have turned
  [`selection-at-the-gate`](2026-09-06.selection-at-the-gate.completed.md)'s
  per-turn narrowing into a permanent one.
- **The map is deliberately left alone.** It is the cached prefix, and a prefix
  rebuilt mid-session is not one — the precision run measured what losing prefix
  reuse costs (93% to 17.7%, 11.6× wall clock). A stale line number in the map
  is a number a reader follows by hand and finds off by four; a stale range in a
  fragment is *content* delivered as the definition. Different failures, and
  only the second one is silent.

### The honest bound, and what is not tested

- Same mtime tick **and** same length is not detected. Closing that means
  hashing every file every turn, which is the cost the stamp exists to avoid.
- The tests are at the walk: an edit pushes a definition down and the re-walk
  follows it; an unchanged file is not re-parsed; added and dropped files are
  counted; and the end-to-end one, which asserts that the **stale** walk hands
  back a fragment without the definition in it and the re-stamped walk does not.
  Nothing tests the `serve`/`stdio` wiring itself — a multi-turn session that
  edits a file and then asks about it would be the test that would have caught
  the original bug, and it does not exist yet.

### Still open, updated

- Everything above, minus the index, which is now a *no*.
- A multi-turn test at the `serve` seam, named above.
- Whether the map should re-render when the tree moves. The prefix argument says
  no by default; nothing has measured a session long enough for its map to be
  wrong in a way anybody noticed.
