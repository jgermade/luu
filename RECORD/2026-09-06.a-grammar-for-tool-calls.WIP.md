# A grammar for tool calls: which field, and what it costs to be told what to write

**Status:** a proposal, and the code it plans. Roadmap item 4 —
[*a GBNF grammar for tool calls*](../ROADMAP/2026-09-05/README.md) — carried
since [`open-after-pr-1`](2026-08-26.open-after-pr-1.completed.md) as a line in
five different "still ahead" lists and never argued. **It arrives here narrower
than it was ordered**, and that is this record's first claim.

## What the text parse actually costs, measured twice

[`the-gate-probe`](2026-08-31.the-gate-probe.completed.md), fifteen prompts
against `qwen2.5-coder:7b` at temperature 0, found the two halves pull apart:

````text
The format is not too hard for a 7B. 100% parseable plans at temperature 0.
[…] While planning was 100% compliant with the ```plan block, in turn execution
the unconstrained 7B produced ```write_file rather than
```tool {"name": "write_file", …}.
````

And [`runs/2026-09-06.precision/map.json`](runs/2026-09-06.precision/map.json),
question 1, is the same failure caught doing something worse. The whole reply,
one turn, abbreviated only where marked:

````text
The loop […] is typically found in the `run_agent_turn` function. […] look at the
`crates/agent-core/src/agent.rs` file […] ```tool {"name": "read_file",
"arguments": {"path": "crates/agent-core/src/agent.rs"}} ```The `run_agent_turn`
function is where the loop […] Here is the continuation of the `run_agent_turn`
function: ```rust let started = std::time::Instant::now(); let deadline =
limits.deadline(&call); let result = sandbox.execute_tool(…)  […]
                                                  (≈1 700 more characters)
````

The block is in the middle of the reply, against a preamble that says *end your
reply with a fenced block and nothing after it* — and then the model **writes the
tool's result itself**. `sandbox.execute_tool`, `ToolStep::new(call, result)`:
none of it exists. The parse is not what failed;
[`parse_call`](../crates/agent-core/src/tools/mod.rs#L341) reads that block
correctly. What failed is that generation did not stop, and roughly 1 700
characters of invented Rust were paid for, streamed to whoever was watching, and
stored in the turn.

That is the case for constraining: not *the block cannot be read*, but **the
model does not know when to stop writing**, and the fenced format has no way to
tell it. `parse_call`'s own doc comment already concedes the first half —

> it accepts […] a bare JSON object, because a 7B that has never seen a tool API
> drops the fence about a third of the time

— which is a text parse absorbing a format failure rather than a format that
holds.

## What it must not be pointed at

**The plan block.** Item 4 says "replace the text parse"; applied to the gate
that would be a mistake with an owner, and the same probe says why:

1. **It is not broken.** 100% parseable plans at temperature 0. A grammar would
   buy nothing measurable and cost a compile step per planning call.
2. **The failure is elsewhere.** *"Whenever the prompt explicitly stated a path
   […] the 7B correctly placed it. When the path was implicit […] the 7B left the
   lists empty or guessed Python defaults (`pytest`). This confirms that plan
   completeness is an indexing/relevance problem, not a grammar problem."* A
   grammar forcing `files` to be non-empty produces **invented paths**, checked
   against the policy file, refused at the gate — noise where the gate's whole
   value is signal.
3. **It would delete a measurement.**
   [`PlanSource::Prose`](../crates/agent-core/src/job.rs#L393) exists so that *a
   model that answered in prose* and *a model that declared nothing* are not the
   same row. Under a grammar the first is unreachable, and the gate's headline
   number — how often a small model produces a plan worth reading — loses its
   denominator.

So: **a grammar for tool calls, and the plan block stays as it is.** The roadmap
row is edited to say so, and the reasoning is here rather than there.

## Which field — and the lesson the window already taught

There is no single one. [`openai.rs`](../crates/agent-core/src/backend/openai.rs#L12)
opens with the rule this repository learned the expensive way, about the context
window:

> This API has no field for the window at all […] So `context_limit` is not sent
> — not because it does not matter, but because there is nowhere to put it that
> would not be a different number in a different field.

Constraints are the same shape, one step better: the field exists everywhere and
is different everywhere.

| server | endpoint we use | the field | what it accepts |
| --- | --- | --- | --- |
| `llama-server` | `/v1/chat/completions` | `response_format` | `json_object`, or a JSON schema |
| `llama-server` | `/completion`, `/v1/completions` | `grammar`, `json_schema` | **GBNF**, or a JSON schema |
| vLLM | `/v1/chat/completions` | `structured_outputs` (was `guided_grammar` / `guided_json`), via extra body | grammar, JSON schema, regex, choice |
| Ollama | `/api/chat` | `format` | `"json"`, or a JSON schema |
| mock | — | — | nothing; it ignores it |

**Read the second row against the first.** GBNF — the thing item 4 names — is on
the endpoints this project does *not* use. Through
`/v1/chat/completions`, where both real backends live today, what is available
is a **JSON schema**, and a JSON schema constrains a whole document.

That is the load-bearing consequence, and it is not a detail:

````text
what the preamble asks for:   <prose> ```tool {…} ```      or   <prose>
what a JSON schema gives:     {…}                          — always
what GBNF can express:        root ::= prose | prose call  — on /v1/completions
````

A `response_format` schema makes **every reply a tool call**, including the ones
that should be an answer — it deletes the second branch of the preamble. It is
usable only where the loop already knows a call is wanted, which it never does:
that is the thing the model is deciding. Getting the alternation instead means
`/v1/completions`, which means **applying the chat template here**, and the
template is currently the backend's business by an explicit decision
([`context.rs:105`](../crates/agent-core/src/context.rs#L105)):

> Special tokens are the chat template's business, and the template is applied by
> the backend where we cannot see it. That gap is accepted and reported rather
> than guessed at.

**So item 4 as ordered cannot be built without picking one of those two prices.**
Naming that is most of what this record is for.

## The proposal

1. **`CompletionRequest` carries a constraint, it does not format one.**
   `constraint: Option<Constraint>`, where `Constraint` is *what* to enforce — a
   JSON schema for one call, or the alternation — never a server's syntax. Each
   backend renders it into its own field **or declines**, and a backend that
   declines says so once, the way
   [`OpenAi::window_caveat`](../crates/agent-core/src/backend/openai.rs#L73)
   already does. A run that silently sent no constraint and a run that sent one
   must not look the same afterwards; that is the rule the window taught.
2. **The schema is compiled from `Tool::parameters()`**, which is already in the
   prompt verbatim (`luu tools` prints it) — one `oneOf` over the five
   `{name, arguments}` pairs. No second definition of a tool's shape; two would
   drift, and the drift would be invisible until a call was refused.
3. **Two arms, one flag apart, because they are two different bets:**
   - `--constrain schema` — `response_format` on the chat endpoint. Every reply
     is a call. Honest use: a *retry*. The first reply is free; if it drifted, the
     second is constrained. That is the only shape in which "always a call" is
     true by construction.
   - `--constrain grammar` — GBNF on `/v1/completions`, template applied here,
     alternation preserved. The one that answers item 4, and the one that costs
     a template.
4. **`luu tools --constrain grammar` prints the compiled grammar**, the way
   `luu map` and `luu select` print their exact bytes. A constraint nobody can
   read is a constraint nobody can argue with.

## What it costs

- **A template, or a branch.** Stated above; there is no third door through
  `/v1/chat/completions`.
- **A compile that can fail on our own schemas.** llama.cpp
  [#25923](https://github.com/ggml-org/llama.cpp/issues/25923): `{"type":
  "object", "properties": {}}` compiles to invalid GBNF (`"{" space space "}"`)
  and the server answers *failed to parse grammar* — and because every tool
  compiles into one grammar, **one bad schema fails every call**. Today
  `list_dir` is the closest: one property, `"required": []`. The first tool with
  no arguments trips it.
- **The prefix does not obviously get cheaper.** The tool block is ~470 tokens by
  the approximate counter, of which the JSON schemas are **~286** and the format
  preamble ~71. A server enforcing the shape makes some of that redundant — but
  the descriptions carry meaning a grammar cannot (*"Program name, which must be
  in the sandbox's allowed commands"*), and the block is **cached prefix**, so
  the saving is smallest exactly where it is easiest to measure. Cutting it is a
  separate change with its own measurement, not a bonus claimed here.
- **The mock backend cannot enforce anything.** Every scripted test stays valid
  and none of them tests this, so a `--constrain` run cannot be exercised with
  `--mock-reply`. The constrained path needs a real server in the loop or it is
  untested code.
- **A constrained model is a model that cannot say no.** The 32b run in
  [`the-size-sweep`](2026-09-03.the-size-sweep.completed.md) produced *"the
  provided repository map does not include a file specifically named…"* — the
  only two genuine declines the sweep produced, and both would be unreachable
  under a schema that must emit a call.

## What was rejected, and what was not

- **Rejected: a grammar for the plan block.** Three reasons, above.
- **Rejected: keeping the bare-object fallback under a grammar.** If the server
  enforces the shape, a parse that also accepts what the shape forbids is
  measuring the fallback, not the grammar. It stays for unconstrained runs and is
  bypassed under `--constrain`.
- **Not rejected: native function calling** (`tools:` / `tool_calls`, llama.cpp's
  `--jinja` templates). It is the real alternative and this record does not have
  the evidence to dismiss it. Against it: the format moves into the model's chat
  template, which differs per model and per server, is invisible to our token
  counting, and would put a second `ToolCall` shape in the tree — where
  [`tools/mod.rs:34`](../crates/agent-core/src/tools/mod.rs#L34) says the type is
  the interface *precisely so* the loop never learns which. For it: it is what
  the models were tuned on. It belongs as a **third arm**, measured, not as a
  paragraph here.

## The instrument, which does not exist

Coverage and precision both had a corpus before they had a result; this has
neither. `map-order-probe` measures which file reaches the prompt and says
nothing about calls. What is needed is small and this record does not build it:
**N prompts that each require exactly one call**, scored per reply on four
outcomes — *parsed* / *drifted* (the fenced `write_file` case) / *no call* / **
*continued past the fence*** — the fourth being the one the precision run found
by accident and the one no existing probe counts.

Without it, "the grammar helps" is a sentence. With it, it is the same
one-flag-apart division every other claim in this repository has had to survive.

## Still open

- **Whether `/v1/chat/completions` accepts a bare `grammar` field** on current
  `llama-server` builds as an undocumented extension. The README documents
  `response_format` there and `grammar` only on the completion endpoints. This is
  **one curl against a running server** and it decides whether the template
  question above is real or moot — it is the first thing to do and it is not
  done here.
- **Whether the retry shape is enough.** If constraining only the second attempt
  removes the drift, item 4 costs a branch instead of a template, and the whole
  argument about alternation becomes a paragraph nobody has to act on.
- **What a refused grammar does to a session.** A server that rejects the
  compiled grammar fails *every* call until the tool set changes. That wants the
  same treatment as a backend that cannot report usage — reported once, loudly,
  not per call.
- **Ollama's `format` with a JSON schema** is the same "every reply is a
  document" problem as `response_format`, and Ollama is the backend every model
  run in this repository has used. If only the grammar arm preserves the
  alternation, the arm that can be run on the machine the work happens on is the
  one that cannot answer the question.

## 2026-09-15, the envelope collapse: a schema change, tried

Closes the bullet directly above it — the fix named there and left "unbuilt
and untried" is now both.

**The proposal.** `run_command`'s parameters were `{command: string, args:
[string], cwd, timeout_ms}`. That pair — a name-shaped string beside an
argument list — is a call in its own right, structurally identical to the
`{name, arguments}` envelope every tool sits inside. Three times across three
machine-and-corpus combinations (the twelve-prompt 14B run and the
fifteen-prompt 14B run above, both on machine 4, and the 7B's official
fifteen from
[`the-tool-call-probe-run`](2026-09-14.the-tool-call-probe-run.completed.md)),
a model handed `run_command`'s own inner object straight to the top level,
with no `name` field and nothing to rescue it — the one collapse
`score_call`'s bare-object fallback cannot catch, because that fallback was
built for a model that drops the *fence*, not one that drops the *wrapper*.

The change: fold `command` and `args` into one `argv` array, program first —
`execve`'s own shape, and one that no longer has a lone string sitting where
a reader (model or otherwise) could mistake it for `name`. `cwd` and
`timeout_ms` are untouched; neither one reads as a call on its own.

```json
{"argv": ["cargo", "test", "-p", "agent-core", "score_call"]}
```

replaces

```json
{"command": "cargo", "args": ["test", "-p", "agent-core", "score_call"]}
```

**What it touched.** Not only [`command.rs`](../crates/agent-core/src/tools/command.rs)'s
own schema and `run()`. `job.rs`'s [`command_line`](../crates/agent-core/src/job.rs)
reads a step's arguments by the same key names to render the string
[`Plan::met_by`](../crates/agent-core/src/job.rs) matches a job's
`closes_on` against — the exact drift its own doc comment warns about
("two renderings of one command line would drift, and the day they drift a
task stops closing for a reason nobody can see") would have been *this*
change, silently, had `command_line` been left reading a key the schema no
longer sends. Six call sites needed the new shape: `command.rs`'s tests,
`job.rs`'s two, `context.rs`'s one, `agent.rs`'s one, and
`crates/luu/tests/serve_ws.rs`'s `runs()` mock-reply helper — the one that
exercises `closes_on` end to end over a live WebSocket, which is why it is
the test that would have caught the drift above if nothing else had. One
non-Rust site: `scripts/container-check.sh`, the level-3 CI script, carries
two hand-written `run_command` calls. `luu-design.md`'s one sentence
documenting the shape is rewritten, with a note for a reader who remembers
the old one. `cargo test --workspace`, `cargo clippy --workspace
--all-targets` (`-D warnings`) and `cargo fmt --all --check` are all clean
after.

**Measured the same way item 4's own number was**: the official fifteen
prompts, the real `score_call`, `qwen2.5-coder-14b`, same `llama-server`
process and settings as
[`runs/2026-09-15.14b-tool-call-probe/`](runs/2026-09-15.14b-tool-call-probe/),
one flag apart — the rebuilt binary and nothing else. Full transcripts and
reproduction steps in
[`runs/2026-09-15.14b-argv-schema/README.md`](runs/2026-09-15.14b-argv-schema/README.md).

| verdict | before (`command`/`args`) | after (`argv`) |
| --- | ---: | ---: |
| Parsed | 12 / 15 | 12 / 15 |
| Drifted | 0 / 15 | 0 / 15 |
| Continued past the fence | 2 / 15 | 3 / 15 |
| No call | 1 / 15 | 0 / 15 |

**The one `NoCall` — prompt 9's envelope collapse — is gone, and nothing new
broke.** The clean-call rate itself does not move (12/15 both times) because
prompt 9 did not become `Parsed`, it became `ContinuedPastFence`: the fence
closed with `{"name": "run_command", "arguments": {"argv": [...]}}`, correct
this time, and the model kept writing a sentence after it — the same
pre-existing habit prompts 4 and 14 already had, on the *first* call, before
and after this change alike. That is a real difference in kind and not a
wash: `NoCall` on the old schema meant `parse_call` — the function the
execution loop actually calls, which has the identical `name`-required
shape `score_call`'s fallback does — would not have run the tool at all;
`ContinuedPastFence` means the tool ran and the reply merely paid for a
sentence it did not need to. One is a functional miss, the other is waste
already tracked and already out of this record's scope (see "What the text
parse actually costs" at the top of this file).

**Stronger evidence than the table: the retry loops.** All three
`run_command` prompts (4, 9, 14) hit `--max-tool-steps` this run, the model
re-issuing a slightly reworded call eight times each after misreading its
own `cargo` exit codes (unrelated to format — see below) — 24 `run_command`
calls in this run alone, not 3. Every one of the 24 wrapped correctly,
`{"name": "run_command", "arguments": {"argv": [...]}}`, with zero
collapses. Against a defect that fired 3 times total across three prior
runs, 0/24 in a single run is a real sample, not a coincidence — though it
is one model, one machine, one seed, and the honest caveat from every
number in this record still applies: this does not prove the pattern is
gone, only that it did not fire here.

Two things found in passing, neither this section's business to fix, and
both already named by the section above as out of scope:

- **All three retry loops chased the same non-format ghost**: the model
  decided `--all`/`--workspace`/`-p` "must be a `rustup` flag" after the
  first `cargo` call exited 1, and spent its remaining steps re-issuing the
  identical correct command with cosmetic variations, never fixing anything
  because there was nothing wrong with the call. Exactly prompts 4 and 14's
  behavior in the prior run, now joined by 9. Not a parse failure — every
  one of the 24 calls parsed — and not this record's concern.
- **`cargo fmt --all --check` exited 1 inside the sandbox** on a tree where
  the same command exits 0 run directly from this shell, moments apart. The
  prior run hit the identical thing on the identical prompt and called it
  out as unchased; it still is. Worth someone's attention separately from
  either tool-call-format question this file asks.

## 2026-09-15, a second seed that was not one, and the 7B instead

**The "different seed" half of the bullet above turned out to be nothing.**
At `--temperature 0` decoding is greedy — there is no randomness for a seed
to seed — and a `--seed 13` re-run of
[`runs/2026-09-15.14b-argv-schema/`](runs/2026-09-15.14b-argv-schema/)
produced byte-identical replies to `--seed 7` on every prompt checked,
`run_command`'s three included. Not a second data point; deleted rather than
committed once that was confirmed, because keeping a run on disk that
proves nothing beyond "this project already knew temperature 0 is
deterministic" is noise. Worth writing down here so nobody re-tries it: a
genuine second sample at zero temperature needs a different **model**, not
a different seed.

**The 7B instead** — the model the collapse was first found on. Machine 4
has no Ollama (the original discovery's backend), so this is not that
combination repeated; it is `qwen2.5-coder-7b` over `llama-server`, same
machine and settings as every other argv-schema run today. Full transcripts
in
[`runs/2026-09-15.7b-argv-schema/README.md`](runs/2026-09-15.7b-argv-schema/README.md).

| verdict | count |
| --- | ---: |
| Parsed | 6 / 15 |
| Drifted | 6 / 15 |
| Continued past the fence | 1 / 15 |
| No call | 2 / 15 |

**Zero envelope collapses, and a completely different failure profile
otherwise.** 40% clean-call — higher than the original 3/15 = 20% on
Ollama — but dominated by `Drifted`: six replies fenced a call under the
tool's own bare name (` ```run_command `, ` ```list_dir `) instead of
` ```tool `, the exact 7B habit
[`the-gate-probe`](2026-08-31.the-gate-probe.completed.md) named at the top
of this file, at a much higher rate than the original run showed (2/15
there). That gap is almost certainly the backend, not the model:
`llama-server` and Ollama apply the chat template differently for the same
GGUF, and this record has no way to separate "different backend" from
"different day" from the comparison alone — which is exactly why it is
flagged rather than read as a number to trust.

**What does hold, cleanly, across the backend swap:** all three
`run_command` prompts (4, 9, 14) sent a correctly-shaped `{"argv": [...]}`
payload every time they attempted a call at all — two of them mistagged the
fence (`Drifted`, the pre-existing habit above), one wrapped and fenced
correctly (`Parsed`). None hoisted `argv`/`cwd` to the top level the way the
old `command`/`args` pair did. The defect this section is chasing did not
reappear on the model it was first found on, even under a backend that
otherwise made this model perform worse in an unrelated way.
