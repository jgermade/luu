# A grammar for tool calls: which field, and what it costs to be told what to write

**Status:** a proposal, and the code it plans. Roadmap item 4 —
[*a GBNF grammar for tool calls*](../ROADMAP/2026-09-05/README.md) — carried
since [`open-after-pr-1`](2026-08-26.open-after-pr-1.completed.md) as a line in
five different "still ahead" lists and never argued. **It arrives here narrower
than it was ordered**, and that is this record's first claim.

## What the text parse actually costs, measured twice

[`the-gate-probe`](2026-08-31.the-gate-probe.completed.md), fifteen prompts
against `qwen2.5-coder:7b` at temperature 0, found the two halves pull apart:

````text
The format is not too hard for a 7B. 100% parseable plans at temperature 0.
[…] While planning was 100% compliant with the ```plan block, in turn execution
the unconstrained 7B produced ```write_file rather than
```tool {"name": "write_file", …}.
````

And [`runs/2026-09-06.precision/map.json`](runs/2026-09-06.precision/map.json),
question 1, is the same failure caught doing something worse. The whole reply,
one turn, abbreviated only where marked:

````text
The loop […] is typically found in the `run_agent_turn` function. […] look at the
`crates/agent-core/src/agent.rs` file […] ```tool {"name": "read_file",
"arguments": {"path": "crates/agent-core/src/agent.rs"}} ```The `run_agent_turn`
function is where the loop […] Here is the continuation of the `run_agent_turn`
function: ```rust let started = std::time::Instant::now(); let deadline =
limits.deadline(&call); let result = sandbox.execute_tool(…)  […]
                                                  (≈1 700 more characters)
````

The block is in the middle of the reply, against a preamble that says *end your
reply with a fenced block and nothing after it* — and then the model **writes the
tool's result itself**. `sandbox.execute_tool`, `ToolStep::new(call, result)`:
none of it exists. The parse is not what failed;
[`parse_call`](../crates/agent-core/src/tools/mod.rs#L341) reads that block
correctly. What failed is that generation did not stop, and roughly 1 700
characters of invented Rust were paid for, streamed to whoever was watching, and
stored in the turn.

That is the case for constraining: not *the block cannot be read*, but **the
model does not know when to stop writing**, and the fenced format has no way to
tell it. `parse_call`'s own doc comment already concedes the first half —

> it accepts […] a bare JSON object, because a 7B that has never seen a tool API
> drops the fence about a third of the time

— which is a text parse absorbing a format failure rather than a format that
holds.

## What it must not be pointed at

**The plan block.** Item 4 says "replace the text parse"; applied to the gate
that would be a mistake with an owner, and the same probe says why:

1. **It is not broken.** 100% parseable plans at temperature 0. A grammar would
   buy nothing measurable and cost a compile step per planning call.
2. **The failure is elsewhere.** *"Whenever the prompt explicitly stated a path
   […] the 7B correctly placed it. When the path was implicit […] the 7B left the
   lists empty or guessed Python defaults (`pytest`). This confirms that plan
   completeness is an indexing/relevance problem, not a grammar problem."* A
   grammar forcing `files` to be non-empty produces **invented paths**, checked
   against the policy file, refused at the gate — noise where the gate's whole
   value is signal.
3. **It would delete a measurement.**
   [`PlanSource::Prose`](../crates/agent-core/src/job.rs#L393) exists so that *a
   model that answered in prose* and *a model that declared nothing* are not the
   same row. Under a grammar the first is unreachable, and the gate's headline
   number — how often a small model produces a plan worth reading — loses its
   denominator.

So: **a grammar for tool calls, and the plan block stays as it is.** The roadmap
row is edited to say so, and the reasoning is here rather than there.

## Which field — and the lesson the window already taught

There is no single one. [`openai.rs`](../crates/agent-core/src/backend/openai.rs#L12)
opens with the rule this repository learned the expensive way, about the context
window:

> This API has no field for the window at all […] So `context_limit` is not sent
> — not because it does not matter, but because there is nowhere to put it that
> would not be a different number in a different field.

Constraints are the same shape, one step better: the field exists everywhere and
is different everywhere.

| server | endpoint we use | the field | what it accepts |
| --- | --- | --- | --- |
| `llama-server` | `/v1/chat/completions` | `response_format` | `json_object`, or a JSON schema |
| `llama-server` | `/completion`, `/v1/completions` | `grammar`, `json_schema` | **GBNF**, or a JSON schema |
| vLLM | `/v1/chat/completions` | `structured_outputs` (was `guided_grammar` / `guided_json`), via extra body | grammar, JSON schema, regex, choice |
| Ollama | `/api/chat` | `format` | `"json"`, or a JSON schema |
| mock | — | — | nothing; it ignores it |

**Read the second row against the first.** GBNF — the thing item 4 names — is on
the endpoints this project does *not* use. Through
`/v1/chat/completions`, where both real backends live today, what is available
is a **JSON schema**, and a JSON schema constrains a whole document.

That is the load-bearing consequence, and it is not a detail:

````text
what the preamble asks for:   <prose> ```tool {…} ```      or   <prose>
what a JSON schema gives:     {…}                          — always
what GBNF can express:        root ::= prose | prose call  — on /v1/completions
````

A `response_format` schema makes **every reply a tool call**, including the ones
that should be an answer — it deletes the second branch of the preamble. It is
usable only where the loop already knows a call is wanted, which it never does:
that is the thing the model is deciding. Getting the alternation instead means
`/v1/completions`, which means **applying the chat template here**, and the
template is currently the backend's business by an explicit decision
([`context.rs:105`](../crates/agent-core/src/context.rs#L105)):

> Special tokens are the chat template's business, and the template is applied by
> the backend where we cannot see it. That gap is accepted and reported rather
> than guessed at.

**So item 4 as ordered cannot be built without picking one of those two prices.**
Naming that is most of what this record is for.

## The proposal

1. **`CompletionRequest` carries a constraint, it does not format one.**
   `constraint: Option<Constraint>`, where `Constraint` is *what* to enforce — a
   JSON schema for one call, or the alternation — never a server's syntax. Each
   backend renders it into its own field **or declines**, and a backend that
   declines says so once, the way
   [`OpenAi::window_caveat`](../crates/agent-core/src/backend/openai.rs#L73)
   already does. A run that silently sent no constraint and a run that sent one
   must not look the same afterwards; that is the rule the window taught.
2. **The schema is compiled from `Tool::parameters()`**, which is already in the
   prompt verbatim (`luu tools` prints it) — one `oneOf` over the five
   `{name, arguments}` pairs. No second definition of a tool's shape; two would
   drift, and the drift would be invisible until a call was refused.
3. **Two arms, one flag apart, because they are two different bets:**
   - `--constrain schema` — `response_format` on the chat endpoint. Every reply
     is a call. Honest use: a *retry*. The first reply is free; if it drifted, the
     second is constrained. That is the only shape in which "always a call" is
     true by construction.
   - `--constrain grammar` — GBNF on `/v1/completions`, template applied here,
     alternation preserved. The one that answers item 4, and the one that costs
     a template.
4. **`luu tools --constrain grammar` prints the compiled grammar**, the way
   `luu map` and `luu select` print their exact bytes. A constraint nobody can
   read is a constraint nobody can argue with.

## What it costs

- **A template, or a branch.** Stated above; there is no third door through
  `/v1/chat/completions`.
- **A compile that can fail on our own schemas.** llama.cpp
  [#25923](https://github.com/ggml-org/llama.cpp/issues/25923): `{"type":
  "object", "properties": {}}` compiles to invalid GBNF (`"{" space space "}"`)
  and the server answers *failed to parse grammar* — and because every tool
  compiles into one grammar, **one bad schema fails every call**. Today
  `list_dir` is the closest: one property, `"required": []`. The first tool with
  no arguments trips it.
- **The prefix does not obviously get cheaper.** The tool block is ~470 tokens by
  the approximate counter, of which the JSON schemas are **~286** and the format
  preamble ~71. A server enforcing the shape makes some of that redundant — but
  the descriptions carry meaning a grammar cannot (*"Program name, which must be
  in the sandbox's allowed commands"*), and the block is **cached prefix**, so
  the saving is smallest exactly where it is easiest to measure. Cutting it is a
  separate change with its own measurement, not a bonus claimed here.
- **The mock backend cannot enforce anything.** Every scripted test stays valid
  and none of them tests this, so a `--constrain` run cannot be exercised with
  `--mock-reply`. The constrained path needs a real server in the loop or it is
  untested code.
- **A constrained model is a model that cannot say no.** The 32b run in
  [`the-size-sweep`](2026-09-03.the-size-sweep.completed.md) produced *"the
  provided repository map does not include a file specifically named…"* — the
  only two genuine declines the sweep produced, and both would be unreachable
  under a schema that must emit a call.

## What was rejected, and what was not

- **Rejected: a grammar for the plan block.** Three reasons, above.
- **Rejected: keeping the bare-object fallback under a grammar.** If the server
  enforces the shape, a parse that also accepts what the shape forbids is
  measuring the fallback, not the grammar. It stays for unconstrained runs and is
  bypassed under `--constrain`.
- **Not rejected: native function calling** (`tools:` / `tool_calls`, llama.cpp's
  `--jinja` templates). It is the real alternative and this record does not have
  the evidence to dismiss it. Against it: the format moves into the model's chat
  template, which differs per model and per server, is invisible to our token
  counting, and would put a second `ToolCall` shape in the tree — where
  [`tools/mod.rs:34`](../crates/agent-core/src/tools/mod.rs#L34) says the type is
  the interface *precisely so* the loop never learns which. For it: it is what
  the models were tuned on. It belongs as a **third arm**, measured, not as a
  paragraph here.

## The instrument, which does not exist

Coverage and precision both had a corpus before they had a result; this has
neither. `map-order-probe` measures which file reaches the prompt and says
nothing about calls. What is needed is small and this record does not build it:
**N prompts that each require exactly one call**, scored per reply on four
outcomes — *parsed* / *drifted* (the fenced `write_file` case) / *no call* / **
*continued past the fence*** — the fourth being the one the precision run found
by accident and the one no existing probe counts.

Without it, "the grammar helps" is a sentence. With it, it is the same
one-flag-apart division every other claim in this repository has had to survive.

## Still open

- **Whether `/v1/chat/completions` accepts a bare `grammar` field** on current
  `llama-server` builds as an undocumented extension. The README documents
  `response_format` there and `grammar` only on the completion endpoints. This is
  **one curl against a running server** and it decides whether the template
  question above is real or moot — it is the first thing to do and it is not
  done here.
- **Whether the retry shape is enough.** If constraining only the second attempt
  removes the drift, item 4 costs a branch instead of a template, and the whole
  argument about alternation becomes a paragraph nobody has to act on.
- **What a refused grammar does to a session.** A server that rejects the
  compiled grammar fails *every* call until the tool set changes. That wants the
  same treatment as a backend that cannot report usage — reported once, loudly,
  not per call.
- **Ollama's `format` with a JSON schema** is the same "every reply is a
  document" problem as `response_format`, and Ollama is the backend every model
  run in this repository has used. If only the grammar arm preserves the
  alternation, the arm that can be run on the machine the work happens on is the
  one that cannot answer the question.

## 2026-09-15, the envelope collapse: a schema change, tried

Closes the bullet directly above it — the fix named there and left "unbuilt
and untried" is now both.

**The proposal.** `run_command`'s parameters were `{command: string, args:
[string], cwd, timeout_ms}`. That pair — a name-shaped string beside an
argument list — is a call in its own right, structurally identical to the
`{name, arguments}` envelope every tool sits inside. Three times across three
machine-and-corpus combinations (the twelve-prompt 14B run and the
fifteen-prompt 14B run above, both on machine 4, and the 7B's official
fifteen from
[`the-tool-call-probe-run`](2026-09-14.the-tool-call-probe-run.completed.md)),
a model handed `run_command`'s own inner object straight to the top level,
with no `name` field and nothing to rescue it — the one collapse
`score_call`'s bare-object fallback cannot catch, because that fallback was
built for a model that drops the *fence*, not one that drops the *wrapper*.

The change: fold `command` and `args` into one `argv` array, program first —
`execve`'s own shape, and one that no longer has a lone string sitting where
a reader (model or otherwise) could mistake it for `name`. `cwd` and
`timeout_ms` are untouched; neither one reads as a call on its own.

```json
{"argv": ["cargo", "test", "-p", "agent-core", "score_call"]}
```

replaces

```json
{"command": "cargo", "args": ["test", "-p", "agent-core", "score_call"]}
```

**What it touched.** Not only [`command.rs`](../crates/agent-core/src/tools/command.rs)'s

## 2026-09-15, the retry shape, built

Closes the bullet directly above about `--constrain schema`'s retry shape,
named unbuilt in this file's own §The proposal and again in
[`what-constrain-does`](2026-09-14.what-constrain-does.completed.md)'s "what
is still open": *send an unconstrained first attempt, and only on a drifted
verdict retry once under `Constraint::Schema`.*

**What was built.** `agent_core::agent::SchemaRetry { schema, tool_names }`,
threaded through `run_agent_turn` as a new parameter
(`#[allow(clippy::too_many_arguments)]`, the same escape hatch three other
functions in this codebase already use rather than a struct invented to
dodge a lint). Inside the loop, after an unconstrained model call: if
`parse_call` fails **and** `score_call` on the same text calls it
`Drifted` — fenced under a tool's own name, the exact shape this file has
tracked since its opening section — the loop announces a second
`ModelCall` for the same step and re-issues the request with
`constraint: Some(Constraint::Schema(retry.schema.clone()))`. A `NoCall`
verdict is never retried: a schema forces a call every time, and forcing
one where the model made a clean decision not to call is the "a
constrained model cannot say no" cost this file named as a risk before any
of this was measured. The CLI wiring changes to match: `--constrain schema`
no longer becomes the per-step `constraint` every call in the turn carries
(the always-on behaviour `what-constrain-does` measured never answering a
single prompt) — it is built once into a `SchemaRetry` and spent only where
`run_agent_turn` decides it should be. `--constrain grammar` is unchanged,
because it was already honestly a first-attempt constraint. Two new unit
tests in `agent.rs` drive a `Scripted` backend through both branches: a
drifted-then-recovered call executes exactly once (not twice), and a clean
decline is never retried at all — `cargo test`, no model required, the same
proof-without-a-model shape `tool_call_probe.rs`'s own doc names.

**Measured against a real model, and the instrument had a blind spot worth
naming.** `qwen2.5-coder-7b` over `llama-server`
([`runs/2026-09-15.7b-schema-retry/`](runs/2026-09-15.7b-schema-retry/)) —
the model with `Drifted` replies to retry against, unlike the 14B
([`runs/2026-09-15.14b-schema-retry/`](runs/2026-09-15.14b-schema-retry/)),
which parses 12/15 clean unconstrained and so never exercises the retry at
all (a genuine negative result, kept for the record: `--constrain schema`
costs nothing where there is nothing to retry). `score_call`, run against
the probe's own extraction script the way every prior measurement here has
been scored, reported **the identical 6/15 Drifted** the unconstrained
baseline shows — which looked, before checking further, like the retry did
nothing. It is not that: the extraction script concatenates every `token`
event for the turn with no marker between one model call and the next
(`TurnEvent::ModelCall` exists and fires before the retry, exactly as it
does before the first attempt, but is deliberately not written into the
recording), so a drifted-then-recovered reply reads as one string — the
drifted fence immediately followed by the retry's bare, unfenced JSON —
and `score_call`'s own `Drifted` check matches the first half of that
string. True of the string, false of what happened. See
[`runs/2026-09-15.7b-schema-retry/README.md`](runs/2026-09-15.7b-schema-retry/README.md)
for the exact text.

**Read from execution instead — did the first attempt's model call
actually run a tool — and the real number is 7/15 → 13/15.** Every one of
the six `Drifted` prompts (02, 04, 05, 07, 09, 12) went from *no tool ever
touched* (the unconstrained turn returns the malformed fence as its final
answer, because `parse_call` can't read it and the loop has no second
attempt) to a correctly-shaped call executed on the first real attempt,
`argv` and all — 6/6 recovered, 0 retries that themselves failed to parse.
The two genuine declines (01, 10) are untouched, which is the design
working as intended, not a miss. No new failure mode: four prompts still
end `[tool limit reached]`, but three of those four are newly-retried
prompts guessing at `cargo` flag orderings after a real `exit 1` — the same
"correct call, wrong troubleshooting" pattern already named for the 14B —
so reaching the step limit while actually working the problem is strictly
more progress than the unconstrained turn's zero attempts. And no
reproduction of the always-on arm's own failure: `what-constrain-does`
found every one of fifteen prompts ending `[tool limit reached]` after
eight identical calls; here 11/15 end `[stop]`.

### Still open, updated an eighth time

- **The tool-call probe's own instrument cannot see a retry.** `score_call`
  and `.tmp/extract_first_reply.py` were built for one model call per
  prompt; a retried reply's text is the concatenation of two calls with no
  boundary between them, and no existing verdict category describes that

  this file's own versioning rule prices as a bump) for a debug-instrument

- Why the two Ollama-registry builds cut opposite ways on the 7B and 14B is
  still unexplained, per the section above this one.
- **What a refused grammar (or a refused schema) does to a session**
  remains untouched — nothing measured here or before has hit a server
  that rejects the compiled constraint outright.
- **`serve` and `stdio` still have no `--constrain`** — `SchemaRetry` is
  `chat`-only, same as the constraint it replaces.

## 2026-09-15, what a refused retry does to a turn, fixed for the one case that exists

Narrows the bullet directly above, rather than closing it. Before this
section, a refused retry (`retried.error.is_some()` in `run_agent_turn`)
was treated exactly like any other backend failure: `TurnEvent::Failed`,
the pre-retry answer discarded, the turn ends in error — even though the
turn already had a real reply, the drifted one the retry was trying to
improve on. That is a real defect, found by writing the test for it rather
than by hitting it against a server (no backend measured in this project
has ever actually refused a compiled schema or grammar; llama.cpp
[#25923](https://github.com/ggml-org/llama.cpp/issues/25923) needs a tool
with an empty `properties` object to trigger, and `list_dir` — "the
closest" per this file's own §What it costs — has one property and
`"required": []`, not an empty `properties`, so it has never actually
tripped it).

**The fix**: on `retried.error.is_some()`, fall back to the pre-retry
`outcome` instead of failing the turn — the ordinary `parse_call` check a
few lines below already knows what to do with a drifted reply that never
got fixed, which is exactly the state a refused retry leaves the turn in.
A genuine cancel (`EndReason::Cancelled`) is unchanged: that is the caller
stopping the turn on purpose, not a fallback case. One new test,
`a_refused_retry_falls_back_to_the_drifted_answer_instead_of_failing_the_turn`,
with a new two-call scripted backend (`DriftThenRefuse`) whose second call
returns `BackendError::Rejected` — asserts the turn ends without an error
and with the original drifted text intact, not empty and not failed.

**What this does not close.** "Reported once, loudly, not per call" — this
file's own words for the fix, from before any of it was built — is still
two claims, and only the first is true now: the turn survives (falls back
cleanly) rather than failing, but nothing *reports* that it happened. A
session that hits this on every drifted prompt gets silent degraded
answers, not a loud note the way `constrain_caveat` prints one for a known
incompatibility at startup — this is a *runtime* rejection, discovered per
constraint compile rather than known in advance, and giving it the same
treatment needs either a new field on `AgentOutcome` the CLI prints from or
a new `TurnEvent` variant kept out of the wire protocol the way
`ModelCall` already is. Neither is built here. And the scenario itself
remains unreproduced against a real server — this section closes the "the
turn loses data" defect the design already anticipated, not the "does this
actually happen" question, which stays exactly as open as it was.

### Still open, updated a ninth time

- **A refused retry is silent.** The turn no longer loses its answer, but
  nothing tells anyone a constraint got rejected — no loud, once note the
  way a known-incompatible backend gets one at startup. Needs a field or a
  CLI-only event; not built.
- Whether any real server actually refuses this project's compiled schema
  or grammar remains unreproduced — `list_dir`'s empty-`required`,
  one-property shape has never tripped the llama.cpp bug this file names.
- Why the two Ollama-registry builds cut opposite ways on the 7B and 14B is
  still unexplained.
- **`serve` and `stdio` still have no `--constrain`.**
- **The tool-call probe's own instrument still cannot see a retry** — see
  the eighth update above; unchanged by this section.

## 2026-09-15, the zero-properties tool: reproduced, and it does not fail

Narrows the bullet directly above about a real refusal being unreproduced.
No tool in this project has ever had literally zero properties — `list_dir`
is "one property, `required: []`", not `"properties": {}` — so llama.cpp
[#25923](https://github.com/ggml-org/llama.cpp/issues/25923), the reason
this file's own §What it costs named a zero-argument tool as a risk
("today `list_dir` is the closest... the first tool with no arguments trips
it"), has never actually had a tool shaped to trigger it. Built one — not in
the real tool set, a throwaway `Tool` impl in a `cargo run --example`,
deleted after use, same as `stats.json`'s own scoring method elsewhere in
this file — and ran both arms against it, machine 4, `llama-server` build
`b10809` (`0.4.0-dev`, current on this machine, not whatever build #25923
was filed against).

**The schema arm.** `Tools::call_schema()`'s own shape
(`{"oneOf": [{"name": {"const": "no_args_tool"}, "arguments": {"type":
"object", "properties": {}, "required": []}}]}`) sent as
`response_format.json_schema` to `/v1/chat/completions`: **200, not 400** —
`{"name": "no_args_tool", "arguments": {}}`, correctly shaped, first try.

**The grammar arm.** `agent_core::grammar::compile` on the same
zero-property tool does not produce the malformed
`no-args-tool-arguments ::= "{" space space "}"` #25923 describes for
llama.cpp's own JSON-schema-to-grammar converter — this project's own
from-scratch compiler emits `no-args-tool-arguments ::= "{" ws empty ws
"}"`, `empty` being the same named rule every other object shape already
shares. Sent as the bare `grammar` field
([`the-bare-grammar-field`](2026-09-14.the-bare-grammar-field.completed.md)'s
own path): **200, not 400.** The model didn't take the call (plain prose,
`finish_reason: length` — valid under the alternation, which permits any
text that never opens a `` ```tool `` fence, so a decline is not a grammar
violation), but the server accepted and enforced the grammar without
complaint — the same record's own "invalid GBNF" probe already showed this
exact server *does* return `400 failed to parse grammar` when the grammar
actually is broken, so this is a real accept, not a field silently ignored.

**What this narrows, and what it does not.** The specific mechanism this
file worried about — this project's own compiled constraint failing to
parse on a zero-argument tool — does not reproduce on the one server this
project measures against, on either arm. That is evidence about *this

## 2026-09-15, a refused retry stops being silent: `TurnEvent::ConstraintRefused`

Closes the "refused constraint fails silently instead of loudly" question,
open since the ninth update. "What this does not close" from that update
named the exact shape needed — "a field or a CLI-only event" — and named the

is only assembled at a turn's return points, and the fallback does not
return, it keeps looping, so a field would have to survive being threaded
through every iteration for a fact that happens once. An event fits the
shape the loop already has for exactly this — "debug data that explains the
agent rather than driving it."

be a bare `Some(_) => outcome`). `protocol.rs::from_turn_event` answers

`chat`'s printer task and `serve`'s forwarder task each gained one arm,
`eprintln!("note: a constrained retry was refused: {error}")`, mirroring
`constrain_caveat`'s own startup note rather than inventing a second style.

against one made before this existed should not diff on a note neither one
asked for.

## 2026-09-15, the tool-call probe's own instrument can see a retry now

Closes the bullet carried since the eighth update. The root cause was one
field doing two jobs: `TurnEvent::ModelCall`'s `step` counts *tool-loop*
steps, and the interceptors in `chat` and `serve` both used `step > 1` as a
proxy for "a second call worth measuring into the `StepCall` chain." A
schema retry's own extra call shares `step` with the attempt it retries —
by design, it is not a new tool-loop step — so it always read as `step ==
1` and the proxy silently excluded it. That is exactly what the eighth
update named and what every schema-retry run made today, real model
included, was blind to.

The fix does not touch the wire or the record format: `TurnEvent` carries no
`serde` derive and is never serialized, so adding `retry: bool` to
`ModelCall` costs nothing versioned — the format-bump the tenth update's own
text guessed this would need turns out not to be required, because the
*consumer* of the new field (`TraceMessage::StepCall`) already existed at
record format 10 and only needed a wider trigger. `run_agent_turn` sets it
`false` on the ordinary per-step call and `true` on `SchemaRetry`'s own
extra one; both interceptors' condition changed from `*step > 1` to `*step >
1 || *retry`. A retry's call now measures against the same
`PrefixTracker` chain a tool-loop's second call already did — correctly:
the retry resends the same `messages`, only `constraint` differs, so it
shares the full text of the attempt it retries and the chain records that as
the near-total overlap it is.

New test, `serve.rs`:
`a_schema_retry_reaches_the_step_call_chain_even_at_step_one` drives a real
drift-then-retry through `start_turn` on a scripted `Mock` backend (fenced
under the tool's own bare name, scored `Drifted`, then a plain-prose retry
reply) and asserts a `TraceMessage::StepCall { step: 1, .. }` lands on
`app.events`. `agent.rs`'s own exhaustive match on `TurnEvent::ModelCall`
(the one counting calls per round trip) and `protocol.rs`'s construction
test both updated for the new field; nothing else in either crate matched
`ModelCall` by name.

## 2026-09-15, why the two Ollama-registry builds cut opposite ways: they were never the same question

Closes the bullet carried since "the 14B's two-GGUF check" section. Read all
four GGUF files' headers directly — no model call, no third-party `gguf`
package installed on this machine, so
[`runs/2026-09-15.gguf-provenance/gguf_diff.py`](runs/2026-09-15.gguf-provenance/gguf_diff.py)
parses the documented binary layout by hand. Full output and exact paths in
[`runs/2026-09-15.gguf-provenance/README.md`](runs/2026-09-15.gguf-provenance/README.md).

**Both pairs share one real, minor finding: same nominal Q4_K_M, not the
same actual quantization.** Identical tensor-type histograms (7B: 169
`Q4_K`/141 `F32`/29 `Q6_K` of 339 tensors both files; 14B: 289/241/49 of 579
both files) but 16 of 339 (7B) and 14 of 579 (14B) tensors — always
`attn_v.weight` or `ffn_down.weight`, always in the earlier blocks — disagree
on which of `Q4_K`/`Q6_K` they got, always as a straight swap. `llama-quantize
--help` on this machine documents `--imatrix` as exactly the input that
steers this choice in llama.cpp's `*_M` mixtures. Consistent with a
different (or absent) importance matrix between two independent
quantization runs of the same source — not proof, since neither imatrix
file is available to compare directly.

**That minor finding is not the answer, and chasing it further would have
been chasing the wrong thing.** The provenance metadata each file carries
answers a bigger question first: **the two pairs are not two instances of
the same phenomenon.**

- **7B**: local file's `general.finetune = "Instruct-GGUF"`, no
  `base_model`/`license`/`tags` block — a third-party repack with the
  source repo's own card stripped. Registry file: clean
  `general.base_model.0.repo_url =
  https://huggingface.co/Qwen/Qwen2.5-Coder-7B`, full license and tags — a
  conversion that kept the upstream card. Two independent single
  fp16-to-GGUF conversions, differing only in the imatrix-shaped way above.
- **14B**: local file's `general.finetune = "Instruct-AWQ"`, `general.name
  = "Qwen2.5 Coder 14B Instruct AWQ"` — this file's own metadata says its
  source was already 4-bit AWQ-quantized before being converted and
  requantized to Q4_K_M. **Every 14B `llama-server` run in this project's
  records, including today's, ran a twice-quantized model.** The registry
  file carries no `-AWQ` anywhere and the same clean `base_model.0.repo_url`
  shape the 7B registry pull has.

**So "why opposite directions" had a false premise: it is not one
mechanism cutting two ways, it is two different comparisons that happened to
share a headline.** The 14B's registry-wins result is explained outright by
an unambiguous handicap on the losing side — double quantization, not a
subtle recipe difference. The 7B's local-wins result has no such handicap on
either side; its two files are both ordinary single conversions that merely
picked a different `Q6_K` subset, and nothing gathered here says which
imatrix (if either run used one) was better calibrated.

`qwen2.context_length` also differs in both pairs (131072 local, 32768
registry) but every tool-call-probe run used `--ctx-size 8192`, inside both
figures, so this is a provenance detail — which of Qwen's own advertised
numbers each converter wrote down — not a runtime one.
