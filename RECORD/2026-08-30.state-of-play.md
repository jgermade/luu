# Where this stands, and what is waiting on what

**Status:** stock-taking, not a proposal. Nothing here decides anything — it
gathers what the ten files before it left open, says which of those questions
today's two commits answered, and puts the rest in the order their preconditions
allow.

It exists because the open questions had scattered: ten records, most ending in
their own *Still open* table, and no single place that says what is actually
next.
[`loude-design.md`](../loude-design.md) is still the current answer to *what is
true today* and this file does not compete with it — this one is dated, and will
read as history the moment something below lands.

## What landed today

Two commits, and one measurement worth keeping in front of everything else.

**Tasks in code.** `Task`, `Plan`, the lifecycle, and the fold: a closed task's
turns stay in the history and stop being rendered, replaced by a deterministic
summary made of the approved plan and what the tool results reported. Closing is
an event, so reopening is folding differently rather than undoing a deletion.
Eviction moved from turns to items, so a folded task is kept or dropped whole.
See [`2026-08-30.tasks-in-code.md`](2026-08-30.tasks-in-code.md).

**The gate.** A prompt with no task open buys one planning call, and is then held
on the server — unrun — until a person approves or refuses it. Nothing runs
behind it. The planning call has no tools, because a planning call that could
execute something would be the gate leaking. A model that answers in prose does
not cost the gate: the ask becomes the objective and the panel says nothing was
declared. See [`2026-08-30.the-gate.md`](2026-08-30.the-gate.md).

**The number**, twenty prompts, 1024-token window, one boundary apart:

| Run | Mean reuse | Worst turn | Prompt tokens |
| --- | ---: | ---: | ---: |
| no tasks, `--evict turn` | 69.9% | 47.5% | 16 715 |
| no tasks, `--evict block` | 89.9% | 65.7% | 15 495 |
| four tasks | **91.3%** | **87.6%** | **13 417** |

With tasks, `--evict turn` and `--evict block` produced byte-identical prompts:
eviction never fired, because the folded history never grew enough to need it.

**And one thing the instrument was getting wrong.** The recorded eviction pair
had been degenerate since the commit that added tools: the definitions are 465
tokens, so at the 512-token window the fixtures used, the fixed part of the
prompt filled the window and no history was ever retained. Two files showing an
empty history bucket, read as a comparison of eviction policies. The fixtures
record at 1024 now. Nothing said so, and nothing could — which is the argument
for the next item in the list below.

## Pending, grouped by what is actually blocking it

### Blocked on nothing, and overdue

- **Eviction as a recorded event.** Asked for in
  [`cline-openhands`](2026-08-27.cline-openhands.md) with the precondition
  *"nothing — it is small, and the gap is already visible"*, repeated in
  [`tasks-in-code`](2026-08-30.tasks-in-code.md) as *"still nothing; still
  small"*. It is the oldest unpaid debt in the repo: a recording still cannot say
  what a session forgot, only that its history got shorter. The degenerate
  fixtures above are exactly the class of thing a tombstone would have made
  visible.
- **Reading the context window from the backend**, instead of `--context-limit`
  being a flag someone has to remember to set correctly.
- **Sessions in SQLite.** Nothing is persisted; `serve` loses the conversation on
  restart. The decision already taken is that it must be *derivable from the
  event stream*, not a second truth beside it — see the persistence section of
  [`context-manager`](2026-08-27.context-manager.md).

### Unblocked by today, and next in line

- **The approved plan narrowing the sandbox for its task**, with the policy file
  as its floor. This is the design's own commitment and the last structural piece
  of step 4. It was blocked on there being a human who could widen a plan that
  forgot a file; that human now exists.
- **A plan that distinguishes what it will read from what it will write.** Today
  the check asks only whether a file is readable, so a write into a read-only
  root passes the gate and is denied at the call — the one case the check exists
  to catch and misses.
- **Relevance selection over a `tree-sitter` reference graph.** Unblocked since
  tools landed. The [`aider`](2026-08-27.aider-repo-map.md) record's own addendum
  corrects its cost estimate: every `tree-sitter-*` crate exports its tags query
  as a `pub const`, so there is nothing to vendor and nothing to write.
- **Pruning tool results** out of the history, which now has results in it to
  prune and a bucket to watch shrink.

### Waiting on a real model, which is most of the list

Nine open questions across five records share one precondition, and it is the
same one: **everything measured so far is against a mock backend that does not
read its context.** It can validate prompt shape and cache reuse, and it can
never say whether a shorter history costs an answer. Running the same scripts
against Ollama with Qwen2.5-Coder is the cheapest single thing that turns this
whole block from open into answerable:

| Question | Record |
| --- | --- |
| Can a 7B write a summary worth freezing into the prefix, or does deterministic stay the only safe answer? | cline-openhands, tasks-instead-of-modes |
| Does the fold cost task success — what did those 3 298 saved tokens contain? | prefix-reuse addendum |
| Does the reuse become *time*? (llama.cpp with a real prompt cache, measured in seconds) | prefix-reuse addendum |
| Does the planning call produce a plan worth reading, or prose every time? | the-gate |
| Does the boundary still beat the threshold when tasks carry real tool work? | tasks-in-code |
| Does resurrection ever fire under `Turn` on a real session? | prefix-reuse |
| Judge accuracy against the user's own verdict (needs thirty closed tasks first) | tasks-instead-of-modes |
| Is the low-water knee at 0.9 sharp or gradual, and does it move with turn size? | prefix-reuse addendum |
| Does the reference-graph signal survive a model that names identifiers less reliably than a frontier one? | aider-repo-map |

### Security debts, named and unpaid

- **`openat2(RESOLVE_BENEATH)`** for the in-process tools, closing the TOCTOU
  window that canonicalize-then-open leaves.
- **Level 3**, the container, with the level-2 restrictions still applied inside
  it.
- **Auth**, if `serve` is ever bound off-loopback. Out of scope by assertion
  today, which is fine until it isn't — it exposes an agent that runs commands.

### Smaller, and honest about being small

- **Native function calling and a GBNF grammar**, replacing the text parse for
  both tool calls and plan blocks.
- **A reason on a rejection**, so the agent can propose again in its light rather
  than the user retyping.
- **Sub-tasks and nesting.** Deliberately not now: one level until one level
  demonstrably hurts.
- **The CLI has no gate.** `luu chat "prompt"` runs with the policy file as the
  standing approval, because a one-shot has no human loop. Whether it should grow
  one, or stay the scripted surface it is, is undecided.

## What I would do next, and why

**Narrowing, then a real model.** In that order, and not the other way round.

Narrowing is the only item that is both structurally load-bearing and blocked on
nothing any more — it closes step 4, it is the design's own sentence
(*the approved plan **is** the `SandboxPolicy` for that task*), and every day it
stays open the gate is a confirmation of something that is not actually enforced.
It is also small: the plan already exists as a typed thing and is already checked
against the policy.

The real-model run is bigger in value and larger in scope, and it wants the
narrowing done first for a plain reason: the first thing a real 7B will do is
propose plans that forget files. That is the workload narrowing has to survive,
and discovering it with narrowing already in place is one experiment instead of
two.
