**Status:** a proposal, and the UI it plans.

Item 10 of [`ROADMAP/2026-09-17`](../ROADMAP/2026-09-17/README.md), left open by

## The problem

Three fields of a plan are on the protocol, signed by
[`Approval::canonical`](../crates/agent-core/src/approval.rs), bounded by
[`Plan::unmet`](../crates/agent-core/src/job.rs) and reachable from a script:

```rust
// crates/agent-core/src/protocol.rs — ClientMessage::ApproveJob
network: Option<bool>,
enforcement: Option<crate::sandbox::Enforcement>,
egress: Option<Vec<String>>,
```

The page sends four things and none of them is one of those three:

```js
// crates/luu/ui/store.js
export function approveJob(job, files = [], writes = [], commands = [], closesOn = "") {
  socket.send(JSON.stringify({
    type: "approve_job", job, files, writes, commands,
    closes_on: closesOn.trim() || null,
  }))
}
```

So a person at the only surface that actually approves anything can widen a plan
with a file and can neither grant it the network, nor pin its egress to two
domains, nor demand the kernel hold its children. **A narrowing nobody can reach
from the surface they use is a narrowing nobody applies** — which is the whole
of the row, and is why it sits next to item 9: item 9 was a grant outliving the
posture it was approved under, this is a grant nobody can express in the first
place.

**The half that is worse, and it is not in the row.** The gate does not *show*
the three either:

```html
<p :if="proposed?.plan.files.length" class="dim">reads: …</p>
<p :if="proposed?.plan.writes.length" class="dim warn">writes: …</p>
<p :if="proposed?.plan.commands.length" class="dim">commands: …</p>
```

A model that writes `"network": true` into its plan block gets it approved by a
person who was never told. The plan **is** the job's sandbox, so the gate is
displaying three quarters of what it is asking somebody to sign off. Reading the
panel to write this is what found it, which is the third time in two weeks that
reading code for a reason other than "find the bug" is what found one — the
pattern [`state-of-play`](2026-09-17.state-of-play.completed.md) named this
morning.

## The proposal

**Nothing on the server, nothing on the wire.** Every field exists, every bound
is already enforced, and the refusal path already reports what was dropped
(`Refusal::NotGranted`, which the page prints in `.refused`). This is a page
change and a test, and that is the point of the row.

**What the gate shows.** Three lines beside the three it has, on the same rule
as those: a grant is shown when the plan asks for it, because a line that says
*no network* on every plan in the tree is a line nobody reads by the third one.

```
reads: AGENTS.md
network: yes · egress: crates.io, *.github.com
enforcement: kernel
```

**What the gate sends.** The amendment row grows a fourth button and two
choices, each shaped like the field behind it:

- **egress** is a list, additive, merged by `Plan::amend` exactly as files are —
  so it is the fourth button on the input that is already there, and the
  placeholder becomes *a path, command or domain the plan forgot*.
- **network** is `Option<bool>`, and the three states are real: `null` leaves
  the plan's own answer, `true` asks (bounded by the policy — `permitted` hands
  back `sandbox.network()`, not the ask), `false` takes it away from a plan that
  asked. Three buttons: **leave · grant · deny**.
- **enforcement** is the field that narrows backwards. `kernel` is a tightening
  and needs no permission; `best-effort` is asking the policy file to relax and
  `unmet` refuses it unless the session is already there. Three buttons:
  **leave · kernel · best-effort**, and the last one is offered rather than
  hidden — a refusal a person can read (*the policy requires kernel enforcement
  (luu.toml)*) teaches where the line is; a button that is not there teaches
  nothing.

**`approveJob` takes an amendment object.** Eight positional parameters with
three of them nullable is a call nobody can read at the call site:

```js
approveJob(id, { ...adding, closesOn, network, enforcement })
```

`approveTask` stays as the alias it is.

## The test

In `tests/smoke/gate.spec.js`, against the live server, because that is the
suite that exists for exactly this failure mode:
[`a-test-that-clicks-approve`](2026-09-08.a-test-that-clicks-approve.completed.md)
was written after two bugs in two days where the protocol was right and the page
was wrong, which is the shape of this row as well.

A session on the `wide` posture the spec already writes (`network = true`), a
prompt, and at the gate: add a domain, grant the network, ask for `kernel`.
Then the same assertion the amendment test makes — `/api/sessions/live`, the
job's plan as approved:

```js
expect(plan.network).toBe(true)
expect(plan.egress).toEqual(["crates.io"])
expect(plan.enforcement).toBe("kernel")
```

Driving the socket instead is what `serve_ws.rs` already does and is precisely
what could not have caught this: **the protocol was never wrong.**

## What it costs

- **Six controls in a panel that had two.** The gate is `max-height: 50vh` with
  its own scroll, and this makes a tall gate taller. The three amendment rows
  are `:if="!replaying"` like the two before them.
- **A signature written by `luu sign` now has three more fields to get right.**
  It always did; the difference is that a person will now produce them from a
  browser, where the server signs nothing and `[approvals] required` refuses the
  frame. Unchanged behaviour, newly reachable — and the refusal says so.
- **One more way to be refused at the gate.** Asking for `best-effort` under a
  `kernel` policy now costs a click and a `.refused` line. That is the intended
  cost: it is the only surface where the person learns the policy file has a
  floor.

## What was rejected

- **Hiding `best-effort` when the session is at `kernel`.** The page would have
  to know the session's enforcement to do it, and it does — Settings → Models
  already prints `state.settings.posture?.enforcement`. Rejected because the
  refusal is the better teacher, and because a disabled control makes the reason
  invisible at the exact moment somebody wants it.
- **A checkbox for network.** `Option<bool>` has three states and a checkbox has
  two; the missing one is *leave the plan alone*, which is what every approval
  that does not care wants to send.
- **Showing `network: no` on every plan.** The three lines above it show grants,
  not the absence of them, and a gate that lists what a plan may not do is a
  gate three lines longer for information the sandbox already guarantees.
- **A `data-testid` pass first.** Same answer as the record that built this
  suite: worth doing, not ahead of the test.

## And the same shape, one panel over: `[ui] icon-theme`

Item 15 — *nothing on the page says `[ui] icon-theme` exists*, from
[`what-the-debug-ui-does-not-need`](2026-09-16.what-the-debug-ui-does-not-need.completed.md)
§Still open.

**That record is wrong about the panel, and it is worth writing down because the
error is the same one item 9 made this morning.** It says: *the preferences
panel already exists and already shows the theme's name when one is loaded; it
says nothing when one is not.* The first half is not true. `settings-general.html`
has Theme, Editor, Layout and Workspace, and the string `icons` does not appear
in it — the manifest carries a `name` for the panel to show and no panel ever
showed it. So the row is not *add the missing half of a sentence*; it is **the
whole sentence**, in a panel that never had it. Both halves of the fix are five
lines, which is why the row was cheap either way and why nobody noticed the
premise.

What lands: a **Files** section in General, above Workspace, saying which theme
drew the tree — its name when one loaded, and when none did, the one line that
says the fallback is a fallback and names the key that replaces it.

```
Icons     the tree's own two shapes
          `[ui] icon-theme` in config.toml points at any VSCode icon theme on
          this machine — an installed extension's directory, or its theme JSON.
          Nothing is vendored, so with no theme named the tree draws its own.
```

It is `workspace.icons`, which the panel already imports the module for, so
there is no fetch and no new route.

## 2026-09-17, during the code: three things the plan above did not know

**The refusal a person most needs to read was being erased within a frame, and
the test is what found it.** The second test — best-effort under a `kernel`
policy — failed on `.refused` not existing, with the server having sent it. The
page clears `state.refused` in `turn_started`, under a comment that is right
about every other refusal in the protocol:

```js
// Whatever was refused, the answer to it is on screen now.
state.refused = null
```

`not_granted` is the exception and it is the only one: every other refusal stops
something, so the next turn starting *is* the answer to it. This one is about an
approval that **went through** — the list of what the policy file would not let
it carry — and the turn it describes starts in the same breath the refusal
arrives. So the one surface that teaches where the policy's floor is taught
nothing, and had taught nothing since the refusal was added. It now survives the
turn and is cleared when the next gate opens, which is the first moment it stops
being true.

This is the fourth defect in ten days found in code that nothing drove, and the
first one *this* record predicted nothing about: the plan above treats the
refusal path as already working, and it was already working on the wire.

**A session started from the page never sees `--mock-reply`.** The test was
written to start a session on the `wide` posture and be proposed a plan
declaring `network`. It got the user's own ask, declaring nothing — because a
session started from the browser builds its backend out of `config.toml` via
`crate::backend_for`, which passes `None` where the CLI passes its scripted
`Mock`. So a browser-started session always gets `Mock::default()` and its
planning call always answers in prose.

That is not a bug and the test is better for it: the empty plan is **the
ordinary case for a 7B**, so the two tests now type the whole of a job's sandbox
at the gate, which is exactly what they are about. What it costs is that the
*display* half had to be asserted in the first test instead, whose plan gained
`"network": true` and one domain — and that session runs under the server's own
policy, which grants no network at all.

**Which turned out to be the more honest case.** A panel that reads
`network: yes` off a plan is reporting an ask, not a grant: `Plan::narrow` bounds
the job by the session (`session.network() && …`), so inside a session with no
network that plan reaches nothing. Showing the ask alone would have been the gate
misreporting a permission at the one moment somebody is deciding, so the line
says both — and the page already knew, from
`state.settings.posture.network`.

## What it cost, in the end

- **Two smoke tests, 13 → 15**, both against the live server: one narrows a job
  from the browser and reads the plan back out of `/api/sessions/live`, one asks
  to loosen enforcement and reads the refusal. The second fails without the
  `store.js` fix above, which is the only reason that fix is provable.
- **Three assertions added to the test that was already there**, for the display
  half: what the plan asks to reach, and that the session denies it.
- **One selector swept in four places.** The amendment input's placeholder grew
  *or a domain*, and `gate-probe.mjs` and `gate.spec.js` matched on
  `placeholder*="a path or command"`. They now match on `"the plan forgot"`,
  which is the half of the sentence that is not a list of what may go in it.
- **No Rust.** `cargo test --workspace` is 455 tests and unchanged, which is the
  measure of how much of this row was a UI gap: every bound this panel now
  reaches was already written, tested, and unreachable.
