# The modals are `<dialog>`s, ESC means four things, and the cog moves

Three asks in one sitting, and they turn out to be one change: *use `<dialog>`
for the modals so ESC closes them*, *make ESC swap the columns when there is
nothing left to cancel*, and *move the settings button to the right of the
inspector's foot*. The first two are the same key, and the third is what makes
the second reachable.

`completed` the day it is written: the code it plans is in the same commit, and
the smoke test that holds it is beside it.

## The modals had no keyboard at all

All three — settings, the folder picker, the session starter — were the same
hand-built shape:

```html
<div class="modal-backdrop" @click="closeSettings()">
  <div class="modal wide" @click="$event.stopPropagation()">
```

A fixed div at `z-index: 50` with a click handler, and a second div inside it
that stops the click from propagating so that clicking the box is not clicking
outside it. **No ESC, no focus trap, nothing inert behind it.** Tab from inside
the settings modal walked into the file tree underneath.

`<dialog>` opened with `showModal()` brings all four for free — ESC, the focus
trap, everything behind it inert, and a `::backdrop` that is one pseudo-element
rather than a positioned div competing in a z-index. It also deletes the
`stopPropagation` trick: on a modal dialog a click that lands on the *backdrop*
has the dialog itself as its target, so `@click.self` — which jq79 already
supports — is exactly "outside the box", provided the dialog has no padding of
its own for a click to land in. It does not.

So the whole pattern becomes one line:

```html
<dialog id="settings-dialog" class="modal wide" @click.self="closeSettings()">
```

## What `<dialog>` does not bring, which is the only interesting part

**State.** Whether a modal is on screen is the page's own: `state.settingsOpen`,
`workspace.picker.open`, `ui.starter`. A `<dialog>` the browser closed on ESC
without telling the page would leave the component mounted, invisible, holding
the top layer, with no way back to it. So `modal.js` routes every native
dismissal back to the same close function the close button calls, and the
component unmounts the way it always did.

**And one of them must refuse.** The folder picker on a first visit is `forced`:
there is nothing behind it to go back to, and `closePicker` already returns
without closing. ESC had to learn the same refusal, or the browser would close
a dialog the page still believed was open — which is the exact failure above,
reached by the one modal where it is unrecoverable. `cancel` fires before
`close` and can be `preventDefault()`ed, which is what that is for:

```js
asModal("folder-dialog", { close: closePicker, locked: () => workspace.picker.forced })
```

`locked` is asked at dismissal time rather than read once, because `forced`
changes while the dialog is on screen.

`modal.js` opens the dialog from a `requestAnimationFrame`, for the reason
`content-viewer.html` attaches Monaco and `rows.js` that way and says so:
`:setup` runs to completion *before* the template renders, so the element does
not exist yet, and **the id is the one thing both sides can name**. This is the
third use of that seam and the first one that is not about performance, which
is worth noting — it is becoming the page's answer to *the platform owns this
element*, not a workaround for the renderer.

## ESC, and the ladder it walks

> if there is nothing else to cancel and it is in two-column mode, it toggles
> between content and chat

Which makes ESC mean different things depending on what is open, so the order is
the design. Innermost first, columns last:

1. **a modal is open** → return, and do nothing. `<dialog>` cancels itself, and
   one keypress must not both close the settings and swap the column
   underneath it. This is the only rung that acts by *not* acting.
2. **the history popover** → close it.
3. **a session being renamed** → drop the edit. This needed a `cancelRename`
   that did not exist: `commitRename` also runs on blur, and taking the field
   away *is* a blur, so `cancelRename` clears the flag first and that call
   returns on its own guard.
4. **an armed close in the history** → disarm it.
5. **two columns** → swap content and chat. With three, everything is on screen
   and there is nothing to swap, so ESC is inert rather than doing something
   arbitrary.

**A running turn is deliberately not on the ladder**, and this is the one place
the request was read narrowly on purpose. It is the only cancellable thing on
this page whose undo costs real work — a turn that has already been sent — and
ESC is too easy to hit for that. The composer's own stop button stays the way to
end one. If that is the wrong call it is one line, and it is called out here so
the line can be found.

## The cog moves, and it is not only tidiness

Settings was in the chat's head, beside new-session and history. **The chat's
head is the one head that disappears**: below 1260px two columns are on screen
and the second is a choice between content and chat, so with the content showing
there was no settings button anywhere on the page. The inspector is the column
that is always on screen, and its foot already carries the things that are about
the whole page rather than about a session — the chosen folder and the status
word. The cog goes at the far right of it, past the status.

That also makes rung 5 of the ladder reachable: ESC now swaps the two columns,
and the control it used to take you away from is no longer in the one that
leaves.

## What it costs

- **The CSS moves from two elements to one.** `.modal-backdrop` is gone;
  `dialog.modal` is the box and `::backdrop` is the dim. Two things had to be
  written out that the backdrop div used to do implicitly: the viewport is a
  dialog's containing block, so `width: min(72rem, 100%)` would have been the
  whole window and the gutter is now `calc(100vw - 2rem)` explicitly; and
  `margin: 3rem auto` replaces the backdrop's `align-items: flex-start` plus
  `3rem` padding.
- **`dialog.modal[open] { display: flex }`, not `dialog.modal`.** A dialog is
  `display: none` until it is open, and a bare `display: flex` overrides that —
  the box would be on screen, unmodal and unstyled by the backdrop, for the
  frame between the template rendering and `showModal()`.
- **Four smoke assertions changed** (`.modal-backdrop` → `dialog.modal`, and the
  settings button's new home), and `.chat .acts button` is 2 rather than 3.

## What was rejected

- **A key handler on each modal.** It is what `<dialog>` is, done worse, and it
  would have needed the focus trap written by hand too.
- **`inert` on the app div, by hand.** `showModal()` already does it.
- **Making ESC cancel a running turn.** Above.
- **Keeping `.modal-backdrop` as a wrapper inside the dialog.** It would have
  meant the backdrop click target was a div again, and `@click.self` on the
  dialog is the thing that made the `stopPropagation` pair go away.

## Checked

The new smoke test, `ESC closes what is open, and swaps the columns when
nothing is`, holds: the forced picker refusing ESC, the settings button's
absence from the chat's head, ESC closing a modal *without* swapping the column
under it, ESC swapping with nothing open, and ESC being inert at three columns.
Twelve tests pass.

Measured rather than eyeballed, once, because the eyeball was wrong: on the dark
theme the screenshot looked as though `::backdrop` was not painting at all. The
mean brightness of a patch of the chat column is **35.1 with nothing open and
15.5 with a modal open** — it paints, and a 55% black over a near-black theme is
just hard to see in a thumbnail.

Also confirmed by hand: the element really is a `DIALOG` and `open`, focus is
inside it after `showModal()`, a click on the backdrop closes it, the box is
1216px wide (76rem) and 48px (3rem) from the top, and both themes draw it with
no console errors.

## Still open

- **The other two asks from the same sitting are not here.** The tree's
  selection and a VSCode-style preview tab both touch *editing files from the
  page*, which the design doc says this surface does not do — "every write still
  goes through the job gate". That needs arguing with rather than routing
  around, and it is a record of its own.
- **Nothing tests the focus trap in the suite.** It was confirmed by hand
  (`dialog.contains(document.activeElement)`), and the reason it is not an
  assertion is that what to assert about tab order is not obvious — the useful
  version is "tab from the last control does not reach the tree", which needs a
  known last control.
- **`modal.js` never removes its listeners.** The element is thrown away when
  the component unmounts, so they go with it; a dialog that was ever reused
  would accumulate them, and nothing reuses one today.
