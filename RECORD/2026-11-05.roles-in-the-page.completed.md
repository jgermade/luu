# Roles in the page

> adelante con el paso 3

**Settings writes by role, Settings → Users, and Account.** The owner's half

This is the rest of it.

## What is true today

- **An owner writes every Settings write, a user and an admin none.**
  `settings_editable` is the loopback flag or an owner in `WHO`. The role
  table the users record set out has a middle row, and nothing reads it.
- **People are added, suspended and removed only with `luu user`**, on the
  machine. A server in a cluster has to be `kubectl exec`ed into for each
  person.
- **A login cannot be seen or ended from the page**, except the one in this
  browser (*Sign out*). A lost laptop's cookie lasts its week.
- **Only an owner may send a session off this machine.** A user who is not
  one is held to providers whose URL is this machine, which in a cluster is
  none of them. This morning's record left it open for this one.

## The proposal

### Writes by role

Two levels, read per request, beside the loopback flag that stays what it is
on a laptop:

| Level | Who | What |
| --- | --- | --- |
| shared inside luu | admin, owner | providers (and their probe), the tool limit, policy lists and environments, resend rules, authority notes |
| the machine | owner | engines, runtimes (install, start, images, postures, the host shell rule), the icon theme, brand marks |

```rust
fn may_write(state, needs: Role) -> bool {
    state.providers_editable || who().is_some_and(|who| who.role >= needs)
}
```

`Role` is already ordered `user < admin < owner`.

**Images are the machine's, not shared**, against the users record's table,
which put *images* in the admin row. In the tree as built, the images and
the postures are written by the same Runtimes routes that install and start
a container runtime, and building one runs that runtime on the machine. A
line through the middle of one pane would be a second rule for a reader to
learn, for a distinction nobody has asked to make.

**A refusal says the role.** On a server with users, a write that is refused
says *an admin's* or *an owner's*, not *bound off loopback*: that sentence is
true there and is not the reason.

**Renaming in the workspace is any user's**, in their own session's folder:
it goes through the session's sandbox, which is their folder, and the users
record gives every user *their own folder*.

### Where a session sends

On a server with users, **any logged-in user may choose any provider in
`config.toml`**, wherever it sends. The rule kept prompts on this machine
because *a token says who may reach the port, not where this machine's
prompts may go*: whoever held the token would be choosing. With users, a
provider is in the file because an admin or an owner wrote it there, and
that is the choice of where prompts may go, made by someone the role table
lets make it. A `private` server keeps the rule as it is.

### Settings → Users

For admins and owners. A list of everyone, with role, state and last login,
and:

```text
GET    /api/users                          everyone
POST   /api/users          {email, role}   add
PUT    /api/users/{id}     {role?, suspended?}
DELETE /api/users/{id}                     remove
```

- **An admin manages users and admins**: adds them, moves them between the
  two, suspends, resumes and removes them. An admin cannot touch an owner,
  or make one.
- **An owner manages everyone**, owners included. The last owner who can log
  in cannot be demoted, suspended or removed, as `luu user` already refuses.
- **Nobody suspends or removes themselves** from the page. Suspending ends
  every login, the one making the request included, and the page would lose
  the person mid-click; `luu user` stays for that.
- **Removing is refused while the user has sessions**, with the count, as
  `luu user remove` refuses: what removing does with them is still open in
  the users record. Suspending keeps everything.

### Account

In General, under *Account*: this user's logins, when each started and when
it ends, which one is this browser, *End* on each other one, and *Sign out
everywhere else*.

```text
GET  /api/account/logins                {id, created_at, expires_at, current}
POST /api/account/logins/{id}/end
POST /api/account/logins/end-others
```

A login's `id` is the first twelve hex characters of its stored hash. The
hash is of a 32-byte random token and is not the cookie, and twelve
characters only have to tell one person's logins apart.

## What it costs

- **Every write's refusal changes its words** on a server with users.
- **Three routes for people and three for logins**, all behind the login and
  `Origin`, which `require_login` already checks on every write.
- **A pane** (Users), and a list in General.

## Rejected

- **Admin writes the machine's half**, as the table a reader might expect
  from *admin*: an engine and a container runtime are processes on the
  machine, which is what *owner* was defined to mean.
- **An admin making owners.** The users record already said no.
- **Ending the current login from the list**: that is *Sign out*, and
  having it twice is two ways to lose the page.
- **A per-user allowlist of providers.** Nobody asked; it would be a second
  configuration language, which the users record rejected as RBAC.

## Still open

- **What removing a user does** with their sessions and folder, carried over.
- **An audit line** for who changed whose role: the server's log has the
  requests, not the people.

## Built, the same day

As proposed. `may_write(state, Role)` and `refusal` replace this morning's
`settings_editable`; `sends_anywhere` decides the destination rule; the six
routes sit beside the user's keys, behind the login. `auth.db` did not
change schema: a login's id is read off the hash it already stores.

**Found while writing it:** the workspace rename had been refused to every
user on a server with users since the users record, because it read the
same flag as Settings. It is any logged-in user's now, in their own
session's sandbox.

**Verified:**
- `tests/server_config.rs`, against the binary, three people on a public
  server, their folders under the test's scratch directory:
  - an admin writes the tool limit and is refused the engines with
    *an owner's*; a user is refused both;
  - a user is refused the list of people; an admin lists them, adds a user,
    is refused making an owner and changing an owner, suspends a user
    (whose login then answers `401`), removes the user who never logged
    in, and is refused removing the one who did, for their session;
  - an owner makes the admin an owner, and is refused suspending
    themselves;
  - an owner's second login is listed beside the first, this one marked;
    ending this one by id is refused; *everywhere else* ends one, after
    which the second cookie answers `401` and the first `200`.
- **Chromium**, against a local public server: Users listed with the
  owner marked *you* and its own Suspend and Remove disabled, a role
  changed from the select, and General's *Logins* showing this browser
  with when it began and ends.
