# The context manager, at last: history as a type, and a budget that is a budget

**Status:** proposal, no code. Follows
[`2026-08-26.walking-skeleton.md`](2026-08-26.walking-skeleton.md), which built the
instrument and, deliberately, nothing to point it at. This file is about finally
starting step 2 of the work order.

## The problem

The debug client was built early — before the context manager rather than after —
on the argument that it is the instrument used to measure it. That argument was
right and it has now come due: the instrument measures nothing, because there is
nothing to measure.

Two lines say it better than a paragraph:

```rust
// crates/luu/src/session.rs:24 — every turn, always
pub fn messages_for(prompt: impl Into<String>) -> Vec<Message> {
    vec![Message::system(SYSTEM), Message::user(prompt)]
}

// crates/luu/src/lib.rs:305 — the "budget" is the backend's counters, after the fact
buckets: vec![Bucket::new("prompt", usage.prompt_tokens),
              Bucket::new("completion", usage.completion_tokens)]
```

There is no history, so there is nothing to compact, nothing to select from, and
no history bucket to plot. The budget panel draws two bars that are not a split of
anything. The prompt-diff panel — the one whose whole purpose is showing how much
of the stable prefix survived — compares turns that always begin identically
because there is nothing after the system block. Both panels work. Both are
honest. Neither says anything.

## Proposal

The smallest thing that turns the instrument into an instrument. Not a strategy —
strategies come next and have to beat something.

1. **`Context` in `agent-core`, with the turn as the unit.** Not a message list: a
   sequence of turns, because everything the context manager will later do —
   drop, summarize, replace with a rolling summary — operates on turns, and a tool
   call belongs to the turn that made it.

2. **Selection before rendering.** `Context` decides what goes in against a token
   budget, and *then* renders. The rendering is a pure function of the selection,
   so attribution falls out instead of being reconstructed:

   ```rust
   pub struct Selection {
       pub messages: Vec<Message>,
       pub buckets: Vec<Bucket>,   // what was counted is what was sent
   }
   ```

3. **A real tokenizer** — the `tokenizers` crate with the loaded model's
   `tokenizer.json` — splitting the window into `system+tools · history · reserve`.
   The reserve is the part a budget has and a counter does not: room for the answer,
   set aside before deciding what history fits.

4. **A recorded baseline, before any strategy exists.** The trivial policy — keep
   whole turns until the next one does not fit, then drop the oldest — recorded over
   a handful of multi-turn sessions with `--record`. That is the "before" every
   later claim is measured against.

Done means: a multi-turn session where the budget panel shows a real split with
real headroom, the prompt diff shows the stable prefix surviving byte for byte
across turns, and there is a recording on disk that the next change has to beat.

## The shape of the prompt: one rule

**`system`, then strict `user`/`assistant` alternation. Anything that is not a turn
is fused into the nearest turn's user message. Storage keeps them separate.**

```
[system]      SYSTEM + tool definitions      ← never changes: this is the cached prefix
[user]        (fused summary) + oldest retained turn
[assistant]   …
[user] …      recent turns, verbatim         ← appended to, never rewritten
[assistant] …
[user]        selected code + the new prompt ← fused, as late as possible
```

Three consequences, each of which is the rule doing actual work:

- **Retrieved code never goes in the `system` block.** It is the thing that changes
  every turn; putting it there invalidates the whole prefix and nothing fails —
  it just gets slower, which is the failure mode `AGENTS.md` warns about by name.
- **Whatever changes most often goes last.** Stable prefix, then the rolling summary
  (changes rarely), then recent turns (append-only), then this turn's code and
  prompt. Bucket order in the rendered prompt is a cache decision, not a
  readability one.
- **Fusing instead of standalone messages keeps the alternation legal.** A summary
  as its own `user` message leaves two `user` messages back to back — some chat
  templates collapse that, others reject it. Fused, the case does not arise.

Storage stays split, because that is what makes later pruning possible at all:

```rust
pub struct Turn {
    pub prompt: String,
    pub answer: String,
    pub code_context: Vec<Fragment>,  // rendered fused, stored apart
    pub summary_of: Option<Range>,    // set if this turn absorbed a summary
}
```

Attribution does not depend on message boundaries: `Selection` counts buckets
itself, so two buckets landing in one rendered `Message` is fine. That is precisely
why the decision happens before the rendering.

The good part: this is falsifiable. The prompt-diff panel exists to show whether
the prefix survived, so the day something volatile creeps above it, the next turn's
diff says so.

## The overhead we cannot see, and report anyway

We talk to `POST /api/chat` (`ollama.rs:96`): we send `messages` and **Ollama
applies the model's chat template on its side**. The `<|im_start|>` markers and
per-message separators are tokens we never see, and our own `rendered()` is
explicitly not the wire format — it is a rendering for the trace (`session.rs:31`).

So our count under-reports, by roughly a constant per message, and the error grows
with the history. Owning the number would mean owning the prompt string —
`/api/generate` with `raw: true`, applying the template ourselves — which
contradicts what `CompletionRequest` says today, that the backend assembles.

**Decision: stay on `/api/chat` and accept the gap.** What that costs is paid by
reporting rather than hiding it: the trace carries **both counts** — ours, per
bucket, before sending; the backend's `usage.prompt_tokens`, after — and the panel
shows the difference as its own labelled bar, template overhead. It is not
distributed across buckets and not smoothed away. When that difference stops being
stable, it is the signal that the model's template changed, which is worth more
than the precision we gave up.

## What changes today

- `messages_for` becomes `Context::render`, and both call sites — `chat` and
  `serve` — go through it. They already share one assembler; this keeps them
  sharing it.
- `TraceMessage::Budget` stops echoing the backend and carries the real split,
  plus the backend's count beside it as above. The two disagreeing by a *stable*
  amount is expected; the amount moving is a finding.

## Rejected: history as a flat `Vec<Message>`

The obvious shape, and it is wrong by one release. Compaction replaces a *unit* of
history with a summary of it, pruning drops a tool result belonging to a *unit*,
and relevance selection scores *units*. Flat messages make every one of those a
grouping problem solved by convention, and the day a tool call arrives — the next
step — the convention breaks. Choosing flat now means rewriting it then, with the
protocol and the record format already carrying its shape.

## Rejected: trimming the rendered prompt

Render everything, count the string, cut until it fits. It is fewer moving parts
and it forecloses the whole point. A rendered prompt no longer knows where each
span came from, so there is nothing to attribute to a bucket — the stacked bar
becomes unimplementable and the compaction log has nothing to log. Worse, cutting
a rendered string cuts wherever the limit lands, which sooner or later lands in
the stable prefix and silently costs the KV reuse the prefix exists to protect.

Decide, then render. Never the other way round.

## Rejected: approximate token counting as the measurement

`chars/4`, or a generic BPE that is not the model's. Cheap, no model file to
resolve, and it disqualifies every number it produces. The error is not uniform —
it concentrates in exactly what we put in context: paths, identifiers, code — so
two strategies that differ by less than the error are indistinguishable, and a
recording made under it cannot be compared to one made after it is fixed.

An approximate count may exist as a *fallback* when the tokenizer file cannot be
resolved. It is labelled approximate on the trace channel and never plotted as a
measurement. See the first failure mode below for what enforces that.

## Silent failure modes

Three ways this plan produces a plausible, wrong number and reports nothing. They
are grouped because they are one category, and it is the category that already bit
this repo once: the lost `.await` that left `prompt_sent: null` on every live turn
while the panel merely looked empty.

### The fallback counter poisoning a comparison

> Monday: the baseline is recorded on a machine where `tokenizer.json` resolves.
> Wednesday: the "after" run happens elsewhere, the path is missing, the
> approximate counter takes over, and every bar comes out ~12% lower. The
> conclusion is that compaction saved 30%. It saved 18%.

Nothing errors, and the number is believable. What closes it:

```rust
pub enum Counter { Model { id: String }, Approximate }
```

- The trace carries it: `budget { counter: "qwen2.5-coder-7b", … }` versus
  `counter: "approximate"`.
- The panel labels an approximate bar rather than hiding it.
- The baseline runner **refuses to record** under it:
  ```
  error: refusing to record a baseline with the approximate counter
         (no tokenizer.json for qwen2.5-coder:7b; pass --tokenizer <path>)
  ```

A baseline with the wrong counter is worse than no baseline, because it gets used.

### Dropping half a turn, or starting the window on an assistant

Evicting by message rather than by turn leaves an orphan:

```
✗ turn 3 user:      "and now do it in Rust"           ← dropped
  turn 3 assistant: "Here you go: fn main() { … }"    ← kept, dangling
  turn 4 user:      "why did you use unwrap there?"
```

The model now sees an answer to a question nobody asked, and turn 4 asks about an
`unwrap` in code that appears for no reason. That is worse than dropping both: the
noise is introduced by the pruning itself. This is the concrete case behind
"the turn is the unit".

And after eviction the retained window must start on a `user` message. Starting on
`assistant` renders, under ChatML, as:

```
<|im_start|>system … <|im_end|>
<|im_start|>assistant        ← the model continues instead of answering
```

Qwen tolerates it and behaves oddly; Llama-3 and Mistral templates assume
alternation from `user` and mis-render outright. So: the window always starts on a
user message, even when that means dropping one turn more.

There is also an undefined case to define rather than discover. `--context-limit 0`
means "unknown" today and is only recorded (`lib.rs:76`). With no limit there is no
budget: everything goes in, the trace emits `limit: null`, and the panel says
*unknown window* instead of drawing a bar against nothing. Treating 0 as "infinite"
silently means the first real overflow arrives as a backend error nobody can
attribute.

### Re-tokenizing the whole history every turn

A closed turn does not change. The naive version re-tokenizes all twenty turns on
turn twenty-one, which is quadratic total work over a session:

```rust
pub struct Turn { …, pub tokens: u32, pub counted_by: Counter }  // counted once, at close
```

At 8–32K the absolute cost is small, and it still deserves doing right because of
*where* it shows up: as latency inside the instrument that exists to measure
latency. A context manager that slows down as the session grows is exactly the
artifact that ruins the reading.

The stored count must record **which counter produced it** — that is what
`counted_by` is for. Swap the tokenizer mid-session without it, and one bar sums
turns measured in two different units.

## What it costs

- **Resolving `tokenizer.json`.** Ollama does not expose it cleanly, so this needs
  a `--tokenizer <path>` escape hatch, and the fallback above for when it is
  absent. This is the part of the plan most likely to be annoying.
- **A dependency in `agent-core`.** `tokenizers` is not small. It is the one place
  where being exactly right beats being light.
- **A scripted runner, which does not exist.** The plan assumes multi-turn
  recordings and there is no way to produce one repeatably: `chat` is one turn
  (`const TURN: TurnId = 1`, `lib.rs:222`) and `serve` means typing into a browser.
  So this plan also owes:

  ```sh
  luu chat --script tasks/refactor.txt --context-limit 8192 \
    --record baselines/refactor.drop-oldest.jsonl
  ```

  With a sharp edge attached: **the mock backend cannot validate a strategy.** It
  does not read the context, so it answers identically whether it is handed the
  full history or none of it — every strategy "wins" against it. Baselines need a
  real model, which makes the runs slow and machine-dependent. The record header
  therefore has to say what it was measured with: it carries `backend` and `model`
  today, and needs `context_limit` and the tokenizer's identity too. Without that,
  two files a fortnight apart cannot be known to be comparable.
- **The double fold, kept honest.** `api::SessionView` is built two ways — the
  server folds live events, `luu export` folds a recording — and
  `folding_live_events_gives_the_same_view_as_folding_the_record` asserts they are
  byte-identical. Every field this plan adds to the trace has two places that must
  fill it. No new field lands without the test covering both directions; that is
  cheap now and invisible later.
- **The fixtures are all single-turn.** `make-fixtures.sh` records three sessions —
  completed, cancelled, backend down — and every one of them is one turn. The Pages
  demo would go on showing precisely the world this plan abolishes: one bucket, no
  history, a prompt diff comparing two identical prefixes. It needs a fourth, and
  the ugly one:

  ```sh
  "$luu" chat --script tasks/long-session.txt --context-limit 2048 \
    --record "$out/eviction.jsonl"    # small on purpose: it overflows and evicts
  ```

  A deliberately small window makes the recording show a real split, a whole turn
  being evicted, and the prefix surviving the eviction. CI regenerates it on every
  build, so the eviction path gets a smoke test for free — the same argument that
  made the fixtures recordings rather than hand-written JSON.
- **The budget panel needs the real split.** Small, but it is UI work in a plan
  that otherwise is not.
- **Pruning of tool results stays unmeasured** until tools land. That is the
  strongest argument for doing tools first, and it is accepted rather than
  answered: see below.

## What this does not touch, because it was already decided

Stated so their absence does not read as an oversight, not because they were
weighed here: history lives in `agent-core` and not in `luu`; buckets travel on
the trace channel and not in `protocol`; the system prefix stays byte-identical,
so history is appended after it and never interpolated into it. All three are
commitments in [`AGENTS.md`](../AGENTS.md). This plan complies with them; it does
not revisit them.

## Still open

Ordered by what unblocks what, which is the only ordering that means anything
here.

| Question | Precondition |
| --- | --- |
| Tools + application-level sandbox | this plan landed; its own dated plan first |
| Compaction (rolling summary) | the baseline above, recorded — otherwise there is no "before" |
| Relevance: grep/`tree-sitter` vs. embeddings | tools, so the context pressure is real rather than synthetic |
| Sessions in SQLite | none — but see below: it must be derivable, not a second truth |
| Reading the context window from the backend | none. `--context-limit 0 = unknown` until there is a reason |

The first two are sequencing, not doubt. The third is genuinely undecided, and
deciding it before there is a workload to test against is how the wrong index gets
built.

### On persistence, so SQLite does not arrive as a second truth

Nothing is persisted today. `--record` is opt-in and per-run, and `GET
/api/sessions` lists exactly one session because there is nothing to list from.
Under this plan history lives in memory for the life of a `serve` process: enough
to measure, and it means restarting loses the conversation.

Two different things could be persisted, and conflating them is the trap:

- **The event stream** — the JSON-lines record. Append-only, replayable, already
  the measurement artifact, and already the thing `api::SessionView` folds.
- **Session state** — turns with their token counts, so a long task resumes without
  recomputing context from scratch. This is what the design's *Persistence* section
  means by SQLite.

The rule that keeps them from diverging: **whatever SQLite holds must be
reproducible by folding the record.** A store that accumulates state the events
cannot regenerate is a second truth, and the double-fold test exists precisely
because a second truth is how the static twin and the live server start disagreeing
about what happened.

When it lands, the delicate part is *what* a stored turn keeps: `code_context`
separate from `prompt` (per the fusion rule above), and `tokens` with its
`counted_by`. Store the fused rendering instead and a resumed session either
recomputes everything or mixes two units in one bar.
