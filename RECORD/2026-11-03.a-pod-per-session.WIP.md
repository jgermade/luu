## What is true today

Sessions side by side have been possible since #68: every live session has its
own worker, and where its runtime is a container, its own container. Which
runtimes a session can have depends on where `luu serve` runs:

| | `host` (Landlock) | a container per session |
| --- | --- | --- |
| **The binary, on Linux** | yes | yes: `docker`, `podman`, `nerdctl` |
| **The binary, on macOS** | best effort (no Landlock) | yes: Docker Desktop, Podman, colima, `container`, with Landlock inside the VM |
| **The image** (`ghcr.io/jgermade/luu`) | yes, Landlock inside the container (ABI 7 on a runner, 8 under Docker Desktop) | no: the image has no runtime's CLI and no socket |
| **The chart** | yes, the same container in a pod; never run on a cluster | no: there is no Kubernetes runtime |

So in the image and the chart every session runs in luu's own container, as
one uid. Landlock over each session's folder is the only wall between them,
with the two gaps
[`a-user-a-code-and-a-folder`](2026-11-03.a-user-a-code-and-a-folder.completed.md)
names: the shared cargo cache, and signals.

## Docker: no container inside a container

Every way to give a session a container of its own from inside luu's
container costs more than it gives:

| Way | What it costs |
| --- | --- |
| **Docker-in-Docker** (`docker:dind`) | `--privileged`, which is root on the host. It also means a second image store and overlay on overlay. |
| **The host's socket** (`/var/run/docker.sock`) | Whoever drives luu is root on the host, since a container with `/` mounted is one `create` away. Also, the base is mounted at its own absolute path, so the work tree would have to be a bind mount at the same path on both sides, never a named volume. |
| **Rootless Podman inside** | Needs `/dev/fuse`, and `newuidmap`, which is setuid. Both fight `no-new-privileges` and `cap_drop: ALL`, the container's own hardening. Fragile from host to host. |
| **Sysbox** on the host | The one clean way: a `dockerd` inside without `--privileged`. But it is the host's to install, Linux only, and not Docker Desktop. |

**Decided: the image is one trust domain.** Sessions run in it on `host`,
held by Landlock: one person, or a team that trusts each other. What closes
the gaps *inside* that domain stays open: a cargo home per user, and
Landlock's scoping of signals. A container per session is for the binary on a
Linux host (rootless Podman), or for the chart. The socket is not offered: a
deployment that wants it can mount it and name `docker` in its policy, which
works today and is that deployment's decision to own.

## The proposal: `kubernetes`, a pod per session

A seventh `Runtime`. Its program is `kubectl`, and a session's worker is a pod:

```text
luu (the chart's pod) ──kubectl run -i──▶ worker pod, session A   /work/<user>/<a> by subPath
                      ──kubectl run -i──▶ worker pod, session B   /work/<user>/<b> by subPath
```

The worker already speaks over its stdin and stdout, so `kubectl run --rm -i`
is `docker run --rm -i` in another spelling. The seam does not move.

### The pod

`kubectl run <name> --rm -i --restart=Never --image <worker image>
--overrides=<pod>`, where the override is the whole pod:

- **The work volume, by `subPath`.** The claim holding `/work` is mounted at
  the session's base, at its own absolute path, which is the rule every
  runtime keeps. Only that folder is mounted, so another user's folder is not
  in the pod at all. That is a wall made of the mount, not of Landlock.
- **On luu's node, by default.** The claim is `ReadWriteOnce`, and a
  `ReadWriteOnce` volume can be mounted by any number of pods on one node. So
  the worker carries a required `podAffinity` to luu's pod
  (`LUU_KUBE_SAME_NODE`). With a `ReadWriteMany` claim, `worker.sameNode:
  false` drops it.
- **A home of its own.** An `emptyDir` at `HOME`, and another at `/tmp`. The
  cargo home under `HOME` is then per session, which closes the shared-cache
  gap for this runtime.
- **Held like the chart's own pod.** uid and gid as luu's, `runAsNonRoot`, a
  read-only root, every capability dropped, no privilege escalation,
  `RuntimeDefault` seccomp, and no service account token. That is Pod Security
  `restricted`, so the namespace can enforce it. `runtimeClassName` is there
  for gVisor or Kata, where a cluster has them.
- **Owned by luu's pod** (`ownerReferences`), so the garbage collector removes
  every worker of a luu that is replaced.
- **Network by label.** A session that may not reach the network makes a pod
  labelled `luu.dev/network: none`, and the chart's NetworkPolicy denies such
  pods everything. Whether that holds is the CNI's to enforce. A cluster whose
  CNI ignores NetworkPolicy leaves the pod attached, and `Runtime::cannot`
  says so, as it says it for Apple's `container`. The per-command seccomp
  filter still denies, as it does there.

### The start: one line on stdin first

`kubectl run -i` attaches once the pod is running, and what a container wrote
before the attach is not replayed. The worker's first act is its hello, so a
fast worker would greet nobody. **So the container waits for a line before it
starts the worker**, and luu writes one as soon as `kubectl` is spawned:

```sh
sh -c 'read -r _ && mkdir -p "${CARGO_HOME:-$HOME}" && exec "$@"' luu-worker luu worker …
```

The line sits in `kubectl`'s stdin until the attach carries it. By then the
hello has someone to read it. The `mkdir` is the entrypoint's own rule: a
granted path has to exist, and on an empty volume it does not until something
makes it.

### How it is configured: the environment

Half of what the pod needs exists only once luu's pod does: its name, its uid
and its namespace, which come from the Downward API. So the settings are
`LUU_KUBE_*` variables that the chart writes, not a table:

```text
LUU_KUBE_CLAIM        the claim that holds /work         (required)
LUU_KUBE_CLAIM_ROOT   where luu's pod mounts it          (/work)
LUU_KUBE_NAMESPACE    the workers' namespace             (luu's own)
LUU_KUBE_OWNER_NAME   luu's pod, for ownerReferences
LUU_KUBE_OWNER_UID
LUU_KUBE_SAME_NODE    luu's pod's labels, for podAffinity (unset: anywhere)
LUU_KUBE_LABELS       labels every worker carries        (the NetworkPolicy's selector)
LUU_KUBE_RUNTIME_CLASS, LUU_KUBE_RESOURCES (JSON), LUU_KUBE_PULL_POLICY
LUU_KUBECTL           the program                        (kubectl)
```

The image and the runtime come from where every runtime's do: `[worker]`, or
`--worker kubernetes --worker-image …`.

### The chart

`runtime: kubernetes` in `values.yaml` adds:
- a ServiceAccount, and a Role limited to creating, watching and deleting pods,
  attaching to them and `exec` into them;
- the NetworkPolicies;
- the `LUU_KUBE_*` variables;
- the worker image (`ghcr.io/jgermade/luu-worker`, the chart's version).

`kubectl` is in `ghcr.io/jgermade/luu`, at a pinned version, checked against
the sha256 `dl.k8s.io` publishes.

### What it does not have

- **`install`.** It runs `apt-get` as the container's root through `exec`, and
  a worker pod has no root to run as. It answers that it is not in a
  container it may change, which is the truth here.
- **A card in Settings → Runtimes.** That section lists what a machine can
  install and start. A cluster is neither, so `kubernetes` is chosen by the
  deployment, not offered beside Docker.
- **Image builds.** The cluster pulls the worker image; luu builds nothing on
  it.

## What it costs

- **A new runtime arm in every `match`**, and a pod spec that is now luu's
  to keep right. It is tested as JSON, not against a cluster.
- **About 55 MB of `kubectl`** in the server image.
- **A service account that can create pods** in luu's namespace. Without Pod
  Security `restricted` on that namespace, that is a node one bad pod away.
  The chart's notes say to enforce it.
- **A pod start per session**, measured in seconds, not the 100 ms of a
  container. The image is pulled once per node.

## Rejected

- **`kube-rs` instead of `kubectl`.** It is a client library plus
  `k8s-openapi`, a large dependency, and a second way of being a runtime when
  every other one is an argv. `kubectl` keeps the layer what its first
  paragraph says it is: building an argv.
- **One pod per user instead of per session.** That is the pod-per-identity
  shape [`users-and-a-code-by-email`](2026-11-03.users-and-a-code-by-email.WIP.md)
  moved away from. A session is the unit that already has a worker.
- **`ReadWriteMany` by default.** It needs NFS, EFS or CephFS, which many
  clusters do not have. `ReadWriteOnce` with affinity works on any cluster, at
  the price of one node.
- **Docker-in-Docker, the socket, or Podman in the image**, for the reasons in
  the table.

## Still open

- **A run on a cluster.** Nothing here has met one. Above all the attach race
  that the stdin line exists for, and the image pull under
  `--pod-running-timeout`.
- **Workers whose `kubectl` died.** Their attach closes, so their stdin
  closes, so they exit. But without `--rm`'s own cleanup they stay as
  `Completed` pods until luu's pod is replaced. A sweep at startup would take
  them.
- **Inside the image, the two gaps between users**: a cargo home per user, and
  Landlock's signal scoping.

## Built, the same day

All of the above is built. Where the build differed from the plan:

- **luu's pod is its workers' *controller*** (`controller: true`), not only an
  owner. A Deployment's ReplicaSet adopts any pod that matches its selector
  and has no controller, and then deletes the extra one. So the workers also
  carry their own name label, `app.kubernetes.io/name: luu-worker`, which
  neither the ReplicaSet's selector nor the Service's matches. Found while
  writing the chart: the first draft gave workers the server's labels.
- **The chart's own pod is now `automountServiceAccountToken: false`** under
  `runtime: host`. Nothing there talks to the cluster.
- **`persistence.work.accessMode`**, so a `ReadWriteMany` claim can be asked
  for beside `worker.sameNode: false`.

**Verified here:**
- `worker::kubernetes` (7 tests): the claim is required, and every other
  setting has a default. Only the session's folder is mounted, at its own path,
  by `subPath`, and a base outside the claim is refused. Home and `/tmp` are
  the pod's own, with the cargo home under them. The hardening, the owner as
  controller, the affinity, the network label, the `kubectl run` line, and
  pod names that do not repeat.
- `worker::runtime` (2 tests): `kubernetes` parses, runs `kubectl`, and is
  not among the runtimes Settings offers. It builds and inspects nothing. A
  spec without pod settings names `LUU_KUBE_CLAIM`. The terminal is `kubectl
  exec … -- env … sh -c`, and there is no root `exec` for `install`.
- `tests/kubernetes_seam.rs`, with a fake `kubectl` that reads the pod from
  `--overrides` and runs its container's command here:
  - The real worker waits for its line, greets after it, and answers
    `read_file`, `list_dir` and a refused read with the same bytes as a host
    call.
  - **With the line taken out, the same test never returns**, which is the
    race the line exists for, reproduced without a cluster.
  - A base outside the claim is refused before anything starts.
- The images' pairing test still holds, with the `kubectl` stage in both
  `deploy/Containerfile` and `deploy/Containerfile.release`. The pinned
  `kubectl.sha256` files (v1.34.1, amd64 and arm64) were fetched and are bare
  digests, which is the shape the check expects.
- `cargo +1.99 clippy --workspace --all-targets -D warnings` (CI's version),
  `cargo +1.99 test --workspace` (736 passed), and `cargo fmt --check` all
  pass.

**Not verified:**
- **The chart.** `get.helm.sh` is refused from this session, so `helm lint`
  and a render with `runtime: kubernetes` are CI's first run. `build.yml`'s
  `chart` job now renders it and checks:
  - the Role, RoleBinding, ServiceAccount and NetworkPolicies are there, and
    so is every `LUU_KUBE_*`;
  - `worker.sameNode: false` drops the affinity;
  - `runtime: host` has none of it.
- **A cluster**, as *Still open* says. Neither the attach, the scheduler, the
  claim, the image pull nor the NetworkPolicy has met a real one.
