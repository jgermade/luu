# An owner proved by email: `luu config`, and setup in the page

**Status:** proposal, built in the same change. Step 2 of
[`users-and-a-code-by-email`](2026-11-03.users-and-a-code-by-email.WIP.md)
(roadmap row 57, the code by email), and a correction to
[`local-or-online`](2026-11-03.local-or-online.WIP.md).

> En comando del setup.sh, no añadiría el email, ya que antes hay que
> verificar que el envío de SMTP funciona
>
> Quizá lo pondría en el wizard de `luu config` y en la web, cuando no haya
> owner asignado
>
> La comprobacion del SMTP, puede ser mediante el OTP al owner

## What is wrong with what was built

`setup.sh --mode online` asks for the owner's email and `luu setup` makes them
owner on the spot, with a code printed on the terminal. Nothing proves the
address is theirs, and nothing proves the server can write to it. The first
email the server ever sends would then be the first test of its mail, sent to
an owner who never got one.

## The proposal

### The order: the server, then mail and the owner together

1. **The server**: the origin and the bind, `[server]` with `exposure =
   "public"`. Nothing more is needed to start.
2. **Mail and the owner, in one step**: `[auth.smtp]` (a URL —
   `smtps://smtp.example.com:465`, or `smtp://…:587?tls=required` for
   STARTTLS — a from address, a user, and a password kept in
   `<state dir>/smtp.password`, `0600` like a provider's key) and the owner's
   email. **The code sent to the owner is the test of the mail.** It goes out
   under the settings as typed, which are not saved yet. If the send fails,
   nothing is saved and the reason is said. When the code comes back, the
   settings are saved and the owner made. One code proves three things: the
   server can send, the address receives, and it is theirs.

### `luu config`: the wizard, and its steps alone

```sh
luu config                                   # both steps, asked on a terminal
luu config server --origin URL [--bind ADDR] # what setup.sh runs
luu config owner                             # mail settings and an email, its code typed back
luu config mail                              # other mail settings, proved by a code to an owner
luu config setup-url                         # a one-time link to do the owner step in the page
```

It replaces `luu setup`, which did the first step and half of the second,
without proving anything. `luu user add --role owner` and `luu user code`
stay: they are the person at the machine, and a server without mail still
needs them.

### In the page, when there is no owner: behind a one-time link

A public server with no owner yet has a page anyone can reach. A setup form
open to whoever arrives first would let *anyone* make themselves the owner. So
setup in the page takes **a key**: `luu config setup-url` prints
`<origin>/?setup=<key>`. The key is 32 random bytes, stored as its sha256,
valid for an hour, and spent when an owner is made. Typing that command needs
the machine, which is what made the CLI the way in.

With the key, the page shows one form: the mail settings and your email.
*Send me a code* sends it under those settings. Then come the six boxes, and
the person is logged in as owner, with the settings saved. Without the key,
the page says the server has no owner yet and names the command. The settings
wait in memory between the send and the code, so a restart in between asks
for another code.

```text
GET  /api/auth/me.json   → {users, owner, mail, …}             what the page decides by
POST /api/setup/send  {key, url, from, user, password, email}  a code, under these settings
POST /api/setup/claim {key, email, code}                       saved, the owner, logged in
```

Every `/api/setup/*` request needs users, no owner, a live key, and this
server's `Origin`.

### The code by email, for everyone after

`POST /api/auth/code {email}` sends a code to a user who exists and is not
suspended. It answers `202` with the same body whoever asked, so it says
nothing about who is a user. **One code per address a minute**, and at most
ten requests from one address an hour, counted in memory, which is enough for
one replica. The login view gains *Email me a code* once the server has mail.

### `setup.sh`, corrected

Online asks for the origin only. It runs `luu config server`, starts the
service, and prints the setup link and the terminal alternative:

```text
Finish it in the page — email delivery, then you as its owner:
  https://luu.example.com/?setup=…        (an hour, once)
or on this machine:  sudo -u luu env LUU_HOME=/var/lib/luu luu config
```

`--owner` goes. `--origin` stays.

## What it costs

- **`lettre`**, the SMTP client, with rustls and without its default
  native-tls, which would bring in OpenSSL.
- **A second secret file**, `smtp.password`.
- **A setup key table** in `auth.db` (schema 2), and an `issued_at` on codes
  for the one-a-minute rule.
- **A page for setup** beside the login view.

## Rejected

- **The owner's email in `setup.sh`**, for Jesús's reason above.
- **Setup in the page with no key**: whoever arrives first owns the server.
- **The SMTP password in `config.toml`**: it is the file Settings renders and
  writes back, and a secret goes in a file whose mode is checked.
- **Saving mail settings that were not tested**: the first email sent would
  then be the first test, and the owner would be the one to find out.
- **A separate test email before the owner's code**: the owner's code is that
  test, and it also proves the mailbox. Jesús: *la comprobación del SMTP
  puede ser mediante el OTP al owner*.

## Still open

- **Deliverability** (SPF, DKIM) is the domain's. luu sends, and says when a
  send failed.
- **Rate limits across restarts**: in memory, they reset with the process.
