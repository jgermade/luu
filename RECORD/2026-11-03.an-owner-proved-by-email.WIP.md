# An owner proved by email: `luu config`, and setup in the page

**Status:** proposal, built in the same change. Step 2 of
[`users-and-a-code-by-email`](2026-11-03.users-and-a-code-by-email.WIP.md)
(roadmap row 57, the code by email), and a correction to
[`local-or-online`](2026-11-03.local-or-online.completed.md).

> En comando del setup.sh, no añadiría el email, ya que antes hay que
> verificar que el envío de SMTP funciona
>
> Quizá lo pondría en el wizard de `luu config` y en la web, cuando no haya
> owner asignado
>
> La comprobacion del SMTP, puede ser mediante el OTP al owner

## What is wrong with what was built

`setup.sh --mode online` asks for the owner's email and `luu setup` makes them
owner on the spot, with a code printed on the terminal. Nothing proves the
address is theirs, and nothing proves the server can write to it. The first
email the server ever sends would then be the first test of its mail, sent to
an owner who never got one.

## The proposal

### The order: the server, then mail and the owner together

1. **The server**: the origin and the bind, `[server]` with `exposure =
   "public"`. Nothing more is needed to start.
2. **Mail and the owner, in one step**: `[auth.smtp]` (a URL —
   `smtps://smtp.example.com:465`, or `smtp://…:587?tls=required` for
   STARTTLS — a from address, a user, and a password kept in
   `<state dir>/smtp.password`, `0600` like a provider's key) and the owner's
   email. **The code sent to the owner is the test of the mail.** It goes out
   under the settings as typed, which are not saved yet. If the send fails,
   nothing is saved and the reason is said. When the code comes back, the
   settings are saved and the owner made. One code proves three things: the
   server can send, the address receives, and it is theirs.

### `luu config`: the wizard, and its steps alone

```sh
luu config                                   # both steps, asked on a terminal
luu config server --origin URL [--bind ADDR] # what setup.sh runs
luu config owner                             # mail settings and an email, its code typed back
luu config mail                              # other mail settings, proved by a code to an owner
luu config setup-url                         # a one-time link to do the owner step in the page
```

It replaces `luu setup`, which did the first step and half of the second,
without proving anything. `luu user add --role owner` and `luu user code`
stay: they are the person at the machine, and a server without mail still
needs them.

### In the page, when there is no owner: behind a one-time link

A public server with no owner yet has a page anyone can reach. A setup form
open to whoever arrives first would let *anyone* make themselves the owner. So
setup in the page takes **a key**: `luu config setup-url` prints
`<origin>/?setup=<key>`. The key is 32 random bytes, stored as its sha256,
valid for an hour, and spent when an owner is made. Typing that command needs
the machine, which is what made the CLI the way in.

With the key, the page shows one form: the mail settings and your email.
*Send me a code* sends it under those settings. Then come the six boxes, and
the person is logged in as owner, with the settings saved. Without the key,
the page says the server has no owner yet and names the command. The settings
wait in memory between the send and the code, so a restart in between asks
for another code.

```text
GET  /api/auth/me.json   → {users, owner, mail, …}             what the page decides by
POST /api/setup/send  {key, url, from, user, password, email}  a code, under these settings
POST /api/setup/claim {key, email, code}                       saved, the owner, logged in
```

Every `/api/setup/*` request needs users, no owner, a live key, and this
server's `Origin`.

### The code by email, for everyone after

`POST /api/auth/code {email}` sends a code to a user who exists and is not
suspended. It answers `202` with the same body whoever asked, so it says
nothing about who is a user. **One code per address a minute**, and at most
ten requests from one address an hour, counted in memory, which is enough for
one replica. The login view gains *Email me a code* once the server has mail.

### `setup.sh`, corrected

Online asks for the origin only. It runs `luu config server`, starts the
service, and prints the setup link and the terminal alternative:

```text
Finish it in the page — email delivery, then you as its owner:
  https://luu.example.com/?setup=…        (an hour, once)
or on this machine:  sudo -u luu env LUU_HOME=/var/lib/luu luu config
```

`--owner` goes. `--origin` stays.

## What it costs

- **`lettre`**, the SMTP client, with rustls and without its default
  native-tls, which would bring in OpenSSL.
- **A second secret file**, `smtp.password`.
- **A setup key table** in `auth.db` (schema 2), and an `issued_at` on codes
  for the one-a-minute rule.
- **A page for setup** beside the login view.

## Rejected

- **The owner's email in `setup.sh`**, for Jesús's reason above.
- **Setup in the page with no key**: whoever arrives first owns the server.
- **The SMTP password in `config.toml`**: it is the file Settings renders and
  writes back, and a secret goes in a file whose mode is checked.
- **Saving mail settings that were not tested**: the first email sent would
  then be the first test, and the owner would be the one to find out.
- **A separate test email before the owner's code**: the owner's code is that
  test, and it also proves the mailbox. Jesús: *la comprobación del SMTP
  puede ser mediante el OTP al owner*.

## Still open

- **Deliverability** (SPF, DKIM) is the domain's. luu sends, and says when a
  send failed.
- **Rate limits across restarts**: in memory, they reset with the process.

## Built, the same day

All of the above is built. Beyond the plan:

- **A send that fails forgets its code.** Otherwise the minute's rule would
  hold a second try against an address the first never reached. Found by the
  test, whose first attempt sends to a closed port.
- **`smtp://` with no `tls=` is refused except to this machine**, and so is a
  password inside the URL. The URL is written to `config.toml`; the password
  goes to `smtp.password`.
- **The ceiling on codes by email is sixty an hour for the whole server**, not
  ten per IP. Behind a proxy every request comes from the proxy's address. A
  list of addresses tried one after another is what the ceiling is for, and
  one an address a minute is there already.

**How the SMTP password is kept** (Jesús asked):
- It is a file, `<state dir>/smtp.password`. It is written with mode `0600`
  from the moment it is created (`secret::write`), and it belongs to the
  server's user.
- `config.toml` names the file (`password-file`) and never holds the
  password.
- The mode is checked on every read: a group- or world-readable file is
  refused.
- It is in plain text inside that file, because SMTP AUTH sends the password
  itself, so a hash would be of no use. The file's mode and the user's account
  are what keep it.
- On its way in, it is typed without echo on a terminal, or sent once in the
  setup form over the page's HTTPS. It is held in memory until the code comes
  back, and written only then. No log line carries it.

**Verified here:**

- `users`: one owner made by the code a setup link's address was sent, the
  link spent by it, one code by email a minute, and a schema 1 file migrated.
- `mail`: a URL and a from address checked before anything is sent; the clear
  refused except to loopback; a password inside the URL refused.
- `tests/server_config.rs`, against the binary and a fake SMTP server
  (`tests/support/smtp.rs`):
  - **`luu config server`** turns a private file public and keeps the rest of
    it. The server it describes says `owner: false`, and `setup-url` prints a
    link.
  - **`luu config owner`** with a mail server that is not there says *nothing
    was saved*, and saves nothing. With the fake one, the code arrives, is
    typed back on stdin, and makes the owner. `[auth.smtp]` is saved, with the
    password in `smtp.password` (`0600`) and not in `config.toml`. After that
    there is no second owner and no setup link.
  - **Setup in the page:**
    - without a key, `403`;
    - unreachable mail, `502` and nothing saved;
    - a wrong code, `401`;
    - the right code makes the owner, logged in, with the mail saved, and
      the link is spent.
  - **After setup**, a user's code by email arrives and logs them in. A
    stranger gets the same `202` and no email.
- **Chromium**, against an ownerless server and a scripted mail server:
  - without the link, the page says what to run;
  - with it, unreachable mail is said;
  - the right settings send a code, and typing it into the boxes makes the
    owner;
  - logged out, *Email me a code* logs back in after the minute.
- **`setup.sh` online**, with the stand-in `systemctl`: it asks the origin
  only, prints the setup link, and the service answers `owner: false`. Every
  local check still passes.

**Not verified:**
- **A real mail server**: only the fake one, over plain TCP on loopback. TLS
  (`smtps://`, `?tls=required`) and real authentication are `lettre`'s, and
  have not met a server here.
- **Online under a real systemd**, which is CI's to run again.

## Still open, added

- **A password from a Kubernetes Secret.** A mounted Secret is `0644`, or
  group-readable under `fsGroup`, which the mode check refuses. Through `luu
  config` the password lands in the state volume instead, `0600` and luu's.

## Appended 2026-11-03: the link stays a link, and is a QR code too

> Por seguridad, setup.sh puede mostrar al final un código que se use en la
> web para configurar el SMTP
>
> El código en la URL para la configuración del SMTP no importa, ya que es una
> clave de un sólo uso
>
> Se podría mostrar un QR en el terminal

**The key stays in the link.** A key in a URL ends up in browser history and
in a proxy's log, which is why a token stopped riding in one. Here that costs
nothing: the key lasts an hour, and is spent by the owner it makes.

**`luu config setup-url` draws it as a QR code**, so it can be opened on a
phone:

- It is drawn when stdout is a terminal, or with `--qr`, which is for `docker
  exec` without `-t` and for `setup.sh`, which passes it. A script reading
  stdout still gets the link alone, on one line.
- Each character is two modules, in half blocks, in black on white whatever
  the terminal's colours: a scanner wants dark on light, and a dark terminal
  would otherwise invert it.
- A quiet zone of two modules runs round it.
- The `qrcode` crate draws it, without its `image` feature, so it brings no
  dependency of its own.

**Verified:**
- A link of this shape, drawn, was turned back into pixels from its
  characters and decoded by `zxing-cpp`, installed into a scratch folder for
  the purpose. It decoded to the link exactly.
- A test holds the shape: lines of half blocks only, as wide as the code and
  its quiet zone, wrapped in their colours.
- Without a terminal or `--qr`, `setup-url` prints one line.

## Appended 2026-11-03: a password the cluster mounts, read where it is

> Cómo se guarda la contraseña SMTP en intergate?
>
> Ok, dale

intergate keeps it in one of three places:

1. Its YAML, in the clear or as `${SMTP_PASSWORD}`.
2. Its database, sealed with AES-256-GCM under a key derived from
   `<data>/secret.key`.
3. A reference read on every send: `env:NAME` or `file:/path`, with no mode
   check, so a Kubernetes or Docker secret works as it is mounted.

**What luu takes from it is the reference, and only `file:`.**

- **Sealing is not taken.** The key would sit in the same volume as what it
  seals. A copy of the database alone would be kept from the password, and
  nothing else would. `smtp.password`, `0600`, is the same protection without
  the ceremony.
- **`env:` is not taken.** Every command a session runs inherits luu's
  environment: `run_command` adds the proxy variables and clears nothing. On a
  public server those commands are other people's, so `env` would print the
  mail account's password to any user. `secret.rs` gave this reason first,
  for the token and the provider's key. `env:` is refused with that sentence.
- **`file:` is taken**, as `password-ref = "file:/run/secrets/luu/smtp-password"`
  in `[auth.smtp]`, and `--smtp-password-ref` on `luu config owner|mail`.
  - It is read on every send, so a rotated Secret is the next email's.
  - Its mode is not checked. A Secret is mounted `0644`, or `0440` under
    `fsGroup`, and inside luu's container there is nobody else for a mode to
    keep out. That closes the *Still open, added* item above.
  - Saving one removes an `smtp.password` written for earlier settings.
  - A reference that is neither `file:` nor `env:` is refused **without
    repeating it**: a reference typed wrong may be the password itself.

**One rule for every password file, luu's or mounted.** Looking for what would
keep a session's commands away from a mounted file, the answer was not its
mode. The commands run as luu's own user, so `0600` does not stop them. What
stops them is Landlock: a command reads only what its policy grants, plus the
fixed `SYSTEM_ROOTS` (`/usr`, `/bin`, `/sbin`, `/lib`, `/lib64`, `/etc`,
`/opt`). So **a password file under one of those is refused**, whether it is
`password-file` or `password-ref`. `/etc/luu/smtp.password` would have been
readable by every session. `/run/secrets` and the state directory are not.

**Where it is mounted, in each way in:**

- **Helm**: `mail.passwordSecret` (and `mail.passwordKey`, `password` by
  default) mounts the Secret at `/run/secrets/luu/smtp-password`, `0400`. It
  goes under `/run`, not `/etc`, for the rule above. NOTES.txt gives the
  `luu config owner --smtp-password-ref` line.
- **Compose**: a commented `secrets:` example, mounted at
  `/run/secrets/smtp-password`. A file secret is a bind mount, so the
  image's uid 10001 must be able to read it.
- **The binary under systemd**: nothing new. The typed password goes to
  `/var/lib/luu/smtp.password`, `0600`, as before.

**Verified here:**

- `mail`:
  - `env:` is refused with its reason;
  - a password typed as a reference is refused without being echoed;
  - a relative path is refused;
  - a `0644` file is read, saved as `password-ref` and not copied, and the
    earlier `smtp.password` is removed;
  - a rotated file is the next read's;
  - both keys at once are refused;
  - an empty file is refused;
  - `/etc` and `/usr` are refused for both keys.
- `tests/server_config.rs`, through the binary:
  - after the owner step, `luu config mail --smtp-password-ref` with `env:`
    fails, and with a `0644` file it sends;
  - the fake SMTP server now decodes `AUTH PLAIN`, and the code arrives logged
    in with the mounted password (and the owner step's with the typed one);
  - `config.toml` names the file and does not contain the password;
  - `smtp.password` is gone.

**Not verified:**

- **The chart's render**: `helm` cannot be downloaded here. CI's chart job
  renders it with and without `mail.passwordSecret`.
- **A real cluster mounting the Secret.**
- **The page's setup** still takes a typed password only. A Helm install with a
  Secret proves its mail through `kubectl exec … luu config owner`.

## Appended 2026-11-04: against Mailpit (row 71)

> quizá podrías usar mailpit para pruebas

This container has no DNS and no outbound connection but its proxy's, so no
mail provider can be reached from it. Mailpit (1.33, in Docker) can: a real
SMTP server that is not ours, with a password (`--smtp-auth-file`) and a
certificate. Three of them: plain, STARTTLS required, TLS only. The binary
is the release's 0.1.6 Linux build, checked against its `SHA256SUMS`, and a
script ([`runs/2026-11-04.mail-against-mailpit/`](runs/2026-11-04.mail-against-mailpit/))
runs `luu config owner`, reads the code from Mailpit's API and types it back.

| URL | Mailpit | What luu did |
| --- | --- | --- |
| `smtp://127.0.0.1:1025`, wrong password | password, no TLS | `535 Authentication credentials invalid`; nothing saved |
| `smtp://127.0.0.1:1025` | the same | the code arrived, the owner was made, `smtp.password` `0600` and not in `config.toml` |
| then `POST /api/auth/code`, a user | the same | `202`; the code arrived; `/api/auth/login` `204` with the cookie |
| `smtp://localhost:1587?tls=required` | STARTTLS required | `invalid peer certificate: UnknownIssuer`; nothing saved |
| `smtps://localhost:1465` | TLS only | the same |
| `smtp://localhost:1587` | STARTTLS required | `530 Must issue a STARTTLS command first`; nothing saved |
| `smtp://172.17.0.2:1025?tls=opportunistic` | no TLS offered, not this machine | **sent**: the password and the code in the clear |

**Found: `tls=opportunistic` passed the check.** The rule was written as
"`smtp://` with no `tls=`", so any `tls=` passed it, and lettre's
`opportunistic` falls back to the clear when the server offers no STARTTLS —
which anyone between the two can arrange by removing it from the reply. Now
`smtp://` to anything but this machine needs `tls=required`, and the URL is
read the way lettre reads it (the `url` crate, the first `tls`), so a
fragment or a second `tls` cannot make the check see one thing and lettre do
another. The same run on this branch: refused before anything is sent, and
every other row unchanged.

**Found: only Mozilla's roots are trusted.** lettre's `rustls-tls` is
`webpki-roots`, not the system's store, so a relay whose certificate comes
from a private CA is refused (`UnknownIssuer`,
[`tls-private-ca.txt`](runs/2026-11-04.mail-against-mailpit/tls-private-ca.txt))
whatever the machine trusts. That is the refusal both TLS rows above show,
and it is what made a successful handshake impossible here: Mailpit's
certificate cannot chain to a public root. Said in the design doc now.
Whether luu should take a CA file, or the system's store, is a decision, and
nobody has asked for it yet.

**Verified:**
- real SMTP AUTH against a server that is not ours, and a wrong password
  refused with nothing saved;
- the code arriving, for the owner step and for a user at the login;
- both TLS modes reaching the certificate check and refusing a certificate
  luu does not trust;
- the opportunistic downgrade, found and closed (`mail::tests`).

**Not verified, and why this stays `WIP`:** a TLS handshake that succeeds — a
server whose certificate chains to a public root — and with it a provider's
own authentication. That needs a real account and a network that reaches
it. The Secret mounted by a cluster is still the cluster's.
