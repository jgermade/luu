# The map order probe: a corpus that can compare path order against rank order

**Status:** a protocol and a corpus, written before either order is checked against
it. Nothing here has been scored yet — this file exists to be run once, the way
the fold probe, the gate probe and the map probe itself were: written first, argued
before it can be fitted to a result, run after.

[`2026-09-02.ranking-the-map.completed.md`](2026-09-02.ranking-the-map.completed.md) shipped
`--map-rank` off by default because it lost to path order on
[`map-probe.txt`](../scripts/tasks/map-probe.txt) — and then found, in its own
appended measurement, the reason the loss cannot be trusted:

> **The corpus cannot compare two orders.** `map-probe.txt`'s group A is defined
> in its own comment as "the four files a 1024-token map actually holds" — the
> files a *path-ordered* map holds. It is the baseline's home turf by
> construction, so any reordering loses on it before a model is asked anything.

[`ROADMAP/2026-09-01/README.md`](../ROADMAP/2026-09-01/README.md) named building
that corpus as the first thing relevance selection's row is blocked on, and said it
"blocks nothing else." This is that corpus.

## The question, stated so it can come out wrong

> At a fixed token budget, does ranking the map by its reference graph put a 7B in
> a better position to answer "where does X live?" than the alphabet does — not
> merely a smaller one?

## Why `map-probe.txt` cannot answer it, restated as a rule

`map-probe.txt`'s group A was chosen by first running the path-ordered map at 1024
tokens and reading off what it held. That is consulting one of the two things
under test to build the instrument that compares them. It is not a mistake of
diligence — the file's own comment names the construction honestly — it is a
mistake of order: **a corpus that can compare two orderings has to be chosen
before either ordering is looked at**, or it is measuring which ordering built the
corpus.

The fix is one sentence: pick every target the same way, and let the way not be
"is it in some map."

## The corpus: one question per file, all 38 of them

Every `.rs` file this tree has, each with exactly one question, phrased from what
the file's own module doc says it is for — never from a token count, never from
either ordering's output. `crates/luu/src/bin/luu.rs` and `bin/loude.rs` are
byte-identical `main` functions and are asked about by which binary name they
back, which is the one fact that tells them apart and is true independent of any
map.

This is a change of shape from `map-probe.txt`'s three hand-picked groups of six
to one un-grouped pass over the whole tree, and the shape is the point: nobody
chose which files would be "in" or "out" of anything. Coverage — how many of the
38 a given order and budget actually holds — becomes a **measured output**, not a
premise the corpus was built to match.

Written to
[`scripts/tasks/map-order-probe.txt`](../scripts/tasks/map-order-probe.txt).
No `## fragment:` lines, the same discipline `map-probe.txt` set and for the same
reason: a corpus that hands over the file cannot measure whether a model located
it.

## The budget: 4096, one flag apart

`--map-tokens 4096`, `--map-rank` the only thing that changes between the two
runs. Chosen by looking only at *how many files each order fits* — not at the
corpus, and not at which files those are:

| order | files in | of 38 |
| --- | ---: | ---: |
| path | 15 | 38 |
| rank | 8 | 38 |

Both non-trivial, and both a minority of the tree — the map still has to be
selective for the comparison to mean anything. 1024 was rejected: rank order holds
one file there, which is a sample size of one. 8192 is left for a second run if
this one's n is too small to read; the reason to prefer 4096 first is that it is
the budget [`ranking-the-map`](2026-09-02.ranking-the-map.completed.md)'s own
appendix already measured group A/B on, so a result here sits next to a known one.

## What "better" means here, stated before the run

Two numbers per order, not one, because conflating them is the exact failure this
file exists to avoid:

- **Coverage** — of the 38 targets, how many fall inside this order's map at 4096
  tokens. This is a structural count, needs no model, and is already known to
  favour path order (15 vs 8) for the reason
  [`ranking-the-map`](2026-09-02.ranking-the-map.completed.md)'s Finding 2 gives: the
  fill rule stops at the first file that does not fit, and rank order's big central
  files eat the budget faster. Reporting it again here is not the finding; it is
  the denominator the next number needs.
- **Precision** — of the targets a given order actually holds, how many of *those*
  the model names correctly. This is the number `map-probe.txt` could not produce,
  because its group A was the path-ordered map's holdings by construction, so path
  order's precision on it was never at risk of being anything but measured against
  its own home turf.

A rank order that loses on coverage but **matches or beats path order on
precision** would say the ranking chooses better content per file it keeps, and
that the thing to fix next is the fill rule, not the ranking — which is exactly
the tension Finding 2 left open. A rank order that loses on both says the ranking
is not yet better than the alphabet at all, coverage aside.

## Running it

Same shape as the map probe: nothing attached, ever, sampling pinned, one flag
apart.

```sh
cargo build --release --bin luu
for rank in "" "--map-rank"; do
  target/release/luu chat --script scripts/tasks/map-order-probe.txt \
    --backend ollama --model qwen2.5-coder:7b \
    --context-limit 8192 --reserve 512 \
    --tokenizer ~/models/qwen2.5-coder-7b/tokenizer.json \
    --temperature 0 --seed 7 --map-tokens 4096 $rank \
    --sandbox luu.toml --record map-order-$([ -z "$rank" ] && echo path || echo rank).jsonl
done
```

**Scoring**, per question and per run, the same three outcomes the map probe used:
names the right path / names a wrong path / declines. Then split each run's score
by whether that question's target file is structurally inside that run's map
(from `luu map --explain --map-tokens 4096 [--map-rank]`) to get coverage and
precision apart.

## What was rejected

- **Reusing `map-probe.txt`'s groups and adding a rank-order pass over them.**
  That repeats the exact construction Finding 1 named as broken — group A would
  still be the path-ordered map's holdings, so rank order would still be scored on
  the other order's home turf, only now in both directions at once.
- **A corpus sampled from real user questions.** There are none on record — this
  project has no users yet — so "sampled without knowing what any map holds" is
  approximated by "one question per file, from the file's own stated purpose,"
  which is the closest thing to an unbiased sample this tree can produce of
  itself. Worth naming as the approximation it is.
- **Weighting questions by file size or centrality.** Would reintroduce exactly the
  bias the un-grouped, one-per-file design exists to remove — a corpus that already
  agrees with one of the two rankings under test before a model answers anything.

## Still open

- **8192 and other budgets**, if 4096's n does not settle it either way.
- **Finding 2's own question** — whether ranking and the fill rule are one decision
  — is not answered by this probe and was never going to be; this probe only tells
  us whether it is worth answering.
- **Weighted in-degree** as the aggregator instead of PageRank
  ([`ranking-the-map`](2026-09-02.ranking-the-map.completed.md) Finding 3) is a
  different ordering than either one under test here and would want its own run.

## 2026-09-03, later the same day: run

Same machine and model as
[`the-map-against-a-7b`](2026-09-01.the-map-against-a-7b.completed.md) — an M1 Pro,
`qwen2.5-coder:7b` at Q4, Ollama, `--temperature 0 --seed 7`, `--context-limit 8192
--reserve 512`, real tokenizer. Two runs, one flag apart, exactly the command above.
38 questions each, scored by hand as names the right path / names a wrong path /
declines, then split by whether the target was structurally inside that order's map
(`luu map --explain --map-tokens 4096 [--map-rank]`).

### Coverage, as predicted

| order | targets in the map | of |
| --- | ---: | ---: |
| path | 15 | 38 |
| rank | 8 | 38 |

Not a finding — the input to one. Restates
[Finding 2](2026-09-02.ranking-the-map.completed.md#finding-2-rank-order-buys-fewer-files-and-that-half-is-real)
on a corpus that did not exist when it was written.

### Precision — the number `map-probe.txt` could not produce

| order | correct, of targets it holds | precision | correct, of targets it does not hold | correct overall |
| --- | ---: | ---: | ---: | ---: |
| path | 15 / 15 | **100%** | 4 / 23 (guessed by naming convention) | 19 / 38 |
| rank | 1 / 8 | **12.5%** | 1 / 30 | 2 / 38 |

Path order is not merely bigger, it is *right whenever it holds the answer* — every
one of the 15 in-map questions was answered with the exact path, several down to
the exact line implied by the outline. Rank order is wrong on seven of the eight
files it kept, including `tools/mod.rs` and `repo_map.rs` — two of the three files
its own outline literally names as holding the answer to the questions asked about
them.

The rank order's one hit (`crates/luu/src/session.rs`, for "which file makes sure
chat and serve assemble the same prompt the same way?") does not survive a second
look: **the literal string `` `session.rs` file within the `luu` crate `` appears
in ten of the thirty-eight answers**, for questions with nothing to do with
sessions — the Ollama backend, the Backend trait, the message schema, the eviction
question itself. It is a stuck default, not a located answer, and the one time it
was right is the one time the default happened to be true. Read that way, rank
order's real precision is 0/8.

### What this outcome means, against the predictions on file

Stated in [`ranking-the-map`](2026-09-02.ranking-the-map.completed.md): *"A rank
order that loses on coverage but matches or beats path order on precision would say
the ranking chooses better content per file it keeps... A rank order that loses on
both says the ranking is not yet better than the alphabet at all, coverage aside."*
It loses on both, badly, and the corpus that could not be accused of favouring
either order is the one that shows it.

### The finding nobody predicted: rank order's map broke the session

| order | completion tokens, 38 turns | peak prompt | real evictions |
| --- | ---: | ---: | ---: |
| path | 2 228 | 7 313 | 0 |
| rank | 16 493 | 7 762 | **24** |

Path order's answers stayed to a sentence or two, the shape every earlier probe's
answers took. Rank order's answers grew paragraphs of fabricated Rust — plausible
struct definitions, method bodies with `// comment` stubs, cross-references to an
invented `Agency` struct — starting from the very first turn, at **7.4× the output
tokens** for the same 38 questions. That volume filled the window inside the same
session `map-probe.txt`'s runs never came close to, and by the fourth question
history was being evicted for good every turn or two thereafter. Nothing upstream
of this probe predicted it; the two runs share a session mechanism
(`--script`, one shared history) that every prior probe also used without it firing.

The plausible mechanism, stated as a hypothesis and not a finding: rank order's
eight files are the tree's densest and most self-referential —
`tools/mod.rs` and `repo_map.rs` are the two heaviest outlines in the whole map,
loaded with method signatures and no simple structs to answer a locating question
with. A model asked to name a file, shown thirty-odd methods instead of the short
structs path order's first fifteen files mostly are, appears to answer in the
outline's own register — inventing more of the same shape — and once one turn does
that the shared history primes the next one to as well. Path order's first fifteen
files are small and plain by comparison; nothing here isolates content density from
mere token count as the cause, and that is worth a probe of its own before it is
believed.

### What this changes

- **`--map-rank` staying off by default is no longer resting on a biased
  measurement.** [`ranking-the-map`](2026-09-02.ranking-the-map.completed.md)'s own
  appendix flagged its numbers as possibly an artifact of group A being the
  baseline's home turf. This run cannot be read that way — every target was chosen
  before either order was checked — and the gap it finds is wider, not narrower.
- **The open question changes shape.** It was "does ranking choose better content
  once the fill rule is fixed" (Finding 2). It is now also "does the *content*
  ranking surfaces cost more to hold in a shared session than the content path
  order surfaces" — a question about what a dense outline does to generation, which
  a structural coverage number cannot see and this probe found by accident.
- **Relevance selection's row in the roadmap can close on a negative result.**
  Not "not yet measured" but "measured, twice, on two corpora built two different
  ways, and it loses both times." Whether that is the row's end or its next
  redesign is not this file's call.

### Still open, updated

- **Whether density or token count explains the eviction finding** — the
  hypothesis above, unisolated.
- **Weighted in-degree**, unchanged from above — a different ranking might not
  select the two densest files first, and would want this same corpus rerun
  against it.
- **8192 and other budgets**, unchanged from above — this run answers the question
  at one budget and the gap it found is large enough that a second budget is a
  confirmation, not a new experiment.
- **The stuck-default pattern** (`session.rs` in ten answers) as a phenomenon in
  its own right, independent of ranking — whether it recurs with other dense maps,
  other models, or a map that is merely long rather than rank-ordered.
