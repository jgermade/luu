# A header per session, and what a line's `at_ms` is relative to

**Status:** completed — it plans code and the code is in the same commit.

It answers item 23 of [`ROADMAP/2026-09-17`](../ROADMAP/2026-09-17/README.md),
found on 2026-09-18 while checking that a session's chosen rules reach the
recording — they reach the store and the fold, and not that file — and recorded
in
[`the-window-rules-are-a-session-fact`](2026-09-18.the-window-rules-are-a-session-fact.completed.md)
§Found while checking. The row says it is **not the two-line fix it looks
like**, and the row is right.

## The defect

`luu serve --record` writes **one** header, at process start. `create_session`
and the resume route both write one into the *store's* stream and neither
writes one into the recorder, which takes `Event`s and has no header variant at
all. So a file spanning two sessions names the **first** one's backend, model,
window, counter, eviction, posture and three resend rules for all of it.

A `POST /api/sessions` that switches provider, or a resume onto a different
posture, produces a file whose first line is a claim about turns it does not
describe. This predates the resend rules by every field it already carried: the
posture went in on format 10 and the same file has been misnaming it since.

The store does not have the bug, which is how it was found: a session's own
stream starts with its own header, and a resume that moved anything appends
another through `retarget_header`. **The fold already reads mid-stream
headers** — *the last header wins* is written into `SessionView::from_record`
and was put there for exactly that case. So the reader was ready before the
writer was.

## Why it is not a line to add

The two streams count time from different places.

| | first line | every line after |
| --- | --- | --- |
| the store's stream | the **session's** `started_at` | `now − session_started_at` |
| a `--record` file | the **process's** `started_at` | `now − recorder.started_at` |

They agree today only because the two are the same number for the first
session — `bind` computes one `started_at` and hands it to both. They stop
agreeing the moment a second session starts, and that is the real content of
this row: a header is not decoration, it *declares the base every later line is
relative to*. Adding a second one without deciding what the lines after it are
relative to produces a file that is wrong in a new way instead of the old one.

## The decision: a line's `at_ms` is relative to the header above it

One sentence, and it is already true of the store's streams, so this makes the
file obey the rule its reader was written for rather than inventing one.

**What survives is the property that matters:** the wall-clock time of any line
is `that header's started_at + at_ms`, and it is unchanged by re-basing. A
reader that wants durations within a session subtracts as it always has; a
reader that wants absolute time adds the header it is under, which is what
absolute time always required.

So the recorder **re-bases** when it writes a header, and it writes one exactly
when the session it is recording changes: `create_session`, and a resume. After
this the file's `at_ms` and the store's are the same number again, for every
session and not only the first — which is the state the two were always assumed
to be in.

**A resume re-bases to the resumed session's own start, which may be hours
ago**, so the lines after it carry large `at_ms` values. That is correct and it
is what the store's stream for that session already does: the session started
when it started, and a resume does not restart it. Said here because it is the
one number a reader could mistake for a bug.

## What was rejected

**Rejected — later headers as metadata only, with `at_ms` still relative to the
first.** The smallest diff: append a header, change nothing else. It makes
`at_ms` mean *relative to the header above you* in a store stream and *relative
to the first header in the file* in a recording, for the same field, in the same
format, read by the same fold. One of the two readers would eventually be
written by somebody who checked the other one.

**Rejected — absolute timestamps on every line.** It removes the question by
removing the base, and it removes what the relative form is for: a recording is
meant to be comparable with another recording, and two runs that started at
different wall-clock times are read against each other by their own clocks. It
is also a format change to every line rather than to the lines that were wrong.

**Rejected — one file per session.** `--record <path>` is a file a person
named. Turning it into a directory, or into `path.1`, `path.2`, changes what the
flag means for the case that has no defect — a single-session run — to fix the
case that does.

**Rejected — refusing to record across a session switch.** Honest and useless:
the whole point of `serve --record` is to have the run afterwards, and a run
where somebody pressed *New* is still a run.

## What is built

**`Recorder::session`**, which writes a header line and re-bases the recorder to
it. `started_at` becomes an `AtomicU64` because the recorder is shared and the
base now moves; the channel already takes `RecordLine`, so the header needs no
new variant anywhere — it is the line `session::header` has always built, sent
down the same pipe as the rest.

**Two call sites**, and they are the two places the store's stream already gets
one: `create_session`, and the resume route. Both had the header in hand
already — they build it for the stream — so what lands is the same value going
to a second place rather than a second value.

## Still open

- **`luu export` still folds a multi-session file into one session.** The file
  is keyed by its stem and the last header wins, so a two-session recording
  exports as one session whose metadata is the second one's and whose turns are
  both. That is now *visible* rather than hidden — the second header is in the
  file — and splitting it is a decision about what a `--record` file **is**,
  which this record does not take.
- **Nothing says which lines belong to which session** beyond the header
  between them. A session id on the header would say it, and the header has
  never carried one: the store keys sessions outside the stream. It is the
  natural next field and it is not needed by anything today.
- **The turn numbering restarts and the fold merges them.** Two sessions in one
  file both have a turn 1, and `apply_protocol` pushes a `TurnView` only *"if
  the turn is not already there"* — so the second session's turn 1 is dropped
  and its tokens are appended to the first session's. Pre-existing, untouched
  here, and now the thing standing between a `--record` file and being readable
  across a session switch: the header says which session the lines belong to,
  and the turns still do not. It is the real shape of the export question above
  and it wants the session id the bullet before this one asks for.
