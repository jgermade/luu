# The container, decided — and a measurement that moved it

**Status:** the seam is decided, the ordering changed on a measured fact, and the
network half is proposed rather than settled.

[`2026-08-27.tools-and-sandbox.completed.md`](2026-08-27.tools-and-sandbox.completed.md) put level 3
last and gave four reasons. One of them has stopped being true on the hardware
this is being built on, and that is what this file is mostly about.

## The fact

Docker Desktop was already running on the M1 Pro. Its VM:

```
kernel:  6.12.76-linuxkit  aarch64
LSMs:    capability,bpf,landlock
config:  CONFIG_SECURITY_LANDLOCK=y
         CONFIG_LSM="yama,loadpin,safesetid,integrity,bpf,landlock"
```

**Landlock is available and active on a Mac today**, inside a VM that was already
installed. Nothing had to be bought, reinstalled or dual-booted.

That matters because of which of the four objections it hits. The record's reasons
for level 2 first were: it needs something installed; it costs a rebuild per
iteration; the two are not alternatives; and —

> **The backend is on the host.** The design already says so: inference wants the
> GPU, so a container would isolate tool execution only and talk back out over an
> exposed socket. **That is the same split level 2 gives, without the socket.**

That is the load-bearing one: *the container buys nothing new*. It is true
wherever level 2 exists, and the same record names the exception in its own last
paragraph — "the honest cost is that level 2 is **Linux-only**. macOS gets level 1
for in-process tools and nothing for subprocesses" — without following it to the
container's ordering.

On a Mac the container does not duplicate a boundary. **It is the only one there
is.** Every model run in this repository has been on macOS, where `run_command` is
denied before it starts, so the three command prompts of
[`2026-08-31.the-gate-probe.WIP.md`](2026-08-31.the-gate-probe.WIP.md) have never been
observable anywhere. The container is what makes them observable, on the machine
the work is actually happening on.

This does not overturn the decision — level 2 first, which happened. It changes
where level 3 sits relative to everything after it.

## Where the seam falls

**All tools inside the container. The context manager and the model client
outside.** One enforcement point, and the host runs nothing it did not write.

The design says this twice, differently, and the two do not agree:

| | says |
| --- | --- |
| [`loude-design.md:156`](../loude-design.md#L156) | "the container only wraps **the core**" |
| [`loude-design.md:388`](../loude-design.md#L388) | "the container isolates **only tool execution** (fs, bash)" |

Line 388 is right and 156 is being corrected in the design as part of this record.
Splitting anywhere else re-opens something #8 closed: the gate grants `files`,
`writes` and `commands` in one plan, and `Plan::narrow` made the task's roots the
authority for reads and for the child's writes alike. If `read_file` ran on the
host and `run_command` in the container, one approved plan would be enforced in
two places by two mechanisms.

**And the design gives the wrong reason for the split.** Line 388 justifies it by
GPU/Metal — performance. The strong reason is security, and it is the one nobody
wrote down:

> The topology does not justify `network = false`. **It makes it affordable.**

If the model call originated inside the container, you could not turn the
container's network off, and you would lose the build-script protection at the
exact moment you raised the isolation level. That the traffic that matters is born
on the host is what lets the container stay at zero. Under local-first it gets
stronger, since the model may now be remote: the host genuinely needs the network,
and the container still does not.

## What goes in the image, which the design also contradicts

"Compile to a static binary (`musl`) → minimal image (`scratch`/distroless)" sits
a few lines above a container whose entire job is running `cargo`, `rustc`, `git`,
`rg` and `ls`. A `scratch` image has none of them. Mounting the host's toolchain
does not help either: the host is macOS/aarch64 and the guest is Linux.

So the image is `loude-worker` plus the programs the policy allows, and the
finding is what that makes true:

**`commands = [...]` is the image's manifest.** The policy and the image have to
agree, and a mismatch is a *third* failure mode — "granted by the policy, absent
from the image" — distinct from "denied by the policy" and "the kernel will not
hold it". It gets the treatment every other gap in this project gets: named in the
verdict, the way `fallback.rs` says "landlock and seccomp are Linux-only, and this
is macOS". `luu tools` prints the resolved sandbox; its container form has to
print that column too.

`loude-worker` is not a new name — [`2026-08-31.the-portal-and-the-gate.completed.md`](2026-08-31.the-portal-and-the-gate.completed.md)
already says "the container is already step 5, `loude-worker` is level 3 under
another name". It does not exist in the tree. `luu` is one binary with
subcommands, and level 3 needs either a second binary or a subcommand that is the
executor half of an IPC.

## Lifetime: long-lived, one per session

Decided, on the project's own terms — a tuned experience on constrained hardware.
A container per command means a start per command, and on Apple's runtime that is
a VM boot per command.

Two consequences, and the second is a cost that was not being counted:

- **Not per command, but not global either.** `serve` is single-session today, so
  nothing shares anything. The moment multi-session lands, two concurrent sessions
  inside one container share a filesystem and a process table. One container per
  session keeps the efficiency and gives the boundary a meaning.
- **Long-lived is cheaper in time and more expensive in memory.** It is efficient
  precisely because it does not start; it is costly because it does not leave. On
  a 16 GB machine that is a three-way split — ~5 GB of resident model, whatever the
  VM is given, and `cargo build` inside it, which is the greediest thing that will
  run. At 48 GB it does not matter. At 16 it is the decision that binds.

## Network across the seam

**Leave the container's network attached and deny it per command with seccomp.**

The filter is built at every spawn — `build_filter(network)` in
[`sandbox/linux.rs:174`](../crates/agent-core/src/sandbox/linux.rs#L174) — and
each `run_command` forks a new child. A seccomp filter is immutable once
installed, and it never needs to change: the next command brings its own. So:

| | |
| --- | --- |
| startup cost | zero — the container is not touched |
| scope | exactly the task that declared it |
| race between tasks | none; each child carries its own filter |
| new mechanism | none |

`docker network connect`/`disconnect` would move by hand what the kernel already
decides per call, and its window would not line up with the task that asked for
it. This is "defence in depth, not instead of" doing its job: level 3 draws the
coarse, permanent boundary, level 2 makes the fine cut inside it.

It also answers the design's first open question — "narrowing `network` and
`enforcement` with the rest of the plan, which needs a plan that declares them" —
for the network half, at the level where it is nearly free.

## Egress through the host (proposed, not decided)

The limit that forces this: **the kernel cannot filter by destination.** seccomp
cannot dereference a user-space pointer, and `connect()` takes a `sockaddr *` —
which is why the current filter discriminates by address *family*. Landlock's
network rules (ABI v4) are TCP bind/connect by *port*, and the earlier record
already notes "so UDP walks out". "Only crates.io" is not expressible down there.

A host-side binary can express it, because it reads a protocol rather than a
syscall: an HTTP proxy sees the hostname in the `CONNECT` line. The layer that
cannot answer the question is the kernel; the layer that can is userspace.

**The condition that makes it a boundary rather than a convenience:** the
container must have no other route. With `HTTP_PROXY` set and a route to the
internet still open, `cargo` and `git` honour the proxy and a hostile `build.rs`
opens a raw socket — and `build.rs` is precisely what is not trusted. On an
`--internal` network whose only reachable peer is the host's proxy, enforcement is
by routing, not cooperation.

What it buys: HTTPS without MITM (the `CONNECT` hostname is enough, no certificate
store to touch); no DNS in the container at all, since the proxy resolves, which
closes DNS tunnelling; and egress becomes an **event in the record**, per task —
the asymmetry [`2026-09-01.local-first.completed.md`](2026-09-01.local-first.completed.md) named, where
the gate guards `writes` and says nothing about where bytes go. It turns
`network` from a boolean into `network: ["crates.io"]` in a plan.

What it costs, stated plainly: an allowlisted host is still a channel — data
encodes into a path. Programs that ignore proxy variables simply fail, and the
failure has to say why. And it is another process, though a small one: a CONNECT
proxy with a hostname allowlist, on `hyper`, which is already in the tree.

## The development posture

**Open now, narrowed at a trigger.** Building the worker, the IPC, the image and
the egress control at once means a failure that cannot be attributed. This is the
same argument the original record used to put level 2 before level 3.

Three conditions on it, because "we'll tighten it later" is the thing that does
not happen:

1. **Not everything costs the same, so do not loosen everything.** Inside a Linux
   container, Landlock works and is free — already written, already tested,
   blocking nothing. Loosening `enforcement` buys no speed and switches off the
   one part of the sandbox this whole exercise exists to reach. Widen `network`
   and `commands`; leave `enforcement` alone.
2. **Explicit, not ambient.** `luu.toml` ships strict on purpose — it fails on
   first run so that a person makes an informed choice. The loosening belongs in a
   separate file or a per-run flag, so that in three weeks nobody has to do
   archaeology to tell a default from a leftover.
3. **The trigger is a fact, not a date:** narrow when `run_command` first runs
   inside the container with a model in the loop.

And the reason this matters more here than it would elsewhere: probes will be run
during that window. A permissive environment that is not recorded makes those
numbers incomparable with later ones, and "one flag apart" is the sentence the
whole measurement discipline rests on.

## Runtime independence

Level 3 should produce an **OCI image** and invoke whatever runtime the user
names, rather than speaking any runtime's API. That is the same shape the policy
already has: `commands` is an allowlist of program names, not an integration with
each program. Docker, Podman, `nerdctl` and Apple's `container` then substitute
for each other, and the dependency becomes a choice — local-first applied to
runtimes instead of to models.

Two findings from checking the alternatives:

- **containerd directly: no.** It is a daemon, which is objection 1 verbatim and
  the one still standing; Podman rootless is daemonless and is what the design
  already names. Its Rust client is low-level gRPC over `containerd.sock` — a lot
  of surface for "run one process with these mounts and no network". And on macOS
  it is moot: containerd, Docker and Podman all need a Linux VM. **The VM is the
  cost; the runtime inside it barely matters.**
- **`apple/container` fits the constraint of not depending on Docker Desktop**
  (macOS 26 and Apple silicon, which these machines are), and supports
  `--cap-drop`, read-only mounts, `--uid`/`--gid`, and `-k` for a custom kernel —
  that last one being the escape hatch if its minimised kernel lacks Landlock,
  which is unverified and is the first thing to check. It has **no `--network
  none` equivalent** documented, only `--network <net>` to attach and `--no-dns`.

That gap is the price of portability, and it is why the thin layer has to declare
what it requires and fail naming what is missing, rather than assuming the flags
are uniform. It is also survivable here for the reason above: the per-spawn
seccomp filter is what actually denies the network, and it does not care what the
runtime can express.

## Still open

- Whether Apple's kernel has Landlock. One command, and it decides whether that
  runtime is usable for this at all.
- The IPC between the host half and `loude-worker`: it carries approvals, so it is
  a trust boundary inside one machine — the same question signed approvals answer
  for the network, arriving from inside.
- Whether the image is built by this project or declared by the user. "The policy
  is the manifest" points at generating it; "one informed line" points at the user
  owning it.
