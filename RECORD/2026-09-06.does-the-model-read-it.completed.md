# Does the model read it? Precision, with a 7B in the loop

**Status:** a protocol and the predictions it will be scored against, written
before the run. Item 10 of
[`ROADMAP/2026-09-05`](../ROADMAP/2026-09-05/README.md), and the half
[`choosing-fragments`](2026-09-05.choosing-fragments.completed.md) put on its own
Still-open list the day it landed:

> **Precision, which needs a model**, and is the half that says whether any of
> this reaches the answer.

## The question, stated so it can come out wrong

At 1024 tokens the selector puts the right file in the prompt for **32 of 38**
questions, against a path-ordered map's 3. That number is coverage, it is
structural, and `cargo test -p luu --test select_probe` recomputes it on every
commit with no model on the machine.

What no number in this repository says is whether a 7B, handed those fragments,
**answers out of them**. A selector that wins coverage and loses precision is a
worse selector than the map it beat, and — the sentence worth keeping —
*nothing in the coverage table would notice*. The table's own record says so; this
file is the run that can contradict it.

## The blocker on the roadmap was wrong, and that is why this is happening today

Item 10 is listed as blocked on "a box from [`machines.md`](../ROADMAP/2026-09-05/machines.md)".
Machine **1** in that file is this M1 Pro — *"16 GB unified, 7B comfortable"* —
`qwen2.5-coder:7b` has been on it since 2026-09-01, and the corpus is 38
questions about *this* repository, so no other tree and no larger model is
implied by any of it. The boxes still outstanding (4 and 5) answer questions about
native confinement and a 6 GB VRAM floor, neither of which is precision. The item
was ordered behind hardware it never needed.

## The arms: one flag apart

Three runs of the same 38 prompts, same sampling, same window. The primary
comparison is the first two — the flag item 10 names — and the third is the arm
that makes this table readable beside the coverage table it answers.

| arm | flag | coverage on file |
| --- | --- | ---: |
| **off** | *(nothing in the `code` bucket)* | 0 |
| **select** | `--select-tokens 1024` | **32 / 38** |
| map | `--map-tokens 1024` | 3 / 38 |

1024 is not a new choice: it is the budget
[`choosing-fragments`](2026-09-05.choosing-fragments.completed.md) reports its
headline at, and *"a budget a small window actually has"*.

The `code` bucket does not accumulate — [`lib.rs`](../crates/luu/src/lib.rs)
takes the turn's fragments rather than copying them, *"these fragments are this
turn's, and the next turn starts with none"* — so the select arm's history grows
at the same rate as the other two and only its per-turn prompt is larger. That
matters because of what the last model-in-the-loop probe found by accident, and it
is recorded per arm rather than assumed: see the eviction prediction below.

## What "better" means here, stated before the run

The same three outcomes and the same split
[`the-map-order-probe`](2026-09-03.the-map-order-probe.completed.md) used, because
a probe that invents its own scale cannot be read beside the one it extends:

- **names the right path / names a wrong path / declines**, per question per arm.
- Then split by whether that question's target was structurally in that arm's
  `code` bucket, which the key already answers. **Coverage** is the denominator;
  **precision** is correct-of-held.

The result that closes item 10 is *select's precision on its 32 held targets is
high*. The result that reopens the design is *coverage 32, precision low* — the
fragments were in the prompt and the model answered past them, which makes the
next fix the prompt's shape and not the selector, and which nothing in the
selector's own tests could ever have told us.

## Predictions on file, so the run can falsify them

1. **`serve_ws.rs` is the selector's stuck default.** It is scored first for
   **7 of the 38** questions, and in **5** of those the answer is somewhere else
   — Q1 (`agent.rs`), Q2 (`api.rs`), Q6 (`backend/openai.rs`), Q31
   (`export.rs`), Q33 (`serve.rs`). It is a long test file whose function names
   (`a_prompt_is_planned_approved_and_answered_over_the_socket`) carry half this
   project's vocabulary, so it matches everything and locates nothing. **If the
   model reads the first fragment and stops, those five come back naming a
   test.** If they come back right, the model is reading past rank 1, which is
   the single most useful thing this run can establish.
2. **The 13 held-but-not-first targets are where precision is decided.** The
   selector puts the target first 19 times and inside the top three 31 times; the
   gap between 19 and 32 is the set where being *present* is all the selector
   did.
3. **Evictions stay at 0 in every arm.** The rank-ordered map evicted 24 times in
   38 turns and nobody predicted it. The mechanism there was a map in the
   *prefix* driving the model into paragraphs of fabricated Rust; selection is
   per-turn and discarded, so the same failure has no route in. If it evicts
   anyway, that is a finding and not a footnote.

## Scoring: mechanical, and then read by hand, because the last probe says so

The key is on disk, so a first pass is `answer contains target path` and needs
nobody. That pass is **not** the score, for a reason this repository already paid
for: `the-map-order-probe` found the literal string ``session.rs`` in ten of
thirty-eight answers, for questions about the Ollama backend and the message
schema, and a mechanical scorer would have banked the one time that default
happened to be right. So all 38 answers per arm are read, looking for exactly
that shape — a path repeated across unrelated questions — and a stuck default is
scored as wrong everywhere including where it is accidentally correct.

## What was rejected

- **A new corpus.** Extending an instrument mid-experiment is what
  [`map-order-probe.key`](../scripts/tasks/map-order-probe.key) refuses in its own
  header, and three files this tree has today (`beneath.rs` among them) are asked
  about by no question precisely because they were written after the corpus.
- **A larger model, or a remote judge.** Both change more than a flag. The 7B is
  the machine this project is *built for* — the design's first sentence — so a
  precision number from a 32B would answer a question nobody asked.
- **A real tokenizer for the structural half.** The coverage table on file is
  counted by the approximate counter on both sides; matching it matters more than
  being right about absolute tokens. The model arms take the real tokenizer,
  since there the count is the model's own.
- **Scoring precision only on the select arm.** The off arm is what says how much
  of any score is the corpus being guessable from naming conventions — the map
  probe found 4 of 23 out-of-map answers correct by that route alone.

## Still open

- Everything `choosing-fragments` left open is untouched by this: a question that
  is not "which file", and a follow-up that says "and that one?".
- Whether a stuck default is a property of the model, the corpus or the block's
  shape. Two probes will have seen one; neither will have isolated it.

## 2026-09-06, before the run: the denominator on file is not the tree's

Written above as "32 of 38", taken from
[`choosing-fragments`](2026-09-05.choosing-fragments.completed.md). Recomputing it
on this tree — `cargo test -p luu --test select_probe`, at `b55b6c9`, which is the
commit that record landed in — does not reproduce its table:

| run | record, at 1024 | this tree, at 1024 | record, at 4096 | this tree, at 4096 |
| --- | ---: | ---: | ---: | ---: |
| map, path order | 3 | 3 | 16 | **14** |
| the selector | 32 | **33** | 38 | 38 |

**The cause is three files, and the record's own PR added them.**
[`map-order-probe.key`](../scripts/tasks/map-order-probe.key) names the files no
question asks about — *"approval.rs, sandbox/proxy.rs and tests/stdio.rs, all
written after the corpus was"*. On this tree there are **six**: `select.rs`,
`sandbox/beneath.rs` and `tests/select_probe.rs` joined them, and all three
arrived in `b55b6c9` alongside the record that reports the table. The table was
computed before the branch finished writing the code it was describing.

`beneath.rs` is the one that moves the map: it sorts into
`crates/agent-core/src/sandbox/` — early in path order — and at 4096 it displaces
two files that used to fit. The fill rule stops at the first file that does not
fit, which is the same mechanism
[`in-degree-and-fill`](2026-09-04.in-degree-and-fill.completed.md) named, arriving
here from a direction nobody was watching: **not a change of order, a change of
tree**.

What this does and does not change:

- **The conclusion is untouched.** 3 against 33 is the same result as 3 against
  32, and no sentence in `choosing-fragments` turns on the difference.
- **The denominator of *this* run is 33**, not 32, and precision is scored
  against the held set measured today, per question, not against a number quoted
  from yesterday.
- **The corpus is now 38 questions over 44 files.** It was one-per-file by
  construction and it is not any more. That is still the right call — the key's
  header refuses to extend an instrument mid-experiment — but "one question per
  file" has quietly stopped being a description of the tree, and a later reader
  would otherwise find it stated as present tense in three records.
- **A coverage number belongs in the test, not in prose.** `select_probe` prints
  the table on every commit and cannot go stale; the three records that also
  print it in Markdown already have. Nothing needs deciding here, but it is the
  reason this section exists at all.

## 2026-09-06, the run: the model reads it, and the reading is not free

`qwen2.5-coder:7b` on the M1 Pro, `b55b6c9`, sampling pinned, three arms one flag
apart. Every answer is in
[`runs/2026-09-06.precision/`](runs/2026-09-06.precision/), which is why the
numbers below can be argued with rather than believed.

### The answer to the question this file was opened for

| arm | right | wrong | declines | held | **precision on held** |
| --- | ---: | ---: | ---: | ---: | ---: |
| off | **0** | 0 | 38 | 0 | — |
| map, 1024 | 8 | 2 | 28 | 3 | 2 / 3 |
| **selection, 1024** | **33** | 3 | 2 | 33 | **30 / 33 = 91%** |

**A 7B uses what the selector hands it.** Handed nothing, the model does not even
know the tree is Rust — it answers `main.py`, `ollama_client.py`, and for "which
file is agent-core's crate root" it says `Cargo.toml`. That is a harder floor than
`the-map-order-probe` measured (4 of 23 by naming convention) and the difference
is explained: there the map was in the prefix telling it the tree was Rust. Here
the floor is zero, so the selection arm's 33 is attributable to the fragments and
nothing else.

The hand read the scoring section promised: no stuck default in either arm. The
most-named file in the selection arm appears **twice**, against `session.rs`
appearing in **ten of thirty-eight** answers in the rank-order run. Reading the
answers marked right, they are answers and not accidental mentions — each names
the full path and then a symbol inside it (`MockBackend`, `run_turn`,
`run_command`), which is the shape of a model quoting what it was given.

### The three predictions, all three wrong

**1 — falsified, and it is the most useful thing here.** `serve_ws.rs` scores
first for 7 of the 38 questions and the prediction was that a model reading only
the first fragment would name a test on the five where the answer is elsewhere.
Four of the five came back **right**, and no answer in the arm named a test file
that was not the target:

| | verdict | named | target |
| --- | --- | --- | --- |
| Q1 | right | `agent.rs` | `agent.rs` |
| Q2 | wrong | `export.rs` | `api.rs` |
| Q6 | right | `openai.rs` | `openai.rs` |
| Q31 | right | `export.rs` | `export.rs` |
| Q33 | right | `serve.rs` | `serve.rs` |

The model reads past rank 1 and past a decoy that outranked the answer. Q2 is not
a counter-example: `api.rs` was not in the bucket at all, so nothing was read past.

**2 — falsified, and it has consequences.** Position barely matters once the file
is in the bucket:

| the target was | correct |
| --- | ---: |
| held, ranked **1st** | 17 / 19 = 89% |
| held, **not** 1st | 13 / 14 = **93%** |

Being *present* is worth as much as being *first* — very slightly more, on numbers
this size, which is the honest way to say *the same*. That is a result about the
project's own past decisions: the graph hop was rejected three times, and
[`choosing-fragments`](2026-09-05.choosing-fragments.completed.md) rejected it the
third time partly because *"it moves the right file out of first place five times
in 38"*. On this evidence that was the wrong reason to reject it — first place is
not what pays. The other reasons stand untouched (it holds no more targets and
costs 13% more tokens), so the decision survives; the argument for it needs
correcting, and a fourth attempt should be argued against coverage and tokens
alone.

**3 — falsified, with the mechanism found.** 31 evictions in the selection arm
against 0 in the off arm. The reasoning in the protocol above was wrong and the
code says so: `push_turn` counts `user_text(&code_context, &prompt)` into the
turn's tokens, so the fragments are fused into the user message and stay in
history. The selector starts fresh each turn; the *history* does not.

### The cost, which is the finding nobody was looking for

| arm | prompt tokens | completion | tool calls | evictions | **prefix reuse** | wall clock |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| off | 138 651 | 5 480 | 0 | 0 | 93.3% | 4.2 min |
| map | 140 532 | 3 933 | 9 | 1 | **97.1%** | 7.3 min |
| selection | 254 273 | 3 670 | 0 | **31** | **17.7%** | **48.8 min** |

One causal chain, and every link is measured: selection fuses ~1 000 tokens into
each turn's message → history grows about five times faster → 31 evictions →
eviction cuts the *front* of the history, which is the shared prefix → reuse
collapses from 93% to **17.7%** → the arm takes **11.6× the wall clock** of the
one that answered nothing.

**91% precision costs 11.6× on this box.** That is still worth paying — 33 right
against 0 is not a trade, it is the difference between a usable agent and an
unusable one — but it is the first time this project has a price for its own
differentiator, and it is much higher than "not part of the cached prefix"
suggested. `choosing-fragments` says a selection run *"is not comparable on prefix
reuse"* to one without. It is worse than incomparable: it is 17.7%, and the reason
is eviction rather than the fragments themselves.

### What one flag did to the model's behaviour

Not measured, not predicted, and visible in the tool counts: the three arms did
three different things.

- **off** — declines. 38 times, at length: it produced *more* completion tokens
  than either grounded arm while saying nothing.
- **map** — *navigates*. It is the only arm that called a tool: handed an outline
  of the tree, the model reached for `read_file` to go and look. Nine calls, and
  it still declined 28 times.
- **selection** — answers, from what it was handed, in a sentence or two.

A map tells the model what exists; a selection tells it what is there. The first
invites a search and the second ends one — which is an argument for selection that
no coverage number contains, and one that would flip if the tool loop were cheap
and reliable.

### Still open, updated

- **Precision at 4096**, where coverage is 38/38. Confirmation, not a new
  experiment.
- **The eviction cost is fixable and nobody has tried.** A fragment is quoted into
  history for a turn that has already been answered. Dropping it from the stored
  turn — keeping the prose, not the code — would leave the answer intact and the
  history small. That is a design change and it belongs to Item 6, active pruning
  of tool results, which is the same problem with a different bucket.
- **A question that is not "which file"**, unchanged.
- **The map arm's tool calls are a probe of their own.** Nine calls, 28 declines:
  the model tried to navigate and mostly gave up. Whether a bigger step budget or
  a better tool prompt turns that into answers is untested.
