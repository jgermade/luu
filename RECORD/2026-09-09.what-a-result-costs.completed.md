# What a tool result costs, once its turn is behind the line

**Status:** a proposal, and the code it plans. Roadmap item 9 of
[`ROADMAP/2026-09-08`](../ROADMAP/2026-09-08/README.md), carried into
[`ROADMAP/2026-09-09`](../ROADMAP/2026-09-09/README.md) as the first row that
does not need a box with a model on it.

It is the third rule over the same window, and it is deliberately not a new
idea: [`prune-behind`](2026-09-08.prune-behind.completed.md) settled a shape —
a ratchet, a citation, and the eviction policy's own target — and this record's
whole claim is that a tool result is the object that shape was already
describing.

## The problem

The design says it out loud, and has since the tool loop landed:

> Output is capped at 8 KiB with a `truncated` flag — pruning old results out of
> the history is a later, measured change; a cap is the part that is not a
> strategy.

The later change is this one. Today `MAX_OUTPUT_BYTES` is 8 KiB, which at the
approximate counter is **~2 000 tokens for one `cat`** — against a whole turn's
selection at `--select-tokens 1024`. So the largest single block a turn can put
in the window is not the code the selector chose and the budget knows about; it
is the output of one command the model ran, charged in full to every turn after
it until the turn is evicted whole.

And nothing reaches it. `Repeat::Once` walks `code_context`. `Prune::Behind`
walks `code_context`. `ToolStep` is inside the same turn, counted into the same
`history` bucket by [`steps_tokens`](../crates/agent-core/src/context.rs), and
neither rule has a line for it:

```text
turn 4   assistant: let me look                       ← 6 tokens, the call
         user: [run_command] ok                       ← the head
               <8 KiB of cargo test output>           ← ~2 000 tokens
turn 5..  the model has moved on; the output is in every prompt since,
          at full length, and the only thing that will ever remove it is
          evicting turn 4 with its question and its answer
```

That is the trade `prune-behind` refused for quoted code, refused for the same
reason here: **the expensive part of an old turn is its bytes; the useful part
is that it happened.**

## The proposal

### 1. The same line, one more thing given up on it

No second ratchet and no second knob. Below `Context::pruned` a turn already
gives up its spans; under this rule it also gives up its tool *output*. The
line is chosen exactly as it is today — [`prune_to`](../crates/agent-core/src/context.rs),
shallowest that fits, otherwise the one that leaves the window smallest — and
the only difference is that a turn behind it is now worth less, so the same line
buys more and a deeper one is needed less often.

### 2. The call stays; the output becomes the line that cites it

```text
assistant: let me look                                ← unchanged, verbatim
user:      [run_command] output — 1 987 tokens, pruned
```

The assistant half is the model's own words and is never rewritten — that rule
predates this record and is why `ToolStep::text` is stored verbatim rather than
re-rendered from `call`. What is replaced is `result_text()` **whole**, head
included, so the number in the citation is the cost of exactly what is no longer
there. That is `pruned_fragment_text`'s rule, restated: a citation reports what
it replaces, or it is a number nobody can add up.

The tool's name stays in the citation because it is the cheapest possible
identity and the alternative is a user message that says nothing about which
call it answers.

### 3. A citation that is not cheaper is not taken

Same guard as spans, same reason: `[read_file] ok\n42` is three tokens and its
citation is eight. Where the citation would cost more, the result stays as it
is, which is also what keeps the window's cost monotone in the prune line.

### 4. Its own flag

`--prune-results`, off, beside `--prune-behind`. **It could have been folded
into `--prune-behind` and it must not be**: there is a run on disk from
2026-09-08 made under that flag, and a flag that quietly starts meaning
something else turns a recorded arm into an unrecorded one. One flag apart is
the only measurement discipline this project has.

The two compose rather than nest: `--prune-results` alone is inert, because
without a prune line nothing is behind it. That is a real state and not an
error — the line is rule B's, and asking for the second saving without the first
is asking for nothing.

## What it costs

- **A rewrite of the history block where it fires**, which is rule B's cost and
  not a new one: the same call that moves the line already rewrote everything
  behind it.
- **Three counts per pruned step** instead of one, on the calls where the line
  moves. `prune_to` recounts the window per candidate line and that loop is
  unchanged; what grows is the per-turn count, by the steps it carries.
- **A fourth thing to say when reading a recording back.** The header names
  `context_limit`, `counter`, `eviction` and the posture, and it does not name
  `repeat`, `prune` or this — see *Still open*.

## What was rejected

- **Rule A for tool results** — dedup an identical result the way a repeated
  span is deduped. Rejected for now, and not on principle: the case is
  unmeasured and probably rare. A repeated *span* is mechanical (the selector
  re-scores the same file across consecutive turns about it, which is what the
  grounded corpus does five turns running); a repeated *result* needs the model
  to make the same call twice and get the same bytes back — and for
  `run_command` the same bytes are not even the same fact, because a command
  re-run is new evidence, not a copy. Nothing in the tree counts how often it
  happens, which is the number that would justify the rule.
- **Lowering the 8 KiB cap.** It is not a strategy; it is what stops one `cat`
  blowing the window open at the moment it arrives, and the turn that made the
  call is precisely the turn that needs the bytes.
- **Pruning the call text.** It is small, it is the model's own words, and
  removing it leaves a result answering nothing.
- **A `results` bucket of its own.** The saving is the difference of two
  windows and is not decomposable into spans and results — under `Repeat::Once`
  the two interact — so a bucket claiming the split would be a claim the number
  cannot support. `Pruned.tokens` stays what it is: what the window actually
  lost.

## Found while writing it, and fixed here

**`job_closed`'s `replaced.tokens` over-reports a pruned turn.** The fold counts
what it stopped sending with `tokens_of`, the *stored* count, and its own
comment says that is "what the `history` bucket sums" — which stopped being true
on 2026-09-08, the day rule B landed. A pruned turn contributes its citations to
that bucket, not its spans, so a job folded after its turns were pruned claims a
saving it already had. The same bug, larger, arrives with this rule. It is
counted through the same accounting as the bucket now, and the test is a fold
after a prune.

Format 9 is unchanged by that: the field means what it always said it meant, and
what changes is that the number is now the one the sentence describes.

## Still open

- **The header does not say which rules a run was under.** `eviction` is in it
  and `repeat`, `prune` and `results` are not, so two arms one flag apart
  produce recordings that are distinguishable only by the run's own README. That
  is a format bump and an argument nobody has written; it is bigger than this
  record and it is the reason this one does not take one.
- **No model has been asked whether it minds.** The same sentence rule A and
  rule B both end on. A citation where a `cargo test` output stood is a stronger
  claim than one where a quoted span stood — the output is *evidence*, and the
  job's own closing condition reads exit codes from `ToolStep`, not from the
  prompt. The fold is unaffected (it reads the stored steps), but what the model
  does when the bytes go is unmeasured.
- **What a fold quotes from a pruned step.** `summary_text` builds its evidence
  from stored steps, so a fold after a prune is complete — but it is complete by
  accident of where the bytes live, exactly as it was for spans, and nobody has
  decided that it should be.

## 2026-09-09, later: what the diff actually was

Built as proposed, with two things the writing did not know.

**`Budget::results`, `Results::{Kept, Cited}`, `--prune-results`.** The rule is
threaded through the same four functions rule B is — `item_tokens`,
`window_tokens`, `fits_from`, `prune_to` — as a fifth argument rather than as a
struct grouping it with `repeat` and the line. That was a choice against
tidiness: the three do always travel together and a `Render { repeat, results,
pruned }` would read better at every call site, but it would also rewrite lines
that have nothing to do with this rule, in the four functions where the window's
cost is decided. The tidying is worth doing on its own day, against tests that
did not change in the same commit.

**A resumed session is the one place this rule reaches turn 1.**
`Context::from_view` rebuilds turns without their fragments — which is why rule B
has nothing to prune after a resume — and it rebuilds them **with their steps**.
So after a resume the only prunable thing in the window is exactly the thing this
rule takes. That was not an argument for the rule and it is not a claim that it
is good; it is a fact about where it will fire first, and it is written down
because the first person to see a resumed session prune something will otherwise
read it as a bug.

**The fold fix landed with it**, as §*Found while writing it* said it would:
`replaced.tokens` now counts the job's turns through `item_tokens` under the line
and the render rule in force, instead of through the stored count. That needed
one new piece of state — `Context::cited`, the render rule the last selection
used, beside `Context::pruned`, the line it left. The line says *which* turns
gave something up and the rule says *what*; a fold that reads one without the
other is the over-report again with a different sign.

Seven tests, all in `context.rs`: the rule itself, one flag apart against rule B
alone (where the same window evicts a turn instead), inertness without the line,
the too-small-to-cite guard, a turn named in the prune report though it carries
no spans, the `history` bucket against what was actually sent, and the fold after
a prune. `cargo test --workspace` is green, clippy under `-D warnings` is clean.

**No number.** Nothing here was run against a corpus, let alone against a model.
The flag exists so that the run can be made one flag apart, and until it is, the
only honest claim is the one the tests make: the prompt is smaller and the
conversation is intact.

**And the corpus for it does not exist yet**, which is worth naming here rather
than discovering twice: `--mock-reply` is consumed one per model *call* with the
last repeating, so a twenty-turn script on the mock calls a tool exactly once and
the grounded corpus — the one both earlier rules were measured on — has no tool
output in it at all. Measuring this rule wants a mock that answers with a call
per turn, which is the same instrument the tool-call probe of the roadmap's item
4 wants. Built once, it unblocks both; that is `ROADMAP/2026-09-09` item 3b.
