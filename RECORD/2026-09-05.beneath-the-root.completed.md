# Beneath the root: closing the in-process TOCTOU with `openat2`

**Status:** a proposal and the code it plans, written on 2026-09-05. Item 7 of
[`ROADMAP/2026-09-05`](../ROADMAP/2026-09-05/README.md), named as an open
question since [`tools-and-sandbox`](2026-08-27.tools-and-sandbox.completed.md)
and named again this morning by
[`a-clock-where-there-is-no-seam`](2026-09-05.a-clock-where-there-is-no-seam.completed.md)
as the last filesystem call in a turn that nothing above it can hold.

## The problem, which the code has been admitting in a doc comment

`Sandbox::check_path` says it itself:

> The path is canonicalized before it is compared, or a symlink walks straight
> out of the sandbox. **What canonicalization cannot close is the race between
> this answer and the `open` that follows it** — that is level one's hole, the
> answer for subprocesses is level two, and the answer for in-process tools is
> `openat2(RESOLVE_BENEATH)`, which is not in this change.

Every in-process file tool is two steps:

```rust
let check = sandbox.check_path(path, Access::Read);   // canonicalize, compare
…
std::fs::read_to_string(&check.path)                  // open, by path, again
```

Between them the path is a *string*, and a string is not a file. Anything that
can replace a component with a symlink in that window gets the tool to open
something the sandbox refused — and the verdict, written before the open, says
`allowed` about a file that was never checked.

**Who can do that is not hypothetical.** `write_file` and `run_command` are
granted inside the sandbox by design, so the model can create the symlink
itself; the plan gate approves *what* a job may touch, not the order it does
things in. The two steps are also both cheap, so the window is small — small is
not closed, and "small" is the argument every TOCTOU has been dismissed with.

`Sandbox::new`'s own `canonicalize` of the roots is a different matter and stays:
it happens once, at startup, before any model has said anything.

## The proposal

**Let the kernel do the resolving, atomically with the open.**

`openat2(2)` (Linux 5.6+) takes a directory descriptor and a `resolve` mask.
`RESOLVE_BENEATH` refuses any resolution step that would leave that directory —
absolute paths, `..` above it, and symlinks pointing out, all of them — and it
refuses *during* the walk, so there is no window between deciding and opening.
`RESOLVE_NO_MAGICLINKS` is asked for with it, because `/proc/self/fd/N` is a
door out of any tree that does not say so.

- `PathCheck` grows `root`: which granted tree answered. It was already known —
  `root_for` picked it — and was thrown away.
- `Sandbox::open_beneath(&check, mode)` opens the root directory, then
  `openat2`s the path *relative to it*, and hands back the `File` **and how it
  was opened**.
- The file tools read and write through that `File` instead of by path.

### Who enforced it is reported, never assumed

This repository's rule
([`luu-design.md` §Who enforced it is reported](../luu-design.md)) applies to
the new mechanism as much as to Landlock, and here it has something new to say:
an in-process read has always been `Applied::Process` — *our own check, before
the fact, all an in-process tool can have*. That sentence stops being true. On a
kernel with `openat2` the verdict now reads `Applied::Kernel { how:
"openat2(RESOLVE_BENEATH)" }`, and it is the first time anything in this program
holds an in-process tool with something other than its own good intentions.

Where the syscall is missing — kernel below 5.6, a filesystem that refuses it,
macOS, or a container runtime whose seccomp profile does not pass it through —
the open falls back to the path, exactly as today, and the verdict says
`Applied::Process` exactly as today. **The fallback is visible in the verdict
rather than in a comment**, which is the whole point of the rule: two machines
running the same policy get different guarantees, and the recording says which
one this was.

## What it costs

- One extra syscall per file tool call: the root directory is opened `O_PATH`
  per call rather than cached. Caching a descriptor on `Sandbox` would mean the
  sandbox owns an open fd, which changes its `Clone`, its `Send`, and what it
  means to hold one across a `Plan::narrow` — for one `open` of a directory
  that is already in the dentry cache.
- The tools read through a `File` instead of a path, so a couple of them get
  three lines longer.
- `PathCheck` gains a field. It is constructed in exactly one place.

## What was rejected

- **`RESOLVE_IN_ROOT` instead of `RESOLVE_BENEATH`.** `IN_ROOT` *rewrites*
  escapes to land inside the root (chroot-style), so `../../etc/passwd` silently
  becomes `<root>/etc/passwd`. A sandbox should refuse what it was not asked for,
  not quietly answer with something else — a model that reads a file it did not
  ask for and is not told is worse off than one that gets a denial.
- **`RESOLVE_NO_SYMLINKS`.** It would refuse *every* symlink, including the ones
  a normal checkout has inside itself. `BENEATH` allows a symlink that stays
  inside the tree, which is the right rule: the sandbox is about where a path
  lands, not about how it got there.
- **Re-checking after the open** (open, `fstat`, compare device and inode
  against a `stat` from before). It is the portable version and it is strictly
  weaker — it narrows the window instead of removing it, and it doubles the
  syscalls to do so. Worth having only on a platform with nothing better, and
  the platform with nothing better is macOS, where level 2 already does not
  exist and the honest answer is the container.
- **Doing this for `run_command`'s program path too.** A child is not held by
  our `open` at all; it is held by Landlock, which is level 2's job and already
  done. Adding a check here would be a second mechanism wearing one config file,
  which is the thing `the-worker-and-the-seam` refused.

## What the container gets for free

The worker on the far side of the seam runs `Tools::standard()` — *the same
code, not a second copy of it*, which is the property
[`the-worker-and-the-seam`](2026-09-02.the-worker-and-the-seam.completed.md)
built the seam to have. So a contained run gets `openat2` for the same reason a
host run does, with nothing added here and nothing to keep in sync. What a
contained run can lose is the syscall itself: a runtime whose seccomp profile
does not pass `openat2` through falls back, and the verdict inside the container
says `in-process check` where the host's says the kernel. That difference being
readable is the whole reason the mechanism is in the verdict.

## Still open

- **`list_dir` is still the old two-step.** There is no stable way to read a
  directory from a file descriptor in Rust, so `openat2` here would mean
  `fdopendir` and a hand-written iterator over `dirent`. What the window leaks is
  a list of *names* rather than the contents of anything, which is a smaller
  exposure than the ones this closes — and it is smaller, not closed.
- **`Sandbox::new` canonicalizes the roots.** Startup, before any model input,
  so not the same hole — but a granted root that is itself a symlink is resolved
  once and trusted forever after.
- **`run_command`'s `cwd`** is checked and then handed to the child as a path.
  The child is held by Landlock where Landlock exists; where it does not, this
  is the same window, one process out.
- **Nothing measures the window.** No test in this repository loses the race on
  purpose to show the old behaviour failing — the new test proves the kernel
  refuses the escape, not that the previous code allowed it. Proving the latter
  wants a loop and a racing thread, which is a flaky test on a busy machine.
