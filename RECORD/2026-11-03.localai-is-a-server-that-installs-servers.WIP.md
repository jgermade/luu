# LocalAI is a server that installs servers

Asked:

> *¿Qué tal si añadimos LocalAI?*

"Add" means one of two things here, and they cost very different amounts:

1. **A destination** — a `[provider.<name>]` that sends to a LocalAI somebody
   started. That is already built: LocalAI speaks OpenAI's chat completions.
2. **An engine** — `[engine.<name>] kind = "localai"`, a server luu downloads,
   checks, starts, and stops ([A model server luu
   starts](../luu-design.md#a-model-server-luu-starts)). That is new code, and
   it runs into a commitment the design already made.

`WIP` because it waits on two things: a run against a real LocalAI (refused in
the session that wrote this — see *Still open*) and a decision on the second
meaning.

## What LocalAI is, as read on 2026-11-03

Read, not measured: the v4.12.1 release page (2026-10-23), its
`LocalAI-v4.12.1-checksums.txt` (fetched, and it matches the digests GitHub
shows per asset), and `docs/content/reference/cli-reference.md` in
`mudler/LocalAI`. `localai.io` itself was not reachable from that session.

- **One binary per platform, not an archive**: `local-ai-v4.12.1-linux-amd64`
  (188 MB), `-linux-arm64` (176 MB), `-darwin-arm64` (183 MB). No Windows, no
  Intel Mac. llama.cpp's `llama-server` archive is ~12 MB.
- **The binary is a gateway, not the inference.** Backends (`llama-cpp`,
  vLLM, MLX, …) are OCI images from a *backend gallery*, chosen for the GPU it
  detects and installed by LocalAI itself. `--disable-backend-install` exists
  to stop that, "including automatic installs"; `--backends-path` says where
  they go.
- **Flags that matter to an engine**: `--address` (default `:8080` — *every
  interface*), `--models-path`, `--context-size` (`-1` = the model's trained
  context), `--max-active-backends` (`0` = unlimited, LRU-evicted),
  `--disable-webui`. Environment variables win over flags.
- **Readiness**: `GET /readyz`.
- **Models are named, not pathed**: a file or a YAML config in
  `--models-path`, addressed by name in the request — ollama's shape, not
  `llama-server -m <path>`'s.

## 1. As a destination: no code

```toml
[provider.localai]
backend = "openai"
url = "http://127.0.0.1:8080/v1"
model = "qwen2.5-coder-7b-instruct"   # LocalAI's name for it
context-limit = 8192                  # what it was started with: --context-size 8192
```

```sh
luu chat "hola" -p localai
```

The window rule is llama-server's, unchanged: the chat-completions request has
no field for it, so it is what the server was started with (`--context-size`,
or `context_size` in the model's YAML), and the profile's `context-limit` says
so once. A LAN LocalAI is `remote = true` like any other box on the LAN.

**Not verified**: whether it streams `usage` under
`stream_options.include_usage` (if not, the budget panel reads *not
reported*, which is correct, not a bug), and how its `tools` field holds up
under `tool-calls = "native"` for a 7B. Both are one run each.

## 2. As an engine: what fits

| The engine question | LocalAI | Fits? |
| --- | --- | --- |
| luu's own copy, by tag | GitHub release, `v4.12.1` | yes |
| sha256 GitHub publishes | per-asset digest + `checksums.txt` | yes |
| unpack | none — a bare file | small change: install today always unpacks |
| port | `--address 127.0.0.1:<placed>` | yes, and **must** be passed: the default is every interface |
| default port | 8080, same as llama-server | `engines::place` already resolves the collision |
| ready | `/readyz` | yes (does it answer before a backend is installed? unknown) |
| window | `--context-size` at start | yes, like `-c` in `args` |
| the session's model | by name, from `--models-path` | needs a luu-owned models dir of links — the `gguf_link` mlx already uses |

## 2. As an engine: what does not fit

**a. The thing that does the matmul is not the thing luu checked.** The design
says *luu's own copy is an official release by tag, checked against the sha256
GitHub publishes for the asset before it is unpacked, and refused when there is
none.* Under LocalAI that holds for the 188 MB gateway and for nothing it then
runs: the llama.cpp that loads the model arrives later, as an OCI image LocalAI
picked for the GPU it detected, from a gallery luu never read. Starting it as it
ships is luu starting a process that downloads and executes code luu did not pin
and did not check — the exact case the digest rule exists to refuse.

There are two ways out, and only one keeps the rule:

- **Keep it**: `--disable-backend-install`, `--backends-path` under
  `<state dir>/engines/localai/`, and luu installs the one backend itself,
  pinned by OCI digest. OCI is content-addressed, so a pin *is* a digest and the
  check is native to the format — but it is a second installer (registry
  manifest → layers → unpack) beside the GitHub one, for one kind.
- **Bend it**: let LocalAI install, and the card says *installs its own
  backends*. A verdict that names its gap is better than one that hides it, and
  it is still a weaker engine than the three there are. Not proposed.

**b. Which models it runs depends on what it installed.** `runs_on` is a pure
function today — format and source decide it. For LocalAI the answer for
safetensors or MLX depends on which backends are in `--backends-path`, a fact
about the disk at runtime. Under *keep it* with one pinned `llama-cpp`, the rule
collapses to llama.cpp's (GGUF only), which is also the answer to (c).

**c. For this project's target it is llama.cpp with a gRPC hop.** 7B–32B GGUF,
one session, one model loaded: `llama` already runs that in 12 MB, with
`variant` for the GPU builds llama.cpp publishes. What LocalAI adds that luu does not
have is several models resident at once (luu stops what no session uses, on
purpose) and backends none of the three kinds run — **vLLM on a CUDA box** is
the real one (machine 4 in `ROADMAP/2026-09-23/machines.md`). That is a reason
to want vLLM, and LocalAI is one way to get it, not the obvious one.

## The proposal

1. **Now: destination only.** No code. After one run confirms streamed usage
   and a native tool call, LocalAI joins *llama-server, vLLM, LM Studio* in the
   lists AGENTS.md and the design doc keep of what `--backend openai` reaches.
2. **Engine: not now.** Reopened when a machine needs a backend `llama`,
   `mlx` and `ollama` do not run, and then only as *keep it*:

   ```sh
   local-ai run \
     --address 127.0.0.1:<placed> \
     --models-path <state dir>/engines/localai/models \   # links, nothing copied
     --backends-path <state dir>/engines/localai/backends \
     --disable-backend-install \
     --max-active-backends 1 \
     --context-size <the profile's window> \
     --disable-webui
   ```

   `--max-active-backends 1` because an engine holds one model, the way
   `llama` does, and luu's rule is that a model nobody uses is not in memory.

## What it would cost, as an engine

A fourth `EngineKind` arm in every `match` in `engines.rs` (name, binary, port,
pin, repo, health, url, asset, start), a no-unpack install path, an OCI pull
with digest check, a models dir of links and the naming that goes with it,
`runs_on` for the new kind, its card and a brand mark (`web/brands/` has
none), and tests for each. Roughly the size of the mlx-serve kind plus the OCI installer.

## Rejected

- **A fourth backend.** It speaks OpenAI's API; `openai` already is that
  backend. A backend per server is the shape the one-trait design avoids.
- **LocalAI instead of the three engines** — one dependency for every kind is
  tempting, and it moves every engine's inference code outside what luu pins.
- **Bending the digest rule** — above, (a).

## Still open

- **The run.** In the session that wrote this, downloading the release binary
  to run it was refused by the harness (code from outside the repository), so
  nothing here is measured. What a person runs, on any Linux box:

  ```sh
  curl -LO https://github.com/mudler/LocalAI/releases/download/v4.12.1/local-ai-v4.12.1-linux-amd64
  grep linux-amd64 <(curl -sL https://github.com/mudler/LocalAI/releases/download/v4.12.1/LocalAI-v4.12.1-checksums.txt) | sha256sum -c
  chmod +x local-ai-v4.12.1-linux-amd64
  ./local-ai-v4.12.1-linux-amd64 run --address 127.0.0.1:8080 --context-size 8192 --disable-webui
  curl -s 127.0.0.1:8080/readyz
  luu chat "read AGENTS.md" -p localai --tool-calls native --record localai.jsonl
  ```

  Four answers to write down: does `/readyz` answer before any backend is
  installed; what did it download on the first load, from where; is `usage`
  in the stream; did the native tool call parse.
- **Whether vLLM is wanted at all** on machine 4 — that decides whether the
  engine half is ever reopened, and it is a question about vLLM, not LocalAI.
