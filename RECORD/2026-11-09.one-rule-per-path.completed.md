# One rule per path

Row 54 of [`ROADMAP/2026-11-08`](../ROADMAP/2026-11-08/README.md): *the
`--allow-*` flags add a second rule for a path, and the first answers:
`policies::widen` merges by path, and the flags do not.* Left by
[`policies-not-postures`](2026-10-22.policies-not-postures.WIP.md) step 2a,
*found while building*.

## The problem

`Sandbox::new` turned every `PathRule` into a `Root`, canonicalized, sorted
longest first, and `root_for` answers with the first root that contains the
path. Two rules for the **same** path were two roots of the same length, and
the first one answered:

```toml
[sandbox]
paths = [{ path = ".", access = "read" }]
```
```sh
luu chat --allow-write . "…"    # `.` at read-write, pushed after: never consulted
```

`policies::widen` fixed it for the lists, on 2026-10-23, by merging at the
policy. Every other caller of `SandboxPolicy::allow` still pushed: the flags,
and **`Plan::narrow`**, which adds a `Read` rule for each of `files` and a
`ReadWrite` rule for each of `writes`. A plan that declares a file in both —
the natural thing for a model to write when it reads a file it means to edit —
narrowed to a sandbox where that file **could not be written**. The row named
the flags; the plan is the case a person meets.

And the two halves of the sandbox disagreed. The kernel's ruleset is built
from the roots (`kernel::prepare`), and Landlock grants the union of rules on
one path, so a command run under that plan could write the file while
`edit_file` was refused it.

## The proposal

Merge where the rules become roots, not where each caller adds one: in
`Sandbox::new`, a rule whose canonical path is already a root raises that
root's access to the greater of the two (and takes its `source`, so a verdict
names the rule that grants), rather than adding a second root. The implicit
system roots are untouched: they are added after, and skipped when a path is
already a root, as before.

`policies::widen` stays. It keeps the lists' own reading of a policy
(`lists_of_file`) to one entry per path, which is a fact about what the page
shows rather than about what is granted.

## What it costs

Nothing a person could rely on: no order of rules for one path was documented,
and *the first answers* was an accident of `Vec::push`. A policy that wrote the
same path twice now gets the wider of the two everywhere, which the kernel was
already giving its commands.

## What was rejected

- **Fixing the flags alone**, as the row said. The plan would have stayed
  read-only, and the next caller of `allow` would have reintroduced it.
- **The later rule wins.** As arbitrary as the first, and a narrower rule
  written after a wider one would silently take away what the kernel still
  grants.

## Still open

- **Overlapping paths are not one path.** `.` at read and `./src` at
  read-write are two roots on purpose, longest first; only identical canonical
  paths merge.
