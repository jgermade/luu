# Fragments across a resume: the reference, not the bytes

**Status:** completed — it plans code and the code is in the same commit.

It answers item 20 of [`ROADMAP/2026-09-17`](../ROADMAP/2026-09-17/README.md),
whose design argument was written a day earlier in
[`the-window-rules-are-a-session-fact`](2026-09-18.the-window-rules-are-a-session-fact.completed.md)
§Fragments across a resume and has been a row with nothing blocking it since.
That section decided *what* to store — the reference, anchored in the session's
timeline. This one builds it, and two things turned up on the way that it could
not have known.

## What is lost today, in one line

`Context::from_view` rebuilds every turn with `code_context: Vec::new()`,
because `SessionView` carries no fragments and nothing on the wire ever said a
turn had any. **It is the only place in this system where something is
genuinely lost rather than merely not sent.** An evicted turn is named by a
tombstone; a pruned turn is named by a citation; a turn whose spans went through
a resume is silently a turn that never had any.

Storing the bytes was rejected the day before, and not for the obvious reason.
*Stored bytes go stale* does not decide it — a live session's already are, which
is item 19 and now has a number. What decides it is the sandbox: **bytes in the
store come back without being re-read**, so a session resumed under a narrower
posture gets back a file it is no longer allowed to open. That is
2026-09-17's defect walking back in through the store, and it is the one thing
this change must not do.

## Two things the argument did not know

### `code_context` holds two different kinds of thing and nothing can tell them apart

A turn's `code_context` is built in `chat` from **the fragments a person typed**
(`--fragment`, `## fragment:`) and then **the spans the selector chose**, pushed
into one `Vec<Fragment>` in that order, with the person's first because "a
selector that could crowd out an explicit ask would be answering a question it
was not asked". After that line, nothing anywhere distinguishes them. They have
different claims:

- **Attached** is the person's input, as much as the prompt is. Losing it loses
  something that was said.
- **Selected** is a decision the prompt builder made against *that turn's* text.
  The next turn re-scores from scratch and may choose differently.

In `serve` — the surface a person actually works in — there is no `--fragment`
at all, so **every span in a session the store holds was chosen by the
selector**. The resume question is therefore mostly about the kind whose claim
is weaker, which is worth saying out loud before restoring both.

It is restored anyway, and rule A is the argument: since 2026-09-19 a span is
rendered **once, by the oldest turn of the window that carries it**, so an old
turn's selected span is not that turn's private decoration — it is the copy the
whole window is reading. Dropping it at a resume does not return the session to
some neutral state; it takes code out of the window and leaves the next
selection to fill the hole against a different prompt, with nothing recording
the substitution.

**The origin is carried on the wire even though both are restored**, because
the distinction exists in the tree today and can be seen from nowhere. A field
that names it is how the next decision about it gets to be a decision rather
than a rediscovery.

### A resume is the one place the item 19 defect is repaired

The only way to bring a fragment back by reference is to **read it again**. So
every restored span in a resumed session carries the bytes that are on disk at
the moment of the resume, which means the window comes back with **one body per
path** — the contradiction item 19 detects is gone, for the turns that were
restored, because there is nothing else it could be.

That is a consequence and not a fix, and the difference matters:

- It repairs the window **once**, at the resume. From the next turn on the
  session goes stale exactly like a live one, by the same mechanism.
- It reaches `banner.rs` — the blind spot
  [`a-corpus-that-edits`](2026-09-19.a-corpus-that-edits.completed.md) named,
  where a file edited after its only read is stale with nothing to contradict it
  — which supersession by comparison can never reach, because there is no second
  body to compare.

So item 19's *re-read at render time*, rejected there as an architectural change
to what the context manager may touch, is what this does at exactly one moment,
where a sandbox is already in the caller's hand. Item 19's decision is untouched
and still waits on a model.

## What is built

**One protocol message.** `ServerMessage::Grounded { turn, spans }`, published
after `TurnStarted` and before the prompt it explains, where `spans` is the
specs as they were written — `src/greeting.rs:1-10`, the same string
`Fragment.path` carries — each with its origin. Protocol 5 → 6, `record::FORMAT`
12 → 13, and `store.js`'s pair with them.

**Protocol and not trace, and the line is between the reference and the bytes.**
The rule this project has applied twice — *trace and not protocol, because what
changed is the prompt and not the conversation* — sends `pruned` and `diverged`
to the trace channel. This goes the other way: **that a turn was asked with a
file in front of it is a thing that happened**, and it is what the person typed
when they typed `--fragment`. The bytes are the prompt fact, they are already on
the trace channel inside `prompt`, and they are exactly what this refuses to
store. A client that cannot parse the new message still shows a correct
transcript; a session that cannot read it comes back with turns that never had
code, which is the defect.

**`from_view` re-reads, once, through a sandbox the caller hands it.** The
signature gains `Option<&Sandbox>`, `SessionStore::resume` passes it through,
and `serve`'s resume route already holds the right one — the agency it has just
settled, which is the posture the session is resumed under and not the one it
ran under. `None` restores nothing and is what a caller with no filesystem in
hand gets, which keeps the fold's own tests free of a sandbox.

**A span that cannot be re-read becomes a citation**, which is rule B's
mechanism and is already built, already tested and already guarded. The turn
keeps its exchange, the model is told the span was there and where it was, and
nothing shows bytes the session may not read. The citation says *why* it is one,
because a reader has to be able to tell "this turn gave up its code under
pressure" from "this file is not readable from here" — the two look identical
otherwise and mean opposite things about the policy.

**And the resume says which ones.** A refusal nobody can read was 2026-09-17's
finding one surface along, and a resume that quietly restores four spans of six
is the same shape.

## What was rejected

**Rejected — storing the bytes.** The posture bypass above. It is also the only
option that would make a resumed session's window *different* from what a live
session's would be, since every other path re-reads.

**Rejected — failing the resume when a span cannot be read.** A session that
cannot be opened because a scratch file was deleted is worse than one that opens
with a citation where the file was. The store is a cache of a fold, not a lock
on the filesystem.

**Rejected — restoring only what a person attached.** Tempting once the two
origins are named, and wrong under rule A for the reason §Two things gives: in
`serve` it would restore nothing at all, because nothing there is attached.

**Rejected — re-reading at every render instead of once at the resume.** That is
item 19's second option and it is still an architectural change: `Context` holds
no sandbox and `select` would have to. Doing it at `from_view` needs no such
thing, because the caller is already holding one. The cost is that the repair is
a moment rather than a property, and this record says so rather than implying
the defect is fixed.

**Rejected — a digest of the bytes beside the reference.** Proposed on
2026-09-18 and dropped there as more than the question needs; nothing since has
made it need more. A digest would let a resume *report* that a file changed
while the session was closed, which is a different feature and one nobody has
asked for.

## Found while building it

**A resume reads through the resuming process's root, and that is the whole
point said back uncomfortably.** The sandbox a resume uses is resolved fresh —
the posture it is being resumed *under* — so a session resumed from a different
working directory finds none of its spans and comes back all citations. That is
correct by this record's own argument and it is still a surprise, because the
files are right there on disk. It was found by the warning: a test whose server
selected over a scratch tree resumed into an agency rooted at the package
directory, and the line said *`window.rs:2-4`, which is not readable here* about
a file two directories away. The report earned its keep before the feature
shipped.

**The turn after a resume is inside the job that was open when it stopped.**
Not new and not this change's, but this is the first test to drive it: the
resumed session proposes nothing and gates nothing, because `live_job` is still
`Some`. It is the same fact that makes the history worth restoring at all.

**Selection is not on a blocking thread, and a big tree shows it.** The re-walk
is in `spawn_blocking` with a comment saying why; `select` itself runs inline in
the async block underneath it. Pointing a selecting test server at
`crates/luu` — two files of about five thousand lines — made the turn after an
approval miss a ten-second deadline, with the server's own socket starved
behind it. Worked around here with a three-file scratch tree, and named rather
than fixed: it is a row of its own and it is not item 20's.

## Still open

- **The repair is a moment.** A resumed session is clean at turn 1 and goes
  stale again by exactly the mechanism item 19 describes. Anyone reading a
  divergence count across a resume boundary has to know that, and nothing in the
  recording marks the boundary except the header line the resume writes.
- **No corpus covers this.** `edit-reread.txt` is one session;
  [`a-corpus-that-edits`](2026-09-19.a-corpus-that-edits.completed.md) §Still
  open says the resume case needs that corpus *plus* a resume in the middle, and
  a script has no directive for one. The tests here are unit and end-to-end,
  not a measurement.
- **The origin is carried and nothing reads it.** Named deliberately — see
  §Two things — and the first thing to read it should be the panel, because "the
  person attached this" and "the selector chose this" are different sentences to
  a reader deciding whether the window is doing its job.
- **A restored citation can make the divergence detector fire.** A citation is a
  `Fragment` like any other, so a path restored as one and then read
  successfully by a later turn is a path the prompt sent under two bodies, and
  item 19's detector will say so. The bodies are *a note saying the file was not
  readable* and *the file*, which is not the contradiction that count is about.
  It needs the sandbox to widen mid-session — which cannot happen — or a file to
  be deleted and put back, so it is rare enough to name rather than solve, and
  anyone reading a divergence count across a resume boundary should know it is
  there.
- **A turn restored as a citation is cheaper than it was**, so a resumed
  session's budget is not the budget it had. That is true of the whole fold
  already (a folded job is cheaper than its turns) and it is worth one line here
  because the citation is the first case where the *difference* is a policy
  outcome rather than a summary.
