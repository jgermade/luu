# Measuring prefix reuse, and the first strategy to be judged by it

**Status:** plan, then code. Follows
[`2026-08-27.aider-repo-map.md`](2026-08-27.aider-repo-map.md), which closed with
*"Strategy 1, to be measured against the recorded baseline: evict in blocks"* and
called it the one thing that could start immediately.

It could not, quite. This plan is why, and what goes in first.

## The problem: the number that decides it does not exist

Strategy 1 is judged by prompt-cache reuse. Nothing in the codebase computes it.

`TraceMessage::Prompt` carries the exact string handed to the model, and
`trace.rs` says of it, in a doc comment: *"the panel that diffs this against the
previous turn is the one that shows how much of the stable prefix survived."*
That panel was never built. `similar` is not a dependency, `api::SessionView`
folds `prompt_sent` and stops there, and `store.js` prints the last prompt with
nothing to compare it to.

So the situation is the one `AGENTS.md` names: a change to eviction could land
today, and the only thing anybody could say about it is that it looks better.
**Building the strategy before its instrument is how a context change becomes an
argument.** The instrument goes first, and it produces the "before" from the
baseline that is already recorded.

One thing makes this cheap, and it is worth saying because the opposite was
assumed: **prefix reuse is measurable against the mock backend.** The
context-manager record warns that "the mock backend cannot validate a context
strategy — it does not read the context, so every strategy wins against it."
True of task success. Not true here: reuse is a property of the string we
assemble, decided before the call, by code the mock never touches. Task success
still needs a real model. Reuse does not, and that is the whole reason this is
the first entry in the table.

## Part 0 — the instrument

A new trace message, emitted per turn from the second turn onwards:

```rust
PrefixReuse {
    turn: TurnId,
    /// Bytes of this turn's rendered prompt shared with the previous turn's.
    shared_bytes: usize,
    /// Those shared bytes, counted by the same counter as the budget.
    shared_tokens: u32,
    /// The whole rendered prompt, by the same counter, so the ratio is exact
    /// within one rendering.
    prompt_tokens: u32,
}
```

Four decisions inside that, each of which could have gone the other way:

- **Nothing is emitted for the first turn.** There is no previous prompt, so the
  quantity is undefined — and "0% reuse" on turn 1 reads as a measurement of a
  cold cache rather than the absence of one. An absent panel says the true thing.
- **Counted where the counter lives**, in `agent-core`, not folded out of the
  recording afterwards. A fold sees `prompt_sent` for both turns and could diff
  them for free — including in old recordings — but it has only the counter's
  *identity*, not the counter, so it could report bytes and never tokens. KV
  reuse is token-granular. Bytes alone would be the wrong unit for the one
  number this exists to produce.
- **The shared byte prefix is tokenized as a substring**, so its last token may
  not be a token the model would emit at that boundary. The error is one token,
  the same order as the boundary error `Context::select` already accepts between
  buckets, and the same order as the template overhead we accept and report.
  Precision beyond that would mean owning the prompt string, which is where this
  deliberately does not sit.
- **We diff our rendering, not the templated string.** `session::rendered` is the
  trace channel's rendering and its doc comment already anticipated this: *"the
  panel that diffs two of them only needs them to be rendered the same way
  twice."* The proxy holds because chat templates render message by message in
  order: if messages `0..k` are byte-identical across two calls, the templated
  prefix is identical too. What we measure is a property of the message sequence,
  which is the thing we control and the thing a strategy changes.

`session.rs` grows the tracker that holds the previous prompt, because
`chat` and `serve` must not each invent it — that is what the module is for.
`api::TurnView` grows `prefix: Option<PrefixReuse>`, filled by both folds, under
`folding_live_events_gives_the_same_view_as_folding_the_record`. The panel shows
reuse as a percentage of the prompt with the shared token count beside it.

## Part 1 — block eviction, and a correction it forces

```rust
pub enum Eviction {
    /// Drop exactly as many turns as it takes to fit. The baseline.
    Turn,
    /// When it no longer fits, drop down to a low-water mark instead: the
    /// history is rewritten once every N turns rather than every turn.
    Block { low_water: f32 },
}
```

`--evict turn|block` and `--low-water 0.5` on both subcommands, and the policy
goes in the record header beside `context_limit` and `counter`, for exactly the
reason those are there: two runs under different policies are not comparable, and
by the time you are comparing them nobody remembers which was which.

### The correction: eviction has to be monotone, and today it is not

Block eviction does not work at all without this, which is how the bug was found.

`select` takes `&self` and chooses newest-first every turn against the turns
still in `Context`. Evicting is therefore not a thing that happens to the
history — it is a thing recomputed from scratch each call. So a turn that left
the window **comes back** the moment a shorter prompt leaves room for it.

Under `Turn` that is a rare, harmless-looking waste. Under `Block` it is fatal:
cut to half the history budget, and the next turn's newest-first fill happily
walks back past the cut to spend the full budget again, so the front of the
history moves on every single turn — worse than the baseline it was meant to
beat.

So `Context` gains a floor: the index of the oldest retained turn, which only
ever moves forward. `select` takes `&mut self`. The window a conversation has
already lost is not a view that can be recomputed; it is something that happened.

**This changes the baseline, and the baseline gets re-recorded.** Leaving `Turn`
resurrecting while `Block` cannot would hand the challenger a win against a
straw man — the baseline is supposed to be the dumb thing that has to be beaten,
not the broken thing. Both policies get the floor, and the table below reports
the corrected baseline. Whether resurrection ever fires on this task set is
itself a number worth having.

### What lands with it

- Both policies on the same script, same window, same counter, one table.
- A `--evict block` recording joins the fixtures beside `eviction.jsonl`, so the
  Pages demo shows the two policies side by side rather than being told about
  them. CI regenerates both, so both paths keep their smoke test.

## What this costs

- **`select` is no longer pure.** It was never called twice on one turn, so
  nothing is lost today, but a future "what would this strategy have done"
  preview now needs an explicit dry-run rather than just calling it.
- **`0.5` is a guess.** It is a flag so it can be measured, and it must be:
  inheriting a constant is the mistake the Aider record warned about, and this
  one is not even inherited, it is invented.
- **A fifth fixture** to record on every CI build.
- **Reuse is a proxy, twice over**: our rendering rather than the template, and
  the byte prefix tokenized at a boundary the model may not share. Both are
  bounded and both are stated where the number appears.

## What was rejected

- **`similar` and a span-level diff.** The design names it for the prompt-diff
  panel, and it stays right for *showing* what changed. It is the wrong tool for
  *this* number: a cache reuses a prefix and stops at the first difference, so
  the longest common prefix is the whole measurement, and a diff that finds
  matching spans after the divergence would report reuse the cache never gets.
- **Folding the metric out of recordings in `api.rs`.** Free retrofit for old
  files, but bytes only. See above.
- **A `luu summarize` subcommand for the table.** The table belongs in this file,
  and `jq` over the recording produces it. A reporting subcommand is a thing to
  maintain in exchange for something a one-liner already does.

# 2026-08-27, later the same day: the table

Both parts landed. What follows is what the instrument says, and it is the first
row of a comparison table that was empty this morning.

## What was run

```sh
for policy in turn block; do
  luu chat --script scripts/tasks/steady-state.txt --mock-delay-ms 0 \
    --context-limit 512 --reserve 64 --evict "$policy" --record "$policy.jsonl"
done
```

Same script, same window, same reserve, same counter (`chars/4` — the mock has
no tokenizer, and every number below is labelled approximate for that reason).
One flag apart. `steady-state.txt` is new and exists for this: `long-session.txt`
is six turns, which shows *an* eviction but not what happens after one, and
after one is the entire difference between the policies.

The mock backend is fine here, and this is the claim the context-manager record
would have said was wrong. It said the mock cannot validate a context strategy,
and for task success that stands. Reuse is not task success: it is a property of
the string we assemble, decided before the call, by code the backend never
touches. Nothing below depends on the model having read anything.

## Reuse per turn, 20 turns into a 512-token window

`reuse` is the share of this turn's prompt that the previous turn's prompt
already contained, as a prefix — where a cache stops.

| turn | `turn` reuse | `block` reuse |
| ---: | ---: | ---: |
| 2–9 | 30 → 88% | 30 → 88% |
| 10 | **3%** | 6% |
| 11 | **3%** | **82%** |
| 12 | **3%** | 84% |
| 13 | 4% | 87% |
| 14 | 4% | 9% |
| 15–18 | 4% | 78 → 87% |
| 19 | 4% | 7% |
| 20 | 4% | 82% |

Until the window fills, the two are identical, and reuse climbs: the history is
appended to and nothing is rewritten. Turn 10 is where the baseline falls off a
cliff it never climbs back up. **3–4% is the system block and nothing else** —
from the first eviction onwards, every single call rewrites the history from its
front, exactly as predicted in the Aider record, which is where this started.

The block policy pays for the same cut once every four or five turns and spends
the turns in between at 78–87%.

|  | mean reuse (turns 2+) | history tokens sent | turns spent below 15% |
| --- | ---: | ---: | ---: |
| `turn` (baseline) | 33% | 6113 | 11 of 19 |
| `block`, low-water 0.5 | **67%** | 4842 | 3 of 19 |

## The low-water mark, and the shape it has

| low-water | mean reuse | history tokens sent | turns below 15% |
| ---: | ---: | ---: | ---: |
| — (`turn`) | 33% | 6113 | 11 |
| 0.25 | 68% | 4085 | 1 |
| 0.5 | 67% | 4842 | 3 |
| 0.75 | 63% | 5583 | 4 |
| 0.9 | **37%** | 6011 | 10 |

There is a knee, and it is at the top: **0.9 is the baseline wearing a different
flag.** A cut that shallow leaves the history back over the line within a turn
or two, so it cuts again, and the front moves nearly every turn. That is worth
more than the winning row — it says the mechanism is the cut *depth*, not the
policy's name, and a badly chosen constant gives all of it back.

Below that the curve is flat in reuse and steep in history: 0.25 buys one point
of reuse over 0.5 and pays 16% of the history for it. **0.5 stays**, now as a
measured choice rather than a guess.

## What this is not

**It is not "fewer tokens".** The block policy sends 21% less history, and less
history is less of what the model was told. The context-manager record's own
warning applies to this table: dropping the fragment the model needed is also
fewer tokens. Whether a 7B model answers turn 18 as well with a shorter window
is a question about task success, and nothing here answers it.

**It is not wall-clock.** Reuse is what a prefix cache *could* use. What it
saves is prompt-eval time in llama.cpp, and we have not measured a second of it.
Against Ollama's `/api/chat` we do not even control the templated string the
cache actually sees — the rendering we diff is a proxy, stated as one.

So the honest reading is: the baseline had a defect this instrument makes
visible, the block policy fixes it in the quantity the instrument measures, and
the two questions that matter next both need a real model.

## The correction, and whether it mattered

Eviction is monotone now, for both policies. On this task set it changed nothing
measurable — the prompts are of a size that never freed enough room to pull a
dropped turn back — so the baseline in the table is the baseline as it was, and
`a_turn_that_left_the_window_does_not_come_back_when_room_reappears` is the only
place the difference is visible. It was still worth doing before the comparison
rather than after: a floor is what makes the block policy a policy at all.
