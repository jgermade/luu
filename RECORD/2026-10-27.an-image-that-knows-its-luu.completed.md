# An image that knows its luu

The same day as
[`runtimes-without-the-wait`](2026-10-27.runtimes-without-the-wait.completed.md),
Jesús:

> *Si hay cambios en el código que afecta a luu-worker:dev, ¿se regenera
> luu-worker:dev?*

No. Nothing rebuilt it, and only part of the problem was even noticed.

## What was true

- **Settings said `built` if `image inspect` found the tag.** It did not
  check which luu the image came from.
- **The handshake compared one number, `PROTOCOL`.** An image whose worker
  spoke another protocol was refused (*rebuild it*) and left as it was.
- **Anything else went unnoticed.** That covers a change to `read_file`,
  `run_command`, Landlock or seccomp that did not bump the protocol, a new
  package in `Containerfile`, or an upgrade through `setup.sh` from 0.1.4 to
  0.1.5 with the same protocol. The session ran the old worker inside the
  container and nothing said so.
- **`Hello.version` was printed and never compared.** It would not have
  helped anyway: between releases, a development build and the image both
  say `0.1.4` while their code differs.

The protocol number alone has failed before. `Authority::Person` landed
without a bump, and an image built that morning answered approved writes with
`unknown variant 'person'` (see the doc comment on `PROTOCOL`).

## The proposal

**The worker says which sources it was built from.**
`crates/agent-core/build.rs` hashes the worker's sources and passes the
hash to the compiler as `LUU_WORKER_BUILD`. It covers every file under
`crates/agent-core/src`, `crates/agent-core/Cargo.toml`, the workspace's
`Cargo.toml` and `Cargo.lock`: path and bytes, sorted, FNV-1a, 64 bits.
`Hello` gains `build`.

- **A content hash, not a commit.** The proposal in chat said *version and
  commit, with a dirty mark*. A dirty mark cannot tell two different
  uncommitted states apart, and uncommitted edits are exactly the case a
  developer of the worker is in. A source build also has no `.git` to read,
  because `.dockerignore` leaves it out. The content hash needs neither
  git nor a build argument. Inside the image it is computed over the same
  files the `COPY` brought in, so a source build and the host that ordered
  it agree when their sources do.
- **agent-core's sources, not the whole binary.** `luu worker` is
  `serve_stdio(Tools::standard())`, and everything a call does there is
  agent-core. A change to `serve.rs` does not make an image stale. A change
  to `Cargo.lock` does, which is conservative: one of agent-core's
  dependencies may have moved.
- **An optional field, not a protocol bump.** `Hello` has no
  `deny_unknown_fields`, so an older host ignores the field. A worker that
  does not send it is reported as being from before workers said what they
  were.

**One rule says whether an image is current: `Hello::differs`.** It returns
`None` when version and build both match this luu's, and otherwise a
sentence saying how they differ. `luu tools` prints it under the worker
line. The session start and Settings use the same rule.

**luu labels what it builds**: `--label luu.from=release` or
`luu.from=source`, which all five runtimes' `build` take. That is how luu
knows which images it may rebuild by itself. An image without the label was
built by hand, or by luu before this change, so luu only warns about it.

**At session start**, after the worker starts or after the handshake
refuses it for its protocol:

| image | its luu is a different **version** | same version, other **sources** |
| --- | --- | --- |
| `luu.from=release` | rebuilt from this version's release, then the worker started again | said: a release cannot help, *from source* can |
| `source`, or no label | said: rebuild it | said: rebuild it |

The rebuild happens while the old worker is still running, because a tag
in use can be rebuilt. If the rebuild fails, a worker that did start keeps
the session and the failure is said. If the handshake had already refused
it, the session fails with both reasons.

**In Settings**, each image that is present has its worker started once,
with nothing to do: `<runtime> run --rm --network none <image> luu worker`
with no stdin. It says its hello and exits when its input ends. That is the
handshake itself, so it needs no new command line and no bookkeeping that
could disagree with the image. The row then reads
`built · luu 0.1.4 (3f2a9c1b)` or `out of date` with the reason, and *build*
or *from source* is offered for a rebuild too, not only when the image is
missing.

## What it costs

- **A container start per present image per probe**, which means about a
  second on a VM-backed runtime. Probes are already one per runtime and only
  happen on open and on *check again*, so it delays that runtime's card and
  nothing else.
- **A build script in agent-core.** It hashes about a megabyte of source.
  It reruns when agent-core's sources, `Cargo.lock` or `Cargo.toml` change,
  and agent-core recompiles in those cases anyway. It needs no node and no
  git.
- **Every development change to agent-core makes a source image stale.**
  That is accurate. The session still starts, and says it.

## Rejected

- **Rebuilding source images by themselves.** That costs minutes, on every
  edit to agent-core.
- **Labels for the identity** (`luu.build=…` set at build time). A release
  build cannot know the release binary's hash before it fetches it, and a
  label is a claim about the image while the hello comes from the image.
- **The whole binary's sources in the hash.** Every change to the server
  would make every image stale.

## Still open

- **A stale image is said in the log and on stderr, not on the page's
  session.** Settings shows it. Whether the terminal's posture line should
  say it as well is for later.
- **`--label` on Apple's `container build`** has been taken from its
  documentation and not run.

## Built, the same day

As proposed, plus one change found while looking at the page.

- **`crates/agent-core/build.rs`** writes `LUU_WORKER_BUILD`, which
  `agent_core::worker::BUILD` reads. `Hello` gained `build`,
  `Hello::identity` (`0.1.4 (023096d0)`) and `Hello::differs`.
  `WorkerError::Protocol` now carries the worker's version. `luu tools` prints
  the identity on the worker line, and a `stale` line under it when the two
  differ.
- **`Runtime::build_argv` takes labels** and **`Runtime::hello_argv`**
  starts an image's worker with nothing to do (`--network none` where the
  runtime can say it). `crate::runtimes` labels its builds and reads the label
  back by key from `image inspect`'s JSON, wherever a runtime puts it
  (`built_from`). It also asks an image's worker for its hello (`hello_of`)
  and rebuilds from the release for a session that is waiting (`rebuild`).
- **`start_worker`** in `lib.rs` holds both of a session's repairs: a runtime
  that is down, from the record before this one, and an image that is not this
  luu's, from this one.
- **The change: what would cure it.** In the first screenshot, a release
  image of this same version, from before a worker said its build, offered
  *rebuild*. That rebuild would only fetch the same release again. Each image
  now also says `cure: release | source`. *Rebuild* is offered only where the
  release would change something. Otherwise the row says that only a build
  from source can make the image this luu's worker.

**Run here, on Linux with Docker.**

- An image of v0.1.4's release (a worker from before `build`), labelled
  `release`, read `out of date · luu 0.1.4 · from release`. Settings offered
  only *from source*, and `luu tools` printed the same reason under `stale`.
- An image of this branch's own binary (on `ubuntu:24.04`, whose glibc this
  machine's build needs, which is the earlier record's point) answered the
  bare `docker run --rm --network none luu-worker:dev luu worker </dev/null`
  with `{"kind":"hello","protocol":2,"version":"0.1.4","build":"023096d0ab2b429d",…}`.
  Settings read `built · luu 0.1.4 (023096d0) · from source`.
- Adding one comment line to an agent-core source file and rebuilding moved
  this luu to `d7a20ec4`, and the same image became `stale … built from other
  sources`. Removing the line brought back `023096d0`, and the image was
  current again.
- A copy of the tree without `.git` and `target/`, which is what a source
  build's context holds, checked under another path and another target
  directory, produced the same `LUU_WORKER_BUILD=023096d0ab2b429d`. A source
  image and the host that ordered it agree without git and without a build
  argument.

**Tested.**

- `tests/runtime_wake.rs`'s stand-in `colima` now also plays an old worker
  (a hello from a file, then nothing until its input closes), returns labels
  from `image inspect`, and runs `build`. Five new cases, through `luu tools`:
  - a release image of another version is rebuilt with
    `-f Containerfile.release --build-arg LUU_VERSION=<this> --label luu.from=release`,
    and the session ends on this luu's worker with no `stale` line;
  - one refused for its protocol is rebuilt too;
  - a `source` image and an unlabelled image are reported, kept, and left
    unbuilt;
  - a release of this same version from other sources is not rebuilt, and
    the message says only a build from source can help;
  - a rebuild that fails keeps the worker the session has, and says so.
- Unit tests:
  - `Hello::differs` covers version, build, and a hello with no build;
  - a hello without `build` still parses, and one with it still serializes;
  - the label is found in Docker's shape and in Podman's;
  - each build line carries its `luu.from`.
- In `settings.spec.js`, each image in a probe carries `from`, `worker`,
  `stale`, `cure` and `unasked`. 23 of 23.
