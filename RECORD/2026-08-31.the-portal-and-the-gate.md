# The portal and the gate: what federating this costs

**Status:** argument, not a decision. Nothing here changes
[`loude-design.md`](../loude-design.md) — it is still the current answer to
*what is true today*, and a federated architecture is not true today.

A draft plan arrived on 2026-08-31 (*"Loude — Sistema Federado de Agentes"*,
v0.1-draft) proposing that Loude become a federation of sovereign hosts around a
stateless portal. It is written as a design document rather than as a record, so
this file is the record: what it proposed, the four places it collides with
decisions already made here, and what I would do instead. The proposal is worth
arguing with rather than routing around — which is the rule in
[AGENTS.md](../AGENTS.md), and it cuts both ways.

## What was proposed

- Every machine runs `loude-host` (or `luu host`, replacing `luu serve`) with its
  own `~/.loude/sessions.db`. The host owns its sessions; the portal never holds
  turn content.
- Hosts hold a persistent **outbound** WebSocket to a portal. No open ports, no
  public IP.
- The portal keeps two tables — a host registry (online, capabilities) and a
  session index (title, status, model, `updated_at`) — plus a relay that tunnels
  a browser to a host, forwarding frames without inspecting them.
- Session transfer is **explicit**, `git push`/`git pull` shaped: `luu export`
  writes a `.loude` file (a JSON snapshot of turns, tasks, floor, budget, and
  evidence — file contents and command outputs — zstd'd), `luu import` reads one,
  `luu transfer` moves one between hosts through the portal.
- Six phases: host daemon → relay → portability → multi-backend → cloud workers →
  optimizations (direct connection, E2EE, evidence compression).

## Where it is right

Four things in it are right and are worth keeping whatever happens to the rest.

- **Outbound-only.** It is the only shape that works from a laptop, and it is
  strictly better than the alternative anyone reaches for first, which is telling
  people to bind `serve` to `0.0.0.0`.
- **Transfer as an act, not a migration.** Consistent with the one authority rule
  this project already has: *the user is the only thing that closes a task*. An
  agent system that silently relocated a session would be deciding something the
  rest of the design refuses to decide for the user.
- **The container is already step 5.** `loude-worker` is level 3 under another
  name, and the plan's version of it (gvisor in cloud, Landlock locally) is
  compatible with what §Container mode already says.
- **Multi-backend is cheap and it is owed.** `Backend` is a trait with two
  implementations; a third is small. The honest reason to want it is not product
  reach, it is *measurement*: the whole context-management argument is stated for
  8K–32K windows and nobody here has ever run the corpus at 128K to see how much
  of it still pays for itself.

## Four collisions

### 1. `.loude` is a second truth

[`loude-design.md`](../loude-design.md) §Persistence:

> **Whatever the store holds must be reproducible by folding the record.** The
> JSON-lines stream is the account of what happened, and `api::SessionView`
> already folds it; a store that accumulates state the events cannot regenerate
> is a second truth, which is how the static mirror and the live server start
> disagreeing.

The `.loude` of §7.2 is that second truth, in a new file format, built by new
code, with its own `"version": 1` to maintain alongside the record format that is
already at **5** and the protocol already at **v3**.

And the portable format already exists. `--record` writes an append-only event
stream; `SessionView` folds it; `luu export` folds it into a static site that a
server-less host serves, which is the *only* reason anyone can trust the fold —
the live server and the static mirror are checked against each other because they
are the same fold. A transfer built on the same stream inherits that check for
free. A transfer built on a snapshot needs its own, and will not get one.

So the shape is:

```
luu transfer sess-abc --to cloud-worker-1
  → the record for sess-abc, its fixtures, and a manifest
  → destination appends nothing, folds it, and has the session
```

Not a snapshot of `Context`, which is a rendering of the events, taken at one
moment, by code that will drift from the events the first time either changes.

Two smaller things fall out of this. `luu export` is **already a subcommand**
(`crates/luu/src/lib.rs:50`) and means something else; the plan needs a different
verb or a different noun. And a snapshot cannot answer *"resume from turn 5"*
honestly, which the plan's own CLI transcript claims it does — resuming is a
position in a stream, which is what a stream has and a snapshot does not.

### 2. The format carries no policy, and narrowing dies at the border

This is the one that is not a matter of taste.

Since #8, the commitment is: **the approved plan is the sandbox for its task.**
A plan naming `writes: ["src/auth.rs"]` is checked against `luu.toml`, and from
approval to close the task may touch what the plan named and nothing else.

The `.loude` of §7.2 has `session.tasks[].plan` and no policy, no sandbox, and no
`luu.toml`. §7.4 then says:

> los paths absolutos del host origen se convierten a relativos en el `.loude`.
> Al importar, el host destino los resuelve contra su working directory.

Which means a write a person approved over one tree is re-resolved, without a
second approval, over a different tree. `src/auth.rs` on the origin and
`src/auth.rs` on the destination are two files. The gate happened once, on the
origin, about paths that no longer exist.

The nearest-existing-ancestor rule makes this worse rather than better: it is the
widest thing in #8, it exists so a plan can name a file it is about to create,
and it has only ever been exercised by hand against `/tmp`. Import is the first
place it would meet paths chosen by someone other than the person approving.

The rule this needs, and it should be in the format rather than in prose:

- **An imported task in any state but `Closed` returns to the gate.** The
  destination re-runs the plan against its own `luu.toml` and a person approves
  it there, in the destination's paths. A plan that does not resolve imports as a
  refused proposal, not as an approved task with dangling paths.
- **The manifest names the origin's resolved sandbox**, so the person approving
  on the destination can see what the task was allowed to do before, and the
  difference. *Nothing may say "sandboxed" without saying by what* has a sibling
  here: nothing may arrive approved without saying approved **where**.

Closed tasks are fine — they are summaries, they run nothing.

### 3. The relay carries `approve_task`

Today `serve` is loopback. The debt is named in three records: *auth, if `serve`
is ever bound off-loopback*.

The plan binds it off-loopback in phase 2 and puts E2EE in **phase 6**, as an
optimization, next to WebRTC and evidence compression. That inverts the order the
risk is in, because of what travels through the tunnel.

`approve_task` is on that wire. An approval is not a UI convenience: it grants
read over the task's `files`, read-write over its `writes`, and the commands the
plan named — including `run_command`, which is the thing the parent builds a
Landlock ruleset and a seccomp filter for and then `exec`s. **Whoever can put a
frame on the relay can approve a plan**, and approving a plan is the whole
mechanism by which anything in this system is allowed to touch a disk.

TLS on both legs does not address this. It protects the frames from everyone
except the party in the middle, and the party in the middle is the portal. A
"transparent proxy that does not inspect the payload" is a design intention, not
a property the host can verify.

The minimum for phase 2, before a single host is reachable through a portal:

- The client signs approvals with a key the portal does not hold. The host
  **rejects an unsigned or badly-signed approval** the same way it refuses a
  prompt behind the gate — as a `Refusal` on the wire, which is a variant that
  already exists and would need one more reason.
- The host verdict records who approved, so a recording can distinguish a plan a
  person approved at the keyboard from one that arrived over a relay. Same rule
  as `Authority` on the sandbox verdict, for the same reason: afterwards the
  recording is the only thing that could tell them apart.

That is a phase-2 requirement. It is not an optimization and it is not E2EE for
privacy — it is what stops the portal being a remote code execution path by
construction.

### 4. Nothing negotiates the protocol version across the relay

Today the UI ships **inside** the binary — `rust-embed` reads
`crates/luu/ui/` from disk in debug and bakes it in for release — so the client
and the host are the same artifact and cannot disagree.

Federation splits them: the portal serves the UI, the host speaks the protocol,
and they are deployed by different people on different days. In a tree where one
new enum variant took the protocol to **v2**, another to **v3**, and the record
format to 4 and then 5 — inside one week — a relay that forwards frames blind is
forwarding them between two versions nobody checked.

`ClientMessage`/`ServerMessage` need a version in the handshake and the host needs
to refuse a client it cannot parse, out loud. The relay stays transparent; the
endpoints stop assuming.

## The claim that needs a probe, not a phase

> Una sesión exportada desde un host con Ollama puede importarse en un host con
> OpenAI y continuar **sin pérdida de contexto**.

Nothing here knows that, and this project has a precedent for exactly this shape
of claim. Folding a closed task into a summary was believed to be lossless, and
was not: against a real 7B, **two of four** closed-task questions came back wrong,
one of them a refusal — and it was only known because
[`2026-08-27.grounded-fold-probe.md`](2026-08-27.grounded-fold-probe.md) wrote
down what to run and what a right answer contains *before* anyone ran it. The
fold's question got answered twice while the gate's, which has only a table row,
has not been asked once. The difference is not the machine.

There are also two mechanical reasons to expect loss, not just to fear it:

- Every count in a session is stored with the `Counter` that produced it
  (`Counter::Model { id }`), precisely so that a resumed session does not sum two
  units into one bar. A history measured with Qwen's tokenizer, continued against
  another model, has a budget whose every number was measured with a different
  ruler.
- Eviction and the fold are **decisions already taken** under the origin's
  window. A session evicted down to fit 8K and then continued at 128K is not the
  session that would have existed at 128K; it is a smaller one, permanently. The
  tombstones say so, which is the good news — but "continue without loss" is
  false in the direction that matters and the recording can prove it.

So: write the transfer probe before the transfer. At minimum it has to separate
*the destination model answered worse because the history moved* from *the
destination model is worse*, which needs the same session continued on the same
model on both hosts as the control.

## What the proposed order costs

**Relevance selection is the only unbuilt piece of step 2**, and step 2 is the
stated differentiator — *"what gets into the prompt, and what earns its place
there"*. The repository makes its own case: the whole outline is 6 327 tokens,
77% of an 8K window, so at any affordable budget most of the repo is missing and
**path order chose which part**. The baseline is recorded and waiting to be beaten.

The plan spends six phases on registry, relay, transfer service, OAuth, worker
images and autoscaling. Every agent product has a cloud relay. None of that is
the thing this one is for, and all of it has to be operated forever once it
exists.

## What I would do instead, in order

1. **Sessions in SQLite, derived from the record.** Blocks everything else here —
   there is no session to transfer while `serve` forgets on restart — and it is
   the piece where the "reproducible by folding the record" rule gets its first
   real test.
2. **The gate probe against a real model.**
   [`2026-08-31.the-gate-probe.md`](2026-08-31.the-gate-probe.md) is written and
   unrun. No model has ever proposed a plan that this tree then held it to, and
   federation makes the gate remote — asking a remote gate to work before knowing
   the local one does is the wrong order.
3. **Relevance selection.** The last of step 2, and it has to beat the path-order
   baseline the map now records.
4. **Multi-backend**, framed as measurement: how much of the context strategy
   still pays at 128K.
5. **Federation, starting without a portal.** `luu host` ↔ `luu host` on a LAN,
   transfer over the record stream, approvals signed. If host-to-host transfer
   does not earn its place, the portal does not either — and if it does, the
   portal is then a discovery and relay problem with the hard parts already
   solved.

## Rejected here, and why

- **`.loude` as a snapshot.** Second truth. The record is the format.
- **`luu host` replacing `luu serve`.** `serve` is the instrument step 2 is
  measured with — *"early, because it is the instrument used to measure step 2"* —
  and it is what `crates/luu/tests/serve_ws.rs`, the fixtures, and the deployed
  page use. `host` wraps it; it does not take its name.
- **E2EE and signed approvals as phase 6.** See collision 3.

## Still open

- **Push or pull.** The plan leaves it open; the record being append-only argues
  for push (the origin knows what it has), but the destination is the side that
  has to re-approve, so the handshake is two-sided either way.
- **A session on two hosts at once.** The plan asks it as *last-writer-wins vs.
  manual merge*. With an append-only stream, neither: it is a **fork**, and the
  useful question is whether to forbid it (origin marks the session archived on
  transfer) or to name it and let two branches exist. Forbidding is smaller and
  is what I would ship first.
- **Whether evidence leaves the machine at all.** `.loude` embeds file contents
  and command outputs, and §8.2 uploads them to a transfer service with a 24h
  TTL. For a local-first project that is the single largest thing in the design
  pointing the other way. Encrypted-blob-the-portal-cannot-read is the obvious
  answer; whether it is enough is not obvious.
- **Reading the context window from the backend** rather than `--context-limit`
  being a flag someone sets right. It was already open, and transfer makes it
  sharper: the destination's window is a property of the destination.
- **Billing.** Out of scope, agreed.
