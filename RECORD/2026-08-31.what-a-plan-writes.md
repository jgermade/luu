# A plan that says what it will write

**Status:** plan, then code. It is the first of the design's open questions —
put there yesterday by [`2026-08-30.narrowing.md`](2026-08-30.narrowing.md),
which could not cut the *level* of access because a plan had no way to say which
level it meant. It also closes an item that has been in `RECORD/` since the
tasks work: *a plan that distinguishes what it will read from what it will
write*.

## The hole, precisely

`Plan::unmet` asks one question per file: is it readable?

```rust
let check = sandbox.check_path(Path::new(file), Access::Read);
```

So a plan that names a file under a `read` root and then edits it **passes the
gate** and is denied at the call, four turns in — which is the exact failure the
check exists to prevent, and the one case it misses. Its own doc comment has
said so since the day it was written.

Narrowing made the second half of it visible: a task's sandbox grants each
planned file *whatever the policy grants*, read-write included, because a plan
that cannot say "I will only read this" cannot be held to it. Every task
therefore runs with write access to everything it named, whether it meant to or
not.

## The shape

`Plan` gains `writes`, beside `files`:

```json
{"objective": "add a --dry-run flag",
 "steps": ["read the CLI", "add the flag"],
 "files": ["crates/luu/src/lib.rs", "AGENTS.md"],
 "writes": ["crates/luu/src/lib.rs"],
 "commands": ["cargo"]}
```

`files` is what the task may **read**; `writes` is the subset it may also
**change**. A path in `writes` need not be repeated in `files` — writing implies
reading, because `edit_file` reads before it replaces.

- **`unmet`** checks `files` for `Read` and `writes` for `ReadWrite`, so a write
  into a read-only root is refused *at the gate*, by name.
- **`narrow`** grants `Read` for `files` and `ReadWrite` for `writes`. That is
  narrowing on level, which yesterday deferred: a task that declared a file and
  did not declare a write may read it and cannot touch it, even where the policy
  file would allow both.
- **The script** gains `## write:`, next to `## file:`.
- **The planning instruction** asks the model for both lists, because a model
  that is never asked will never say.
- **The gate** gains *add write* beside *add file*, and `approve_task` a
  `writes` amendment. Additive with a default, so no version bump: v2 stays.

## Strict, and what that costs

A plan that declares no `writes` may not write. That is a behaviour change for
any task that edits a file it only listed under `files` — today they all do,
because there was nothing else to list — and it is the point: the check is worth
having only if the answer can be no.

The four scripts in `scripts/tasks/` read and never write, so none of them
changes. What does change is the first real editing task against a 7B: it will
propose a plan with `files` and no `writes`, try to edit, and be denied by its
own plan. The denial names the plan and the file, the gate has an *add write*
field, and the person is right there. That is the same trade the whole gate
makes, and it is why this waits until after the gate rather than before it.

## The thing narrowing got wrong, found writing this

`Sandbox::new` requires every granted path to exist — Landlock takes a file
descriptor per root, so it must. `Plan::narrow` passes the plan's paths straight
into it, which means **a plan naming a file that does not exist yet fails to
resolve**, and yesterday's code then logs a line and runs the task with nothing
granted. A plan that says "I will create `src/flag.rs`" is exactly the ordinary
case, and it produces a dead task.

The rule this change adopts, which is also what the kernel rung can actually
express:

- **A read of a path that does not exist grants nothing.** There is nothing to
  read; `read_file` will say so.
- **A write to a path that does not exist grants its nearest existing
  ancestor**, at `ReadWrite` — because creating a file *is* a write to its
  directory, and at the kernel rung a grant is a directory anyway. A file-level
  grant is an in-process fiction; this is where that shows.

The second one is wider than what the plan literally said, and it is the honest
resolution rather than a convenient one: the alternative is that no plan can
ever create a file. It is called out in the verdict text and in the gate's plan
view, so the person approving sees the directory rather than only the file.

## What was rejected

- **Making `files` a list of `{path, access}` objects.** It is the tidy shape and
  it breaks every plan a model has ever emitted, every script in the repository,
  and the parse in one go. Two flat lists cost one field and read better in a
  fenced block a 7B has to produce.
- **Lenient mode: `files` keeps granting write when `writes` is absent.** Then
  the check still passes a write into a read-only root, which is the entire bug.
  A rule that only applies to plans that opt in is not a rule.
- **Inferring writes from the steps.** "add the flag" is prose; guessing a write
  out of it puts a permission decision in a string match.
- **Granting the file itself for a not-yet-existing write, by creating it.**
  Touching a file to make a grant resolvable is the sandbox writing to the disk
  in order to decide whether it may write to the disk.

## Still open after this

- Narrowing `network` and `enforcement`, which still needs a plan that declares
  them.
- Whether `writes` should also gate `run_command`: a command can write anything
  its own grants allow, and the plan's `commands` list says nothing about paths.
  The kernel restrictions for a child are built from the *task's* roots now, so
  this is already narrower than it was — but a command remains the widest thing
  a plan can ask for, and nothing here changes that.

## 2026-08-31, later: built

`writes` is in the plan, the script (`## write:`), the planning instruction, the
gate (*add read* / *add write* / *add command*) and `approve_task`. `unmet` asks
`Read` of `files` and `ReadWrite` of `writes`; `narrow` grants exactly those.
Additive fields with defaults again, so v2 stays v2.

Driven through the real page against a real server, the same task twice.
Approved as the model proposed it — `reads: Cargo.toml`, no writes:

```
write_file {"content":"written by the task","path":"/tmp/luu-gate-write.txt"}
denied  no rule grants read-write on /tmp/luu-gate-write.txt, under the approved plan for task 1
```

and the file was not there afterwards. Then the same plan with the path typed
into the gate and *add write* pressed:

```
allowed  /tmp (read-write)
         held by an in-process check · 0 ms · 39 bytes back
```

with the file on disk holding what the task wrote. Note what the verdict names:
**`/tmp`, not the file** — the path did not exist, so the grant is the directory
that will hold it, exactly as this file argued it has to be. The widening is
visible in the verdict rather than hidden in the resolution, which is the part
that makes it acceptable.

The four scripts in `scripts/tasks/` read and never write, so the recipe is
unchanged; all three were run end to end against the mock.

### What this fixed that was not the point

Yesterday's narrowing passed the plan's paths straight into `Sandbox::new`,
which requires every granted path to exist. A plan naming a file it was about to
*create* therefore failed to resolve, and the task ran with nothing granted at
all — a dead task from the most ordinary plan there is. It never showed up
because no plan in the repository names a file that is not there. The
existence rules this change had to write for `writes` cover it: a read of a
missing path grants nothing, a write to one grants its nearest existing
ancestor, and `narrow` no longer fails.
