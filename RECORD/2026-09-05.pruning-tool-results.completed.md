# Pruning tool results: the cap is not the strategy

**Status:** plan, then code. Takes item 6 off
[`ROADMAP/2026-09-05/`](../ROADMAP/2026-09-05/README.md), which is one of the three
entries that link to the design's open questions instead of to an argument —
*ordered but not yet argued*. This is the argument.

## The problem

A tool result is written once and then paid for on every call until its turn
leaves the window.

`ToolOutcome::ok` clamps output at `MAX_OUTPUT_BYTES` (8 KiB) and the doc comment
beside the constant has said what that is since the day it was written:

> Tool output is capped rather than pruned. Pruning old results out of the
> history is a later, measured change; a cap now is the part that is not a
> strategy — a `cat` of a 2 MB file must not be able to blow the window open.

The cap bounds **one** result. Nothing bounds their sum, and the sum is what
fills a window: eight `read_file` calls at the cap are 16 K tokens of a history
block, which is more than the whole window of the machines this project is built
for. The asymmetry is the point — a tool result's *value* decays within a turn
or two (the model read the file, used it, answered), while its *cost* is paid on
every call for as long as the turn is above the floor.

Three mechanisms already act on the history and none of them reaches this:

- **Eviction** drops the oldest turns *whole*, results included — but only once
  the window is already full, and it takes the conversation with them.
- **The fold** replaces a *closed* job with a deterministic summary. It reaches
  a result only after the job that produced it is finished, and a session with
  one long-running job never gets there.
- **The cap** acts at write time, per result, and never again.

So between them there is a hole exactly the shape of a live turn that read a big
file four turns ago: too recent to evict, in a job too young to fold, capped
already and therefore untouched. That turn's 8 KiB is in every prompt.

What makes it worth fixing rather than waiting out: the thing that gets evicted
to make room for it is the *conversation* — the prompts and answers, which are
small, dense, and the only part of the history a model cannot re-derive. A run
that drops turn 3 to keep the bytes of a file listing has its priorities exactly
backwards, and today that is the only trade the context manager can make.

## The proposal

**A second floor.** `Context::floor` is the turn below which nothing exists any
more. `Context::prune_floor` is the turn below which the *steps* exist but are
rendered as a digest: the exchange keeps its shape, and loses its bytes.

```
floor                    prune_floor                     len
  |------------------------|--------------------------------|
   gone, and never          in the prompt as              in the prompt
   coming back              call + digest                 verbatim
```

Like the eviction floor it **only moves forward**. A pruned result that came back
would rewrite the history block on both edges — and would show the model a file's
contents reappearing after it had been told they were gone, which is a worse lie
than either state on its own.

### The digest is deterministic and it is not prose

Same rule the fold already lives under: the summary of a closed job is the plan,
the paths, the commands and the exit codes, never the model's own sentences,
because a summary enters the write-once region every later turn is built on. A
pruned step renders as its own first line — which `ToolOutcome::render` already
builds out of the structured fields — plus one line naming what left:

```
[read_file] ok
[read_file] 5130 bytes elided (pruned)
```

and for a `run_command` that failed, the first line is *already* the fact worth
keeping (`[run_command] cargo exited with 101`), because the exit code became a
field in [`what-the-audit-left`](2026-09-01.what-the-audit-left.completed.md) and
`render` puts the error before the output. So the digest keeps *that it ran, and
how it went*, and drops *what it printed*. The call itself — the assistant half
of the exchange — is never pruned: it is short, and a result with no call is a
result the model cannot attribute.

### Two policies, and they are the eviction argument on a different axis

```rust
pub enum Pruning {
    Off,
    Age { keep: usize },
    Watermark { keep: usize, above: f32 },
}
```

- **`Age { keep }`** prunes every step outside the newest `keep` turns. The
  boundary moves *every turn*, so the history block is rewritten from the middle
  on every call — which is precisely the failure `Eviction::Turn` has, on a
  different axis, and it is here to be the baseline rather than the answer.
- **`Watermark { keep, above }`** prunes nothing until the steps in the window
  are worth more than `above` of the history budget, and then prunes everything
  but the newest `keep` in one cut. Deep and infrequent: the block is rewritten
  once every N turns and is byte-identical in between, which is what a prefix
  cache pays for.

`low_water` was invented for `Eviction::Block` and made a flag so it could be
measured rather than defended; `above` is the same and is a flag for the same
reason.

### Decided, then rendered — so the record keeps what the prompt lost

`Turn::steps` keeps the full text. Pruning is a **rendering** decision, taken in
`Context::select` from the prune floor, exactly as the fold is. Three things
fall out of that and each of them would be lost by mutating the steps in place:

- `fold(record) == load(store, id)` still holds, and a stored session still
  replays at full fidelity.
- The debug UI can show *what the model no longer sees*, which is the one thing
  a debug client is for — the same argument that keeps an evicted turn in the
  transcript with a line through it.
- Re-reading a pruned file is a `read_file` away, and the sandbox and the plan
  still say whether it may be read. Pruning forgets; it does not forbid.

The cost of not mutating: a turn's stored `tokens` no longer describes what is
rendered once its steps are pruned. `Turn` gains `steps_tokens`, counted once at
`push_turn_with_steps` beside `tokens`, so a pruned turn costs
`tokens - steps_tokens + digest_tokens` and nothing is re-counted per turn per
turn. Additive and `#[serde(default)]`; a stored turn from before it re-counts
once on resume.

### Pruning is decided before eviction, and that ordering is the whole point

`item_tokens` and `fits_from` see pruned costs, so a turn that pruning shrank
may now fit where it would have been evicted. That is the trade this exists to
make: **give up the bytes to keep the turns.** The two floors cannot deadlock
over it, because the prune floor is computed from the end of the history (the
newest `keep` turns) and never from the eviction floor.

## What goes on the wire

One message, the same shape and the same argument as `evicted`:

```jsonc
{"type": "pruned", "turn": 9,
 "turns": [3, 4, 5],
 "tokens": 4102,
 "counter": {"kind": "model", "id": "qwen2.5-coder:7b"},
 "policy": {"policy": "watermark", "keep": 2, "above": 0.35}}
```

- **`turn`** — the turn whose selection pruned them, because pruning happens
  when the *next* prompt is assembled.
- **`tokens`** — what came off, by a named counter, because a count whose
  counter is not named is not comparable to any other count in this system.
- **`policy`** — for the same reason the eviction tombstone carries one: the
  whole difference between the two policies is when and how deep, and a reader
  who has to subtract to find out has been failed by the record.

That is a new variant of a tagged enum, which is the rule that took the protocol
to 2, 3, 4 and 5: **protocol 7 and record format 9** (6 and 8 are the burned
numbers from the transfer mechanism that was un-made). A client that cannot parse
it would be showing a transcript whose tool output is silently no longer in the
prompt — which is the eviction-tombstone argument, verbatim, and it was right
then.

The header gains `pruning`, additively, beside `eviction` and for the same
reason: two runs under different policies are not comparable, and by the time
anyone is comparing them nobody remembers which was which.

`TurnView` gains `pruned` (what this turn's selection pruned) and `pruned_by`
(the turn whose selection pruned this one's results), mirroring `dropped` and
`evicted_by` exactly.

## What "better" means here, stated before the run

Off by default, because it changes every number in every recording made so far.
So the measurement is a comparison of one flag, on a script that makes a tool
call per turn against real files in this repository, with everything else held:

1. **Prompt tokens over the run.** Pruning must win here or it does nothing at
   all. The interesting number is not the win, it is the win *net of what it
   cost in evictions avoided*.
2. **Turns evicted.** The claim is that pruning trades bytes for turns. If a
   pruned run evicts as many turns as an unpruned one, the trade did not happen
   and the policy is only shrinking prompts.
3. **Prefix reuse, under each policy.** `Age` is expected to lose to
   `Watermark` here, for the reason `Eviction::Turn` loses to `Eviction::Block`:
   a boundary that moves every turn rewrites the block every turn. If it does
   *not* lose, then the block being rewritten is smaller than the argument
   assumes and the watermark is not worth its second flag.

A fourth thing this run cannot say, stated now so it is not claimed later:
**whether the model still answers.** Coverage of the answer is not use of it —
the same gap `choosing-fragments` left open and the same box it needs. What is
measurable without a model is that the digest keeps the exit code and the call,
which is what the closing ladder rests on; what is not is whether a 7B four
turns later needed the bytes.

## What it costs

- **A third mechanism acting on the history**, after eviction and the fold. The
  interactions are the risk, and the mitigation is that all three are decided in
  one function against one set of items.
- **A protocol bump**, paid by every client. Mitigated by it being the fifth
  time and the reason being the same one.
- **A field on `Turn`**, which is the price of not mutating the steps.
- **Two flags with invented defaults.** `keep = 2` and `above = 0.35` are
  guesses in the way `low_water = 0.5` was a guess, and they are flags so they
  can stop being guesses.

## What was rejected

- **Mutating `Turn::steps` in place.** Simpler, one field cheaper, and it breaks
  store parity, blinds the UI to what was elided and makes a pruned session
  un-replayable at fidelity. The record is the artefact this project is for.
- **Summarizing a result with the model.** It is the obvious reading of
  "summarize or drop old tool outputs", and it puts model prose into the region
  every later turn is built on — rejected once already for the fold, and for a
  worse reason here: it costs a model call per pruned result on a machine where
  the model call *is* the budget.
- **Head-and-tail retention** (keep the first 20 lines and the last 5). It keeps
  a shape that reads like a file and is not one, and the boundary is another
  invented number. The digest is either the bytes or a statement about them; a
  third thing that looks like the bytes is the worst of both.
- **Lowering `MAX_OUTPUT_BYTES`.** Cheapest change available, and it makes every
  result worse to make the sum smaller — the model reads the *first* result in
  full and it is the one that matters most.
- **Pruning by size rather than by age.** "Prune results over N bytes" leaves a
  history whose small results are immortal, which is the same failure at a
  different threshold. Age is what value decays with.

## Still open

- **A pruned result cannot be un-pruned, and the model is not told it may
  re-read.** The digest says bytes left; nothing says `read_file` would bring
  them back. Whether a 7B works that out unprompted is a question for a box.
- **The watermark is measured against the history budget, not against what the
  turn is about.** A result the *current* prompt points at is pruned exactly as
  one nothing points at is — relevance is what `select.rs` does, on files, and
  the two have not been introduced.
- **Nothing prunes a folded summary.** By construction it is already the
  deterministic digest of a job; if summaries ever dominate a window, that is a
  different measurement and a different record.

## 2026-09-05, the same day: the run

`scripts/tasks/tool-heavy.txt` is twelve turns that each read a real file of
this repository (120 lines, through the sandbox) before answering — the first
corpus here whose history is mostly *tool output* rather than prose, which is
the case the cap bounds one result of and nothing bounded the sum of.
`scripts/prune-probe.sh` runs it four times, one flag apart, and
`scripts/record-summary.py` adds up what the recordings already say. Mock
backend, `chars/4`, 8192-token window, 512 reserved, per-turn eviction
throughout.

| run | prompt tokens | reuse | turns evicted | prunes | tokens pruned |
| --- | --- | --- | --- | --- | --- |
| `--prune off` | 144 401 | 62.5% | **6** | 0 | 0 |
| `--prune age --prune-keep 2` | **87 759** | 55.8% | 0 | 9 | 11 015 |
| `--prune watermark --prune-above 0.35` | 87 759 | 55.8% | 0 | 9 | 11 015 |
| `--prune watermark --prune-above 0.8` | 110 897 | **78.1%** | 0 | **3** | 11 015 |

### The trade happened, and it is the first row against the second

The unpruned run **evicted six of its twelve turns** — half the conversation,
to make room for file listings the model had already read. The pruned runs
evicted **none**, and sent 39% fewer tokens doing it. That is the claim this
was built on, and it is the one number that would have killed the idea if it
had come back the other way.

### The second policy degenerated at the number it was written with

`0.35` and `0.8` are the same policy one constant apart, and at `0.35` the
watermark is **byte-for-byte the `age` run**: two 120-line results are worth
more than a third of the history budget on their own, so the condition is true
on every turn and the "wait, then cut deep" policy becomes "cut every turn".
The default moved to `0.8` because of this run, and the low arm stays in the
probe as the finding.

### And at a share two results cannot reach, it is `Eviction::Block` again

Per-turn prefix reuse of the first call, which is where the shape lives and
where the mean hides it:

```
off             99  99  99 100 100   7   7   7   7   7   7
age             99  99  17  18  19  23  27  25  28  32  30
watermark(0.8)  99  99  99 100  15  99 100  21  99 100  26
```

Three readings, and the third is the one that was not obvious before the run:

- **`off` collapses to 7% at turn 7 and stays there** — the window filled, and
  per-turn eviction rewrote the history from its front on every call
  afterwards. This is the collapse `RECORD/2026-08-27.prefix-reuse-and-block-eviction.completed.md`
  found, reproduced here without being looked for.
- **`age` collapses at turn 4 and never recovers**, exactly as predicted: a
  boundary that moves every turn rewrites the block every turn. It sends the
  fewest tokens of any arm and it is the worst of them for a cache.
- **The watermark keeps 8 of 11 calls at 99–100% and pays on the 3 that cut.**
  That is `Eviction::Block`'s shape on a different axis, and it says the two
  policies were worth building as a pair rather than picking one.

**The mean is not the comparison, and neither is a reuse number across the
`off` boundary.** A bigger constant block raises shared and total together —
the arithmetic `RECORD/2026-08-31.the-repo-map.completed.md` names — so
`off`'s 62.5% against `age`'s 55.8% is not a result. The per-turn series is,
because it says *when* the block was rewritten rather than how big it was.

### What is now true that was not

- A tool result's cost is bounded over a session and not only per call. The
  doc comment on `MAX_OUTPUT_BYTES` no longer has to say "pruning is a later,
  measured change".
- The three mechanisms compose: the pruned run evicted nothing, the folded
  runs are unaffected (a closed job's turns have no steps in the prompt to
  prune), and all three are decided in one function against one set of items.
- `pruned` is on the wire, so a recording says which results the model had
  stopped seeing. The prune floor no longer dies with the process.

### What this run does not say

- **Whether the model still answers.** Twelve mock turns cannot be asked
  whether a 7B four turns later needed the bytes. That is precision, it needs a
  box, and it is the same gap
  [`choosing-fragments`](2026-09-05.choosing-fragments.completed.md) left open
  — the pruning half of it belongs in the same run, because a digest that says
  `[read_file] ok` and nothing else is exactly the kind of thing a small model
  might read as *the file was empty*.
- **Whether `keep = 2` is right.** It was not varied. One turn back is the
  minimum that keeps the just-read file, and nothing was measured above two.
- **How it behaves under `--evict block`.** Every arm here evicts per turn,
  which is the baseline; the two block-shaped policies have not been run
  together and might interact.
