# A certificate from Traefik, and a key the chart does not have

> he probado también con esto:
>
>     helm install luu oci://ghcr.io/jgermade/charts/luu --set ingress.enabled=true
>       --set ingress.host=luu.germade.dev --set ingress.tls.enabled=true
>       --set runtime=kubernetes --set traefik.tls.certResolver=letsencrypt-dns
>
> y no funciona el certificado

The first install of the chart on a real cluster: 0.1.7, under Traefik, every
resource up. The browser was served `TRAEFIK DEFAULT CERT`, self-signed,
issued at the install's own minute. It is `completed`: the cause is found, the
chart is changed, and the change renders as intended. A live Traefik getting a
certificate through it is the person's cluster's to show.

## Why

Rendered here with Helm 3.16 (`mirror.gcr.io/alpine/helm`), the command
above gives an Ingress with no annotations and

```yaml
tls:
  - hosts: ["luu.germade.dev"]
    secretName: luu-tls
```

Two things, each enough on its own:

- **`secretName: luu-tls` names a Secret nothing writes.** The chart expected
  cert-manager to write it, from an issuer annotation. `values.yaml` said so in
  a comment, and the landing's one-line install said nothing at all. Without
  cert-manager the Secret does not exist, and Traefik answers with its own
  default certificate.
- **`traefik.tls.certResolver` is not a key of this chart**, so Helm ignored it
  without a word: the chart had no schema. The resolver was never asked.

## What changed

- **`ingress.tls.certResolver`**: the name of a `certificatesResolvers` entry
  in Traefik's static configuration. When it is set, the Ingress carries
  `traefik.ingress.kubernetes.io/router.tls: "true"` and
  `…/router.tls.certresolver: <name>`, and a TLS entry with no `secretName`:
  Traefik keeps the certificate in its own store, and a named Secret would only
  be one more thing for it to look for and not find. It also turns TLS on, so
  the origin (`LUU_ORIGIN`) is `https://`. An annotation the person sets
  in `ingress.annotations` wins over the chart's.
- **`values.schema.json`**, for the top level and `ingress` only: an unknown
  key is refused rather than ignored. The command above now fails with
  `Additional property traefik is not allowed`, and a typo such as
  `ingress.tls.certresolver` fails the same way. `runtime` must be `host` or
  `kubernetes`. The rest of the tree (`worker`, `links`, `mail`, …) is typed as
  objects and not walked. Listing every key there would make the schema a
  second `values.yaml` to keep in step, for less return.
- **NOTES.txt, the landing and the README say where the certificate comes
  from**: the Secret `luu-tls`, which cert-manager writes, or Traefik's
  resolver, by name.

**Found on the way: CI's chart checks that could not fail.** Under `set -e` a
command negated with `!` never stops the script, so a `! grep …` that is not a
step's last line is not a check. There were two (`LUU_KUBE_SAME_NODE` on a
ReadWriteMany claim, and no Role or NetworkPolicy under `runtime: host`). All
six negations are `if …; then exit 1; fi` now. The two that could not fail
pass as they are.

## For the install that exists

On 0.1.7, the chart that was installed, the same Ingress comes from the
values it already has (rendered here from the `v0.1.7` tag):

```sh
helm upgrade luu oci://ghcr.io/jgermade/charts/luu --version 0.1.7 --reuse-values \
  --set-string 'ingress.annotations.traefik\.ingress\.kubernetes\.io/router\.tls=true' \
  --set-string 'ingress.annotations.traefik\.ingress\.kubernetes\.io/router\.tls\.certresolver=letsencrypt-dns' \
  --set ingress.tls.secretName=null
```

From the release after this one, the key is `ingress.tls.certResolver`. An
upgrade with `--reuse-values` carries the old `traefik.*` key along, which the
schema refuses, and a `--set traefik=null` does not take it out (Helm keeps the
null as a value). So that upgrade passes its values again, with
`--reset-values`.

## Rejected

- **A `traefik:` section, as typed.** The chart's values say what they are
  for: `ingress.*` is the Ingress, whichever controller reads it. The
  resolver is a property of the Ingress's TLS, so it lives beside
  `secretName`.
- **An `IngressRoute`** (Traefik's own resource). It would serve Traefik
  alone, and the chart is "an Ingress of any class". Two annotations on the
  Ingress do the same.
- **The chart writing a cert-manager `Certificate`.** It would make
  cert-manager a dependency, where an issuer annotation already lets
  cert-manager do it.

## Still open

- **Traefik getting the certificate**, on the person's cluster. The
  resolver's name has to exist in Traefik's static configuration. With a DNS
  challenge it also needs Traefik's own access to the DNS provider, which is
  Traefik's to have.
- **Entry points.** Without `traefik.ingress.kubernetes.io/router.entrypoints`
  the router listens on every entry point Traefik has, which is the usual
  setup with a redirect from `web` to `websecure`. A Traefik without that
  redirect needs it set, through `ingress.annotations`.
