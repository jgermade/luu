# Ports luu places

Asked:

> ```
> transport: error sending request for url (http://127.0.0.1:11435/api/tags): client error (Connect): tcp connect error: Connection refused (os error 61)
> ```
>
> *luu debería gestionar los puertos dinámicamente, de hecho, en la
> configuración de cada motor de inferencia, la opción de configurar puerto,
> podría tener un checkbox integrado que haga que el puerto sea automático,
> ese checkbox marcado por defecto*

## What it was

An engine's port was written twice, when the engine was made: as `port` in
`[engine.<name>]`, the first free one from the kind's own at that moment
(`11435` beside an Ollama.app on `11434`), and inside the `url` of the
provider that starts it. The design doc said why the provider kept its own
copy: *so the destination a run prints is still one line of the file*. That
cost two things:

- **The port was a guess about the machine, made once and kept.** Whatever
  took the port afterwards, the file still said it.
- **The provider's copy drifted from the engine's.** *move to port N* in the
  engine's sheet rewrote both, but only where the URL still matched, and
  nothing else kept them in step.

The error itself is a third thing. **A stopped engine was asked what it
serves.** Every picker that showed an ollama engine's provider asked
`/api/tags` on its port before any session had started it. For llama.cpp and
mlx the list was already the catalog on disk; ollama's was a `connection
refused`.

## What it is

- **`port` absent is automatic.** The process **places** the engine the first
  time anything needs its address: a session pointed there, the page listing
  its models, a start from its sheet. The port is the first free one from the
  kind's own, past every port a table names and every other placement
  (`engines::place`), and it is kept for the life of the process, so every
  backend built for the engine dials the same port. Nothing about a
  placement is written down: it is a fact about this process and not about
  the file.
- **The port is the engine's, and only the engine's.** `provider::resolve`
  sends a profile that names an engine to that engine's port, fixed or
  placed. It keeps the path of the profile's own URL, so an anthropic profile
  on a local `/v1/messages` stays one (`engines::at_port`), and drops the
  port. A profile on an automatic engine is written with no `url` at all.
  The line a run prints before it sends names the port it actually uses.
- **A fixed port is kept exactly as before**: the form with *Auto* unticked,
  the free-port suggestion, the sheet's *move to port N* when something else
  answers there, and "used as it is" when that something is a server of the
  engine's own kind.
- **An automatic port that is taken is placed again, never used.** When the
  sheet starts an automatic engine and something that is not luu's answers on
  its port, the engine is placed again and started there. When a session's
  `ensure` finds the same, it forgets the placement and refuses with *start a
  new session to place it on a free one*, because that session's backend
  dials the old port.
- **The form**: *Port* carries an **Auto** checkbox in its box's top right,
  ticked for a new engine. Ticked, the field is disabled, says *chosen when it
  starts* (or *8081 for now* when this process has placed it), and the table
  has no `port`. Unticked, it starts from the first free port and takes a
  number. *use* on a binary the machine has writes no port either. The card's
  *Sends* says *a free port, chosen when it starts* until the engine is
  placed, and then its URL marked *· automatic*.
- **The form no longer refuses the engine it is adding.** Asked with a
  screenshot, *no debería mostrar error por el modelo que está añadiendo*:
  once *Add engine* had written the table, the view handed back to the form
  held the new engine. While its provider was written or luu's copy
  downloaded, the form's own checks found it and said *already an engine of
  that name* and *another engine listens there*. The form now remembers the
  name it wrote, and neither check counts it.
- **An ollama engine nothing answers for lists ollama's store**: the
  catalog's ollama models, by ollama's own names (`tiny:1b`, not
  `ollama:tiny:1b`), the names a session on it sends. When the store is
  empty it says so as the reason, which is what the error used to be.

## Argued against the design doc

*The profile keeps its URL, so the destination a run prints is still one line
of the file* is reversed for any profile that names an engine. What the
sentence protected was *a run says where it sends before it sends*, and that
still holds, with the right port. What is lost is grepping `config.toml` for
an automatic engine's port. That port is not in any file, because no file can
know it before the process starts. A port somebody needs to know in advance
is written in the table, and kept.

## A behaviour that changed under an old file

A table with no `port`, written by hand, meant *the kind's own port*. It now
means *the first free one from the kind's own*. Where the kind's own port is
free they are the same. Where it is not, the old reading started on it anyway,
or used whatever answered there. The usual case is an ollama table with no
port beside a running Ollama.app on `11434`. That table used to send to the
app; now luu starts its own ollama on `11435`. Writing `port = 11434` gets the
old behaviour back. Every table the page wrote before this change has a port,
so this only reaches files written by hand.

## Rejected

- **`port = "auto"`** as an explicit value. Absent already meant *the kind's
  own answer* for every other key in the table, and *checked by default* is
  what absence is for.
- **Writing the placed port back into the file.** It would make the file say
  what one process did, and it would be wrong the next time the engine
  started elsewhere.
- **Re-placing under a session that is already pointed at the engine.** Its
  backend was built with the old port. Rebuilding the backend inside the
  wrapper that waits for the engine is possible, but it is a second way for a
  destination to change under a session, and the session-level answer, *start
  a new one*, already exists.

## Tested

- `engines::tests`: a placement is kept, avoids a port a table names and
  another placement, and is forgotten by `unplace`; `at_port` keeps a path,
  keeps a bare host bare, keeps a trailing slash, and refuses what will not
  parse.
- `provider::tests`: a profile on a fixed engine sends to the table's port
  whatever its URL said; one on an automatic engine sends to the placed port,
  past a table's, the same one twice.
- `settings.spec.js`, 21 passed. The form opens with *Auto* ticked and *Port*
  disabled; unticked it fills a free port and takes `8097`, the test the rest
  of the file builds on. *use* on a binary the machine has writes a table
  with no `port` and a provider with no `url`, and the card says *a free port,
  chosen when it starts*. An ollama engine whose binary is `/bin/false`
  lists `big:27b-mlx` and `tiny:1b` with no reason.

## Still open

- A session whose automatic engine's port was taken refuses until a new
  session is started. Rebuilding its backend is the alternative rejected
  above, and it is the thing to revisit if that refusal turns up in practice.
- `free_port` refuses past a hundred ports from the kind's own. An automatic
  engine with none free fails its start with that sentence, where a fixed one
  fails on the bind.
