# Text file busy

## The question

The first `release.yml` run after the installer landed failed in
`build / test`. `a_worker_that_is_alive_and_stuck_is_abandoned_and_replaced`
could not start the script it had just written:

```
the worker greeted: Spawn { command: "/tmp/luu-worker-stuck-4328/stuck-worker.sh worker",
  source: Os { code: 26, kind: ExecutableFileBusy, message: "Text file busy" } }
```

`version` had already run, so `main` carries `Release v0.1.2` and the tag
`v0.1.2`, and there is no release and no Pages deploy for either. The request:
*Ha fallado el workflow de la release*.

## What it was

A race between two tests, not a fault in either, and not new.
`std::fs::write` holds the script open for writing for as long as the write
takes. Any other test in the same binary that spawns a child in that window
forks, and the child carries the descriptor until its own `exec` closes it
(`O_CLOEXEC` closes it at the exec, not at the fork). An `exec` of a file that
somebody holds open for writing is refused by the kernel with `ETXTBSY`. It is
rust-lang/rust#114554, and every multi-threaded program that writes a binary
and runs it can lose it.

Two tests in `worker_seam.rs` wrote a script that way and ran it: the stuck
worker and the runtime that refuses to start. Nothing else in the tree does.
The same binary had passed on the installer's branch an hour earlier; it needs
the timing. At `61d1fcb` it failed **1 run in 300** here, at the same line.

## What it is

`write_script` hands the writing to a `sh` child — `cat > "$0" && chmod 755
"$0"`, fed on stdin — and waits for it. The test process never opens the file
for writing, so no fork of it can carry a descriptor for it, and the only writer
there ever is has exited before anything runs what it wrote. Both tests use it.

Not a retry on `ETXTBSY`: a retry makes the race rarer to see and leaves it
there, and a test that passes on its second attempt is the kind this
repository's smoke config already refuses (`retries: 0`).

Production has the same shape already: `engines.rs` unpacks a downloaded engine
with an external `tar` and only then starts it, so no descriptor of luu's own
is open on the file.

Measured twice, and the first measurement could not tell the two apart. A
thousand runs of the test binary at `61d1fcb` against a thousand with this
change, interleaved so the machine's load fell on both alike, failed **0 and
0**: one in three hundred is too rare a race for a thousand runs to compare. So
the race was made common instead — one thread writing a script and running it
2 000 times while four others spawned `true` without pause:

| written by | `exec` refused with `ETXTBSY`, of 2 000 |
| --- | --- |
| `std::fs::write` | 68, 69, 114 (three runs) |
| a `sh` child | 0, 0, 0 |

The second row is the fix; the first is the failure, at 3–6% instead of once a
release.

## The release

`v0.1.2` points at `61d1fcb`, which has the old test. The shipped code is not
what failed, so re-running the failed jobs of that run builds and publishes
`v0.1.2` as tagged, and this change keeps the next release from losing the same
race. Moving the tag to include it would rewrite a published ref; bumping to
`v0.1.3` would leave `v0.1.2` a tag with no release.
