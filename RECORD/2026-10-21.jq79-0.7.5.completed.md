# jq79 0.7.5, and the vendored file is jq79's again

Since [`one-modal`](2026-10-01.one-modal.completed.md), `web/vendor/jq79.js`
carried one expression that was luu's: a bare `.html` specifier went through
`import.meta.resolve` before `fetch`, so `@web/components/modal.html` reached
the import map the way `@web/lib/store.js` already did. The record said it
should go upstream and the copy be replaced when it landed. It landed as
[jq79#29](https://github.com/jgermade/jq79/pull/29), released as 0.7.5.

## What changed upstream

One function, `resolveBare`, in front of `fetchComponent`:

```ts
const resolveBare = (url: string): string => {
  if (RESOLVABLE_SPECIFIER_RE.test(url)) return url
  const resolve = (import.meta as { resolve?: (spec: string) => string }).resolve
  if (typeof resolve !== "function") return url
  try {
    return resolve(url)
  } catch {
    return url
  }
}
```

It is **not where luu's line was**:

- luu patched `importResource`, which only a setup script's `import()`
  reaches. Upstream it is in `fetchComponent`, so `Component79.fetch` and
  `fetchAll` read the map too. luu's own entry is `C79.fetch("./app.html")`,
  relative, so nothing here depended on the difference.
- **The component's `filename` is the resolved URL** in both, because luu's
  line resolved before calling `fetchComponent` too, so a component's own
  relative imports landed beside it either way.
- The `typeof` guard is for jq79's CJS and classic-script builds, which have no
  `import.meta`. luu vendors the ES module and is not affected.

Nothing else changed between 0.7.4 and 0.7.5 in `src/`.

## Checked

- The vendored file before this was **0.7.4 byte for byte except luu's
  expression** — compared against the published 0.7.4 tarball — so replacing
  it loses nothing luu had added besides that line.
- `web/vendor/jq79.js` and its map are now `dist/jq79.js` and
  `dist/jq79.js.map` from `npm pack jq79@0.7.5`, unchanged.
