# Sessions in SQLite: a cache of the fold, and the assertion that keeps it one

**Status:** a proposal and the code it plans. It is item 2 of
[`ROADMAP/2026-09-01`](../ROADMAP/2026-09-01/README.md), spec'd a day earlier in
[`session-store.md`](../ROADMAP/2026-08-31/session-store.md), and it is the
oldest thing on that list with nothing in front of it.

`serve` loses the conversation when the process ends. There is no long task to
resume, nothing to hand to a second machine, and no corpus of closed tasks to
count — which the record beside this one
([`closing-on-an-exit-code`](2026-09-02.closing-on-an-exit-code.completed.md)) just
discovered it needs.

## The rule, which is the whole design

From `loude-design.md` §Persistence:

> **Whatever the store holds must be reproducible by folding the record.**

So the store is a **cache of a fold, not a second log**. The JSON-lines record
stays the account of what happened; SQLite holds what `api::SessionView` already
computes from it.

Everything below follows from taking that literally.

## What goes in a row

`SessionView`, serialised, in one column.

That is not laziness, and the alternative is worth naming to see why. The
obvious schema is normalised — `turns`, `tasks`, `tool_calls`, `evictions`, a
foreign key each — and it is **a second definition of the fold**. `api.rs`
already says what a turn is; a `turns` table says it again, in DDL, and the two
have to be changed together forever. The first time they are not, the store and
the live server disagree about a session, which is precisely the drift the
static mirror was built to avoid and the reason `luu export` folds through
`SessionView` instead of generating JSON its own way.

A blob has one definition. It is `SessionView`'s.

**The listing columns are derived and duplicated.** `id`, `title`, `backend`,
`model`, `started_at`, `turns`, `record` are also plain columns, so
`GET /api/sessions` does not parse every blob to list them. Every one of them
comes out of `SessionView::summary()` at write time and never from anywhere
else, and the parity test below is what stops that from becoming a place to keep
a fact the fold does not have.

```sql
CREATE TABLE sessions (
  id          TEXT PRIMARY KEY,
  title       TEXT NOT NULL,
  backend     TEXT NOT NULL,
  model       TEXT NOT NULL,
  started_at  INTEGER NOT NULL,
  turns       INTEGER NOT NULL,
  record      TEXT,
  view        TEXT NOT NULL,   -- SessionView as JSON
  saved_at    INTEGER NOT NULL
);
```

`PRAGMA user_version` carries the schema number, because a store that cannot say
which shape it is is a store that has to be deleted the first time the shape
moves.

## The acceptance test, which is the interesting part

The spec asked for exactly one assertion and it is right:

```
fold(record) -> SessionView   ==   save(store, that) ; load(store, id) -> SessionView
```

Run over **real recordings**, produced by the same `luu chat --record` path
`scripts/make-fixtures.sh` uses, not over hand-built `RecordLine` vectors. A
fixture written by hand can only contain the variants whoever wrote it
remembered; one produced by a run contains what the code actually emits, which
is the set that matters — the eviction lines, the task lifecycle, the tool
results with their `command` field, and whatever lands next without anyone
remembering to update a test.

**A store that can drift is a store that will**, and this is what makes the
drift a test failure rather than a support question.

## When it writes

At **checkpoints**, not per event: a turn ending, a task changing state.

Writing the whole fold on every token is quadratic in the length of a session,
and the thing being written is a cache — so the store is explicitly **allowed to
lag the record**. What it is never allowed to do is contradict it.

That gives the spec's last open question its answer:

> what happens to a session whose record was truncated or lost while the store
> still has the fold

**The record wins wherever both exist.** A row whose record file is still there
is a cache of that file and is rewritten from it rather than trusted. A row whose
record is gone is all there is, and it already says so: `SessionSummary.record`
is `None`, which the read side has meant "no replayable recording" since it
existed. Nothing new has to be invented to label it, which is a small sign the
shape is right.

## Where the database lives

`--store <path>`, defaulting to `~/.loude/sessions.db`.

The draft left this open against `luu.toml`, and the answer is that they are not
competing — **they answer different questions and both exist**. `luu.toml` is
*this project's* policy: which paths, which commands, what enforcement. It sits
in the checkout because it describes the checkout, and it is meant to be
committed. The store is *this machine's* history, and a session store that
travelled with a checkout would put one project's conversation into every clone
of it, which is a data leak with a plausible-sounding rationale.

## What it must not accumulate

The spec lists three temptations and every one of them is already impossible,
because `SessionView` does not have a field for it:

- **A turn's fused prompt.** `TurnView` keeps `prompt` and `prompt_sent`
  separately, and `code_context` is not in the view at all.
- **A token count without its `Counter`.** `Budget` carries `counter` beside
  `limit`, and `Summary` carries `counted_by`. There is nowhere to put a bare
  number.
- **The floor as a number with no `evicted` line behind it.** `dropped` is an
  `Evicted`, with the turns, the tokens, the counter and the policy; there is no
  integer column to degrade it into.

Storing the fold rather than designing a schema is what buys all three. A
hand-written schema would have had to re-derive each of these decisions, and the
odds of getting all three right a second time are not good.

## What this does *not* do, said plainly

**It does not resume a session.** The roadmap item's motivation is "to resume
long tasks without recomputing context from scratch", and this lands the store
and the parity, not the resume.

The reason is a fact about the two structures rather than a shortage of time.
`SessionView` is the **read** side — what a client browses. `Context` is the
**write** side — what the next prompt is built from — and it holds things the
view deliberately does not: each turn's `ToolStep`s as values rather than as
rendered `ToolCallView`s, and its `code_context` fragments, which the view has no
field for because a client never needed them.

So loading a stored view back into a live context is a **second fold**, in the
other direction, and it has to be argued rather than written: which of the
view's renderings can be un-rendered, what a resumed turn's fragments are when
the file has changed underneath them, and whether a resumed session may be
compared with the run that produced it at all. That is the next record. This one
stops at the line where the store stops being derivable.

Naming it is not a hedge. A store that shipped with a resume nobody had argued
would be the second truth this whole item exists to prevent, arriving through the
door marked *convenience*.

## What this rejects

**A normalised schema.** Above: a second definition of the fold.

**SQLite as the write-ahead log.** Tempting — one artifact instead of two — and
wrong. The JSON-lines record is greppable, appendable from a task that must never
block a turn, survives a half-written last line, and is what `luu export` reads
to build the static mirror. A database file is none of those. The spec asked
whether the record is the WAL or a sibling; it is neither, because it is the
account and the store is the cache.

**Compression.** The draft says "compressed state". Deferred, with a number
rather than a preference: a fixture session's fold is tens of kilobytes of JSON,
and `zstd` is a dependency, a format decision and a thing to get wrong. It
becomes worth it when a real session is measured and is not tens of kilobytes.

**`rusqlite` without `bundled`.** SQLite is compiled in rather than linked
against whatever the host has. That is the same argument as everything else here:
a store whose behaviour depends on the machine's system packages is not a
local-first store, it is a store with an undeclared dependency.

## Still open, after this

- **The resume**, above. It is the item this unblocks and it is a record of its
  own.
- **Multi-session `serve`.** The server holds one `Session` behind a mutex and
  refuses a second prompt as `Busy`. The store makes several sessions
  *storable*; making them *servable* is the roadmap's next row and touches the
  gate, the sandbox-per-task map, and the socket's fan-out.
- **Retention.** Nothing deletes a row. A daily user accumulates them forever,
  and the first person to notice will be someone whose `~/.loude` is a gigabyte.
- **Whether the record path should be rewritten on load.** A row stores where
  its recording *was*. A moved or renamed file leaves a row pointing at nothing,
  and the read side will call that "no recording" rather than "a recording I
  cannot find", which are different facts.

## 2026-09-02 — what building it decided

The store is as proposed: one row per session, the fold as JSON, the listing
columns derived from `SessionView::summary()`, `PRAGMA user_version` for the
schema, and the parity assertion over recordings produced by running the binary.
Two things the proposal did not have.

**The id is the session's name, not part of the fold.** The live view is served
as `live`, which is what every client asks for and what the UI has hard-coded.
Storing it under that name would mean each restart overwrote the previous
session — a history that only ever holds one thing. So the row is keyed on the
session's own id and the view's `id` is replaced at write time.

That looked like a mutation of the fold until the precedent turned up:
`SessionView::from_record(id, lines)` takes the id **as an argument** because
the recording does not contain one, and `luu export` takes it from the file
stem. The id has never been part of what the fold computes. Nothing is being
bent.

**The finding: `started_at` alone is not an id, and the failure is silent.**
The first version named sessions `session-{started_at}`. Two servers started in
the same millisecond — which is not hypothetical, it is what the end-to-end test
does — produce one row, and the second one's first checkpoint overwrites the
first one's session with no error anywhere. A store that loses sessions is worse
than no store, because nothing says it did.

So the id carries the process and a per-process counter after the timestamp. It
stays sortable and readable, which is the property that made a timestamp the
right start.

**The parity test does not run `make-fixtures.sh`, and the reason is a number.**
The intention was to assert over exactly the fixtures the static deploy replays,
so the two could not drift. Running that script takes **27 seconds**, against a
suite that runs in one — the fixtures are paced with `--mock-delay-ms` so a
person can watch them play, and the test does not need to watch anything. It
records the same shapes at delay 0 in half a second: a plain turn, a task closed
to a summary, an eviction run, the tool loop with both verdicts, a fused
fragment, and a failed turn. Still real runs of the real binary, which was the
part that mattered; not the same file list, which is the part given up.

### Still open, after building it

- Everything the record already listed: the resume, multi-session `serve`,
  retention, and the moved record path.
- **Nothing prunes a lagging row.** The store is allowed to lag and the record
  wins wherever both exist — that is the rule — but nothing yet *re-folds* a
  record over a stale row. Today a session's last checkpoint is its last task or
  turn boundary, so the gap is bounded by one turn; the moment anything writes
  less often than that, the rule needs code behind it rather than a sentence.
