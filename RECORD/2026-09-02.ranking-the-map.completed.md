# Ranking the map, and why that does not move it out of the prefix

*2026-09-02*

[`2026-08-31.the-repo-map.completed.md`](2026-08-31.the-repo-map.completed.md) built the map and
closed with four open threads. This file takes the first, which it called "the
next commit":

> **Ranking**, and then the reference graph: edges from `@reference.call`, which
> the same query already captures. The next commit, measured against this one.

and it has to answer the fourth in order to take the first, because they are the
same question asked twice:

> **Whether the map belongs in the prefix at all once it is ranked.** Ranking
> personalizes; personalization moves per turn; the prefix wants stillness. That
> tension is the next real decision, and it is not this one.

## The problem, which is a table rather than an argument

The map is ordered by the alphabet. At every budget an 8K window can pay, most of
the repository is not in it, and which part survives was decided by `a` sorting
before `l`:

| `--map-tokens` | files outlined | left out |
| ---: | ---: | ---: |
| 512 | 2 | 27 |
| 1024 | 5 | 24 |
| 2048 | 10 | 19 |
| 8192 | 29 | 0 |

`crates/agent-core/` outlines completely before `crates/luu/` gets a line. The
map's own module doc has said so since the day it was written — *"path order is a
bias … and it is the baseline the reference graph has to beat"* — and the score
against a 7B ([`the-map-against-a-7b`](2026-09-01.the-map-against-a-7b.completed.md))
made the shape of the failure exact: group A, the files a 1024-token map holds,
went 0/6 → 6/6. Group B, the placebo, stayed flat. The map works on what it
contains, and the alphabet chooses what it contains.

## The decision: ranking is not personalization

This is the whole of the file, and everything below is mechanism.

Aider's PageRank runs with **a personalization vector** pointed at the files in
the chat and the identifiers the conversation mentioned
([`2026-08-27.aider-repo-map.completed.md`](2026-08-27.aider-repo-map.completed.md) §4). That is
what "ranking personalizes" meant when the open thread was written, and the
conclusion followed correctly from it: a map seeded by the current turn is
rewritten every turn, and a block rewritten every turn is not a prefix — it is a
fragment with a bad name, and it would be paid for on every call while pushing
the changed bytes to the front of the prompt.

But the personalization vector is a *seed*, not the ranking. Take it away and
PageRank still ranks — by the repository's own shape, uniformly teleported. **A
file's score then depends on nothing but the tree**, which is precisely the
property the prefix asks of every block it holds: the map changes when the
repository changes, and at no other time.

So the fourth thread closes with a *no*, and it closes without a compromise:

> Does the map leave the prefix once it is ranked? No — because the half of
> Aider's ranking that would have moved it is the half we are not taking.

That is also the honest statement of what this buys and what it does not. An
un-personalized rank cannot know that *this turn* is about the HTTP router. It
can only know what the repository is built on top of. Those differ, and §*What
this will not fix* below predicts exactly where.

## The mechanism

One pass, the same query, three captures instead of one. `tags.scm` for Rust
already carries everything needed:

```scm
(call_expression function: (identifier) @name) @reference.call
(call_expression function: (field_expression field: (field_identifier) @name)) @reference.call
(macro_invocation macro: (identifier) @name) @reference.call
(impl_item trait: (type_identifier) @name) @reference.implementation
(impl_item type: (type_identifier) @name !trait) @reference.implementation
```

Nothing to vendor and nothing to write, which was decision one of the map and is
unchanged.

1. **Tags per file.** `tags(source) -> { entries, defines, references }`. `entries`
   is what the map already renders; `defines` and `references` are the `@name`
   nodes of the definition and reference matches. `#[cfg(test)]` is excluded from
   all three, and for references the reason is stronger than for definitions: a
   test module calls everything, so leaving them in flattens the graph toward
   "whatever the tests exercise" — which is a real signal about the test suite and
   a false one about the code.
2. **The graph.** Nodes are files. An edge `A → B` exists when `A` references a
   name `B` defines. Weight is `sqrt(count)`, spread across the files that define
   the name, and multiplied by `0.1` when the name is defined in more than five
   places — Aider's rule and worth keeping for the reason it exists: `new`,
   `render` and `count` are not evidence of anything.
3. **Self-edges are dropped.** A file that calls its own helpers is not depended
   on by anybody; without this, the longest file wins for being long.
4. **PageRank, damping 0.85, uniform teleport**, dangling mass redistributed
   evenly, a fixed iteration cap and an epsilon so two runs on one tree give one
   answer. Ties break on the path, ascending, so the alphabet stays as the
   *tie-breaker* it should always have been rather than the ranking it was.
5. **The fill rule does not change.** Whole files, in rank order, stopping at the
   first that does not fit. Skipping to fill the budget better is still not
   monotone, and monotone nesting is what makes two budgets comparable.

## What it costs

- **Nothing in the walk.** The loop already parses every file it finds, even
  after the budget is full, because it counts what it left out. The graph is
  built from a pass that was already happening; PageRank on 29 nodes is noise.
- **The map's order stops being legible from the tree.** A person could
  previously predict the map by running `ls`. Now they cannot, and a selection
  nobody can interrogate is the thing this project rejected embeddings for. So
  the explanation ships with the ranking rather than after it: `luu map
  --explain` prints each file's score and the files that reference it, **outside
  the rendered block** — the bytes that reach the prompt are unchanged in shape,
  because a map that explained itself to the model would be spending the budget
  on its own footnotes.
- **A new file sinks.** Nothing references it yet and it may reference little, so
  it ranks last exactly when a person is most likely to be working on it. This is
  real and it is not fixed here; see below.
- **Every recording made before this is comparable only at `--map-tokens 0`.** The
  flag is off by default, so the archive is safe, but a map-on run from yesterday
  and one from today hold different files at the same budget.

## What was rejected

- **Personalized PageRank**, for the reason above. It is not rejected as a
  technique — it is rejected *in the prefix*. If it ever ships it belongs on the
  fragment side of the prompt, where per-turn rewriting is already the deal.
- **Ranking by size or definition count.** It rewards the longest file, which on
  this tree is nearly the same answer as ranking by importance and for none of the
  same reasons — and it cannot say *why* a file was included, which was the whole
  case against embeddings.
- **Ranking by `mtime` or git recency.** It moves the map without the repository's
  structure changing, which breaks the property that just bought us the prefix.
- **Writing our own reference query** to catch what `tags.scm` misses. It
  contradicts decision one of the map, and the gap is worth *measuring* before it
  is worth closing; see the next section.
- **Aider's binary search over ranked tags** to fit the budget within 15%. The map
  keeps whole files, for the reason recorded when it was built: half an outline is
  a list of methods whose type has gone.

## What this will not fix, predicted before it is run

The scored corpus is [`scripts/tasks/map-probe.txt`](../scripts/tasks/map-probe.txt), and the
prediction below is written here so the run can contradict it.

Group B — the placebo, six files no 1024-token map has ever held — will **not**
move as a group. It should split, and the line it splits on is the ranking's own
definition:

- **Should rise:** the eviction question and the prompt-assembly question, both
  `context.rs`; the Landlock question, `sandbox.rs`. These are the files the tree
  is built on top of, and in-degree is what "built on top of" means.
- **Should not:** the HTTP router, the CLI subcommands, the static read API.
  `serve.rs` and `lib.rs` are entry points. **Nothing calls into an entry point**,
  so a graph ranked by what depends on what puts them last — and they are among
  the files a person asks about most.

If that split is what comes back, the ranking works and its limit is named: **a
reference graph ranks what is depended on, not what is asked about.** If group B
moves as a whole, the prediction is wrong in a way worth more than the ranking. If
group A *falls out*, the ranking is worse than the alphabet on the only questions
the map had ever answered, and that is the result that would send this back.

One more, cheaper to check and worth checking first: the stock query captures
`foo()` and `x.render()` but **not** `Type::method()` — a `scoped_identifier` call
is in none of the five patterns above. In a codebase that spells most of its calls
`RepoMap::build`, that is a large hole in the edge set, and the ranking's quality
is bounded by it before any model is involved.

## Still open

- **Entry points**, per the prediction above. A second signal (a file that is a
  binary target, or one nothing references *and* that references many things) is
  the obvious shape and is not this commit.
- **Scoped calls**, per the paragraph above. Measure the hole, then decide whether
  closing it is worth reopening decision one.
- **Whether rank should choose fragments too**, which is relevance-over-recency
  proper and the reason the roadmap row is not closed by this file.
- **Rebuilding a stale map**, unchanged from the record this one continues.

## Appended the same day: built, measured, and shipped **off**

The ranking exists, it explains itself, and on the only corpus this repository
can score today **it loses to the alphabet**. So `--map-rank` is a flag and path
order is still the default — the same shape the map itself shipped in, and for
the same reason: a default that changes what every recording holds needs a scored
run behind it.

This section is the evidence, and three of its four findings were not in the plan.

### The numbers

`luu map` at three budgets, one flag apart, counting which of the files the
probe's questions are *about* the map actually holds. Group A's five files are
`agent.rs`, `backend/mod.rs`, `session.rs` (`PrefixTracker`), `api.rs`
(`SessionView`) and `backend/mock.rs`; group B's are `serve.rs`, `luu/src/lib.rs`,
`export.rs`, `context.rs` and `sandbox/linux.rs`.

| budget | order | files | tokens spent | group A | group B |
| ---: | --- | ---: | ---: | ---: | ---: |
| 1024 | path | 5 | 876 | **4/5** | 0/5 |
| 1024 | rank | 2 | 756 | 0/5 | 0/5 |
| 2048 | path | 8 | 1 989 | **4/5** | 1/5 |
| 2048 | rank | 4 | 1 693 | 0/5 | 0/5 |
| 4096 | path | 18 | 4 083 | **4/5** | 2/5 |
| 4096 | rank | 12 | 4 100 | 1/5 | 2/5 |

Worse or equal in every cell. The prediction written above said group B would
*split*; what happened is that group B did not move at all and group A collapsed.

### Finding 1: the corpus cannot compare two orders, and says so in its own comment

> `# --- Group A: the four files a 1024-token map actually holds.`

Group A is **defined by the baseline**. It is the set of files an alphabetical map
holds, so it is the alphabet's home turf by construction, and *any* reordering
loses on it before a model is asked anything. The 6/6 that
[`the-map-against-a-7b`](2026-09-01.the-map-against-a-7b.completed.md) scored is
still a real result — it measured whether a map helps at all, which was the
question — and it cannot be reused to measure *which* map.

That is a flaw in the instrument and it was invisible until something tried to
use the instrument for a second purpose. What a comparison of orders needs is a
group defined by the **questions a person actually asks**, sampled without knowing
what any map holds, and then scored per order. That corpus does not exist and this
file is not going to pretend the old one substitutes for it.

### Finding 2: rank order buys fewer files, and that half is real

Half the collapse has nothing to do with the corpus. **At 1024 tokens path order
holds five files and rank order holds two.**

The fill rule stops at the first file that does not fit, decided in
[`the-repo-map`](2026-08-31.the-repo-map.completed.md) so that a wider budget is
always a superset of a tighter one. Under path order, size and position were
uncorrelated and the rule cost little. Under rank order they are *strongly*
correlated — the files the tree stands on are the big ones — so the head of the
ranking eats the budget and the rule then refuses everything behind it.

This is a genuine tension between two things the map wants, and it is not
resolved here:

- **Monotone nesting** makes two budgets comparable, which is what the map is for.
- **Skip-and-continue** fills the budget but is not monotone: at costs `[10, 5]`,
  a budget of 6 holds the second file and a budget of 10 holds the first, so the
  wider map is not a superset of the tighter one.

Both cannot hold. The recorded decision picked the first and this file does not
overturn it on one afternoon's measurement — but it is now clear that **ranking
and the fill rule are one decision, not two**, and the next attempt has to bring
them together. That is the shape of the next record, and it is the reason this one
ships a flag rather than a default.

### Finding 3: PageRank demotes exactly what the entry points depend on

The prediction said `context.rs` would rise, because everything assembles a
prompt through it. It **fell** — out of the top ten, holding referrer weights
(`serve.rs` at 3.93, `lib.rs` at 1.48) larger than anything else in the table.

The reason is PageRank working correctly and answering a different question than
the one asked. Rank flows *from* the referrer, so a file referenced only by
entry points inherits an entry point's score — and entry points are exactly what
an un-personalized ranking puts last. The prediction had the first-order effect
right and missed that it is transitive:

> **a reference graph ranks what is depended on, not what is asked about** —
> and it demotes the second layer down as well as the first.

Weighted in-degree does not have this property and would have put `context.rs`
near the top. Whether that makes it the better ranking here is a real question
and an unmeasured one; it is not a change to make in the same commit that found
the problem.

### Finding 4: a method call is not evidence, and weighting it down is not enough

The first run put `crates/agent-core/src/repo_map.rs` at the head of the ranking.
It earned that with two edges:

```
  66  method  push      (defined in 1 file in this tree)
  50  method  is_empty  (defined in 3 files in this tree)
```

Every `Vec::push` and every `str::is_empty` in the repository was an edge pointing
at whichever file happened to define a function of that name. `tags.scm` captures
`x.push(..)` and `push(..)` with the *same* capture, and the difference between
them is a type `tree-sitter` cannot see.

Downweighting was tried first and failed, which is the finding worth keeping:
**at 0.25 per edge it still won**, because PageRank rewards breadth and these
edges arrive from every file in the tree. What works is refusing the edge
outright when the name is short and reached through a method call — `push`,
`render`, `is_empty` are the standard library's vocabulary, and this tree does
not own them merely by spelling them.

So the reference kinds are separated (`Call`, `Method`, `Implementation`), and
Aider's "well named" heuristic, dismissed above as a nicety worth skipping, turns
out to carry most of the signal. It is kept for a reason this repository measured
rather than on Aider's authority.

The hole predicted before the run — `Type::method()` is a `scoped_identifier`
call and is in none of `tags.scm`'s patterns — is still there, unmeasured, and
now looks more consequential than it did: with method calls this unreliable, the
scoped calls are where most of the true coupling in this codebase actually is.

### What landed

- `agent_core::rank`: the graph and PageRank, pure and testable without a
  filesystem, with the weighting rules each named for what they exclude.
- `repo_map::tags`: definitions and references from one pass of the same stock
  query, with `#[cfg(test)]` excluded from both — a test module calls everything.
- `repo_map::Order`, and `--map-rank` on `chat`, `serve` and `map`, defaulting
  to path order.
- `luu map --explain`: every outlined file, its score, whether it fitted, and the
  files that reference it — printed after the block and never inside it. It works
  under both orders, so the ranking can be read beside the order that beat it.

### Still open, after the fact

Everything the plan listed, plus:

- **The fill rule and the ranking are one decision.** Finding 2.
- **Whether PageRank is the right aggregator at all**, against weighted
  in-degree, which does not inherit the entry points' low score. Finding 3.
- **A corpus that can compare orders.** Finding 1, and it blocks the flag ever
  becoming a default honestly.
