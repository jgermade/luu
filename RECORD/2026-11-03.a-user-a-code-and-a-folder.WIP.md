# A user, a code and a folder: step 1 of users

**Status:** proposal, built in the same change. Step 1 of
[`users-and-a-code-by-email`](2026-11-03.users-and-a-code-by-email.WIP.md),
roadmap row 56.

> Ok, dale

Step 1 is everything users need **except email**: a user, a code to log in
with, a login that stays logged in, sessions and a folder that belong to the
user, and a wall between two users that the server holds itself. Codes come
from `luu user code` on the machine, so one person can run a public server
without a mail server, and without a token in the URL.

## What this step decides

### `auth.db`, beside `sessions.db`

It holds three tables:

```text
users   id, email, role, suspended, created_at, last_login
codes   email, hash, expires_at, tries
logins  hash, user, created_at, expires_at
```

- **The file is created `0600` and checked on every open**, with the rule
  `secret::read` applies to a token file. A looser mode is refused and the
  refusal names `chmod 600`.
- **A user's id is 12 random hex characters**, not the email. It names the
  user's folder, so changing an email does not move files, and a folder name
  does not publish an address.
- **Emails are trimmed and lower-cased** before they are stored or compared.
- **A code is six digits.** It lasts ten minutes, can be used once, and is
  stored as `sha256(email \0 code)`. Five wrong tries burn it. A new code
  replaces the previous one.
- **A login is 32 random bytes**, stored as their `sha256`. It lasts
  `[auth] session-hours`, 168 by default.
- **Suspending a user ends their logins.** Removing one does too.

### `luu user`, the way in that needs no request

```sh
luu user add ana@example.com --role admin
luu user list
luu user role ana@example.com user
luu user suspend ana@example.com
luu user resume ana@example.com
luu user remove ana@example.com
luu user code ana@example.com      # prints a code; ten minutes, one use
```

- **The last owner cannot be demoted, suspended or removed**, so a server
  always has someone who can add the next person.
- **`remove` refuses while the user has sessions** and names how many. What
  removing should do with them is still open in the parent record, so this
  step does not decide it by default. `suspend` is the alternative until then.
- **The CLI writes `auth.db` directly.** It is the person at the machine, which
  is what loopback stands for today.

### `exposure = "public"`

```toml
[server]
exposure = "public"
bind = "0.0.0.0:7878"
origin = "https://luu.example.com"   # required

[auth]
session-hours = 168
```

- **`origin` is required.** A public server whose origin is not stated is
  refused at startup, because `Origin` is checked against it.
- **A token file is refused.** `public` does not accept a token, in the URL or
  in a header, until a user can hold their own (step 5).
- **Nothing is trusted because of the address a request comes from.** The
  bind is not loopback, so every Settings write stays refused, as it is in
  `private` today. Roles reach Settings in step 3.

### Logging in, and what a login is

```text
POST /api/auth/login  {email, code}  → 204 + Set-Cookie
POST /api/auth/logout                → 204, the cookie cleared
GET  /api/auth/me                    → {users, email?, role?}, 401 when users and no login
```

- **The cookie is `luu_login`**, set with `HttpOnly; SameSite=Strict;
  Path=/` and `Secure` when `origin` is `https`. A plain `http` origin is only
  a server tried on this machine, and a browser drops a `Secure` cookie there.
- **`Origin` has to be the stated origin on every request that is not a
  `GET`, and on every socket upgrade.** That includes the login itself, so a
  page on another site cannot log a browser into its own account.
- **One answer for every failed login** (`401`, *that code is not valid*). It
  does not say whether the email is a user, whether a code was ever issued, or
  how many tries are left.
- **`/api/auth/me` exists in every exposure**, so the page asks one question
  before it loads: `{"users": false}` on loopback and `private`, which is
  today's page.

### A user's session

- **A user has their own current session.** `Lives.current` is per owner, and
  a socket that names no session follows its user's current one, never anyone
  else's. On loopback and `private` there is one owner, *nobody*, and nothing
  changes.
- **A user with no live session gets one at their first request.** It is made
  in their folder and sends where the server's own session sends: the session
  a fresh `serve` gives the one person today, given to each user. The server's
  own session, which belongs to nobody, is never shown to a user.
- **Sessions carry their owner.** `sessions.owner` is schema 6. Rows from
  before it are `NULL`, made before there were users, and they are shown to
  owners only.
- **Another user's session is a `404`**, not a `403`, because a `403` would
  say it exists. That holds for the history list, `/api/sessions/{id}/…`,
  `?session=`, and both sockets.
- **`max-live` counts per user** in `public`
  ([the parent's §2](2026-11-03.users-and-a-code-by-email.WIP.md)).

### A user's folder, and the wall the server holds

- **`<root>/<user id>/`**, created with the user's first session. Every
  session of theirs is made under it, the folder picker browses only it, and
  the page names paths relative to it.
- **The server refuses an agency that reaches past it.** `finish` is where
  every session's agency is built: new, resumed, moved. In `public`, it
  refuses one whose sandbox grants any path that:
  - contains the root (every user's folder at once), or
  - is under the root and outside this user's folder.

  This holds whatever the policy file says. It is a check on the policy, not
  a policy, so a deployment's file cannot widen it.
- **`deploy/luu.toml` grants `.`** (the session's folder) instead of `/work`.
  This changes `private` too: a session made in a subfolder no longer reaches
  its siblings, which is what a folder per session meant
  ([`sessions-side-by-side`](2026-10-30.sessions-side-by-side.WIP.md) §5).
- **A writable path outside the root is shared by every user**, and `serve`
  says so at startup in `public`, naming each one. The image's own
  `/state/cargo` is one: a cargo cache one user's build could leave something
  in for another's. It is said rather than refused, because refusing it would
  leave the published image without cargo. See *Still open*.

### A host shell

- **Owners only, and only where `[terminal] host = "always"`.** In the image a
  host shell is every user's folder plus `/state`.
- **`/h/<name>/` is already refused off loopback** (`hosts_allowed`), and stays
  refused.

### The page

`index.html` asks `/api/auth/me` before it mounts anything. If users are on and
there is no login, it mounts a login view (email and code) instead of the app,
and reloads once the login is accepted. Settings → General gains *Account*:
the email, the role, and *Sign out*.

## How the user reaches the code

The person is held in a task-local, `WHO`, set by the login middleware around
the request. That is the way `?session=` already reaches a handler
(`ADDRESSED`). `App::current()` reads it, so the ~30 places that ask for *the
current session* get the user's own without each being rewritten. A socket
outlives its request, so it takes the user when it opens, as it already takes
the session.

## What it costs

- **A task-local is invisible at the call site.** A handler that spawns work
  and asks for `current()` inside it would get *nobody's*. So `may_sleep`,
  `sleep_live` and `end_live` stop comparing against `current()` and ask the
  session whose current it is (`App::is_current`). The sockets take the user
  explicitly.
- **Schema 6** for `sessions.db`: one column, no row touched.
- **The first request of a user's day may build a session.** That means an
  agency and a map over their folder. Empty, it costs the ~100 ms a container
  start costs, or less.
- **The page gains a second entry**: the login view, before the app.

## Rejected

- **Threading the user through every handler as an argument.** It is about a
  hundred signatures for the same fact `ADDRESSED` already carries this way.
- **Leaving the user without a session until the page makes one.** Every route
  and the socket assume a current session exists. A user without one would be
  a new state in thirty places, while a session made on arrival is the state
  that already exists.
- **A `403` for another user's session**, for the reason given above.
- **Showing `NULL`-owned sessions to everyone.** They were made by whoever held
  the machine before there were users, so they are the owners'.

## Still open

- **Signals.** Two users' commands run as one uid, and Landlock scopes signals
  only from ABI 6, which `agent-core` does not ask for yet. One user's command
  can signal another's, or `serve` itself.
- **Shared writable paths outside the root** (`/state/cargo`): said at
  startup, not removed. A cargo home per user, under their folder, would close
  it.
- **What removing a user does with their sessions**, carried over from the
  parent.

## Built, the same day

All of the above is built. Where the build differed from the plan:

- **`GET /api/auth/me.json` too.** The page asks with `.json`, the one spelling
  a static copy can answer, and `luu export` writes `api/auth/me.json` as
  `{"users": false}`. Without it, the Pages copy logged a 404 before it
  mounted.
- **The history calls a user's current session `live`**, as it has always
  called *the* current one. Its real id is in the `hello` the socket sends.
- **On the login view, `/api/auth/me` answering `401` logs one console
  error.** That is the answer, and it is left as one.

**Verified here:**
- `users` (5 tests): a code becomes a login once, five wrong tries burn it,
  suspending ends logins, the last owner stays, one email is one user, and the
  file is `0600`, with a looser mode refused.
- `store`: an owner is written once and kept.
- `auth`: `public` resolves to users and refuses a token.
- `tests/users.rs` (5 tests, a real server):
  - No login gets a `401`, and so does `?token=`.
  - A wrong code reads exactly like a stranger's.
  - A login, and a write, from another `Origin` are `403`.
  - Two users each get their own session in their own folder. Neither reaches
    the other's session by path, by `?session=`, by resume, or through the
    workspace tree. The folder picker shows only their own folder, and
    `../<other>/secret` is a `400`.
  - Logging out ends the login.
  - A policy granting the root is a `403` naming *every user's folder*.
  - A socket from another `Origin` is refused, a socket follows its own user
    and not the other's, and naming the other's session is refused.
- `tests/server_config.rs`, through the binary:
  - `public` without `origin` is refused.
  - `luu user add`, `role` (refused for the last owner) and `code` work.
  - A login sets a cookie with `Max-Age` from `[auth] session-hours`.
  - A Settings write is still `403`.
  - `auth.db` is `0600`.
- **Chromium** against a real public server:
  - The login view is shown, a wrong code is said, and the right code mounts
    the app on the user's own folder.
  - The static site still mounts and replays with nothing new in the console.
- `cargo clippy --workspace --all-targets` with `-D warnings`,
  `cargo fmt --check`, and `cargo test --workspace` all pass.

**Not verified, and why this stays `WIP`:** the published image under
`exposure = "public"` with Landlock holding it. The checks above are the
server's own, at the API. What the kernel holds is still to be run: a
*command* in one user's session trying another user's folder, `/state`,
another session's `/tmp`, and signals and `/proc`. That run is what the parent
record ordered before a second user is let in.

## Appended 2026-11-03: the code in six boxes

> para el otp, me gusta este componente: https://www.rareui.com/components/otpinput

The login view's code field is now `web/components/otp-input.html`. It takes
rare-ui's `otp-input` as an idea and none of its code: rare-ui is MIT plus the
Commons Clause, and this project's rule for it is in
[`components-of-our-own`](2026-09-28.components-of-our-own.completed.md).
`rareui.com` was not reachable from the session; the repository was, and was
read for the effect.

**What it does:**

- a digit rolls up into its box;
- one caret slides to the box that is waiting;
- a refusal shakes the row and rings it red;
- a login draws a green ring round each box in turn before the page reloads;
- Backspace steps back, and the arrows and Home and End move;
- a paste or the phone's autofill (`one-time-code`) fills every box from the
  one it lands in;
- a click past the first empty box lands on it;
- the sixth digit submits.

**Found while building:**

- **The caller's model arrives a moment after the component's own edit.** A
  reactive pass in that moment still sees the old model, and following it
  wiped the digit just typed. So the component follows only a model it did
  not send itself.
- **`.error` is a class the page already draws.** The component's state is a
  `data-status` attribute instead.

**Verified in Chromium** against a server put online with `luu setup`:
- typed, a Backspace, a wrong code refused (submitted by its sixth digit),
  then a pasted code logging in;
- 375px wide with nothing past the screen;
- no console errors besides the `401` the login view is.
