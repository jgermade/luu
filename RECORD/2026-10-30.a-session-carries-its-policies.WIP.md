# A session carries its policies: copies, a runtime that moves, and what was installed

**Status:** proposal; nothing of it is built. Worked out in conversation, in
these words:

> personalmente, veo que cuando se crea una nueva sesión, se le adjunta una
> copia de cada política elegida (o ninguna), un runtime, y un modelo inicial
> (usaría el último usado, ya que se puede cambiar una vez iniciada la sesión)

> no entiendo el problema de 2, la sesión guarda los jobs, las copias de las
> políticas, los grants y forbiddens, etc, etc
>
> el runtime es simplemente dónde se ejecutan los comandos
>
> lo que implica para el usuario, es advertir que lo que se haya instalado en
> un contenedor ya no estará en el otro... a menos, que añadamos un tool para
> instalar paquetes, de esa manera, podríamos cambiar a otro contenedor e
> instalar lo que tenía el anterior

It finishes what
[`policies-not-postures`](2026-10-22.policies-not-postures.WIP.md) began, and
it disagrees with two decisions recorded before it — named where they come up.

## What there is today

Since 2026-10-23 the new session's dialog makes every session from a runtime
and three lists by name (*every session from lists*, in the record above). No
posture is offered there. Postures are still alive in five places:

| Where | What it does |
| --- | --- |
| `[posture.<name>] policy = "<file>"` in `config.toml`, written by Settings → Runtimes | names a whole policy file: `[worker]`, `[sandbox]`, `[approvals]` |
| `/api/postures` → `runtimes` | the dialog's *Runtime* offers *every image a posture or an environment names*, with the in-image `[[worker.paths]]` of the file that named it (`policies::Place`) |
| `PUT /api/session/posture` | the terminal's place picker moves a live session between postures and environments by name |
| `record::Posture` | the header's name for *where it ran and what it could do* |
| `gate.spec.js` | the gate's tests start on the posture `wide` through the API |

And a session holds its lists **by reference**. `record::Lists` is three
`Hashed { name, sha256 }`. A resume looks the names up in `config.toml` again
and refuses with a 409 when a hash moved. That is the rule
[`what-an-approval-was-granted-under`](2026-09-17.what-an-approval-was-granted-under.completed.md)
settled, and `luu-design.md` gives its reason: *the file behind a name can be
edited tomorrow*. So editing `tools` in Settings → Policies quietly makes every
older session that used it impossible to resume. Deleting it does the same.

## The proposal

### 1. A session is made from copies

A new session takes three things, and keeps them:

```jsonc
{
  "runtime": { "kind": "docker", "image": "luu-worker:0.1.5" },
  "lists": {
    "shell":   { "from": "tools",      "allow": ["git", "cargo"], "deny": ["rm"] },
    "network": { "from": "registries", "allow": ["crates.io"] },
    "files":   { "from": null,         "allow": [] }
  },
  "model": { "provider": "llama", "model": "qwen3.8-27b" }
}
```

- **The lists are copied whole** into the header, not named. `from` is a label
  that says which list it was copied from; nothing reads it back. No list
  chosen is the empty list, as today.
- **The grants and the forbiddens fold on top of the copy**, as they already
  fold on top of the resolved lists (`record::FORMAT` 22, 23). Everything a
  session may do is in its own stream.
- **The model is the last one used**, not the one that started the last
  session: it can be changed once the session runs, so what the dialog offers
  first is what the person was last talking to. `prefs.start` gains it beside
  the runtime and the lists.

What this changes:

| | Today | With the copy |
| --- | --- | --- |
| Edit `tools` in Settings | older sessions on it refuse to resume | they keep their copy; only new sessions see the edit |
| Delete or rename a list | 409 on resume | nothing; `from` is a label |
| Resume | look up by name, compare hashes | rebuild from the copy |
| A posture | a fourth concept beside runtime, lists and model | gone: nothing is left for it to name |

**Against 2026-09-17.** That record compared hashes because a name is a label
and the list behind it moves. A copy does not move, so the reason is gone, and
with it the 409 for *the list was edited*. What stays is the other half of that
rule: a resume does not start a container because somebody clicked a row in the
history. A session on `docker` resumed where there is no Docker is still
refused, naming what is missing.

**Against `record::Posture`'s own comment.** It chose three facts *without
copying a policy file into every stream*. The lists are what has to be copied
now, not the file: three short tables, a few hundred bytes in a header that is
already the largest line. The cost is real and small, and it is what buys a
session that does not depend on `config.toml` staying as it was.

### 2. The runtime is where commands run, and it moves

The runtime decides nothing about what a session may do: the copies, the
grants, the forbiddens and the jobs are the session's, and they go with it. So
a live session may move to any runtime this machine has.

- **`PUT /api/session/runtime`** replaces `PUT /api/session/posture`. It takes
  `{ runtime, image }`, touches no list, and writes a header line, as the move
  does today, so *last header wins* still says from where on it ran somewhere
  else.
- **It waits for a turn to end and a proposal to be answered**, because a
  command in flight has to finish somewhere. It **no longer refuses an open
  approved job**: that refusal existed because a posture moved the policy with
  the place, and an approval granted under one set of rules was carried into
  another. A runtime move carries the same rules.
- **The one thing a move can change is what holds them.** A list is the same
  list everywhere, but on a Mac's host nothing holds a child to it the way
  Landlock does on Linux or a container does anywhere
  ([`a-yes-runs-what-the-kernel-cannot-hold`](2026-10-27.a-yes-runs-what-the-kernel-cannot-hold.completed.md)).
  A move to a place that holds less says so in the warning, below. It does not
  refuse.

**What the person is told.** What was installed in one container is not in the
next:

```
Move to podman · luu-worker:0.1.5
What was installed in docker · luu-worker:0.1.5 will not be there:
  apt: ripgrep, jq    npm: typescript
[Move]  [Move and reinstall]  [Cancel]
```

**Where an image comes from, once postures are gone.** Today an image is
offered because a posture's file names it, with its in-image paths. That moves
to `config.toml`, as one table per image, edited in Settings → Runtimes:

```toml
[image.luu-worker]
ref = "luu-worker:0.1.5"
install = "apt"                       # which manager `install` uses, see §3
[[image.luu-worker.paths]]
path = "/usr/local/cargo"
access = "read"
```

### 3. `install`: a tool, so what was installed is a fact of the session

```json
{ "tool": "install", "manager": "apt", "packages": ["ripgrep", "jq"] }
```

- Its result is a stream line, `installed { manager, packages, runtime }`, folded
  into the session as grants are. That is what *Move and reinstall* replays on
  the new runtime, each install a visible step in the chat.
- **A tool and not a guess.** Reading `apt install …` out of `run_command` misses
  it inside a script, behind flags, or under `sudo`. A tool is one entry that can
  be asked, denied and granted like any other.
- **It asks on `host`, always**, whatever the lists say: there it installs onto
  the person's own machine.
- **It needs the network.** The registry (`deb.debian.org`,
  `registry.npmjs.org`, …) goes through the network list, and is asked for when
  the list does not name it.
- **The manager is the image's.** An `apt` install does not replay on an Alpine
  image. The image declares its manager (`install` above); a replay that cannot
  translate something says which packages it left behind, and does not guess.

## What it costs

- `record::FORMAT` 26: the header carries the copies and `installed` is a new
  line. Every stream before 26 is still read: a posture by name, a header with
  `Hashed` lists and the 09-17 comparison, unchanged, for exactly those.
- A `protocol::VERSION` bump for `installed` and for the move's new route.
- The tool registry grows by one, and its size is asserted in a test (rule C's
  *a new tool has to say which it is*): `install`'s output is evidence, not a
  re-readable view.
- `[posture.<name>]` in `config.toml` is read as an image plus three lists, with
  a warning, for one release, then refused. `luu.container.toml` becomes an
  `[image.luu-worker]` table and the lists it held.
- `[approvals]` leaves the policy file; that is roadmap row 50, and this needs it
  first.

## Rejected

- **Keep the lists by reference and only stop refusing.** A resume would then
  run under whatever the list says today, silently. A copy is what the session
  was started with; a reference is a promise nobody keeps.
- **Freeze the runtime for the session's life.** The runtime decides nothing about
  what a session may do, so freezing it protects nothing, and it makes trying a
  second image cost a new session and its history.
- **Commit the container** (`docker commit`) to carry what was installed. It
  carries everything, the scratch with it, only between the same runtime, and
  nothing on the page can say what is in it.
- **Infer installs from `run_command`.** See §3.

## In what order

Each step leaves luu working.

1. **The copy.** The header carries the lists whole; a resume rebuilds from them
   and stops comparing hashes for streams at 26. The model joins `prefs.start`.
2. **Images in `config.toml`.** `[image.<name>]` with its ref, paths and manager;
   the dialog's *Runtime* reads it instead of the postures.
3. **The move.** `PUT /api/session/runtime`, the terminal's picker over runtimes
   and images, the warning, and the approved-job refusal dropped.
4. **Postures go.** `[posture.*]` read as an image and lists, with a warning;
   Settings → Runtimes stops writing them; `/api/postures` becomes
   `/api/runtimes`; `gate.spec.js` starts on lists. Needs row 50.
5. **`install`**, and *Move and reinstall*. Last, because 1–4 are worth having
   without it.

## Still open

- **`luu-design.md` §*A session picks its posture*** has to be rewritten the day
  step 1 lands: *what is chosen is not a runtime but a posture … on purpose* is
  the sentence this record argues with.
- **The roadmap.** Row 51's *the environment picker where the posture picker is*
  becomes a runtime picker, and rows 49–50 are what step 4 waits on. The
  next revision orders this; this record does not.
- **Environments.** With no preset in the dialog, `[environment.<name>]` is used
  only through the API. Whether it stays as a saved trio of lists, or goes with
  the postures, is not decided here.
- **Which managers.** `apt`, `apk`, `npm`, `pip`, `cargo` are the obvious ones;
  whether a project-level install (`npm install` with no packages) is `install`
  or still `run_command` is not decided.
- **A replay that fails half-way**: the move has happened by then. Whether the
  session stays on the new runtime with what did install, and says what did not,
  or moves back.
