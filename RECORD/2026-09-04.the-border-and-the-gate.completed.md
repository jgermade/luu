# The border and the gate: a session crosses on its own stream

**Status:** stage 1 items 3 and 4 of
[`ROADMAP/2026-08-31/federation.md`](../ROADMAP/2026-08-31/federation.md),
proposed here and built in the same branch. Items 1 and 2 —
[`signed-approvals`](2026-09-04.signed-approvals.completed.md) — are in and this
sits directly on them: what crosses a border is admitted by a host that already
says what it speaks and already knows who approved.

## The problem

Two things have to be true before a session can move between hosts, and both are
false today.

### 1. There is nothing to ship

[`the-portal-and-the-gate`](2026-08-31.the-portal-and-the-gate.completed.md)
rejected the draft plan's `.loude` snapshot in its first collision, and the
reason was not taste:

> A transfer built on the same stream inherits that check for free. A transfer
> built on a snapshot needs its own, and will not get one.

The check is `fold(record) == load(store, id)`, which
[`store_parity.rs`](../crates/luu/tests/store_parity.rs) runs over recordings
produced by running the binary. It is the reason anyone can trust the fold, and a
transfer that ships the stream inherits it.

But **the stream is not on disk unless someone asked for it**.
[`sessions-in-sqlite`](2026-09-02.sessions-in-sqlite.completed.md) stores the
`SessionView` whole and nothing else, deliberately — a normalised schema would be
a second definition of the fold. `--record <file>` writes the stream, and it is a
flag that nothing sets by default and that `serve` points at one file for the
whole process, which multi-session made wrong in a second way.

So for the ordinary session — `luu serve`, no flags, the store on — the only
account on the machine is *the fold*: a rendering of the events, taken at
checkpoints, by code that will drift from the events the first time either
changes. Shipping that is shipping the snapshot the record already rejected,
under a different file name.

### 2. Nothing re-approves

[`session-resume`](2026-09-04.session-resume.completed.md) restores the write
side of a stored session, jobs included: an `Approved` job comes back approved
and its plan is narrowed into a sandbox again. That is right on the machine that
approved it and wrong on any other one, because of what an approval is:

> The approved plan is the sandbox for its job.

An approval is a statement about *resolved paths on one tree*. `src/auth.rs` on
the origin and `src/auth.rs` on the destination are two files, and the plan
carries the words rather than the resolution. Resuming an imported session as-is
would let a person's approval, given at one gate about one tree, grant
`ReadWrite` over a different tree nobody was shown. The nearest-existing-ancestor
rule in `Plan::narrow` makes it wider still, and it has never met paths chosen by
someone other than the person approving.

## The proposal

### The store keeps the stream

`sessions.db` gains one table and the schema goes to 2:

```sql
CREATE TABLE events (
    session TEXT NOT NULL,
    seq     INTEGER NOT NULL,
    line    TEXT NOT NULL,
    PRIMARY KEY (session, seq)
);
```

One row per `RecordLine`, in order, appended at the same checkpoints the fold is
written and in the same transaction as it. This is **not** the normalised schema
`sessions-in-sqlite` rejected: those rows would be a second *definition* of a
turn, competing with `api.rs`. A `RecordLine` is the account itself, opaque to
SQL, and the fold beside it becomes what it always claimed to be — a cache, now
of something in the same file.

What it buys beyond transfer: the parity rule stops being checkable only against
files somebody remembered to record, and `luu transfer` works for the session a
person actually has rather than for the one they would have had if they had set a
flag.

A session stored before schema 2 has no stream. It is **refused for transfer, out
loud**, naming what it has and why that is not enough. Reconstructing a stream
from a fold is exactly the snapshot this record exists to refuse — and it would
be a *forged* one, carrying line orderings and timings that never happened.

### The bundle is a directory

```
sess-2026-09-04/
  manifest.json     the envelope
  record.jsonl      the stream, verbatim
```

The manifest carries only what folding the stream cannot answer, so there is
nothing in it to disagree with:

```json
{
  "kind": "luu-transfer v1",
  "protocol": 6,
  "format": 8,
  "created_at": 1757012345678,
  "origin": {
    "host": "m1-pro",
    "session": "session-1757008000000-3f1a0",
    "base": "/Users/x/luu",
    "sandbox": { "roots": [...], "commands": [...], "network": false, ... }
  }
}
```

`protocol` and `format` are the same handshake the socket has, applied to a file:
a bundle from a host that speaks something else is refused **before** the stream
is parsed, in either direction of mismatch, by the same rule and for the same
reason — neither side can repair it, so neither side guesses.

`origin.sandbox` is the resolved sandbox, which is what
[`the-portal-and-the-gate`](2026-08-31.the-portal-and-the-gate.completed.md) asks
for: *nothing may arrive approved without saying approved where*. The person at
the destination gate can see what the job could reach before, and the difference.

### The border is an event

An imported job that is not `Closed` returns to the gate. That is a thing that
*happens to the session*, on the destination, so it is a line in the stream and
not a state the importer edits into the fold behind it:

```json
{"channel":"protocol","at_ms":0,"message":{"type":"imported",
  "from":{"host":"m1-pro","session":"…","base":"/Users/x/luu","sandbox":{…}},
  "jobs":[{"job":2,"state":"proposed","unmet":[]},
          {"job":3,"state":"rejected","unmet":["write /etc/hosts: outside the sandbox"]}]}}
```

The destination appends that one line, folds the whole thing, and the fold *is*
the imported session — parity intact, because the view was produced by folding
the stream that is stored beside it.

Three rules decide what the line says:

- **`Closed` jobs cross unchanged.** They run nothing; they are a summary the
  history is sent as. Re-gating them would be asking a person to approve a
  paragraph.
- **Everything else returns to `proposed`**, and its approval is *moved* rather
  than dropped: `approved_at_origin` keeps who approved it over there, because
  the difference between an approval given here and one given elsewhere is
  precisely what the destination's gate exists to make visible.
- **A plan that does not resolve against the destination's `luu.toml` crosses
  as `rejected`**, carrying the `unmet` lines that refused it — the same
  `Plan::unmet` the local gate runs, so a plan is refused at a border for
  reasons a person can read in the same words they see at the keyboard.

`imported` is a new variant of a tagged enum, which by this project's own rule is
exactly the change that bumps both numbers: **protocol 5 → 6, record format 7 →
8**.

### The gate holds on resume

`Pending` — the prompt held between a proposal and the answer to it — becomes
`Option<String>`. An imported job has **no held prompt**: the prompt that opened
it already ran, on the origin, and inventing one would put words in a person's
mouth to give the gate something to release. Approving it opens the job and
starts nothing; the next prompt is a turn inside it.

Resume then re-establishes the gate whenever the session's last job is
`Proposed` — imported or not. The local case is the same bug with a smaller blast
radius: a proposal pending when `serve` stopped came back as a job sitting in
`Proposed` with nothing holding the gate, so the next prompt quietly proposed a
second job beside it.

### The two commands

```sh
luu transfer <session-id> --out ./sess           # from the store on this host
luu transfer --record run.jsonl --out ./sess     # or from a recording
luu import ./sess                                # into the store on that host
```

`import` prints what the border did: which jobs are waiting at the gate, which
were refused and why, and the origin's sandbox beside this host's, which is the
difference the person approving is being asked to judge.

## What it costs

- **A schema migration**, from 1 to 2. Additive — the `sessions` table does not
  move — and a store written by an older `luu` keeps its sessions and gains the
  table. What it cannot gain is the streams those sessions never wrote.
- **The store grows by the size of the stream**, which is every token line. A
  twenty-turn session is hundreds of kilobytes of JSON. Compression stays
  deferred for the reason it always was: it is a dependency, a format decision
  and a thing to get wrong, and nobody has measured a real session yet.
- **Protocol 5 → 6 and format 7 → 8.** One new variant, one bump each, and the
  handshake built in the last record is what makes the bump legible to the other
  side rather than fatal to it.
- **The origin's sandbox is resolved at transfer time, not at run time.** The
  stream carries a `Verdict` per tool call and never the sandbox itself, so what
  the manifest can honestly say is *what the origin's policy file resolves to
  now*. If `luu.toml` changed since the run, the manifest is about the file and
  not about the run — and the plans in the stream, which are exact, are what the
  gate actually re-checks. Named here rather than papered over.
- **Two clients now have to understand a session that arrived from elsewhere.**
  The web UI learns one message; anything older ignores it, which for a client
  older than this record means a job that looks approved and a server that will
  not run it. That is what the version in the handshake is for.

## What was rejected

- **Shipping the fold.** Collision 1 of
  [`the-portal-and-the-gate`](2026-08-31.the-portal-and-the-gate.completed.md),
  again, and the answer has not changed: the record is the format. Shipping a
  `SessionView` would work on the first day and drift on the day `api.rs`
  changes, and nothing would fail.
- **Reconstructing a stream from a stored fold** for sessions that predate the
  events table. It is a snapshot wearing a stream's clothes, and it would put
  line orders and timings into a record that never had them.
- **Re-approving automatically when the destination's policy grants everything
  the plan named.** It looks safe and it is the exact case the gate exists for:
  identical *words* over a different tree. A plan that resolves cleanly on
  arrival is still a plan nobody on this machine has ever been shown.
- **Making `job_proposed` reset an existing job** instead of adding a variant.
  It would change how every recording already made folds, and re-proposal at a
  border is not the same event as a proposal — one of them has an origin.
- **A tar or a zip.** A directory needs no dependency and is readable with
  `cat`; the transport that will eventually want a single blob can make one.
- **Signing the bundle.** Not because integrity does not matter, but because it
  is not what stops the dangerous thing: the *approval* is signed and the gate
  re-runs on arrival, so a forged stream buys a liar some history and no
  authority at all. Still open below.
- **Moving the session over a socket, in this item.** Stage 1's four items are
  about *what* crosses a border and what happens when it lands. A wire leg is a
  transport with its own argument (push or pull, discovery, who initiates), and
  `scp` moves a directory today.

## Still open

- **Nothing archives the origin.** After a transfer both hosts hold the session
  and an append to either is a fork. Forbidding it — the origin marks the session
  archived on transfer — is smaller than naming it and is what
  [`the-portal-and-the-gate`](2026-08-31.the-portal-and-the-gate.completed.md)
  said it would ship first. It is not in this record because "transferred" is a
  state the store does not have yet, and inventing one to hold a flag is the
  kind of column that becomes a second truth.
- **Nothing signs the stream as a whole.** A relay that drops lines is not
  detected by anything here, and the manifest's `format` and `protocol` are not
  a checksum.
- **The transfer probe is unrun**, which is the whole point of the item after
  this one. This builds the mechanism; the claim *a session moves between
  backends without loss of context* is unmeasured, and this project has already
  been wrong about a claim of exactly that shape once — the fold's.
- **Counters do not travel.** The stream's header names the counter that measured
  the origin's history, and a destination running another model will count the
  same turns with a different ruler. The header says so; nothing yet refuses, or
  even warns, and the probe's protocol is where that number has to be read.
- **Evidence leaves the machine.** A `tool_result` carries the bytes the model
  was given, which is the whole point of shipping the stream — and it means a
  transfer moves file contents and command output off the host. For a
  local-first project that is the largest thing here pointing the other way, and
  it is why the bundle is a local directory rather than an upload.

## Appended the same day: withdrawn

Everything above was built and then removed, hours later, when the question it
answers turned out to be the wrong question. **A session belongs to the host that
made it**: the model somebody wants on a bigger machine is reached by pointing
the backend at it, and the tree — which is what a session is about here — moves
by git. So there is no transfer, no bundle, no border and no portal. The
argument, and what the rule closes by construction rather than manages, is
[`sessions-stay-home`](2026-09-04.sessions-stay-home.completed.md).

What is left of this record is not nothing, and it is worth naming so the file
reads as what it is rather than as a dead end:

- **The store keeps the stream** (schema 2). It was built here for a transfer to
  ship and it stayed for its own reason — the fold is a cache, and until this the
  thing it was a cache *of* existed only when somebody passed `--record`.
- **The gate is re-established on resume**, and `Pending.prompt` stays optional.
  Found here as the imported case; kept because the local one is real: a proposal
  that outlived its server used to come back with nothing holding it.
- **A session's lines are timed from the session's start**, not the process's.
- **The argument itself.** What a transfer would have to be — the stream and not
  a snapshot, the envelope checked before the stream, an approval that does not
  cross a border — is the argument anyone re-opening this has to answer, and it
  is easier to argue with something that was built than with something imagined.

Nothing above this line was changed. `protocol::VERSION` is 5 again and
`record::FORMAT` is 7: the bump this record describes was un-made with the
variant that caused it, because a number whose whole job is to tell two peers
what they can parse must not carry a variant that no longer exists.
