# The image `serve` was started on

## The problem

Reported while creating a session on an Alibaba Cloud provider:

```
Could not create session: no [image.*], posture or environment in config.toml
names the image `ghcr.io/jgermade/luu-worker:0.1.13`, and a session runs only
on an image this machine names
```

The provider has nothing to do with it. That image is the Helm chart's: it
starts `luu serve --worker kubernetes --worker-image
ghcr.io/jgermade/luu-worker:<appVersion>`.

## Why

`--worker` and `--worker-image` are the flags *over every* `[worker]`
(`SandboxArgs::worker_over`): every place `/api/postures` offers is described
through them, so on the chart the new session's dialog is offered
`kubernetes · ghcr.io/jgermade/luu-worker:0.1.13` and nothing else. Starting the
session sends that runtime and image back, and `place_for` checks the image
against `images_named` — `[image.*]`, the postures' files, the environments —
which never looked at the flag. The server refused the only place it had
offered. Reproduced without a cluster: `serve --worker docker --worker-image
ghcr.io/jgermade/luu-worker:0.1.13` with a `docker` on `PATH` that runs the
worker here; `POST /api/sessions {runtime: "docker", image: <that>, lists: {}}`
answered the message above.

## The proposal

`images_named` also names the image `serve` was started on — its own policy
described through the flags (`describe_for(None, None)`), where that is a
contained runtime with an image — with the in-image paths of its own file
where it has one. Last, after `[image.*]` and the files, so nothing about the
order a configured machine sees changes. *A session runs only on an image this
machine names* still holds: whoever started the server named it.

## Cost

One more image in the list, on a server started with a contained worker. One
`describe` per listing, which reads a policy file and asks whether the runtime
is installed — the work every offered place already pays.

## Rejected

- **An `[image.*]` written by the chart** (a ConfigMap with `config.toml`): the
  state directory's `config.toml` is the owner's, written from Settings, and a
  second writer would fight the first on every upgrade.
- **Not applying `--worker-image` to the places offered**: the flag is how the
  chart says *every session is a pod on this image*, and a cluster has no
  other runtime to offer.

## Evidence

- `serve::tests::the_image_serve_was_started_on_is_one_this_machine_names`:
  the started image named and accepted by `place_for`, an image nobody named
  refused, and a server whose own worker is on the host naming none.
- The reproduction above, after: the session is made (`201`), and
  `luu-worker:9.9.9` is still refused with the same sentence.

## Still open

- **A session stored on the previous release's image.** After `helm upgrade`
  from 0.1.13 to 0.1.14 the flag names `:0.1.14`, and a session that copied its
  place on `:0.1.13` is refused on resume with this message. Whether a worker
  image of luu's own repository should follow the release, as a locally built
  release image is rebuilt when its version moved, is not decided here.
