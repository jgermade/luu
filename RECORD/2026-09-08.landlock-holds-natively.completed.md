# Landlock holds the child natively, no VM in the way

**Status:** closed. Machine 4 (`Ryzen 5 3600 + RTX 5060 Ti`, native CachyOS Linux,
hostname `ryzen-cachy`) answers the question
[`machines.md`](../ROADMAP/2026-09-01/machines.md) left open for machines 4 and 6:
*does native Linux hold a subprocess the way the M1 Pro's Docker VM does, or does
it need something in the way too?*

## Setup, so the run is reproducible

Nothing was installed on this box before this record: no `ollama`, no
`llama-server`, no Rust. Built from scratch —

- `pacman -S llama-cpp ggml-cuda` — `ggml-cuda` pulls the `cuda` toolkit (~2.2 GB)
  and loads as a plugin (`/usr/lib/ggml/libggml-cuda.so`); `llama-cpp` ships
  `llama-server`/`llama-cli` and picks it up at runtime, no separate CUDA build.
- `pacman -S rustup && rustup default stable` — `cargo build --release --bin luu`.
- `Qwen/Qwen2.5-Coder-7B-Instruct-GGUF` (Q4_K_M, ~4.7 GB) plus the HF
  `tokenizer.json` from the non-GGUF repo (the GGUF does not carry it).
- `llama-server --ctx-size 8192 --n-gpu-layers 99` — full offload, ~6 GB VRAM
  resident on a 16 GB card.

```sh
luu chat "hola" --backend openai --openai-url http://127.0.0.1:8080/v1 \
  --model qwen2.5-coder-7b --context-limit 8192 \
  --tokenizer ~/models/qwen2.5-coder-7b/tokenizer.json
```

answered, confirming the OpenAI-compatible backend
([`2026-09-01.an-openai-compatible-backend.completed.md`](2026-09-01.an-openai-compatible-backend.completed.md))
reaches `llama-server` as designed — the first time anything in this repository has
been measured against it rather than Ollama.

## The command, and what it said

With the real model in the loop (not the mock) and no container, no VM, nothing
between `run_command` and the kernel:

```
$ luu chat 'Use the run_command tool now. End your reply with exactly:
```tool
{"name": "run_command", "arguments": {"command": "ls", "args": ["-la"]}}
```
and nothing else.' --backend openai --openai-url http://127.0.0.1:8080/v1 \
  --model qwen2.5-coder-7b --context-limit 8192 \
  --tokenizer ~/models/qwen2.5-coder-7b/tokenizer.json

  [1] → run_command {"args":["-la"],"command":"ls"}
  [1] ← ok · commands allows `ls` · held by landlock ABI v10 + seccomp (no sockets, no ptrace) + rlimits (cpu 300s, file 1024M) · 4 ms
```

`luu tools` shows the same policy resolves with `enforce kernel` and no gap noted
— unlike the M1 Pro, where the verdict is only reachable at all inside the Docker
VM's Linux kernel
([`2026-09-01.the-container-decided.completed.md`](2026-09-01.the-container-decided.completed.md)),
and unlike macOS bare-metal, where `fallback.rs` denies `run_command` outright and
says what's missing.

## The finding

**Native Linux needs nothing in the way.** `linux.rs`'s Landlock ruleset and
seccomp filter apply directly in `pre_exec`, on the host kernel, with no VM boot
and no container runtime — the thing level 3 exists to *simulate* on macOS is
simply what this machine already has. `ABI v10` is also the first time the actual
negotiated Landlock ABI version has appeared in a verdict in any record; the M1
Pro's VM kernel was never checked for which ABI it negotiates.

This closes the machines-4/6 half of the Open item verbatim: *"Landlock on
machines 4 and 6, once either runs Linux... One command each, and it decides
whether the box can hold a subprocess at all."* It can. Machine 6 (BC-250) is
still unchecked — different kernel, different distro, and it is also carrying the
separate open question of a third serving stack (Vulkan).

## What this does not answer

- **Not speed.** The inventory's bandwidth column is what set machine 4's
  "fastest box for 16 GB" claim before this record; nothing here times anything,
  on purpose — this project scores answers, not seconds.
- **Not the grounded pair.** Deliberately not re-run here —
  [`machines.md`](../ROADMAP/2026-09-01/machines.md) says why: token accounting is
  backend-independent and already recorded on machine 1, and repeating it
  elsewhere would measure the machine instead of answering anything new.
- **Not the tool-call grammar.** The model's first, uncoached attempt at the same
  ask used a ` ```run_command ` fence instead of ` ```tool ` with a `"name"`
  field, and `luu` did not recognise it as a call — it answered as prose and
  stopped. Only an explicit, spelled-out format in the prompt got a real call
  through. That is the open question in
  [`2026-09-06.a-grammar-for-tool-calls.WIP.md`](2026-09-06.a-grammar-for-tool-calls.WIP.md),
  observed here rather than chased — this record is about the sandbox, not the
  grammar.
