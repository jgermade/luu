# What rule C is worth: measured, on the corpus it needed

**Status:** closes roadmap item 3b of
[`ROADMAP/2026-09-09`](../ROADMAP/2026-09-09/README.md) — *what rule C
(`--prune-results`) is worth* — using the instrument
[`a-call-every-turn`](2026-09-14.a-call-every-turn.completed.md) built earlier
today. Follows the same split
[`what-a-result-costs`](2026-09-09.what-a-result-costs.completed.md) left
open: "the prompt is smaller and the conversation is intact" was a claim the
tests made; this is the run that checks it.

## The question

`--prune-results` lets a turn behind the prune line give up its tool
*output* too, the same way `--prune-behind` already lets it give up quoted
code — call stays, result becomes a citation. Built and tested on
2026-09-09, never run: no corpus existed where a tool was called often enough
for it to matter. `--mock-cycle` fixes that. This is the run.

## The run

Twenty turns, one flag apart, three arms — `off`, `--prune-behind`,
`--prune-behind --prune-results` — against the **mock** backend at
`--context-limit 8192 --reserve 512`, the same split `prune-behind`'s own
first measurement used, because this is a claim about the window's mechanics
and does not need a model to check it. Every turn calls `read_file` on a
136 KB source file (truncated to the 8 KiB cap every time) and answers in one
word, so every turn is dominated by one maximal tool result and nothing else
competes with it. Full methodology, transcripts and the derived numbers are
in [`runs/2026-09-14.prune-results/`](runs/2026-09-14.prune-results/).

## What it says

| | `off` | `--prune-behind` | `--prune-behind --prune-results` |
| --- | ---: | ---: | ---: |
| turns evicted, of 20 | 16 | 16 | **0** |
| turns pruned | — | 0 | **16** |
| tokens freed by pruning | — | 0 | **32 752** |
| turn 20's prompt (content, excl. reserve) | 6 776 | 6 776 | 7 545 |
| mean prefix reuse | 21.7% | 21.7% | **26.9%** |

**`--prune-behind` alone changes nothing here, and that is the problem this
row exists to state precisely rather than gesture at.** Fifteen `pruned`
trace events fire — the ratchet moves, exactly as designed — and every one of
them prunes zero turns and frees zero tokens, because rule B walks
`code_context` and this corpus has none: every turn's content is a `ToolStep`,
which rule B has never reached. `off` and `--prune-behind` are
indistinguishable on every row of this table. That is not this run failing to
find a difference; it is the exact gap
[`what-a-result-costs`](2026-09-09.what-a-result-costs.completed.md) named —
*"an 8 KiB `cat` and a 1 000-token fragment are the same object to the
window"* — reproduced as a number instead of an argument.

**`--prune-results` does not just shrink the window here — it stops eviction
happening at all.** 16 of 20 turns were evicted whole under the first two
arms: by turn 20, most of the conversation is simply gone, the question and
the answer both, not only the code. Under `--prune-results` nothing is
evicted — 16 turns are pruned to a one-line citation instead, `32 752` tokens
of tool output are freed over the run, and all 20 exchanges are still in the
prompt at turn 20. **Full conversational continuity, at a prompt that is
still under budget** — turn 20's content is 7 545 tokens against an available
7 680 (`8192 − 512` reserve).

**The turn-20 prompt is *larger* under `--prune-results` than under the arms
that evict (7 545 against 6 776), and that is the same finding
`prune-behind`'s own record made, sharper.** *"Rule B does not make the
prompt cheaper, it changes what the same prompt is made of"* — rule C does
that and more: spending the freed room on keeping every exchange instead of
losing most of them to eviction is a choice the numbers show being made, turn
by turn, not a side effect. Mean prefix reuse rising with it (21.7% → 26.9%)
is the same consequence `--repeat-once` and `--prune-behind` both produced —
a cheaper turn fills the window more slowly, so the block is rewritten less
often.

## What this does not answer

- **Whether a model minds.** Stated as open when the code landed and still
  open: a citation where `cargo test` output stood is a stronger claim than
  one where quoted code stood, because the output is evidence and a job's
  closing condition reads exit codes from `ToolStep`, not from the prompt.
  The backend here is the mock; nothing here says a real model is unbothered
  losing eight kilobytes of a command's output to one line.
- **A mixed corpus.** Every turn here calls the same tool on the same file at
  the cap. A conversation where tool output varies in size — a `list_dir`
  next to a `cargo test` — was not built, and `prune_to`'s guard (a citation
  that costs more than it saves is not taken) never had a chance to bind in
  this run because every result here clears it by a wide margin.
- **Whether the numbers generalize past this window size.** One
  `--context-limit`, the same one `prune-behind`'s first measurement used, for
  the same reason — comparability to that record, not a claim that 8192 is
  representative.

## What was rejected

- **A corpus with real fragments as well as tool calls.** It would answer a
  more realistic question and a noisier one — rule A and rule C would then be
  saving room from the same turn at once, and the table above would not be
  able to say which one a given freed token came from. Isolating the tool-only
  case first is what makes the "rule B reaches nothing here" row legible; a
  mixed run is a different, later measurement.
- **Measuring against a real model.** The claim under test — how many tokens
  a citation frees, whether eviction still fires — is entirely mechanical and
  the mock answers it exactly, the same call `prune-behind`'s first
  measurement made before its own later model-in-the-loop question was filed
  as open rather than answered here.
