# An installer and a landing

## The question

*En GitHub pages desplegaremos una landing con info de la aplicación, que incluya
un comando one-line para instalar la aplicación jgermade.github.io/luu/setup.sh.
Que permita instalar, reinstalar o desinstalar en Linux y MacOS.* And, while it
was being written: *la web mobile first*.

Until today the root of Pages was the web UI replaying recordings, and getting
luu onto a machine meant finding the release, picking the tarball, unpacking it
and putting the binary somewhere on `PATH` by hand. There were two tarballs:
x86_64 Linux and Apple Silicon.

## What it is

- **`pages/` is the root of Pages, served as it is**, like `web/`: an
  `index.html` with its CSS and its one script inline, and `setup.sh`. The
  assembled `site/` goes beside it as `demo/`. Nothing in the replay moved: it
  only ever used relative paths, and the suites keep serving `site/` at its own
  root, so they do not know it moved either. The landing is held to the site's
  rule — no CDN, no font host — by the same `grep`.
- **The page is mobile first**: the base rules are a 375px phone and each
  `min-width` query only adds. The install commands *wrap* rather than scroll,
  because the end of the line — `| sh`, `reinstall`, `--purge` — is what tells
  the four apart, and the quick-start block is broken by hand, one flag a line,
  so its longest line fits a phone edge to edge. Checked at 375, 768 and 1280,
  light and dark: no element scrolls sideways and the console is empty.
- **`setup.sh` is POSIX sh**, because `curl … | sh` is dash on Debian, and it is
  all functions with `main "$@"` as the last line, so a download cut short runs
  nothing.
  - `install` (the default) resolves the latest tag from the redirect GitHub
    answers `releases/latest` with — no API call, no rate limit — and does
    nothing when that version is already installed. An older one is replaced.
  - `reinstall` downloads and replaces whatever is there.
  - `uninstall` removes the binary and **keeps the state directory**, saying
    where it is. `--purge` deletes it too: every one of `LUU_HOME`, `~/.luu` and
    `$XDG_CONFIG_HOME/luu` that exists, the way `config.rs` resolves them, listed
    with their sizes and asked about on `/dev/tty`. With no terminal and no
    `--yes` the answer is no. A `LUU_HOME` of `/` or `$HOME` is refused before
    anything is listed.
  - **The binary goes to `~/.local/bin`**, or `--dir`. No root, and no shell
    profile is edited: when the directory is not on `PATH` the script prints the
    line to add for the shell it finds.
  - **The download is checked, then run, then moved into place.** Checked
    against the release's `SHA256SUMS`, which `release.yml` now publishes; for a
    release made before it had one (v0.1.1 is the only one), against the
    `digest` GitHub keeps for every asset, which is what `engines.rs` checks
    engines against. A mismatch stops; a release with neither warns and
    installs. Then `luu --version` runs from the temporary directory, because
    v0.1.1's Linux binary needs `GLIBC_2.39` and would otherwise replace a
    working binary with one that cannot start on Debian 12. Then it is copied
    beside the old one and renamed over it, so a running `luu serve` keeps its
    file.
  - `LUU_DOWNLOAD_URL` swaps GitHub for a directory — a mirror, or `file://` for
    a local build — which is also how CI tests it.
- **Four targets.** `x86_64` and `aarch64` Linux, built on `ubuntu-22.04` and
  `ubuntu-22.04-arm` so the glibc floor is 2.35 rather than 2.39; Apple Silicon,
  and Intel macOS cross-built on the Apple Silicon runner. The sandbox already
  had its seccomp arch for `aarch64`.
- **`scripts/setup-check.sh` walks the installer** against each archive a runner
  can execute: install, install again (nothing to do), reinstall, a wrong
  checksum (refused, old binary untouched), a `--dir` with a space in it,
  uninstall keeping the state, `--purge` with nobody to ask (refused), and
  `--purge --yes`. `shellcheck` runs over both scripts in the `web` job.

Checked by hand before CI: the script under dash and bash against the real
v0.1.1 release (installed, verified through the asset digest, found already
installed, reinstalled); `setup-check.sh` against v0.1.1's Linux archive and
against one packaged from this commit, every step passing; and the Pages tree
assembled as the `web` job assembles it, served under `/luu/` — the landing's
demo link opened the replay at `/luu/demo/` with its eleven fixtures, no
response above 399 and nothing in the console.

## What it costs

- **Two more binary jobs on every push**: arm Linux, and the Intel cross-build.
- **The demo's address moves** from `/luu/` to `/luu/demo/`. An old link lands
  on the landing, which links the demo twice.
- **Pages deploys only on a release**, so the landing and
  `jgermade.github.io/luu/setup.sh` exist from the next release on — which is
  also the first with four targets and a `SHA256SUMS`, so the page never
  promises a build the release does not have.

## What was rejected

- **Editing `~/.zshrc` or `~/.bashrc`**, the way rustup and bun do. A script
  piped from the web writing dotfiles is a lot to take on trust for what a
  printed line does in one paste.
- **`/usr/local/bin` with `sudo`.** Nothing in luu needs administrator rights,
  and the installer should not be the first thing that does.
- **A static musl build** instead of the older runner. It would start on any
  Linux, at the price of a different allocator and resolver under a binary no
  run here has measured. The glibc floor moved instead; musl is told to build
  from source.
- **`jq` or Python** to read GitHub's JSON: neither is on a stock macOS. `awk`
  over the pretty-printed response is enough for the one field, and it is only
  read for releases that predate `SHA256SUMS`.
- **`wget`.** Every macOS has curl, and the one-liner is a curl line.
- **The landing inside `web/`**: `rust-embed` would bake it into every binary,
  for a page no binary serves.

## Still open

- **The four-target matrix had not run when this was written**, nor the
  `ubuntu-22.04` runners. The branch's own CI is the first run.
- **The Intel macOS binary is built and never executed**: its runner is Apple
  Silicon, and the installer check skips it.
- **Monaco and xterm.js are out of reach of an installed binary.** `serve` looks
  for them under the build machine's checkout unless `LUU_UI_DIR` says
  otherwise, and the installer installs neither. The page draws files itself
  and the terminal panel says how to install xterm.js, as on a checkout without
  npm.
- **Nothing is notarized.** curl sets no quarantine attribute, so the binary
  runs; the same tarball downloaded by a browser would be stopped by Gatekeeper.
- **No Windows.**
