# Why every `git` call exited 128, and what the sandbox was missing

**Status:** closed. Root cause found, one code fix, one documented policy
line, both verified against the real sandbox on machine 4.

## The aside that had been sitting around

`RECORD/2026-09-15.the-drift-was-never-the-backend.completed.md`'s session
noticed in passing that `git status --short` "failed every time in this
machine's default `luu.toml` sandbox (exit 128) despite the tool call being
correctly formatted every time", and said it was "worth someone checking why
`git` is denied here specifically." Nothing was written up, so it was not in
`RECORD/` at all — it survived only as a line in an agent's memory file, which
is exactly the shape of thing this directory exists to stop.
`RECORD/2026-09-15.a-three-pane-inspector.completed.md` picked it up again because a
git panel would depend on the answer.

## It was never about `git status`, or about git's repo detection

The first probe that mattered was the cheapest one: **`git --version` exited
128 too**, in one millisecond. Nothing about a repository, a config, or a
working tree can explain that — `git --version` reads nothing and answers from
a constant. Whatever was wrong happened before git did any work at all.

The `run_command` result carries the child's stderr, and the recording had it:

```
fatal: could not open '/dev/null' for reading and writing: Permission denied
```

**Git calls `sanitize_stdfds()` before `main()` gets going**, which opens
`/dev/null` to guarantee fds 0, 1 and 2 exist. The sandbox's implicit grants
are [`SYSTEM_ROOTS`] — `/usr`, `/bin`, `/sbin`, `/lib`, `/lib64`, `/etc`,
`/opt` — granted `Access::Execute` so a command can read its own interpreter
and libc. `/dev` is not among them, and would not have helped if it were:
opening the null device wants read *and write*, which is not what execute
grants.

`ls`, `cargo` and `rg` never tripped it, which is why this looked like "git is
denied" rather than "the sandbox has no null device": those three do not open
`/dev/null` on the way up.

## The fix, and the second thing hiding behind it

**`NULL_DEVICE` (`/dev/null`) is now an implicit read-write grant**, added
beside `SYSTEM_ROOTS` and separately from them because it is the one path here
that execute permission cannot answer. Read-write on the null device is not a
hole and is not a judgement call: writes are discarded and reads are EOF, by
definition of the device, so nothing can be persisted through it, hidden in it
or read back out of it. Every sandbox that runs ordinary programs — bubblewrap,
Docker, systemd — mounts it unconditionally for the same reason.

**And the first attempt at the fix did not work**, which was the more
interesting half. Registering the root was not enough: Landlock rules on a
*regular file* may carry only rights that mean something for a file, and
`build_ruleset` was asking for `AccessFs::from_all(TARGET_ABI)` — which
includes `ReadDir`, `MakeReg` and the rest of the directory-only set — for
every root indiscriminately. Every root a policy names is a directory, so
nothing had ever exercised that path. `/dev/null` is a character device, and
the rule was rejected. The build now masks a non-directory root's access with
`AccessFs::from_file(TARGET_ABI)`.

With both in place `git --version` answers `git version 2.55.0`, exit 0.

**`git status` still exited 128**, and this time the cause is by design rather
than a gap. Git reads the global config at startup, and the sandbox does not
grant `$HOME`:

```
warning: unable to access '/home/joshua/.gitconfig': Permission denied
fatal: an unknown error occurred while reading the configuration files
```

Note the asymmetry that makes this bite: git tolerates a config that is
**missing** and treats one it gets `EACCES` on as **fatal**. The design's
answer is the one already written into `luu.toml` for `~/.cargo` and
`~/.rustup` — "everything else a command needs is the user's to name … one
informed line beats a prompt per call". Adding

```toml
[[sandbox.paths]]
path = "~/.gitconfig"
access = "read"
```

makes `git status --short` return `ok` against the real ruleset. That line is
now documented in `luu.toml` beside the other two, with the fatal-vs-missing
asymmetry spelled out, because the error text git produces for it names
neither the file nor the permission.

## Why the `/dev/null` half is implicit and the `~/.gitconfig` half is not

They fail at different heights. Without the null device a command **cannot
start**, and a policy that lists `git` under `commands` while granting a git
that cannot reach `main()` is a policy lying about what it granted — the
grant has to be implicit or the sandbox does not do what it says. A global
config is ordinary user data the program reads once it is running, which is
the category the design deliberately makes a person name: granting `$HOME`
implicitly to make `git status` work would hand every allowed command the
user's whole home directory, which is the trade `luu.toml`'s own comment
argues against.

## What this does not answer

- **Which other allowed commands want `/dev/urandom` or `/dev/zero`** is
  untested. Both are as harmless as `/dev/null` by the same argument, and
  neither was added: nothing has been observed needing them, and a grant with
  no demonstrated need is a grant nobody can evaluate.
- **The container posture** (`luu.container.toml`) was not re-checked. A
  container image has its own `/dev`, so this is likely moot there, but
  "likely" is not a measurement.
- **Whether `git` inside a job's narrowed sandbox** (a plan that grants less
  than the session) hits anything further was not probed; everything here was
  run under the session's own policy.
