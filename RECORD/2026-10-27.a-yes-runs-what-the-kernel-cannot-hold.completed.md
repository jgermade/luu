# A yes runs what the kernel cannot hold

Reported from a Mac, on a session made from lists, on the host:

> *Parece que no aplican los grant: al hacer click en allow, falla el comando
> y no sale nada en grants.*

And, asked which of three it should be — the yes runs it; nothing is asked
where a yes could not run it; or the session chooses its enforcement when it is
made:

> *La 1, que el Allow lo ejecute.*

## The problem

**On a Mac a draft's command was asked about and then refused anyway.** Off
Linux there is no Landlock and no seccomp, so under `enforcement = "kernel"` —
the default, and the only value a session made from lists can have — every
`run_command` is refused with *the kernel cannot hold this child*. A program
the shell list leaves to a person was asked about all the same: the ceiling
(`grants::DraftCeiling`) built the sandbox a yes runs under with the program
allowed, but with the same enforcement, so the yes ran the call into the same
refusal. The question was one whose answer changed nothing.

**A program the list allows was never asked about.** The ceiling refused to
ask about a listed program — *it was refused for something other than its
name, so a yes would change nothing* — which on Linux is true and on a Mac
meant that `ls`, allowed, could not run, while `git`, unlisted, could at least
be asked about.

**Nothing in *grants* was the other half, and not a fault.** *Allow* without
*Apply to session* is a yes for that call; only a yes or a no for the session
is a grant, listed under the draft and in Permissions → Granted.

## The proposal

**A person's yes runs the command, where the kernel cannot hold it, under
`best-effort`.** In `DraftCeiling::escalate`, once the program is allowed in
the sandbox a yes would run under, that sandbox is asked to prepare the command
(`Sandbox::prepare_command`, which runs nothing). If it refuses — the one
refusal left once the name passes is the kernel's gap — its policy is rebuilt
with `enforcement = BestEffort`. The child is held by its resource limits only,
and the verdict says so, as every `best-effort` verdict does: `Partial`, with
what is missing.

**Said before the click.** `Asker::ask` is handed `unheld` — what will not hold
the call under the sandbox a yes runs it in (`agent::unheld`) — and `call_held`
carries it to the page, which draws it on the question: *Nothing on this
machine holds it (landlock and seccomp are Linux-only, and this is macos):
allowed, it runs as you, held only by its resource limits.* The session view
keeps it beside `held`, so a page that reloads gets the warning back with the
question. An optional field on a message that already exists, absent wherever
the kernel holds the command: additive, as `tool_result.command` was, and no
protocol bump.

**A listed program is asked about where the kernel refused it.** Allowed by
name and refused all the same is the kernel's gap; the ceiling now treats it as
it treats an unlisted program, and a yes runs it the same way. On Linux,
where the kernel holds it, nothing changes: the floor runs it, and nobody is
asked.

**The same for the session.** A yes with *Apply to session* is the same
sandbox, granted: later calls to that program run without asking, under
`best-effort`, until it is taken back.

## The commitment it bends

`AGENTS.md`: *a subprocess is the kernel's to hold … where the kernel cannot,
the default is to deny rather than to run the child unheld.* The default still
does: a command nobody answered is refused, and a draft's floor is not
widened. What changes is that a person's explicit yes, about one program, with
the gap named in the question, is no longer overridden by the default. That is
the answer chosen; the second option kept the commitment whole and left a Mac
unable to run any command in a draft.

## What it costs

- On a Mac, an allowed command in a draft runs held by its resource limits and
  the in-process check of its name — not by the filesystem rules of the
  session's lists. That is what the question says.
- `Asker::ask` takes one more argument; the three that implement it (the
  server's, and two in tests) pass it on or ignore it.

## Rejected

- **Not asking where a yes could not run it.** Honest, and kept the commitment;
  it left every draft's command on a Mac refused, with no way past it from the
  page.
- **Choosing the enforcement when the session is made.** A session-wide
  `best-effort` would run commands nobody was asked about unheld; the yes is
  per program, and per session only when somebody says so.

## Still open

- macOS has Seatbelt (`sandbox-exec`), deprecated and still shipped. A profile
  built from the session's lists would hold a child's filesystem there the way
  Landlock does here; then `unheld` would say less, and the yes would be needed
  less.

## Built, the same day

As proposed. Tested: `grants::tests` — whatever holds a command on this
machine, the sandbox a yes runs `git` under can prepare it, and `unheld` is
said exactly where the kernel cannot hold a listed one; a listed `ls` is
refused unasked where the kernel holds it and asked where it cannot.
`grants.spec.js` — on Linux the question says nothing of it; with `unheld` set
as the server words it on a Mac, the question says *held only by its resource
limits*. Not run on a Mac.
