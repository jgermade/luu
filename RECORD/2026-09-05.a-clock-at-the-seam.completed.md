# A clock at the seam, and a ceiling on the one inside it

**Status:** a proposal and the code it plans, written on 2026-09-05. Item 1 of
[`ROADMAP/2026-09-05`](../ROADMAP/2026-09-05/README.md), and the second of
`luu-design.md`'s open questions — *"a tool call has no timeout at the seam"* —
plus one thing found while closing it.

## The problem

Level 3 puts every tool call on the far side of a pipe
([`the-worker-and-the-seam`](2026-09-02.the-worker-and-the-seam.completed.md)).
Three things can go wrong there, and today only two of them are covered:

| what happens | what the host sees |
| --- | --- |
| the call is denied | an `Outcome` with an unallowed verdict |
| the worker dies mid-call | EOF, which `epitaph()` turns into a named error |
| **the worker is alive and stuck** | **nothing, forever** |

`Pipe::round_trip` awaits `read_line` with no deadline. A worker that never
answers is not a failed call — it is a session that stops, with a `serve` turn
that never ends, a `job` that never leaves `Running`, and a container that has to
be killed from another terminal. The one clock in the picture is *inside* the
tool: `run_command` wraps its child in `tokio::time::timeout`. That clock covers
the child and nothing else — not a wedged `read_file` on a dead network mount,
not the worker's own loop, and not the container runtime between the two.

**A clock inside the thing being timed cannot time it.** That is the whole
argument for moving it to the seam, and it is the same argument the sandbox
already makes about the kernel: the party that must not be trusted to stop is
not the party that holds the stopwatch.

### The second finding

Reading `run_command`'s clock to write the seam's turned up a hole in the clock
itself. `timeout_ms` is a **model-supplied argument with no ceiling**:

```json
{"name":"run_command","arguments":{"command":"sleep","args":["36000"],"timeout_ms":36000000}}
```

That is a ten-hour hang the gate does not see, because the gate approves
*commands* and this is an argument. It is not a level-3 problem — it is there on
the host today — and it has to be closed first, because a seam whose deadline is
derived from that number would inherit it.

## The proposal

### 1. The tool's clock gets a ceiling

`MAX_TIMEOUT_MS = 600_000` in `tools/command.rs`, applied where `timeout_ms` is
read. A request above it is clamped rather than refused: the command still runs,
and the outcome says the ceiling did the killing rather than the number the model
asked for. Ten minutes is chosen against the thing this project actually runs —
`cargo test --workspace` on the slowest box in `machines.md` — and it is a
constant with a reason rather than a knob, because a person who needs longer has
`[worker] timeout-ms` and a plan that says so.

### 2. The seam's deadline is derived from the request

The host already knows what it asked for, so it does not need a second config
knob to guess:

```
deadline(call) = the call's own clock + patience
```

- the call's own clock is `timeout_ms` (clamped by the ceiling above) for
  `run_command`, and **zero for every other tool**, because no other tool has
  one;
- `patience` is `[worker] timeout-ms`, default 30 000 — the same number
  `run_command` defaults to, which is not a coincidence: it is "how long a thing
  with no clock may take before it is stuck", answered once.

So a `read_file` gets 30 s, a `run_command` that asked for five minutes gets five
and a half, and no honest call is ever killed by the seam before the tool's own
clock has had its chance. **The seam must never fire first.** A seam that
pre-empts the tool turns every slow build into a killed worker, and the person
reading that verdict would learn the wrong thing about their command.

### 3. Firing kills the worker, and the next call starts a new one

A deadline that only gives up on the read is worse than no deadline: the answer
may still arrive, and the pipe would then pair *the previous call's outcome with
the next call's request* — silently, since both are well-formed JSON. So when the
clock fires the child is killed and the pipe is marked dead. The same mark is set
on every other pipe error, which fixes a smaller bug in passing: today a worker
that exits takes the rest of the session's tools with it.

The restart is **lazy and transparent** — the next call spawns a new worker and
redoes the handshake before sending. That is only sound because the worker holds
no state between calls: every request carries its own `WireSandbox`, which is why
`Executor` has one method. A restarted worker whose handshake fails, or whose
protocol number differs (a rebuilt image mid-session), is a failed call that says
so, not a panic.

The restart is bounded by the same patience, because it happens **on the call's
path**: a runtime that hangs while creating a container would otherwise
reintroduce the hang one layer up, which is the shape a clock in the wrong place
always has. The session's *first* start stays unbounded on purpose — there is a
person watching a terminal, and a first `docker run` that pulls an image is
legitimately slow in a way no later restart is.

Under a container runtime the restart is a new container, which is what `--rm`
and a spec kept on the `Worker` already make cheap. What it costs is honest and
worth writing down: **a stuck `run_command` leaves its child inside a container
that is about to be destroyed**, and `--init` is what reaps it.

## What it costs

- One number crosses from the tool into the host: the seam reads `timeout_ms` out
  of the call's arguments. The alternative — a flat seam deadline — is worse in
  the direction that matters, since it either pre-empts long commands or is so
  generous it never fires.
- The `Worker` now keeps its `WorkerSpec` and the command list, because a restart
  needs both. It was already the only thing that had them.
- A verdict can now say the worker was killed, which is a new sentence in the
  record for a case that previously produced no sentence at all.
- **The cached prefix moves.** `timeout_ms`'s one-line description now says the
  cap, so the tool definitions block is not byte-identical to the one every
  recording before today was made against. It is paid deliberately: a ceiling the
  model cannot see is one it asks past and is silently clamped under, which is the
  kind of gap this repository's whole reporting habit exists to close. Runs either
  side of it stay comparable on everything but the absolute prefix byte count.

## What was rejected

- **A heartbeat on the pipe.** A worker that answers pings while its tool is
  wedged is exactly the failure being covered, so the ping would report health
  during the outage it exists to detect.
- **Cancelling the call rather than the worker.** There is no cancel in the IPC,
  and adding one means the worker's tool loop has to be interruptible — which is
  the tool's own clock again, one level down.
- **Reusing the pipe after a timeout.** Discussed above: it is the one failure
  mode that would be silent, and this design's whole habit is to prefer a named
  error to a quiet mispairing.
- **A knob per tool.** `[worker] timeout-ms` is one number for "a tool with no
  clock", and a tool that grows a clock of its own grows a `timeout_ms` argument
  with it, which the seam already reads.

## Still open

- **Host mode has no seam and therefore no clock.** `Runtime::Host` runs tools
  in-process, where a wedged `read_file` still hangs the turn. The honest fix
  there is a deadline in the agent loop rather than at a seam that does not
  exist.
- **A killed worker is not counted.** Nothing yet reports "this session restarted
  its worker three times", which is the number that would tell a person their
  image is broken rather than their command.
- The ceiling is a constant. If a real run needs more than ten minutes for one
  command, that is a measurement worth having before the constant moves.
