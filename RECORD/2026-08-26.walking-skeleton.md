# Where to start: a walking skeleton, and the protocol written after it

**Status:** proposal, no code. Follows
[`2026-08-26.web-debug-client.md`](2026-08-26.web-debug-client.md), which settled
the transport and the UI but left the message enums open. This file is about the
first commits.

## The problem

Nothing exists. The work order in the design doc reads as layers — core types,
then context manager, then protocol and UI — and building it in that order means
the protocol enums get written from imagination, before a single real turn has
been observed. They will be wrong in exactly the places that matter: the field
that turns out to be missing once a tool result needs pruning, the event that
turns out to need a sequence number, the distinction between "the model stopped"
and "we stopped it".

That correction is cheap now and expensive after the VSCode bridge and the record
format both depend on v1.

## Proposal: thinnest end-to-end path first

Build the narrowest thing that carries a token from the model to a browser, then
read the protocol off what it actually emitted.

1. **Cargo workspace.** `crates/agent-core` (lib) and `crates/luu` (bin, with the
   `loude` alias as a second `[[bin]]`). Mechanical.
2. **`trait Backend`** with one implementation, streaming a completion.
3. **One turn, no tools, streaming to stdout.** This is the step that produces
   evidence: `token`, `turn_end`, `error` and a cancel path stop being guesses.
4. **The protocol enums**, written from what step 3 emitted, plus the transport
   trait. This is the point at which v1 gets frozen.
5. **`luu serve` + one jq79 page** rendering that stream, and `--record` writing
   the JSON-lines file the page can replay.

Done means: run `luu serve`, open the browser, type a prompt, watch tokens arrive,
then replay the same session from a file with the socket closed.

## The backend: Ollama over HTTP first

The design doc leans toward binding `llama-cpp-rs` directly, for control over the
KV cache across calls and to avoid an HTTP hop — right eventually, wrong as the
first step. Starting there means debugging FFI and cache lifetimes while trying to
get a first word to appear on a page, and the performance goal has nothing to
measure yet.

Ollama's HTTP API behind `trait Backend`, then. The trait is the whole point: the
swap is confined when the numbers eventually demand it, and by then the debug UI
exists to show what the swap bought.

**Cost:** an HTTP hop and no KV-cache control, both of which the performance goal
will reject later. Accepted, because "later" is after there is something to
measure.

## What is deliberately not in the skeleton

Tools, the sandbox, context management, sessions and SQLite, plan/run/auto modes.
None of them are needed to validate the protocol shape, and a skeleton that grows
features stops being a skeleton — it becomes the thing itself, built in the order
that was being avoided.

`context_snapshot` and `usage` are the exception worth stubbing: emitting them with
placeholder numbers keeps the debug half of the protocol present from the first
day, on the `--trace` channel, rather than being retrofitted once stdio consumers
already depend on v1.

## Blockers and parallel work

- **jq79 needs a teardown hook before step 5.** The page holds a WebSocket and has
  nowhere to close it. Recorded in the previous file; it is the one item that
  gates rather than parallelises.
- **Effect batching is not a blocker.** Buffer `token` and flush on
  `requestAnimationFrame`; migrating to `batch(fn)` later is deleting the buffer.

## Still open

- Whether the record format is the raw WS frame log or a container with a header
  (model, config, timestamps). The header is probably needed to compare two runs,
  which is the whole reason the format exists — but that is an argument to have
  once two runs need comparing.
- Cancellation semantics: whether a cancelled turn emits `turn_end` or its own
  event. Step 3 should answer this rather than the file.

## Revising the previous file

[`2026-08-26.web-debug-client.md`](2026-08-26.web-debug-client.md) left "freeze v1
of the message enums" as the next step, and the conversation that produced it
called that the thing unblocking both server and UI. That framing is wrong in its
order: the enums are the *output* of the first working loop, not its input.
Nothing about the transport decision changes — one schema, several transports,
trace behind `--trace`. Only when the schema gets written down.

## 2026-08-26, later: steps 1–3 built, and what the running loop answered

The workspace, `trait Backend` (Ollama + a mock), and `run_turn` streaming to
stdout are in. Nine tests, `cargo test --workspace` green. Three paths were run
by hand: a full turn, a cancelled one, and an unreachable backend.

What the loop answered, now that it exists rather than being imagined:

- **Cancellation reuses the end event; it does not get its own.** `Ended` carries
  a reason, and `Cancelled` is one of its variants. The open question in this file
  is closed: a separate event would have forced every consumer to handle two
  shapes of "the turn is over" for no gain.
- **`usage` is not available on a cancelled turn.** The counts arrive on the
  backend's final line, and cancelling means never reading it. So `usage` is
  `Option<Usage>`, and the CLI prints "usage unknown" rather than zeros — zeros
  would be a lie the debug UI's budget panel would then plot. This is the first
  thing the skeleton found that a hand-written enum would have got wrong.
- **A third ending exists**: the backend's stream can stop without a `done` line.
  Treated as `Stop` with unknown usage rather than an error, since text already
  arrived.
- **`EndReason` is not the backend's `StopReason`.** It needs a variant no backend
  can report (`Cancelled`), which settles that the wire protocol cannot simply
  re-export backend types — there is a conversion at the boundary, and it belongs
  in core.

### The bug worth keeping

`run_turn` selected on `cancel.changed()` in a `biased` select. When every cancel
sender is dropped — the ordinary case for a caller with nothing to cancel with —
`changed()` becomes permanently ready with an error, the biased arm won every
poll, and the backend stream was never read: the turn hung forever, in a loop
with no cancellation in sight.

It was found by the two tests that pass a receiver whose sender was dropped, and
it had already been papered over once without being understood: the CLI carried a
`std::mem::forget(stop)` to keep the sender alive, written while the cause was
still unknown. Both are fixed —
`dropping_the_cancel_sender_does_not_stall_the_turn` is the regression test, and
the `forget` is gone.

The lesson is the one the skeleton was for: this is a two-line bug that no amount
of designing the enums would have surfaced, and it sat directly under the
happy path.

### Deviations from the plan above

- **The mock backend was not in the plan.** It earns its place: the skeleton has
  to be runnable and observable without a model on the machine, and it is the only
  way to exercise slow generation deterministically — which is where a UI that
  re-renders per token falls over. It lives in the library, not in `tests/`.
- **`async-stream` was added** after a hand-rolled `Stream` adapter for Ollama's
  NDJSON came out unreadable. One small dependency against a chunk-boundary state
  machine nobody would want to revisit.
- **Two `[[bin]]` entries over one `main.rs`** — the design doc's suggestion for
  the `loude`/`luu` alias — makes Cargo warn about a file in multiple build
  targets. Replaced with a small `lib.rs` exposing `run()` and two three-line
  binaries.

### Still open, unchanged or new

- The record-format header question from above is untouched.
- `CompletionRequest` takes assembled `messages`. The stable-prefix commitment in
  `AGENTS.md` says the system block and tool definitions must be byte-identical
  across calls; nothing enforces that yet, and nothing will until there is a
  second turn in a conversation. It is the first thing to check when history
  arrives.

## 2026-08-26, later still: steps 4–5 built, and a jq79 bug the UI found

The protocol, the trace channel, the record format, `luu serve` and the jq79 page
are in. 17 tests green, and the whole path was exercised in a real browser:
prompt typed, tokens streamed, budget and prompt panels populated, no console
errors, no 404s.

### What the protocol ended up being

Written from the loop, so it is smaller than the sketch in the previous file.
`ClientMessage` is `prompt` and `cancel` — `approve_plan`, `edit_plan` and
`set_mode` were in the plan and are not here, because nothing produces them yet
and a v1 that ships imaginary variants is a v1 that has to keep them.

`ServerMessage` is `hello`, `turn_started`, `token`, `ended`, `failed`. Two of
those exist for reasons only a second client makes visible:

- **`hello`** carries the protocol version and the turn in flight, so a client
  attaching mid-turn learns what it missed instead of inferring it from the first
  token it happens to catch.
- **`turn_started`** carries the prompt. The `ClientMessage` that started the turn
  was seen by one socket; every other client, and the record file, never saw it.
  A server that does not echo the prompt produces a record you cannot read.

The trace channel is a separate enum on a separate socket (`/ws/trace`), as
`AGENTS.md` requires — `TraceMessage::Prompt` carries the exact string sent to the
model, `Budget` carries real backend counts and nothing invented. It is emitted
only when usage exists, so a cancelled turn plots nothing rather than plotting
zeros.

### The record header question, closed

The previous file left open whether the record is bare frames or has a header.
It has one: `format`, `protocol`, `backend`, `model`, `started_at`, then one
JSON line per message with milliseconds since the header. The argument that
settled it is the one the format exists for — a file whose model you have to
remember is not comparable against another run, which is the whole point.

### The jq79 bug

The UI mounted, the header and budget panels updated, and the transcript stayed
empty. Isolated to fifteen lines with no loude code in them:

```js
// store.js, at module scope
export const state = $reactive({ items: [{ id: 1, text: "inicial" }], plain: "inicial" })
```
```html
<script :setup>
  const { state } = await import("./store.js")
</script>
<div>{{ state.plain }}</div>
<li :each="item in state.items" :key="item.id">{{ item.text }}</li>
```

| written from outside the component | renders |
| --- | --- |
| `state.plain = x` | yes |
| `state.items[0].text = x` | **no** |
| `state.items[0] = { ...x }` | yes |

Assigning a property of an object inside a reactive array does not wake the
`:each` binding; replacing the item does. The store is bridged into the
component (module-scope `$reactive`, pulled in by `await import`), which is the
shape the docs describe as shared state, so this is not a misuse — the write
notifies at a path the item binding is not woken by.

Worked around in `store.js` by replacing messages instead of mutating them:
one object per frame, and `:key` keeps the DOM. The repro above is what should
go upstream.

**This moves the upstream list.** It is now three items, and this one is first:
it is a correctness bug, where the teardown hook is a missing feature and the
batching is a performance one. It also passes the promotion rule the previous
file set without needing the rule at all.

### Two smaller things the browser found

- **A `:setup` script takes `await import(...)`, not a static `import`
  statement** — the static form is for factory scripts, and produces "Cannot use
  import statement outside a module" at runtime rather than a parse-time
  complaint.
- **`@submit="$event.preventDefault(); submit()"` silently does nothing.** The
  attribute is an *expression*, and two statements separated by a semicolon is
  not one. `@submit.prevent="submit()"` is the form. It fails quietly, which is
  the part worth remembering.

### On the teardown hook, which did not block after all

The previous file called it a blocker for this step. It was avoided rather than
faced: the WebSocket lives at module scope in `store.js`, owned by the page and
not by any component, so nothing needs releasing on unmount. That works for one
page and stops working the moment a component owns a per-session socket. The
item stays on the list, undemoted.

### Still open

- `run_turn` is called with `messages` assembled inline in `serve.rs` and again
  in `lib.rs`. Two call sites building the stable prefix by hand is exactly what
  the byte-identical-prefix commitment in `AGENTS.md` warns about. It wants one
  place before there is a third.
- One turn at a time, one session, no history. `start_turn` returns silently if a
  turn is already running, which a client cannot distinguish from a lost message.
- No replay yet: the record file is written and parses, but the UI cannot load
  one. That is the remaining half of "compare runs, don't recall them".

## 2026-08-26, later still: CI, and what a static deploy forced

Two workflows. `build.yml` runs fmt, clippy (with `RUSTFLAGS=-D warnings`), the
tests, both binaries (linux-gnu and darwin-arm64) and the site, on every push and
pull request, and is `workflow_call`-able. `release.yml` is manual, takes
`patch`/`minor`/`major`, raises the workspace version, tags it, and publishes the
release and Pages.

### The reusable-workflow trap, avoided on purpose

A called workflow checks out **the caller's** ref, not whatever the caller did
during the run. `release.yml` commits a version bump and then calls `build.yml` —
without an explicit `ref` input, the release artifacts would carry the *previous*
version while the tag says otherwise, and nothing would fail. `build.yml` takes a
`ref`, and the release passes the post-bump SHA.

`cargo metadata` refreshes the workspace members' versions in `Cargo.lock`
without compiling and without touching any other dependency — which is what the
bump needs, and less than `cargo update` would do.

### The fixtures are recordings, not fixtures

GitHub Pages has no agent behind it, so the UI needed something to show. The
answer was already built: the record format. CI runs the real binary against the
mock backend and records three sessions — completed, cancelled, unreachable
backend — and the page replays them.

This is better than hand-written fixture JSON in a way worth stating: a
hand-made fixture drifts from the format silently, and the day it does, it lies
about the thing it exists to demonstrate. These cannot drift — they are produced
by the same code that serves them, in CI, on every build. The three files also
happen to cover every ending the protocol has, so generating them is a smoke
test of the record format for free.

`store.js` gained the replay path: `?replay=<file>`, or — when no WebSocket ever
connects and `fixtures/index.json` is there — it stops reconnecting and offers
the recordings instead. That closes "no replay yet" from the previous section,
though only the loading half; comparing two runs side by side is still not built.

### Two things the browser caught again

- **`{{ state.budget.limit }}` inside a `:if` that had already gone false.**
  Guarding the `:if` was not enough; the interpolation is its own expression and
  its own effect. jq79 reports it and renders nothing, which is a good failure
  mode and still a real bug. Both reads are `?.` now.
- **Status flickered to `ready` mid-replay**, because ending a turn hardcoded it.
  What "not running" means depends on whether an agent is behind the page, so
  that is a function now.

### Two Rust things worth not rediscovering

- **`cargo fmt --check` and clippy were never run before this**, and both failed
  on the first try. Anything added to CI must be run locally first, or the first
  CI run is red for reasons that have nothing to do with the change.
- **Let chains do not work inside `async_stream::try_stream!`.** The body is
  macro-expanded and loses its edition, so `if let ... && ...` is rejected as
  "only allowed in Rust 2024 or later" while the crate *is* on 2024. Both
  backends now avoid them, with a comment saying why.

### Still open

- The release has never been run, not even as a dry run. `release.yml` has a
  `dry-run` input for exactly that, and it should be used before the first real
  one — the version-bump shell is the part most likely to be wrong, and it is the
  part that pushes a tag.
- Pages must be enabled for the repository (Settings → Pages → source: GitHub
  Actions) before `deploy-pages` can succeed. Nothing in the workflow can do that.
- `build.yml` builds a darwin-arm64 binary that nothing tests. It compiles; that
  is all that is claimed.

## 2026-08-26, later still: the read API, and its static twin

The previous section built the Pages deploy around replaying recordings, and
called that the fixtures. It was half the ask. The design's read side —
`GET /api/sessions`, `/turns`, `/turns/:n/prompt`, `/context` — had never been
implemented at all, live or static, and a static *API* is what makes a Pages
deploy exercise the same code paths a real one does.

### One structure, fed two ways

`agent_core::api::SessionView` is the read model. The live server folds events
into it as it publishes them; `luu export` folds a recording into it. Same
structure, same fold.

That is the whole point, and it is worth stating plainly: a static mirror
generated by separate code drifts from the server it mirrors, and the day it
drifts it lies about the one thing it exists to stand in for. A test asserts the
two folds produce byte-identical JSON —
`folding_live_events_gives_the_same_view_as_folding_the_record`.

### `.json` everywhere, because a static host has no choice

GitHub Pages cannot serve `…/turns` as JSON, so the exported tree is all
`.json` files. The live server answers **both** spellings, so a client uses one
set of URLs against either. Verified: all nine paths 200 live, and the shapes of
all six endpoints match the exported files key for key.

The suffix is not a route of its own where it lands on a parameter — axum allows
only one parameter per path segment, and `"/api/sessions/{id}.json"` panics the
router at startup with exactly that message. `{id}` captures `completed.json`
whole and the handler strips it; only the literal segments get a second route.

### Two bugs this turned up

- **A `publish` call lost its `await`** when `publish` became async to fold into
  the view. The compiler said so — "unused implementer of `Future`" — and the
  symptom was `prompt_sent: null` on every live turn, i.e. the trace channel's
  most important message silently never sent. Worth noting that the *warning*
  was the only thing that caught it: nothing failed, and the panel just looked
  empty.
- **The fixtures were exported by a glob**, so the page led with
  `backend-failure` — alphabetically first, and the worst possible first
  impression of a deploy. They are named in order now, with a comment saying
  why, because the next person to add one will otherwise reach for the glob.

### Still open

- `GET /api/sessions` lists exactly one session live, because sessions are not
  persisted. The shape is already plural, so SQLite arriving does not change the
  API — only how many entries it returns.
- `?from=&limit=` from the design is not implemented on `/turns`. A static host
  cannot answer query parameters at all, so when it lands it needs a shape that
  degrades — pre-exported pages, most likely, not a truncated array.
- The UI reads the API for the session list only. Everything else still comes
  from the socket or the recording, so most of the exported tree is served and
  unread. That is fine for now and should not be forgotten: an endpoint nobody
  reads is an endpoint nobody notices breaking.
