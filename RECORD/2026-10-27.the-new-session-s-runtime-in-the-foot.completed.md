# The new session's runtime, in the foot

> *Al iniciar nueva sesión, no se inicia el Runtime correctamente, debería
> aparecer el seleccionado en el footer del Editor.*

## What it was

Two things, one in each half of the foot's job.

**The name.** Every session the page starts is made from a runtime and three
lists ([`RECORD/2026-10-22.policies-not-postures.WIP.md`](2026-10-22.policies-not-postures.WIP.md)),
and such a session is named by its lists (`tools+registries+…`), not by a
posture. The foot found where the session runs with `livePlace`, which looks
the session's name up among the postures and environments `/api/postures`
offers — a session made from lists is never one of them — and drew the
option it found. It found none, and drew `…` with this machine's mark,
whatever runtime had been chosen. The Runtime dialog had nothing checked, for
the same reason.

**The shell.** The terminal asked `/api/terminal` again when the session
changed, and kept its shell. A move from the dialog ended it and opened it
again; a new session did not. So a shell opened on this machine stayed there
under a session that ran in a container, and one opened in the last
session's container ended with it and said *ended*, waiting for a click.

## What it is

- **`hereOption(postures, live)`** (`lib/places.js`): the option the live
  session is, or, when it is none of them, one made from what `/api/terminal`
  says it runs on — `composed`'s runtime and image, or the worker's label
  (`docker (luu-worker:dev)`) where there is no `composed`. The foot draws it
  (`host`, `podman · luu-worker:dev`, with the runtime's mark), and the dialog
  draws it first, checked, *now*: it is where the session is, not a place to
  move to, and the places to move to follow it.
- **`followSession()`** (`lib/terminal.js`), in place of `loadTerminal` on the
  page's session-or-runtime line: it asks `/api/terminal`, and when the open
  shell was opened somewhere else — another container (each session has its
  own), or this machine against a container — it ends it and opens it again in
  the panel it was drawn in. On this machine, a new session keeps the shell: it
  is the same account in the same folder, and ending it would only lose what
  was typed. A move from the dialog opens the new shell itself, and the
  comparison then finds it already there.

## Tested

- `policies.spec.js`: a session made from the *tools* and *registries* lists
  on this machine is `host` in the foot with this machine's mark, and the
  Runtime dialog's checked place is it, *now*. With the foot as it was, the
  same assertion read `…`. And one in a container is named by its runtime and
  image, with the runtime's mark, from what `/api/terminal` would say of it.
- The shell's move to a new session's container is not run here: this
  machine has no container runtime that answers, and `terminal.spec.js`, the
  test that has one, is skipped without it.
