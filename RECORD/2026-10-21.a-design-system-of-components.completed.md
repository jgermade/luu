# A design system of components, beside the ones in use

Jesús: *"crea un sistema de diseño de componentes, no los reemplazaremos por
ahora — se servirá una demo de los componentes en theme/default/"*.

## The problem

What the page calls a design system today is three things that grew apart:

- **Tokens in `app.css`**, written for the page: `--bg`, `--panel`, `--accent`,
  the buckets' colours, Monokai. Colours only. Sizes, radii, type, spacing and
  motion are literals repeated in every component — `6px` radius, `13px` text,
  `cubic-bezier(.32, .72, 0, 1)`, `.35rem .65rem` padding.
- **`web/components/`**, thirteen components that import nothing
  ([`components-of-our-own`](2026-09-28.components-of-our-own.completed.md),
  [`form-components-and-layout`](2026-10-08.form-components-and-layout.completed.md)).
  Each reads the page's tokens with a fallback, so each also carries its own
  copy of the light palette.
- **`.ds-*` classes in `app.css`**
  ([`settings-design-system-and-folio`](2026-10-08.settings-design-system-and-folio.completed.md)):
  heroes, cards, badges and flows for Settings, global rules rather than
  components.

There is no page where all of it can be seen at once, so nobody can tell
whether a button in one place matches a button in another without opening
both screens. And there is no single place a value lives: changing the radius
is a search across a dozen files.

## The proposal

**A theme is a folder: its tokens, its components, and a page that shows
them.** `web/theme/default/` is the first one.

```
web/theme/default/
  index.html          the demo's document: tokens.css, the import map, jq79
  demo.html           the demo itself, one section per component
  tokens.css          every value the components draw with, light and dark
  components/*.html   the components
```

`luu serve` already embeds `web/`, so the demo is at `/theme/default/` with
one change to the server: a path that ends in `/` serves that folder's
`index.html`, and the same path without the slash redirects to it, so the
page's relative URLs resolve. Under a host's prefix (`/h/<name>/theme/default/`)
it is the same page.

**Nothing in the app changes.** The page does not load `tokens.css`, no view
imports a component from `theme/`, and `web/components/` stays what every
screen uses. Moving a screen over is a later decision, one screen at a time,
each with its own record.

### Tokens

One file, three layers of decision, all custom properties under `--luu-`:

- **Colour**, by role and not by hue: `bg`, `surface`, `sunken`, `border`,
  `border-strong`, `fg`, `fg-muted`, `fg-subtle`, `accent`, `on-accent`, and
  four tones — `accent`, `ok`, `warn`, `bad` — each with a `-soft` ground for
  badges and alerts. The values are the page's current ones, so a screen that
  moves over later does not change colour by moving.
- **Shape and type**: a type scale (`--luu-text-xs` … `--luu-text-2xl`),
  weights, a spacing scale (`--luu-space-1` … `--luu-space-8`), radii, the
  three control heights (`sm`, `md`, `lg`), shadows, and z-layers.
- **Motion**: two curves (`--luu-ease` for things that move, the damped one
  `Segmented` already uses; `--luu-ease-out` for things that arrive) and three
  durations. **`prefers-reduced-motion: reduce` sets the durations to `0ms` in
  `tokens.css`**, once, instead of a media query in every component.

`:root` is light; `:root[data-theme="dark"]` re-points the colours, the same
attribute `prefs.js` already sets on the page. Light first here, unlike
`app.css`: the page has been light-only since `prefs.js` stopped offering dark,
and the demo should open on what the app looks like.

### Components

The rules of `web/components/` hold, with one exception argued below: a
component imports nothing, takes everything as props or slots, gives
everything back through `$updateModel` and `$emit`, and scopes its styles.
And a few conventions so that every component reads like the others:

- `size` is `sm`, `md` or `lg`. `tone` is `neutral`, `accent`, `ok`, `warn` or
  `bad`. `disabled` is a boolean.
- A value goes up through `:model` and always as `change` (or `input` for
  text, on every keystroke), with the value in `$event.detail`.
- **A component that wraps a native control re-emits what a parent needs**:
  jq79 binds `@click` on a component tag to `$emit` and nothing else, so a
  click inside it never reaches the tag unless the component passes it on.

The first set, nineteen:

| Kind | Components |
| --- | --- |
| Actions | `Button` (primary, secondary, ghost, danger; square for an icon; loading) |
| Form | `TextInput`, `Textarea`, `Select`, `Checkbox`, `RadioGroup`, `Switch`, `Segmented`, `Field` |
| Display | `Badge`, `Card`, `Alert`, `Progress`, `Spinner`, `Kbd` |
| Navigation | `Tabs`, `Menu` |
| Overlay | `Modal`, `Tooltip` |

`Menu` and `Tooltip` use the platform's `popover`, so they sit in the top
layer over anything that clips, with no portal and no z-index to win.

### The demo

One page, a section per component, each showing its variants, sizes, tones
and states (disabled, invalid, loading), and the state a control is in,
printed next to it, so a binding that goes wrong is visible. It opens on the
tokens themselves — swatches, the type scale, spacing, radii, shadows — read
back from the computed style, so the page shows what the CSS says and not a
copy of it. A switch at the top moves between light and dark.

## The exception: no fallbacks

`web/components/` reads every token with a fallback
(`var(--accent, #2f5bbd)`) so a component draws on a page with none of
luu's CSS. That rule is not kept here, and this is why: a theme's components
are drawn by **their theme's** `tokens.css`, which is part of the same folder
and loaded by any page that uses them. A fallback in every component is a
second copy of the palette per file — nineteen copies — and the copies are the
thing that drifts: the day a second theme exists, it would change one file and
leave nineteen fallbacks drawing the first one wherever a token is missing.
A missing token should look missing.

The rule's purpose — a component that does not depend on the page — still
holds: it depends on the theme, which the page chooses to load.

## What it costs

- A second set of components to keep while the first is still in use. Until
  screens move, a fix to `web/components/select-input.html` may need its twin
  in `theme/default/components/select.html`.
- One small change in `serve.rs`, and a test for it.
- Bytes in the binary: the folder is embedded like the rest of `web/`, on the
  order of 100 KB.

## Rejected

- **Rewriting `web/components/` in place.** Asked against: *"no los
  reemplazaremos por ahora"*. And a design system is easier to judge on a page
  of its own than inside screens that also have to work.
- **Tokens added to `app.css`.** The page would start drawing with them
  before any component does, and the demo would depend on the page's
  stylesheet — the opposite of what a theme folder is for.
- **A component library from npm**, or a storybook. The UI stack decision in
  `luu-design.md` (no node in `cargo build`) holds, and a demo that is a jq79
  page is one more page of the same kind as the app.
- **Unprefixed token names** (`--accent`). Both sets will be on one page the
  day a screen moves over, and `--accent` already means something there.

## Still open

- Which screen moves first, and whether `web/components/` is retired or kept
  as a compatibility layer while the rest move.
- Global rules in `app.css` (`button`, `input`, `select`) reach into scoped
  styles on the app's page — `input { flex: 1 }` among them. The demo page
  loads no `app.css`, so it does not show this; the first screen that moves
  will.
- A second theme, and how a person chooses one: a setting, a `[ui] theme` in
  `config.toml`, or a folder of their own beside `default/`.
- Per-component tokens (`--luu-button-radius`) for overriding one component
  without the rest. Not in the first set: the semantic tokens are enough until
  something asks for more.

## Appended 2026-10-21: built, and what jq79 said back

Built as proposed: `tokens.css`, the nineteen components, the demo, and the
folder route in `serve.rs`. Four things changed on the way, all of them from
running the demo, and each says something about writing a jq79 component that
`web/components/` had not run into or had not noticed.

**A bare boolean attribute arrived as `""`, which is off.** `<Button disabled>`
was enabled, `<Badge solid>` was soft, `<Alert dismissible>` had no close
button. jq79 hands a plain attribute to a component as its string, and an
attribute with no value is the empty string. Every boolean prop here goes
through `flag()` — `""`, `true` and `"true"` are on — so a theme component
reads like HTML. `web/components/` has the same hole and nobody saw it:
`sessions-modal.html` writes `<TextInput … autofocus clearable>`, and neither
reaches the input.

**`:value` and `:checked` never reach a component.** `<Progress :value="35">`
drew as indeterminate: jq79 counts `:value`, `:checked` and `:selected` among
its control attributes, which bind the element's own state, and drops them
from a component tag without a word. So `Progress` takes `amount`, the inputs
take only `:model` (or `model="…"` for a fixed value), and `Checkbox` and
`Switch` have no `checked` — `model="true"` is a box that is on.

**Named slots are `<slot.name />`**, not the platform's `<slot name>`, which
jq79 reads as the default slot: Card's head and foot first drew its body three
times. And **a scoped style does not reach slot content** — the content
carries the stamp of whoever wrote it — so the rules that sized a button's
icon or set an alert's `code` were dead and are gone. The page that writes the
icon sizes it.

**A `var()` shorthand that a later longhand overrides comes back empty.** jq79
scopes a style by re-serialising it through the CSSOM, and Chromium writes
`border: var(…) solid var(…)` followed by `border-bottom-width: 2px` as a set
of empty longhands: `Kbd` had no border. It is written in longhands now, and a
scan of the other components found no second case. `:each` on a `<template>`
also draws nothing (jq79 warns about this one); Menu and the demo use an element
with `display: contents` instead.

Two defects in the components themselves, found by the spec rather than by
eye: a loading `Button` hid its label with `visibility: hidden`, which takes
the button's name out of the accessibility tree (it is `opacity: 0` now), and
the invisible native radio and checkbox sat under the drawn ones, so a click
landed on the drawing (they are on top now).

### What was checked

- `tests/smoke/theme.spec.js`, four tests against a live `luu serve`, under
  `gate.config.js`: every section renders with no console output, the swatches
  read `#f4f5f8` and `#111111` either side of the theme switch, which survives
  a reload; bare and bound attributes; typing, clearing, Enter, selects, the
  indeterminate box resolving both ways, radios, switches, Segmented's arrows,
  a field's error and its label focusing the control; Tabs skipping a disabled
  tab; Menu opening focused, choosing by keyboard and closing on ESC; a tooltip
  below its anchor on focus; a modal that ESC asks and the owner closes, and
  one that ESC cannot. **4 of 4 pass.**
- `a_folder_is_its_index` in `serve_ws.rs`: `/theme/default/` is the page,
  `/theme/default` is a 308 to `default/`, and a folder with no index is a 404.
  `cargo test --workspace`, `cargo clippy --workspace --all-targets` under
  `-D warnings` and `cargo fmt --all --check` pass.
- Looked at, in screenshots of every section in both themes, at 1280 px and at
  390 px (no horizontal scroll), with the menu and a modal open.

Not checked: Firefox and Safari, where `popover` and `@starting-style` are
newer than in Chromium; reduced motion, which is not emulated.

### Still open, added

- The jq79 points above, which Jesús offered to fix upstream: a bare attribute
  as `true` for a declared boolean prop; `:value`/`:checked` on a component
  passed as props, or at least warned about; `<slot name>` warned about; a way
  for a component to style its slot content; scoped CSS that keeps a
  declaration's text instead of re-serialising it. Once they land, `flag()`,
  `amount` and the longhands can go.
- `web/components/`'s booleans, broken the same way today.

## Appended 2026-10-21: four more, a pressed state, and names that collide

Jesús, once the theme was on the page: *"añade al sistema de diseño: input
container, input|select + label + description; typeahead, input[text]+select;
section#id anchors"*, and *"a algunos elementos del sistema de diseño le falta
un estilo para css `:active`"*.

**`InputContainer`** is one box holding a control and what is said about it:
the name inside the border at the top, an `<input>` (any `type`) or — with
`type="select"` — a `<select>` of `options` under it, borderless, and the
description under the box, or the error in its place. Where `Field` puts a name
above *any* control, this *is* the control: the whole box is the label element,
so a click anywhere in it focuses the field, and the description is the
field's `aria-describedby`.

**`Typeahead`** is the ARIA combobox: a text field whose list of options opens
under it and narrows as it is typed into, the matching part of each option
marked. The arrows move the mark (past a disabled option), Enter takes it, ESC
closes the list without closing a modal around it, and a click on an option
takes it — the list keeps the focus in the field on pointer-down, or the field's
blur would close it before the click landed. What is typed is a value too,
unless `strict`, which puts the last real option back on leaving. The list is a
`popover`, so a column or a modal does not clip it.

**`Section` and `AnchorNav`.** A `Section` is `<section id>` with its title, a
`#` link to itself shown under the pointer and the keyboard, a lead and its
content. An `AnchorNav` lists sections by id and marks the one being read: the
last whose top has passed `offset`, and the last of all at the very bottom.
**It follows whatever its sections scroll in** — the window, or the first box
around them with an `overflow` — and nothing else, so two on one page do not
answer each other's scrolling; and a click marks its section through the jump
it causes, until something scrolls away from where it landed. The demo is
rebuilt on the two: its index and its twenty-three sections, and a box that
scrolls on its own inside one of them. A page with a sticky head sets
`--luu-anchor-offset` to its height.

Two of these were wrong first, and the demo showed both. `AnchorNav` kept its
marked link in view with `scrollIntoView`, which scrolls *every* box around the
link: the box's nav, marking its first item on load, took the whole page down to
where the box was. It scrolls its own list now and nothing else (so does
`Typeahead`'s list). And a click ignored scrolling for 600 ms, which also
swallowed the next real scroll; it is a position now, not a time.

**Pressed.** `--luu-active`, `--luu-accent-active` and `--luu-bad-active` are a
step past each hover, so a press reads as one even under a finger, where there
was no hover before it. Every component that is pressed has one: `Button` per
variant, `Segmented`, `Tabs`, `Menu`'s trigger and items, an interactive `Card`
(back down onto the page), `Checkbox` and `RadioGroup` (the box gives), `Switch`
(the thumb gives, wherever it is), `Select`, and every small close and clear
button. Checked by pressing each with the mouse held down and reading the
computed style: `Button`'s filled variants did not change at first, because
their `:active` came before their `:hover` in the file at the same weight.

**Names that collide.** A component's own classes share the page with
`app.css`'s global ones, and three did: `Select` marked an empty one `.empty`
(the page's grey text), `Field` its message `.error` (the page's red box), and
the tones in `Alert`, `Badge` and `Progress` included `.warn` (the page's amber
text). They are `.unset`, `.problem` and `tone-*` now. The rule for the
theme: no class a component uses on its own elements may be one of
`app.css`'s.

Checked: `theme.spec.js`, six tests, the new one driving the container, the
typeahead by keyboard and by pointer, strict, and the box's index against the
page's.

## Appended 2026-10-21: a modal with tabs for a head, and a head that follows the size

Jesús: *"me gustaría probar una idea, añade un componente, una modal con
pestañas en el header"*; then *"me gustan las modales con header oscuro y
también las modales con header integrado con el body; por norma general, las
modales grandes con el header oscuro y las pequeñas con el header integrado"*;
and, looking at the first dark one, *"el borde del header oscuro, debería ser del
mismo color"*.

**`TabModal`** is a `<dialog>` whose head is its tabs: an optional title, the
strip with the line that slides under the chosen tab, and the close button. As
with `Tabs`, only the strip is the component's — the owner shows the panel the
model names — and the arrows, Home and End move the choice past a disabled tab.
The focus starts on the chosen tab, a tab chosen starts at the top of its panel,
and `height` fixes the body's so the dialog does not move as the tabs change
(the demo's test measures it). It carries its own copies of `Modal`'s dialog and
`Tabs`' strip: a component imports nothing.

**The rule for heads**, in `Modal`, `TabModal` and the page's own `Modal`:
`head="auto"` measures the dialog as it is drawn, and from 40rem (640 px) it has
a dark head — a bar like the columns' — and below it a head that is part of its
body. `dark` and `integrated` say it outright. Measured rather than read from
`width`, because a modal asked for at 40rem on a phone is a small one there; the
page's `Modal` also guesses from `width` before it opens, so its head does not
change colour on the first frame, and a folio (Settings) is always large. **The
dark head is a `data-tone="dark"` island**, the same mechanism as the page's
bars, so it is drawn with the theme's dark values and no second copy of them.
On the page this makes the session starter, at 34rem, the first modal with an
integrated head; Settings and the context modal keep theirs.

**Edges.** The dialog drew one light border round everything, which framed a
dark head in a light line. Now the dialog draws none and each part draws its
own: a dark head's edge is its own colour, the body's and the foot's the light
line, and the first and last parts round the corners. The page's `Modal` is
left as it was: its border is the dark `--luu-divider` the page uses where a
modal ends.

**And the session starter is three `InputContainer`s** (*"usa InputContainer
en la modal de new Session"*): Provider, Model — with the provider's models as a
`<datalist>` the field still lets a person type past — and Runs. What used to be
a `dim` line beside each control is the box's description: the file's default,
where the model was suggested from, the policy a session's jobs are approved
against. "Could not list this provider's models" is a `warning`, a new
`InputContainer` prop: said where the description is, in the warning tone, with
the box's border in it too. `selectClass` keeps `select.place` where the gate
tests look for it.

**The demo's theme picker** is auto, light and dark as icons (*"mejor con
iconos"*): `Segmented` takes an `icon` per option, an SVG path on a 24×24 grid,
and `icons-only` draws it alone with the label as the button's name and title.
Auto is `prefers-color-scheme`, followed as it changes, and the page's
pre-paint script reads it too, so a dark system does not open white.

Checked: `theme.spec.js`, seven tests — the new one opens the small and the
large modal and reads each head's tone, and drives the tab modal by pointer and
keys; the first follows the system's scheme in and out of dark. The gate and
history specs pass with the starter rebuilt, but for *started on a posture*, as
before.

## Appended 2026-10-21: sub-modals, a bar above a tab's body, and feet of one height

Jesús: *"añadamos un componente de sub-modales con y sin pestañas"*, and, of the
sessions dialog below, *"el input de búsqueda de sesiones, más grande y más pegado
a las pestañas, y más separado del listado"* and *"que el footer de la modal de
nueva sesión y el footer de la modal del historial, tengan la misma altura"*.

**`SubModal`** is the page's child sheet as a theme component: written inside a
`Modal` or `TabModal`, it comes down out of the parent's head over the parent's
body only, with a veil there, and the parent's head stays lit — its close button
closes both. It is opened with `show()` and not `showModal()`, because a second
modal would make everything under it inert, the parent's head included; what the
top layer would do is done by hand: the rest of the parent made `inert` (each
sibling on the way up, but the parent's header), ESC caught on the window before
the parent's `cancel` sees it, and the focus put on the sheet's first field.
With `tabs` its head is their strip. Two things the demo found: the first-field
lookup, `.body input`, matched the sheet's *own close button*, because a selector
is matched against the whole document and the parent's `.body` is an ancestor of
the sheet — it is `:scope > .body …` now; and a parent closed under an open sheet
left the sheet marked open and the parent inert, so the sheet listens for its
parent's `close` and goes with it.

**`TabModal` has a `bar`**: a slot between the head and the body that does not
scroll with it — a search over what the body lists — and `height` now fixes the
bar and the body together, so a tab with a bar measures what a tab without one
does. And **a foot is as tall as a row of buttons whatever is in it**, in `Modal`
and `TabModal`: its content box has the control's height as its minimum, so a
foot of text and a foot of buttons are the same foot (measured on the page: 56 px
on both of the sessions dialog's tabs, and the dialog 521 px on both). The first
attempt counted the borders into a border-box minimum and missed the bottom one,
which the last part of a dialog draws.

Checked: `theme.spec.js`, nine tests; the new one opens a parent, a sheet
without tabs (focus in its field, the parent's body inert and its head not, the
sheet under the head), one with tabs (click, arrows, ESC closing it alone), and
the parent's close with a sheet open (both gone, nothing left inert on
reopening).
