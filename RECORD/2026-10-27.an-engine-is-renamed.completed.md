# An engine is renamed

Asked from the engine form, over `Engine ollama-2` — the Ollama app's own
binary, used from its card:

> *¿Por qué no puedo cambiar el nombre?*
>
> *Al ser del sistema, no se puede borrar, quiero poder renombrarlo.*

## The problem

**The name is the one field the form will not touch once written.** It is
`:disabled` while editing, and for a reason: the name is the key of
`[engine.<name>]`, and everything else reaches the engine by it.

- **Its providers.** `engine = "ollama-2"` in each profile that starts it, and
  the loader refuses a file where one names a table that is not there
  (`NoSuchEngine`). So the form cannot do it in its two writes — `PUT
  /api/engines` without the old key is refused while a provider still names
  it, and `PUT /api/providers` first is refused while the new key is not there.
- **The process luu started**, its output, its readiness, and the port it was
  placed on: `Supervisor`'s slots and `engines::PLACED`, each by name.
- **The live session.** Its destination resolved `(name, table)` when it was
  created and is replaced only when another session is, so every turn asks
  `ensure` for the engine by the name it had then.

Before *use* and *don't use*, the way out of a name was to remove the engine
and add it again. A binary the machine had cannot be removed — it is used or
not — so `ollama-2`, the name *use* gave it because `ollama` was taken, is its
name for good.

## The proposal

**`POST /api/engines/{name}/rename` with `{ "to": "<new>" }`, one write.**
`[engine.<name>]` becomes `[engine.<new>]`, table untouched, and every profile
whose `engine` named it names the new one — in the same `write_config`, so the
file is never one the loader refuses. Refused when the new name is not a name
(the rule `PUT /api/engines` already has), when a table has it, and when there
is no `[engine.<name>]`. Loopback and `Host`-checked, like every engine write.

**Providers keep their names.** `[provider.ollama-2]` stays `ollama-2`: a
profile is renamed in Models, where its default and its key go with it. An
engine rename that renamed a profile too would move the default and the
pickers from a form that is about a process.

**What luu runs moves with the name, and nothing restarts.**
`Supervisor::rename` moves the slot (the child, its output, its exit), the
readiness and the per-engine `ensure` gate to the new name, and `PLACED` moves
the port an automatic engine was placed on. The pane then shows the same
process, still running, under the new name.

**The old name keeps answering for the session that holds it.** The supervisor
keeps `old → new` and reads every name it is handed through it, so the live
session's next turn asks `ensure("ollama-2")` and gets the engine now called
`ollama` — the same process, not a second one started under a name no card
shows. A name that is a table again (renamed back, or a new engine given it)
stops being an old name: `rename` and `PUT /api/engines` drop it.

**Not while it loads.** A rename takes the engine's `ensure` gate without
waiting; one that is starting, downloading or restarting is refused with
*`<name>` is starting: rename it once it has*, rather than moving a slot an
`ensure` is half-way through filling.

**The form's name field is open while editing**, saying under it that the
providers that start it follow. *Save* with another name renames first, then
writes the table under the new one, as it writes any edit.

## What it costs

- A route, and a map in the supervisor read on every call that takes a name.
  It only grows by renames, and only within one `serve`.
- An alias is a second name for a process. It is never shown: the pane lists
  tables, and `/api/engine` names the live session's engine by its current
  name.

## Rejected

- **Two writes from the page** — the table, then the providers. The first is
  refused by the loader, whichever goes first.
- **Stopping the engine on a rename**, as `PUT /api/engines` stops one it
  takes away. Simpler, and the live session's next turn would start it again
  under the old name: a process no card shows, holding the port and a model,
  until the session moves.
- **Renaming the live session's destination.** It is replaced only when a
  session is created (`RECORD/2026-09-07.the-first-run-has-no-provider.completed.md`),
  and the backend it holds carries the name inside it.
- **Renaming the provider of the same name with it.** See above: Models does
  that, with what a profile rename involves.

## Still open

- A rename of an engine another `luu serve` runs — two processes on one state
  directory — moves this one's process and not the other's. The same is true
  of every engine edit today.

## Built, the same day

As proposed, with these differences:

- **`ensure` checks the name again once it holds the gate.** It read the name
  through the map and then waited on that name's gate; a rename in between
  moved the gate and left it holding an old name, which would have started a
  second process in a slot nobody shows. It loops until the name it holds is
  still the current one.
- **Whatever the new name left behind goes.** A slot, a readiness or a
  placement under `to` — an engine removed under that name — is dropped before
  `from`'s move in, so the new name starts with only its own.
- **A refused write undoes the move**: the supervisor is renamed back and the
  alias the undo leaves (`to → from`) is forgotten, since the file never had
  `to`.
- **The form's description names the providers that follow**: *`ollama-2`
  will start it as `ollama`*. A second *Save*, after the rename wrote and the
  table's own write did not, renames from where the first left it.

Tested: `engines::tests` — a process started under one name is the same pid,
running, under the new one, with its readiness and its placed port; the old
name reaches it; renamed again, the oldest name follows; given to a table, it
is that table's; and a held `ensure` gate refuses the rename and moves
nothing. `settings.spec.js` — the Ollama-shaped case asked about: a binary the
machine had, used, switched off, renamed from its form; `[engine.mine]` with
`enabled = false` still in it, the old table gone, and its provider, under its
own name, saying `engine = "mine"`.
