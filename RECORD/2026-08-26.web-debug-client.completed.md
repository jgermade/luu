# A web client to see what the context manager is doing

**Status:** proposal, no code. Written from the design conversation that produced
the *Debug web client* section of [`loude-design.md`](../loude-design.md). Nothing
in the repo is scaffolded yet, so every decision here is still cheap to revisit —
which is the point of writing it down now.

## The problem

The differentiator is context management, and none of it is visible from a
terminal. A CLI can print the model's answer; it cannot show how the token budget
was split, which fragments were selected and which were dropped, how much of the
stable prefix survived into the next call, or what a rolling summary replaced.
Iterating on a context strategy without those numbers is guessing.

So: a local web UI with chat, session browsing, and — the actual reason to build
it — the panels that expose the context manager's decisions.

## The transport, which is the real decision

**One JSON message schema, several transports (stdio, WebSocket), over plain
HTTP.** Define the messages once as `serde` enums (`#[serde(tag = "type")]`) and
put the transport behind a trait.

The argument is not about the browser. The VSCode bridge already needs a JSON-lines
protocol over stdio; if the web client speaks something else, there are two
protocols to version and two sets of bugs. One schema means the extension and the
UI are debugged together, and the record/replay format falls out for free.

### Rejected: gRPC

Browsers cannot speak it natively — it needs grpc-web plus a proxy (Envoy) or
Connect. `tonic` also means a protobuf IDL maintained in parallel with the `serde`
types, codegen in `build.rs`, and binary frames that are unreadable in devtools.
For a tool whose entire purpose is making things inspectable, the last one is
disqualifying on its own. gRPC earns its setup cost across languages, services and
throughput; this is one local process and one browser.

### Rejected: REST only

No streaming of tokens or tool events, and polling makes a debug UI useless. Adding
SSE on top gets you most of a WebSocket with more moving parts. SSE stays, but as a
*mirror* of the WS stream (`GET /events`), so a session can be followed with
`curl -N` without a browser — that is worth having and is not the main channel.

## The shape

`luu serve --http 127.0.0.1:7878`, loopback by default, no auth; a bearer token
only if it is ever bound elsewhere. UI embedded with `rust-embed`.

- `WS /ws` — client sends `prompt`, `approve_plan`, `edit_plan`, `cancel`,
  `set_mode`; server streams `token`, `plan`, `tool_call`, `tool_result`,
  `context_snapshot`, `usage`, `error`, `turn_end`.
- Plain GETs for the read side, browsable and curl-able. The one that matters:
  `GET /api/sessions/:id/turns/:n/prompt` — the exact string sent to the model.
- `luu serve --record <file>` dumps the JSON-lines stream, and the UI can load one
  instead of a live socket. Sessions become replayable offline, which is what makes
  two context strategies comparable rather than merely remembered.

## What it costs

The protocol becomes a thing that must be versioned, and it acquires a debug half
(context snapshots, raw prompts) that stdio would otherwise never carry. Mitigation
recorded in `AGENTS.md`: trace events go behind `--trace` on their own channel from
the start. Untangling that later is the expensive version.

It also moves work earlier — the protocol and UI land before the sandbox. Accepted
deliberately: this is the instrument used to measure the step before it, so
building it after the context manager would mean tuning the differentiator blind.

## Still open

- The message enums are not frozen. Everything above assumes them.
- Whether `context_snapshot` streams per turn or is fetched on demand. Streaming is
  simpler for the UI and wasteful for long sessions.
- Auth if the server is ever bound off-loopback. Currently out of scope by
  assertion, which is fine until it isn't.

## 2026-08-26, later: the UI stack, and jq79 replaces Vite + React

The first answer here was **Vite + React + TypeScript**, with the protocol types
generated from the Rust enums by `ts-rs`. The reasoning was that the deciding
factor is where the message types live, and that generated types turn a renamed
variant into a compile error instead of a runtime `undefined`. That part still
holds.

What it got wrong was treating the build pipeline as a detail to be paid rather
than a constraint to design against. A bundled frontend forces one of two bad
options: `npm` inside `build.rs`, so `cargo build` requires node, or a committed
`dist/` with the noise that brings. The file recorded that as a trade-off and moved
on. It is not a trade-off if it can be deleted.

**[jq79](https://github.com/jgermade/jq79) deletes it.** No compiler step —
components are `.html` loaded at runtime — so `rust-embed` ships one dependency-free
runtime file plus a handful of `.html` components, and the build stays pure Cargo.
`jq79 dev` hot-reloads with no bundler and applies no transforms, so serving from
disk in debug and from `rust-embed` in release serves the same bytes. Proxy-based
fine-grained reactivity with no virtual DOM, and `:each` with `:key`, suit an
append-only transcript.

Two consequences, chosen rather than discovered:

- **The prompt diff is computed in Rust** (`similar`) and sent as resolved spans.
  Pulling in CodeMirror or Monaco would reintroduce the bundler this choice just
  removed — and the server holds both prompt strings anyway, so it was always the
  right place for the work.
- **The compile-time check of protocol types is lost**, which was the previous
  stack's headline argument. Recovered in part by splitting the UI: transport and
  store as a `// @ts-check`ed `.js` module validated against the `ts-rs`-generated
  `.d.ts`, templates untyped. `tsc --noEmit` becomes an optional check task, never
  a build step. This is a real reduction in safety, accepted for a debug tool with
  one consumer; it would be the wrong call for a shipped product surface.

### What loude needs from jq79, and the rule that keeps it honest

Two gaps, both confirmed by reading `src/reactive.ts` and `src/jq79.ts` rather than
assumed, and neither expressible from userland:

1. **A teardown hook** (`$onDestroy`, or a cleanup returned from `$effect`).
   Effects, stores and injected styles are disposed with the component, but a
   resource the component itself owns — a WebSocket, a `requestAnimationFrame`
   loop, a mounted imperative widget — has nowhere to be released. The first
   component written here needs it.
2. **Effect batching** (`batch(fn)`, microtask-coalesced). There is no scheduler;
   the only `queueMicrotask` in the source is for expression-error reporting.
   Writes propagate synchronously, so a token stream costs one DOM write per token.
   Workaround until it exists: buffer `token` messages and flush on
   `requestAnimationFrame` — worth doing under any framework.

Only (1) blocks: it is needed before the first useful component. (2) is genuinely
parallel, because the rAF buffer works meanwhile and migrating later is deleting
it.

**Promotion rule.** Co-evolving a library with its first serious consumer bends the
library toward that consumer, and in one whose value is "single file, zero
dependencies" that is paid where it hurts most. So: a gap moves upstream only when
it cannot be expressed in userland, or when the same workaround has appeared twice.
Both items above pass the first test. List virtualization fails both — it is
ordinary component code (a computed window over `:each` plus two spacers, with
`?from=&limit=` already paginating server-side) and stays here until something else
asks for it.

### Noted about this decision

jq79 is the author's own library, so "it fits" was the conclusion the conversation
was primed to reach. The check applied was to look for where it does *not* fit; the
two candidates found — diff rendering and virtualization — both turned out to have
better answers without a library than with one. That is a real result and also
exactly what motivated reasoning looks like from the inside. If some later
requirement forces a bundler back in, this is the paragraph to re-read first.
