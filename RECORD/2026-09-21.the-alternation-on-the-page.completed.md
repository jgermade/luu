# The alternation on the page

Row 33 of [`ROADMAP/2026-09-21`](../ROADMAP/2026-09-21/), the last of the
neighbourhood rows 31 and 32 came from, and the only one the roadmap marks
*needs a design argument* rather than an afternoon. It was written in
[`every-turn-belongs-to-a-job`](2026-09-20.every-turn-belongs-to-a-job.completed.md)
§Still open as one sentence:

> **What the debug UI does with an alternation.** The gate panel approves a
> proposal; under this it closes a draft and opens a plan in one action, and the
> folded history it sits above is twice as long and half as uniform. Unargued.

This file is the argument, and it is shorter than the row implies because
driving the page answered most of it. **Three of the four findings below are
defects, not design questions**, and the fourth is the only real decision.

## What already reached the page, and it is more than the row assumed

Item 22 did not leave the page behind entirely. The live-job block reads the
alternation correctly today:

```html
<span :if="drafting">draft {{ live?.id }} · {{ live?.objective }}</span>
<span :if="!drafting">job {{ live?.id }} · {{ live?.objective }}</span>
```

— with `plan this` offered on a draft and not on a job. So the page knows the
difference at the bottom of the chat. **Everything below is somewhere else on
the same page disagreeing with that block.**

## Finding 1: a fold does not say which half of the alternation it was

Every closed job renders the same:

```html
job {{ (entry.job || entry.task).id }} · {{ (entry.job || entry.task).objective }}
```

So a draft — exploration nobody approved, run on the floor — and an approved job
— work under a plan somebody signed — are the same words in the transcript. The
live block calls one of them *draft 3* and the history calls the same job *job
3* four lines above it. A reader scrolling back cannot tell what was approved,
which is the one thing the gate exists to record.

**Fixed by the rule the live block already uses** (`!job.plan`), stated once and
shared, so the two surfaces cannot drift apart again.

## Finding 2: a draft closed *by an approval* is `ClosedBy::User`

`approve_plan` closes the draft on the way in and publishes:

```rust
by: Some(ClosedBy::User),
```

— the same value a person clicking *close & fold* produces. `ClosedBy`'s own doc
comment says why that is wrong:

> On the close rather than inferred afterwards, because the ladder above the
> person is only worth climbing if each rung can be *counted*.

Under the alternation there is a third rung and it is the common one: **most
drafts end because a plan was approved out of them**, not because anybody folded
them. A recording cannot count how often exploration led to approved work, a
reader cannot see it, and the page's `closed by exit code` line — which exists
for exactly this distinction — has nothing to say about the case that now
happens most.

`ClosedBy::Approval`, set where the approval closes the draft.
`protocol::VERSION` 7 → 8 and `record::FORMAT` 16 → 17, because a new value in a
plain enum is a parse error to an older reader, which is the rule those numbers
are for.

## Finding 3: `reopen` is offered where it cannot work, and item 22 is why

`Context::reopen_job` succeeds only for the **last** job:

```rust
if self.jobs.last().map(|job| job.id) != Some(id) {
    return false;
}
```

Its doc comment argues that well and is not what changed. **What changed is how
often the last job is the one you are looking at.** Before item 22 a jobless
turn opened nothing, so a person could close job 2, chat for a while and still
reopen it. Now every prompt opens a draft, so *the next prompt* is what ends the
window — and the transcript offers a `reopen` button on every fold in it, almost
all of which the server will refuse.

This is item 22 changing the meaning of a control nobody re-read, which is the
same shape as the gate panel that could narrow nothing and the refusal nobody
could see — both found by driving a surface, both in
[`the-gate-panel-narrows`](2026-09-17.the-gate-panel-narrows.completed.md).

**The page offers it where the server would take it**: the last job, and only
while it is closed. That is a rule stated in two languages, which this project
normally refuses — and the exception is argued below.

## Finding 4: and when it refuses, it says something false

```rust
refuse(&app, "reopen_job", Refusal::Job, format!("job {job} is not closed"))
```

`reopen_job` returns `false` for two different reasons and the message names
only one of them. In the case finding 3 describes the job **is** closed, and the
person is told it is not. A refusal a person cannot act on is the thing
`RECORD/2026-08-30.a-refusal-is-a-message.completed.md` exists to prevent, and
this one is worse than silent: it is wrong.

The route says which: *not the last job* when something came after it, *not
closed* when that is true.

## The decision: mark the halves, do not merge them

The row's other half — *twice as long* — is the only part that is a design
question rather than a defect. A session that plans three times leaves six folds
where it used to leave three, and half of them are drafts.

**The transcript keeps both, and marks them.** A draft's turns happened: they
were asked, answered, and are what the approved plan was written from, and the
model can still be asked about them. Merging a draft's fold into the job it
became would make the history shorter by hiding turns that are still in the
window, which is the opposite of what a transcript is for — and it would hide
them at exactly the moment somebody is auditing what was approved.

What makes the history *uniform* is not fewer entries, it is entries that say
what they are, which is findings 1 and 2. Whether a three-turn draft that
concluded nothing deserves a summary at all is **row 30** and stays there: that
is a question about the fold, not about the page drawing it.

## Rejected: linking the draft to the job it became

The tempting fifth change is *draft 3 — approved into job 4*, since the page
sees `job_closed` and `job_approved` as one transition the server deliberately
orders. It is rejected because **it would exist only in a live session**: the
link is nowhere in the store, so the same transcript reloaded would lose the
line, and a panel that says different things live and after a reload is the
class of bug [`the-panel-reads-the-pruned-lines`](2026-09-16.the-panel-reads-the-pruned-lines.completed.md)
found two of. `closed by approval` comes off `Job::closed_by`, which the view
already carries, so it survives a reload — and it answers the same question one
word shorter.

## Also rejected

- **A `can_reopen` field on the view**, so the page asks rather than knows. It is
  the right shape and it is one field for one button; the rule is *the last job,
  and closed*, both of which the page is already holding and already ordering.
  The cost of the duplication is a test, and the cost of the field is a wire
  fact that means nothing to any other reader. Revisit if a second rule about
  job order appears on the page.
- **Hiding refused controls generally.** Only this one is refused *by position*
  in a list the page has. `close & fold` on a running turn, for instance, is
  refused by state the server owns, and the page correctly just asks.

## What it costs

- A protocol and a format bump, in lockstep with `store.js`'s two constants,
  which `crates/luu/tests/ui_versions.rs` pins.
- One rule about job order expressed on the page as well as in the context,
  covered by a browser test that drives the case rather than by a comment.
- A recording made at format 16 still reads: `ClosedBy` is `#[serde(default)]`
  at its call site and the two old values are unchanged. What an older *reader*
  cannot do is read a new one, which is what the bump announces.

## Still open

- **Nothing counts the alternation.** How many drafts end in an approval against
  how many are folded is now a countable fact and nothing counts it — row 29's
  neighbourhood, and the first thing `ClosedBy::Approval` makes possible.
- **Row 30 is untouched**: whether a draft that concluded nothing is worth a
  summary.
- **The `!plan` rule is wrong for a pre-alternation recording**, where an
  approved job can arrive with no plan on the line and now reads as a draft. It
  is the rule the live block already uses, so this makes one surface agree with
  another rather than adding an error — but it is a rule about *what a null
  means*, and the honest fix is the kind the store's `RESTORED_DRAFT` already
  is.

## Appended 2026-09-21, second section: built, and the fifth finding is the one that mattered

Findings 1 to 4 landed as argued, the decision stands, and **the browser test
written to prove finding 1 failed for a different reason** — which is how the
real defect turned up.

### 5. A draft's turns were loose, live, and attributed after a reload

The new assertion was *two folds in the transcript*. It found one. The draft's
fold was not there at all, so the row's *twice as long* was never even true on
screen — and the reason is worse than the complaint:

```
PHASE1 ["turn_started", … , "ended", "draft_opened", "plan_proposed"]
```

`turn_started` carries the job a turn is **in**, and a turn that opens a draft
is in a job that did not exist when it started, so that field is null. The wire
already solves this and says so in a doc comment written with item 22:

> The turn that opened it, which is the only way a job ever opens. Carried
> rather than left for a client to infer, because it is the only place that
> attribution exists… Without this the first turn of every session would read as
> belonging to nothing, which is the exact claim item 22 retired.

**The page dropped it.** `store.js`'s `draft_opened` pushed the job and ignored
`message.turn`, so live, a draft's turns belonged to nothing, `foldTranscript`
never grouped them, and its fold never rendered. Reloaded, the same session came
back from `/api/sessions/:id` with each turn's job on it and the fold appeared.
**Two answers to one question depending on whether you refreshed** — the same
shape as the pruning panel that showed turn 5's cut under turn 8's budget, found
the same way, by driving the surface.

The fix is four lines in the store: back-fill the job on the turn the line
names. Nothing on the wire changed, because nothing on the wire was missing.

### What the row was and what it turned out to be

The row said *unargued*. Of the five findings, **four are defects and one is a
decision** — and the decision (keep both folds, mark them) took a paragraph
while the defects took the commit. Worth writing down as a calibration note: a
row that reads as a design question because nobody has looked at the surface is
usually a row about what is broken on it, and this is the third revision running
in which that has been true.

### What was run

- `cargo test --workspace`: **518 passed, 0 failed**, after one existing
  assertion was corrected — `a_green_command_closes_the_task_with_nobody_at_the_gate`
  pinned `closed_by == "user"` on a draft an approval had closed, which is the
  conflation this record is about, encoded in a test.
- `cargo fmt --all --check` and `RUSTFLAGS=-Dwarnings cargo clippy --workspace
  --all-targets`: clean.
- The 16 live-server Playwright specs: green.

Confirmed against their absence: reverting the refusal's `match` makes it say
*job 2 is not closed* and fails the new test; reverting the store's back-fill
leaves one fold where the spec asserts two.

### A note on the scratch test

The message order above came from a throwaway test that dumped every frame of
one alternation and was deleted in the same session. It took four minutes and
replaced twenty of reading `serve.rs`. Nothing in the suite does this, and the
next person to ask *what does the wire actually say here* should write the same
thing and throw it away again.

## Still open, after building it

- **The `!plan` rule still reads a pre-alternation approved job as a draft**, as
  §Still open said before it was built. Unchanged, now on two surfaces rather
  than one.
- **Nothing counts the rungs.** `ClosedBy::Approval` makes *how often
  exploration led to approved work* answerable and nothing asks it — row 29.
- **`reopenable` is the page holding a rule the context owns.** One button, one
  browser test, and a `can_reopen` on the view is the fix if a second such rule
  appears.
- **The static twin's fixtures are at format 16.** They are generated by
  `scripts/make-fixtures.sh` from a real run, so they carry whatever the binary
  that made them wrote; a deploy assembled from an older binary would now be
  refused by the page. Not new with this bump and not tested anywhere.
