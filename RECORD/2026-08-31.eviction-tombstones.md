# Eviction tombstones: what a session forgot, on the wire

**Status:** plan, then code. Takes the first item off
[`2026-08-31.what-no-model-has-seen.md`](2026-08-31.what-no-model-has-seen.md),
which closed with *"eviction tombstones, then the gate protocol"* and put them in
that order for a reason worth repeating here: the gate run will produce
recordings nobody has read before, and it should not produce them through an
instrument that cannot say what it dropped.

## The problem

Eviction is the one thing this project is about that leaves no trace.

`Context::floor` moves forward, whole turns leave the window and stay out — and
nothing anywhere says so. Not on the protocol, not on the trace channel, not in
the record file. `Selection::evicted` is a `usize` that reaches exactly one
place: it is returned and dropped on the floor by both call sites.

```
$ grep -rn "evicted" --include=*.rs crates/ | grep -v tests
crates/agent-core/src/context.rs:206:    pub evicted: usize,
crates/agent-core/src/context.rs:627:            evicted: self.floor,
```

So a recording shows a `history` bucket that got smaller and **cannot say why**.
Three readings produce the same picture and mean completely different things:

- the policy cut the history (`Eviction::Block` cutting to the low-water mark),
- the arithmetic did (a fragment arrived, `available` shrank, one turn fell out),
- or nothing was dropped at all and the turns in it were simply short.

This is not hypothetical. The degenerate 512-token fixtures survived a whole
commit for exactly this reason: the bucket read empty and the recording could not
be asked whether that was a decision or a subtraction. It has been asked for
three times — [`cline-openhands`](2026-08-27.cline-openhands.md) with the
precondition *"nothing — it is small"*,
[`tasks-in-code`](2026-08-30.tasks-in-code.md),
[`state-of-play`](2026-08-30.state-of-play.md) — and is the oldest unpaid debt in
the tree.

It is also the one measurement that a later reader cannot reconstruct. The
backend's `usage` is on `Ended`; the buckets are on `Budget`; what a turn asked
is on `TurnStarted`. The floor is in memory and dies with the process.

## The proposal

One protocol message, emitted by the selection that moved the floor:

```jsonc
{"type": "evicted", "turn": 12,
 "turns": [1, 2, 3],
 "tokens": 843,
 "counter": {"kind": "model", "id": "qwen2.5-coder:7b"},
 "policy": {"policy": "block", "low_water": 0.5}}
```

- **`turn`** — the turn whose selection dropped them. Eviction happens because
  the *next* prompt no longer fits, so it belongs to the turn that did not fit,
  the same way `budget` describes the call that is about to be made rather than
  the one that was.
- **`turns`** — which turns left, oldest first. Named, not counted: see below.
- **`tokens`** — what they were worth in the prompt they are no longer in.
- **`counter`** — because `tokens` is a count, and every count in this system
  says who produced it. Two runs measured by different counters are not
  comparable and nothing else here would say so.
- **`policy`** — which cut this was. The whole difference between the two
  policies is *how deep*, and a tombstone that did not name the policy would
  leave the reader doing the subtraction the message exists to spare them.

### Three consequences, and none of them is incidental

**1. Turns need ids.** The floor is an index into `Context::turns`; the protocol
counts turns from 1 per session. Those are *not* the same number, and the place
they come apart is already in the tree:

```rust
// serve.rs:906, lib.rs:971 — both call sites
if !outcome.text.is_empty() || !outcome.steps.is_empty() {
    session.context.push_turn_with_steps(...)
}
```

A turn that produced nothing is never pushed. One of those in a session and every
tombstone after it names the wrong turns — silently, and in the one file whose
purpose is to be trusted months later. So `Turn` gains an `id`, assigned by the
caller that already owns the numbering, and `push_turn`/`push_turn_with_steps`
take it. Twenty call sites, most of them tests.

This is worth more than the tombstone that forced it: the history's units are now
addressable from outside the context manager, which is what relevance selection
will need in order to say *which* turn it scored.

**2. It goes on the protocol, not the trace channel.** This is the closer call,
and the rule in `protocol.rs` is *debug data does not live here — things that
explain the agent rather than drive it belong in `trace`*. Eviction reads like
budget accounting, and budget accounting is trace.

It is not. It is the same class of fact as `TaskClosed`, which is on the protocol
with this reason written beside it:

> the task's turns are sent as this summary. It travels on the wire because a
> transcript has to be able to show what the model will see from now on.

A fold and an eviction are the two ways the history stops being sent. One of them
is already a protocol message; putting the other behind `--trace` would mean a
recording taken without the flag can show a session's turns and cannot show that
half of them are no longer in the prompt. That is not a debug detail, it is the
state of the conversation — and a stdio client driving the agent is entitled to
know that the history it is watching has been cut.

The `Budget` bucket beside it stays on trace, and that split is right: *how many
tokens the history is worth* explains the agent, *which turns are gone* is what
happened.

**3. Protocol v3 and record format 5.** A new variant of a tagged enum is a parse
error to an older reader, not a line it can skip. Same rule as `Refused` (v2),
used the same way.

## What the transcript does with it

The evicted turns **stay in the transcript, marked**. Removing them would repeat
the exact mistake this message exists to fix — the UI would then agree with the
prompt and no longer be able to show the difference between them, which is the
one thing the debug client is for.

It is the fold's posture, one step further: a closed task collapses to what the
model now sees and expands to what it no longer does; an evicted turn is dimmed
and says which turn dropped it. `TurnView` gains both halves — `evicted`, the
turns this turn's selection dropped, and `evicted_by`, on each of them.

## What it costs

- One more message per selection that cuts, which is at most one per turn and
  zero in a session that never fills its window.
- `Turn` gains a field, and the two callers must pass the id they already have.
- A recording gets longer by a line per cut. The header already carries the
  policy; this repeats it per message, which is redundancy bought on purpose —
  a line that is copied out of a file into a note stays true on its own.

## Rejected

- **On the trace channel.** See above: it would make the record's fidelity depend
  on a debug flag, and the fold's own argument applies unchanged.
- **A count instead of ids** (`{"evicted": 3}`). Cheaper, and it answers *how
  many* while leaving *which* to a reader who would have to re-implement the
  floor to get it. It also cannot mark a transcript.
- **Deriving it on the reader's side** from consecutive `Budget` messages. The
  reader would need the turns' token counts, the item folding and the low-water
  arithmetic — that is the context manager, re-implemented in a viewer, drifting
  from the day it is written.
- **A restore/uneviction event.** There is none. The floor only moves forward;
  that is the commitment, and an event for its opposite would suggest otherwise.
- **Making it a `Turn`-level flag only** (`turn.evicted = true`) with no message.
  A flag in a view is not an event in a stream: `SessionView` is fed *by* the
  stream, and the two ways it is fed — live and from a recording — agree only
  because everything goes through the messages.

## Still open

- **Partial eviction has no tombstone, because it does not exist yet.** Pruning
  tool results out of a turn ([`state-of-play`](2026-08-30.state-of-play.md))
  would drop part of a turn that stays in the window, and this message cannot say
  that. Deliberately: a message for a thing nobody has built would be guessed at,
  and guessing at message shapes is what the freeze rule exists to stop.
- **A folded task whose turns leave** is reported as its turns, oldest first,
  and the fact that they were folded rather than live is left to `summaries`
  falling in the budget beside it. Naming the task too would be a second way to
  say the same thing.
- **Nothing yet reads these back.** `luu export` folds them into the view, and no
  analysis uses them. The first one that will is the gate run's recordings, which
  is why this went first.

## Appended the same day: what building it found

**The turn-id divergence is not the edge case the plan above described.** The
plan justified `Turn::id` with a turn that produces nothing and is never pushed
— rare, and easy to read as pedantry. The socket test found the ordinary case
immediately: **the planning call is a turn of the session that is deliberately
never remembered.**

```rust
// serve.rs, above `propose_task`
/// The planning call is a turn: a prompt goes in, tokens come out, it costs a
/// window [...] It is the one turn that is **not** remembered — what survives
/// it is the task, and a plan block in the history would be paid for on every
/// later call.
```

So in *every* session that goes through the gate, the first turn of the history
is turn 2. An index-based tombstone would have named turn 1 — the planning call
— as the first thing evicted, in every recording the gate run is about to
produce. `the_window_filling_up_says_which_turns_it_dropped` asserts exactly
this: the first cut names turn 2, and turn 1's `evicted_by` stays null, because
nothing evicted it and it was never in the window to leave it.

## What the recorded fixtures now say

Re-recording `scripts/make-fixtures.sh` unchanged — the same three files the
page has always replayed — the tombstones fall out as the first direct reading
of the two policies:

| fixture | cuts | shape |
| --- | ---: | --- |
| `eviction-turn` | 10 | one or two turns at a time, from turn 11 on |
| `eviction-block` | 2 | six turns at once, then five |
| `eviction-tasks` | **0** | the fold kept the history under the limit; eviction never fired |

The first two are the argument for block eviction stated in the recording rather
than in a reuse percentage derived from it. The third is the more interesting
line: `RECORD/2026-08-30.tasks-in-code.md` already claimed the tasks run never
evicts, and until now that claim rested on a bucket that *looked* like it had
not moved. It is now the absence of a message rather than the absence of a
symptom.

## Also true, and left alone

- **The replay test waits 30 seconds.** The first cut in `eviction-block` lands
  eleven turns in, and a recording replays at the pace it was recorded. Given
  the choice between a fixture that is a real run and a fast test, the fixture
  wins; the test carries a comment saying so.
- **A turn that was never in the window looks like a turn that is still in it.**
  `evicted_by: null` covers both, and the planning call is the one that is
  always the first. Not fixed here: the honest fix is for the view to know which
  turns the history holds, which is a bigger claim than a tombstone and belongs
  with whatever finally reads these back.
- **The field is `dropped`, not `evicted`.** The plan above names `TurnView`'s two
  halves `evicted` and `evicted_by`; in the code the first is `dropped`, because
  `turn.evicted` beside `turn.evicted_by` reads as *this turn was evicted* and
  means the opposite. Left as written above rather than corrected in place: the
  wrong name is what was believed when the plan was written.
