# What a container start costs — measured

**Status:** closes item 7 of [`ROADMAP/2026-09-09`](../ROADMAP/2026-09-09/README.md).
[`a-session-picks-its-executor`](2026-09-08.a-session-picks-its-executor.completed.md)
chose *the worker starts with the session, not at its first tool call* on the
shape of the thing — a lazy start makes `describe()` and `luu tools` either
start a container anyway or say "not yet" — and left the cost of that choice
unmeasured. This is the number.

## The question

Every new session created under a container posture now pays for a
`docker run` and a handshake **before the first prompt**, where the lazy
design would have deferred it to the first tool call — or skipped it
entirely, for a session that only ever asks questions. How much is that,
against a session that starts under the host posture instead?

## The run

`luu serve --backend mock --no-store`, a `config.toml` naming two postures —
`host` → `luu.toml` (no `[worker]`, the default in-process worker) and
`container` → `luu.container.toml` (`[worker] runtime = "docker"`, the same
image `scripts/container-check.sh` builds and CI's `container` job runs) —
and twenty interleaved pairs of `POST /api/sessions`, timed at the
millisecond. Machine 1 (M1 Pro, 16 GB, macOS), Docker Desktop, the real
image — not a mock of the worker. Full script, raw readings and the
reproduction command are in
[`runs/2026-09-15.container-start-cost/`](runs/2026-09-15.container-start-cost/).

Each `POST` also ends the *previous* session's agency
(`previous.shutdown().await`, synchronous, before the handler answers) — so
the `container` arm's number is "shut down one container, start the next,
handshake with it" end to end, which is what a person actually waits on
switching sessions or starting a new one. The `host` arm pays the same
shutdown-then-start shape with an in-process worker, which is why it is the
baseline rather than zero.

## What it says

| | host | container |
| --- | --- | --- |
| mean | 55.2 ms | 155.8 ms |
| median | 57 ms | 151 ms |
| stdev | 5.9 ms | 11.7 ms |
| min–max | 41–63 ms | 144–183 ms |

**A container start costs ~100 ms over a host one** (100.6 ms by the mean,
94 ms by the median) — cheap enough that eager start is not a real trade for
the common case: nobody will notice a tenth of a second added to opening a
session. The container arm's own variance (stdev 11.7 ms against the host's
5.9 ms) is the interesting half — Docker Desktop's `create`/`attach`/`start`
round trip crosses into its Linux VM and back, and that crossing is where
the extra tens of milliseconds live, confirmed against `docker events` during
one extra call outside the timed run: a real `container create` → `attach` →
`start` for the new one and a real `die` → `destroy` for the one it replaced,
never a cached reuse.

**This is a warm number, and the record says so rather than hiding it.**
The image is already built and already on the machine — the twenty pairs
measure the steady state a running server is in, not the first session of a
cold checkout. A first-ever container start pays image pull and build on top
of this, which is a different, already-answered question
(`docker build` itself, timed separately while preparing this run: a few
minutes, dominated by `cargo build --release` inside the image, on a machine
with the crate registry already warm).

## What it does not decide

The number says eager start is cheap; it does not say lazy start was wrong to
reject. `a-session-picks-its-executor` rejected lazy for a reason unrelated to
cost — `describe()` and `luu tools` needing a real answer rather than
"not yet" — and this measurement does not reopen that. What it closes is
narrower: the shape was chosen without a number, and now there is one, and it
is small enough that nobody revisiting the choice on cost alone would flip
it.
