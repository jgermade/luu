# Eviction is a recorded event

**Status:** built. Closes the item both stock-takings put first among what is
"blocked on nothing" —
[`2026-08-30.ready-for-the-m4-run.md`](2026-08-30.ready-for-the-m4-run.md) and
[`2026-08-31.what-no-model-has-seen.md`](2026-08-31.what-no-model-has-seen.md)
— and builds the shape `loude-design.md`'s persistence section already named
as decided: "the shape is OpenHands' condensation tombstones", from
[`2026-08-27.cline-openhands.md`](2026-08-27.cline-openhands.md). No model was
needed for this one; it is code and its own tests.

## The gap

`Context::floor` (`crates/agent-core/src/context.rs`) only ever moves forward,
and `Selection::evicted` already counted how many turns are behind it — but
nothing published that count anywhere. A recording could show the `history`
bucket shrink turn over turn and could not say which turns caused it, when, or
by what id a reader could look them up. The symptom was on the wire; the cause
stayed in memory.

## The shape

OpenHands models forgetting as an event carrying `forgotten_event_ids`, not a
projection recomputed from a live pointer. Ours is smaller because most of the
machinery already existed:

- **`TraceMessage::Evicted { turn, forgotten }`** (`trace.rs`) — one new
  variant, `forgotten` the ids that left the window as of `turn`. Nothing else
  changed shape; it travels the same channel `Budget` and `PrefixReuse` do.
- **`EvictionTombstones`** (`crates/luu/src/session.rs`) — the one piece that
  had nowhere to live. `Context` tracks eviction as a floor over its own turn
  *indices* and deliberately knows nothing of `TurnId`: that split is the same
  one that already has every `TraceMessage` variant take `turn` from its
  caller rather than track one itself. So the id-to-index mapping is kept
  beside `PrefixTracker`, in the one layer that already assigns `TurnId`s and
  pushes turns into `Context` — `.pushed(turn)` alongside every
  `push_turn_with_steps`, `.mark(selection.evicted)` beside every `select`,
  turning a *count* into the slice of ids newly past it. A turn that produced
  nothing is never pushed (an empty answer is not a thing that happened), so
  the id sequence a real session hands in can skip numbers — `mark` does not
  assume consecutive ids, only a consistent order, which is what
  `ids_need_not_be_consecutive` in `session.rs` exists to pin down.
- **`TurnView::evicted`** (`crates/agent-core/src/api.rs`) — the fold: one new
  arm in `apply_trace` sets it `true` for every id in `forgotten`. Never
  unset — nothing currently un-evicts a turn short of reopening the task that
  folded it, and reopening does not resurrect what left the window before the
  fold, only what the fold itself replaced.

`Context` itself is untouched. `Selection::evicted` already existed and already
said everything the tombstone needed; the fix was entirely in the layer that
was throwing that number away.

## What was verified, and how

Against the code, not a model — this is bookkeeping, not a context strategy:

- `trace::tests::an_eviction_names_the_turns_it_forgot` — the variant survives
  the wire.
- `session::tests` — three cases: nothing marked before the floor moves,
  reporting only the ids newly behind a rising floor and not the ones already
  named, and a non-consecutive id sequence (the skipped-turn case) still slices
  correctly.
- `api::tests::an_eviction_marks_the_turns_it_names_and_leaves_the_rest` — the
  fold sets `evicted` on exactly the named turns, not the one whose selection
  caused it.
- `folding_live_events_gives_the_same_view_as_folding_the_record` — extended
  with an `Evicted` line so the parity check the live server is trusted
  against also covers this variant.

`cargo test --workspace`: 162 → 167. `cargo fmt --all --check` and
`RUSTFLAGS=-D warnings cargo clippy --workspace --all-targets` both clean.

## What this does not do

The debug UI's budget panel does not show tombstones — `onTrace` in
`crates/luu/ui/store.js` ignores an unknown `type` silently, so nothing broke,
but nothing renders `evicted` either. That is a panel feature, not a recording
gap, and the design note's own scope for this item ("one message on the trace
channel and two lines in the fold") did not ask for it. Worth a small follow-up
— a struck-through or dimmed entry in the turn list — but not blocking
anything named in either stock-taking.

The gate protocol against a real model — the item the last stock-taking
actually recommended running *after* this — is still just a table row in
[`2026-08-30.the-gate.md`](2026-08-30.the-gate.md).
