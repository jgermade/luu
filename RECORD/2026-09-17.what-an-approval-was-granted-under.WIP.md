# What an approval was granted under: a resume inherits the live posture, and the stream does not say so

**Status:** WIP — a proposal and the code it plans. Roadmap item 9 of
[`ROADMAP/2026-09-17`](../ROADMAP/2026-09-17/README.md), carried from item 8 of
[`2026-09-09`](../ROADMAP/2026-09-09/README.md), where it read *"a session
resumed under a different posture is refused by nothing"* and sat for eight
days. It is written before the diff because the last row that sat that long
turned out to have the argument and the code the same age
([`enforcement-per-job`](2026-09-06.enforcement-per-job.completed.md)), and the
lesson taken from that was not *skip the record*.

The row's own sentence turned out to be right about the symptom and wrong about
the mechanism, which is the reason this file is longer than the row.

## The problem

[`luu-design.md`](../luu-design.md) says it in bold:

> **A resume may not move it** — a destination is where a session sends and a
> posture is what it may do, and its jobs were approved against this one.

That is not what the tree does. `resume_session` reads the posture out of the
**live process**, not out of the session it is resuming:

```rust
// crates/luu/src/serve.rs:3102
// The posture is the one already in place — a resume moves where a session
// sends and never what it may do — and it is read before the stream lock,
// because nothing in this file holds two locks across an await.
let posture_name = app.posture.lock().await.clone();
let posture = app.agency().await.posture(posture_name);
```

`app.posture` is whatever the *last session started on this server* named — or
the server's own policy file, if nobody named anything. The comment is an honest
description of what the code does and it is implementing a different sentence
from the one the design wrote. Two readings of *a resume may not move it*:

- **What the code implements:** the resume endpoint does not accept a `posture`
  field, so nobody can *ask* for a different one. True, and enforced.
- **What the design means:** the session keeps the posture its jobs were
  approved under. False, and enforced nowhere.

They coincide exactly when the live posture already is the session's, which is
the case in every test in the tree and in every session anybody has resumed
inside one `serve` that only ever had one posture. They come apart the first
time a server restarts, or the first time two sessions on one server pick
different postures — which is the whole feature
[`a-session-picks-its-executor`](2026-09-08.a-session-picks-its-executor.completed.md)
landed.

### The sequence, with nothing exotic in it

```toml
# config.toml
[posture.container]
policy = "luu.container.toml"
```

1. Session `s-1` starts under `container`. Tool calls run inside the image,
   `enforcement = kernel`, `network = false`. A job proposes
   `run_command ["sh", "-c", "curl …"]`; a person reads the plan **knowing it is
   contained**, and does not answer it. The session is checkpointed with the job
   in `Proposed`.
2. `serve` is restarted, or somebody starts a second session and picks no
   posture. `app.posture` is now `None` and `app.agency()` is the host: no
   worker, `runtime = "host"`.
3. `s-1` is resumed. `pending_proposal` (`serve.rs:2303`) puts it back **at the
   gate**, exactly as designed — a trailing proposal is a question still waiting
   on a person, and coming back to it is the right behaviour.
4. The person answers it. The plan they are answering is the one written for a
   container; the sandbox it is granted against is the host's.

Nothing in that sequence is a misuse. Step 3 is a feature added on purpose, and
step 4 is the gate working as specified. What is missing is that **nothing
between 1 and 4 compares two postures**, because nothing on either side of the
comparison is kept where a comparison could reach it.

### Three places the fact is lost, and they are not the same bug

**One — the fold drops it.** The posture is on the wire and has been since
format 10 (`record::Posture`, `record.rs:85`): a name, a runtime, an enforcement
and a network bit, in the `Header`. The fold reads the header for three fields
and throws the rest away:

```rust
// crates/agent-core/src/api.rs:555
RecordLine::Header { backend, model, started_at, .. } => {
    view.backend = backend.clone();
    view.model = model.clone();
    view.started_at = *started_at;
}
```

`SessionView` has no posture field, so the store's blob — which *is* the view,
by [`sessions-in-sqlite`](2026-09-02.sessions-in-sqlite.completed.md)'s rule that
a row holds the fold and nothing else — has no posture either. `SessionStore::resume`
goes through `load`, which reads the blob (`store.rs:319`). The event stream
beside it *does* hold every header verbatim, so **the fact is on disk and the
resume path never looks at it.**

**Two — a resume that changes only the posture writes no line at all.**

```rust
// crates/luu/src/serve.rs:2814
let same = view.backend == sending.backend.name() && view.model == sending.model;
```

`retarget_header` returns `None` when the destination has not moved. A resume
from `container` to `host` on the same backend and model changes nothing it
compares, so the stream gains **nothing**, and the rest of the session is
recorded as if it had continued under the posture the first header names. The
existing test says so out loud, as a statement of intent:

```rust
// crates/luu/src/serve.rs:3538
// The posture is carried, not compared: a resume moves where a session
// sends and never what it may do.
```

This is the half that matters most, and it is the half the roadmap row did not
see. A gate that can be argued about later is a different thing from a
**recording that is wrong**: the project's whole method is that a run can be
re-read afterwards, and here the account of what a turn was allowed to do
silently describes a posture it did not run under.

**Three — a signature does not bind it.** `Approval::canonical`
(`approval.rs:80`) builds the signed bytes from `session`, `job`, `files`,
`writes`, `commands`, `closes_on`, `network`, `egress` and `enforcement`. No
runtime, no posture name. Since `resume` restores the session under **its own
id** and job ids are handed out by position, a signature made for
`{session s-1, job 3}` is admissible for `{session s-1, job 3}` in any posture
that session is ever resumed under. `enforcement` is in the string, which
narrows this usefully — a signature that named `kernel` still names `kernel` —
but `enforcement` is the *strictness*, not the *executor*: `kernel` on the host
and `kernel` inside the container are the same four bytes and two very different
places for a `curl` to run.

### What is not broken, and saying so is not a consolation prize

- **The surface is honest.** `get_settings` reads the live agency
  (`serve.rs:2340`), and `store.js`'s `resumeSession` calls `refreshSettings()`
  right after the resume, so the header line in the page names the posture that
  is actually in force. A person who looks sees the truth. This is exactly the
  distinction 2026-09-08 keeps finding: *visible* and *enforced* are different
  properties, and three bugs that day were found by looking at a surface that
  was telling the truth to nobody in particular.
- **An already-approved job's grant does not survive.** `resume_session` sets
  `session.narrowed = None` (`serve.rs:3130`), so no narrowed sandbox is carried
  across. Only a *trailing proposal* comes back, which is the case above.
- **`chat` and `stdio` are unaffected.** There the process is the run and the
  policy file is a flag; there is no live posture to inherit.

## The proposal

Three changes, in the order they depend on each other, and the first one is most
of the value.

### 1. The fold keeps the posture

`SessionView` gains one field:

```rust
/// The posture the stream's last header named, or `None` for a session
/// recorded before format 10 — which is *unknown*, and specifically not
/// `host`.
#[serde(default)]
pub posture: Option<record::Posture>,
```

folded in the `Header` arm beside `backend` and `model`. **No format bump and no
new wire field**: every fact this needs has been recorded since 2026-09-08. The
store's blob gains it because the blob is the view, and
`tests/store_parity.rs` already pins that relationship.

`record::Posture` needs `PartialEq`, which it has (`record.rs:84`).

### 2. The resume compares, and refuses

```
POST /api/sessions/{id}/resume
409 Conflict
  session s-1 ran under posture "container"
  (docker (luu-worker:dev), kernel, no network); this server is on the host
  (host, kernel, no network). Start it under "container" to resume it, or
  resume it read-only.
```

Compared on the **three facts, not the name** — for the reason `record::Posture`
gives for carrying three facts in the first place: a name is a label and the
file behind it can be edited tomorrow. `None` on the stored side is *unknown*
and is not refused; it is named in the message and in the header line, because a
session recorded before format 10 has no answer and inventing `host` for it
would be a fabricated number in a project that does not keep them.

**Why refuse rather than rebuild the posture.** `posture_for` can build an
agency from a policy file, so the endpoint could silently start the container
the stored session needs. It must not: building a posture can start a container,
and a resume that starts one nobody asked for is a resume that does something
outside what the person clicked. It can also simply fail — the policy file may
not exist on this machine, the runtime may not be installed — and a failure
there would end a live session to service a resume, which is the exact mistake
`create_session` was written to avoid by resolving the posture *before* anything
is reset.

The endpoint gains an optional `posture` field, admitted only when it resolves to
the same three facts. That keeps the design's sentence true — a resume still may
not *move* the posture — while letting a caller say which one it means on a
server that has several.

### 3. The header is written when the posture moves, too

```rust
let same = view.backend == sending.backend.name()
    && view.model == sending.model
    && view.posture.as_ref() == Some(&posture);
```

Strictly this is unreachable once 2 refuses the mismatch, and it goes in anyway,
for two reasons: the `None` case *is* reachable (an old session resumed on a
host, allowed through, and its stream should say where the rest of it ran), and
a recording's honesty should not be a downstream consequence of an access check
that might be relaxed later. The rule is the one
[`what-a-fold-writes-down`](2026-09-08.what-a-fold-writes-down.completed.md)
already argued: the line goes in where the fact changes, not where somebody
happens to be looking.

### Not in this proposal: the signature

Binding the posture into `Approval::canonical` is the right end state and is
**deliberately not here**. See *What was rejected*.

## What it costs

- **One field on `SessionView`**, which is the structure `luu export` writes and
  the static mirror serves. `#[serde(default)]` keeps every recording and every
  stored row readable, and the parity test is what proves it.
- **A 409 on a path that has never refused anything.** Somebody with one server,
  one posture and a habit of resuming sessions will never see it; somebody
  running a container posture will see it the first time they restart `serve`
  and pick up yesterday's session. That is the point, and it is still a new way
  for a familiar action to fail.
- **`retarget_header` gains a third term**, and its test gains the case its own
  comment currently documents as intended behaviour. The comment goes.
- **Nothing in the sandbox or the seam changes**, and no format moves. This is a
  read of something already written down.

## What was rejected, and why

- **Putting the posture in `Approval::canonical`.** It is the strongest fix and
  it is a different decision. Appended last and written only when present, the
  way `enforcement` was, every existing signature still verifies byte for byte —
  and an attacker simply omits the field, so *optional* buys nothing here. Made
  mandatory it invalidates every signed approval on disk, which is a migration
  and needs an argument about key rotation that item 16 says nobody has had yet
  ([`signed-approvals`](2026-09-04.signed-approvals.completed.md) §Still open).
  Between the two sits a config switch, which is a third state to reason about.
  This record refuses to pick under time pressure it does not have: with 1 and 2
  in place, the *replay* needs a resume that is now refused, so the signature
  question stops being the load-bearing one and can be argued on its own.
- **Refusing every resume whose posture differs, with no way to say which one you
  mean.** That makes a stored session unreadable on a machine that no longer has
  its runtime, which is a worse failure than the one being fixed: the history is
  a cache of the fold, and reading it is not a privileged act.
- **Carrying the posture in the `sessions` table as its own column.** The
  listing columns are duplicated *out of* the view at write time and the store
  module's whole argument is that a row holds the fold and nothing else. A
  column that the view does not have is the second definition
  [`sessions-in-sqlite`](2026-09-02.sessions-in-sqlite.completed.md) rejects.
- **Reading the posture out of the event stream instead of the fold.** It is
  where the fact actually is, and it would work — and it would mean the resume
  path parses a stream to answer a question the fold could answer, for sessions
  that have a stream at all (`SessionStore::stream` answers with nothing for
  those written before schema 2). The fold is the thing everything else reads.
- **Treating this as a UI problem.** The page already tells the truth. A rule
  that holds only while somebody is reading the header is not a rule, and this
  is the same conclusion item 10 of the current revision reaches from the other
  direction: `network`, `egress` and `enforcement` are narrowable by protocol and
  unreachable from the gate panel.

## Still open

- **What a *read-only* resume is.** The refusal message above offers one and
  nothing in the tree implements it. Today a resume makes a session live — it
  becomes the thing the next prompt continues. A mode that folds a session into
  the page without making it live is plausibly five lines and plausibly a new
  concept in the surface; it is named here because the refusal is more
  defensible when there is somewhere to go from it.
- **Whether `enforcement` in the signed string was already doing this job
  badly.** It narrows the replay without naming the executor, and nobody has
  asked what an `Approval` is *for*: the grant, or the environment. The answer
  decides the signature question above.
- **Nothing counts how often postures differ in practice.** The same shape as
  item 12 of the current revision — nothing counts file-versus-directory grants
  either — and the same reason it matters: a refusal nobody ever hits and a
  refusal everybody hits every morning are different features, and the tree
  cannot currently tell which this is.
- **`limits` is still session-wide**, which
  [`enforcement-per-job`](2026-09-06.enforcement-per-job.completed.md) left as
  the last field a plan cannot narrow. Unrelated to this file except that it is
  the other thing an approved job does not fully describe.
