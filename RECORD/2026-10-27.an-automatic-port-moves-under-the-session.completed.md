# An automatic port moves under the session

> *port 11435, where luu placed engine ollama, answers and is not luu's: start
> a new session to place it on a free one* — *luu debería encargarse del
> cambio de puerto, estando en auto, debería ser transparente para el
> usuario.*
>
> And then: *pone que ollama no se ha podido iniciar, pero sí ha ejecutado
> bien. ¿Se está mezclando el del sistema con el de luu?*

## What it was

Not the system's ollama. That one listens on 11434, and luu had placed its
own on 11435 as it should
([`RECORD/2026-10-26.ports-luu-places.completed.md`](2026-10-26.ports-luu-places.completed.md)).
It was luu's own ollama, taken for somebody else's by luu itself.

`Supervisor::ensure_now` read the engine's slot first: `Some(model)` when luu
runs it. Then it had one arm for *luu runs it on another model* (restart it)
and a catch-all for everything else. Two cases ended up in the catch-all: luu
running it on this model, and luu not running it at all. Both reached
*something answers on the port*. Where the port was one luu placed, both were
treated as *taken since*.

`provider::resolve` wrote the placed port into the resolved engine's table,
so the session's engine always looked placed. So:

1. The first `ensure` started ollama on 11435. The first turn ran on it.
2. Every `ensure` after that found luu's own ollama answering on 11435. It
   called it somebody else's, forgot the placement and failed with *start a
   new session*.
   - The second `ensure` comes at once: the turn's, the window's, a warm's.
   - The foot said *could not start ollama* under an answer that had just
     streamed from it.

The case the sentence was written for still happens: luu places an automatic
port when a session is made, and starts the engine at its first turn, minutes
later. Another `luu serve`, or anything else, can take the port in between.
That case was answered with *start a new session*: the session's backend was
built with the old port in its URL, and moving the engine left it dialling
nothing.

## What it is

- **luu's own engine is luu's.** The slot's `Some(_)` is its own arm: if it
  answers, `ensure` is done. Only a port nobody in this process runs on can be
  somebody else's.
- **A taken automatic port moves the engine.** `ensure` forgets the placement,
  places it again past the taken port (`place(name, kind, &[taken])`), starts
  it there, and logs both ports. A port the table names that answers is still
  used as it is.
- **`ensure` answers with the port.** It is what the engine answers on, fixed
  or placed, now.
- **The session follows it.**
  - `engines::Started` keeps the port its backend dials. When an `ensure`
    answers with another, it builds the backend again for that port
    (`crate::rebuild_for`: the resolved destination with its URL's port
    replaced) and sends there.
  - A turn already streaming keeps reading the backend it began on: its
    stream holds that backend itself (`engines::owned`), and is dropped with
    the turn.
- **The resolved engine keeps no `port`.** `resolve` still places it, and
  writes the placed port into the URL. The table stays automatic, so every
  `listening`, `status` and `ensure` asks the placement, and the placement can
  move.
- **The CLI and the engine sheet's chat.** `luu chat` and `luu stdio` build the
  destination again when the engine started elsewhere. The sheet's chat sends
  to the port `ensure` answered with.

## Also, the same day

**The engine's state beside the picker opens its output.** Asked: *al hacer
click en el estado del motor de inferencia … podría abrir Settings > Engines,
en la SubModal del engine correspondiente, en la pestaña output.*
- The state is a button now. `openSettingsAt("engines", { name, tab:
  "output" })` opens Settings on Engines.
- Engines opens that engine's sheet once its view has loaded, since the sheet
  reads the view when it mounts.
- `ui.engineSheet` carries the ask and is cleared when taken.

## Rejected

- **Using whatever answers on the taken port when it is the same kind.** Every
  ollama serves any model in the shared store, so for ollama that would have
  worked. A llama-server holds one model, and somebody else's holds theirs. And
  either one could go away under the session at any moment.
- **Writing the new port into the file.** Rejected before, for the same
  reason: it is a fact about this process, not about the file.

## Tested

- `engines::tests`:
  - A stand-in ollama luu runs on an automatic port is ready on three
    `ensure`s in a row, on the same port.
  - With an HTTP squatter on the port luu placed it on, a `Started` asked for
    its window places the engine again, starts it there, and builds its
    backend once, for the new port. Asked again, it builds nothing.
- `provider::tests`: an automatic engine resolves with its URL on the placed
  port and its table's `port` empty.
- `settings.spec.js`: after a session made from the engine's sheet, the
  engine's state in the chat's foot (`could not start`) opens Settings on
  Engines, the `fake` sheet on Output, with what it printed.
