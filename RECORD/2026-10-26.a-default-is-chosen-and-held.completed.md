# A default is chosen, and held until its host is typed

Asked, in four messages over one evening:

> ```
> /Users/joshua/.config/luu/config.toml: [provider.AliOAi] is the default and https://token-plan.ap-southeast-1.maas.aliyuncs.com/compatible-mode/v1 is not this machine, so every run with no -p sends there. Add `remote = true` to say so, or name a local profile as the default.
> ```
>
> *¿problema de modelado de entidades? debería, en la medida de lo posible, migrar automáticamente*

> *quitamos el 'make default' del proveedor, lo define el modelo*

> *esta maquetación está mal* — a screenshot of the models column: the
> hover's ground running into the column's edge, the tool icons riding
> high — *y el click debería marcar por defecto, sin abrir la modal de
> configuración de proveedor*

> *¿a qué se debe esto?* — the first-run banner, *Nothing says where this
> machine sends. There is no provider in config.toml…*, over a file with
> providers in it.

## What it was

`check_default` was a load-time error. A file whose `default` pointed off the
machine without `remote = true` **did not load**. Every table in it went down
with it: the providers, the engines, the policies, the icon pack. `serve` would
not start on it, and a `serve` already running answered every Settings section
with the error, including the one that could have fixed it. So did a `remote =
true` on a default that was this machine. Every write was checked by the same
loader. The page relied on that refusal: a *make default* on a remote provider
was refused, and the refusal opened the provider's form with *default* ticked,
where the host was asked for.

How this file got there is not known. Every write the page makes goes through
`Config::write`, which loads its own text first, so the page could not have
written it. A hand edit, or a file from elsewhere, can. The record of
2026-09-07 meant exactly that case when it said *fails to load*.

## The question, answered

**Yes, it is a modelling problem, and not the one it looks like.** Two facts
were stored as one:

- **The default**: which provider a run that names none uses. It is a
  *choice*, and it changes often. Since this afternoon it is made by a click on
  a model.
- **The consent**: that this machine may send there without anybody typing
  the destination. That is `remote = true`, and it is the one thing the rule
  exists for. It is written by a person answering the machine's objection: the
  host, typed back.

The loader enforced the second by refusing the first, and a refused default
meant a refused *file*. A rule about one key failed the whole file.

**Migrating automatically, as far as possible**, is then two different answers:

- **`remote = true` on a default that is this machine** migrates by itself. The
  loader drops it, the next write leaves it out, and nobody is asked. No
  consent is given or taken by removing a word that was not true.
- **A remote default without `remote = true`** cannot be migrated by writing
  the word. Writing it would be the program consenting on the person's behalf,
  which is the promise local-first makes and this rule keeps. It is what the
  2026-09-07 record argued, and nothing in this ask argues with it. So what
  migrates is *everything else*. The file loads with that default **held**:
  - chosen, kept in the file, and written back as it is;
  - **not sent to** by any run that names nothing. `chat` and `stdio` with no
    `-p` refuse with the same message, at the moment they would have sent.
    `serve` starts on the mock and says why on its terminal. A new session
    with nothing named is the mock too;
  - named, it is typed: `-p AliOAi` and the chat's picker reach it as they
    always did;
  - and the page says so over the columns, *AliOAi is the default, and sends
    off this machine*, with a field for the host and *Confirm*. That writes
    `remote = true`, and from then on the default is a destination.

## What it is

- `Config` carries `held: Option<Held>` (the profile and its URL), worked out
  by `check_default`, which no longer fails. `usable_default()` is the default
  unless it is held. `resolve` refuses a held default when nothing is named.
  `resolve_holding`, used by `serve`'s start and by a new session with
  nothing named, resolves as though the file named no default.
- `Config::write` still loads its own text first. A held default is not one of
  the things it refuses, because that file loads. So the page **writes the
  choice and the consent separately**: a click on a remote provider's model
  writes `default` and that profile's `model`, and the default is held. The
  refusal that used to open the form is gone, and with it the form's
  `defaulting` prop and its declaration box.
- `GET /api/providers` has `held: { profile, host }`. `waiting` and the live
  session's following of the default use the usable default, so a held one
  neither moves the session nor reads as *waiting* for it.
- **The provider's *make default* is gone** from the columns' head. A default
  is always some model, and the click on it is the gesture. The mock's row
  keeps its *make default*: the mock has no models to click.
- **The first-run banner says why.** It was shown whenever the live session
  was on the mock because nobody chose (`unconfigured`). It said *There is no
  provider in config.toml* whether or not there was one. Now it reads *No
  provider is the default… click a model below* when the file has providers
  and none is the default, keeps the old sentence when it has none, and is not
  shown while a default is held, since that line says why on its own.
- **The models column is on the providers column's grid.** Rows are inset
  .5rem and padded .5rem, with rounded corners. `align-items: center` puts the
  tool icon on the name's line, where `flex-start` had left it riding high.
  `.models-head` reaches both edges for its rule and starts its text 1rem in,
  where the names do.

## Rejected

- **Writing `remote = true` on load.** It is the migration the question asked
  for, and the one thing that cannot be migrated: the word would no longer
  mean that anyone typed anything.
- **A checkbox, *this default is remote*, ticked by the click.** It is the same
  thing with a step a person learns to skip. The typed host is what makes it
  an answer.
- **Keeping the load-time refusal and making the page tolerate it.** The page
  is not the only reader. `serve` would still not start, and an engine or a
  policy edited while the file did not load would be written over a file read
  as empty (`put_providers` falls back to `Config::default()` when the file
  will not load). That last part is still true for every other way a file can
  fail to load. See *Still open*.

## Tested

- `provider.rs`: a remote default without the word loads held, the rest of the
  file with it; no `-p` refuses with the old message; `-p` reaches it;
  `resolve_holding` is the mock and `unconfigured`. A local default's `remote =
  true` is dropped and not rendered. A remote default is *written* held, and
  carried through a write about an engine, still held. A write that would not
  load still replaces nothing, shown now with a default naming no profile. 27
  passed.
- `settings.spec.js`, 21 passed. A new test clicks a model of a provider at
  `models.example.invalid`: no form opens, `default` is written, `remote` is
  not, the live session stays on the mock, the held line names the host,
  *Confirm* stays disabled until the host is typed and then writes `remote =
  true`. Also: the banner's *No provider is the default*, and no *make
  default* in the head.

## Still open

- `put_providers` and the other section writers read a file that will not
  load as `Config::default()` and write over it. With the hold, the case that
  produced one in practice no longer does. A TOML syntax error still would, and
  a save from the page would then drop every table it does not write.
- Consent is per profile, not per host: an edit that moves a declared remote
  default to another host keeps `remote = true`. That was true before this
  change too.

## 2026-10-26, later — a server that lists no models

*¿por qué en Settings > Models para
'https://token-plan.ap-southeast-1.maas.aliyuncs.com/apps/anthropic' sale 'use
it with its own model'? mientras que en el Chat sale bien el listado*

**Both ask the same route**, `GET /api/providers/{name}/models`, through the
same component, and both mount it afresh each time it is opened. A stand-in
anthropic server under `/apps/anthropic` with a listing was drawn identically
in both, three requests in all. *use it with its own model* is what the
columns offer when that route answers an empty list with no reason. The
anthropic backend gives exactly that for a **404** on `<url>/v1/models`, which
`listing()` reads as *lists nothing* on purpose. So the difference was in what
the endpoint answered at the moment each view asked, not between the views.
The endpoint itself is not reachable from here, so this is the reading of the
code and of the stand-in, not a measurement of Alibaba's server.

What changed because of it:

- **An empty list says so.** *<name> lists no models*, with *: type one
  below* where a model can be typed, instead of a lone *use it with its own
  model*.
- **Settings → Models takes a typed model** (`typable`, as the new session's
  dialog already did). Enter makes it, and its provider, the default, exactly
  as a click on a listed model does.
- **The profile's own model is drawn as the list is drawn**, not when the list
  arrived. It used to be prepended once, at load, so a model chosen since was
  not in the column until the component was mounted again.

Tested: `settings.spec.js`, 22 passed. A provider on a server that answers 404
to everything shows *unlisted lists no models: type one below*. `typed-1`,
typed and entered, writes `default = "unlisted"` and `model = "typed-1"` and
is drawn chosen at once. The test's cleanup runs in `finally`, because one
that leaked a default broke four tests after it on the first try.

## 2026-10-26, later still — no default per provider, in the form either

*por qué en .head-acts .said, sale el nombre de un modelo, habíamos acordado
que no hay default por provider, el default es para luu*

It said the profile's `model`, beside the URL and the window. That reads as
*this provider's default*, which is the thing that went with *make default*.
Two places still said it:

- **The head over the models** says where the provider is (its URL, its
  window) and no model. luu's default is the ✓ in the columns.
- **The provider form's *Models* tab** had a radio per model, under *The
  default is what a new session here starts on*. It is gone. The form carries
  the profile's `model` as the file has it, chooses none for a new provider,
  and its placeholders describe that model, or the first listed.

The key itself stays, with two readings that are both luu's and neither
the provider's: the model luu's default sends to when this profile is the
default (what a click in the columns writes), and the model `-p <name>`
starts on with no `-m`.

Tested: a provider added through the form is written with no `model`; its
edit lists `tiny` and `tiny-q4` with no radio; a click on `tiny-q4` in the
columns writes `model = "tiny-q4"`, draws the ✓, and the head does not name
it. The anthropic test's max-tokens check now reads against the first listed
model (`claude-opus-5-5`'s 128000), and the profile it writes has no `model`.
