# More than one call in a reply

Found from the page, on the native transport: a turn whose first `list_dir`
card said *done* and whose second said *not run*, in the same reply. Nothing
was refusing — the reply simply carried two calls, and the loop runs one.

## The problem

**A server answers a request with a *list* of calls.** That is the OpenAI
API's shape (`delta.tool_calls[]`, by `index`) and Anthropic's (`tool_use`
blocks in one message), and llama.cpp and vLLM emit both when a model asks for
two things at once. luu re-renders every call in that list back into the
reply's text as a ```` ```tool ```` fence — `openai.rs` streams
`native::fence` per call after the reply is over, which is what lets
`parse_call` find calls "where it finds every other call" and keeps one
history shape across the two transports (`native.rs`'s module note).

**And the loop executes exactly one of them.** `run_agent_turn` asks
`parse_call` of the step's text (`agent.rs`), which returns the *first* call
it finds; executes it; pushes the assistant text and the one result; and calls
the model again. The remaining fences are in the history verbatim, were never
run, and the page — which pairs fences with executed calls in step order
(`segments.js`) — draws the leftovers as *not run*.

The fenced transport has the same hole, quietly: a 7B that writes two fences
in one reply gets one call run. The preamble asks for one call and the
`ContinuedPastFence` verdict treats text after a call as the model writing its
own result, so two fences are drift — but drift that today silently strands a
call the model meant.

So the bug is not that a call was denied, refused or lost to the sandbox —
those all have a record and say so. It is that **what the model asked for is
not what the loop does**, with nothing between them saying no.

## The proposal

**A step runs every call its reply carries, in the order the model wrote
them.**

- `tools::parse_calls(text) -> Vec<ToolCall>` — every fenced or bare call
  outside the thinking, in text order, reusing the scan `split_call` already
  has. `parse_call` becomes its first, and `split_calls` returns prose plus
  the list, so the native history rebuild sees all of them.
- The loop executes the list sequentially inside the one step: for each call,
  the `ToolCall` event, the sandbox check, the escalation and its question if
  it comes to one, `run_call`, the `ToolResult`. Sequential, not parallel: a
  second call is usually written *after* the first in the order a model needs
  its answer in, the tools are in-process and cheap, and `run_command`'s
  limits are per-child anyway.
- The history stays the invariant it is — the assistant message once, verbatim
  with all its fences, then **one user result per call**, in order. This is
  why the calls are run inside the step and not left to re-emerge on the next
  one: re-asking the model to repeat a call it already made spends a full
  model call and a full window to say what the loop already knows.
- `native::messages` pairs one assistant message carrying N calls with the N
  user messages that follow, each opening with its own `[name]`, into one
  assistant `tool_calls[N]` and N `tool` messages. The identity check is
  unchanged — the result has to open with the call's name — it just repeats.
- **The wire keys a call by `(step, index)`.** `index` is an optional field
  on `tool_call`, `tool_result`, the held question and `answer_call`, default
  to absent meaning the one call of a step that is every step today. Optional
  fields do not bump: the protocol stays v3 and the record format stays 5, by
  the rule that closed the exit-code rung.
- `--max-tool-steps` counts *executed calls*, which is what `AGENTS.md`
  already says it caps; a step that carries three spends three.
- The page: `store.js` keys `state.tools` by `(step, index)`, `segments.js`
  sorts calls by `(step, index)` before pairing fences, and the held-question
  key gains the index. A reply whose second call is answered at the gate is
  asked one at a time, since the loop awaits each answer inline.

## What it costs

`agent.rs`'s loop body moves inside a `for call in calls`; `tools/mod.rs`
grows the plural scan; `native.rs` grows the plural pairing; the protocol
gains one optional field on four messages; `store.js`, `segments.js` and the
tool card's `held` key gain the index. The tests that key by step and must now
key by `(step, index)`: `serve_ws.rs` over the gate, `agent.rs`'s own fixture
drives, and the smoke specs that answer a question. `ollama_wire.rs` does not
move — it asserts what goes *out*, and nothing out changes except a history
that can now hold two results for one message.

## Rejected, and why

- **Re-asking the model** (today's accidental behaviour): a model call and a
  window of tokens to have it repeat a call that is already sitting in its own
  history, and meanwhile the page shows a call the model made as *not run*.
- **Parallel execution**: calls are written in a dependency order more often
  than not, the escalation question would have to be asked of two calls at
  once, and there is nothing here that gets faster — the tools are this
  process, and a container pipe is one pipe.
- **Duplicating the assistant message per queued call**: it would reuse the
  one-call machinery, but `ToolStep.text` is verbatim-by-commitment — a
  history that replays a reply twice is a different prompt, and the prefix
  rule says so. It also does not avoid the `(step, index)` keying.
- **Truncating the reply at its first fence**: throwing away what the model
  asked for because the loop cannot hold it.

## Still open

- **The Anthropic half.** `openai.rs` re-renders every streamed call; read
  `anthropic.rs` and confirm it folds all `tool_use` blocks the same way, and
  that a signed thinking block survives being sent back beside an assistant
  message carrying two calls — the byte-identical-prefix rule is about the
  prefix, but this is the first history shape where one message ends with more
  than one call.
- **How often it happens.** The change is justified by the API's shape, not
  by a count; but the count belongs in `RECORD/` before the roadmap row is
  called done — a run of the grounded scripts under `--tool-calls native` with
  the recording's tool cards counted per step tells us whether this is a
  common reply or a rare one, and that decides whether the planning prompt
  should mention the possibility at all.
- **`score_call`'s `ContinuedPastFence`** scores one call per prompt and reads
  anything after the first fence as the model writing its own result. With the
  loop running every fence, the probe's four-way verdict stays as it is — a
  second fence is still drift worth counting — and this record is neutral on
  changing it.

## Built — 2026-10-25

The loop runs the list. What landed, and what the open questions turned out to
be.

**`tools::parse_calls` and `tools::split_calls`** scan every call outside the
thinking, in text order, and the scan is `first_call` repeated after each call's
end — so the first of the list is exactly the one `parse_call` always found,
under its fence-before-bare precedence, and a single-call reply moves by
nothing. `bare_object_span` now reports where the object ends, which is what
lets the scan carry on after it.

**`run_agent_turn`** pushes the assistant message once — the reply verbatim,
fences and all — and then runs each call, pushing one user result after it. The
budget counts executed calls (`steps.len()` against `max_steps`), which is what
`--max-tool-steps` always said it capped, and a reply that spends it mid-list
ends the turn on `ToolLimit` with the remaining fence left where the page can
say *not run* — the same shape as a cancelled turn, not a new one.

**The key is `(step, index)`, added as an optional field.** `index` is on
`ToolStep`, `ToolCallView`, and the four protocol messages that name a call
(`tool_call`, `call_held`, `tool_result`, `answer_call`), and on `granted` /
`forbidden` for the stream. Absent is 1, and the wire omits 1 — so a single-call
reply streams the bytes it streamed before, the protocol stays where it is, and
the record format stays at 5. `serve.rs` holds a question by `(turn, step,
index)` and answers the one it names.

**`native::messages`** pairs one assistant message carrying N calls with the N
results that follow, each opening with its own `[name]`, into one `tool_calls`
list and N tool messages; one unanswered call sends the whole exchange up as
text, the way a half-written step did before. The page sorts a turn's calls by
`(step, index)` before pairing fences, and keys the held question and every
`:key` by the pair.

### The open questions, answered

- **The Anthropic half resolves to: nothing to do.** `anthropic.rs` already
  folds *every* `tool_use` block into a fence (`for block in &blocks`), so a
  server that streamed two would hand both to the loop. And it asks for one:
  `tool_choice` carries `disable_parallel_tool_use: true`, so its native path
  never produces a second call to run. Its history render pairs a single call
  with its `tool_result` and leaves anything else as text — which is right for
  the only multi-call reply it can receive, a fenced-drift one where the second
  block is the model writing its own result rather than a call the server
  parsed. The signed-thinking replay keys off the reply text as it was, and that
  text is unchanged; this is the first history shape where one message ends with
  more than one call, and on this backend it cannot.
- **The count is the one thing still owed.** The change is justified by the
  API's shape and the *not run* card it produced, not by a frequency; a run of
  the grounded scripts under `--tool-calls native` with the recording's tool
  cards counted per step is what says whether to mention parallel calls in the
  planning prompt at all. That run is the roadmap row's own evidence, and the
  row stays until it is made.
- **`ContinuedPastFence` stays as it is**, as decided above: a second fence is
  still drift worth counting, and the probe scores one call per prompt.

Tests: two fences run in order and key `(1,1)` `(1,2)`; a three-call reply under
a budget of two spends two and ends on `ToolLimit`; the native rebuild makes one
`tool_calls[2]` and two tool messages; the fold makes two views of one step and
answers each result its own call; a call drafted in the thinking is still not in
the list; and a stored two-call turn renders one assistant message and two
results.

## Appended the same day — the first of the list is now the earliest

This record said the scan's first call is exactly the one `parse_call` always
found, "under its fence-before-bare precedence". That precedence is gone: the
scan now takes the earliest of the three forms, because a fence later in a
reply was stepping over the `<tool_call>` blocks before it and leaving them
unexecuted. See
[`the-transport-a-run-resolves`](2026-10-25.the-transport-a-run-resolves.completed.md)
§*Same day — the mixed reply*. A single-call reply is unaffected; a reply that
quotes a call in prose before a fence now runs both, which is the same rule as
running every call a reply carries.
