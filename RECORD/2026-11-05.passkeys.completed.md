# Passkeys

> adelante con el paso 4

Step 4 of [`users-and-a-code-by-email`](2026-11-03.users-and-a-code-by-email.WIP.md):
**passkeys, and first whether WebAuthn can be had without OpenSSL.**

## The question it started with: OpenSSL

`a-public-luu` and the users record both carried *`webauthn-rs` links
OpenSSL, and this tree is rustls throughout*. That was true of 0.5.

**It is not true of 0.6.2** (released 2026-10-31): `webauthn-rs-core` moved
to `crypto-glue`, Kanidm's facade over RustCrypto (`p256`, `p384`, `rsa`,
`ed25519`), and nothing in its tree links OpenSSL or native-tls. Measured
here: added with `conditional-ui`, `cargo tree -p luu -e normal | grep -i
openssl` is empty, it builds, and it adds 45 crates to `Cargo.lock`.

The other candidate was `webauthn_rp` (RustCrypto as well, one maintainer,
no OpenSSL either). And the third was writing the relying party here, on
the `p256` and `ed25519-dalek` already in the tree for SSH links, with
attestation `none`. Rejected below.

## The proposal

What the users record said, built with `webauthn-rs` 0.6.2:

- **After a login with a code**, the page offers to add a passkey for this
  device: *Add a passkey* or *Not now*, before it reloads.
- **The login page offers the passkey first**, with no email: *Log in with a
  passkey*, a discoverable credential, so the authenticator says who. The
  email and the code stay under it. **The code is how one gets back in**: a
  lost device costs one email, not an account.
- **General → Account lists the passkeys**, with *Add a passkey*, and each
  one renamed or removed.

```text
POST /api/auth/passkey/start                 {ceremony, options}     outside the gate
POST /api/auth/passkey/finish {ceremony, credential}  → 204 + the cookie
GET    /api/account/passkeys                 {passkeys}
POST   /api/account/passkeys/start           options                behind the login
POST   /api/account/passkeys/finish {name, credential}
PUT    /api/account/passkeys/{id} {name}
DELETE /api/account/passkeys/{id}
```

- The relying party is the server's `origin`: its host is the RP id, and
  the origin itself the only one accepted. A server with users already
  refuses to start without one.
- **Ceremony state stays in memory**, five minutes, at most a thousand
  waiting logins: one replica, and webauthn-rs keeps its state types
  unserialisable unless a feature named `danger-` says otherwise.
- **A passkey is a row in `auth.db`** (`passkeys`, schema 4 with the user
  removal of the same day): the credential id, the user, a name, webauthn-rs's
  `Passkey` as JSON, when it was added and last used. Its counter is updated
  on every login.
- **A passkey login is a login**: the same cookie, refused to a suspended
  user, and clearing a pending removal as a code does.
- **The user handle** is the user's id, padded to a UUID: twelve hex
  characters are six bytes, the rest zeros. It is checked against the row the
  credential id finds, never trusted on its own.
- Every POST is held to `Origin` as every write is; the login ones are
  outside the gate like `/api/auth/login`.

## What it costs

- **45 crates** in the lock file, RustCrypto's and webauthn-rs's own, and
  MPL-2.0 for `webauthn-rs` itself: file-level, and luu does not modify it.
- **A table**, and seven routes.
- **The page converts base64url to and from `ArrayBuffer`**: a few lines,
  because the browsers' own `parseCreationOptionsFromJSON` is not
  everywhere yet.

## Rejected

- **Writing the relying party here.** It is a hundred lines of CBOR and
  signature checks, every one of which is a way to accept a forged login;
  a maintained library audited by Kanidm's use is the better bet.
- **`webauthn_rp`**: as correct on paper, one maintainer, and its API asks
  for more type plumbing for the same three ceremonies.
- **Passkeys instead of codes**: the code is the recovery, as decided.
- **Attestation**: who made the authenticator is not a question luu asks.

## Still open

- **Whether a passkey login signs approvals**, carried over again.
- **Conditional UI** (the passkey offered in the email field's autofill):
  the feature is on in the crate and not used by the page yet.

## Built, the same day

As proposed. `crate::passkeys` holds the ceremonies; `users` holds the
passkeys (schema 4, shared with the removal); `serve` has the seven routes;
the page has the passkey first on the login, the offer after a code, and the
list in General.

**Found while building it:**
- `webauthn-rs`'s `start_passkey_registration` asks for **no** resident key,
  and a login with no email needs one. The options are rewritten as JSON
  before they leave (`residentKey: required`), because the type that says it
  is in `webauthn-rs-proto`, which the prelude does not re-export.
- `finish_discoverable_authentication` is deprecated in 0.6 for `_v2`, which
  takes the one passkey the credential id found.
- **A passkey login clears a pending removal**, as a code's does: it is a
  login, and the removal record says a login keeps them.

**Verified:**
- `passkeys::tests`: the user handle is the id padded, two ids two handles;
  the relying party is the origin; a login starts with no email.
- **Chromium with a virtual authenticator** (CDP `WebAuthn`), against a
  public server on `http://localhost:7979`:
  - after a code, *Add a passkey* registers one, resident, named *Chrome on
    Mac*, and the page goes into the app;
  - the server's login ceremony, answered by that authenticator, logs in
    (`204`, the cookie, `me` the owner), and the passkey's `last_used` is
    set;
  - the same answer sent again is refused (`401`): the ceremony is spent.

**Not verified: the discoverable get itself, in this browser.** Chromium's
virtual authenticator refuses a `get` with no `allowCredentials` here
(`NotAllowedError`) even for a credential made a line earlier with no server
involved, while the same credential listed by id signs. So the login above
was answered with the credential listed, which the server does not see: its
verification is the discoverable one either way. A real authenticator on a
real page is what is left.
