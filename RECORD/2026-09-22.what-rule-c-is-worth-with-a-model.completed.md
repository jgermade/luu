## A binary correction, first

Every arm in this file ran on `luu` rebuilt from `HEAD` (2026-09-22). Every arm in
`8k-against-96k-on-the-m4-pro`, written earlier the same day, ran on a `target/debug/luu`
dated 2026-09-14 — eight days stale, predating `[resend]` landing in `config.toml`
entirely, which is what this file needed rebuilt to reach `Results::CitedReads` at all
(`--prune-results` only ever sets `Cited`; `CitedReads` is reachable from `config.toml`
and the page, not from a flag — see `crates/luu/src/lib.rs` around `still means
Results::Cited now that there are three values`). One flag the earlier file's own
methodology names but did not catch: the runs it compares were not one *binary* apart
from each other, only stale from today's `HEAD` uniformly, so nothing within that file's
own arms is miscalibrated by it. Noted here because rebuilding surfaced a difference
worth flagging rather than because it changes that file's reading of its own arms — see
*A wrinkle, not chased* below.

## The run

`long-session.txt`, `--context-limit 8192 --reserve 512 --temperature 0 --seed 1
--prune-behind`, three arms differing in exactly `results`: `kept` (no flag, no config —
the code default), `cited-reads` (`LUU_HOME` pointed at a scratch state directory whose
`config.toml` sets `[resend] results = "cited_reads"`, since no CLI flag reaches it), and
`cited` (`--prune-results`, which the previous file already established means `Cited`).

## What it confirms mechanically

`could_be_read_again` in `crates/agent-core/src/context.rs` is exactly `read_file` and
`list_dir`; everything else, `run_command` included, is kept under `CitedReads`. Counting
every `— N tokens, pruned` citation line sent over the whole session, by tool:

| | `kept` | `cited-reads` | `cited` |
| --- | ---: | ---: | ---: |
| `evicted` events | 2 | 0 | 0 |
| `pruned` events (turns actually pruned) | 0 (1 fired empty) | 4 | 4 |
| `[read_file]` citations sent | 0 | 415 | 389 |
| `[list_dir]` citations sent | 0 | 125 | 125 |
| `[run_command]` citations sent | 0 | **0** | **77** |
| turns answered (`[stop]`) | 1 of 6 | 1 of 6 | 1 of 6 |

`cited-reads` cites reads and never once cites a command's output across the whole
session; `cited` cites the same reads and 77 lines of `run_command` output beside them.
The code's own distinction is not aspirational — it is what the wire carries.

## Whether a model minds

**Not measurably, on this corpus.** All three arms answer 1 of 6 turns, and the five that
end at the tool-step limit are the same shape in all three: the model explores, calling
`list_dir`, `run_command` (`grep`/`rg`/`git grep`) and `read_file` on
`crates/agent-core/src/context.rs`, and runs out of steps before concluding. Keeping
`run_command`'s output whole (`cited-reads`) against citing it too (`cited`) changes
**zero** answered turns.

The reason is in what this corpus's commands return. Every `run_command` call here is a
search that comes back empty — `grep`, `rg` and `git grep` for strings the model itself
picked, none of which match anything, because the questions are answerable from the file
and not from a search over it. An empty result is a fact worth almost nothing either
kept or cited, which is the opposite of the case
[`what-rule-c-is-worth`](2026-09-14.what-rule-c-is-worth.completed.md) named: *"a citation
where `cargo test` output stood is a stronger claim… because the output is evidence and a
job's closing condition reads exit codes from `ToolStep`, not from the prompt."* This
corpus never puts a model in the position of needing to recall what a command found —
only what a file said — so `cited-reads` and `cited` land in the same place by
construction, and **item 5's real case is still unmeasured**: no run in this repository has
yet put a model's answer at stake on a command's *result*, as opposed to a file's bytes.

The turn that does show a difference is the last one, and it separates `kept` from
**both** cited arms rather than separating the two cited arms from each other:

- **`kept`:** *"Eviction always cuts from the front… `Repeat::Once` renders a repeated
  code span only in the oldest turn that carries it, and `Prune::Behind` makes old turns
  give up their code… before they are evicted whole."* Three correct, specific claims,
  matching the file.
- **`cited-reads`:** *"Every `read_file` result came back pruned, so I never actually saw
  the code — I have no verified implementation details to summarise."*
- **`cited`:** *"every tool output came back pruned, so I never actually saw the
  code… I can't honestly summarise the implementation details."*

Both cited arms refuse rather than confabulate, which is the good failure mode
[`8k-against-96k-on-the-m4-pro`](2026-09-22.8k-against-96k-on-the-m4-pro.completed.md)'s
managed arm already showed once. What is new here is that **the citation that costs the
answer is `read_file`'s, and `cited-reads` does not spare it** — the file's own bytes are
the evidence this corpus's questions need, and pruning those is enough to lose the
summary whether or not `run_command`'s empty greps go with them.

## A wrinkle, not chased

`kept`'s last turn answers with 5 458 prompt tokens and evicts only twice (`[1,2]` then
`[3,4]`, turn 5 surviving); the equivalent arm in `8k-against-96k-on-the-m4-pro`
(`--prune-behind` alone, no `results`, stale binary) evicted three times and answered
turn 6 from 519 tokens — the system prompt alone, nothing of the conversation. Both ran
`--temperature 0 --seed 1`. Turn 1 already differs between the two in prompt-token
count (6 579 here against 6 636 there), which is the same multi-slot prefix-reuse
nondeterminism `8k-against-96k-on-the-m4-pro` §*third section* already found — a pinned
seed fixes the sampler, not the batch a shared four-slot server composes it with, and
this machine ran every arm of both files against slots that had already served other
requests. **Not attributed to the rebuild**, because that explanation requires no new
mechanism where one already measured suffices; also not ruled out, because the two runs
were never made one variable apart from each other on purpose. Whichever it is, it is
outside what this file was run to answer and is left as found rather than chased into a
fourth arm.
