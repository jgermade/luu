# A key typed into the form

The provider modal writes every field of a profile except the one a hosted
endpoint will not answer without. `Key file` takes a path, so adding a provider
from the browser is six fields in the page and then a seventh somewhere else:

```sh
mkdir -p ~/.luu && umask 077 && printf '%s' 'sk-…' > ~/.luu/minimax.key
```

A person who came to Settings to avoid `config.toml` is sent back to a terminal
anyway, and the one step that is easy to get wrong — the mode — is the step the
page cannot help with. `luu` then refuses to send, correctly, with a message
about `0644` that arrives at the end rather than at the field.

## The decision this argues with

[`luu-design.md`](../luu-design.md) says it in bold:

> **The key is a path, never a value, and its mode is checked.**

and [`2026-09-07.naming-a-provider.completed.md`](2026-09-07.naming-a-provider.completed.md)
gives the two reasons under it:

> - **No `key = "sk-…"`.** A key in a config file is a key in every backup, every
>   screen share and every `cat ~/.luu/config.toml` in a bug report. A path is not.
> - **No environment variable, including `OPENAI_API_KEY`.** […] an env var is
>   inherited by every child this process spawns — and spawning children is what
>   this process does.

**Both are about where the key rests. Neither is about how it arrives.** That
distinction was never drawn, because at the time there was one way in and it was
a text editor. The commitment the two bullets defend is *the key is not in
`config.toml` and not in the environment*, and nothing in this proposal puts it
in either. What moves is the typing, not the resting place.

So this is not a reversal. It is the first time the question has been asked.

## The proposal

The modal's key control takes **either** a path (what it takes today) **or** the
key itself. When a value is typed, the server writes it to a file and puts that
file's path in `config.toml`. The file is created `0600`, the way
[`run_token`](../crates/luu/src/lib.rs#L1078) creates the bearer token — *with*
that mode rather than chmod'd into it afterwards, so there is no moment it is
anything else.

What ends up on disk is byte-for-byte what a person typing the three shell
commands would have produced. `config.toml` still holds a path. `check_mode`
still runs on every read and now never fires, because the writer and the checker
finally agree.

### The secret does not go on `Profile`

`Profile` is serialized **twice**: into `config.toml`, and into `ProvidersView`,
which is the JSON `GET /api/providers` hands the page. A field on it would do
both — the key would land in the config file this exists to keep it out of, *and*
be served back to the browser on every settings load. That second one is the
worse of the two and the easier to miss, since nothing would look wrong.

So the value arrives on `ProvidersEdit` instead, which is the inbound type and
has no outbound twin:

```rust
struct ProvidersEdit {
    default: Option<String>,
    providers: BTreeMap<String, Profile>,
    /// Provider name → the key as typed. Deserialize-only, and there is no
    /// field anywhere that sends one back.
    keys: BTreeMap<String, Secret>,
}
```

**It is write-only, and that is a property of the types rather than of the
handlers remembering.** The page learns that a key is set from the `key-file`
path it already receives, never from its contents.

### Order, and what a failure leaves

The key file is written **before** `config.toml`. A config that points at a file
that is not there is a run that dies at its first send; a key file nobody points
at is a file nobody reads. If the config write then fails — a remote default that
has not declared itself is the likely one — an orphan `0600` file is left behind.
That is the right way round, and it is named rather than cleaned up: deleting a
file that may hold the only copy of a credential, because a *different* write was
refused, is worse than leaving it.

### Where it goes

`<state dir>/<name>.key`, beside `config.toml`, unless the path field says
otherwise — in which case that path, so somebody who already has a key file
still points at it instead of retyping the secret to adopt it.

## What it costs

- **A secret now travels in an HTTP body.** Loopback only, because this is the
  same route `providers_editable` already refuses off it, and
  [`log.rs`](../crates/luu/src/log.rs#L123-L124) records the method and the path
  and *"never the query […] and never a body"* — so it is not written down. It
  is still in the browser's memory and in devtools' network tab, which is more
  exposure than a terminal with `umask 077` and strictly less than a key pasted
  into a config file. The field is `type="password"` so it is not on screen, and
  that is the whole of the mitigation.
- **`luu` creates files it did not create before**, in a directory whose virtue
  was that its existence was the only thing it said.
- **Removing a provider does not remove its key file.** Two profiles can name
  one, and a credential is not ours to delete on the way past. An orphan `.key`
  is the cost of that, and it is the same one the paragraph above accepts.
- **One more thing that can be wrong on a machine without a state directory.**
  There is nowhere to put the file, and the route already answers that case for
  `config.toml` with a 409; the key write joins it rather than inventing a
  second message.

## What was rejected

| | |
| --- | --- |
| `key = "sk-…"` in `config.toml` | The 2026-09-07 decision, untouched. Every backup, every screen share, every `cat` in a bug report. |
| `OPENAI_API_KEY` | Also untouched, and this proposal does not weaken its reason: there is still no `env_clear` in the tree, so a key in the environment is still handed to every `cargo` and `git` the model asks for. |
| Keychain / secret-service | A different dependency per platform, and the thing `check_mode` verifies has no equivalent to check there. A file is the only one of the shapes whose exposure the program can read back. |
| Generating the file from a `luu` subcommand the page shells out to | The page would be driving a terminal to avoid admitting it writes a file. It writes a file. |

## Still open

- **Whether the modal should offer to `chmod` a path it was given.** Pointing at
  an existing `0644` key is still a run that fails later with a message about a
  mode. The form could say so at the field, where it would be useful, but
  fixing somebody's permissions from a browser is a different kind of act from
  writing a file the browser was told to write.
- **Nothing verifies the key before it is saved.** `GET /api/providers/{name}/models`
  would answer that in one call, and it is the obvious next thing — a key saved
  and a key that works are not the same fact, and the form currently claims the
  first while a person reads it as the second.

## Showing part of the key, without keeping part of the key

*Appended the same day.*

A box that is empty whether or not a key is set cannot be told apart from a box
whose key was never saved. The obvious fix is to keep the first characters and
the last ones beside the path, and show `sk-…WXYZ`.

**Refused, and replaced with the same display derived instead of stored.** Two
ends of a key in `config.toml` are two ends of a key in every backup and every
`cat` of it. That is the 2026-09-07 bullet again at a smaller quantity, and the
quantity is not the part that was being argued. It would also *lie*: a fragment
written on Tuesday still reads `sk-…WXYZ` after somebody replaces the file by
hand on Wednesday, and the page would be reporting a key that is no longer
there.

So `secret::preview` reads the file where it is, on every `GET /api/providers`,
and returns what may be said about it:

```rust
pub struct Preview {
    /// `sk-…cdef`, or `None` for a key too short to show any of without
    /// showing most of it.
    pub mask: Option<String>,
    pub problem: Option<String>,
}
```

Three characters at the front, because on these keys that is a public vendor
prefix; four at the back, because that is what a person recognises their own key
by; and **nothing at all below twelve**, where the two ends are the key. It
costs one small read on a settings load, which is what one send already costs,
and it cannot drift because there is nothing to drift from.

`problem` is the other half and it closes the first of the open threads above:
the mode is checked *at the field*, where the answer is `chmod 600`, instead of
at the first send, where the answer arrives as a failed run. A missing file
reports itself the same way.
