# A mock that calls a tool every turn

**Status:** WIP — a proposal and the code it plans. Roadmap item **3b** of
[`ROADMAP/2026-09-09`](../ROADMAP/2026-09-09/README.md), and the instrument
item **4** waits on: *built once, it unblocks a measurement and a probe at
once*, which is the only reason it is a record of its own rather than two lines
inside either.

It exists because [`what-a-result-costs`](2026-09-09.what-a-result-costs.completed.md)
ended on a discovery rather than on a number:

> `--mock-reply` is consumed one per model *call* with the last repeating, so a
> twenty-turn script on the mock calls a tool exactly once and the grounded
> corpus — the one both earlier rules were measured on — has no tool output in
> it at all.

## The problem

The mock hands back one reply per call and repeats the last once the list runs
out ([`backend/mock.rs`](../crates/agent-core/src/backend/mock.rs)):

```rust
match replies.len() > 1 {
    true => replies.pop_front().unwrap_or_default(),
    false => replies.front().cloned().unwrap_or_default(),
}
```

That is exactly right for what it was built for — *a scripted call, then the
answer to its result* — and exactly wrong for a corpus. Over twenty prompts:

```text
turn 1   call 1  ```tool {"name":"read_file",…}```   ← the list's first reply
         call 2  "it says two things"                ← the list's last reply
turn 2   call 1  "it says two things"                ← and from here, forever
turn 3   call 1  "it says two things"
…
```

One tool call in the whole run. So the two rules that reach a tool result —
rule C (`--prune-results`, landed 2026-09-09) and whatever comes after it — can
be *tested*, which they are, and cannot be *run*, which they have not been.
Rule C is a rule built without a number, which is precisely the shape item 1 has
been at the top of two revisions to warn about.

The tool-call probe of item 4 has the same hole from the other side: its harness
scores *parsed / drifted / no call / continued past the fence* per prompt, and
with nothing on this machine able to emit a call per turn, the scorer itself
cannot be exercised before a box with a model is in front of it.

## The proposal

### 1. The list cycles; the last stops repeating

One field on the mock and one builder: `Mock::replies(…).cycling()` rotates the
deque instead of holding the last reply. Two replies — a call, then the answer
to its result — become *one turn's worth of calls*, repeated for as long as the
script runs.

```text
turn 1   call 1  ```tool {… context.rs …}```     turn 2   call 1  ```tool {… job.rs …}```
         call 2  "it opens with two commitments"           call 2  "three things"
```

**Alignment is the whole mechanism, and it is arithmetic rather than luck.** A
turn costs `1 + (the calls it made)` model calls — [`run_agent_turn`](../crates/agent-core/src/agent.rs)
loops until a reply parses as no call — and a *scripted* run makes no planning
call, because [a script carries its plan](../crates/luu/src/lib.rs). So a list
whose length is a multiple of the calls-per-turn stays in phase for the whole
run, and a list of `2 × n` blocks is `n` turns of tool-then-answer, cycling.

Default behaviour does not change: without `.cycling()` the last reply repeats,
which is what `make smoke`, the gate spec and every existing test are written
against.

### 2. The replies come from a file: `--mock-script <path>`

A reply that contains a ```` ```tool ```` block is four lines of JSON, and four
of them on a command line is a run nobody can reproduce from a README. The file
is the project's own script idiom, one directive:

```text
# what the mock answers on the grounded corpus, two blocks per turn.
## reply
looking at the head of the module
```tool
{"name":"read_file","arguments":{"path":"crates/agent-core/src/context.rs","max_lines":120}}
```
## reply
It opens with two commitments: decide then render, and a stable prefix.
```

Everything before the first `## reply` is the file's own comment header — every
other file in `scripts/` has one and this one needs it more than most, because
what it is is *the model's half of a recording*. `--mock-script` implies
cycling, and giving both it and `--mock-reply` is an error rather than a merge:
two lists of replies and no way to say which is the phase.

### 3. The corpus is the one already measured

Not a new script of prompts. `scripts/tasks/grounded.txt` is what rules A and B
were both measured on, it opens no job — so the session's own policy grants the
tree and every call is allowed without a plan narrowing it — and the mock's half
lives beside it in `scripts/mock/grounded-tools.txt`. The rule-C run is then the
rule-B run with one file added to the command, which is what makes the two
comparable at all.

```sh
luu chat --script scripts/tasks/grounded.txt \
  --mock-script scripts/mock/grounded-tools.txt \
  --select-tokens 1024 --context-limit 8192 --mock-delay-ms 0 \
  [--prune-behind] [--prune-results] --record <arm>.jsonl
```

## What it costs

- **Phase is fragile by construction.** A turn that makes one call fewer than
  the list expects shifts every later turn by one, and the mock cannot notice:
  it is handed a prompt, not a turn. The cost is bounded by being *visible* —
  a drifted run has turns with no `ToolStep` in the recording, and the run's
  own README reads the step count per turn before it reads anything else.
- **The mock learns a second mode.** Two behaviours in one backend is worse
  than one, and the alternative was worse still: see below.
- **Nothing here is a model.** The same sentence every run on the mock ends on.
  This buys the *window's* half of rule C — how much smaller the prompt is, and
  what it is made of — and says nothing about whether a model minds a citation
  where `cargo test` output stood.

## What was rejected

- **Teaching the mock where a turn begins** — a `reset()` the loop calls, or a
  turn number on `CompletionRequest`. It is the accurate fix for the phase
  problem and it pays for it by putting *the concept of a turn* into the
  `Backend` trait, which today knows about a prompt and a stream and nothing
  else. Every real backend would carry a field only the mock reads.
- **`## reply:` directives inside the task script.** Tempting — one file, no
  second flag — and wrong: `grounded.txt` is run against real models, and a
  corpus that carries the model's half is not a corpus. The two halves are
  separate files because only one of them is the experiment.
- **Making `--mock-reply` cycle by default.** It would silently change what the
  gate demo, the smoke test and `serve --mock-reply` do, to buy one flag.
- **A new prompt corpus for tooled runs.** The point of item 3b is a number
  against the rule-B run; a different twenty prompts would produce a number
  that cannot be put next to it.

## Still open

- **`serve` makes a planning call and stays out of phase.** The cycle is a
  scripted-run instrument; a gate session that wanted one would need the reset
  this record rejects, and nothing wants it yet.
- **A cycle is a *loop*, and a session is not.** Every turn asks for the same
  four files in the same order, so the corpus is regular in a way a real
  session is not — which flatters any rule that likes repetition. Rule C does
  not (it takes bytes regardless), but rule A might, and a run that mixes them
  should say so.
- **Nothing checks the phase.** The run README reads it off the recording by
  hand. A `--mock-script` that knew how many calls a turn should make could
  refuse to drift, and that is a bigger instrument than this one.

## 2026-09-13, later: what the diff was, and what it bought

Built as proposed, in four pieces and with nothing the writing got wrong:

**`Mock::cycling()`** — one bool and one `push_back`, in the one place a reply
is taken. The default path is untouched, which is what every existing test,
`make smoke` and the gate spec depend on. Three tests: the old behaviour, the
ring, and a ring of one (which repeats its single reply rather than answering
nothing — `--mock-script` with one block is a legitimate file).

**`--mock-script <path>`, `parse_mock_script`** — `## reply` per block, the
header above the first, nothing stripped inside a block. `conflicts_with` on the
flag pair rather than a merge, and the file is read in `chat`'s own arm, before
`destination` announces anything: a file that will not parse should not first
print where the run was going to send.

The parser refuses an **empty block**, which is the guard the proposal did not
think of and the only failure this instrument cannot see from the inside. A
block that answers nothing is a model call that produced no text, so the turn
after it reads the wrong reply and every turn after that is one out of phase —
and nothing downstream would ever say why. It is refused by number
(`block 2 is empty`), at the point the file is read.

**`scripts/mock/grounded-tools.txt`** — eight blocks, four turns of
call-then-answer, over `scripts/tasks/grounded.txt` unchanged. Four files read
at the cap rather than at their heads, because a ten-line result measures
nothing.

### What the run found

[`RECORD/runs/2026-09-13.prune-results/`](runs/2026-09-13.prune-results/), six
arms, and the phase held in all six: **20 turns, 20 tool calls**, every arm.
That was the first number to read and it is the one the instrument is judged on.

The number item 3b existed for, and it is not the one the roadmap expected:

- **Rule B alone does not hold a tooled session.** On the untooled corpus it
  ended with nothing evicted; here it drops **16 turns of 20** and sends *more*
  than the flagless arm. What it takes from an old turn is its quoted spans, and
  the expensive thing in a tooled turn is not a span — mean result **1 736
  tokens** against the 1 024 the same turn selects.
- **Rule C is what that corpus needed.** The pair ends with **all twenty turns
  still in the window**, 0 cuts against 15, 48 434 tokens freed against 17 687,
  and mean prefix reuse 25.7% → 41.2% — 46.7% → **70.4%** under `--evict block`,
  the highest any arm has recorded on this corpus.
- **`--prune-results` alone is inert byte for byte.** Its recording is the
  flagless one, message for message, every field but the clock. The tests said
  so about a window; this says it about a run.

So the rule that had no number now has one, and the run also says something
about the corpus every earlier rule was measured on: it had no tool output in
it, and a window strategy measured only there was being asked about half a
prompt. That is not a fault in the earlier runs — it is what this instrument
existed to fix, and the fix is one flag in the command.

### Still open, after building it

- **Nothing checks the phase automatically.** The run checks it by reading
  `tool_calls` and `turns_with_a_tool_call` out of the recording. A
  `--mock-script` that was told how many calls a turn should make could refuse
  to drift instead, and that is a bigger instrument than this one.
- **The probe of roadmap item 4 has not been written**, only unblocked. This
  record claims the instrument, not the probe.
- **`run_command` is not in the corpus.** Every result here is a `read_file`,
  and the 8 KiB sentence in the design doc was written about a `cat`. The five
  programs `luu.toml` allows produce bytes that move between runs, so a
  `run_command` corpus wants something that does not — and that is a decision
  about the policy, not about the mock.
