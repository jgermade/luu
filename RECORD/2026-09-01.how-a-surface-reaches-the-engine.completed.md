# How a surface reaches the engine

**Status:** decided for the editor, argued for the rest.
[`ROADMAP/2026-08-31/surface.md`](../ROADMAP/2026-08-31/surface.md) put "the
protocol over stdio" third and said its open questions would get a record before
a commit. This is that record, and it settles one of them.

## The asymmetry that is not there

The question that started it: the CLI can call Ollama or llama.cpp directly, but
the extension would always have to go through an endpoint — so are they different
kinds of thing?

They are not, and the first half of the premise is false.
[`backend/ollama.rs:1`](../crates/agent-core/src/backend/ollama.rs#L1) is
"Ollama over HTTP (`POST /api/chat`, NDJSON stream)" with a `reqwest::Client`
against `localhost:11434`. **The CLI has never called a model directly.** With
llama.cpp it would be the same: you talk to `llama-server`. Direct would mean
linking llama.cpp in-process — `llama-cpp-rs`, candle, mistral.rs — which is not
in the tree, not in the design, and not proposed here.

So on the axis that matters for inference, every surface is identical and always
was: an HTTP client to a local endpoint. Under
[`2026-09-01.local-first.completed.md`](2026-09-01.local-first.completed.md) that is now a feature
rather than an accident — the same client reaches a local `llama-server` and a
remote host, and which one is the user's choice.

| | reaches the weights | reaches `agent-core` |
| --- | --- | --- |
| CLI | HTTP to an endpoint | links the crate |
| VSCode extension | HTTP to an endpoint | **cannot link it** — TypeScript in Node |

The real asymmetry is the second column, and it is a *process* boundary, not a
network one. Conflating the two is what makes the extension look expensive.

## Three transports, as a ladder

1. **stdio.** The extension spawns `luu` per window and speaks the protocol on
   its stdin/stdout, the way an LSP server works.
   [`protocol.rs:3`](../crates/agent-core/src/protocol.rs#L3) already says these
   types travel "over stdio (the VSCode bridge)"; stdio appears in the tree in
   that sentence and four others like it, and nowhere else.
2. **A socket.** The extension attaches to a running `luu serve`. Sessions shared
   between editor, browser and CLI, one gate for all of them.
3. **WASM in-process.** No `luu` at all; `agent-core` compiled to WebAssembly and
   loaded by the extension host.

**stdio is the choice, and the reason is the security ordering the roadmap
already committed to.** The moment there is a socket, `approve_task` is reachable
on it, and an approval grants read, write and `run_command` — which is why
[`federation.md`](../ROADMAP/2026-08-31/federation.md) makes signed approvals the
precondition for the first off-loopback bind rather than a later hardening step.
stdio has no socket. The extension over stdio needs none of that machinery, and
gets full capability on day one.

Option 2 is not available yet in any case: `serve` holds one `Mutex<Session>` and
refuses a second turn with *"one at a time until sessions exist"*
([`serve.rs:790`](../crates/luu/src/serve.rs#L790)). It becomes possible when the
session store and multi-session land, and it is worth having then — but as an
addition, not as the first transport.

## What WASM would actually get you

Worth stating precisely, because "it could run in the browser" is the kind of
claim that survives on vagueness. Against the real dependency list:

| | in WASM |
| --- | --- |
| `context.rs`, `repo_map.rs`, `task.rs`, `protocol.rs`, `api.rs`, `tokenizers` | **yes** — tree-sitter ships as WASM; that is its original delivery vehicle |
| `reqwest` | no sockets in VS Code's WASM host; HTTP would be an imported host function in TypeScript |
| `tokio` with `rt-multi-thread`, `process`, `io-std` | none of the three exist on wasm32 |
| `tools/command.rs` | **no processes in WASI preview 1.** `run_command` cannot exist |
| `sandbox/linux.rs` | already compiled out everywhere that is not Linux |

So a WASM extension is **the context manager without the agent**: it can decide
what the model sees and cannot act on anything. That is a coherent product — "chat
about your code, with the context chosen well" — and it is not this product. An
agent that cannot run the tests is missing the half that makes the gate worth
having.

One thing found while working it out and worth keeping: **WASI preopens are the
sandbox's own model.** An allowlist of trees, with no way to name a path outside
one — which is what `luu.toml` describes and what
[`sandbox/mod.rs:312`](../crates/agent-core/src/sandbox/mod.rs#L312) admits it
cannot fully deliver, since canonicalize-then-open leaves a TOCTOU window. The
file sandbox is *stronger* under WASM. The command sandbox does not exist there,
because commands do not.

## The split this creates if both are built

If the extension runs WASM in-process, it is not connected to anything: two
engines, two session stores, two gates, on one machine. Moving a session from one
to the other is exactly the problem
[`federation.md`](../ROADMAP/2026-08-31/federation.md) describes, arriving from
inside instead of across a LAN. That is an argument for picking one transport and
meaning it, and it is a second reason the answer is stdio.

## Decided

- **The VSCode extension talks to a spawned `luu` over stdio.** One process per
  window, sandbox scoped to that window's workspace, no port, no bind, no token.
- **The socket transport stays** as what `serve` already offers, and becomes
  interesting for the editor only after multi-session exists.
- **WASM is not on the path.** If it is ever built it is a different product with
  a different name, not a build target of this one.

## Still open

- Whether a spawned-per-window `luu` should share anything with a running `serve`
  — the same question `surface.md` asks as "is the local web an instrument, a
  product, or two modes?", seen from the editor.
- Where the stdio consumer's trace channel goes. `protocol.rs` is careful that
  debug data lives in [`crate::trace`] "so a stdio consumer never has to carry
  them", and the extension is the first consumer that will test whether the split
  was drawn in the right place.
