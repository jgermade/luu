# What Cline and OpenHands do about context, and the one question they answer differently

**Status:** study, and one decision it forces. Follows
[`2026-08-27.aider-repo-map.md`](2026-08-27.aider-repo-map.md), which read the
closest prior art on *relevance*. This one reads the closest prior art on
*forgetting*, because that is what we just built and measured in
[`2026-08-27.prefix-reuse-and-block-eviction.md`](2026-08-27.prefix-reuse-and-block-eviction.md).

Read at `main` on 2026-08-27:

- **Cline**, `cline/cline` @ `b4fd4ee` — now a monorepo. The loop is
  `sdk/packages/agents/src/agent-runtime.ts`, deliberately stateless; compaction
  is `sdk/packages/core/src/extensions/context/{compaction,basic-compaction,agentic-compaction,budget-projection}`.
- **OpenHands**, `OpenHands/software-agent-sdk` @ `6fce026` —
  `openhands-sdk/openhands/sdk/context/{condenser,view}`. Note the split: the repo
  that used to be `All-Hands-AI/OpenHands` is now *Agent Canvas*, a host for ACP
  agents, and the agent itself moved here.

Both are built for frontier models with six-figure windows. Their **shapes**
transfer; their **constants** do not, and the Aider record's warning about
inheriting somebody else's tuned numbers applies twice over here.

## Three things all three enforce, arrived at separately

### 1. Cut deep, cut rarely — and both say the reason is the prompt cache

We measured this yesterday and wrote it up as a finding. It is the consensus.

OpenHands says it in prose, in `context/condenser/README.md`:

> "condensation destroys the prompt cache, but doing so regularly keeps the cost
> of rebuilding the prompt cache low"

and implements it as: replace the **first half** of the events with one summary,
leave the back half untouched (`max_size=240` events, cut to `max_size // 2`; on
token pressure, cut to `max_tokens // 2`).

Cline implements the same curve with two constants instead of one: compact when
the transcript reaches `COMPACTION_TRIGGER_RATIO = 0.9` of the usable input
budget, down to `DEFAULT_TARGET_RATIO = 0.7`, preserving
`DEFAULT_PRESERVE_RECENT_TOKENS = 20_000` verbatim.

Ours is `--evict block --low-water 0.5`, and the sweep found 0.9 collapses back
to the baseline. Read the three together and the interesting part is not that we
agree; it is that **nobody publishes the number**. OpenHands asserts the
cache argument in a README, Cline encodes it in two constants, and neither shows
what either buys. That is the gap the instrument fills, and it is worth
remembering the next time this project's differentiator sounds grandiose: the
strategy is table stakes, the measurement is not.

One caveat on their side of the trade, in fairness: they cut to a *fraction of
the budget*, which is what we do. OpenHands additionally cuts to a fraction of
the *event count*, which we cannot copy — our unit is the turn and our windows
are small enough that a count-based rule would be noise.

### 2. Never cut inside an atomic unit

Our rule is "eviction drops whole turns, so the window can only start on a user
message". Both generalise it, and both had to.

OpenHands computes **manipulation indices** — the set of positions where the
history may be spliced — as the intersection of *view properties*
(`tool_call_matching`, `batch_atomicity`, `tool_loop_atomicity`,
`observation_uniqueness`). A tool call and its result are one unit; a forgetting
range must land on a boundary.

Cline reaches the same place from the other end: its budget projection records
`tool_pair_boundary` as a *reason* for preserving a block it would otherwise
have dropped.

**The reading for us:** our rule is theirs with exactly one property, and the
property set grows the day tools land — an action and its observation become a
unit, and the whole-turn rule stops being sufficient. That is not a reason to
build a property lattice now. It is a reason to write the rule so that adding
the second property is an addition rather than a rewrite.

### 3. What has already been compacted is frozen

Cline, in `basic-compaction.ts`:

> "Messages that survived an earlier compaction are frozen: a later compaction
> never re-folds them […] Without this, each pass would re-drop the previously
> preserved answers and stack duplicate summary blocks onto the already-folded
> prompts."

That is the monotone floor we added yesterday, for the same reason and with the
same failure mode. Two codebases finding the same invariant independently is the
strongest evidence available that it is one — and it is quietly reassuring that
the correction went in *before* the comparison rather than after.

## Where they disagree, and it is our open question

Both must answer: **how is forgetting represented, so that the record and the
live state cannot drift?** They answer differently, and we have the question
open in the context-manager record under "on persistence, so SQLite does not
arrive as a second truth".

**OpenHands: forgetting is an event.** The conversation is an append-only log;
a condensation is a `Condensation` event carrying `forgotten_event_ids`, a
`summary` and a `summary_offset` — explicitly modelled on Cassandra/Kafka
tombstones. `View.from_events` folds the log into what the LLM sees. Nothing is
deleted; the account of what happened stays complete, and what the model sees is
a projection of it.

**Cline: forgetting is a cached projection, tied to its source.**
`SessionCompactionState` stores the compacted messages plus
`source_message_count`, `source_prefix_hash` and `source_last_message_key` — so
the projection can be checked against the transcript it was derived from, and
invalidated when it no longer matches.

**Decision: we take OpenHands' answer, because we already have most of it.**
The JSON-lines record *is* an append-only event log, `api::SessionView` *is* the
fold, and `folding_live_events_gives_the_same_view_as_folding_the_record` already
asserts the two agree. Making eviction an event costs one message on the trace
channel and two lines in the fold.

It also fixes a gap that yesterday's work made obvious and did not close:
**a recording cannot currently say what was evicted.** The floor is in-memory
state. You can watch reuse collapse in the panel and you cannot see which turns
left the window, when, or under which policy — you can only infer it from the
history bucket getting smaller. The instrument shows the symptom and hides the
cause, which is a strange thing to ship and an easy thing to fix.

## On dividing a session into tasks

Both have the shape, from opposite directions, and neither does the thing that
makes it interesting to us.

**Cline has task lifecycle.** `AgendaTaskManagerApi`: `createTask` →
`approveTask` → `runTask`, with `expectedRevision` for optimistic concurrency and
an `AgendaAutomationPolicy` for what may run unattended. Approval is a state a
task is in, not a mode the agent is in — which is the argument for dropping
`plan | run | auto` as a global enum, made by someone who shipped it.

**OpenHands has goal loops.** `sdk/conversation/goal`: send the objective, run
the agent, **judge completion with a second LLM**, re-prompt until done or a cap
is hit. `GoalController` is transport-agnostic and does no I/O — the same
boundary as `agent-core`.

So "when is a task done" has two answers in the wild: a judge model, or a person.
For 7B–32B local inference the judge is another local model, and you pay a full
generation to be told "not yet" by something no more reliable than the model that
just failed. Asking the user — a final question that closes the task — is
cheaper, more honest about what the model knows, and produces a decision we can
record. **For this workload the person is the judge.** That is not a general
claim; against a frontier model with a large window the judge loop is clearly
right, which is why they built it.

What neither does: **use the task boundary as the compaction boundary.**
OpenHands condenses on token or event thresholds regardless of what the agent was
doing; Cline compacts on a ratio. Both cut wherever the counter says, which is
exactly the "cuts wherever the limit lands" failure our own design objects to at
the *rendering* level and then commits at the *history* level.

That gap may be an opportunity or it may be a warning. The honest version: a task
boundary is a *preferred* cut point, not a sufficient one, because one task can
overflow the window on its own. So the threshold stays as the fallback, and the
task boundary becomes the place the cut is taken *when there is a choice*. Which
is a strategy, and therefore has to beat the recorded baseline like any other.

## Two things worth stealing that are not about compaction

- **The recovery path must not depend on the thing that failed.** When a provider
  rejects a request as over the window, Cline forces the *deterministic* basic
  strategy rather than the LLM-driven one: "recovery must not depend on another
  successful LLM request". We currently treat being over the limit as the
  backend's error to report. Turning that error into a trigger is right; doing it
  with a summary generated by the same 7B that just failed is not.
- **A rewritten transcript invalidates stored counts.** Cline strips per-message
  metrics on compaction: "per-message token metrics describe the request context
  at the time the message was produced; after compaction rewrites the transcript
  they no longer add up." Our `Turn.tokens` carries `counted_by`, which catches a
  changed *counter* and would not catch a changed *turn*. The day compaction
  lands, a folded turn's stored count is a lie of exactly this kind.

And one to note rather than steal: Cline's `BudgetAction` records, per removal, a
path, an original and final size, a kind (`truncated_text` / `dropped_block` /
`dropped_message` / `preserved`) and a **reason** (`over_budget`,
`unsafe_to_truncate`, `tool_pair_boundary`, `protected_live_tail`). Our buckets
attribute what survived; that attributes what did not. The compaction-log panel
in the design is where it would go, and the eviction event above is what would
feed it.

## What this does not change

`agent-core` knowing nothing about the CLI is the same boundary Cline draws
around `@cline/agents` ("stays stateless — no session/storage/config concerns")
and OpenHands draws around `GoalController`. Three for three. It is not a
preference.

Fusing non-turn content into the nearest turn stays, unrevisited here: both of
these talk to API models that normalise message sequences, which is the same
reason the Aider record gave for not taking Aider's standalone summary message.

## Still open

| Question | Precondition |
| --- | --- |
| Eviction as a recorded event, so a recording says what was forgotten | nothing — it is small, and the gap is already visible |
| Task boundary as the preferred cut point, threshold as fallback | the tasks plan, which does not exist yet |
| Deterministic recovery when the backend rejects the window | tools, or a real model that actually rejects one |
| Whether a property lattice is needed, or one hardcoded rule keeps sufficing | tools, when the second property appears |
| Whether a 7B can produce a summary worth freezing into the prefix | a real model; until then compaction is deterministic or nothing |
