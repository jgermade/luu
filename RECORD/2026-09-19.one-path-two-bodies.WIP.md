# One path, two bodies

**Status:** WIP — it plans code, and only half of what it plans is built. The
detector is in; the fix is argued here and not taken, on purpose, for the reason
§What is built and what is not gives.

It answers item 19 of [`ROADMAP/2026-09-17`](../ROADMAP/2026-09-17/README.md) —
*a span is read once and never re-read* — which was found on 2026-09-18 while
arguing about what a resume should store, recorded in
[`the-window-rules-are-a-session-fact`](2026-09-18.the-window-rules-are-a-session-fact.completed.md)
§5th as an aside, and has been a row with nothing blocking it since.

## The problem is not the one the row names

The row says *a live session already sends bytes that a later turn edited away*.
That is true and it is the smaller half. Here is the whole of it, from a probe
run against the tree as it stands:

```
[0] "// src/lib.rs:1-4\nfn main () { old }\n\nquestion number 0 padded out"
[1] "// src/lib.rs:1-4\nfn main () { new }\n\nquestion number 1 padded out"
[2] "now this"
```

**One prompt, one path, two bodies, and nothing anywhere says which is true.**
Not a stale block sitting harmlessly behind a fresh one — a contradiction handed
to the model inside a single render, with both blocks carrying the same `//
src/lib.rs:1-4` header and no ordering cue beyond their position in a history
the model has no reason to read as chronological.

### Why it happens, in three facts that are each individually correct

**`code_context` is written once and never refreshed.** `push_turn_with_steps`
takes `Vec<Fragment>`, stores it on the `Turn`, and nothing in the tree ever
touches it again. `Fragment` is `{ path: String, text: String }` — the bytes, not
a reference to them.

**Every turn re-reads.** `select::select` scores candidates against *this* turn's
prompt and loads each chosen span fresh through the sandbox with
`fragment::load`, which does a `read_to_string`. So turn 5 asking about the same
file gets turn 5's bytes, correctly, while turn 3 keeps turn 3's forever.

**A fragment's identity is its path *and* its bytes.** `split_shown` dedups
through a `HashSet<&Fragment>`, and `Fragment` derives `Hash`/`Eq` over both
fields. This is written down in `luu-design.md` as a decision — *the same span
after an edit is a different span* — and it is the right rule for the question it
was written to answer, which is *has this exact block already been rendered in
this prompt*.

Each of the three is defensible. Together they guarantee that the one case where
a span genuinely needs re-reading is precisely the case rule A cannot see.

### Which makes this rule A's problem, and as of yesterday that is the default

Under `Repeat::Always` two bodies for one path is *the documented behaviour*:
every turn re-sends what it selected, the record says so, and a reader of that
prompt knows the blocks are per-turn snapshots.

Under `Repeat::Once` the rule's whole promise is in its name — **a span is
rendered once** — and it silently does not hold for exactly the spans that
changed. The dedup passes them through because they are, by its own identity
rule, different spans. So the guarantee the prompt appears to offer is narrower
than it reads, and it is narrower in the case that matters most.

[`the-window-rules-are-a-session-fact`](2026-09-18.the-window-rules-are-a-session-fact.completed.md)
§fourteenth turned `Repeat::Once` on by default yesterday. **That commit made
this defect the default path**, and it did so on evidence — the 2026-09-14 run —
that could not have contained the case, because `grounded.txt` is twenty
questions over a tree nothing edits. Said plainly rather than left for somebody
to find: the flip was right on what it measured and this is a thing it did not
measure.

## What is built here: the detector, and nothing else

The row's own words are *nothing in the tree detects it*, and that is the half
with no trade in it. `Context::select` now reports, per render, every path it
sent with more than one distinct body — the path, the turns that carried each
body, and how many bodies there were.

It is carried out of `select` on `Selection` rather than logged inside it,
because that is what `Evicted` and `Pruned` already do and for the same stated
reason: the context manager does not know which turn is about to be sent and the
caller does. It reaches the wire as a **trace** line, beside `pruned`, on the
same argument that record made — *trace and not protocol, because what changed
is the prompt and not the conversation*. Nothing about the session's turns, their
answers or the transcript is different. What is different is that a person can
now see the prompt contradict itself.

Computed over what is **sent**, not over what is stored: a turn below the prune
line has given its span up, and an evicted turn is gone. A detector that counted
stored fragments would report contradictions the model was never shown, which is
the failure mode `Pruned`'s own doc comment guards against one field along.

## The fix, argued, and why it is not in this commit

Three shapes were considered and one of them is right. It is not built, and
§What is built and what is not says why.

**Rejected — oldest body wins, by widening the dedup to path-only.** The
cheapest change: make `split_shown` key on the path and the first body rendered
survives. It removes the contradiction and it removes it by keeping **the stale
copy**, because the render walks oldest to newest and rule A hands ownership to
the oldest turn that carries a span. The model would be left with exactly one
body for the path and it would be the one that is no longer on disk. A prompt
that is wrong and consistent is worse than one that is wrong and visibly
inconsistent, because nothing in it invites doubt.

**Rejected — re-read every fragment at render time.** The clean answer, and it is
item 20's *the reference, not the bytes* generalised from resumes to live
sessions. It is rejected **here** and not in general: `Context::select` lives in
`agent-core` and holds no sandbox, so this is an architectural change to what the
context manager is allowed to touch, and it drags in what a now-denied or deleted
file does to an old turn's render. That is item 20's design argument, it is a row
of its own, and pre-empting it from this record would be deciding it in the
wrong file.

**Recommended — the newest body wins, and the older ones become citations.** The
freshest bytes are the true ones; an older turn's block becomes the line that
cites it, which is the mechanism rule B already has, already tested, and already
guarded by *a citation that would cost more than the span it replaces is not
taken*. The model keeps the historical fact that turn 3 saw something, loses the
bytes that are no longer true, and is told where the current ones are.

**What it costs, and the cost is the reason it needs a number first.** It rewrites
the history block above the newest message, which is the one thing rule A was
shaped to avoid: *oldest and not newest is the whole decision*, taken because it
leaves the prefix byte-identical and worth **+18 points of prefix reuse** on the
2026-09-07 run. Superseding spends some of that back, and how much depends
entirely on how often a window carries a path whose bytes moved — which is the
number nothing in this tree has ever had.

It also needs a **ratchet**, for the reason the prune line needs one. Once turn
3's block is a citation because turn 5 disagrees with it, evicting turn 5 would
put turn 3's stale bytes back and rewrite the block a second time. The floor and
the prune line both solved this by only ever moving forward and this would be the
third instance of the same shape, which is either a good sign or a sign that
something wants naming once.

## What is built and what is not

**Built: the detector.** No trade, no measurement owed, and the row asked for it
in those words.

**Not built: the fix.** Not because it is unclear — it is recommended above, in
one paragraph, with its cost named — but because landing it now would be the
thing this project spent five days refusing to do with item 6. The fix trades
prefix reuse for truthfulness. Prefix reuse here is a measured quantity with a
number on it. The frequency the trade turns on has **no** number, and cannot have
one until the detector has run against a corpus that edits files.

So the honest order is the one rule A itself went through: detect, measure,
decide, and the decision gets its own dated section or its own file. Building it
the other way round would be *defaulting to the rule that saves most* with the
sign flipped — a change justified by a failure mode's badness rather than by its
frequency, which is the same error measured from the other end.

**And the corpus is the real blocker, not the code.** `grounded.txt` cannot
produce this case: twenty questions, nothing edits. A corpus that edits a file
and then asks about it again is a new artefact this tree does not have, it is a
prerequisite for the fix, and it is worth a roadmap row of its own rather than a
line in this one.

## Still open

- **The line range is part of the path.** `Fragment.path` is the whole spec
  string — `src/lib.rs:1-4` — so two *overlapping* ranges of the same file
  (`1-4` and `1-9`) are different paths to the detector and their contradiction
  is invisible to it. The common case (`select` re-scoring the same entry to the
  same span) is caught; partial overlap is not. Named rather than solved: it
  needs a notion of one span containing another that nothing here has, and the
  detector is honest about what it counts.
- **Nothing counts how often it fires across a session**, only per render. Fourth
  instance of this same gap in one revision, after item 12's grants, the
  `not_granted` refusal and the three window rules. At some point the answer is
  one counter surface rather than a fourth thing that reports per call.
- **Our own edits are knowable and this does not use that.** A successful
  `edit_file` or `write_file` step is a fact the session already holds, and it
  could invalidate older fragments for that path at the moment it happens —
  forward-only by construction, no byte comparison. It would miss a file changed
  *outside* the sandbox, which for a project shipping a VSCode extension is not a
  corner case. The byte comparison catches both, so it is what the detector uses;
  the step is noted because a future fix may want both.
- **Whether a model even notices.** The failure is stated here as obviously bad
  and it has not been put in front of one. It is the same bar item 5 is held to,
  and this record does not get to skip it because its failure sounds worse.

## Appended 2026-09-19: the defect on a real run, and the detector naming it

§The problem opened with a unit probe, which is enough to show the mechanism and
not enough to claim it happens. It happens. Three turns through `luu chat`
against the mock, in a scratch project, with a real `write_file` through the
real sandbox:

```
## fragment: greeting.py
what does greeting.py say?
now change the greeting          ← the model writes greeting.py
## fragment: greeting.py
what does greeting.py say now?
```

Turn 3's rendered prompt, `// greeting.py` appearing twice in it:

```
--- block ---
def greet():
    return "Hello, "
--- block ---
def greet():
    return "Hi, "
```

The first block is turn 1's `code_context`, stored when turn 1 closed and never
touched since. The second is the bytes `fragment::load` read at turn 3. The file
on disk has one of these in it. Nothing in the prompt says which.

And the line the recording now carries:

```json
{"type":"diverged","turn":3,"path":"greeting.py","turns":[1],"asking":true,"bodies":2}
```

**`asking: true` is the case §The fix calls the one that matters most**, and it
is what the *first* run of this script produced by accident: the binary was a
release build from before the detector existed, wrote `"format": 11`, and said
nothing. Worth recording because it is the defect's whole character — a prompt
that contradicts itself and a recording that looks completely normal. The only
difference between the two runs is which binary wrote the file; the prompt was
wrong both times.

Note what the run does **not** need: no relevance selection, no window pressure,
no eviction, no rule B, no `--context-limit`. Two `## fragment:` lines and one
tool call. The cheapest possible reproduction, which says something about how
often this is likely to fire in a session that edits the code it is reading —
and that "likely" is exactly the number §What is built and what is not says the
fix waits for, now that there is something that can count it.

## Appended 2026-09-19: the blocker is gone, and the number is bigger than this file assumed

§What is built and what is not ends *the corpus is the real blocker, not the
code*. It is built:
[`a-corpus-that-edits`](2026-09-19.a-corpus-that-edits.completed.md), thirteen
turns over a committed scratch tree, with the control and both blind spots this
record's §Still open names.

What it says about the fix, which is not what this record assumed while arguing
it. Against the mock, with the edits scripted: **two edits left 8 of 13 prompts
carrying two bodies for one path.** This record framed the defect as a property
of *the turn that re-reads* — §The problem opens on turn 3 of a three-turn run,
and §The fix is written about the turn whose bytes are fresh. Six of those eight
renders attach nothing of the file at all. The contradiction is in the history
the moment turn 6 closes, and every later prompt renders it until eviction takes
turn 1 out.

So the frequency this record says the trade turns on is not *how often does a
session edit a file it has quoted*. It is *what share of a session's prompts are
sent after the first time it does*, and those are different questions with
different answers: the first is a count of edits, the second is nearly the whole
session once an edit has happened. Rule A's +18 points are paid per turn, and on
this corpus so was the defect.

**This does not decide the fix**, and deliberately: the edits were scripted, so
8-of-13 is a fact about a corpus and not about a model, which is the same
distinction §What is built and what is not refused to skip in the other
direction. What has changed is that the question now has an instrument pointed
at it, and that the instrument has already contradicted one assumption this file
made before anyone ran it.
