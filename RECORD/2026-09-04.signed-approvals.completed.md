# The wire says its version, and an approval says who signed it

**Status:** Stage 1 items 1 and 2 of
[`ROADMAP/2026-08-31/federation.md`](../ROADMAP/2026-08-31/federation.md), built.
Items 3 and 4 — the record stream and an imported job returning to the gate —
are not in this record and are not built.

## The problem

Federation's stage 1 is *host to host, on a LAN, with no portal at all*, and its
own file names four things that have to be true before a host is reachable by
anything other than a browser on the same machine. The first two are the ones
whose ordering is a safety property, and both are false today:

1. **Nothing on the wire says what it speaks.** The host announces
   `protocol: 4` in its `Hello` and the client answers nothing. Host and client
   are one artifact (`rust-embed`), so a mismatch has never been possible — and
   the moment a second machine's `luu` connects, a mismatch is not only possible
   but the normal state of a fleet updated one box at a time. An unknown `type`
   in a tagged enum is a parse error rather than a line to skip, which is the
   rule [`protocol::VERSION`] exists to enforce; without a handshake the rule is
   enforced by the client *failing to parse*, silently, on its own side.

2. **An approval is a bare line of JSON.** `approve_job` is the authority this
   whole design is built around — nothing runs behind the gate until it arrives
   — and today it is admitted on the strength of having reached the socket. That
   was defensible while the socket was loopback:
   [`what-the-audit-left`](2026-09-01.what-the-audit-left.completed.md) made the
   port refuse to bind off loopback without a bearer token, so *who may reach the
   surface* is answered. But a bearer token answers reachability, not authorship:
   it is one secret shared by everyone the port admits, it is replayable by
   anything that sees it, and a relay — which is exactly what stage 2 proposes —
   holds it in the clear. **A verdict already records who enforced it and never
   assumes; an approval records nothing about who approved it at all.**

## The proposal

### The handshake

`ClientMessage::Hello { protocol, format }`. The client says what it speaks; the
host compares against its own `protocol::VERSION` and `record::FORMAT` and, on a
mismatch in either direction, answers `Refused { refusal: Version, detail }` and
closes the connection. Out loud, as the federation file asks, rather than by
misreading the next message.

**A mismatch in either direction, not just an older client.** `VERSION`'s own
doc comment says it is "bumped when a change would break an older client" — so a
newer client is the case the host cannot parse, and an older one is the case the
client cannot. Neither side can repair it, so neither side guesses.

**Whether it is required is the question the bearer token already answered.**
The rule is the same one and reads the same way: on a port that requires a token
— which is every non-loopback port, because binding one without a token is
refused before the listener exists — the first message must be `Hello`, and
anything else is refused. On loopback, and over stdio, it stays optional: the
peer is a browser on this machine or a parent process that spawned us, both of
which are the same artifact, and requiring it there would break every client
written before this without buying a property the operating system does not
already give. Our own clients send it anyway, so absence means *a client older
than this record*, and that is the only thing it means.

### The signature

`approve_job` gains an optional `signature: { by, sig }`: Ed25519 over a
canonical rendering of the approval, verified against public keys named in
`luu.toml`.

```toml
[approvals]
# An approval must carry a signature from one of the keys below. Off by default:
# a loopback session with a person at the keyboard is the run every measurement
# in this repository was made under, and it has no key to sign with.
required = true

[[approvals.key]]
name = "jgermade"
public = "ed25519:1f8b…"
```

What gets signed is the grant, not the message, so a relay that rewrites the
grant invalidates the signature it is relaying:

```
loude-approval v1
session 2026-09-04T18-02-11
job 3
files src/**
writes src/main.rs
commands cargo
closes_on cargo test
network false
```

Three properties are load-bearing and each costs one line:

- **The session is in the bytes.** Without it, a signature captured on one host
  is replayable against another host that happens to number its jobs the same
  way — which two machines on a LAN running the same repository will. So
  `ServerMessage::Hello` now carries the session id: the signer has to be told
  what it is binding to.
- **Every grant is in the bytes**, in the order the message carries them, so
  `files` and `writes` and `commands` cannot be widened between signer and gate.
  The `Refusal::NotGranted` check still runs afterwards and is unchanged: a
  signature says *this person asked for this*, never *this is permitted*. The
  policy file remains the outer bound nobody may widen past.
- **A value containing a newline cannot be canonically encoded** and is refused
  rather than escaped. An escape scheme is a second parser, and two parsers that
  disagree about the same bytes is the whole class of bug a signature is supposed
  to remove.

**A bad signature is refused whether or not signatures are required.** `required`
decides whether an *unsigned* approval is admitted; it never decides whether a
*wrong* one is. The three failures — no signature where one is required, a name
no key answers to, and bytes that do not verify — are one `Refusal::Signature`
with a `detail` that says which, because a client branches on the variant and
shows the detail to a person.

### What the verdict records

`Job` gains `approved_by`, beside `closed_by` and dropped by nothing, and
`job_approved` carries it on the wire. It is `operator` for the local
unsigned case — what every approval before this record was, which is why an
absent value reads as that one — and `key { name }` when a signature verified.
The same argument as `ClosedBy`: the rung above the person is only worth
climbing if each rung can be *counted*, and a recording where both approvals
look the same cannot answer how often either happened.

### The keys

`luu key new` writes a private key `0600` and prints the `[[approvals.key]]`
block to paste; `luu key sign` reads an `approve_job` message on stdin and
writes it back out with its signature attached. Two commands, because a
verification path with no way to produce a signature is a feature nobody can run
— and because the signing half belongs in a place a remote operator's `luu` can
call, not inside one surface's UI.

## What it costs

- **One dependency: `ed25519-dalek`.** Signature schemes are the canonical thing
  not to hand-roll. The randomness for a new key is read from `/dev/urandom`
  rather than pulling `rand_core` and its feature matrix for one 32-byte read,
  and hex is written here for the same reason: they are the two pieces small
  enough that a dependency costs more than the code.
- **Protocol 4 → 5, record format 6 → 7.** `Refusal` gains two variants and
  `ClientMessage` gains one; by this project's own rule that is exactly the
  change a bump is for, and the handshake this record adds is what makes the
  bump legible to the other side instead of fatal to it.
- `job_approved` gaining `approved_by` is additive and backwards compatible:
  absent means `operator`.

## What was rejected

- **A shared secret (HMAC) instead of a keypair.** It is smaller, and it is the
  thing the bearer token already is: every holder can mint approvals
  indistinguishable from every other holder's, and the relay stage 2 proposes
  holds it. "A key no relay holds" is the property, and only asymmetry has it.
- **Signing the whole `ClientMessage` as serialized JSON.** It would bind the
  transport encoding into the signature: a field reordered by any serde version,
  or a client that emits `"network": null` where ours omits it, becomes a forged
  approval that verifies nowhere. The canonical form is written by this project,
  for this purpose, and is the only thing either side hashes.
- **Requiring the handshake everywhere.** It would break every client written
  before this record for a property loopback already has, and it would make the
  first message of `luu stdio` a round trip that the subprocess bridge has no
  reason to pay.
- **A signature on every client message.** Only approval is authority. `prompt`
  is not: it is held behind the gate, and what it can cause is exactly what an
  approval later grants it.

## Still open

- **Nothing rotates or revokes a key.** A compromised key is removed by editing
  `luu.toml` and restarting, which is the same shape as every other thing that
  file decides — and is not good enough once the fleet is more than the boxes in
  one room.
- **The signature is not in the record stream's own integrity story.** A
  recording carries the signed approval, so a reader can re-verify it, but
  nothing signs the recording *as a whole*: a relay that drops lines is not
  detected by this.
- **`luu chat` still has no gate**, so it has no approver either — the policy
  file is its standing approval and `approved_by` there is `operator` by
  default. Whether the one-shot surface should be able to carry a signed
  standing approval is the same open question the gate itself has.
- The remaining two items of stage 1 — the record stream shipped rather than a
  snapshot, and an imported job that is not `Closed` returning to the
  destination's gate — are untouched. The transfer probe that would answer
  whether host-to-host earns its place cannot run until they are.
