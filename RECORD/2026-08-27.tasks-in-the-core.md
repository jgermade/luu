# Tasks in the core: the boundary, in code

**Status:** plan, then the change that follows it. It implements
[`2026-08-27.tasks-instead-of-modes.md`](2026-08-27.tasks-instead-of-modes.md),
which argued that a session is a sequence of tasks and that the boundary is
worth having because compaction, permission and the transcript all want the same
cut point. That file decided *what*. This one decides *how*, and says out loud
which of the three payoffs this change actually collects.

It collects two: the cut point, and the transcript. **Per-task permission is not
in this change**, for a reason that only showed up in the code — below.

## What a task is, in the history

The temptation is a `Task` that owns its turns and a `Context` that renders
tasks. That is a second history beside the one that already exists, and the two
disagree the first time a turn is evicted.

So a task owns nothing. It is bookkeeping — a plan, a state, and *where in the
history it began* — and everything it produces enters the history as an ordinary
turn:

| What | Enters as | Written |
| --- | --- | --- |
| the approved plan | a turn: prompt = the objective as typed, answer = the plan | once, at approval |
| the work | ordinary turns | appended |
| the closing summary | a turn: prompt = the objective, answer = the summary | once, at the close |

Two things fall out of that and both are the reason for it:

- **Alternation holds.** `AGENTS.md` says the retained window can only start on
  a user message and that a turn is evicted whole. A summary rendered as a
  standalone `user` message would put two user messages back to back — the exact
  thing `user_text` exists to avoid — and several chat templates read that as a
  prompt to continue. A summary that is a turn cannot break it.
- **Nothing gets exempted from the budget.** A summary is a turn, so it is
  counted, evictable and attributable like every other one. A summary region
  that could not be evicted would be a second, quieter window nobody measures.

`Turn` therefore grows a `kind` — `exchange`, `plan { task }`, `summary { task }`
— and the budget grows one bucket, `tasks`, for the plan and summary entries.
That bucket is the whole point of tagging them: "the scaffolding costs N tokens"
is a number the strategy has to justify, and without the tag it hides inside
`history`.

## The fold

Closing task *t* replaces the turns from its plan entry to the end of the
history with one summary turn. That is the only rewrite in a session, and it is
deliberately deep and rare — the shape yesterday's prefix numbers say a cache
pays for.

The floor needs a rule. `Context::floor` is monotone on purpose: what leaves the
window stays out, or block eviction walks back over its own cut. But a fold can
span turns that are already below the floor, and then the summary — brand new
text, written once — would land below it too and never be sent. The rule is:

```
floor = min(floor, index of the summary)
```

The index moves back; **the content does not come back**. The folded turns are
gone from the vector entirely, and what stands in their place is not one of them.
That is compaction doing its job, at the one moment we already decided to pay for
a rewrite. If the summary were left below the floor the fold would cost tokens to
produce and change nothing, which is the worst of both.

What the fold cost and bought is a **trace** message, not a protocol one:
`task_folded` carries the turns folded and the tokens before and after. The
summary itself is protocol — a client draws it — and the arithmetic is debug data
that a stdio consumer should never have to carry. Same split the file already
makes for `budget` and `prompt`.

## The gate

`Prompt` while a proposal is awaiting approval is **refused, visibly**:
`ServerMessage::Refused { reason }`. Not dropped, and not queued. A gate that
silently swallows the message is one nobody trusts twice, and a queued prompt
would run against a plan the user had not yet read — which is the one thing the
boundary exists to prevent.

Tasks are opt-in in this change. `luu chat "hola"` still runs a turn with no task
around it, because the walking skeleton's path is what every fixture and every
baseline recording uses. A session that is *entirely* a sequence of tasks is the
end state, and forcing it now would rewrite the instrument in the same change
that adds the thing to be measured.

## Who writes the plan

The model, and the parse is the tool parse again: a fenced ` ```plan ` block with
`steps`, `paths` and `commands`. Same shape as a tool call, so the mock backend
scripts it with `--mock-reply` and the whole lifecycle is exercised end to end
without a model — which is how tools were built and is the only reason the
fixtures are reproducible.

**When the block does not parse, the model's own words become the steps.** Not a
plan we invented on its behalf: the user is about to approve this, and a plan
with our sentences in it is a confirmation of something nobody proposed. The plan
carries `parsed: false` so the client can say so.

The planning call is an ordinary user message on top of the unchanged prefix, so
proposing a task costs no cache. It is not remembered: the approved plan enters
the history, the request that produced it does not, or the objective is in the
prompt twice before any work has happened.

## The summary is evidence, not prose

Deterministic first, as the previous record decided — the plan plus what the
steps actually did, gathered from the `ToolStep`s the turns already store:

```
[task 2] rename the counter — closed
plan:
  1. read context.rs
  2. rename the field
touched: crates/agent-core/src/context.rs
commands: cargo test --workspace → ok
          cargo clippy → exited with 101
denied: 1 call
folded 4 turns
```

No model call, so the close cannot fail because generation did, and the same
session produces the same summary twice. Model prose on top is a later, measured
addition — it lands in the write-once region every later turn is built on, and
that is the region where a 7B's invention is most expensive.

**Denials are in the summary.** A task that was refused three times and a task
that was not are different tasks, and the difference is exactly what a later turn
needs in order to not try the same thing again.

## What is deliberately not here

- **Per-task permission**, and this is the one that changed on contact with the
  code. `Sandbox::new` requires every granted path to *exist* — Landlock takes a
  file descriptor per root, so a rule that cannot be opened cannot be a rule. A
  plan's most ordinary claim is "I will create `src/task.rs`", which has no file
  to open yet. So narrowing the sandbox to the plan's paths either denies the
  work the plan describes, or silently widens to the nearest existing ancestor —
  a grant on `src/` wearing the label of a grant on one file. Neither is
  shippable, and choosing between them is a design decision with its own record,
  not a paragraph in this one. The plan therefore *declares* its paths and
  commands, the confirmation shows them, and the session policy is still what is
  enforced. The design's open question stays open, and now says why.
- **Reopening.** The previous record left "what a reopened task does to a prompt
  already built on its summary" open, and it stays open. Closing is an event; the
  fold is what an event does. Reopening is a different fold, and inventing it
  before anything has been closed in anger is guessing.
- **The judge.** It runs at the close in shadow mode and needs thirty closed
  tasks to say anything. There is nothing to close yet.
- **Auto-closing.** The rung ladder starts at deterministic checks, which need a
  task long enough to have checks. Same precondition as the judge.

## What it costs

- **Protocol v2.** Four server messages, three client messages, a refusal, and
  `turn_started` grows a `task`. Older clients break, which is what the version
  is for — and this is the freeze the design asked for while it is still cheap.
- **A second wrong-summary risk**, now real: the summary is in the write-once
  region. Mitigated by it being derived, not generated.
- **A planning call before the work.** One extra round trip per task, on the
  cached prefix. It does not stream: the client is shown the plan, not its
  generation, which on a slow local model is a silent wait. Worth watching, and
  cheap to change — the tokens are already events.
- **A fold that spans an eviction moves the floor back.** Argued above; it is the
  one place the floor is not monotone in index, and the invariant it protects
  (content does not come back) still holds.

## Still open

| Question | Precondition |
| --- | --- |
| Does folding on the boundary beat folding on a threshold, in reuse and in tokens? | recorded runs of the same script with and without tasks |
| What a task's `paths`/`commands` should grant, given that a created file has no descriptor | its own record; see above |
| Whether the deterministic summary is enough | a real model on tasks with something to summarise |
| Reopening | the first task somebody wants back |

# 2026-08-27, later the same day: the table

The change above landed with the question it was supposed to answer left open —
*does folding on a boundary beat folding on a threshold, in reuse and in tokens?*
This is that comparison. It also found the baseline it was going to be compared
against had stopped working, which comes first.

## The baseline was broken, and had been since tools landed

`scripts/make-fixtures.sh` records the eviction pair at `--context-limit 512`.
That window was chosen when the prefix was the system block alone. The tool
definitions are **465 tokens**, so with them in the prefix:

```
system 11 + tools 465 + prompt ~9 + reserve 64 = 549 > 512
```

`available` is zero, no history is ever selected, and both policies record an
empty `history` bucket and a flat 98% reuse — the 465 constant tokens, shared
with themselves. The pair the deploy leads with, the one whose comment says it
is *"the only pair in here that is meant to be read against each other"*, had
been showing two identical runs of nothing since the tools commit. Nothing
failed. That is the failure mode `AGENTS.md` warns about, arriving in the
instrument rather than in the thing being instrumented.

The fixtures now run at `--context-limit 1024`, which leaves ~480 tokens of
history — eight or nine turns of this script. A correction is appended to
[`2026-08-27.prefix-reuse-and-block-eviction.md`](2026-08-27.prefix-reuse-and-block-eviction.md),
whose table was measured before tool definitions existed and is not reproducible
at the window it names.

## What was run

`steady-state-tasks.txt` is new and is the twin of `steady-state.txt`: **the same
twenty prompts, in the same order**, grouped into four tasks that close every five
turns. `diff` on the two, directives stripped, is empty — which is the only reason
the pair is a comparison rather than two runs.

```sh
for policy in turn block; do
  luu chat --script scripts/tasks/steady-state.txt       --mock-delay-ms 0 \
    --context-limit 1024 --reserve 64 --evict "$policy" --record plain-$policy.jsonl
  luu chat --script scripts/tasks/steady-state-tasks.txt --mock-delay-ms 0 \
    --context-limit 1024 --reserve 64 --evict "$policy" --record tasks-$policy.jsonl
done
```

Same window, same reserve, same counter (`chars/4`, approximate, as everything
below is labelled), same replies — the mock answers every call with the same
fixed text, so the four recordings differ only in the boundary and the policy.
Reuse and token counts are properties of the message sequence, decided before the
call; the mock is legitimate for both, as it was for the eviction table. Task
success is not measured here and cannot be, and that is the important gap.

The numbers come out of the recordings with:

```python
for line in open(path):
    m = json.loads(line).get("message", {})
    if m.get("type") == "budget":   buckets[m["turn"]] = {b["name"]: b["tokens"] for b in m["buckets"]}
    if m.get("type") == "prefix_reuse": reuse[m["turn"]] = m["shared_tokens"] / m["prompt_tokens"]
    if m.get("type") == "task_folded":  folds.append(m)
```

## Reuse per turn, 20 turns into a 1024-token window

| turn | 2–5 | 6 | 7–10 | 11 | 12–15 | 16 | 17–19 | 20 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| plain · `turn` | 89–92% | 93% | 94→**48%** | 50% | 50% | 50% | 50% | 50% |
| plain · `block` | 89–92% | 93% | 94→**67%** | 92% | 93–94%, **66%** at 15 | 93% | 93–94% | 94% |
| tasks · `turn` | 91–92% | **78%** | 92–93% | **81%** | 92–94% | **83%** | 93–94% | **51%** |
| tasks · `block` | 91–92% | **78%** | 92–93% | **81%** | 92–94% | **83%** | 93–94% | **66%** |

The bold numbers are the rewrites. Three shapes:

- **Eviction under `turn` is a cliff.** From turn 10 the history is rewritten
  from its front on every call and reuse sits at 50% — the system and tool blocks
  and nothing else — for the rest of the session. Same finding as this morning,
  at a floor of 50% instead of 3% because the tool definitions are now a large
  constant prefix that survives everything. **The floor rose; the cliff did not
  move.**
- **A fold is a dip, not a cliff**: ~14 points on the turn after the close, and
  the next turn is back at 92%. A cut whose replacement is small and lands after a
  large stable prefix costs far less reuse than an eviction that moves the front
  of the history.
- **With tasks, the eviction policy stops mattering.** 88.6% against 89.4%: the
  history never grows big enough for per-turn eviction to fire more than once.

## What it cost and what it bought

|  | mean reuse | tokens sent | `history` | `tasks` | history + tasks |
| --- | ---: | ---: | ---: | ---: | ---: |
| plain · `turn` (baseline) | 69.9% | 16 397 | 6 641 | 0 | 6 641 |
| tasks · `turn` | **88.6%** | 15 174 | 2 103 | 3 315 | 5 418 |
| plain · `block` | 89.9% | 15 294 | 5 538 | 0 | 5 538 |
| tasks · `block` | 89.4% | **14 976** | 2 103 | 3 117 | 5 220 |

Each fold replaced 6 entries of ~315 tokens with a summary of 66–80.

So, the answer to the question, in three parts:

- **Against the naive policy, folding wins outright**: 70% → 89% mean reuse and
  7.5% fewer tokens sent. It gets there differently from block eviction — it
  keeps the history small enough that eviction rarely fires, rather than making
  eviction cheaper.
- **Against block eviction, folding does not win on reuse** (89.9% → 89.4%,
  which is noise in this direction) and wins slightly on tokens (−2%). The two
  are **not additive**: they are two ways of not rewriting the front of the
  history often, and doing both mostly does what either one does.
- **The scaffolding is not free, and it is the surprise.** After four folds the
  `tasks` bucket is 3 315 tokens against a `history` of 2 103 — more than half of
  what the retained window costs is plans and summaries. Folding replaced a large
  evictable history with a smaller one plus a scaffolding that keeps growing,
  and the net is 18% (`turn`) or 6% (`block`) fewer tokens, not the collapse the
  shape of the idea suggests.

**One caveat, and it biases the scaffolding upwards.** The mock does not answer in
a plan block, so every plan here is its 40-word canned reply taken as prose steps.
A parsed four-step plan is roughly a third of that, and the summary restates the
plan, so both halves of the `tasks` bucket shrink with it. The measured 3 315 is an
upper bound; the direction of the error is known and the size is not.

## What this changes

Nothing is reverted and nothing is promoted. The fold stays what it was — the
preferred cut point, with the threshold as the fallback — and the design doc now
says what it costs instead of that it is unmeasured. What the table argues for is
narrower than the plan claimed: **the boundary's win is over the default policy,
and over `block` it is a token win, not a cache win.** The reason to keep it is
the two payoffs a threshold cannot give at any reuse figure — the cut lands where
the work ended, and the transcript collapses the same thing the context does.

## Still open, and now with preconditions that are closer

| Question | Precondition |
| --- | --- |
| Does the summary lose something the task needed? | a real model — the one thing the mock cannot answer, and the reason to be careful |
| What the scaffolding costs with plans that parse | a model that answers in the block, or a fixture that does |
| Does the fold pay for itself in *seconds*? | llama.cpp with a real prompt cache; reuse is still a proxy for time |
| Is the planning call free, as claimed? | it is invisible to the instrument: it sits between two turns and emits no `prefix_reuse`. Measuring it needs the planning prompt on the trace channel |
| Compaction *within* an overflowing task | a task long enough to overflow alone, which is where the threshold is still the only answer |

# 2026-08-27, third pass: the two caveats, closed — and one of them reverses the result

Yesterday's table shipped with two things stated and not measured, and the
instructions say a strategy is measured. Both are now closed, and closing the
second one turns the token result the other way round. That is the whole reason
the hole mattered.

## What was wrong with the instrument

**A planning call was invisible.** It sits between two turns and is not one, so
it emitted no `prefix_reuse`, appeared in no budget, and counted towards no
total. Every "tokens sent" figure for a tasks run was therefore missing one whole
prompt per task — and the claim in the plan above, that proposing costs no cache
because it rides the same prefix, was not checked by anything.

`TraceMessage::PlanCall` now carries the exact prompt, its size, and what it
shared with the call before it. Two decisions inside that:

- **`PrefixTracker` chains every *call*, not every turn.** After a proposal the
  next turn is measured against the planning prompt, because that is what the
  server's cache actually holds. Measuring it against the turn before the
  proposal would report reuse against a prompt that is no longer there.
- **The size travels outside the `Option`.** Reuse is undefined on a session's
  first call; its size is not, and a total that skipped it would be wrong by a
  whole prompt. So `PlanCall` carries `prompt_tokens` always and `shared`
  optionally — which is exactly the mistake this pass exists to fix, avoided one
  level down.

**And the plans were not plans.** The mock answered planning calls with its
canned paragraph, which the parser rejects, so every plan in a measured run was
prose taken as steps — a bigger plan, and a bigger summary restating it. The mock
now answers a request that names the ```plan block with a three-step plan that
parses, unless replies were scripted, in which case what was scripted still wins.

One more thing landed with them, because the Ollama runs would have been fiction
without it: **the window is now sent to the backend** as `options.num_ctx`.
Ollama's own default is a couple of thousand tokens and it truncates silently, so
a run budgeting 8k against a server serving 2k measures a prompt the model never
saw.

## The table, re-run

Same four recordings as yesterday, same script pair, same window and counter.

|  | reuse, turns | reuse, **all calls** | turn prompts | planning | **total sent** | `history` | `tasks` |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| plain · `turn` (baseline) | 69.9% | 69.9% | 16 397 | — | 16 397 | 6 641 | 0 |
| plain · `block` | 89.9% | 89.9% | 15 294 | — | 15 294 | 5 538 | 0 |
| tasks · `turn` | 92.3% | **91.1%** | 13 954 | 2 559 | **16 513** | 2 103 | 2 095 |
| tasks · `block` | 92.3% | **91.1%** | 13 954 | 2 559 | **16 513** | 2 103 | 2 095 |

Per turn, the tasks runs are flat: `91 90 91 92 92 92 91 92 92 93 93 91 92 92 93
94 92 93 93 94`. Yesterday's series had a ~14-point dip after every close. **The
dip did not go away — it moved onto the planning call**, which reuses 81%, 83%,
85% (the first has nothing to measure against). The fold is a rewrite and
something has to pay for it; what changed is that the instrument can now see
which call does.

Plans that parse also halved the scaffolding: `tasks` is 2 095 against yesterday's
3 315, and each fold now replaces ~290 tokens with 40–54 instead of 66–80.

## What this changes, and it is the headline

**Folding buys reuse. It does not buy tokens.**

- Counting only turn prompts, tasks send 15% less than the baseline — which is
  what yesterday's table reported, and it was measuring three quarters of the
  session.
- Counting the planning calls, the tasks runs send **more** than either
  baseline: 16 513 against 16 397 (`turn`) and 15 294 (`block`). Four planning
  calls at 557–718 tokens are 15% of everything this session sent.
- Reuse survives the correction and is still the strongest result: 91.1% over
  every call, against 69.9% and 89.9%. Against the default policy that is a large
  win; against block eviction it is small.
- **With tasks, the eviction policy stops existing.** The two tasks rows are
  identical in every column: the history never grows enough for either policy to
  fire.

The planning call is a per-task cost against a per-turn benefit, so the ratio is
task length. At five turns a task it is 15% of the session; at fifteen it would be
about 5%. **A design that proposes a plan per task therefore wants tasks that are
worth planning** — which is the granularity warning from the modes record,
arriving as a number instead of an intuition.

Nothing is reverted. The reason to keep the boundary is the reuse figure and the
two things a threshold cannot give at any figure; the reason not to oversell it is
in the total column, which is the one a token budget actually pays.

# 2026-08-27, fourth pass: a real model, and two blind spots it found

The AGENTS.md section for this had never been run. It has been now, following its
own recipe exactly: `ollama serve` with `OLLAMA_KEEP_ALIVE=30m` set before it
started, `qwen2.5-coder:7b` pulled alongside `14b` and `32b`, the HuggingFace
tokenizer fetched to `~/models/qwen2.5-coder-7b/tokenizer.json`, and the same
`steady-state`/`steady-state-tasks` pair the mock measured, run with
`--context-limit 8192 --reserve 512 --tokenizer ...`. `ollama ps` confirmed
`num_ctx` reached the server (`CONTEXT 8192`), and a scripted `run_command` call
on this Darwin box came back denied with the exact verdict text AGENTS.md
describes — nothing in the setup instructions was wrong.

Two things the mock could not have shown turned up anyway.

## The scripts carry no grounding, so "does the answer survive the fold" has no baseline

`steady-state.txt` was written uniform-on-purpose for measuring eviction
mechanics against a mock that echoes fixed text — it injects no file, no
design doc, nothing about this repository. Turn 1, against a real model, asking
"what does the context manager do?":

> A context manager in Python is a way to manage resources such as files,
> locks, and network connections... The primary methods used in a context
> manager are `__enter__` and `__exit__`.

That is a correct answer to a question nobody asked. Every turn in both
recordings is like this: fluent, generic software-consulting prose about
"strategy" and "accountability" that never once names a bucket, a policy, or a
file in this project, because nothing in the prompt ever told the model this
project exists. The planning calls confirm it from the other side: task 1's
plan didn't parse at all (prose steps, one of them a garbled attempt to invent
a `{"steps": ...}` block from scratch); tasks 2–4 parsed cleanly but planned
against files that don't exist — `src/eviction.py`, `src/comparison_logic.py`,
`project_status.md` — Python paths, in a Rust workspace the model was never
shown. `"parsed": true` is a syntax check, not a grounding check, and it will
say yes to a plan that is fiction.

So AGENTS.md's "whether the answers after a fold still refer to what the task
did" is not answerable with this pair, in either direction: there is no
correct, grounded pre-fold answer for a fold to lose. Testing fold fidelity
needs a script that actually fuses real file content into a turn — the `code`
bucket exists for exactly this and neither fixture script uses it.

## A tool call inside a turn is invisible to `prefix_reuse`, the same way a planning call used to be

Turn 12 of `steady-state-tasks` (task 3, still working from a hallucinated
plan) had the model call `read_file` on `src/your_count_system.py` — another
path that doesn't exist, denied by `os error 2`. That call makes turn 12 two
model calls, not one: the first ends in a tool block, the second sees the tool
result and answers. `budget`/`prefix_reuse` recorded only the first: 1 590
tokens, 1 000 shared. `ended.usage.prompt_tokens` — the backend's own count for
the call that actually finished the turn — was **3 552**. Every other turn in
both recordings has our count within 3 tokens of the backend's; turn 12 is off
by 1 962. Nothing crashed and nothing looked wrong in the budget panel, because
the panel only ever heard about the first of the two calls.

This is the exact shape of the gap `PlanCall` was added to close two passes
ago — a call that sits between two tracked turns and emits no `prefix_reuse` —
recurring one level down, inside a turn, for the tool-use round trip. The fix
is the same shape too: a trace event for the intermediate call, not just the
one that ends the turn.

## The numbers, with both caveats priced in

Same two recordings, `--context-limit 8192 --reserve 512`, `qwen2.5-coder:7b`,
real tokenizer. Neither run ever evicted — the window is wide enough that 20
short turns fit without either policy firing once, so this pair tests
counting, reuse and grounding, not eviction.

|  | reuse, turns | reuse, all calls | turn prompts (backend) | planning | total |
| --- | ---: | ---: | ---: | ---: | ---: |
| plain · `turn` | 89.5% | — | 66 986 | — | 66 986 |
| tasks · `turn` | 81.3% | 80.7% | 31 879\* | 3 177 | 35 056\* |

\*Turn 12's contribution is the second-call total only, per the blind spot
above — the first call's prompt (~1 590–1 600 tokens by our count, backend
figure unknown) is missing from both the turn-prompts column and the total.
The true total is higher by roughly that much, on both sides equally since the
missing call belongs to the tasks run either way.

**Folding wins on both reuse and tokens here — more than half off, not the ~2%
of the mock's third pass — and the sign of the token result flips from that
pass entirely.** The difference is the window. The third pass fixed
`--context-limit 1024` specifically so the baseline would evict and the two
policies would be comparable; at that width the baseline's history is capped,
so folding could only win on how cheaply eviction happens. At `8192` the
baseline never evicts at all, so its history compounds every one of the 20
turns with nothing pushing back — plain `turn` sends 66 986 tokens total against
tasks' 35 056 (undercounted low) because tasks keeps resetting to a small
history four times and plain never resets. **A window this comfortable relative
to the task is exactly the regime where the naive baseline is at its worst**,
and it is also the regime `luu` targets (7B–32B, 8K–32K) — so the mock's
"folding barely wins on tokens" conclusion holds at the width chosen to force a
fair eviction comparison, and does not hold at the width the tool actually
ships for. State the configuration beside the figure, same rule as before, one
context-limit further in.

Chat-template overhead was the one number that behaved exactly as predicted: on
every plain-run turn (no tool calls, no plan calls to hide a second call inside
one turn number), backend `usage.prompt_tokens` minus our tokenizer count is a
flat **+2**, turn after turn — the stable gap AGENTS.md said a correct chat
template would produce.

# 2026-08-27, fifth pass: the blind spot the M4 run found, closed

The fourth pass found a turn whose prompt we counted at 1 590 and whose backend
count was 3 552, on a run where every other turn agreed within 3 tokens. It was
not a counting error: **a turn that uses a tool is several model calls**, the
backend's `usage.prompt_tokens` is summed over all of them, and the trace channel
only ever heard about the first. Our number and theirs were counts of different
things, and the budget panel presented the difference as chat-template overhead.

Same shape as the planning call two passes ago, one level down, and the same fix.

## What landed

- `TurnEvent::ModelCall { step, messages }` — the agent loop announces **every**
  call it makes, before making it, with the exact messages. Including the first:
  the loop states what it does and the caller decides what that is worth, rather
  than the loop deciding which of its own calls are interesting.
- `ServerMessage::from_turn_event` now returns `Option`. That is the point where
  the trace/protocol split stops being a convention and becomes a type: a model
  call explains the agent rather than driving it, so there is now an internal
  event that provably cannot reach a stdio consumer.
- `TraceMessage::StepCall { turn, step, text, prompt_tokens, shared }` — emitted
  from the second call on, measured through the same `PrefixTracker` chain as
  turns and planning calls, so the chain is every call in the order they were
  sent. The first call is not re-measured: it is the turn's own prompt, already
  measured beside its budget, and measuring it twice would put it in the chain
  twice.
- `chat` shares one tracker with its printer task (`Arc<Mutex<…>>`) because the
  round trips arrive there. Two trackers would measure one session against two
  different pasts.
- The read API grows `TurnView.extra_calls`, and the budget panel says *"this
  turn made 3 model calls: the bar is the first, and the tool round trips sent
  1 155 tokens more"* instead of quietly adding them to the template gap.

On the `tool-calls` fixture — one allowed read, one denied, three model calls —
the second call is 547 tokens with 89% shared with the first. That 547 was the
whole of the discrepancy this pass exists to explain, and it was never anywhere
in the recording before.

## What it does not fix

The comparison is only honest per *turn*: `usage` still arrives once, summed, on
`Ended`. Making the two directly comparable per call means reading the backend's
own per-call counts, which `run_agent_turn` currently sums and discards. That is
worth doing when the question is "which call was expensive"; today's question was
"is the total a lie", and it was.

The other blind spot from the fourth pass is untouched: nothing can fuse a file
into a turn, so the scripts stay ungrounded and *does a summary lose what the
task needed* still cannot be asked.
