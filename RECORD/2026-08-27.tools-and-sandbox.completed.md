# Tools and the sandbox: the kernel holds the subprocess

2026-08-27

## The problem

`agent-core` can hold a conversation and cannot do anything. The design's work
order puts tools and the application-level sandbox at step 4, and two of the
things still ahead — relevance selection over a repo map, pruning of tool
results — say in as many words that they wait on tools existing at all.

So this is the step that makes the agent act. It is also the step where the
design's first commitment stops being free:

> **The model never executes anything.** It emits a structured request; the
> program parses it, validates it against the `SandboxPolicy`, and executes
> real Rust code.

Validating in our own code is necessary and it is not sufficient. An in-process
check is a decision taken *before* the syscall, by a program that then makes the
syscall itself; a subprocess makes its own, and nothing we wrote is in the way.
`run_command("cargo", ["test"])` hands a compiler, a build script and every test
in the tree the same authority the agent has. Checking the string `cargo`
against an allowlist and calling that a sandbox is the part that would be a lie.

There are three rungs on the ladder, and the design currently names the first
and the third:

1. **In-process checks.** Canonicalize, compare against the policy, refuse.
   Everything an in-process tool can have. Nothing a subprocess gets.
2. **Kernel enforcement, same process tree, no image and no daemon.** Landlock
   for the filesystem, seccomp for sockets, applied to the child between `fork`
   and `exec`.
3. **A container.** Podman or Docker, `--cap-drop=ALL`, bind mounts.

**This plan builds 1 and 2, and 2 is what makes 1 worth having.** Level 3 stays
where the design put it: packaging, later.

## Why level 2 first, and not level 3

Level 3 is a better boundary and a worse first version, for reasons that are all
about who is running this:

- **It needs something installed.** Podman or Docker, a daemon or a rootless
  setup, an image built and kept current. Level 2 needs a Linux kernel from 2021
  and nothing else — it is `prctl` and two syscalls in the child.
- **The backend is on the host.** The design already says so: inference wants
  the GPU, so a container would isolate tool execution only and talk back out
  over an exposed socket. That is the same split level 2 gives, without the
  socket.
- **It costs a rebuild per iteration.** A dev loop that goes through
  `podman build` to try an edit is a dev loop people turn off.
- **The two are not alternatives.** Landlock is inherited across `exec` and
  cannot be dropped, so a level-2 child stays restricted inside a container the
  day there is one. Level 3 is defence in depth on top of this, not instead of it.

The honest cost is that level 2 is **Linux-only**. macOS gets level 1 for
in-process tools and nothing for subprocesses — which is why the policy has an
`enforcement` setting, and why its default refuses to run commands rather than
running them unheld. See *What happens when the kernel cannot* below.

## The policy

One TOML block per project, read by `luu` and handed to `agent-core` as a
`SandboxPolicy`:

```toml
[sandbox]
enforcement = "kernel"          # or "best-effort"
network = false
commands = ["cargo", "git", "rg"]

[[sandbox.paths]]
path = "."
access = "read-write"

[[sandbox.paths]]
path = "~/.cargo"
access = "read"
```

Three access levels, because "may read this tree" and "may run binaries out of
this tree" are different grants and the difference is one line:

| `access` | in-process | Landlock |
| --- | --- | --- |
| `read` | open for reading, list | `ReadFile \| ReadDir` |
| `execute` | the above | `AccessFs::from_read(abi)` — adds `Execute` |
| `read-write` | the above, plus write, create, delete | `AccessFs::from_all(abi)` |

**Longest match wins.** A narrower rule under a broader one grants more, not
less, so `path = "."` at `read` and `path = "./target"` at `read-write` reads as
it looks.

The default policy, with no file and no flags, is read-write on the working
directory, no network, and **an empty command allowlist** — so `run_command`
denies everything until something is named. An empty list that meant "anything"
is the failure mode this whole file exists to avoid.

### There is no deny list

The design says `denied_paths`. This drops it, which is the one place this plan
argues with what is written down.

Landlock is allow-only: a ruleset grants access beneath paths, and everything
not granted is denied. There is no rule that subtracts. So a `denied` entry
could be honoured by the in-process checker and could not be honoured in a
subprocess at all — two different sandboxes wearing one config file, with the
weaker one applying exactly where the danger is. `denied = ["./.env"]` would
stop `read_file` and would not stop `cat .env`, and nothing in the config would
say so.

The way to deny is to not grant. Where a real subtraction is wanted later, the
mechanism is granting the siblings, and it should be a generated expansion of
the roots rather than a second kind of rule.

### The commands allowlist is a program name, never a shell string

`run_command` takes `command` plus `args`, and never a string to be parsed by a
shell. A shell string makes the allowlist meaningless — `sh -c "cargo test; curl
evil"` passes any check that looks at the first word. Anyone who wants a shell
puts `sh` in `commands`, and then the grant reads as what it is.

### System roots come with the grant, and only for the child

A command cannot run without reading its own interpreter and libc. So when
`commands` is non-empty, the child additionally gets `execute` on a fixed set of
system roots — `/usr`, `/bin`, `/sbin`, `/lib`, `/lib64`, `/etc`, `/opt` — read
and execute, never write. They are in the code, they are listed by `luu tools`,
and they are part of the verdict.

**They apply to a subprocess and to nothing else.** The justification is that a
command cannot read libc; it says nothing about `read_file`. If the same roots
answered an in-process check, `commands = ["ls"]` would quietly have granted the
agent `/etc`, which is a wider sandbox than the line the user typed. So the
path check has two entry points: the one tools use, which sees only what was
written down, and the one `run_command` uses for the program it is about to
exec, which sees the roots the child's ruleset will carry. This was found by
recording a fixture and reading the verdict, which is the argument for building
the debug client before the thing it inspects.

Everything else the command needs is the user's to grant. `cargo` wants
`~/.cargo`; that is a line in the policy, and having to write it is the design's
"one informed approval" rather than a prompt per call.

## What level 2 actually does

In the parent, before spawning:

- Build a Landlock ruleset from the resolved roots at the highest ABI this crate
  knows, best-effort, so an older kernel gets a smaller handled set rather than
  an error. Take the ruleset's file descriptor.
- Compile a seccomp BPF program: `socket(2)` with `AF_INET`, `AF_INET6` or
  `AF_PACKET` returns `EAFNOSUPPORT` unless `network = true`; `ptrace`,
  `process_vm_readv` and `process_vm_writev` return `EPERM` always. Everything
  else is allowed.

In the child, inside `pre_exec`, which is after `fork` and before `exec`:

- `prctl(PR_SET_NO_NEW_PRIVS)`, then `landlock_restrict_self(fd)`, then the
  seccomp filter. Raw syscalls and no allocation — `pre_exec` runs in a forked
  child of a threaded process, where another thread may have been holding the
  allocator's lock at the moment of the fork.

The ruleset is *built* in the parent for that reason: opening a file descriptor
per root and assembling the rules is ordinary allocating code, and it has no
business running after a fork.

Two things this does not claim to be:

- **Not a network namespace.** Blocking `socket` for the internet families stops
  a program from opening a connection; it does not stop one that inherited a
  socket. Nothing inherits one here, but the mechanism is narrower than
  `--network none` and should be described as what it is.
- **`AF_UNIX` stays open.** libc needs it, and a Unix socket is reachable only
  through a path, which Landlock covers from ABI v6.

## What happens when the kernel cannot

`enforcement` decides, and it is the only place in this design where a security
property is a setting:

- `"kernel"` (the default) — a subprocess runs only if the kernel took the
  ruleset and the filter. On macOS, on a kernel without Landlock, on an
  architecture seccompiler has no target for: `run_command` is **denied**, and
  the denial names what is missing and the flag that lowers the bar. In-process
  tools are unaffected; they never had kernel enforcement to lose.
- `"best-effort"` — apply what this kernel has and report the gap.

The gap is reported either way, per call, in the verdict:

```rust
pub enum Applied {
    Process,                                  // our own check, before the fact
    Kernel { how: String },                   // "landlock ABI v6 + seccomp"
    Partial { how: String, missing: String }, // and what is missing is the point
}
```

Nothing in this system may say "sandboxed" without saying by what. A run whose
subprocesses were held by the kernel and a run whose subprocesses were held by
nothing are not the same run, and after the fact the recording is the only thing
that could tell them apart.

## The tool loop

The model emits a request; the program parses it, checks it, runs real Rust:

```
prompt ─► model ─► text with a ```tool block?
                     │ no  → the turn's answer
                     │ yes → parse → check policy → execute → append → model
```

Capped at `--max-tool-steps` (8). Exhausting it ends the turn with a new
`EndReason::ToolLimit` rather than silently answering from a half-finished
investigation.

Two decisions inside it:

**The steps are messages, and they alternate.** A turn renders as
`user(prompt)`, then `assistant(call) · user(result)` per step, then
`assistant(answer)`. That is the design's fusion rule applied to a new kind of
content, and it means a turn with tool calls is still one turn: it is evicted
whole, and the model on the next turn can see that it already read the file.
Storing only the final answer would have been less code and would have made the
agent forget its own work between turns.

**How the model expresses a call is a transport detail.** `ToolCall` is the
type; the parser is one function. Today it reads a fenced ```tool block out of
plain text, which works against any backend including a 7B that has never seen a
tool API. Native function calling and the GBNF grammar the design asks for
replace that function and nothing else. Doing it the other way — teaching the
Ollama backend about tools first — would have put the loop behind a backend
feature the mock cannot emit, and the loop is the part with the security
property in it.

## The tools

`read_file`, `list_dir`, `edit_file`, `write_file`, `run_command`.

`edit_file(path, old_string, new_string)` replaces an exact, unique occurrence
and fails if there are none or several, per the design: it is the cheap edit in
output tokens, which is the slow half of local generation.

Tool output is capped at 8 KiB with a `truncated` flag. Pruning old results out
of the context is a later, measured change; a hard cap now is the part that is
not a strategy.

Definitions go in the system block, which is the cached prefix, so the rendering
is byte-stable by construction: tools sorted by name, schemas serialized through
`serde_json`'s sorted maps, and a test that builds the same schema with its keys
inserted in the opposite order and asserts identical bytes. That test exists
because the thing that would break this is a transitive dependency turning on
`serde_json/preserve_order`, and nothing else in the build would notice.

The budget gains a `tools` bucket next to `system`, as the design's stacked bar
already says it should.

## What this costs

- **Three dependencies**, all Linux-gated except `toml`: `landlock`,
  `seccompiler` (pure Rust, no libseccomp), `libc`. `cargo build` on macOS pulls
  none of them.
- **One `unsafe` block**, in `pre_exec`, doing three syscalls.
- **A signature change**: `Context::push_turn_with_steps` alongside
  `push_turn`, and `Turn` gains `steps`.
- **TOCTOU in the in-process checks.** We canonicalize and then open, and
  between those two a component could become a symlink. This is a real hole and
  it is level 1's hole: the answer for subprocesses is level 2, and the answer
  for in-process tools is `openat2` with `RESOLVE_BENEATH`, which is Linux-only
  and is not in this change. Recorded rather than papered over.

## Rejected

| | Why not |
| --- | --- |
| Container first (level 3) | Needs an installed runtime and a rebuild per iteration; isolates the same boundary level 2 does, with the backend outside it either way. Still the right level 3. |
| `libseccomp` FFI | A C library and a build dependency to get what `seccompiler` gives in pure Rust. |
| A syscall allowlist instead of a denylist | An allowlist that has to admit every syscall `cargo` makes is a permanent maintenance surface that fails closed on the user's machine at the worst moment. The denylist is narrower than an allowlist and says exactly what it stops. |
| `unshare(CLONE_NEWNET)` for the network | Needs a user namespace, which is disabled outright on several distributions and inside most CI. Denying the socket families is weaker and always available. |
| `denied_paths` | Not expressible in Landlock, so it would apply in-process and not in a subprocess. See above. |
| A shell string for `run_command` | Defeats the allowlist it is checked against. |
| Prompting per tool call | The design already rejected this for tasks, and the reason holds: a prompt per call trains people to click yes. The policy file is the standing approval until tasks exist. |
| Landlock's own network rules (ABI v4) | TCP bind/connect only, so UDP walks out. seccomp covers the families; Landlock's network rules can be added on top later. |

## Still open

- **Nothing confirms anything yet.** The design says a task is approved before
  it runs and the approved plan *is* the `SandboxPolicy` for that task. Tasks do
  not exist, so the file is the standing approval for the session. When tasks
  land, the policy becomes per-task and this becomes its floor.
- **Native function calling and GBNF**, replacing the text parse.
- **`openat2(RESOLVE_BENEATH)`** for the in-process tools, closing the TOCTOU.
- **Pruning tool results** out of the history, which now has results in it to
  prune and a bucket to watch shrink.
- **Level 3**, with the level-2 restrictions still applied inside it.
- **A verdict is not yet recorded as an event.** `tool_call` and `tool_result`
  are on the protocol, so a recording has them; the eviction tombstones the
  persistence section asks for are still the same gap they were.
