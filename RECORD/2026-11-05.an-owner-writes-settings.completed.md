# An owner writes Settings

> haz que el owner logueado pueda escribir Settings

## The problem

A luu installed with the chart is `public`, and its owner cannot add an
engine, a provider or a policy from the page: every Settings write is
refused with *this server is bound off loopback*. `providers_editable` is
`address.ip().is_loopback() && !auth.has_users()`, set once at startup, so on
a server with users it is false for everyone, the owner included. The only
way left is `kubectl exec` and an editor on `config.toml`, which is the
thing the page exists to replace.

[`2026-11-03.users-and-a-code-by-email`](2026-11-03.users-and-a-code-by-email.WIP.md)
already decided the answer, as step 3: **owner gets exactly what loopback
gets today**. This is the owner's half of that step, without admin and
without Settings → Users.

## The proposal

One function decides, per request, whether Settings may be written:

```rust
fn settings_editable(state) -> bool {
    state.providers_editable || who() is an owner
}
```

`who()` is the login `require_login` put in scope, after it checked the
cookie and, on every write, `Origin`. Every place that read
`state.providers_editable` to allow a write or to say `editable` in a view
reads this instead: providers, engines, policies, tool steps, resend rules,
authority notes, icon theme, brand marks, the workspace rename, and the
destination rule that keeps a session's prompts on this machine.

`engines_allowed` and `workspace_writable` also check `Host`, against DNS
rebinding: a page on another domain that resolves to 127.0.0.1 is
same-origin with a loopback server that asks nobody who they are. An owner's
request already carries a `SameSite=Strict` cookie and an `Origin` that is
this server's, which is what the `Host` check stood in for, so for an owner
it is skipped.

## What it does not change

- **Peers and hosts.** A server with users does not dial (`peers_allowed`),
  and a user's hosts are the luus they linked, not `[host.*]`. Both keep
  reading the address, which keeps them off.
- **`[terminal] host = "loopback"`**: a rule in the file with its own
  meaning, *a browser on this machine*. An owner who wants a host shell
  online sets it to `always`, which they can now do from Runtimes.
- **Users and admins.** A user's request still reads the address. Admin is
  step 3's other half.

## Rejected

- **Making `providers_editable` true on a server with users.** Every user
  would write `config.toml`, which is the machine's.
- **Trusting loopback in `public`**, for the reason the users record gives:
  a user's command with network reaches `127.0.0.1:7878`.

## Still open

- **The refusals still say *bound off loopback*** to a user who is not an
  owner, which is true and is not the reason. They want a sentence of their
  own when roles get admin.
- **A user who is not an owner cannot choose a provider that sends off this
  machine**, and in a cluster nearly every provider does. Whether a provider
  the owner wrote is one every user may send to is a decision for the
  admin half.

## Built, the same day

As proposed. `settings_editable` and `is_owner` sit beside
`engines_allowed`; every write and every view's `editable` that read the flag
reads them, except the ones *What it does not change* names.

**Verified:** `tests/server_config.rs`, against the binary, on a public
server: an owner's login writes `max-tool-steps` (`200`, and the file has
it) and is told the engines are editable; a user's login is refused both
the tool limit and the engines (`403`). The test that asserted the owner's
`403` was changed, because that was the gap this closes. The rest of the
workspace passes but for two tests that fail on this Mac before the change
too (`links::providers_cross_both_ways_and_their_keys_stay_home`, whose
socket goes to the temp folder when `LUU_HOME` is long, and
`agent-core`'s `the_policy_says_where_a_command_s_scratch_goes`).

**Not verified:** the page clicked through as an owner online, and an engine
started inside the chart's pod.
