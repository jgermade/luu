# The name is luu, and the state has a home the user picks

**Status:** Built. The rename landed with this record, and so did the one
decision the rename could not make on the user's behalf.

## The problem

Two things, and they are the same thing twice.

**1. The project has two names and only one of them is real.** The design's
*Naming* section decided **Loude** as the project and `luu` as the CLI alias,
with the binary installed under both. That was a decision about a name nobody
had lived with yet. It has been lived with: everything a person types, every
crate, the policy files (`luu.toml`, `luu.container.toml`), the repository
itself — all `luu`. What is left of `Loude` is a title on three documents, a
second binary nobody invokes, a container image tag, a system prompt, a domain
string inside a signature, and a design doc whose filename is the old name. A
second name that appears only in the places a person does *not* type is not an
alias, it is drift.

So: **the project is `luu`.** One name, one binary.

**2. The state directory is `~/.loude`, and it was never chosen.** It is the
old name in the one place a rename cannot simply be applied — the path already
exists on the machines that have run the thing. And the *right* answer to where
a Unix program keeps per-machine state is not one answer: `~/.luu` is what a
dotfile-shaped tool does, `~/.config/luu` is what the XDG basedir spec asks for,
and the argument between them is old, unresolved, and genuinely a matter of how
the person keeps their home directory. Picking one and calling it the default
makes us wrong on half the machines.

## The proposal

### The rename

`Loude` → `luu` everywhere outside `RECORD/`, including:

- `loude-design.md` → `luu-design.md`, and its *Naming* section rewritten to say
  one name rather than two.
- The second binary (`crates/luu/src/bin/loude.rs`) is deleted, and the release
  job stops packaging it. Two `[[bin]]` entries over one `main` was the
  mechanism for an alias; with no alias there is nothing to mechanise.
- `loude-worker:dev` → `luu-worker:dev` (image tag, `Containerfile`,
  `luu.container.toml`, the runtime's defaults and its tests).
- `CANONICAL`, the first line of every signed approval, `loude-approval v1` →
  `luu-approval v1`. **This invalidates every signature made by an earlier
  build.** It is in the signed bytes precisely so that a signature cannot be
  replayed against a different shape, and the failure mode is the safe one — an
  old signature stops verifying, it does not verify against something it did not
  mean. The version stays `v1` because the *shape* did not change; nothing has
  been released, so the population of affected signatures is the ones on this
  machine.

**`RECORD/` is not touched.** It is append-only, and a record is what was
believed on the day it was written — a dated file that says `Loude` is correct
about the day it says it. The cost is real and is accepted: the links in older
records that point at `loude-design.md` now dangle. Rewriting twenty-eight files
to repair a link would erase the evidence that the name ever moved, which is the
one thing those files are for. This record is the forwarding address.

### The config directory

Where `luu` keeps *this machine's* state — the session store, and by convention
the approval key. Resolved in this order:

1. **`LUU_HOME`**, if set and non-empty. An explicit answer ends the question,
   and it is what a test or a container run wants.
2. **`~/.luu`**, if it already exists.
3. **`$XDG_CONFIG_HOME/luu`** (or `~/.config/luu` when `XDG_CONFIG_HOME` is
   unset), if it already exists.
4. Otherwise nothing has been chosen yet — **ask, once**.

Steps 2 and 3 are what makes the answer stable without a config file to hold it:
**the directory's own existence is the record of the choice.** A setting that
says where the settings live has to live somewhere, and that somewhere is the
question being answered. So the first run creates the directory it was told to
create, and every run after it finds one and stops asking. `~/.luu` is checked
first because it is the deliberate one — nothing else puts a directory there,
while `~/.config` is full of directories other programs made.

The prompt, on a terminal:

```
luu has no state directory on this machine yet. Where should it keep
sessions and keys?

  1) ~/.luu
  2) ~/.config/luu   (XDG)

Choose [1/2] (default 2):
```

**When stdin is not a terminal, it does not ask** — it takes `~/.config/luu`,
says so on stderr, and names `LUU_HOME` as the way to have said otherwise. A
prompt nobody can answer is a hang, and a hang in `luu stdio` is a parent
process waiting forever on a pipe. The default is the XDG one because the
machines that cannot answer are the scripted ones, and that is the convention a
script expects.

**`~/.loude` is not migrated.** No release has shipped; the population is
developer machines, and `--store <path>` reaches an old file for anyone who
wants one. A migration is code that runs on every start, forever, to serve a
window that closes this week.

## What it costs

- Every signature made before this stops verifying. Fails closed; see above.
- Dangling `loude-design.md` links in `RECORD/`. Accepted, deliberately.
- Anyone with a `~/.loude` gets a fresh session store and keeps the old one as
  a directory nothing reads.
- One more thing that can block on stdin. Bounded to: no `LUU_HOME`, no
  existing directory, and a terminal attached.

## What was rejected

- **Keeping `loude` as an installed alias.** It is the drift, not a feature.
- **Editing `RECORD/` to repair the links.** Append-only means append-only, and
  the rule is worth more than twenty-eight working links.
- **A config file that names the state directory.** It would have to live in the
  directory whose location is the question.
- **Defaulting to one location without asking.** That is exactly the choice that
  produced `~/.loude`: a path nobody picked, in a name nobody kept.
- **Asking on every command, or offering a third "somewhere else".** `LUU_HOME`
  is the third option, and it does not need a menu entry to work.

## Still open

- The approval key's location is a documentation convention
  (`luu key new --out …`), not something the code resolves. If a second thing
  ever lands in the state directory, `config::dir()` is where it goes and the
  key should move with it.
- Nothing reads `luu.toml` from the state directory, and nothing should until
  there is a setting that is about the machine rather than the project. The
  split the store's doc comment argues for — project policy is committed, machine
  state is not — is the rule that decides it.
