# Choosing fragments: the graph asked the question it is actually good at

**Status:** a proposal, the code it plans, and the run that scores it. Item 2 of
[`ROADMAP/2026-09-05`](../ROADMAP/2026-09-05/README.md), which is the project's
own differentiator and the oldest unbuilt line in `luu-design.md`:

> **Relevance over recency**: inject only the fragments the current turn points
> at, instead of the full history. The graph now exists and ranks the map's
> files; what it does **not** yet do is choose fragments, and that is this item.

## The problem

Two things are true at once and have never been put together:

1. `Fragment` and the `code` bucket have existed since the context manager did,
   and the only thing that fills them is a person typing `--fragment path:1-15`.
   [`fragment.rs`](../crates/agent-core/src/fragment.rs) says so in its own
   header: *"which turns a file belongs in is the question relevance selection
   exists to answer later."* This is later.
2. The reference graph exists, is measured, and **lost** — twice, as an
   *ordering* for the repository map
   ([`ranking-the-map`](2026-09-02.ranking-the-map.completed.md),
   [`the-map-order-probe`](2026-09-03.the-map-order-probe.completed.md),
   [`in-degree-and-fill`](2026-09-04.in-degree-and-fill.completed.md)).

The temptation after two losses is to conclude the graph was the wrong idea. That
would be the wrong lesson, and saying why is most of this record.

## Arguing with the decision already on file, rather than routing around it

`ranking-the-map` rejected Aider's personalized PageRank **for the map**, and the
reason it gave is exact:

> Aider seeds PageRank with a personalization vector pointed at the files in the
> conversation … Take the seed away and the score depends on nothing but the tree
> — so the map still changes only when the repository does, and stays a prefix
> block rather than becoming a fragment with a bad name.

Read that again as a claim about *where* things live rather than about ranking.
It says: **a per-turn score cannot live in the cached prefix.** It does not say a
per-turn score is wrong. The map is a prefix; the `code` bucket is not — it is
already per-turn, already outside everything cached, already the place a
`--fragment` goes and is then gone.

So this record does not overturn that decision, and does not need to: the
personalization that would have ruined the map is the *only* thing that makes a
selector work, and it is being put in the one bucket whose whole contract is that
it changes every turn. The map keeps its uniform teleport and its alphabet. What
changes is that a second, smaller block is chosen per turn by the same graph,
where being per-turn costs nothing that was ever being cached.

The other half of the two losses is worth stating too, because it is a different
finding than "the graph is bad": at 4096 tokens a *ranked map* holds 8 of the 38
files the corpus asks about, against the alphabet's 15. Ranking picks the files
the tree is built on. **The file a question is about is usually not the file the
tree is built on** — it is a leaf, and the ranking's whole job is to put leaves
last. A selector is asked a different question, and a leaf is exactly what it
should return.

## The proposal

`agent_core::select`, pure in the same sense `rank` is — it takes names and
outlines, not paths to read, so it is arguable without a repository:

1. **Terms from the turn's own text.** Lowercased, split on non-word characters
   *and* on `snake_case`/`CamelCase` boundaries, so `run_command` in a question
   yields `run_command`, `run` and `command`. A stop list of the words every
   question in a code corpus contains (`which`, `file`, `the`, `does`) — small
   and named in the source, because a stop list that grows silently is a
   selector nobody can reproduce.
2. **Seeds by what a file defines.** A file scores for each of its defined names
   that a term matches: a whole-name match is worth most, a match on one
   `snake_case` component of a defined name less, and a match on a path component
   least — `sandbox` in a question is weak evidence for `sandbox/mod.rs`, but it
   is evidence, and it is the kind a person uses.
3. **One hop over the reference graph.** The same edges `rank::build_edges`
   already builds: a file that *references* a seed gets a share of the seed's
   score, and so does a file the seed references. One hop and not a full
   personalized PageRank — because two hops from a leaf lands on `lib.rs`, which
   is the loss above wearing a different hat.
4. **Fill with definitions, not files.** The unit is an outline `Entry` — one
   definition and its lines — so a 2 000-line file contributes the twenty lines
   the turn points at rather than all of it. This is the part that makes it a
   *fragment* selector and not a second map, and it is what the `code` bucket has
   always taken.
5. **Out the same door as `--fragment`.** The selector emits
   `fragment::Spec { path, lines }`, which `fragment::load` reads **through the
   sandbox**. A selected path that `read_file` would refuse is refused here too,
   by the code that already refuses it. No new way to read a file exists after
   this record.

Off by default, behind `--select-tokens N` (0 = off), for the same reason
`--map-tokens` was: it changes what every prompt holds, and a default that moves
that needs a scored run behind it.

## What "better" means here, stated before the run

The corpus is
[`map-order-probe.txt`](../scripts/tasks/map-order-probe.txt) — 38 questions, one
per file, each written from its target's own module doc, chosen before any order
or selector was looked at. It is the instrument
[`the-map-order-probe`](2026-09-03.the-map-order-probe.completed.md) built for
exactly this, and its rule stands: **an instrument is not extended mid-experiment.**
Three files written since (`approval.rs`, `sandbox/proxy.rs`, `tests/stdio.rs`)
are asked about by no question, and stay that way.

What is new is that the corpus now has its key on disk
([`map-order-probe.key`](../scripts/tasks/map-order-probe.key)). Every probe in
this repository so far has waited on a person with a model, because scoring meant
reading 38 answers. **Coverage does not.** *Is the target inside what this order
or selector holds* is a structural question, and with the key written down it is
a number CI can compute on every commit with no model on the machine at all.

So, one number, measured one flag apart on the same tree on the same day:

- **Coverage** — of the 38 targets, how many are inside the block the run holds
  at 4096 tokens: the path-ordered map (the baseline, and the default), the
  ranked map, the in-degree map, and the selector.

And one number this cannot produce, said as plainly as the corpus's own record
said it: **precision needs a model.** Whether a 7B *uses* the fragment it was
handed is not answered by whether the fragment was there. A selector that wins
coverage and loses precision is a worse selector, and nothing here would notice.
That run wants a box from [`machines.md`](../ROADMAP/2026-09-05/machines.md) and
is item 2's second half.

The bar is the baseline, not zero: **the selector has to beat 15/38 at 4096
tokens on this tree**, or it is a rejected record and the flag never ships. And
because the tree has moved since that 15 was measured, the baseline is
*re-measured today* rather than quoted.

## What it costs

- **Prefix reuse falls, arithmetically.** The `code` bucket is per-turn and
  outside the cached prefix, so every selected token is a token not reused.
  That is the trade the whole item is: the map buys 870 tokens a turn that are
  cached and mostly irrelevant; a selector buys fewer that are not cached and
  meant to be relevant. **A run with selection on is not comparable on reuse to
  one without it**, exactly as a map-on run is not comparable to a map-off one.
- **The walk happens per turn**, not once per repository. Parsing this tree costs
  what `luu map` costs; a selector that re-parsed on every turn of a long session
  would be paying it every turn, so the outlines and tags are built once and
  reused across turns.
- The stop list and the three match weights are **numbers someone chose**. They
  are named in the source with their reason, and the corpus is what would catch
  them being wrong.

## What was rejected

- **Embeddings**, again and for the reason already on file
  ([`aider-repo-map`](2026-08-27.aider-repo-map.completed.md)): a graph says
  *why* a file was chosen, staleness is `mtime`, and there is no second copy of
  the user's code to ship or govern.
- **Personalizing the map itself.** That is the decision this record argues with
  above and does not take: it would rewrite the cached prefix every turn, which
  is the one property the map is built to have.
- **Full personalized PageRank from the seeds.** Two hops from a leaf is
  `lib.rs`, and the measured failure of rank order *is* that the central files
  win. One hop keeps the neighbourhood a person would call related.
- **Attaching selected fragments to every turn.** Already rejected in
  `fragment.rs` and still right: a fragment belongs to the turn that pointed at
  it, and the fold is what carries anything further.
- **Scoring by a model in this record.** It would have made the result wait for a
  box, and coverage is worth having without one. The model half is named as
  missing rather than skipped.

## Still open

- **Precision, which needs a model**, and is the half that says whether any of
  this reaches the answer.
- **A question that is not "which file".** All 38 are location questions, which
  is the corpus this tree has; a selector for "why does this test fail" is not
  measured by any of it.
- **The turn's text is the whole query.** The conversation so far is not, and a
  follow-up question that says "and that one?" points at nothing this can see.

## 2026-09-05, the same day: the run

No model and no box — that is the point of the key. `cargo test -p luu --test
select_probe -- --nocapture`, on this tree, at the two budgets, counted by the
approximate counter (`chars/4`, which is not a measurement of a model's tokens
and is labelled as one everywhere it appears — it is the same counter on both
sides of every comparison here, which is all this table needs of it).

**Held** is coverage: is the file the question is about among the fragments the
run holds. **1st** and **top-3** are where the target came in the selector's own
ordering, before the budget decided what was affordable — the numbers a bigger
budget cannot flatter.

### Coverage, against the two orders already measured

| run | at 1024 | at 4096 |
| --- | ---: | ---: |
| map, path order (the baseline) | 3 | 16 |
| map, ranked | 2 | 8 |
| map, in-degree | 2 | 7 |
| **the selector** | **32** | **38** |

Path order's 16 is this tree today; `the-map-order-probe` measured 15 on the tree
of 2026-09-03, which had three files fewer. The 1024 column is the one worth
reading: at a budget a small window actually has, a map holds **3** of the 38
answers and a selection holds **32**.

That is not a subtle result and it should not be dressed up as one: they are not
doing the same job. A map is one block for every turn and is cached; a selection
is this turn's and is not. What the number says is that *the budget spent on
being relevant to the turn buys ten times the hit rate of the budget spent on
being the same for all of them* — which is the claim the whole context-management
thesis rests on, measured for the first time in this repository.

### The ablations, and the graph's third loss

| signals, at 4096 | held | 1st | top-3 | tokens/turn | fragments/turn |
| --- | ---: | ---: | ---: | ---: | ---: |
| all (the default) | 38 | **19** | **31** | 3 582 | 14.2 |
| no module doc | 26 | 9 | 15 | 2 052 | 9.1 |
| with the graph hop | 38 | 14 | 24 | 4 061 | 16.7 |

| signals, at 1024 | held | 1st | top-3 | tokens/turn | fragments/turn |
| --- | ---: | ---: | ---: | ---: | ---: |
| all (the default) | **32** | 19 | 31 | 969 | 5.6 |
| no module doc | 19 | 9 | 15 | 800 | 4.9 |
| with the graph hop | 31 | 14 | 24 | 994 | 6.0 |

**The graph hop makes the answer worse, and it was the mechanism this module was
supposed to be about.** Switching it on moves the right file out of first place
five times in 38 and out of the top three seven times, holds no more targets, and
costs 13% more tokens. So it ships **off**, at `graph: 0.0`, exactly as
`--map-rank` did.

Why, stated so it can be argued with: a neighbour is not a relevance signal on a
tree this connected. One hop from anything the query touched is most of
`agent-core`, and what the hop actually does is dilute a sharp first place into a
neighbourhood. That is the same shape as both previous losses — the graph keeps
answering *what is this tree built on*, and every question anybody asks it is
*where is this one thing*.

This is the third measured loss for the reference graph and the first one where
it was asked the question it was supposed to be good at. It stays in the tree,
switchable and printed by `luu select --explain`, because the order not taken is
worth reading beside the one taken; but nothing in this repository now defaults
to it. If it is ever to earn a default, the case has to be made against this
table.

**The module doc is what is carrying the result**, and that has to be read with
the corpus's own construction in mind: the 38 questions were written *from* the
files' module docs. A selector that reads module docs is being scored on a corpus
made of them. The honest reading is the ablation row: **without the doc signal,
tags and path alone still hold 19 of 38 at 1024 against the map's 3** — so the
mechanism `luu-design.md` names does work, and the doc signal is what a tree that
writes `//!` blocks gets on top. On a tree that does not write them, the second
row is the one to expect.

### What is now true that was not

The `code` bucket has existed since the context manager did and has been **zero
in every recording this repository has ever made**. It is not zero any more:

```
$ luu chat "which file applies Landlock and seccomp between fork and exec?" \
    --select-tokens 500 --mock-reply ok --record sel.jsonl
buckets: system 11, tools 470, map 0, summaries 0, history 0, code 277, prompt 16
```

277 tokens that nobody typed, chosen by the turn's own text, read through the
sandbox, and gone when the turn is.

### What this run does not say

- **Precision.** Whether a 7B *uses* the fragment it was handed is not measured
  here and is not implied by any number above. A selector that wins coverage and
  loses precision is a worse selector and nothing in this table would notice.
- **Any question that is not "which file".** All 38 are location questions.
- **Anything about a tree that is not this one.** 41 files, one crate pair, and
  module docs written to a standard most repositories do not keep.
