# Users, three roles, and a code by email

**Status:** proposal; nothing of it is built. It takes over steps 2–4 of
[`a-public-luu`](2026-10-07.a-public-luu.WIP.md) and changes three of that
record's decisions. Each one is argued below.

> Creo que aún no tenemos usuarios ni roles
>
> Mi idea sería que pueda correr en local, para lo que cada usuario tendría su
> configuración; o en remoto, para lo que haría falta usuarios (normales,
> admins y owners), el registro/login sería mediante OTP enviado por email,
> añadiendo soporte para passkeys que simplifiquen el acceso

## What is true today

- **Local already gives each person their own configuration.** The state
  directory (`~/.luu` or `~/.config/luu`, or `LUU_HOME`) belongs to the OS
  account, and so do `config.toml` and `sessions.db`. Loopback has no
  authentication. On a laptop, *each user has their configuration* means *each
  account runs its own luu*, and that holds today.
- **Remote has no users.** `auth::Auth` is `Loopback | Token`, which answers
  *who can reach the port* and never *who you are*. Everyone holding the token
  is the same person. The page carries the token as `/?token=…`, so it ends up
  in the browser's history and in the socket's query string.
- **What a request may write is decided by the address.** Settings writes are
  allowed when the server is bound on loopback and refused otherwise. No person
  is involved in that decision.
- **Sessions have no owner.** The `sessions` table has no column for one. Since
  #68 a `serve` holds several live sessions (`[sessions] max-live`, 4, counted
  across the whole server).
- **In the published image, every session can reach every folder.** Tools run
  inside luu's own container as uid 10001, under `deploy/luu.toml`. That policy
  grants `/work` read-write as an absolute path, so a session in
  `/work/a` can read and write `/work/b`. Today nobody else is in `/work`, so
  this has not mattered yet.

## The proposal

### Local stays as it is

Exposure `loopback` gets no users, no login and no roles. A person at their
own machine already went through a login: the OS one. The proposal below
applies only to a server that is reached from other machines.

### `exposure = "public"` means users

```toml
[server]
exposure = "public"              # loopback | private | public
bind = "0.0.0.0:7878"
origin = "https://luu.example.com"   # required: the code's page and passkeys are bound to it

[auth]
signup = "invite"                # invite | domain | open
domains = ["example.com"]        # read with signup = "domain"
session-hours = 168              # how long a login's cookie lasts
owner = "jesus@germade.dev"      # bootstrap: this email may sign up as owner while there is none

[auth.smtp]                      # optional; without it codes come only from `luu user code`
url = "smtps://smtp.example.com:465"
from = "luu <luu@example.com>"
password-file = "/run/secrets/smtp"
```

`private` stays what it is, a single token and no users, and both its tests
and the deployments already running on it are left alone. In `public`, **no
request is trusted because of the address it comes from**. In the published
image a user's command that was granted network can reach
`127.0.0.1:7878`, so treating loopback as the owner would let any user become
one. Out of band, the person at the machine is the `luu user` CLI (below),
which writes the database directly. It does not go through a request.

### Three roles

| | user | admin | owner |
| --- | --- | --- | --- |
| Own sessions, own folder, Account (logins, passkeys) | ✓ | ✓ | ✓ |
| Users: invite, suspend, remove, user ↔ admin | | ✓ | ✓ |
| What is shared inside luu: providers, policy lists, images | | ✓ | ✓ |
| What belongs to the machine: engines, hosts, icon and brand paths, `[server]`, `[auth]`, a host shell | | | ✓ |
| Making or unmaking an owner | | | ✓ |

**Owner gets exactly what loopback gets today**: every write that is refused
off loopback now is allowed to an owner's login, and only to that. Admin is new
and covers managing people and the things shared inside luu, without access to
the machine itself. There can be several owners, and **the last owner cannot be
demoted or removed**. Each role is a fixed set of permissions; see *Rejected*.

### A code by email

```text
POST /api/auth/code  {email}          → 202, always the same body
POST /api/auth/login {email, code}    → 204 + the cookie
```

- **Six digits, ten minutes, single use.** The code is stored hashed in
  `auth.db`. Five wrong tries burn it, and a new code replaces the previous
  one. Requests for a code are rate-limited per email and per IP, in-process,
  because there is one replica.
- **The first call never reveals whether an email belongs to a user.** It
  answers the same way, in about the same time, for an email that is a user
  and for one that is not.
- **Registration is the first successful login**, as far as `signup` allows:
  - `invite`, the default, lets in only emails an admin has added (or
    `luu user add`).
  - `domain` lets in anyone whose email is under one of `domains`.
  - `open` lets in anyone.

  A new user starts with the role `user`. The email in `[auth] owner` signs up
  as owner while the server has none, which is how a Docker or Helm deployment
  gets its first owner from an environment variable without a shell.
- **The CLI is the way in that does not need email:**

  ```sh
  luu user add ana@example.com --role admin   # an invitation: the user exists, not yet signed in
  luu user list
  luu user role ana@example.com user
  luu user remove ana@example.com
  luu user code jesus@germade.dev             # prints a one-time code; no SMTP involved
  ```

  `docker exec luu luu user code …` is enough for one person with no mail
  server, and it is also recovery when the mail is down.

### Passkeys: a shortcut, not a second door

After a login with a code, the page offers to add a passkey for that device.
From then on the login page offers the passkey first, with no username field,
and the code link is always next to it. **The code stays the way to recover**: a
lost device means one email, not a locked account. Account lists the passkeys,
and each one can be renamed or removed.

### A login, the socket, and API tokens

- **A login is a cookie**: `HttpOnly; Secure; SameSite=Strict`, stored hashed
  with its expiry. Logging out, or an admin suspending the user, ends it.
- **`Origin` is checked on the socket's upgrade and on every write.** A cookie
  is sent by any tab, and `Origin` is what tells this page apart from another
  site's. `public` does not accept `?token=`.
- **An API token belongs to a user and has a name.** It is hashed, listed and
  revocable, for a `[host.*]` on a laptop or for the CLI. It acts as its user
  on sessions and **never writes Settings, whatever the role**, which is the
  reason `a-public-luu` gave for refusing a bearer token there.

### What a user owns

- **Sessions.** `sessions.owner` holds the user's id, and listing, resuming,
  sleeping and deleting are scoped to it. The migration assigns every existing
  session to the first owner.
- **A folder.** `<serve's root>/<user id>/` is created at the first login.
  `folder_under_root` checks against that root, and the folder picker browses
  only inside it.
- **The wall between two users is Landlock.** In the published image both
  users' commands run as the same uid in the same container. So
  `deploy/luu.toml` has to grant `.`, the session's folder, which relative paths
  resolve to since `sessions-side-by-side` step 3, instead of `/work`. **Before a
  second user is let in, a test tries to reach** another user's folder,
  `/state`, another session's `/tmp`, and other processes through signals and
  `/proc`. A container per session would be a stronger wall, but it needs a
  runtime the server can reach (a socket), and that belongs to another record.
- **A host shell is for owners only**, whatever `[terminal] host` says. In the
  container, a shell is every user's folder plus `/state`.

## In what order

1. **Users and a code, without email.** `auth.db`, `luu user`,
   `exposure = "public"`, the login page, the cookie, `Origin`, sessions with an
   owner, a folder per user, `deploy/luu.toml` granting `.`, and the isolation
   test. Codes come only from `luu user code`. This is already enough for one
   person on a public server, with the token out of the URL.
2. **The code by email.** `[auth.smtp]` (`lettre` over rustls), `signup`, and
   the rate limits.
3. **Roles enforced.** Settings writes by role, Settings → Users, and Account
   (logins, sign out everywhere).
4. **Passkeys.**
5. **A user's API tokens** (`[host.*]`, the CLI).
6. **Per-user configuration**, if it is decided (*Still open*).

Each step gets a record of its own when it starts.

## What it costs

- **Every route gains a user.** Each session route checks ownership, and each
  Settings write checks a role instead of the address. This is the largest
  cost, and it is spread across `serve.rs`.
- **`auth.db` is the first store that holds secrets**, even though they are
  hashes. Its mode is checked, as `secret::read` checks a token file.
- **Email.** It means a dependency (`lettre`, which offers rustls), a config
  table, a secret and a failure mode. Deliverability (SPF, DKIM) is the
  operator's problem. Step 1 does not need any of it.
- **WebAuthn**, carried over from `a-public-luu`: `webauthn-rs` links OpenSSL,
  and this tree is rustls throughout. Step 4 starts by checking whether there
  is a path without it. The code comes first, so nothing else waits on that
  answer.
- **The page** needs a login screen, Account and Users, plus a smoke test that
  logs in with a code from `luu user code`.

## What changes from `a-public-luu`, and why

- **Passkeys enrolled by an invitation link → a code by email, with passkeys
  optional.** Jesús chose this. It also removes a failure that record left open:
  with passkeys as the only way in, a lost device needed an admin to send a new
  invitation.
- **`owner = true` → `role = user | admin | owner`.** There is now a middle
  role that manages people without owning the machine.
- **`[identity.*]` in `config.toml` → users in `auth.db`.** With sign-up and
  admins managing people from the page, the list of users is written by the
  server while it runs. Keeping it in the person's file would mean strangers
  appearing in it with `signup = "open"`, and an admin, who does not own the
  machine, writing the file that does.
- **A pod per person and a door (step 4) → one `serve` with users.** That
  record rejected *several identities in one `serve`* for two reasons:
  1. One live session per `serve` (row 14). **That is gone since #68.**
  2. No per-identity permissions in the store. **This record builds them.**

  What is given up is pod-per-person isolation, which came for free; Landlock
  over each user's folder replaces it, and the order above puts its test
  before a second user. The chart stays as one `Deployment`, and the
  process-level `roles = ["sessions", "hosts"]` key is not built.

## Rejected

- **A magic link instead of a code.** A link opens on the device where the mail
  is read, which is often a phone, not where the person is logging in. Mail
  scanners also fetch links ahead of the person and burn single-use ones. A code
  is typed wherever the person is.
- **Passwords**, for the reason `a-public-luu` gave.
- **OAuth/OIDC (GitHub, Google).** It is a third party in the login, and nobody
  asked for it. It could be another method later, beside the code.
- **Permissions as a table (RBAC).** Three roles cover what was asked, and a
  table of permissions is a second configuration language.
- **Trusting loopback in `public`**, for the reason given in its section above.

## Still open

- **The default for `signup`.** `invite` is proposed: on a server where users
  run commands, an open sign-up is an open shell.
- **Whether an admin can read a user's sessions.** Proposed: no. An admin sees
  the list (title, state, size) and can put a session to sleep or delete it, but
  cannot open it.
- **Per-user configuration on a remote server.** Should a user bring their own
  providers and API keys, or their own policy lists? Proposed for later:
  everything in `config.toml` is the server's, edited by role, and Appearance
  is already per browser.
- **Limits per user**: `max-live` per user beside a server-wide one.
- **Whether a passkey login signs approvals**, carried over from
  `a-public-luu`.

## Appended 2026-11-03: the three questions, answered

> 1. Solo un admin o owner pueden añadir a otros usuarios
> 2. No las ve
> 3. De momento las del servidor

### 1. There is no sign-up

**A user exists only because an admin or an owner added them.** That happens
in Settings → Users (step 3), or with `luu user add`, which is the person at
the machine and so does the job of an owner. `signup` and `domains` are not
built. A code requested for an email that is not a user gets the same `202`
and no email is sent. `[auth] owner` stays, because a server with no users
has nobody who could add the first one, and it works only while the server
has no owner. Until step 3, `luu user add` is the only way to add anyone.

*Rejected* gains **sign-up by domain and open sign-up**, for the reason
proposed for the default: on a server where users run commands, letting
oneself in is letting oneself into a shell.

### 2. Nobody sees another user's sessions

This rules out more than *reading* them, which is what was proposed: an admin
gets **no list, no content and no action**. That holds for every role in the
page, owner included. An owner who opens a host shell or runs `docker exec`
reaches the files through the machine, as anyone with that access can, and the
record says so rather than hide it.

Two consequences:

- **Only the session's own user can free its slot.** Nobody else can put it to
  sleep or delete it, so `idle-minutes` is the only other thing that ends it.
  In `public`, then, **`[sessions] max-live` counts per user**: one user cannot
  take every slot on the server when nobody else may free them. This moves into
  step 1. Whether there is a ceiling for the whole server as well stays open.
- **Removing a user has to decide what happens to their sessions and their
  folder**, because no admin will ever see them. Suspending keeps everything.
  Removing is open (below).

### 3. Remote uses the server's configuration

Everything in `config.toml` belongs to the server and is edited by role.
Per-user providers, keys and lists are not built. Roadmap row 61 is struck as
decided.

### Still open, now

- **What removing a user does** with their sessions and their folder: delete
  them, after a confirmation that says how many, or keep them where only the
  machine reaches them.
- **A ceiling on live sessions for the whole server**, beside the per-user
  `max-live`.
- **Whether a passkey login signs approvals**, carried over.
