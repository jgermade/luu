# The panel reads the pruned lines, and two things it was already getting wrong

Roadmap item 6 of [`ROADMAP/2026-09-09`](../ROADMAP/2026-09-09/README.md), which
calls itself *the smallest row here and the one that would have found the most*:

> Nothing in the page reads the trace's `pruned` lines — `/ws/trace` has a
> consumer for `prompt`, `prefix_reuse`, `budget` and `step_call`, and none for
> the lines rule B added. The panel exists to watch the window give way, and the
> one rule that makes it give way without losing a turn is invisible in it.

That is exactly the state of the tree, and looking for the missing consumer
turned up two neighbouring bugs in the code that reads the lines the page *does*
consume. Both are in this change, because the second one cannot be fixed without
touching the line the first one needs.

## The problem

There are two ways the window gives way, and the page can only see one of them.

**Eviction** takes a turn out of the conversation. It travels on the protocol
channel (`ServerMessage::Evicted`), the store keeps it as `state.evicted`
(`store.js:310`), the transcript strikes the turn through and says *out of the
window since turn N* (`app.html:524-531`), and the inspector prints *Turn N
dropped turn(s) … for good, under the `<policy>` policy*
(`inspector-debug.html`, the budget section).

**Pruning** — rule B, `--prune-behind`, and rule C, `--prune-results` — takes a
turn's *code* out of the prompt and leaves the turn itself asked, answered and
citable. It travels on the trace channel as `TraceMessage::Pruned { turn, turns,
tokens, counter }`, for the reason `trace.rs:78-88` gives: what a pruned turn
lost is a fact about the prompt, and facts about the prompt are what that channel
is. `serve.rs:2113` emits it. `onTrace` in `store.js:382-409` has four `if`s, for
`prompt`, `prefix_reuse`, `step_call` and `budget`, and the frame falls through
all four and is dropped on the floor.

So the rule whose entire selling point is *the conversation survives the cut* is
the one cut that leaves no mark anywhere on the page. A person watching
`--prune-behind` work sees a `code` bucket shrink between two turns, with nothing
to say which turns paid for it or whether anything was pruned at all.

The read API is not the missing piece: `TurnView` already carries both halves —
`cited: Option<Pruned>` (what this turn pruned) and `pruned_by: Option<TurnId>`
(the turn that took this one's code), folded in `api.rs:508-527` exactly as
eviction's two halves are. The store's `fromStored` (`store.js:589-604`) does not
read either field. This is a page-only change; no Rust, no format bump.

## The two bugs found on the way in

**1. The live panel over-attributes a cut to every turn after it.**
`state.evicted` is set when the frame arrives and then never cleared:
`turn_started` (`store.js:206-219`) resets `state.tools` and `state.extraCalls`
and nothing else, and `keepTurn` (`store.js:566-583`) copies
`dropped: state.evicted` into *every* turn it keeps from then on. So a session
that evicted something at turn 5 shows that cut under the budget of turns 6, 7
and 8, which evicted nothing. It reads as truthful because the sentence names
its own turn — *Turn 5 dropped turns 1, 2* — so the panel appears to be telling
you about turn 5 while you are looking at turn 8.

It is invisible in one specific way that matters here: reload the page and the
same turns come back from the read API through `fromStored`, which is per-turn
and correct, so the wrong attribution disappears. Live and reloaded disagree, and
the reloaded one is right.

**2. A resumed session loses its eviction marks in the transcript.**
`refreshLiveSession` rebuilds `state.messages` from `view.turns`
(`store.js:854-882`) with `evicted: null` hardcoded on both pushes, while the
API has been answering with `evicted_by` on every turn that was dropped. Open a
session that evicted something, and the transcript shows every turn as if it were
still in the window. The inspector's history is right on the same reload, because
`fromStored` reads `turn.dropped` — so the two halves of the page disagree with
each other about the same recording.

Neither is a pruning bug. Both are in the code pruning has to be threaded
through, and fixing them is the same line.

## The proposal

Mirror eviction, in all four places it exists, and nowhere else.

**The store keeps the cut**, beside `state.evicted` and with the same shape:

```js
pruned: null,   // { turn, turns, tokens, counter }
```

set from the trace frame in `onTrace`, cleared at `turn_started` — where
`state.evicted` is now cleared too, which is bug 1.

**The store marks the turns**, as `messages[].evicted` does: a new
`messages[].pruned` field holding the turn that took this one's code, set on the
same frame, and read out of `t.pruned_by` (and `t.evicted_by`, bug 2) when the
transcript is rebuilt from the API.

**The panel view carries it**: `cited` in `panel()`, `keepTurn` and `fromStored`,
named after the API's field rather than after the store's, because the reader who
has to line the two up is the one to spare. `fromStored` stamps the turn onto it
the way it already does for `dropped`.

**The inspector prints one sentence**, under the budget beside eviction's:

> Turn 9 pruned turn(s) 3, 4 — 412 tokens of code out of the prompt, by the
> `model:qwen2.5-coder:7b` counter. The turns are still in the conversation.

The last clause is the whole difference between the two lines and is worth the
words. The counter is named for the reason `Budget` names it: two runs measured
differently are not comparable and nothing else on the panel would say so.

**The transcript marks the turn** without striking it through. Eviction gets
`opacity: .45` and a line through the text, because the model can no longer be
asked about it. A pruned turn is still there — `· code out of the prompt since
turn N`, in the same `.who` line as eviction's note, in `--dim` rather than in
the strike-through style, and the article is not dimmed.

## What it costs

About seventy lines of JavaScript and CSS across three files, no Rust, no
protocol or record format change, and nothing new on the wire. A page from
before this change drops the frame exactly as it does today, and a recording made
before it has no `pruned` line to read — both degrade to the sentence not
appearing, which is the pre-change behaviour.

The cost that is not lines: `state.pruned` is one more thing `reset()` has to
clear, and the four-way mirror (live frame, kept turn, stored turn, transcript
mark) is now written twice, once for eviction and once for pruning, with no
shared helper. A helper over two cases whose *wording* is the entire point would
save nothing and hide the difference the two sentences exist to draw.

## What was rejected

**A bucket-diff instead of the line.** The `code` bucket shrinking between two
turns is visible on the bar already, and one could argue the number is derivable.
It is not: the bar says what the prompt is made of now, and the pruned line says
which turns paid and what the window actually saved — which under `Repeat::Once`
is not the sum of the spans, because a span the pruned turn owned passes to a
younger turn instead of leaving (`context.rs:399-404`). Deriving it from two bars
would get a different, wrong number.

**Putting it inside the budget object.** Same argument the `Evicted` comment
already makes at `store.js:81-83`: the buckets say what the prompt is worth, this
says what stopped being in it. Two questions, two fields.

**Fixing the `status`/composer bug that `site.spec.js:38-44` names** while in the
same file. It is real, it is written down, and it is not this row.

## Still open

- **Nothing tests it.** The smoke suite drives the page against the mock
  (`tests/smoke/gate.spec.js`) and against the static twin
  (`site.spec.js`), and neither produces a pruned line: pruning needs a window
  small enough to make the line move, which no fixture in the tree has. The
  verification below is a recording made by hand for this change. A fixture that
  prunes would test this, the eviction marks, and bug 1's live-vs-reloaded
  disagreement in one file — and it does not exist.
- **Bug 1's shape is not unique to eviction.** `state.prompt`, `state.prefix` and
  `state.budget` are also carried forward rather than cleared at `turn_started`,
  and for those three it is right: the budget is decided *before* the call, so
  clearing it at the start of a turn would blank the panel. `evicted` and
  `pruned` are the two that describe something that happened, and that is the
  line this change draws. Whether any future per-turn field belongs on one side
  or the other is a decision each one has to make for itself, which is exactly
  the kind of thing that gets forgotten.

## 2026-09-16, later: built, and measured against its own absence

All three files, as proposed, plus the fixture the §Still open above said did not
exist — because without one, nothing in CI would have noticed any of this, which
is how the page arrived at 2026-09-16 with no consumer for a line that has been
on the wire since 2026-09-08.

### What is in the tree

- `store.js`: `state.pruned`, `messages[].pruned`, the `pruned` arm of `onTrace`,
  `cited` in `panel()`, `keepTurn()` and `fromStored()`, both cuts cleared at
  `turn_started`, and `evicted_by` / `pruned_by` read when the transcript is
  rebuilt from the API.
- `inspector-debug.html`: the sentence, under the budget, beside eviction's.
- `app.html`: `.cited` in the `.who` line, dim rather than struck through.
- `scripts/make-fixtures.sh`: `prune-behind.jsonl` — the arm
  `RECORD/runs/2026-09-08.prune-behind/` measured, minus the flag it was measured
  against — recorded and exported like the rest.
- `tests/smoke/site.spec.js`: *a replayed prune marks the turns whose code left
  the prompt*, the counterpart of the eviction test that was already there.

### The fixture, which is the thing that was missing

Twenty turns of `grounded.txt` at `--select-tokens 1024 --context-limit 8192
--prune-behind`: **13 prunes, 0 evictions**, first cut at turn 7 and 2 969 ms
into a 3 487 ms recording, so the whole file replays in about three seconds. The
zero is what makes it a *counterpart* rather than a second copy: the three
eviction fixtures have no `pruned` line in them and this one has no `evicted`
line in it, so the test can assert `article.evicted` has count 0 and mean it.

Exported, the read API answers with both halves, which is what the store now
reads: `cited` on turns 7, 8, 10–20, `pruned_by` on turns 1–8 and 10–15.

### Bug 1, caught by the test that would not have existed

The arm prunes at 7, 8 and 10 — **and not at 9**. That gap is the only place in
any fixture in this repository where a turn that cut nothing sits between two
that did, so the test selects turn 9 in the picker and asserts the panel says
nothing about pruning there. With the two `null`s put back in `turn_started`:

```
✘ a replayed prune marks the turns whose code left the prompt
  Expected substring: not "tokens of code out of the prompt"
```

and with them in place it passes. The whole static suite is 5 passed, the live
gate suite 13 passed.

### Bug 2, measured on a live server rather than a fixture

The reloaded transcript is the one path neither suite reaches: the static twin
replays, and the gate suite's sessions are too short to cut anything. Driven by
hand — `luu serve --context-limit 1024 --reserve 64` on the mock, twenty prompts
over the socket approving each proposal as the page's button does, then a browser
opened at the session *afterwards*, which is the `refreshLiveSession` path:

| | eviction marks in the transcript |
| --- | --- |
| `evicted: null` hardcoded, as it was | **0** |
| `evicted: t.evicted_by ?? null` | **20** |

The API answered with `evicted_by` in both runs. The marks were being thrown away
between the fetch and the transcript, on a line that had been there since the
transcript was first rebuilt from the API.

### One thing the live run says that the fixture cannot

The same live session pruned **nothing** — `code` bucket 0 for all twenty turns,
so there was nothing for a turn to give up. That is not a finding about `serve`:
the driver approved each proposed plan exactly as proposed, and a 7B's plan
grants what it grants, so the selector was bounded to nothing (the
selection-at-the-gate rule, working). It is worth one line here because it is the
shape of the *next* question — rule B needs code in the window before it can do
anything at all, and on a gated surface what puts code there is an approved plan.

### Still open

- The reloaded transcript is still untested in CI. Proving it needs a second
  `luu serve` in the gate suite with its own window and its own port, which is a
  bigger change to that file than this row is worth — written down here rather
  than done.
- The prune fixture replays in three seconds because the mock has no delay. If
  the corpus or the selector gets slower, it is the fixture that gets slower, and
  nothing says so until the suite's 90 s budget is the thing that fails.
- `state.pruned` and `state.evicted` are now cleared in the same place for the
  same reason, and the reason is written at that line rather than at either
  field. The next per-turn field added to the store will have to decide which
  side it is on, and nothing will ask it to.
