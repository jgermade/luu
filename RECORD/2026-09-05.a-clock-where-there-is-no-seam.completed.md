# A clock where there is no seam

**Status:** a proposal and the code it plans, written on 2026-09-05, later the
same day as [`a-clock-at-the-seam`](2026-09-05.a-clock-at-the-seam.completed.md).
Item 5 of [`ROADMAP/2026-09-05`](../ROADMAP/2026-09-05/README.md), which that
record's *Still open* section named and this one answers — including by moving
where the earlier record put the clock.

## The problem, which the morning's record wrote down itself

> **Host mode has no seam and therefore no clock.** `Runtime::Host` runs tools
> in-process, where a wedged `read_file` still hangs the turn. The honest fix
> there is a deadline in the agent loop rather than at a seam that does not
> exist.

`runtime = "host"` is the **default**, and it is the mode every measurement in
this repository has ever been made under. So the clock landed this morning on
the path almost nobody runs, and the one everybody runs kept the hang.

And a second thing, which is why this is not a five-line change:

## `tokio::time::timeout` around a blocking call does nothing

The in-process tools read the filesystem with `std::fs`, inline in an `async`
block:

```rust
match std::fs::read_to_string(&check.path) { … }
```

A future that blocks inside `poll` never yields. The timer beside it never gets
polled either, because the same task is holding the thread. **A deadline over
that is a lie** — it compiles, it reads correctly, and it never fires. On a
`current_thread` runtime it wedges the whole program.

The wedge is not hypothetical and does not need a broken NFS mount to
reproduce: a FIFO with no writer is open, readable, and never answers. That is
the test.

## The proposal

### 1. One clock, in the loop, over every call

`agent::Limits { max_steps, tool_timeout }` replaces the bare `max_steps`
argument, and `run_agent_turn` wraps every `tools.call(…)` in it. The deadline
is derived the same way it was at the seam — **the call's own clock plus the
patience**, where every tool but `run_command` contributes zero — so it still
cannot fire before the tool's own timeout has had its chance.

The loop is the right place for exactly one reason, and it is the reason the
morning's record gave for the seam and did not follow far enough: *the party
that must not be trusted to stop is not the party that holds the stopwatch.* A
container is one place tools can run and this process is another, and the loop
is the only thing above both.

### 2. The seam stops holding a second one, and gets told instead

`Executor` grows `abandon()`, called by the loop when it drops a call. Dropping
the future is what abandons the *work*; `abandon` is the part dropping cannot
do — the worker is still a live process holding half an exchange on a pipe that
must never be reused, so it is killed and the next call starts another. The
in-process executor's `abandon` does nothing, which is the honest answer for a
place with no process to end, and is why it is the default on the trait rather
than something every executor has to write.

So the morning's clock moves rather than doubling: **the seam no longer times
anything.** What it keeps is everything that was actually load-bearing there —
the kill, the never-reuse-the-pipe rule, and the lazy restart.

### 3. The blocking calls move off the poll thread

`off_thread(…)` — one `spawn_blocking` helper in `tools/fs.rs`, wrapping the
four places that touch the filesystem: `read_to_string`, `read_dir` (with its
per-entry `file_type`, which is another syscall each), `write`, and
`create_dir_all`. Only owned data crosses, so nothing needs a lifetime it
cannot have.

The cost, stated rather than discovered later: **the blocking thread is not
cancelled, because a blocking syscall cannot be.** It sits in the kernel until
the kernel answers, holding one slot of tokio's blocking pool. That is a leak
with a bound against a hang without one.

### 4. And therefore: the process has to be able to exit

Dropping a tokio runtime **waits for every blocking thread it started**. So a
turn that survived a wedged read would have come back as a process that will
not exit — the same hang, moved to the end of the program, where there is
nothing left to report it. `bin/luu.rs` builds its runtime by hand and ends with
`shutdown_timeout(200ms)` instead of `#[tokio::main]`.

This was found by the test hanging on the way out after passing, which is worth
recording as the *order* it happened in: the assertion was green and the binary
was broken.

### 5. A restart is counted

The other thing the morning's record left open. `Worker::restarts()`, printed by
`luu tools` when it is not zero — the number that says *your image is broken*
rather than *your command was slow*. And `luu tools` now prints the deadline in
every mode, host included, because that is the mode where nothing else would
mention it.

## What it costs

- `run_agent_turn` takes a struct where it took a number. Three call sites, and
  a signature that now says what bounds a turn instead of half of it.
- Every filesystem tool call is a `spawn_blocking` round trip. For calls that
  answer immediately — which is all of them, nearly always — that is a thread
  hop it did not pay before.
- `[worker] timeout-ms` now decides something wider than its block's name
  suggests: it is the deadline for every tool call, not only for calls that
  cross the seam. Naming it `[tools]` would be a third block for one number and
  a rename of a key that is one commit old, so the key stays and the doc says
  what it does.

## What was rejected

- **Two clocks, one at each level.** They would fire within milliseconds of each
  other and produce two different sentences for one event, and the seam's would
  usually win — which is how you end up with a message about a worker on a
  machine that has none.
- **`block_in_place` instead of `spawn_blocking`.** It moves the blocking work
  off the async worker thread but the call is still inside the future, so the
  timeout still cannot abandon it. It solves the starvation and not the hang.
- **An async filesystem crate.** `tokio::fs` is `spawn_blocking` underneath with
  the same thread-parked-forever behaviour, plus a dependency and a second set
  of error types. The helper is six lines and says why it exists.
- **Killing the blocking thread.** There is no such operation, and every
  language that has pretended otherwise has regretted it.

## Still open

- **`Sandbox::check_path` still canonicalizes inline.** It is one bounded
  syscall on a path rather than a read of unknown length, so it is a much
  smaller window than the one closed here — but it is the same kind, and on a
  dead mount it is the piece that would still hang. `openat2(RESOLVE_BENEATH)`
  (item 7) touches that code anyway.
- **Nothing bounds the blocking pool's exhaustion.** Enough wedged reads in one
  session and the pool has no slots left for the ones that would answer. The
  count exists for the worker; there is no equivalent for abandoned in-process
  calls.
- **A recording does not say a call was abandoned** any differently than it says
  a call failed. The verdict names it in prose; nothing counts it.
