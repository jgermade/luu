## The problem

Row 38 of [`ROADMAP/2026-09-23`](../ROADMAP/2026-09-23/README.md) is one corpus
wanted by three open threads:

- **(a)** Item 2's answer (8K answers 1 of 6, 96K answers 4 of 6) rests on
  `long-session.txt` alone, and that corpus is one 2 000-line file read on
  repeat ([`8k-against-96k-on-the-m4-pro`](2026-09-22.8k-against-96k-on-the-m4-pro.completed.md)).
- **(b)** Item 5's real case was never put to a model. No corpus made an
  answer depend on what a *command* returned. Every `run_command` in
  [`what-rule-c-is-worth-with-a-model`](2026-09-22.what-rule-c-is-worth-with-a-model.completed.md)
  was an empty grep, so `cited` and `cited_reads` could only tie.
- **(c)** No corpus has tool output that varies in size and kind. This gap was
  named on the mock on 2026-09-14 and again on a model.

Row 36 adds a fourth requirement. Its question is whether the 8K arm loses to
the window or to the 8-step limit, and that can only be read on a corpus whose
turns are answerable in **few** calls.

## The instrument

The corpus is [`scripts/tasks/mixed-session.txt`](../scripts/tasks/mixed-session.txt),
with its key in [`mixed-session.key`](../scripts/tasks/mixed-session.key). It
runs against a copy of [`scripts/tasks/mixed-session/`](../scripts/tasks/mixed-session/),
which is `orderbook`: a small Python project that invoices orders. That project
has one failing test, a 157-line log from a nightly run that stopped, and a
180-row CSV. There are eleven turns. The middle column is what the most frugal
agent reads to answer each one. The sizes are from
`crates/luu/tests/mixed_session_probe.rs`'s 98304 run.

| # | Asks | Answered by | Bytes |
| --- | --- | --- | ---: |
| 1 | what this is, how tests run | `read_file README.md` | 775 |
| 2 | which test fails, the two numbers | `run_command python3 -m unittest …` (exits 1) | 681 |
| 3 | why it fails | `read_file` the test, `read_file invoice.py` (**cut at 8 KiB**) | 4 321 + 8 192 |
| 4 | which order the nightly run failed on | `run_command grep -A 14` over the log | 1 345 |
| 5 | why it stopped instead of skipping | `read_file nightly.py` | 5 045 |
| 6 | how many it invoiced, which region most | the log in two ranged reads | 7 831 + 7 309 |
| 7 | that order's region, and its rate | `run_command grep` the CSV, `read_file rates.py` | 51 + 3 977 |
| 8 | how many orders ship there | `run_command grep -c` | 13 |
| 9 | fix it, rerun, how many passed | `edit_file`, `run_command python3 …` | 43 + 129 |
| 10 | **the failing test's class and line, without running or reading** | nothing: only turn 2's output says | — |
| 11 | three-line summary | the session | — |

Every turn takes three calls or fewer. Between them, the turns produce five
kinds of tool output: prose, a failing command, code, a large data file read in
pages, and near-empty counts. Outputs range from 13 bytes to the 8 KiB cap.

**Turn 10 is (b).** Turn 2 asked for the failing test's *name and numbers*.
Turn 10 asks for its *class and line*, and only the traceback in turn 2's
command output has those. Turn 9's run is newer and says `OK`. The test file
would also give the answer, but turn 10 forbids reads. So the window either
still holds turn 2's command output or it does not.

**The key** keeps [`map-order-probe.key`](../scripts/tasks/map-order-probe.key)'s
convention: one line per question, comments skipped. One thing is added: facts
in backticks are literals that must appear in the tool output named after
`<-`, and the rest are conclusions a person scores. That split lets a wrong
answer be told apart from an answer whose evidence had left the window.

## What it shows on the mock

The probe runs the frugal agent scripted, in the real sandbox. `python3` and
`grep` really run, and the edit really lands. Counting is approximate here
(`chars/4`, since the mock has no tokenizer). The prompt budget at 8192 with
`--reserve 512` is 7 680.

| arm | cut | history at turn 10 | turn 10's prompt holds turn 2's traceback |
| --- | --- | ---: | --- |
| 98304 | nothing | 10 394 | **yes** |
| 8192 | turns 1–3 evicted at turn 7 (3 714 tokens) | 6 679 | no |
| 8192, `--prune-behind`, `results = "cited_reads"` | turns 1 and 3 pruned at turn 7, 5 at turn 11 | 7 084 | **yes** |
| 8192, `--prune-behind`, `results = "cited"` | turns 1–3 pruned at turn 7 | 6 915 | no: `[run_command] output — 180 tokens, pruned` |

1. **The overflow comes from the corpus, not from a model that wanders.** An
   agent making the fewest possible calls still reaches 10 394 tokens of
   history, 1.35× what 8K allows. `long-session.txt` could not show this: a
   frugal agent reads one range of `context.rs` and fits.
2. **The four arms come apart by what is in the window, before any model
   runs.** On a model, the question becomes whether answers follow the window.
   `cited_reads` against `cited` is item 5's case, and here they differ by
   design rather than tying by construction.

`the_frugal_session_overflows_8k_and_fits_96k`,
`turn_10_holds_the_command_output_only_where_commands_are_kept` and
`every_literal_in_the_key_is_in_what_the_tools_returned` pin all three
results. They also check that the session actually happened: the test run
failed with `4901 != 5445`, the second run reports 19 tests `OK`, the edit is
on disk, and no call was refused. Without that check, an arm whose `python3`
was denied would look like a window that lost turn 2.

## What building it found

**1. Pruning cites the output and keeps the exchange, so (b) cannot be "ask
for the numbers again."** The first turn 10 asked again for the two numbers
from turn 2. Under `cited`, turn 10's prompt still held them, because the
frugal agent's *own answer* in turn 2 had repeated them. Rule C replaces a
tool result with its citation, and the turn's words stay. A model asked for
something answers it, so any question whose answer was already said aloud
survives every arm that prunes. The question has to ask for something that
only the output carries. One limit remains: a real model may *volunteer* the
class or the line in turn 2. Turn 2's answer has to be read before turn 10 is
scored.

**2. Every tool result is cut at 8 KiB, and `read_file` defaults to 400
lines.** `MAX_OUTPUT_BYTES` in `agent_core::tools` cuts every output, and the
cut is said in the output. `invoice.py` is 17 KB, but `invoice_total` falls at
byte 6 044, so one cut read still answers turn 3. That cut read is one of the
corpus's kinds of output. The log is 15 KB, so reading it all takes two ranged
reads, and the line saying where the run stopped is only in the second. The
probe's key test caught this: it failed until turn 6 read in pages.

The same cut changes how
[`8k-against-96k-on-the-m4-pro`](2026-09-22.8k-against-96k-on-the-m4-pro.completed.md)
reads, though nothing new was measured to show it. `context.rs` was then
already more than 2 000 lines (233 KB today), so no single read of it was ever
whole. That record's own table has **16 distinct argument sets among the 8K
arm's 20 `read_file` calls**, and its 96K transcript pages through
`start_line` 200 and 400 in turn 1. Much of the "19 reads of one file" was
paging through a file the tool never returns whole, not re-reading what was
forgotten. Row 37 (a citation that says where the bytes went) and row 36 both
read differently if that is true. It is a reading of evidence already on disk,
which keeps the calls and not the outputs ([row 42](../ROADMAP/2026-11-08/README.md)),
so it is a guess to check, not a finding.

**3. The corpus was grown until it overflowed, and the growth was not
padding.** The first design had nine turns and a 191-line `invoice.py`, and
the frugal agent fit in 3.7K. A larger module (VAT ids, reverse charge,
numbering, terms, reminders, an export) brought it to 6.1K. A `nightly.py`
with its own question brought it to 6.7K. A question that needs the whole log
is what crossed the line. Each addition is a question a person working on
this project would ask, or a module the size real ones are. But the sizes
*were* chosen with 8K in view. A corpus tuned to overflow one window says
little about a window twice that size, and this one has been run at 8192 and
98304 only.

## Rejected

- **A Rust fixture**, as `edit-reread/` is. `cargo test` output is long and
  toolchain-dependent. A crate needs a `Cargo.toml` and a `lib.rs`, and
  [`a-corpus-that-edits`](2026-09-19.a-corpus-that-edits.completed.md) §What
  it cost measured that a module root in a fixture costs this repository's own
  map two first-place hits. `walk_sources` indexes `.rs` only, so Python files
  are invisible to `luu map` and `luu select`. This corpus is not about
  selection, which was the reason `edit-reread/` had to be Rust.
- **A corpus over this repository.** It would rot, for the reason
  `every_script_names_a_file_that_exists` exists. It would also edit the tree
  it runs in.
- **A pipeline for turn 6** (`grep | sort | uniq -c`). `run_command` takes an
  argv, which is the sandbox's design, so a question that needs a pipeline
  needs a read instead. That is what makes turn 6 the one large read.
- **A fixture generated at test time.** The log and the CSV are committed, and
  so is `invoice.py` with its bug. The generator lived in `.tmp/` and is not
  needed to run anything. The log's traceback names `/srv/orderbook`, the path
  of a server that ran it, and line numbers that match the committed files.

## What it costs

- **`python3` on the machine that runs it**, 3.8 or later, standard library
  only. That includes CI: `ubuntu-latest` has it, and the probe asserts that
  nothing was refused, so a missing interpreter fails loudly. On macOS, the
  Command Line Tools' 3.9 prints tracebacks without the caret lines that 3.11+
  adds. `test_invoice.Totals` and `line 66` are in both formats.
- About 1.2 s of test time (three tests, nine runs of the binary) and 54 KB of
  fixture.

## For the run on machine 3

The same server for every arm, one slot (`-np 1`), `--temperature 0 --seed 1`,
with a fresh copy of the tree for every arm:

```sh
cp -r scripts/tasks/mixed-session "$SCRATCH/$ARM" && cd "$SCRATCH/$ARM"
luu chat --script …/mixed-session.txt --allow-write . \
  --allow-command python3 --allow-command grep \
  --context-limit 8192 --temperature 0 --seed 1 --record run.jsonl
```

The arms: 8192; 98304; 8192 with `--max-tool-steps 16` (row 36); and 8192 with
`--prune-behind` and `[resend] results` set to `cited_reads`, then to `cited`.
`[resend] results` has no flag, so it goes in a scratch `LUU_HOME`'s
`config.toml`.

**Predictions, written before any model has seen the corpus**, because
[`8k-against-96k-on-the-m4-pro`](2026-09-22.8k-against-96k-on-the-m4-pro.completed.md)
admits it did not write its own down:

1. 98304 answers turn 10 and plain 8192 does not, unless the model's turn-2
   answer already gave the class or the line.
2. `cited_reads` answers turn 10 and `cited` does not, with the same caveat.
   If both answer it, or neither does, rule C's middle setting is not what
   decides it on a model.
3. Turns 1–6 score the same in every arm. They run before anything is cut,
   even for the frugal agent, and a model that reads more only cuts sooner.
4. Fewer 8K turns end at the tool limit here than on `long-session.txt` (5 of
   6). If they do not, row 36's answer is "the step limit" before
   `--max-tool-steps 16` is even run.
