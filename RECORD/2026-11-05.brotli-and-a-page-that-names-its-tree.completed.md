# Brotli, and a page that names its tree

## The question

The two items left open by
[`settings-on-demand-and-compressed`](2026-11-05.settings-on-demand-and-compressed.completed.md):
*Sigue con Brotli y el Primer pintado.*

## Brotli

`serve_asset` takes `br` before `gzip` (`Coding::chosen`), each compressed
once per file content and kept, each under its own `ETag` (`-br`, `-gz`).
Chrome sends `br` over HTTPS and to this machine (`gzip, deflate, br, zstd`
to `http://127.0.0.1`); over plain HTTP to another machine it does not, and
gets gzip.

**At quality 5, not 11.** The first build used 11 and compressed every file at
`serve`'s start. Over the page's text (118 files, 1.38 MB as written):

| | bytes | CPU |
|---|---|---|
| gzip 9 | 470 KB | 41 ms |
| brotli 5 | 446 KB | 68 ms |
| brotli 6 | 444 KB | 87 ms |
| brotli 9 | 442 KB | 459 ms |
| brotli 11 | 402 KB | 1550 ms |

Quality 11 is the only one well under gzip, and it cost 2.6 s of CPU at every
start, source maps included. The live suite starts a server per test, four at
a time on this machine's four cores: it took 8.8 minutes instead of 3, with
five Settings tests timing out, each of which passed alone. At quality 5,
without the source maps (only a debugger asks for one), a start costs 0.39 s
of CPU and the suite is back to 2.9 minutes, all passing.

So brotli here is 3–5% under gzip, not the 14% the first build showed
(`app.html` 30.3 KB against 31.5; `jq79.js` 27.1 against 27.9). The tenth more
that quality 11 gives is a build-time job — see *Still open*.

The compression runs on the blocking pool; a cell per file and coding makes the
first asker compress it and every concurrent one wait for that, so six
connections asking for `app.html` compress it once.

## The first paint

What it waited on, at 100 ms a request, after the work of the day:

```
L1  117–236  stylesheets, jq79.js, account.js, me.json, app.html (preloaded)
L2  283–430  app.html's imports
L3  415–557  theirs: places.js, policies.js (static imports of ui.js),
             rows.js, monaco.js, text-input.html, checkbox.html, …
    587      the logo
```

L3 exists because nothing knows those files until their parents arrive. The
server does: it has every file. **`serve_page` sends `index.html` with a
`Link` header naming the whole tree of the page this visitor will get**:

```
link: <./app.html>; rel=preload; as=fetch; crossorigin,
      <./lib/store.js>; rel=modulepreload, <./lib/places.js>; rel=modulepreload, …
```

- `first_load(page)` reads the import graph out of the embedded files: in a
  component, the literal specifiers of a `C79.importAll([...])` or an
  `import("...")`; in a module, its static `import` statements. The same
  statements jq79 0.7.11 preloads, read the same way down the tree; a
  `later("...")` is none of them, so the dialogs stay out. Resolved as the page
  resolves them (`@web/`, `./`, `../`); anything else is not followed. A
  scanner that knows these conventions, not a JavaScript parser; a test pins
  what the app's tree must and must not contain.
- **Which page is the server's to say**, the way `index.html` will decide it:
  the app where there are no users or the cookie is a session, else the login,
  else the setup. So `index.html`'s own `app.html` preload is gone — on a
  login it went unused and Chrome warned. Checked against a server with users
  and no owner: the header names `setup.html`, `account.js` and
  `otp-input.html`, and the console has no warning.
- **`index.html` is `no-store`, without an `ETag`**: the header depends on the
  cookie, and a 304 would answer with the one from before. It is 3 KB.
- jq79's `fetch` and `import()` take what the header asked for. In Chrome,
  first load and reload: every file of the first paint starts within the first
  round trip, no page file is asked twice, no console warning.
- The `/h/{name}/` page is left alone: its API is another luu's, so this
  server cannot say who is asking.

## Measured

`luu serve` on the mock, release builds; *main* the page before 0.7.11, *prev*
commit `1503d2a` (gzip, Settings on demand), *now* this change. Chrome's own
network emulation; seven loads per arm, interleaved, after a warm-up;
medians in ms: the logo, the folder question, Settings opened.

**Through a TLS + HTTP/2 proxy**, the way Caddy sits in
`deploy/compose.yaml` (a Node `http2` server speaking HTTP/1.1 to luu; written
for this, in `.tmp/`):

| Network | main | prev | now |
|---|---|---|---|
| 100 ms, unlimited bandwidth | 873 / 1294 | 576 / 1015 | **381 / 808** |
| 100 ms, 4 Mbit/s | 1954 / 2411 / 499 | 922 / 1362 / 147 | **838 / 1277 / 140** |
| 40 ms, 10 Mbit/s | 859 / 1093 / 235 | 433 / 694 / 87 | **417 / 656 / 86** |
| loopback | 206 / 321 / 109 | 199 / 320 / 71 | 193 / 327 / 68 |

**Straight to `luu serve`, HTTP/1.1:**

| Network | main | prev | now |
|---|---|---|---|
| 100 ms, 4 Mbit/s | 2159 / 2641 / 490 | 1298 / 1845 / 132 | 1272 / 1805 / 134 |
| 40 ms, 10 Mbit/s | 937 / 1147 / 225 | 589 / 847 / 74 | 598 / 852 / 74 |
| loopback | 177 / 283 / 89 | 172 / 280 / 57 | 182 / 286 / 57 |

- **The `Link` header pays where the link multiplexes**: a third off the first
  paint at 100 ms over HTTP/2 when bandwidth is not the limit (576 → 381).
  Over HTTP/1.1, Chrome queues 48 requests on six connections and the result
  is even with three levels of eight-ish each.
- Where bandwidth is the limit, bytes decide, and brotli 5 is a few percent.
- Every proxied run logged the same 500, in every arm, `main` included: the
  proxy does not carry the server-sent events of `/api/workspace/events`. The
  direct runs logged no error.
- The earlier records' "HTTP/2 is modelled, not measured" is answered here.

## Still open

- **Brotli 11 at build time**: a `build.rs` that compresses `web/` into the
  binary would give the 10% without a second at every start; a debug build,
  which reads `web/` from disk, would fall back to compressing at runtime
  when a file's hash is not the one built.
- **HTTP/2 from `luu serve` itself** would make the `Link` header pay without a
  proxy, but browsers speak HTTP/2 only over TLS, and TLS here is Caddy's or
  the Ingress's.

## Later the same day: gzip only, and the modules move into the page

**Brotli is out.** At quality 5 it was 3–5% under gzip (295 KB against 307 for
a first load) for a dependency more; the 15% brotli is known for is quality 11,
which is a build-time job nobody needs yet. Decided: *Nos quedamos con gzip.*
`serve_asset` is back to gzip alone, with the cell per file, the background
warm-up and the `-gz` tag kept; a start now costs 0.23 s of CPU.

**And the `Link` header had a race in it.** The next two runs of the live suite
each failed five or six Settings and reading tests, every one a timeout, and
the one tried alone passed — the run that passed above was the lucky one. The
traces had the same thing: `Failed to resolve module specifier
"@web/vendor/jq79.js"`, then the page drawn as far as the inspector's head. A
`modulepreload` from a header starts as soon as the headers arrive, and fetches
and links the module's own imports as they come; `lib/*.js` import
`@web/vendor/jq79.js`, and `@web/` is the import map inside `index.html`. When
a module beat the parser to the import map, its import failed, and Chrome
keeps a module's failure for the visit. The suite's four servers and four
browsers made it likely enough; a proxy that sends `index.html`'s headers and
holds its body back 500 ms made it certain: 8 loads of 8 stuck.

So the header now names only the components — a component is a `fetch`,
which resolves nothing — and `serve_page` writes the modules into the page as
`<link rel="modulepreload">` tags right after the import map
(`page_naming_its_tree`, with a test that no module is in the header and that
every one comes after the map). Through the same proxy: 0 of 12 stuck; direct,
0 of 40.

The rows above that compare *prev* and *now* were measured with the modules in
the header. Moving them into the page starts them a few milliseconds later —
once the parser reaches them — not a round trip later, so the comparison
stands; it was not measured again.

Two earlier tests (`the_first_load_is_the_tree_of_what_the_first_paint_draws`,
`page_specifiers_resolve_as_the_page_does`) were deleted by accident while
brotli's test was rewritten, and are back.

Checked after both changes: `cargo fmt --check`, clippy with `-D warnings`
and `cargo test --workspace` clean; static twin 5 of 5; the live suite twice in
a row, 78 passed and 1 skipped (no Docker daemon) each time, in 2.8 and 2.9
minutes.
