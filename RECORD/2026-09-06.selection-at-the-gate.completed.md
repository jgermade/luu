# Selection at the gate: the best thing this project has is not in the surface it has

**Status:** a proposal and the code it plans. Not on any roadmap revision, because
the gap it names was only measurable as of this morning.

## The problem, in one table

[`does-the-model-read-it`](2026-09-06.does-the-model-read-it.completed.md) scored
the two context mechanisms against the same 38 questions, one flag apart:

| what the turn was given | right, of 38 |
| --- | ---: |
| nothing | 0 |
| `--map-tokens 1024` | 8 |
| `--select-tokens 1024` | **33** |

And `luu serve --select-tokens` **is not a flag**. `serve.rs` contains no
`select_tokens`, no `select::select` and no `walk_sources`; the map is built once
at startup ([`serve.rs`](../crates/luu/src/serve.rs), `App::create`) because a
map is a prefix, and selection — which is per-turn — was never wired into the
turn.

So the surface a person actually works in runs on the mechanism that scores **8**,
while the one that scores **33** is reachable only from `chat`, which is the
scripted and one-shot surface. That is not a missing flag. It is the project's own
differentiator being absent from the place it differentiates.

Nothing in `luu-design.md` claims otherwise, and nothing hid it: `chat` grew
selection because that is where the probes run, and probes are why selection
exists. The gap is what happens when the instrument and the product are different
binaries.

## The proposal

Mirror what `chat` already does, at the two points in `serve`'s turn where `chat`
has fragments and `serve` passes empty:

1. **Walk once, at startup, beside the map.** `walk_sources` reads and tags every
   `.rs` file in the sandbox; it depends on the tree, not on the turn, and doing
   it per turn would put a full tree walk inside a socket handler. The map is
   built there for a different reason (it is a prefix) and this shares the
   moment, not the reasoning.
2. **Select inside the turn, under the lock that hands out the turn number.**
   That is where `serve` already calls `context.select(&text, &[], …)`, and the
   `&[]` is the `code_context` this fills. Selecting under the same lock is not
   incidental: the comment there says the history a turn is built from is the
   history at the moment it started, and a selection is part of that.
3. **Read through the live job's sandbox.** `session.narrowed` already carries
   `Option<(JobId, Arc<Sandbox>)>` for the approved plan. `chat` does this and
   says why:

   > an approved plan narrows what can be chosen exactly as it narrows what can
   > be opened.

   In `chat` that is a nicety, because a one-shot's plan is the policy file. In
   `serve` it is the requirement: the gate exists so that a person decides what a
   job may touch, and a selector that read outside the approved plan would put
   files into the prompt that the person refused. **The narrowing is not a
   feature of this change, it is the reason the change is allowed to exist.**
4. **Off by default**, as in `chat`, and for the same reason: it changes every
   number in every recording made before it, and unlike the map it is not cached.

## What this costs, stated before it is built

This morning measured the price and it is not small. A fragment is fused into the
turn's user message and **stays in history** — `push_turn` counts
`user_text(&code_context, &prompt)` — so on a 38-turn script at 8 192 tokens the
selection arm evicted **31 times**, prefix reuse fell from 93.3% to **17.7%**, and
it took **11.6×** the wall clock of the ungrounded run.

`serve` is where that hurts most, because a `serve` session is not 38 turns. It is
open for as long as somebody is working.

Three things keep this from being a reason not to build it, and they are worth
writing down so the decision can be argued with later:

- **The flag is off.** Nobody pays who does not ask.
- **The window is the mitigation people already have.** The measurement was at
  8 192 with a 1 024-token selection — an eighth of the window, every turn. At
  32 768, which this machine serves comfortably, the same selection is a
  thirty-second, and eviction pressure falls with it.
- **8 of 38 is not a working alternative.** The cost is real; the thing it buys is
  the difference between a surface that finds the answer and one that does not.

## The thing nobody has measured, which this change makes obvious

`chat` selects from the turn's text and consults nothing else. So when two
consecutive turns are about the same subject — which is what a conversation
*is* — the same fragment is selected twice, injected twice, and stored twice:
once in the previous turn's history and again in this turn's `code` bucket.

**Nothing deduplicates against the history.** A turn could ask for what it needs
and skip what is still visible three turns up, which would cut the per-turn cost
*and* the history growth at once, without the model losing sight of anything.

This is not in scope here — it is a new mechanism and it needs its own
measurement, on a corpus of *conversations* rather than 38 independent questions,
which this repository does not have. It is written down because the 38-question
corpus can never show it: every question is independent by construction, so the
one case where dedup pays is the case the instrument was built to exclude.

## What was rejected

- **Fragments in the prompt but not in the stored turn.** It would make history
  cheap and it is the obvious fix to the cost above. It is also the exact failure
  [`the-fold-fix-verified`](2026-08-30.the-fold-fix-verified.completed.md)
  measured and repaired: a model that reasoned over code it can no longer see
  answers wrong, and two of three closed-task questions came back wrong until the
  fragments were quoted. Making that mistake again, one scope smaller, is not a
  fix.
- **Rebuilding the walk per turn**, so a file written mid-session is selectable.
  It puts a tree walk in a socket handler for a case a person can solve by
  restarting, and `serve` already accepts the same staleness for the map, which is
  built once and never rebuilt.
- **Turning it on by default.** Every recording made before it stays comparable
  only while it is off, which is the rule `--map-tokens` set and there is no
  reason for this to be the flag that breaks it.

## Still open

- Dedup against the history, above.
- **Whether the map and the selector should both be on.** They cost different
  budgets and nothing has measured them together; the probe ran them as separate
  arms because that is what one flag apart means.
- The window's effect on the cost, which is asserted above and not measured: the
  11.6× is a number at 8 192 and the mitigation argument assumes it falls at
  32 768.

## 2026-09-06, the build: what it took, and one consequence nobody asked for

Built as proposed. `serve` and **`stdio`** both take `--select-tokens`,
`--select-docs` and `--select-graph`, and they were never a choice: the two
surfaces share `App`, `StdioOptions` and `begin_turn`, so the turn-side change
covered both the moment it existed and only the flags were missing. Leaving
`stdio` out would have recreated this record's own gap in the **editor**, which is
the surface with the most people in it.

The shape, in four places:

- **`App` carries `walked`**, tagged once at startup beside the map: `selection —
  44 file(s) tagged, 2048 tokens a turn` on this repository.
- **`begin_turn` selects under the lock** that hands out the turn number, and
  reads through `session.narrowed` when a job is open.
- **`begin_turn` returns the fragments**, so `push_turn_with_steps` stores the
  turn with what it was shown rather than with `vec![]`.
- **The planning call discards them.** It was already "the one turn that is not
  remembered", so its selection improves the plan and is charged to nothing —
  which is the cheapest thing in this change and was not designed, only noticed.

### The end-to-end run, which is also the demonstration

`luu stdio --backend ollama --model qwen2.5-coder:7b --context-limit 32768
--select-tokens 2048`, one prompt, approved with no files added:

| turn | prompt tokens | what happened |
| --- | ---: | --- |
| 1, planning | **2 678** | selection over the whole tree; the model proposes a plan granting `crates/luu/src/serve.rs` and nothing else |
| 2, the answer | **797** | the same selector, now reading through the job's sandbox |

**The fall from 2 678 to 797 is the narrowing.** Nothing else changed between the
two turns.

### The consequence: a bad plan blinds the selector

The 7B's plan named `serve.rs`, and the answer to "which file decides what earns
its place in the prompt?" is `agent-core/src/context.rs`. The turn answered
`serve.rs`, naming `on_prompt` — **correctly, for what it was allowed to see**.

That is the gate working and it is also a cost this record did not anticipate.
Before this change the selector reached the whole policy sandbox every turn; now
its reach is bounded by a plan that, in the ordinary case, **a 7B wrote**.
`choosing-fragments` measured the selector against a tree; nothing has measured it
against a tree seen through a small model's plan.

The mechanism to fix it already exists and is the gate's whole point: `approve_job`
carries the files a person adds, checked against the policy file. A person who
sees a plan naming one file and knows better adds the others *at the gate*. So the
answer to this is a sentence in the UI rather than a change in the code — but it
had to be found by running it, and it is the first thing to check if selection in
`serve` feels worse than selection in `chat`.

### A test that proved nothing, briefly

The first version of `a_selection_cannot_reach_outside_the_approved_plan` asked
"which file serves the debug UI over HTTP?", approved a plan granting `serve.rs`,
and asserted the selection held only `serve.rs`. It passed. It was also **vacuous**:
that query reaches `serve.rs` and nothing else with no plan at all, so the
assertion would have held with the narrowing deleted.

The test now asserts, first, that the unnarrowed selection reaches **more than one**
file — it reaches six — and only then that the plan confines it to one. The
lesson is the cheap one and worth writing down anyway: a confinement test has to
show the thing it confines was going somewhere.
