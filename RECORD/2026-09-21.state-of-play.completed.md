# State of play, 2026-09-21

Written after cutting [`ROADMAP/2026-09-21`](../ROADMAP/2026-09-21/), and it is a
stock-taking rather than a proposal: what the four days since the last revision
did, what they did not do, and the two numbers that argue for the order the new
file puts things in.

## The two numbers

**Fifteen commits since 2026-09-17, eleven of them substantive, and every one of
the eleven is a roadmap row.** Items 6, 8, 9, 10, 15, 17, 19, 20, 22, 23, 24, 25
and 26 closed and most of 18 with them — fourteen rows touched across eleven
commits, because an argument and the parts it moved landed together more than
once. The other four commits are `settings.json` three times and a
`pull_request` trigger removed from `build.yml`: repository plumbing, not work.

**Zero runs against a model.** Section A did not move, for the third revision
running.

Read apart, the first number is the best this project has had. The last revision
closed with a calibration finding in the other direction — a fortnight of
debug-UI work that no row had ordered, twelve commits, good work and unplanned —
and the honest answer to it was that *a roadmap listing only what it predicted
flatters itself*. Four days later the roadmap predicted everything. Read
together, the two numbers say why: **the roadmap predicted all of it because all
of it was work a checkout can do**, and a checkout is the one place this project
can always work. The prediction rate went up because the cheap half of the
project was the only half running.

## What that costs, stated as rows rather than as a mood

The bill is not abstract. Four days of building instruments produced four claims
that the instruments cannot make:

- **8 of 13 is a fact about a corpus.** `edit-reread.txt` is scripted, so the
  divergence number measures the script —
  [`a-corpus-that-edits`](2026-09-19.a-corpus-that-edits.completed.md) §Still
  open says so in its first line.
- **Whether a model notices the repair** is unmeasured, and
  [`the-newest-body-wins`](2026-09-20.the-newest-body-wins.completed.md) calls it
  the only thing between the fix and a claim about sessions.
- **What a model is told while drafting** has teeth now that a draft cannot
  write, because a draft that does not know finds out by being refused and a
  refusal costs a turn —
  [`the-drafts-floor`](2026-09-21.the-drafts-floor.completed.md) §Still open.
- **`cited` is still item 5**, unchanged since 2026-09-14.

They became **row 27** of the new revision, one row rather than three, because
they share a corpus family and an afternoon. And Section A stopped being a
section with a date on it — the date
[`the-16gb-threshold`](2026-09-16.the-16gb-threshold.WIP.md) was written for is
five days gone — and became a section with a queue behind it, which is the first
argument for running it that does not depend on a calendar.

The habit itself was named while it was happening, which is the part worth
keeping: *the instrument is again being built ahead of the run that gives it
meaning — third time this week, which is worth naming as a habit rather than
rediscovering as a surprise*
([`one-counting-surface`](2026-09-19.one-counting-surface.completed.md) §Still
open). It was right, it was written down, and nothing in the four days after it
changed course. A habit somebody names and nobody acts on is a better record of
how this project works than either number above.

## How the revision was built, because the last one asked for it

[`the-drafts-floor`](2026-09-21.the-drafts-floor.completed.md) was the first row
this project took straight out of the *Still open* of the record that closed the
row before it, and the 2026-09-17 revision wrote down what that exposed: a
record's closing section is where the next rows are born, and **nothing moves
them into a roadmap but somebody reading it**.

So this revision was cut by reading the *Still open* of all fourteen records
written since 2026-09-17. That produced eight rows — 27 through 34 — and not one
of them is new work. Each was a sentence somebody had already written, between
one and five days before, sitting where a roadmap does not look:

| Row | Born in | Age when ordered |
| --- | --- | --- |
| 27 | three records' *Still open*, 2026-09-19 → 2026-09-21 | 0–2 days |
| 28 | `provider.rs`'s own doc comment and §sixth, 2026-09-18 | 3 days |
| 29 | [`one-counting-surface`](2026-09-19.one-counting-surface.completed.md) | 2 days |
| 30, 33 | [`every-turn-belongs-to-a-job`](2026-09-20.every-turn-belongs-to-a-job.completed.md) | 1 day |
| 31, 32, 34 | [`the-drafts-floor`](2026-09-21.the-drafts-floor.completed.md) | same day |

**The lag is the defect and the rows are fine.** Item 26 is the calibration case:
named in a record on the 20th, priced there at an afternoon, ordered on the 21st
and built the same day for exactly that. The estimate was right; the day it spent
in a file nobody orders from was the only loss, and it is small because somebody
happened to read it. Nothing makes that reliable except doing what this file
just did, which is why the method is written here rather than assumed.

## What did not get written down anywhere else

Two things the four days produced that are not rows and would otherwise be lost:

- **A flipped default broke nine tests, all of which had used *the default* as a
  name for *the arm without rule A*.** One had been comparing the rule against
  itself and passing. Caught by a guard written on 2026-09-07 for an unrelated
  reason. A test that names an arm by what the code happens to default to is a
  test that stops being about anything the moment the default moves.
- **Making one field private found six struct literals where a search found
  four**, two of them in test modules, under a doc comment that had said *two
  call sites resolving a policy differently is two sandboxes* since it was
  written. A comment that has been true and ignored that long is an argument for
  a type.
