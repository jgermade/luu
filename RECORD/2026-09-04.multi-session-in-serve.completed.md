# Multi-session in `serve` and the Web UI

**Status:** a proposal and the code it plans (`WIP`), written on 2026-09-04.
Unblocked by [`sessions-in-sqlite`](2026-09-02.sessions-in-sqlite.completed.md) and
[`session-resume`](2026-09-04.session-resume.completed.md).

## The problem

`SessionStore` can persist sessions whole and reconstruct active contexts via
`SessionStore::resume`. Furthermore, `GET /api/sessions` already lists every
stored session, and `GET /api/sessions/:id` returns its view.

However, `luu serve` runs with a single in-memory `Session` created at startup.
The web UI can view past recorded fixtures (replaying `.jsonl`), but cannot:
1. Start a **new session** without restarting the process.
2. **Switch** the active server context to a stored session from SQLite and
   continue chatting.
3. Browse and select live/stored sessions in the UI header alongside recordings.

## The proposal

### 1. HTTP API additions in `serve.rs`

- `POST /api/sessions`: Creates a new active session. Checkpoints the previous
  active session into SQLite if `--store` is active, generates a new `session_id`,
  resets `AgentContext` and `view`, and broadcasts a `ServerMessage::Hello` over
  `/ws` so connected clients sync.
- `POST /api/sessions/:id/resume`: Resumes a stored session into the live engine.
  Checkpoints the current session, loads `view` and calls `store.resume(...)` to
  reconstruct `Context`, sets `next_turn = view.turns.len() + 1`, and emits
  `Hello` + session updates over `/ws`.
- `DELETE /api/sessions/:id`: Removes a session from the SQLite store (refuses to
  delete the active live session).

### 2. WebSocket notification

When a session is created or resumed:
A `ServerMessage::SessionSwitched { id, title, turns }` (or re-emitting `Hello`
with current turn and new session view) informs open browser tabs to reload/reset
their store state.

### 3. Web UI integration in `crates/luu/ui`

- In `app.html` header, when connected to a live server:
  - Display a session selector dropdown listing stored sessions from `GET /api/sessions`.
  - Provide a `+ New` button to start a fresh session.
  - Selecting a stored session calls `POST /api/sessions/:id/resume` and updates the
    active transcript and budget panel with the resumed fold.

## What it costs

- No schema migrations: uses the existing `sessions.db` schema and `SessionView`.
- Protocol additive: `SessionSwitched` (optional) or `Hello` reuse.
- Minimal state transition complexity: resuming requires acquiring the `session`
  and `view` mutexes when no turn is currently active (`current.is_none()`). If a
  turn is running, the switch request is refused (`busy`).

## What was rejected

- **Per-socket virtual sessions**: running multiple independent active sessions
  concurrently in one `serve` process. Rejected for now because `Agency` /
  `Sandbox` and worker container processes are currently single-tenant per
  session lifecycle. Global active session switching matches the single-operator
  mental model and keeps the engine simple before federation.

## Still open

- Live streaming synchronization across multiple concurrent browser tabs
  switching sessions simultaneously.
