# The window rules are a session's fact, not a screen's

**Status:** WIP — a proposal, waiting on the code it plans. It answers item 6 of
[`ROADMAP/2026-09-17`](../ROADMAP/2026-09-17/README.md) (*whether any default
flips*) in a shape the row did not consider, and grows that revision a row for
the rest.

**Provenance.** A conversation, and it is recorded as one because **both halves
of the proposal moved under examination** and the movement is the useful part.
It arrived as *make the three window rules configurable from the web settings
modal, defaulting to the one that saves most.* The location was wrong against a
decision already written; the criterion was right and I had read it wrong. Both
are below, in the order they were argued, because a record that only prints the
conclusion cannot be argued with.

## The problem, in three parts

**One — three rules nobody can reach from the surface they use.** Rules A, B and
C are built, tested and off by default (`--repeat-once`, `--prune-behind`,
`--prune-results`). They are reachable by typing a flag at `luu serve` and
restarting it. That is the same sentence
[`the-gate-panel-narrows`](2026-09-17.the-gate-panel-narrows.completed.md) wrote
about `network`, `egress` and `enforcement` the day before yesterday — *a
narrowing nobody can reach from the surface they actually use is a narrowing
nobody applies* — one surface along, and this time it is not a narrowing but the
project's own differentiator.

**Two — item 6 has been undecided since 2026-09-14.**
[`the-7b-does-not-miss-it`](2026-09-14.the-7b-does-not-miss-it.completed.md)
closed the measurement and explicitly declined the decision, correctly. The
roadmap has carried it as a row ever since, with the sentence that is the whole
of why it is a row: **a flag nobody ever turns on is a feature nobody has.**

**Three, and this one was found while checking the other two, and it is a defect
rather than a gap.** `RecordLine::Header` (format 10) carries `format`,
`protocol`, `backend`, `model`, `context_limit`, `counter`, `eviction` and
`posture`. It does not carry `repeat`, `prune` or `results`. The four optional
fields it does carry are each there under the same comment, written three
separate times:

> *Two runs under different policies are not comparable, and by the time anyone
> is comparing them nobody remembers which was which.*

So **the header names the policy that decides what *leaves* the window and not
the three rules that decide what the window is *made of*.** The only thing
either rule puts on the wire is the `pruned` trace line, and it fires when rule
B prunes something — which means a `--prune-behind` run that never found a span
to prune is byte-indistinguishable from a run without the flag, and a
`--repeat-once` run is indistinguishable from `off` in every case. There is a
run on disk under each of these flags. Nothing in those files says so.

`prune-behind`'s own record already worried about exactly this class of thing —
*"a flag that quietly starts meaning something else turns a recorded arm into an
unrecorded one"* — and guarded it by making rule C a third flag rather than a
widening of the second. The guard was right and it was applied to the flag
rather than to the file.

**This third part is independent of the rest of this proposal and lands first.**
A project whose whole method is that a run can be re-read afterwards cannot make
these rules easier to turn on while the recording still cannot say they were.

## The criterion, and the correction it went through

The proposal said *default to the one that saves most*. Ranked by tokens saved,
that is unambiguous and it is rule C:

| | flag | what it frees | eviction | accuracy measured |
| --- | --- | --- | --- | --- |
| A | `--repeat-once` | `code` bucket **−17.5%**, prompt −4.4% | 12 cuts → 11 | **yes** — 20 questions, `qwen2.5-coder:7b`, verdicts identical |
| B | `--prune-behind` | prompt **−0.3%** | 13 → **0** | no |
| C | `--prune-results` | **32 752 tokens** over 20 turns | 16 → **0** | no |

C is also the rule with no accuracy measurement at all, and the one whose
failure mode is the worst of the three: it replaces tool output with a citation,
and *the output is evidence*. The closing condition is safe — it reads exit
codes off `ToolStep`, not off the prompt — but the model reasoning about a
`cargo test` it can no longer see is item 5 of the revision, open and unbought.
So *the one that saves most* selects the only one we know nothing about.

**The criterion was not that, and the difference is the whole of why this
proposal has the default it has.** Restated by its author: *the one that
consumes fewest tokens **without affecting the result**.* That is a different
function over the same table. It ranks nothing that has not cleared the second
bar, and today exactly one rule has both halves:

```
savings alone            →  C  (32 752 tokens, and no idea what it costs)
savings proven free      →  A  (−17.5% of the code bucket, 0 verdicts moved)
```

Worth writing down because the two readings differ by four words and select
different defaults, and because the second is the axis this project has used
everywhere else: a number is not a finding until it carries what it cost.

## The proposal

Four changes, in the order they should land.

**1. The header carries the three rules.** A `repeat`, a `prune` and a `results`
field beside `eviction`, `Option<_>` for the same reason and with the same
`None` semantics — a stream written before format 11 does not say, and inventing
the field on the reader's behalf would put a claim in a record the record never
made. `record::FORMAT` 10 → 11. This is the defect above and it is independent
of the other three.

**2. Per session, not per process.** Today `repeat_once`, `prune_behind` and
`prune_results` arrive at `serve` once, as process-wide parameters beside
`context_limit` and `evict`, and every session the process runs shares them.
Choosing them from a page means choosing them per session first. **That is the
real work of this proposal**, and it is not in the modal.

**3. Named in `config.toml`, chosen at session start, immovable on resume —
which is the posture's shape, deliberately.** `[posture.<name>]` names a policy
file, `serve` offers the names to the page, the session picks one when it
starts, the header records it, and a resume that disagrees is refused with a 409
because *its jobs were approved under that one*. The window rules want four of
those five properties for the same reason and the fifth for a weaker one: a
resumed session's stored turns were rendered under a policy, and
`Context::from_view` already rebuilds turns without their fragments, so a
session that changes rules on resume is a session whose recording describes two
different windows under one header.

```toml
# the machine's default, and what a session starts on unless it says otherwise
[window]
repeat  = "once"      # rule A — on, and see the default below
prune   = "never"     # rule B
results = "kept"      # rule C, inert without prune
```

**4. A third Settings section, and not General.** The modal's own comment says
the shape allows it — *a section is a name and a component, not a place in a
scroll* — and General is closed to this by a decision already in
[`luu-design.md`](../luu-design.md):

> *Preferences live in `prefs.js` and in `localStorage`: theme, which editor
> draws a file, the layout, and who answers the gate. **None of it is in
> `config.toml`, which says where a run sends — a fact about the run, not about
> the screen somebody reads from.***

General holds Theme, Editor, Layout, Files and Workspace: five facts about the
screen. The window rules are three facts about the run — they change the bytes
the model is sent. A `localStorage` key that changes the prompt would mean
clearing browser data changes what a run sends, the same session sends
differently from a second browser, and the header records a fact the page can
contradict. The section sits beside Models, which is the other thing in that
modal that is about the run rather than the reader.

**And the default: rule A on, B and C off.** Not the most savings — the most
that has been *earned*. A is the only one of the three that has been through a
model, and it moved no verdict across 20 questions while taking 17.5% out of the
`code` bucket. B and C wait on item 5. This is the decision item 6 asks for, made
on the evidence there is and stated as exactly what it is: **one conversation,
one 7B, one quantization, one window size, one seed, run once.** Turning it on
by default is a claim that that is enough to stop making everybody type it; it
is not a claim that the distance question is answered.

## What it costs

- **A format bump, 10 → 11**, and three optional fields on the header. Readers
  of a format-10 file get `None` on all three, which is the same contract
  `eviction` already has.
- **One budget policy per session where there is one per process**, which is the
  bulk of the diff and touches `serve`, the session store and the fold.
- **A refusal on resume**, and its 409, modelled on the posture's. Cheaper than
  that one was: no container can start from this decision, so the fold has
  nothing to build.
- **A behaviour change for every existing user of `serve` and `chat`**, which is
  what flipping a default *is*. `--repeat-once` becomes the default and wants a
  `--no-repeat-once` to turn off; every recorded arm that says `off` stays
  readable, and every *future* arm has to say which side it was on — which is
  change 1, and is why change 1 goes first.
- **Tests**: a header round-trip per rule, a session started under each from the
  page, a resume that disagrees, and one that pins the default so that flipping
  it again is a diff somebody reads rather than a number that drifts.

## What was rejected

- **`localStorage`, or anywhere in General.** Argued above. The shortest version
  of why: a preference that changes the prompt is not a preference.
- **Defaulting to the rule that saves most tokens.** That is C, which is inert
  without B, unmeasured for accuracy, and the one that replaces evidence with a
  citation. It is also the one item 5 exists to ask about.
- **Defaulting all three on** *because each has a number*. B's number is −0.3% of
  the prompt: what it buys is not tokens, it is that nothing is evicted — 0 turns
  dropped against 13, the whole conversation still in the window. Ranking the
  three by savings puts the most interesting one last, which is a good sign the
  ranking is the wrong instrument.
- **A named window profile** (`[window.thrifty]`, chosen by name like a posture).
  The indirection buys a short label in the header and costs a second place to
  look up what a run did. Three fields say it outright. Reconsider if a fourth
  rule ever lands.
- **Leaving it to flags and writing nothing.** That is the state item 6 has been
  in for four days, and it is the only outcome of the three the roadmap names
  that has no argument behind it.
- **Treating this as an answer to item 6.** It is not, and the row should not be
  struck through by it. Making a default reachable from three places does not
  decide which default ships; this proposal decides that separately, in one
  sentence, on one run's evidence, and says so.

## Still open

- **Item 5 is untouched and it gates B and C.** Whether a model minds losing tool
  output to a citation is the same question it was on 2026-09-14, and no part of
  this proposal moves it. B and C stay off until it is answered, whatever a page
  makes easy.
- **The distance question for rule A**, named as the real one by
  [`a-span-is-rendered-once`](2026-09-07.a-span-is-rendered-once.completed.md)
  and not stressed by `grounded.txt`, whose repeats are a handful of turns apart
  rather than eleven. Flipping the default does not answer it and a second
  corpus still should.
- **n=1 remains n=1.** If a second corpus or a second model ever contradicts the
  2026-09-14 run, the default flips back and this file gets an appended section
  saying so. That is the cost of deciding on one run, accepted knowingly here.
- **Nothing counts how often any of the three fires.** Third instance of the same
  gap in one revision — after item 12's file-versus-directory grants and the
  `not_granted` refusal nobody counts — and the same sentence applies: a rule
  that fires every turn and one that fires twice a week are different features,
  and this tree cannot tell them apart.
- **Whether `chat` should follow `serve`.** This proposal makes the rules a
  session's fact and the CLI has no session-start moment to put them in. The flag
  stays the flag there, which is a seam between the two surfaces that nobody has
  argued about yet.

## Appended 2026-09-18, later the same day: the sentence about "runs on disk" is wrong, and the defect is bigger than it

Checking the §Problem claim in order to explain it found it overstated. The
original sentence, left above where it was written:

> *There is a run on disk under each of these flags. Nothing in those files says
> so.*

**Both halves are wrong, in opposite directions.**

`*.jsonl` is gitignored project-wide and `git ls-files` finds zero of them, so
there are no recordings in this tree at all — only each run's `README.md`,
`stats.json` and its transcripts. And each of those READMEs *does* say which arm
it was:

```sh
for arm in "off:" "prune-behind:--prune-behind" \
           "prune-behind-and-results:--prune-behind --prune-results"; do
  target/release/luu chat --script script.txt … --record ${arm%%:*}.jsonl ${arm#*:}
done
```

So the provenance is not lost. What it is, is **beside the recording rather than
in it, in prose somebody wrote by hand.** Which is the argument for the header
rather than against it: `context_limit`, `counter`, `eviction` and `posture` are
all named in run READMEs too, and every one of them is in the header anyway,
under a comment saying why. Nobody has ever argued that the header is redundant
with the prose next to it. `2026-09-14.prune-results/README.md` says its numbers
were computed "with `jq` directly against the (uncommitted) recording" — a reader
re-deriving those numbers has the file, and the file cannot tell them which arm
they are holding.

**And the half the original sentence missed entirely, which is why this section
exists rather than a one-line erratum.** `RecordLine` is not only what `--record`
writes to a file. It is the stream the **session store** persists and the one
`SessionView` is folded from — `api.rs` mirrors the header's `posture` onto the
live view precisely so a resumed session recovers it, and that is *why* `posture`
was added to the header on 2026-09-17 in the first place, one day before this.

So a resumed session cannot know what rules its stored turns were rendered under,
because the fact was never written down anywhere the fold can reach. That
reorders this proposal's own parts: **part 3 is blocked on part 1 rather than
merely sequenced after it.** A resume cannot refuse a mismatch on three facts a
resume has no way to read. The original §Proposal put the header first for the
weaker reason that it was an independent defect; it is first because nothing else
here can be built without it.

**What this says about the original claim**, and it is the reason the sentence
stays above rather than being fixed: it was reaching for the right defect with an
example it had not checked. The example was decoration — *look, there are files
that don't say* — and the mechanism was load-bearing and unexamined. Checking
decoration is how the mechanism turned up. Fifth time in eleven days that reading
code for a reason other than finding a bug is what found one, and the first where
what nothing drove was a sentence in a record rather than a branch in the tree.

## Appended 2026-09-18, third section: two corrections from the proposal's author, and a fifth part

Both are corrections to §Proposal above, and both are right. They stay here as a
section because the parts they correct were wrong for instructive reasons: one
borrowed an argument it had not earned, and the other stopped one level too
coarse.

### 1. Written to `config.toml` from the page, and applied to the live session

The location half of §Proposal stands and this sharpens it: the value is written
back to `config.toml` when it is saved, and takes effect on the session already
running.

**"Immovable on resume" is withdrawn.** It was copied off the posture together
with the posture's restriction, and only the shape was earned. A posture may not
move because *its jobs were approved under it* — an approval argument, about a
grant outliving the thing that bounded it, argued in
[`what-an-approval-was-granted-under`](2026-09-17.what-an-approval-was-granted-under.completed.md).
The window rules grant nothing and bound nothing. Nobody approves a job under
`--repeat-once`. Reasoning by analogy from the posture imported a refusal that
has no argument behind it here, which is the failure
[`AGENTS.md`](../AGENTS.md) names about routing around a recorded decision, one
step removed: this routed *through* one.

**The mechanism for changing it live already exists and §Proposal did not
mention it.** `retarget_header` compares the live session against where it is
sending and, when backend, model or posture have moved, writes **a fresh header
line into the middle of the stream**. It gained its third term the day before
this record was written. The window rules are its fourth, and they are the only
one of the four that is already sitting in the argument it is handed:
`session::header` takes a whole `Budget` and writes down `budget.limit` and
`budget.eviction` while `budget.repeat`, `budget.prune` and `budget.results` are
in the same struct, in its hand, unread.

So §Problem part three is smaller than it looked and worse than it read. The
fact is not hard to reach. **The function that had all five fields wrote down
two.** And the two doc comments on the builders say why it should have written
five — *"a recording made under it is not the same arm as one made without it"* —
so the code states the reason for the field in a comment beside the call that
drops it.

**The write path exists too.** `PUT /api/providers` already writes `config.toml`
from the browser: refused with a 403 on a server bound off loopback, and rebuilt
from the file on disk first, under a comment saying the page writes one table and
must not delete the other. A `[window]` table is a sibling of that route under
the same two guards.

**What it costs, and it is the one part of this that is not already
precedented: the toggle is not symmetric.** The prune line is a ratchet — *"the
line is a ratchet, so what it gives up now it gives up for good"* — so turning
rule B **on** mid-session is clean (the line starts moving) and turning it
**off** does not give back what was already pruned, because the line does not
move backwards. Rule A has no such state: its owner is chosen inside the window
being rendered and never over the session, so A is clean in both directions.
Three ways out, none chosen here: say so at the control, make the ratchet
conditional on the rule still being on, or refuse the off-switch mid-session and
keep it to a session start. The first is honest and cheap, the second is a change
to a mechanism two records argued for, the third is the restriction this section
just withdrew, reappearing with an argument this time.

### 2. Tool output is not one kind of thing, and `Results` treats it as one

Half of this is already true and is why rule C is a separate flag from rule B:
quoted file content and tool output are different objects, argued in
[`what-a-result-costs`](2026-09-09.what-a-result-costs.completed.md). The
correction goes one level further, and it is right: **`Results` is binary over
*every* result**, `Kept` or `Cited`, and the five tools in the registry are not
one kind of thing.

| tool | what its output is | losing it to a citation |
| --- | --- | --- |
| `list_dir` | a view of the tree, re-derivable | cheap |
| `read_file` | file bytes — *the same object as a selected span*, by this project's own account | cheap |
| `run_command` | **evidence**: exit codes, test output, the thing a closing condition reads | the whole of item 5's worry |
| `write_file`, `edit_file` | a confirmation, already small | nothing to save |

It is cheap to build: `Results::Cited` decides at a point that is already holding
`ToolStep.call.name` — `result_text` renders through it.

**And it may close item 5 rather than wait for it, which is the part worth
checking before anything is built.** The 32 752 tokens rule C freed were measured
on a corpus where **every one of the 20 turns called `read_file`** on a 136 KB
file, truncated at the 8 KiB cap every time. So every measured token of rule C's
win is in the row this table calls cheap, and **none** of it is in the row item 5
is about. A per-tool rule C could ship the whole measured saving while making
none of the unmeasured claim.

Stated as what it is: **a proposal, not a measurement.** No corpus in this
repository has ever pruned a `run_command` result, so nothing here says what that
costs — only that the number rule C is currently justified by never tested it.

### What this does to the order

- **Part 1 is unchanged and still first**, for the reason the second appended
  section gave and now also because it is what makes a mid-session change legible
  at all: a rule that moves at turn 12 needs a stream that can say so.
- **Part 3 becomes live rather than immovable**: a `[window]` table, a `PUT`
  beside the providers one with the same two guards, and a header line through
  `retarget_header` when it moves.
- **Part 5, new**: `Results` becomes per-tool. It should land before anybody
  turns rule C on, because the alternative is turning on a rule whose justifying
  number came entirely from the tools it is safe on.

## Appended 2026-09-18, fourth section: the asymmetry, read in the code, and it is worse than the third section said

The third section named the ratchet and voted for the cheap way out. Reading the
two sites to explain it found a third rule's behaviour it had not separated, and
a consequence that changes the vote.

**Two sites, and only one of them asks whether the rule is on.** Moving the line
is gated:

```rust
if budget.prune == Prune::Behind && self.fits_from(…) > self.floor {
    self.pruned = self.prune_to(target, counter, budget.repeat, budget.results);
```

Rendering below it is not:

```rust
Item::Turn(index) if *index < self.pruned => {
```

That branch asks only whether a turn is below the stored line. So turning rule B
off mid-session stops the line advancing and returns nothing that is already
behind it, for the rest of the session. The third section's claim is confirmed,
and the mechanism is this: the policy gates the *decision* and the line gates the
*render*, and they are not the same gate.

**The three rules are not one case, which the third section ran together.** The
distinction is whether a rule is a render parameter or stored state:

| | on | off | why |
| --- | --- | --- | --- |
| A `repeat` | clean | **clean** | passed per render, stores nothing |
| B `prune` | clean | **does not undo** | the line is session state; the render obeys it ungated |
| C `results` | clean | clean *in itself* | also a parameter — but only reaches turns below B's line, left where B left it |

**And the consequence that changes the vote.** Turning any of them off makes the
prompt bigger, and the way this window absorbs bigger is the floor. The floor is
the other ratchet and it is the destructive one: what it drops takes the question
and the answer with it. So switching rule C off mid-session can hand back tool
output and spend the conversation for it — bigger prompt, over budget, floor
moves, turns gone, and the floor does not come back either.

That is a different sentence from *you do not get the pruned spans back*, and
saying it at the control is no longer obviously enough. Revised standing, still
not a decision:

- **A is safe to toggle live in both directions** and is the default this record
  proposes flipping. Nothing below applies to it.
- **B and C are safe to turn on live and are not safe to turn off live**, for two
  different reasons — B because its line will not retreat, C because what it
  gives back has to fit somewhere and the floor is what pays.
- The honest cheap option is therefore narrower than the third section's first
  way out: **live on, session-start only for off.** That is the third way out
  reappearing, and this time with the argument the section said it was missing.
  It is also the only one of the three that needs no change to a mechanism two
  records argued for.
