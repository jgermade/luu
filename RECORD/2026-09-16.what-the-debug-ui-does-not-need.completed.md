# What the debug UI does not need: a socket, a service worker, an editor

Three "should we adopt X" questions, asked in one sitting while the viewer was
being worked on, and answered the same way each time: by finding out where the
time actually goes before arguing about the shape. They are collected here
rather than in
[`RECORD/2026-09-15.a-three-pane-inspector.completed.md`](2026-09-15.a-three-pane-inspector.completed.md)
because none of them is about the three-pane layout — that file carries the
work itself, phases 1 through 8, including the Monaco measurement this one only
points at.

A study, so it is `completed` the day it was written: what it exists to produce
is the answers, and they are below.

## The shared finding, which is why all three answers are no

Phase 8 of the other record measured the file viewer end to end. The shape of
the result decides every question on this page:

```
crates/luu/src/serve.rs, 3807 lines, release, loopback
  server: highlight + serialise      20 ms
  browser: build the rows           271 ms
```

**The server is the cheap half and the transport is not even that.** A 6-byte
TOML file round-trips in 0.6 ms, which is the whole cost of an HTTP request on
loopback, parse included. Anything that proposes to speed this up by changing
how the bytes arrive is optimising 0.6 ms of a 291 ms job.

## A WebSocket for the panels, with a fetch fallback

**Asked:** the API uses plain `GET`s — would a socket be faster?

**No, and the number is 0.6 ms.** The four workspace endpoints now answer in
0.6 ms (a small TOML) to 20 ms (the largest file in this repository, 153 KB,
highlighted), and every millisecond above the first is work the server does, not
time the transport spends. A socket removes a connection setup that loopback
has already made free.

**And there is a reason they are not on `/ws` that has nothing to do with
speed.** `/ws` carries `approve_job`. The workspace reads were deliberately left
off it — *a person clicking a directory is not a model proposing a tool call* —
and moving them there would put four read paths behind the socket that carries
approval authority, for no gain. The reasoning is in the other record's section
on why the panels are new endpoints.

**If progressive *delivery* is ever wanted, `fetch` already does it.** A
`ReadableStream` over NDJSON gives the page lines as they arrive without a
socket, a second protocol, or a fallback path to maintain. That is the door the
payload reorder (also in the other record) was left open for: `path`,
`language`, `truncated`, `total_lines`, then `lines`.

**Where a socket would earn it:** the day `serve` is reached over something
slower than loopback. There the interesting number is not the transport either —
it is that `serve.rs` is 153 KB of source and 681 KB of JSON that gzips to
59 KB, and nothing compresses today.

## A PWA

**Asked:** is the web UI set up as one?

**No.** [`crates/luu/ui/index.html`](../crates/luu/ui/index.html) is fourteen
lines — a `<main id="app">`, the stylesheet, and the mount. No manifest, no
service worker, no icons, and not one reference to any of them anywhere in the
UI.

**And most of what a PWA is for does not apply here.** `serve` binds loopback,
the sandbox runs with `network = false`, and the page is worth nothing without
the process behind it: caching the shell for offline use would produce a husk
that cannot list a directory, read a file, or reach a session. A service worker
would be a cache in front of a server on the same machine.

**The half that would pay is the half that needs no service worker**: a
`manifest.json` with `display: standalone` and an icon, so the debug UI opens in
its own window without a browser chrome around it and is findable by its icon
rather than by a bookmark to `127.0.0.1:7878`. That is a manifest and four lines
of `<link>`. Not built, because nobody has asked for the window — but it is the
cheap part, and it is worth separating from the expensive part that was actually
being asked about.

## Monaco

**Asked:** would it make sense to use Monaco in the web UI?

**No**, and it was measured rather than argued — the numbers, the two size
tables and the Ctrl+F consequence are in
[`RECORD/2026-09-15.a-three-pane-inspector.completed.md`](2026-09-15.a-three-pane-inspector.completed.md),
under *2026-09-16, Monaco, measured rather than argued*. The short of it: at the
size this panel is actually asked for, this viewer puts text on screen in a
third of Monaco's time over a seventh of the bytes and the whole file stays
searchable; beyond that it is no contest and Monaco wins, but "beyond that" is a
regime the 512 KB cap excludes on purpose. It is not repeated here because a
record that restates another record starts drifting from it.

## One thing that was asked and is worth writing down on its own

**"The viewer loads in two passes — why is there only one request?"**

Because the two passes are two *renders*, not two fetches. The file arrives
whole and already coloured in a single `GET /api/workspace/file`; what is spread
over two frames is building the rows, which the measurement above says is 93% of
the cost. There is no second request for a file of any size, and watching the
network tab for one will never show it. The instrument that shows the split is a
`MutationObserver` on the row count — the other record's phase 8 carries the
snippet and the curve.

This is the second time the same confusion has cost time in this project: the
first was assuming the highlighting was what made a big file slow. Both come
from the same place — **the server is not where the viewer's time goes**, and
nothing on the page says so.

## Still open

- **The payload's head is not self-sufficient yet.** It carries `total_lines`,
  which is the *file's* length, and the viewer's spacer needs the *payload's* —
  they differ exactly when a file was cut at 512 KB, and sizing the scrollbar
  from the wrong one would make it three times too long. Today both are known at
  the same instant, because the body arrives as one `await answer.json()`, so
  nothing is lost. The day anything streams, a `sent_lines` beside
  `total_lines` is what a head-first reader needs, and it is five lines. Left
  unbuilt deliberately: a new optional field costs nothing to add later, and
  adding it now would be a permanently redundant number kept for a hypothesis.
- **Nothing on the page says `[ui] icon-theme` exists.** The first person to
  meet the unconfigured file tree read a working fallback as a broken panel, and
  the only places that mention a theme can be named are `AGENTS.md`, the design
  doc, and `crate::icons`' own doc comment — none of which is where somebody
  looking at a tree of grey shapes is looking. The preferences panel already
  exists and already shows the theme's name when one is loaded; it says nothing
  when one is not.
- **Compression.** Unchanged from above and from the other record: 681 KB of
  JSON that gzips to 59 KB, worth nothing on loopback and worth more than
  everything on this page the day it is not loopback.
