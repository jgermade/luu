# The surfaces first, and the bug that was waiting there

**Status:** a reordering, and the one-line fix it found.

The order in [`ROADMAP/2026-09-08`](../ROADMAP/2026-09-08/README.md) was written
the morning of the same day and every row in it is a measurement, an argument or
a box: *whether a 7B misses the repetition*, *a probe for tool calls*, *a grammar*,
*a judge*, *the BC-250's ceiling*. It is a good order for the question the
project had been asking since 2026-08-26 — **is the context manager any good** —
and it contains nothing at all for the question its owner is asking now:

> Before performance runs and tuning models, I want the UI working so providers
> can be configured, and a development panel to review the activity. What I want
> to try soonest is the chat against the model, the manual supervision of
> commands, and execution in the container.

That is not a smaller ask than the roadmap's, and it is not the same ask. This
record says what it costs, what it found, and why the finding is the argument.

## The reordering is cheaper than it sounds, because three of the four are built

The ask names four things. Reading the tree for them:

| Asked for | Where it already is |
| --- | --- |
| Configure providers from the UI | Built, 2026-09-07: the modal, the refusal a person can answer, the first run with nowhere to send, and a session that names its own destination — [`naming-a-provider`](2026-09-07.naming-a-provider.completed.md), [`configuring-from-the-browser`](2026-09-07.configuring-from-the-browser.completed.md), [`the-first-run-has-no-provider`](2026-09-07.the-first-run-has-no-provider.completed.md), [`a-second-header`](2026-09-07.a-second-header.completed.md) |
| Chat against a model | Built: two backends, the window resolved from the profile, the destination chosen per session |
| Manual supervision of commands | Built, 2026-08-30: the gate holds the prompt unrun, the plan is the job's sandbox, and a person may add what the model forgot — [`the-gate`](2026-08-30.the-gate.completed.md) |
| Execution in the container | Built and observed on macOS, 2026-09-03 — [`the-container-observed`](2026-09-03.the-container-observed.completed.md) |
| A development panel over the activity | **Half built.** The inspector shows the *live* turn — budget, prefix reuse, tool calls with their verdict and who enforced it, the prompt — and resets every one of them at `turn_started`. Nothing in the page can look at turn 3 |

So the work this reordering asks for is not *build the UI*. It is **drive the UI,
and keep what it shows after the turn that produced it**. The distinction matters
because the second half of the panel needs no protocol change and no server work:
`GET /api/sessions/:id/turns/:n` already answers with `prompt_sent`, `budget`,
`prefix`, `extra_calls`, `tools`, `dropped`, `pruned_by`, `cited` and both
timestamps. Every number the live inspector draws is already stored per turn and
already served. The panel is a page that does not read it.

## What driving it found

The three things the owner wants to try were driven end to end against the mock,
over the socket, with the exact messages `crates/luu/ui/store.js` sends:

```text
hello → turn_started → ended → job_proposed → job_approved
      → turn_started → tool_call → tool_result → ended
```

The gate holds, the approval lands, the tool runs, the turn answers. And the tool
result was this:

```json
{"name":"read_file",
 "verdict":{"allowed":true,"rule":"/home/user/luu/AGENTS.md (read)",
            "enforced_by":{"by":"process"}},
 "error":"AGENTS.md: Not a directory (os error 20)"}
```

**The plan granted `AGENTS.md`, the gate approved it, and the read of that exact
file failed.** One flag apart — the same run with a plan granting `crates`
instead of a file — is clean, and held by the kernel:

```json
{"verdict":{"allowed":true,"rule":"crates (read)",
            "enforced_by":{"by":"kernel","how":"openat2(RESOLVE_BENEATH|RESOLVE_NO_MAGICLINKS)"}},
 "output":"//! What earns its place in the prompt.\n…"}
```

### Why

[`beneath-the-root`](2026-09-05.beneath-the-root.completed.md) moved every open
to *resolve the path relative to the root that granted it*, which is what makes
the kernel refuse an escape it cannot see coming. `PathCheck::beneath` returns
that pair, and when the path **is** the root there is no relative part left, so
it returned `"."`:

```rust
// The root asked for by its own name resolves to itself.
let relative = match relative.as_os_str().is_empty() {
    true => PathBuf::from("."),
    false => relative,
};
```

`.` beneath a root is only openable when the root is a **directory**. A plan that
grants a file makes the file the root — `Plan::narrow` builds the job's sandbox
out of the plan's own words, which is the whole point of it — and then `openat2`
is handed a regular file as its `dirfd` and answers `ENOTDIR`. It is not
Linux-only: the non-Linux arm opens `root.join(relative)`, and `AGENTS.md/.` is
`ENOTDIR` on every POSIX system there is.

So since 2026-09-05, **a plan that names a file has been unable to read it**, on
every platform, at the gate — which is the ordinary case, because a model asked
what it needs names files.

### Why nothing caught it

- The sandbox tests in `tools/fs.rs` all grant a **directory** (`PathRule::new(".", …)`).
  A file root is not in the fixture.
- The `narrow` tests in `job.rs` assert what the narrowed policy *grants*. None of
  them opens anything.
- `serve_ws.rs` drives the gate over the socket, and its tool calls read paths
  under a directory grant.
- The only thing that drives the *page* through the gate is
  `tests/smoke/gate-probe.mjs`, which needs a model, a running server and a
  person watching 15 prompts go by. The Playwright test in CI covers the static
  twin, which has no server behind it and therefore no gate.

That is the same shape as the bug [`a-second-header`](2026-09-07.a-second-header.completed.md)
found by hand — *no approval from this UI had reached the server since the
rename* — and it is the second time in two days. **Two bugs found by driving the
surface, none by the tests, and the surface is driven by a person or not at
all.** That is the argument for the reordering, and it is stronger than the
preference that prompted it.

## The fix

`PathCheck::beneath` resolves a root asked for by its own name as **its last
component, beneath the directory holding it**:

```rust
match (root.parent(), root.file_name()) {
    (Some(parent), Some(name)) => Some((parent.to_path_buf(), PathBuf::from(name))),
    _ => Some((root, PathBuf::from("."))),   // `/`, which has no component to name
}
```

The resolution stays the kernel's and the verdict stays honest — it reads
*held by openat2* again rather than *held by an in-process check*, which is what
a failed open had been leaving behind. It does not widen anything: a root is
canonical by construction (`Sandbox::new` canonicalizes and requires existence),
so its last component is not a symlink, and one non-`..` component cannot leave
the directory it is resolved in. `RESOLVE_BENEATH` still refuses everything else.

Rejected: opening the root directly when the path is the root. It is one line
shorter and it is a downgrade — a plain `File::open` is `Applied::Process`, so
every read of a file a plan granted would report *held by an in-process check* on
a platform where the kernel was available and simply not asked.

## What it costs

The measurement rows do not get cheaper by waiting. Two are worth naming:

- **Whether a 7B misses the repetition** was, correctly, called *the cheapest
  unbought answer in the project* — the flag exists, the corpus exists, the model
  is on the machine. It is one afternoon and it now sits behind four rows of UI
  work. Rule A stays off in the meantime, for a reason that is still unmeasured.
- **The probe and the grammar for tool calls** slip together, and they were
  ordered together for a good reason. Nothing here changes that order, only when
  it starts.

What the project gets for it: every number in `RECORD/` was produced through the
CLI, by a probe with a key on disk, and **the surfaces a person actually works in
have been measured by nobody**. The two bugs above are what that looks like from
the inside.

## Still open

- **No container has ever been started on Linux.** Every contained run in this
  repository is Docker Desktop on macOS ([`the-container-observed`](2026-09-03.the-container-observed.completed.md)),
  and machines 4, 5 and 6 are Linux boxes where Landlock is native. The seam runs
  clean under `--worker direct` here; the image has not been built on this side.
- **The executor is the process's, not the session's.** `serve` resolves one
  `Agency` — one sandbox, one worker — at startup and every session in it shares
  that worker, while the design says one container per session. The page shows
  the resolved sandbox and cannot choose it, which is the same shape the provider
  was in before 2026-09-07 and was fixed there by making the choice the
  session's.
- **Nothing counts how often a plan grants a file rather than a directory.** The
  bug above says the case is ordinary; no number in this repository says how
  ordinary, and the gate probe's records would answer it.
- `list_dir` is still the old two-step, unchanged by this
  ([`beneath-the-root`](2026-09-05.beneath-the-root.completed.md) §Still open).
