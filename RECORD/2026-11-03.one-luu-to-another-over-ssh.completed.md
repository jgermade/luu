# One luu to another, over SSH, by key

> Cómo es el mecanismo para remotizar el control de un luu local desde un luu
> online?
>
> La idea es habilitar:
>
> * Gestionar un luu local desde luu online
> * Usar motores de inferencia/proveedores cruzados entre local/local,
>   local/online, online/local, online/online
>
> En lugar de token, prefiero clave pública/privada, como ssh
>
> Quizá se podría usar el mismo sistema de conexión que intergate, con
> mecanismo de reconexion

## What exists, and why it does not reach

`[host.<name>]` (see *Another host is another `luu serve`* in the design doc)
lets a luu show another luu's sessions under `/h/<name>/`. It forwards the API
and the sockets to the host's `url`, with the token from `token-file`. Three
things stop it from doing what is asked:

1. **It dials.** The luu in front opens the connection to the host's URL. A
   luu at home is behind NAT and bound to loopback, so an online luu cannot
   reach it.
2. **It is refused off loopback and with users** (`hosts_allowed`). A host's
   token carries its approvals, engines and terminal, and on a public server
   anyone holding this server's token would get them.
3. **A token is a bearer secret.** Whoever reads it is the holder, and over a
   LAN's plain `http://` it travels in the clear on every request.

Providers do not cross at all. A luu's engine listens on its own loopback, and
a provider's key never leaves its file. So *the GPU is a URL* works for a bare
`llama-server` on the LAN, and not for another luu's engine or for a provider
whose key is on another luu.

## The proposal

### One connection, the way intergate makes one

intergate exposes local services through SSH, like `ssh -R`:

- the client authenticates with an SSH key that the server authorizes;
- the client checks the server's host key, pinned;
- the client asks for a `tcpip-forward`;
- the server opens one `forwarded-tcpip` channel per HTTP request, WebSockets
  and streaming included;
- the client reconnects on its own.

**luu takes the same protocol and the same rules.** The code cannot be shared,
because intergate is Go and luu is Rust (`russh`), but the protocol and the
rules can:

- **Keys, like ssh.** Every luu has an identity: `<state>/id_ed25519`,
  OpenSSH format, `0600`, made the first time it is needed.
  - `luu key` prints its public half: `ssh-ed25519 AAAA… luu@casa`.
  - A luu that listens has a host key too, and the other side pins it on the
    first link, as `known_hosts` does.
- **Who may link is a list of public keys.**
  - On a server with users, each user has their own keys (Settings → Account →
    Keys, or `luu user key add`), the way intergate authorizes keys per
    subdomain. A key acts as its user.
  - On a luu without users, `[peer.<name>] key = "ssh-ed25519 …"` lists who
    may link.
  - An unknown key is refused during the SSH handshake, before any request.
- **One SSH connection, with channels both ways.** Whoever can dial does. That
  is the one behind NAT, which is why the direction of the connection says
  nothing about who controls whom:
  - the side that dialled asks for a `tcpip-forward` and serves the
    `forwarded-tcpip` channels the other side opens, as `ssh -R` does;
  - it opens `direct-tcpip` channels to the other side's API, as `ssh -L`
    does.
- **Reconnection, as intergate's client does it:**
  - it waits 1 s, then doubles each time, up to 30 s;
  - the wait goes back to 1 s once a connection has lasted a minute;
  - a key refused on the first try, or a forward refused, stops it and says
    why, instead of retrying forever;
  - a `keepalive@openssh.com` every 30 s finds a link that NAT dropped
    silently;
  - **a new connection for the same key and name replaces the old one**, so a
    reconnect takes over at once, without waiting for the dead one to time
    out.
- **Its own port, as intergate's 2222.** `[server] ssh = "0.0.0.0:2222"` on a
  luu that accepts links. A luu that only dials, the one at home, listens on
  nothing new.

```sh
# at home: link to the online server, once. It pins the server's key, shown
# as a fingerprint as ssh shows it, and stays in config.toml.
luu link https://luu.example.com --name casa
#   luu.example.com:2222 is SHA256:Xk3…  — the same as Settings → Server? [y/N]
#   casa's key, SHA256:p9Q…, is not on your account: add it in Settings →
#   Account → Keys, or open https://luu.example.com/keys?add=…
# `luu serve` keeps the link open while it runs, and reconnects.
```

```toml
# config.toml at home, as `luu link` writes it
[peer.online]
ssh = "luu.example.com:2222"
host-key = "ssh-ed25519 AAAA…"     # pinned
dial = true                         # this side opens the connection
may = ["sessions"]                  # what online may do here
offer = ["gemma"]                   # providers online may send to, here
```

### 1. A local luu managed from an online luu

- The online luu shows **`/h/casa/` to the user whose key made the link, and
  only to them**. For anyone else it is a 404, as another user's session is.
  `hosts_allowed`'s rule changes for a linked host and only for it: its
  reason was *whoever holds this server's token*, and a linked host is held
  by one user's login, which is checked with `Origin` like every other write.
- Each request the online page makes of `/h/casa/api/…` becomes a channel to
  the local luu. **The local luu serves it under the peer's identity, not as
  loopback.** A loopback request may do anything here, Settings and the host
  shell included. A peer may do what `may` lists:
  - `sessions`: list, create, run, approve, sleep and delete;
  - `terminal`: off unless listed;
  - Settings writes: never.
- The page is the online luu's build, as it is for `[host.*]` today. The wire
  version makes two builds refuse each other out loud.
- **Sessions stay at home.** The online luu carries bytes and keeps nothing,
  as the design doc says of a host. What the online page shows does pass
  through the online server, which ends TLS for the browser and holds the
  connection: **a link trusts the online server with what crosses it**. A
  luu run by somebody else should not be linked.

### 2. Providers across luus

**A luu offers a provider; another sends to it by name. The key and the engine
stay where they are.**

- **The offering side** serves `POST /api/infer/<provider>/…` and passes the
  request through to that provider's own wire (OpenAI, Anthropic or Ollama),
  adding its key and starting its engine as a local session would.
  - It offers only what `offer` lists for that peer. On a server with users,
    it offers only providers the owner marked `offer = true`, to every user's
    key.
- **The sending side** names it:

  ```toml
  [provider.casa-gemma]
  via = "online"          # a [peer.*]
  provider = "gemma"      # its name there
  ```

  - Backend, model list and window are read from the other side, as the
    provider form already asks a server.
  - **A `via` provider is off this machine.** Local-first's rule stands: as a
    default it needs `remote = true`, and every run prints where it sends:
    `provider: casa-gemma → gemma via online (remote)`.
- **The request is not sent through a port on loopback.** On a server with
  users, a loopback port is open to every user's commands. The backend's HTTP
  reaches the channel in-process: either a connector in agent-core's backends,
  which use `reqwest` today, or a unix socket in the state directory, which no
  session is granted. The build decides which.

The four directions are the same two pieces:

| sends → offers | who dials | example |
| --- | --- | --- |
| local → local | either, on the LAN | the laptop uses the workstation's 32b |
| local → online | local | the laptop uses the server's Anthropic key, as its user |
| online → local | local (NAT) | an online session uses the GPU at home, over the link `luu link` opened |
| online → online | the one that can | server A uses server B's engine, with A's key on one of B's users |

**Online → local makes one provider per user on the server.** The provider
that `casa` offers reaches the server through ana's link, so **only ana's
sessions see it**. Row 61 decided that a remote server uses its own
configuration, for now. This narrows that decision rather than reversing it:
nothing ana writes changes another user's list, and the provider exists only
while her link does.

### What `[host.*]` becomes

`[host.<name>]` with `url` and `token-file` keeps working while the links are
built, and is then replaced by `[peer.<name>]`: the same page under `/h/<name>/`,
reached by key instead of by token. The **API tokens of row 60** are
superseded by user keys, for the CLI too: `luu --peer online sessions` opens a
channel with the same key.

## What it costs

- **`russh` and its crypto** must build without OpenSSL, as `lettre` and
  `reqwest` already do here, on the four targets `setup.sh` installs (one of
  them is cross-built for Intel macOS). This is checked before anything else.
- **A second port.** It must be opened in the firewall, published in compose,
  and added to the chart as a Service port (a LoadBalancer or a Traefik
  `IngressRouteTCP`, as intergate's chart does). Caddy, as compose uses it,
  proxies HTTP only.
- **Two identities in one process**: loopback, and a peer limited by `may`.
  Every route that reads `who` today needs a third answer, and a test that a
  peer cannot reach Settings or the host shell.
- **The backends' HTTP through a channel**: either a connector in the backends
  or a socket. Either is new code under the most-used path.
- **What a link trusts.** The online server sees everything that crosses it,
  and a link carries `sessions`, which means running commands under the local
  policy. Cutting a link from home must be one command (`luu link --off
  online`), and from the page, a button.

## Rejected

- **Tokens** (row 60). They are bearer secrets: whoever reads one is its
  holder. Over a LAN's plain HTTP they are sent with every request, and
  revoking one is a database row instead of a line in a list of keys. Asked
  against, in the quote above.
- **`ssh -R` with OpenSSH, straight to `luu serve`'s port.** It works with no
  new code, which is why it came up first: `ssh -R casa:80:localhost:7878`.
  But every forwarded request would arrive from loopback, which here means
  Settings, engines and the host shell. The local side has to know it is a
  peer, so it has to be luu that serves the channel. For the same reason a
  local luu is not exposed through intergate itself.
- **The peer's environment, `env:`, for a key.** A session's commands inherit
  luu's environment (`secret.rs`, and the SMTP password's record). The
  identity key is a file in the state directory.
- **Noise or WireGuard of our own.** Either would encrypt end to end through
  TLS terminators, but SSH already does, with a host-key model people know,
  and fingerprints `ssh-keygen -lf` can read.
- **Tailscale or WireGuard as the answer.** They solve reachability and none
  of the rest: who the peer is on the other side, what it may do there, and
  which providers it may use. They stay a fine way to put two luus on one
  network, and `[peer.*] ssh` works over them as it does over the internet.
- **SSH over a WebSocket on 443**, to need no second port. Possible, since
  `russh` runs over any byte stream, and kept for later. intergate has run
  with a port of its own without trouble, and the first build should not have
  two transports.

### The online server's key comes over HTTPS, not on trust

A first link cannot ask *is this the right key?* the way `ssh` does when it is
started from a form, and a person cannot be expected to compare fingerprints.
intergate writes the host key into the script it serves over HTTPS. luu does
the same with the server's page:

- `GET https://luu.example.com/api/link.json` answers
  `{"ssh": "luu.example.com:2222", "host_key": "ssh-ed25519 …"}`;
- Remote access pins that key, and the SSH handshake must match it;
- so the trust is the certificate's on the address that was typed, once.

The server learns the local luu's key the same way in reverse. Remote access
shows a link to `https://luu.example.com/?add-key=<public key>&name=casa`,
which opens Account → Keys on the online page with the key filled in, for the
logged-in user to add.

## Built, 2026-11-04: rows 65 and 66

The online page is a way into the luu at home. What changed from the plan:

- **`luu link`, not `luu key`.** `luu key` already makes the keys signed
  approvals use, so links have their own command: `luu link key`, `luu link
  add <url> --name <name> [--as <peer>]`, `luu link list` and `luu link
  remove`. A user's keys are `luu user key add|list|remove` online.
- **A refusal is retried every 30 s, where intergate's client stops.**
  intergate's client runs in a terminal, where stopping is how you find out.
  `luu serve` runs in the background, and the fix for a refused key is to
  add it on the other side, so the link should follow by itself. It did, in
  the page check below.
- **No `/dev/urandom` key from `rand`.** The seed is the same 32 bytes from
  `/dev/urandom` that `auth.db`'s codes use (`users::random`), so `rand` is
  not a dependency of luu's own, only of `russh`'s.
- **A key's mode is checked as a token file's is**, for `id_ed25519` and the
  host key. Both are made `0600`.
- **What a peer's request looks like past the gate.** Its `Cookie`,
  `Authorization`, `Origin` and `Host` are dropped. `Host: localhost` and
  `Origin: http://localhost` are set, plus the server's own bearer token when
  it has one. Every check below the gate (the terminal's `Origin`, the
  engines' `Host`, the token) then reads it as this machine's own page, which
  it is allowed to be once `may` has said so. `/api/auth/*` is never a
  peer's, so the page under `/h/<name>/` gets a 403 from `me.json` and draws
  itself as a page without users, which the luu at home is.
- **`[server] ssh` is on by default** from `luu config server`
  (`0.0.0.0:2222`, `--ssh none` for off), with `--ssh-public` for a NodePort
  or another port in front. It is read only on a server with users. The chart
  gives it a `-links` Service (LoadBalancer by default), compose publishes

  visit, so it does not cover the key being added.

Two changes from *2. Providers across luus*, both of them simplifications:

1. **No `[provider.x] via = …` to write.** A provider another luu offers
   appears by itself while the link is up, named `<provider>@<peer>`:
   `gemma@casa` on the online page, `claude@online` at home. A link already
   is the typed destination, and a table written for each provider would be
   a copy of the other side's that goes stale. It is never a default, so
   local-first's `remote = true` rule is not reached: it is chosen per
   session, and that is typing it. `@` is not in any provider name this
   page writes, and a profile with that exact name, if somebody wrote one by
   hand, wins.
2. **The backend's HTTP reaches the channel through a unix socket**,
   `<state>/sockets/links-<pid>.sock`, `0600`, in a `0700` directory under
   the state directory that no session is granted. reqwest 0.12.28 dials one
   (`ClientBuilder::unix_socket`), so the three backends only take a client
   (`with_http`) and stay as they are. The socket routes
   `/via/<owner>/<peer>/…` to the link: `_` for a luu that dials, a user's
   id for a server with users. That is how a server keeps one user's linked
   providers from every other user's sessions.

**The wire.** A luu offers through `/api/infer`:

- `GET /api/infer` lists what it offers: backend, model, window, tool calls;
- `GET /api/infer/<p>/models` gives that provider's model list;
- `ANY /api/infer/<p>/to/<path>` passes the request through to the
  provider's own URL, with its key added and its engine started. The key
  and the engine never leave.

**Who reaches it:**

- At home, the online server comes in over the forwarded channels, behind
  the peer gate. `/api/infer` is `sessions`: whoever may start a session
  here may already send to these providers.
- Online, the luu at home comes in over `direct-tcpip` channels on its own
  link. Those reach a router that has `/api/infer` and nothing else, as the
  key's user.

**What is offered: everything a session there can use**, as answered above,
less a provider marked `offer = false` (Remote access at home; the file on
a server, until roles reach Settings).

**One rule bent, on purpose.** A server with users refuses a session a
destination off the machine (`destination_for`, *a token says who may reach
the port, not where this machine's prompts may go*). A provider through the
user's own link is let through: the link is theirs, and they chose it.

## Built, 2026-11-04: row 67

As appended above, with one correction to it and two details.

**The correction: the socket's folder is not what keeps other sessions
out.** The section above says the socket is in a folder *that no session is
granted*. But a session's commands run as luu's own user, a unix socket's
mode does not stop that user, and Landlock does not restrict `connect` on a
pathname socket. On a server with users, a command could have reached the
socket and named another user's link. **Each path is signed instead**:
`/via/<owner>/<mark>/<peer>/…`, where `<mark>` is SHA-256 of a 32-byte secret
made at start and the owner. The secret never leaves the process, and the
backend's URL carries only its own owner's mark. **The relay also passes only
`/api/infer`**, so even a path that is its owner's own cannot reach a linked
luu's sessions through it.

**Two details:**

- **A socket's path is at most 108 bytes on Linux and 104 on macOS.** A long
  `LUU_HOME` went past that, and the scratch folder used for the page check
  did. Then the folder is `<temp>/luu-<uid>`, made `0700` and refused unless
  it is this user's own and not a link. Sockets of processes gone are
  removed at start, checked with `kill(pid, 0)`.
- **A backend names itself after its URL's host**, so the relay's URL has
  the peer's name there (`http://casa/via/…`). The page says `openai@casa`,
  and the socket ignores the host.

**Not done:**

- **A llama.cpp engine is started on the profile's model**, not on the one a
  request names. A local session restarts it on another model (`for_run` on
  the resolved model). The pass-through does not read the request's body to
  learn it.

   (it used to be read only on a server with users). Who may link is
   `[peer.<name>] key = "ssh-ed25519 …"`: a peer it does not dial. Its
   `may` says what that peer may do here. The link is known by that table's
   name, whatever the dialling side calls itself. A key on no `[peer.*]` is
   refused at the handshake, as on a server with users.
   - `ssh`, `host-key` and `name` are needed only to dial; `key` only to
     accept. A table may have both.
   - `luu link allow <name> <key>` writes one, and Remote access adds one.
     Like every write there, it is this machine's only.
2. **Either side opens the other's page under `/h/<name>/`.**
   - The dialling side opens the accepting side's over `direct-tcpip`
     channels. The accepting side answers with its router behind the peer
     gate, under the `may` it gives that peer.
   - The accepting side opens the dialling side's over `forwarded-tcpip`,
     as an online server does. The dialling side answers under the `may` it
     gives its peer.
   - On a luu without users, `/h/*` stays this machine's page's only
     (`hosts_allowed`), as it was for a host.
   - A server with users still answers a linked luu's own channels with
     `/api/infer` alone: its page is reached by its URL and a login, not
     through home.
3. **`/api/link.json` on a luu without users** says its address from the
   request's own `Host`, when there is no `ssh-public` and no origin. The
   workstation's address is whatever the laptop typed.
4. **Providers cross on these links too**, both ways (row 67's relay, with
   owner `_` on either side).
5. **`[host.*]` is kept and stops being offered.**
   - The project modal lists linked luus beside the hosts.
   - *Add a host* becomes *Link a luu*, which opens Remote access.
   - An existing `[host.*]` still works and can still be edited.

   Removing it would refuse every `config.toml` that has one
   (`deny_unknown_fields`). That is a later decision, once nothing is left
   that only a token reaches.
6. **The CLI by key: nothing to replace.** No `luu` command talks to a remote
   server; `[host.*]` is only the page's. When one does, it reaches the other
   luu over its link, as the page does.
