# The page asks for a file once

> *Me da la impresión de que los componentes de jq79 se piden una y otra vez a
> la red, en lugar de cachearlos.*

## What it was

Counted with a browser, against `luu serve`: one visit that opened Settings
(Engines, Models) and the sessions dialog three times each asked for 74 of the
page's files, and for 25 of them more than once — `scrollable.html` 14 times,
`brand-icon.html` 13, `button.html` and `sub-modal.html` 9. A reload then
fetched all 51 it needed again, whole: 200 for every one.

Two causes, one on each side:

- **jq79 fetches a component every time a `setup` imports it.** Its loader
  (`Component79.fetch`, which an `await import("….html")` in a setup is) keeps
  nothing between calls, and a setup runs each time what it draws is drawn
  again — a card in a list, a dialog opened a second time.
- **The server gave the browser nothing to revalidate with.** `serve_asset`
  answered with a `Content-Type` and the bytes: no `ETag`, no
  `Last-Modified`, no `Cache-Control`. Without a validator a browser cannot ask
  *has this changed?*, so it asks for the file.

## What it is

**The server: each file's sha256 is its `ETag`, with `Cache-Control:
no-cache`.** rust-embed already hashes every file it embeds (and every file it
reads from disk in a debug build). `no-cache` is *revalidate every time*, not
*do not cache*: a reload asks, and a file that did not change comes back as a
304 with no body. A new binary's page is never served out of an old copy,
which a `max-age` would have risked for as long as it said.

**The page: a component's text is kept for the visit.** `lib/components-once.js`,
imported before jq79 in `index.html`, wraps `fetch`: a `GET` for a `.html`
path on this origin, outside `/api/`, is fetched once and every later ask is
answered with the text it brought. A failure is not kept. A workspace file
named `x.html` is never caught, since the page asks for it by a query
(`/api/workspace/file?path=…`), not by its path.

Measured again: the same visit asks for each file once (0 asked twice), and a
reload is 54 files with no body.

## Rejected

- **Keeping components in jq79.** It is the place for it — a loader that
  remembers what it loaded — and it is vendored here as a build; a fix there
  is a change to jq79 and a new copy of it, which this does not wait for. The
  wrapper says what it works around, and goes when jq79 keeps its own.
- **`max-age` on the page's files.** Fewer requests on a reload than a 304
  each, and a window in which an upgraded binary serves the page it replaced.

## Built, the same day

Tested: `serve_ws.rs` — a file of the page carries its hash as a quoted
`ETag` and `no-cache`; asked again with it, a 304 with no body; with another,
the file. The whole live-server suite runs with the wrapper in place.
