# Policies, not postures: lists that combine, grants a session keeps

**Status:** proposal; nothing of the policy model is built. One piece landed with
it, because the rest depends on it: the working directory is a flag
(§*Landed with this record*). Worked out in conversation, in these words:

> la idea es, en lugar de las posturas, tener listados de políticas de acceso:
> uno para shell, otro para el acceso a la red. Un entorno sería una
> combinación de políticas. En una sesión se indicaría el perfil de seguridad
> y se guardarían 'grants' (acciones permitidas por el usuario)

> Para docker podemos usar volúmenes para compartir archivos sin copiarlos, no?

> Estoy pensando que las políticas, grants, etc; no tienen que estar en el
> contenedor, es el harness (luu) el único que debe consultarlo

> Por aclarar, la carpeta raíz ahora mismo es el propio repositorio de luu
> porque es el directorio de trabajo. Cuando se ejecute (en producción) sería
> un binario disponible desde el $PATH y la carpeta de trabajo será en la que
> se arranque el binario, a menos que se le especifique otra a través de un
> parámetro

> Ok, estoy de acuerdo. Para desarrollo, habilitaremos definir el working dir
> en el .env del repositorio de luu

> Ese working dir, será la raíz a partir de la cual el usuario podría elegir
> una subcarpeta

## What there is today

A **posture** is a name in `config.toml` for a policy file
([`a-session-picks-its-executor`](2026-09-08.a-session-picks-its-executor.completed.md)):

```toml
[posture.container]
policy = "luu.container.toml"
```

and the file decides three things that do not depend on each other:

- **where it runs** — `[worker]`: the host, or a runtime and an image;
- **what it may run and touch** — `[sandbox]`: `commands`, `paths` with their
  access, `enforcement`, `limits`;
- **what it may reach** — `[sandbox] network`, plus the `egress` a plan
  declares, filtered by the host's proxy
  ([`egress-through-the-host`](2026-09-04.egress-through-the-host.completed.md)).

The same file also holds `[approvals]`, who may approve and whether it must be
signed. So *Docker with no network* is a copy of the whole file with one line
changed, and a posture cannot be narrowed on one axis without becoming another
posture.

The pieces that decide are already luu's, on the host: the gate and the plan
it approves, the draft's floor, *allow once* on a refused write
([`a-refused-write-asks`](2026-10-02.a-refused-write-asks.completed.md)), the
egress proxy. What crosses to the worker, per call, is a `WireSandbox` —
`base`, the whole `SandboxPolicy` and the `authority` that granted it
(`crates/agent-core/src/worker/mod.rs`) — and the worker resolves it and holds
the child to it with Landlock, seccomp and rlimits. The container keeps nothing
between calls.

And the policy is found **in the working directory**: `policy_path()` is
`<cwd>/luu.toml` unless `--sandbox` names another, and Settings → Runtimes
offers the files at the top of the working directory. In this repository that
is luu's own `luu.toml`. In production the working directory is the project
being worked on — luu is a binary on the `PATH` — so:

1. **A cloned repository brings its own policy.** A `luu.toml` in it decides
   what the agent may run, reach and write, and who approves. Opening a folder
   is accepting its rules: the problem VS Code's workspace trust exists for.
2. **The policy is within the model's reach.** The working directory is
   mounted read-write into the worker, so a job that writes `luu.toml` changes
   the next session's policy. A person sees the write at the gate, but the file
   should not be within reach at all.

## The proposal

### 1. Lists, by axis, each in three zones

Three kinds of policy — shell, network, files — each a named list in three
zones. `allow` is done without asking, `ask` is put to the person, `deny`
cannot be granted by anyone:

```toml
[shell.dev]
allow = ["cargo", "rustc", "git", "rg", "ls"]
ask   = ["npm", "sh"]
deny  = ["curl"]

[network.crates]
allow = ["crates.io", "*.crates.io", "*.github.com"]
ask   = ["*"]

[network.off]
allow = []

[files.tree-rw]
allow = [{ path = ".", access = "read-write" }]
ask   = [{ path = "~/.config/gh", access = "read" }]
deny  = ["~/.ssh"]
```

Files are a third list though only shell and network were named: the most
common thing asked for today is a write, which is neither.

### 2. An environment is a combination

```toml
[environment.local]
runtime = "host"
shell   = "dev"
network = "off"
files   = "tree-rw"

[environment.container]
runtime = "docker:luu-worker:dev"
shell   = "dev"
network = "crates"
files   = "tree-rw"
```

A session names its environment — the *security profile* — when it starts, as
it names its posture today, and a resume compares what the names resolved to,
never the names: the rule
[`what-an-approval-was-granted-under`](2026-09-17.what-an-approval-was-granted-under.completed.md)
settled for postures, because a list behind a name can change tomorrow. The
session's header records each policy as resolved, or its hash.

### 3. Grants: what the person allowed, with a scope

A grant turns an `ask` into an allow. It is never more than that: `deny` is
not grantable, so *never past the policy* stays the rule. Scopes:

| scope | lives in | what is already this |
|---|---|---|
| once | the call | *allow once* on a refused write |
| job | the approved job | a plan approved at the gate |
| session | the session's stream | — |
| project | luu's config, keyed by working directory | — |

```json
{"type":"grant","kind":"network","target":"registry.npmjs.org","scope":"session","by":"person","turn":4}
```

A grant is shown in the session and can be taken back. *Project* is what
*always* means — allowing `npm` in one project does not allow it in another —
and it is written where a person reads it, not kept silently.

### 4. luu decides; the container only holds

Policies and grants are luu's alone. The worker is not told why something is
allowed, only what this call may do. What crosses per call becomes the outcome,
not the policy:

```
{ cmd: ["npm", "install"],
  paths: [{ path: "/home/you/project", access: "read-write" }],
  network: "proxy" | "none",
  limits: { cpu-seconds: 300 } }
```

- **No `authority`.** It is carried so a denial inside the worker can say who
  granted what; luu can word that from the worker's answer.
- **No allowlist.** luu checks `argv[0]` against the shell policy before
  sending. The worker resolves the program in the image and says whether it
  is there — the *granted by the policy, absent from the image* answer it
  already gives in its `Hello`.

Enforcement cannot leave the boundary: luu sees the call (`cargo build`), not
what the process does after it (a `build.rs` that opens a socket or reads
`~/.ssh`). Only the kernel inside sees that.

### 5. Files are mounts, decided when the container starts

The tree is already a bind mount at its own path, nothing copied
(`crates/agent-core/src/worker/runtime.rs`). The files policy becomes the
container's mounts:

| zone | in the container |
|---|---|
| `allow`, read | `--mount type=bind,…,readonly`: the kernel refuses a write |
| `allow`, read-write | a bind mount |
| `ask` | mounted, and closed by Landlock until a grant opens it |
| `deny` | not mounted: the path does not exist inside |

A mount is fixed for the container's life, so what is not mounted cannot be
granted without restarting the worker; that is why `ask` is mounted and held
by Landlock, which is applied per process, per call. `deny` becomes stronger
than today, where only the tree is mounted and Landlock narrows inside it.
**Named volumes** take what should outlive a session without being the
person's files — cargo's registry, `target/`, `node_modules` — which on macOS
is also much faster than a bind mount. The same split applies to the network:
`--network none` is the environment's, fixed at start; a host added to the
proxy's allowlist is a grant, live. Apple's `container` spells some options
its own way (it already does `--user`); whether it takes `readonly` on a mount
is to be checked before it is promised there.

### 6. Policies live in luu's config, never in the working directory

The only source is the state directory's `config.toml` (the *Config dir*
Settings → General shows). A project may ship a **suggestion** — its
`luu.toml`, or `.luu/policy.toml` — which luu shows and does not apply:

> This project suggests: `cargo`, `rustc`, `git`; network to `crates.io`.
> Adopt it?

What is adopted is kept in luu's config with the project's path and the
file's hash; if the project's file changes, luu asks again rather than
following it. `--sandbox FILE` stays: a flag is the choice of whoever starts
luu, not something that came with a clone, and the runs in `RECORD/` made under
this repository's `luu.toml` are reproduced by passing it.

## Migration

`[posture.<name>] policy = "<file>"` reads as an environment whose three lists
are that file's `[sandbox]` with everything in `allow` — what a posture means
today — and whose runtime is its `[worker]`. Nothing asks until a list has an
`ask`. The page's posture picker becomes the environment picker; Settings →
Runtimes becomes the lists and the environments.

## Landed with this record: the working directory

The root luu works under, inside which a session's project folder is picked
(*Which project?*), was always the process's current directory, read by
`current_dir()` wherever it was needed. It is now **`--workdir PATH`**, global,
or **`LUU_WORKDIR`**: the process moves there before anything reads it, so
every reader agrees, and a path that is not there refuses to start
(`--workdir /nope: cannot work there`). The picker says `luu serve` *works in*
it rather than *was started in*.

In this repository the working directory would be luu's own source, so
`make up` sources the checkout's `.env` — `.env.example` documents
`LUU_WORKDIR`, `.env` is ignored by git. **luu itself never reads a `.env`**:
one in a project would set what luu may reach, which is §6's problem again.

Checked: `LUU_WORKDIR`, `--workdir` after the subcommand, and `make up` with
a `.env` each give `/api/settings` the named directory as its `base`;
`--workdir` before the subcommand, at a path that is not there, exits 1 with
that message. `cargo fmt --check`, clippy
with `-D warnings`, `cargo test --workspace` green.

## Appended 2026-10-22: decided, and where every file lives

Asked for an example of the files — what each holds and where it lives —
before deciding (*"Quiero tenerlo bien claro antes"*), and then: *"Ok, me
cuadra"*. What that settles:

### 1. A grant only ever turns an `ask` into an allow

`deny` is not grantable by anyone in a conversation: it is the limit whoever
configured luu set, and the place a model that asks seven times, or asks with
a good reason, gets a yes. **What no zone names is denied** — the rule luu
already has, an empty allowlist never meaning *anything* — and a list that
wants to be permissive says so with `ask = ["*"]`. A refusal carries a way to
the fix outside the conversation: *Add to the policy*, opening Settings with
the item filled in. At the gate: what a plan asks for in `allow` needs nothing,
in `ask` the approval is the grant (job scope), in `deny` it is refused with
the reason, as a plan past the policy is today.

Considered and not taken: grants that widen anything (the policy becomes a
default and the real one is the session's pile of grants, which a resume has
to carry and nobody reads), and `deny` firm with everything unlisted asked
(every new command a question, and a person who says yes without reading).

### 2. Files are the third list, in two layers

What the others do, as their documentation stood at the time: Claude Code has
`allow`/`ask`/`deny` rules per tool, files among them (`Read(./.env)`,
`Edit(./src/**)`), `deny` first, reads in the working directory free and edits
asked, and an optional OS sandbox for its shell; Codex CLI a sandbox mode
(`read-only`, `workspace-write` with `writable_roots`, full access) held by
Seatbelt and Landlock + seccomp, plus an approval policy; Gemini CLI tool lists,
a Seatbelt or container sandbox and trusted folders; Cline auto-approval by
category; Aider no sandbox and only the files `/add`ed; OpenHands everything in
a container. Common to all: files are their own axis, nearly always a coarse
boundary the OS holds and fine rules by path the harness checks.

luu does the same:

- **Coarse, the environment's, fixed at start**: the mounts and Landlock's
  roots — the project folder and the image's toolchains, nothing else.
- **Fine, luu's, per call**: `write_file` and `edit_file` against the list's
  patterns, `ask` going to the gate or *allow once* and `deny` refused even
  inside an approved job. This is what exists already, written down: the
  draft's floor is *read, allowed*, and every write goes through the gate or
  *allow once*, which is *write, asked*.

**The `deny`s that matter most are the ways out**: files the model writes
inside the tree that the person's own machine later runs — `.git/hooks/**`
(on the next commit), `.git/config` (`core.hooksPath`), `.envrc` (direnv) —
and the secrets, `.env`, `.env.*`, `**/*.pem`. Landlock only grants, so it
cannot close a subfolder of a tree it has opened for writing, and a
`run_command` could still write a hook. In a container that is closed by a
mount: the subfolder bound again `readonly` over the tree, and a file denied
for reading covered by `/dev/null`. On the host runtime only luu's own file
tools are held to it, and the page says so.

### 3. `[approvals]` belongs to luu's config, not to a project

It says who may authorise the agent, not what the agent may do: the
configuration of trust in this instance of luu, beside `--auth-token-file` and
how the server is exposed. A project's `luu.toml` can set it today, so a
cloned repository could add a key of its own (whoever holds the private half
then signs approvals this luu admits, and the record names them), turn
`required` off where it was on, or turn it on with keys nobody here holds.

- The **keys** live in `config.toml`'s `[approvals]`.
- **Whether a signature is required** follows the exposure by default —
  optional on loopback, required off it, as the bearer token already is — and
  an environment may make it stricter, never looser.
- Where an environment requires signatures, a session's grants need one too,
  as *allow once* is already off there.
- A project's `[approvals]` is ignored, with a notice, unless the file is
  named with `--sandbox`.

### 4. The folder chosen is the boundary, not a filter

Today *Which project?* narrows what the page **lists**; the sandbox stays the
whole working directory, so a session in `~/proyectos/tienda` can reach
`~/proyectos/blog`. With `files` paths relative to the project, the folder
chosen becomes the session's base: what is mounted, what Landlock opens, what
`.` means. The working directory stays the root it is chosen under.

### Where everything lives

For a person who starts `luu serve` in `~/proyectos` and picks `tienda`:

```
/Users/joshua/
├── .config/luu/                      luu's config dir (LUU_HOME); read by luu only
│   ├── config.toml                   providers, the lists, environments, [approvals]
│   ├── sessions.db                   each session: what it resolved, and its grants
│   ├── token, *.key                  (as today)
│   └── logs/
└── proyectos/                        the working directory
    ├── tienda/                       the folder chosen: the session's base
    │   ├── .luu/policy.toml          the project's suggestion: shown, never applied
    │   ├── .env                      the project's: luu does not read it; denied
    │   ├── .git/hooks/               mounted read-only
    │   └── src/…
    └── blog/                         out of reach of this session
```

| file | path | written by | read by | in the container |
|---|---|---|---|---|
| `config.toml` | `~/.config/luu/` | Settings | luu | never |
| `sessions.db` | `~/.config/luu/` | luu | luu | never |
| a suggestion | `<project>/.luu/policy.toml` | the project's authors | luu, to show it | in the tree, unused |
| the project's `.env` | `<project>/.env` | the project | nothing of luu's | covered |
| luu's `.env` | `<luu checkout>/.env` | a developer | `make up` only | no |

- `config.toml` takes `[shell.<name>]`, `[network.<name>]`, `[files.<name>]`
  and `[environment.<name>]` beside the providers, in place of
  `[posture.<name>]`. An environment names one list of each kind, a `runtime`
  (and `image`), `limits`, and `caches` — paths given named volumes, such as
  `/root/.npm` or `./node_modules`, which outlive a session without being the
  person's files.
- **A suggestion adopted is copied**, as `[shell.tienda]` and so on, with
  `from = { file, sha256 }`; when the project's file no longer matches the
  hash, luu asks again.
- **A session's header** records, per list, its name and the hash of what it
  resolved to; a resume is admitted only when they still match. **A grant** is
  a line of the session's stream: `{"type":"grant","turn","kind","target",
  "access"?, "scope": "once"|"job"|"session", "job"?, "by"}`.
- **The container** gets mounts at start — the project, the read-only
  overlays, `/dev/null` over what may not be read, the named volumes — and
  per call only `{ cmd, paths, network, limits }`. `~/.config/luu` is never
  mounted.
- **This repository**: `luu.toml` stays at its root for the runs in `RECORD/`,
  passed with `--sandbox luu.toml`, and becomes `.luu/policy.toml` as the
  suggestion for when luu works on itself.

### In what order

Each step stands on its own and leaves luu working:

1. **The model**: parse the lists and the environments; read a
   `[posture.<name>]` as an environment whose lists are its file's `[sandbox]`
   with everything in `allow`; record what was resolved, hashed, in the header.
   Nothing asks yet.
2. **luu decides**: the zones checked per call on the host; *ask* generalised
   from *allow once* to commands and hosts; grants as stream lines; the gate
   reading the zones.
3. **The seam**: the worker gets `{ cmd, paths, network, limits }` instead of
   `WireSandbox`, no `authority` and no allowlist (a `PROTOCOL` bump); the
   files list becomes the mounts; the folder chosen becomes the base.
4. **The working directory stops deciding**: its `luu.toml` is no longer the
   policy unless named with `--sandbox`; `.luu/policy.toml` is offered as a
   suggestion and adopted with its hash; `[approvals]` moves to luu's config.
5. **Settings**: the lists and the environments edited where the postures are
   now, and the environment picker where the posture picker is.

*Always* (project-scoped grants) stays for later, as appended above.
