# The alternation that was not one — a GBNF grammar compiled, and shown to change nothing

**Status:** completed the day it was written. Picks up item 5 of
[`ROADMAP/2026-09-09`](../ROADMAP/2026-09-09/README.md) —
[`a-grammar-for-tool-calls`](2026-09-06.a-grammar-for-tool-calls.WIP.md), whose
first move [`the-bare-grammar-field`](2026-09-14.the-bare-grammar-field.completed.md)
cleared that same day — and builds the grammar itself. It compiles, it is
accepted by a live server, and it is proven, by construction and then by a
run, to leave the fifteen-prompt probe
([`the-tool-call-probe-run`](2026-09-14.the-tool-call-probe-run.completed.md))
exactly where it found it. This is not the failure it sounds like — it is the
answer to a question the WIP record left unmeasured — but it is not the
close item 5 was ordered for either.

## What was built

`agent_core::grammar` (new module, `crates/agent-core/src/grammar.rs`)
compiles a GBNF grammar from the same `Tool::parameters()` schemas the
prompt's own tool-definitions block already carries — no second description
of a tool's shape, the reason `tools/mod.rs`'s own `fenced`/`fenced_span`
split gives for `parse_call` and `task::parse_plan`. It compiles all five of
`Tools::standard`'s tools:

- **`string`, `integer`, and `array` of `string`** — every leaf type
  `Tools::standard` actually declares — plus `object`, are the whole scope;
  anything wider fails `compile` with a named `GrammarError` rather than
  compiling to a grammar that accepts the wrong thing.
- **Property order is `serde_json`'s sorted-map order, not the order the
  schema was written in.** `Tools::definitions`'s own doc comment already
  says schemas are "serialized through `serde_json`'s sorted maps"; what
  that means for a *grammar*, checked here for the first time, is that
  `read_file`'s required `path` sorts *between* its two optional properties
  (`max_lines`, `path`, `start_line`) and `run_command`'s required `command`
  sorts *between* its three optional ones. A grammar that assumed
  "required first" — the order every tool's own Rust source happens to
  declare them in — would have been wrong the moment it was run. The
  compiler instead builds two families of rules per object, `head(i)` (given
  nothing has been emitted yet) and `tail(i)` (given something already has),
  so a required property stays mandatory at whichever position it sorts to,
  independent of which optional properties around it are present.

## Two things a live server found that no test in this tree caught first

- **GBNF rule names cannot contain `_`.** `list_dir` alone — nothing else in
  the grammar — is a `failed to parse grammar` on `llama-server`
  (`b1-9d77fa172`, the same binary
  [`the-bare-grammar-field`](2026-09-14.the-bare-grammar-field.completed.md)
  used). Found by bisecting a real parse failure one rule at a time against
  the live server, the same way the underscore-in-rule-name bug always
  surfaces: silently, as a 400 with no line number. Every one of this
  project's tool names has an underscore, so every rule this module names
  after one goes through `rule_name`, which spells `list_dir` as
  `list-dir` for the *identifier* while leaving the JSON text `"list_dir"` a
  call must still contain untouched — two different jobs,
  [`json_literal`] and [`rule_name`], and confusing them is exactly the bug
  this fixes.
- **The alternation itself.** Below.

## What it says: `root ::= prose | call` is `root ::= prose`

`prose` is `[^\x00]*` — every string with no NUL byte in it. Every string
`call` can produce is also a string with no NUL byte in it. **`call`'s
language is therefore a subset of `prose`'s language, so their union is
`prose`'s language, unchanged.** This is not a probabilistic claim about
what a model is *likely* to do; it is a fact about what the two rules
*match*, true before a single token is sampled.

The run confirms it exactly. `RECORD/runs/2026-09-14.grammar-probe/`: the
same fifteen prompts as
[`the-tool-call-probe-run`](2026-09-14.the-tool-call-probe-run.completed.md),
same model, same temperature (0) and seed (7), against the same
`llama-server` instance, `tool.gbnf` attached as `grammar` this time. **Every
one of the fifteen replies is byte-for-byte identical to the unconstrained
run** — the same confident wrong answers (prompt 1's "Tools" heading, prompt
6's "edition 2018"), the same two `\`\`\`list_dir` / `\`\`\`run_command`
drifts, the same two continuations past a clean fence, the same three clean
calls. `score_call`'s verdicts: 3 Parsed, 2 Drifted, 2 Continued past the
fence, 8 No call — identical, prompt for prompt, to the ungrammared run.

**The grammar is not broken; the design built around it does not add
anything.** `object_rule`'s output — proven independently in
`grammar.rs`'s own tests, and by hand against the live server while
debugging the rule-name bug (a bare `read_file-arguments` grammar, asked to
produce JSON, produced exactly the shape it names) — is correct: *if* a
model is constrained by `call` alone, with no `prose` escape, its output
matches the schema exactly. What `root ::= prose | call` fails to do is
narrow anything, because `prose` is a blanket amnesty for every string that
`call` would have refused, including every drifted, malformed, or
run-on reply the unconstrained model already produces. A constrained
sampler picks among *grammatically reachable* continuations, and at
temperature 0 the greedy choice inside "reachable" was already what the
model wanted to say — so nothing about the sampling changed, because
nothing about what was reachable changed either.

## What this means for item 5

The two arms the WIP record named were never symmetric, and this is why:
`--constrain schema` (`response_format`, every reply becomes a document) has
no `prose` to leak through, because there is no alternative production at
all — the whole point named there was that it *narrows away* the "just
answer" case. `--constrain grammar` was supposed to keep that case *and*
narrow the call case, and the only way to keep an alternative while also
narrowing it is for the kept alternative to not be a superset of the other —
which `[^\x00]*` is, maximally. **Preserving the alternation and having it
mean something are in tension, and this grammar chose preserving it, for
free, at the cost of meaning nothing.**

## What was rejected — and what is still open, unattempted

- **Wiring `--constrain grammar` into the CLI as built.** It would be
  indistinguishable from doing nothing, and shipping a flag that changes
  nothing while claiming to is worse than not shipping one — the WIP
  record's own §What it costs already named "a model that cannot say no" as
  `--constrain schema`'s cost; this would have hidden a cost of its own
  (none) as if it were a benefit.
- **Restricting `prose` to exclude `call`'s language (or at least its fence
  prefix), so the alternation is a true partition.** The real fix, named
  and not attempted: GBNF can express "any string not containing this
  substring as a prefix" (a standard construction — build the complement
  automaton), but it is a harder grammar to write correctly than this one,
  and *this* record's job was answering whether the naive version worked, not
  building the one that might.
- **`--constrain schema` (the retry arm), unbuilt.** Still the one design in
  the WIP record with no leak: every reply is a call by construction, no
  `prose` escape exists to reach through. Untouched here — this record
  spent its budget on the arm the roadmap ordered first.
- **The compiler itself is not wasted.** `object_rule`'s two-family
  `head`/`tail` construction is exactly what `--constrain schema`'s
  per-tool argument shapes would need too, and exactly what a corrected,
  non-leaking `call` grammar would still use for its own object rules — the
  part that was wrong is `root`, not `object_rule`.
