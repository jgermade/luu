# Enforcement per job: the one field that narrows backwards

**Status:** plan, then code. Takes item 8 off
[`ROADMAP/2026-09-06/`](../ROADMAP/2026-09-06/README.md), the second of the two
entries left that a keyboard can finish, and the second of the three that link to
the design's open questions instead of to an argument.

## The problem

Narrowing is complete except for one field.

A plan is the sandbox for its job: `files` and `writes` say what it may reach,
`commands` what it may run, and since
[`network-per-plan`](2026-09-04.network-per-plan.completed.md) and
[`egress-through-the-host`](2026-09-04.egress-through-the-host.completed.md),
`network` and `egress` say what it may talk to. `Plan::narrow` builds the job's
sandbox out of all five, intersected with the session's.

`enforcement` is not among them. It is copied from the session, verbatim, in the
same constructor:

```rust
enforcement: session.enforcement(),
```

So the question *how hard does the kernel hold this job's children* has exactly
one answer per process, decided in `luu.toml` before any plan existed.

That is worst where the setting is most likely to be lenient. `best-effort` is
what a person types to get `run_command` at all on macOS, on a kernel without
Landlock, or inside a container whose seccomp profile blocks the filter — and
[`the-m4-pro-run`](2026-08-27.the-m4-pro-run.completed.md) is a whole record of
that being the ordinary case rather than the exotic one. Once it is typed, every
job in the session runs under it: the one reading files, and the one running the
thing nobody has read. The gate can narrow what a job may reach and cannot narrow
how it is held.

The design doc has said so under Open questions since the day egress landed:
*"`network` and `egress` are now per-job and filtered by host-side proxy;
enforcement level remains session-wide."*

## The proposal

`Plan::enforcement: Option<Enforcement>`, `None` meaning *does not ask*, and one
rule: **a plan may tighten and may not loosen.**

```rust
// The strictest of the two wins, which for this field means the session's
// unless the plan asked for more.
policy.enforcement = match (session.enforcement(), self.enforcement) {
    (Enforcement::Kernel, _) => Enforcement::Kernel,
    (_, Some(asked)) => asked,
    (session, None) => session,
};
```

### Why it is not just another field

Every other thing a plan narrows is a **grant**, and grants are monotone: less is
narrower, `false` is the floor, and a plan that names nothing gets nothing. That
is why `Plan::network` is a `bool` defaulting to `false` and why `unmet` reads
`self.network && !sandbox.network()` — *you asked for something the policy does
not have*.

`Enforcement` is not a grant. It is a **strictness**, and its permissive value is
the one with the reassuring name: `best-effort` is what lets a child run when the
kernel cannot hold it. So the check reads backwards from every other one in
`unmet`:

```rust
if self.enforcement == Some(Enforcement::BestEffort)
    && sandbox.enforcement() == Enforcement::Kernel
{
    unmet.push("enforcement best-effort: the policy requires kernel enforcement …");
}
```

A plan asking for `kernel` is narrowing and needs no permission. A plan asking
for `best-effort` is asking the policy file to relax, which is the one thing the
gate exists to make impossible — the same rule that keeps an amendment from
granting a path `luu.toml` refuses. It is the only field where the *plan asking
for more words* is the safe direction, and that is worth a sentence in the type
rather than a comment at the call site.

### `Option`, not a default

`Plan::network` can default to `false` because "asks for no network" is a real
position. There is no equivalent value here: `Enforcement::Kernel` as a default
would silently deny `run_command` in every job on every machine without Landlock
— which is most of the fleet in [`machines.md`](../ROADMAP/2026-09-06/machines.md)
— and `BestEffort` as a default would be every plan asking the policy to relax.
`None` is the third thing, and it is what every plan written so far means.

### The denial has to say which of the two refused

Today the refusal reads:

```
the kernel cannot hold this child (landlock); grant it anyway with
enforcement = "best-effort"
```

Under a per-job setting that advice is wrong half the time: the session may
already *be* `best-effort`, and the thing that refused is the plan. A denial that
names the wrong authority sends a person to edit the wrong file, which is the
failure `RECORD/2026-08-30.narrowing.completed.md` named when it said a denial
says which of the two refused. So the message branches on where the strictness
came from, and the plan's version points at the gate rather than at `luu.toml`.

### Three surfaces, because a plan arrives three ways

- **`## enforcement: kernel`** in a script, beside `## network:` and `## egress:`.
- **`ClientMessage::ApproveJob { enforcement }`** at the gate, so a person can
  tighten a plan the model wrote — additive, `Option`, no new variant, so the
  protocol and the record format do not move.
- **`Plan::describe`** prints it, because a plan the person is asked to approve
  has to show everything it decides.

## What it costs

- **A third spelling of the same enum**, in the policy file, in a script and on
  the wire. Mitigated by it being the same `Enforcement` type serialized by the
  same derive in all three.
- **A plan that can never run its commands is now expressible**: `kernel` on a
  box without Landlock denies every `run_command` the job makes. Deliberately
  *not* refused at the gate, unlike `closes_on` naming a command the plan does
  not allow — whether this kernel has Landlock is discovered when a child is
  prepared, not when a plan is read, and a gate that guessed would be wrong on
  the machine that matters. The denial says it, per turn, naming the plan.
- **One more thing that differs between a host run and a contained one.** The
  policy crosses the worker seam and the narrowed enforcement crosses with it,
  so a job that asked for `kernel` is held to it inside the container too — where
  the answer may be different from the host's, which is exactly what
  [`the-container-observed`](2026-09-03.the-container-observed.completed.md)
  measured.

## What was rejected

- **Letting a job loosen enforcement.** The obvious symmetry — a session at
  `kernel`, one job allowed `best-effort` because its command cannot be held —
  and it makes `luu.toml` a suggestion. If a session needs a lenient child it
  says so once, in the file, where a person reads it before the run rather than
  approves it in a hurry.
- **`limits` per job, at the same time.** Tempting because it is one struct
  along, and it is a different argument: a limit is a number to *spend* and a
  plan has no words for it, which
  [`what-the-audit-left`](2026-09-01.what-the-audit-left.completed.md) already
  argued and left open. Enforcement needs no new vocabulary — it is one enum
  the policy file already has.
- **A `strict: bool` on the plan** instead of the enum. Shorter, and it means a
  second spelling of a two-valued type that would have to grow a third value the
  day `Enforcement` does.
- **Deriving it**: tightening automatically for any job that was granted
  `network` or `commands`. Plausible as a policy and wrong as a default — it
  decides for the person at the gate, silently, in the one place this design
  keeps the decision visible.

## Still open

- **The gate panel exposes none of the three.** `network`, `egress` and now
  `enforcement` are on the protocol and reachable from a script and from a
  client; the debug UI's approve button sends files, writes, commands and
  `closes_on` and nothing else. That is a UI gap, not a protocol one, and it is
  the same gap for all three.
- **Nothing reports the *effective* enforcement of a job in the transcript.**
  `luu tools` prints the session's resolution; a job that tightened it says so
  only in a denial, and only if one happens.
- **`limits` is still session-wide**, and after this it is the last thing in the
  sandbox that a plan cannot narrow.

## 2026-09-06, during the code: two things the plan above got wrong

**The denial names the authority that is holding the child, not the one that set
the value.** The plan said the message would branch on *where the strictness came
from*, and it cannot: a narrowed `Sandbox` carries its `Authority` and its
`Enforcement`, and nothing links the two. A job sandbox at `kernel` looks
identical whether the plan asked for it or the session already had it. Making it
say more would mean a new field on `Sandbox` that also has to cross the worker
seam, where the policy is rebuilt from a `SandboxPolicy` that has no room for it
— a wire change for a sentence.

So the branch is on `Authority` alone, and the advice is written to be true
either way:

```
[run_command] denied: the kernel cannot hold this child (landlock is not
available in this kernel); job 1 runs under kernel enforcement — loosen it in
the plan if the policy allows it, in the policy otherwise
```

Which is the honest version of what the plan wanted: it no longer sends a person
to `luu.toml` when `luu.toml` already says `best-effort`, and it does not claim
to know which of the two typed the value. That gap is now in the design's open
questions rather than in a comment.

**The signature needed a line and it was free.** `Approval::canonical` builds the
signed bytes field by field, appending optional ones only when present, so
putting `enforcement` last means every signature made before this field existed
still verifies byte for byte — an approval that does not mention enforcement
produces exactly the string it used to. The alternative (a field always written,
`enforcement none` included) would have invalidated every signed approval on
disk for nothing. There is a test that pins both halves.

### What it looks like, one directive apart

Same session, `--sandbox-enforcement best-effort`, same command, on a kernel
without Landlock:

```
## job: list the tree                    ## job: list the tree, held by the kernel
## command: ls                           ## command: ls
                                         ## enforcement: kernel

[1] ← ok · commands allows `ls` ·        [1] ← denied · the kernel cannot hold
held by seccomp (no sockets, no          this child (landlock is not available
ptrace) + rlimits (cpu 300s, file        in this kernel); job 1 runs under
1024M) (missing: landlock …)             kernel enforcement — loosen it …
```

The left column is what every job in that session did before this record. The
right one is a job that asked to be held properly and was told the kernel cannot,
rather than being quietly run under an in-process check — which is the whole
point, and it is one line of a script.

### What is not measured

Nothing here is a context-management number, so there is nothing to compare
runs on. What was checked is behaviour: both directions of the gate, both
directions of `narrow`, the canonical form's two halves, the parser, and the
pair above run end to end. Whether a *person* reaches for this at the gate is
not something a test can answer, and the UI cannot even ask yet — the approve
button sends four fields and this is not one of them.
