# The tool-call probe: a scorer, and a corpus, for roadmap item 4

**Status:** a proposal, and the code it plans, built the same day. Roadmap
item 4 of [`ROADMAP/2026-09-09`](../ROADMAP/2026-09-09/README.md) — carried
since [`open-after-pr-1`](2026-08-26.open-after-pr-1.completed.md) — names it
as writable without a model; only running it against one is section A's kind
of work. This writes the harness. It does not run it against a model.

## The problem, restated from the WIP record

[`a-grammar-for-tool-calls`](2026-09-06.a-grammar-for-tool-calls.WIP.md#the-instrument)
named the gap precisely: `map-order-probe` scores which file a selector
reaches and says nothing about calls, and the precision run of 2026-09-06
found a failure by accident that no scanner in the tree counts — a reply
whose `\`\`\`tool` block parses correctly and then keeps writing, roughly
1 700 invented characters of a tool's result the model wrote itself.
`parse_call` reads the block right; the model did not know when to stop.

Four outcomes, one per reply, and only one of the four was ever scanned for:

1. **Parsed** — a call, and nothing after it.
2. **Drifted** — an attempt that missed the shape: `\`\`\`write_file` instead of
   `\`\`\`tool {"name": "write_file", …}` — the exact failure the gate probe of
   2026-08-31 found in turn execution.
3. **No call** — plain prose, no attempt.
4. **Continued past the fence** — a call parsed, and the model kept writing.

## The proposal

### 1. `score_call`, beside `parse_call`, reusing its scanner

Not a second parser. `tools::fenced` already answers *is there a `\`\`\`tag`
block, and what is in it* — the same function `parse_call` and
`task::parse_plan` both call, for the reason its own comment gives: *"two
scanners would drift on the same malformed block."* A caller that also wants
*what came after the closing fence* is a third caller of the same scanner,
not a new one, so `fenced` is split into `fenced` (unchanged signature) and
`fenced_span` (also returns the byte offset the closing fence ends at),
`fenced` a two-line wrapper over the new one.

```rust
pub enum CallVerdict { Parsed, ContinuedPastFence, Drifted, NoCall }

pub fn score_call(text: &str, tool_names: &[&str]) -> CallVerdict {
    // 1. a ```tool block that parses: Parsed, or ContinuedPastFence if
    //    anything but whitespace follows the closing fence.
    // 2. else a fenced block tagged with a tool's own name: Drifted.
    // 3. else a bare object that parses (parse_call's fallback): Parsed —
    //    there is no fence to have continued past.
    // 4. else NoCall.
}
```

**Why drift is checked by fence tag and not by shape.** The gate probe's own
failure — `\`\`\`write_file` — names the tool as the tag. A model that drops the
fence entirely and writes `{"path": …, "content": …}` with no `name` field is
already `NoCall` under `parse_call` (it fails `ToolCall`'s schema) and would be
indistinguishable from a plain wrong-shaped bare object without deciding,
unmeasured, which bare objects are "attempts." The fence-tag case is the one
version of drift this repository has actually observed, so it is the one
version this scores. A shape-based detector is not rejected, it is simply not
built on a single unreplicated example.

### 2. The corpus: fifteen prompts, one call each

`scripts/tasks/tool-call-probe.txt`, grounded the way `grounded.txt` is —
real questions about this repository, each answerable with exactly one call
to one tool (`read_file`, `list_dir` or `run_command`), so a future run
against a model is scoring the model's discipline and not the prompt's
ambiguity. No `.key` file: this probe does not score whether the *answer* is
right, only whether the *call* was made in the shape the preamble asks for —
a question `parse_call` and `score_call` can answer from the reply alone.

### 3. Proved without a model, the way coverage was

`select_probe.rs` computes coverage on every commit because it is a
structural question a fixture can answer. Scoring four reply shapes is the
same kind of question: `crates/luu/tests/tool_call_probe.rs` drives the
corpus against the **mock**, `--mock-cycle`'d through one fixture reply per
verdict, and asserts the harness recovers all four — proof the scorer works,
not a claim about a model. Unit tests beside `score_call` itself pin each
outcome to one literal string, the same way `parse_call`'s own tests do.

## What it costs

- **`fenced`'s signature is now two functions instead of one**, `pub(crate)`
  both, for one more caller inside the crate.
- **The drift detector is one example wide.** Stated above, and worth
  restating: it will not catch a drift shaped differently from the one this
  repository has actually seen.
- **The corpus does not (yet) test whether the model's *answer* is right,
  only its *shape*.** Combining the two — did it call correctly, and did it
  then answer correctly — is a later, larger probe; this one is deliberately
  narrower than that.

## What was rejected

- **Scoring drift by attempting to parse the fenced body as any known tool's
  argument shape.** It would catch more cases and it would also catch false
  positives — prose that happens to contain a fenced block of unrelated JSON —
  without a second real example to calibrate against. Narrower and correct
  beats broader and guessed.
- **A `.key` file scoring answer correctness.** Named above; a different,
  larger probe, and building it now would delay the row this one is for.
- **Running the probe here.** Roadmap item 4 keeps its own line: *the
  instrument is writable without a model; only running it is section A's kind
  of work.* This is the instrument.

  ever observed. One example is a fence tag; a second might not be.
