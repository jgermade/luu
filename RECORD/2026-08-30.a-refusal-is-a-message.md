# A refusal is a message: the server stops saying no in silence

**Status:** plan, then code. It closes the oldest of the small items in
[`2026-08-30.ready-for-the-m4-run.md`](2026-08-30.ready-for-the-m4-run.md) —
*no `busy` reply: `start_turn` refuses silently when a turn is running, and the
gate added a second silent refusal beside it* — which has since grown a third
and a fourth. It is also the **first change to the protocol since v1 was
frozen**, and most of this file is about whether that is worth it.

## The silences, all of them

Four places where a client asks for something, the server decides not to do it,
and nothing is said. A client cannot tell any of them from a message that was
never delivered.

| Where | Today |
| --- | --- |
| `on_prompt`, with a proposal pending | `return` |
| `begin_turn`, with a turn already running | `return None` |
| `close_task` / `reopen_task`, with a turn running | `return` |
| `approve_task`, an amendment the policy file does not grant | the entry is dropped from the plan |

The last one is mine, from the narrowing change earlier today, and its record
already says what is wrong with it: the information is on the wire — the plan
that comes back is missing the path — but *nobody notices*. A person types a
path at the gate, presses Approve, and gets a task that runs without it.

The UI hides three of the four by disabling the composer, which is exactly the
argument for fixing the server: the client behaving well is not a permission
model, and it is not an interface either. A second client, a stdio bridge, or a
person with a slow hand sees nothing.

## The message

```json
{"type": "refused", "request": "prompt", "reason": "pending",
 "detail": "task 1 is waiting to be approved or refused"}
```

`request` is the `type` of the client message that was refused, `reason` is a
small enum a client can branch on, and `detail` is the sentence a person reads.
Four reasons, one per row of the table above: `busy`, `pending`, `task` (the
task named is not in a state where the ask applies), `not_granted`.

**It is a protocol message, not a trace message.** The trace channel explains
the agent and never drives it, and this drives: it is why the composer is empty
and nothing happened. A stdio client running without `--trace` would lose it.

**It is broadcast, like everything else.** A second client watching the session
sees a refusal it did not cause, which is the same thing that is already true of
every other message: there is one session and one stream. Addressing a message
to one socket would need a client identity in the protocol, which is a much
bigger change than the problem justifies.

## The version, which is the actual decision

An unknown `type` in a tagged enum is a parse error, not a line to skip — this
repository has already paid for that once: `record::FORMAT` went from 2 to 3
when the task lifecycle arrived, for exactly this reason. So a new
`ServerMessage` variant is a change an older reader cannot make sense of, and
by the rule written on `protocol::VERSION` itself it bumps the version.

**`protocol::VERSION` becomes 2 and `record::FORMAT` becomes 4.**

This is the first bump since the freeze, and the freeze anticipated it in those
words. The compatibility directions are worth stating:

- **New server, old client**: `hello` carries `protocol: 2`, which is what that
  field is for. A JS client ignores an unknown `type`; a Rust one would not, and
  now has a number to check.
- **New client, old server**: never receives `refused`, and behaves exactly as
  today.
- **Old recordings**: still read. Nothing was removed or renamed; a format-3
  file has no `refused` line in it and every other line means what it meant.

## What was rejected

- **Waiting to batch it with the next protocol change.** There are two on the
  horizon — a plan that declares what it writes, a reason on a rejection — and
  batching them would keep the silence until whichever is last. Versions are
  cheap; a client that cannot tell a refusal from a lost message is not.
- **Reusing `failed`.** It carries a turn, and three of these four refusals
  happen when there is no turn to name. Sending `turn: 0` would be a lie in the
  one place the recording is supposed to be evidence.
- **A refusal on the trace channel.** Above: it drives the client.
- **Refusing an approval that arrives twice.** Two clients can both press
  Approve and the second press is not wrong. It gets a `refused` with reason
  `task` rather than silence, because "I did not do that, and here is why" is
  not the same as calling it an error — but the message is worth having, since
  the alternative for the second client is a button that did nothing.

## One thing next to it, same family

The debug UI enables its composer during a replay while a recorded turn is
mid-flight — `replaying` is `status === "replay"` and the status is `"running"`
until the turn ends — so a person can type into a recording and press Send, and
`send()` returns early with no socket. That is the same silence one layer up,
found by the smoke test earlier today and deferred to this item by name. The
store gains `state.replay`, which is what the flag was always asking to be, and
the composer reads that instead of the status.

## Still open

- A `reason` on a rejection at the gate, so refusing a plan can say why. Same
  shape, other direction, and it waits for someone to be annoyed by retyping.
- Whether a refusal belongs in `SessionView`. It is transient client feedback
  rather than session state, so it stays off the read side until something
  wants to count them.

## 2026-08-30, later: built, and the hole it found

The four refusals are in, `protocol::VERSION` is 2, `record::FORMAT` is 4, and
the composer reads `state.replay` instead of the status word. Then the check
that was supposed to be a formality found something.

**Closing a task that was only proposed used to succeed.** Driving the live page
with a second client — the case the disabled composer cannot cover — a
`close_task` for the task waiting at the gate went straight through:
`Context::close_task` looked up the task and closed it whatever state it was in.
The gate disappeared from the screen, the prompt behind it stayed held, and the
session had no way back: nothing to approve, nothing to reject, and a held
prompt that would never run.

Pulling on it found the sharper one beside it. `reopen_task` set any task to
`Approved`, **including a rejected one**. So: propose, reject, reopen — and the
plan a person just turned down is the live task, with the next prompt running
inside it and no gate in front of it. That is the gate leaking through the
message that exists for unfolding a fold. Nothing in the protocol prevented it
and nothing in the UI would show it; the socket is open to anyone who can reach
the port.

Every transition is now guarded in `Context`, which is where the lifecycle
actually lives: only a proposal is approved or rejected, only an open task
closes, only a closed one reopens. The refusals this file added are what those
guards now say out loud, which is how the first one was noticed at all — the
message that should have appeared did not.

Two unit tests pin the state machine and one socket test pins the sequence:
propose, close (refused), approve, and the held prompt still runs.

### What the check looked like

The busy refusal, rendered on the page by a client that did not cause it:

```
prompt refused — turn 1 is running; one at a time until sessions exist
close_task refused — task 1 is not open
```

with the gate still on screen and the composer still disabled after the illegal
close, and nothing in the console.
