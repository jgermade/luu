# A session starts on the default runtime

> *Al hacer make up indica que docker es la opción por defecto, sin embargo ha
> iniciado con host.*

## What it was

`[runtimes] default`
([`2026-10-27.runtimes-are-acted-on-and-one-is-the-default`](2026-10-27.runtimes-are-acted-on-and-one-is-the-default.completed.md))
decided one thing: which container runtime the new session's dialog listed an
image on first. Where the file named none, that was Docker. Docker's card said
*default*, and Docker was Settings → Runtimes' default.

But no session started there:

- `luu serve` (`make up` runs it with no flags) starts its first session on
  its own policy file, `luu.toml`, which runs on this machine.
- The dialog offered this machine first, or what the last session started on.

So a card promised something the server never did.

## What it is

**Absent is this machine.** No card says *default* until one is chosen, and
the section says so: *las sesiones empiezan en esta máquina*. A session in a
container nobody chose is not a default worth having. Most machines that run
luu have no container runtime that answers, and the ones that do may not have
the image built. `Config::default_runtime()` is now an `Option`, and `None` is
this machine. Docker is written out like any other runtime (`default =
"docker"`); `host` is this machine again, written as no table.

**A container runtime marked default is where sessions start.**

- **The first session of `luu serve`** is made the way the dialog makes one
  with nothing else chosen, through the same route (`create_session`):
  - that runtime;
  - the first image a posture or an environment in `config.toml` names for it;
  - the empty lists (*runs nothing without asking*, *reads the folder, asks to
    write*).

  `serve`'s output says where it landed: `runtime — docker · luu-worker:dev,
  the default in config.toml`. Where it cannot run there, the session stays
  on this machine, on the server's own policy file, and the line says why:

  - nothing in the file names an image;
  - the runtime is not there;
  - the worker would not start.

  It runs in `serve` and not in `bind`, because a test calls `bind` and must
  not read the `config.toml` of whoever runs it.
- **The new session's dialog** starts on the default's first place. It goes
  ahead of what the last session started on, which only counts where no
  default is set. `GET /api/postures` carries `default_runtime` for it.
- **Its two checks take it back.** On the default's card, the double check is
  now the button that returns sessions to this machine.

## Rejected

- **Docker as the default where nothing says.** That is the label that was
  wrong. Making the server honour it would start every fresh install's first
  session in a container that is not there.
- **Starting the first session on the default with `luu.toml`'s lists.** A
  policy file is a posture, and it says where it runs: `luu.toml` says this
  machine. The dialog's way of making a session — a runtime and three lists —
  is the one that can be put anywhere, so the first session is made that way.
  The empty lists are what the dialog starts from with nothing remembered.

## Tested

- `provider::tests`: this machine until the file names a runtime; Docker
  written out; this machine again written as no table.
- `settings.spec.js`, Runtimes:
  - no card says *default*, and the section says sessions start here;
  - nerdctl, made the default, wears the double check and the tag;
  - `/api/postures` names it as `default_runtime`, and offers an image on it
    first;
  - `direct` is refused, and Docker is written out;
  - the double check takes it back, and the table is gone.
- By hand, `luu serve` with `default = "nerdctl"`, the stand-in nerdctl and a
  posture on `luu.container.toml`: the session stays on this machine and says
  `starting on nerdctl · luu-worker:dev failed: … the worker exited`. Without
  the posture it says no posture or environment names an image. The case that
  succeeds needs a runtime that runs containers, which this container does not
  have. It is the same route `policies.spec.js` and the dialog take.
