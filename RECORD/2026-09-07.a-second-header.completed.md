# A second header: resuming a session somewhere else

**Status:** a proposal, and the code it plans.

[`the-first-run-has-no-provider`](2026-09-07.the-first-run-has-no-provider.completed.md)
made the destination the *session's* and closed with the hole it left:

> **Nothing offers the destination to a *resumed* session**, which runs on
> whatever the server is pointed at even when its own header names another. True
> before this change and louder after it.

Two things are wrong in that sentence and only one of them is a missing feature.

## The problem

**1. A resumed session already switches destination, and says nothing.** Resume
loads the fold and keeps running on `App`'s destination. Before a session could
choose one that was a single-server accident; now it is routine — start a
session on `local`, start another on `workstation`, resume the first, and it
runs on `workstation` under a stream whose only header says `local`. The stream
is the thing that says what two turns may be compared as, and it is wrong.

**2. There is no way to keep a conversation and change the model.** The only
control is `POST /api/sessions {provider, model}`, which starts a *new* session.
Wanting the same history against a bigger model is an ordinary thing to want —
"this 7B is not getting it, try the 14B" — and today it costs the history.

The second is why the first is worth fixing rather than merely documenting: the
fix for both is the same line in the stream.

## The proposal

**`POST /api/sessions/{id}/resume` takes the same optional `{ provider, model }`
body `POST /api/sessions` does.** One `destination_for`, one refusal path, one
rule about what may be chosen. Resolved *before* anything is loaded, so a body
naming a profile the file does not have leaves the session that is running
exactly as it was.

**And the stream gains a second `Header` line where the destination changed.**
No new variant, no format bump: `RecordLine::Header` is already *the terms these
lines were produced under*, and both readers that fold a stream —
`SessionView::from_record` and the page's replay — already apply a header by
overwriting backend and model and carrying on. What they must not have is a
second `started_at`: every `at_ms` in a stream is relative to the first one, so
the resume header carries **the session's own `started_at`**, not the moment of
the resume. That is not a workaround, it is what the field says it is — *"Unix
milliseconds. Every later line is relative to this."*

**It is written when the destination differs from what the stream already
says**, which is the fold's `backend` and `model`, and not when it does not. So
it lands on a resume that switches — and on a plain resume that inherited a
different destination, which is problem 1 and is closed here without anybody
asking for it.

The context is re-folded with the **new** counter, which `store.resume` already
takes as an argument: a history counted with one tokenizer and budgeted with
another is two numbers pretending to be one. Every turn in the window is
recounted, and the eviction that follows is the new model's.

### In the page

The starter dialog already asks the two questions. It grows a second action:
**Start session** (a new one, as now) and **Continue here** (this session, over
there). Same provider, same model field, same suggestion — the difference is
whether the history comes along. `Continue here` is disabled with a reason when
there is no session to continue or no store to resume from, because a control
that cannot work must say why rather than fail when pressed.

## What it costs

- **The fold stops naming the session's first destination.** `SessionView` has
  one `backend` and one `model`, so after a switch it names the current one and
  the listing row follows. The *stream* keeps both, in order, which is where the
  answer to "what produced turn 4" lives — but a reader who only has the fold
  now has less than they had.
- **Turn numbers span destinations.** Turn 8 on a 14B follows turn 7 on a 7B,
  and the prefix reuse measured across that boundary is meaningless once. Every
  panel that plots per-turn numbers gets a discontinuity it does not draw.
- **A resume is now a write to the stream**, where it used to be a read. Nothing
  else changes: the line goes down the same checkpoint path every other line
  does.

## What was rejected

| | why |
| --- | --- |
| A new `RecordLine::Retarget` variant, and `FORMAT` to 8 | It says exactly what a header says, and every reader of a header already does the right thing with it. A format bump refuses every existing client for a line they would have folded correctly |
| Switching mid-*turn*, or a `set_model` protocol message | Unchanged and still rejected: a turn is built, measured and sent against one destination |
| Recording the switch as a `Trace` line | Trace is what a turn did. This is the terms the next turn will be done under, which is the header's job |
| Resuming with the counter already in place | The history would carry one tokenizer's counts into another's budget, and the first eviction would be measured against numbers nothing produced |
| Making every session switch in the picker ask first | Switching sessions is a navigation gesture. The question belongs on the control that is already about destinations |

## Still open

- **Nothing shows the boundary in the transcript.** The stream has it and no
  panel draws it, so turn 7 and turn 8 look alike in a session where they were
  produced by different models.
- **A resumed session's window may shrink under its own history.** Moving to a
  profile with a smaller `context-limit` evicts on the first turn, which is
  correct and is not announced.
- `Config` still reads the environment rather than taking its path, so this
  route joins the other three in being driven rather than tested over HTTP.

## 2026-09-07 — what building it decided

Code, in the shape argued above: `resume_session` takes the body, `retarget_header`
decides the line, and the starter dialog grows a second action — all in
[`serve.rs`](../crates/luu/src/serve.rs) and [`app.html`](../crates/luu/ui/app.html).
Four things the plan did not know, and one of them was not about this feature at all.

**Approving from the browser has been broken since the rename, and this is how
it was found.** The drive could not get past the gate: the click did nothing,
the server logged nothing, and the job stayed `proposed`. The page sends
`{"type":"approve_job","job":1,"task":1}` — both spellings of one field, because
`ClientMessage::ApproveJob` carries `#[serde(alias = "task")]`. Serde reads that
as **`duplicate field job`**, the frame fails to parse, and an unparseable frame
is dropped on the floor by design, so the socket survives and the approval does
not. Every approval this repository's own UI has sent since `d70e6d9` went
nowhere. The alias is a second *spelling* for a client that has not been
rewritten, never a second field; the page now names the job once, and
`a_gate_frame_names_the_job_once` pins all three cases. **Nothing in the Rust
tests could have caught it** — they send frames of their own, correctly — which
is the argument for driving the page rather than only the routes.

**The line has to be checkpointed where it is written, not where the next turn
would.** A resume that moved a session and then left it alone kept its second
header in `App::stream` and lost it when the process ended: the store still said
`mock` while the live view said `ollama`. `resume_session` now checkpoints after
the swap. Unlike a new session it invents no row — the session already has one —
which is exactly the objection that stopped the same call being added to
`create_session` in the previous record.

**A proposal at the gate blocks both actions, and the dialog had to say so.**
The server refuses a session change while `pending` is set, which is right — a
proposal is a question waiting on a person and starting elsewhere throws it
away. But the page offered two enabled buttons that answered with a 409. Both
are now disabled with the reason on the page.

**The fold's `backend` is overwritten on a move, deliberately.** `SessionView`
has one backend and one model; after a move it names the one the next turn will
use, and the listing row follows. The *stream* keeps both headers in order,
which is where "what produced turn 4" is answered. The alternative — leaving the
fold naming the first destination — makes the page and the row disagree with the
turn that is about to run, which is the failure this whole record is about.

### What the runs show

A server on `127.0.0.1:7904` with a scratch `LUU_HOME` and two profiles —
`fixture` (mock) and `local` (ollama, `context-limit = 8192`) — driven in a real
browser: a session started on `fixture`, a prompt approved at the gate, then
**Continue here** against `local`.

```text
turns before moving:      2
header before:            ["mock", "mock"]
turns after moving:       2          (the history came along)
header after:             ["ollama", "qwen2.5-coder:7b"]
GET /api/settings:        local · ollama · qwen2.5-coder:7b · window 8192
console/page errors:      none
```

and the store, read with `sqlite3` after the move — two headers in one stream,
sharing the session's own `started_at`:

```text
sessions: (session-…607d1, ollama, qwen2.5-coder:7b, local, 2 turns)
headers:  session-…607d1: mock   / mock              · limit None · started_at …958843
          session-…607d1: ollama / qwen2.5-coder:7b  · limit 8192 · started_at …958843
```

`cargo test --workspace` is 386 green, three of them new: the header rule and
its `started_at`, the resume refusing an unknown profile without touching the
session that is running, and the gate frame naming the job once. The Playwright
smoke test over the static site is 4 green, `clippy --workspace --all-targets`
clean under `-D warnings`.

### Still open, after this one

- **Nothing draws the boundary in the transcript**, as the plan said. The stream
  has it; no panel reads it.
- **A move to a smaller window evicts on the first turn**, correctly and
  silently.
- **`--record` files still carry one header**, from file creation. A session
  moved mid-file is now a second way for that file to be wrong, and the fix is
  the same one the previous record deferred.
