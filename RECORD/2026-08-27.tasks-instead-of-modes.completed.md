# Tasks instead of modes

**Status:** plan, and it replaces a decision. The design's *Operating modes*
section — `plan` / `run` / `auto` as a state enum plus a `Mode` trait — goes away
and a session becomes a sequence of tasks. Follows
[`2026-08-27.cline-openhands.completed.md`](2026-08-27.cline-openhands.completed.md), which found the
alternative already shipped in one of them, and
[`2026-08-27.prefix-reuse-and-block-eviction.completed.md`](2026-08-27.prefix-reuse-and-block-eviction.completed.md),
which is what makes the claims below measurable rather than pleasant.

Nothing was built against modes: `Mode` is in the design and not in the code.
This is cheap now and would not have been in a month.

## What is wrong with `plan | run | auto`

Not that it is a bad taxonomy. That it answers a question we do not have and
leaves ours unanswered.

**It is global.** A mode is a property of the session; approval is a property of
a piece of work. "Rename this variable" and "rewrite the eviction policy" want
different gates, and a mode makes you set the gate for the conversation and then
remember you set it.

**The three collapse.** `plan` produces steps and stops; `run` executes steps it
did not produce; `auto` is the two in a loop. In practice there is one loop and a
gate in front of it, and the enum is a way of saying which gate you left open.

**And the fatal one, for this project: a mode cannot tell you what to compact.**
The whole design is organised around what earns its place in the prompt. A mode
tells the agent how much autonomy it has and says nothing about what the
conversation is *for* — so the context manager gets no boundary out of it, and
`AGENTS.md` says compaction is the next strategy after eviction. Modes were the
one structural decision in the design that gave the differentiating piece
nothing.

Cline is the evidence rather than the intuition: it has no modes, and approval is
a state a *task* is in (`createTask` → `approveTask` → `runTask`). The gate moved
onto the work.

## The proposal

A session is a sequence of tasks. One task:

```
the user asks for something
  → the agent proposes a plan: steps, files it will touch, commands it will run
  → CONFIRMATION                  ← nothing runs before this
  → loop: act · check · ask when unsure
  → closing question: "shall I call this done?"
  → close: the task is summarised; its turns stop being sent verbatim
```

The gate is not a mode anyone selects. **Every task is confirmed before anything
runs**, and what is confirmed is a summary the user can read in one screen.

### Why this is a context decision before it is a UX one

Look at what a task produces, and at how often each piece is rewritten:

| Artefact | Written | Rewritten |
| --- | --- | --- |
| the approved plan | once, when the task starts | never |
| the live turns | appended to | never |
| the closing summary | once, at the close | never |

Everything is write-once. The only rewrite in an entire session is the instant a
task closes, when its turns are replaced by its summary — **one deep cut, rarely,
at a point the content chose.** That is precisely the shape yesterday's numbers
say a prefix cache pays for, and it is the same shape OpenHands and Cline reach
with a threshold. The difference is where the cut lands:

```
[system]                                  ← the stable prefix
[user] summary of task 1 (closed)         ← written once, never edited again
[user] plan of task 2 (approved) + the oldest retained turn
[assistant] …
[user] …                                  ← live turns, appended to
[user] selected code + the new prompt     ← fused, as late as possible
```

The context-manager record left compaction as "a rolling summary of older turns"
and never answered *when*. Threshold compaction answers "when the counter says",
which is the same objection this design already makes to rendering the prompt and
trimming the string: the cut lands wherever the limit falls. A task boundary is a
cut point the work chose.

**With one honest limit: a single task can overflow the window on its own.** So
the boundary is the *preferred* cut point and the threshold stays as the
fallback — and, being a strategy, it has to beat the recorded baseline like
every other. Neither Cline nor OpenHands cuts on task boundaries; that is either
the opportunity or the warning, and the instrument decides which.

## Who declares a task done

Three rungs, and they are not competing answers — they are a ladder:

1. **Deterministic checks.** Exit codes, tests, does it build. Free, reliable,
   always first.
2. **A judge on evidence.** Same model, fresh short context.
3. **The final question.** The user closes the task.

So: **the judge decides whether the loop continues without bothering the user;
the user decides whether it is done.** A judge that is wrong costs one extra
iteration, not a task closed in error.

### Why the same model can judge, and under what condition

The condition is the whole thing: **the judge's context is evidence, not
narrative.**

```
OBJECTIVE:  (verbatim, as the user typed it)
DIFF:       3 files, +47 −12
COMMANDS:   cargo test --workspace → exit 0
            cargo clippy → exit 101, "unused variable: `keep`"
TOUCHED:    crates/agent-core/src/context.rs, crates/luu/src/lib.rs
```

None of that was written by the model. Feed it the model's own account of what it
did and the judge inherits the hallucination — same error twice, at twice the
price. Feed it evidence and the question changes from "do you think you
finished?" (generation, where it fails) to "does this evidence satisfy this
objective?" (verification, which is easier). The reason a same-model judge can
work is not that its context is short. It is that the context **is not its own**.

Cheap addition: do not tell it the work is its own. Self-preference is a known
bias and an anonymous artefact costs one template.

### The cost of judging is a cache cost, not a token cost

This is the part yesterday's work makes visible, and it decides *when* to judge,
which matters more than *who* judges:

| When | What it costs |
| --- | --- |
| every iteration, short context | the judge is cheap to evaluate and **throws away the agent's cached prefix**: the next turn re-evaluates it in full. The worst case |
| every iteration, the same context | prefix cached, nearly free — and it is exactly what a loop already does when the model decides to stop on its own. It is what fails |
| **at the task's close**, short context | the cache miss was already paid there: that is where you were going to compact anyway |

A different, much shorter prompt is a different prefix. The task boundary is the
one place in a session where throwing the cache away is already the plan, which
makes it the only place a judge is close to free.

### Shadow mode, because the labels arrive for nothing

**The final question generates the judge's evaluation set.** Every task the user
closes — or refuses to close — is a label, produced by using the tool.

So the judge ships **running and deciding nothing**: it is called at the close,
its verdict is recorded next to what the user answered, and it gates nothing
until there are numbers. When thirty tasks have closed there is a real accuracy
figure, for this model on this person's work, and the decision to let it gate the
loop is made against it. That is the house rule — strategies are measured, not
argued — applied to the one part of this plan that is a guess.

OpenHands' `/goal` uses a second LLM as the judge and re-prompts until done or a
cap. Right for a frontier model behind an API; wrong economics for a 7B on a
laptop, where the second model is the same model and there is no free label
source in the loop. We take their shape and change their arithmetic.

## What the confirmation buys, beyond not breaking things

Three things fall out of one boundary, which is the argument for the whole plan:

- **Compaction gets its cut point.** Above.
- **Permission gets its scope.** The approved plan named the files and the
  commands; that *is* the `SandboxPolicy` for the task. One informed approval
  beats a prompt per tool call, which is the pattern that trains people to click
  yes without reading.
- **Relevance gets a signal for free.** Aider computes a personalization vector
  with PageRank to guess which files the conversation is about. The approved plan
  is one, and the user wrote it. (Blocked behind tools either way — see the
  correction appended to the Aider record.)
- **The transcript gets its grouping.** A closed task collapses to its summary in
  the UI. The view collapses exactly what the context collapses, which means one
  concept to explain instead of two.

## What it costs

- **A wrong summary is unrecoverable inside the session**, because it lands in
  the write-once region every later turn is built on. So closing a task is an
  **event, not a mutation** — reopening it is folding differently, not undoing a
  deletion. That is the decision already taken in the Cline/OpenHands record, and
  this is the case that makes it non-negotiable rather than tidy.
- **A 7B writing the summary.** Until measured, the closing summary is
  deterministic first — the same evidence block the judge sees, plus the approved
  plan — with model prose as an optional addition, never as the load-bearing
  part. Cline's recovery path refuses to depend on an LLM call for the same
  reason: the fallback must not need the thing that failed.
- **Granularity is a real parameter and it is the user's.** Confirmation per task
  is fine; per tool call is noise. If the model proposes twelve-step plans the
  gate degrades into a habit, so plan size is something to watch from the first
  session.
- **Protocol growth.** Task lifecycle on the wire (`task_proposed`,
  `task_approved`, `task_closed`, `task_reopened`), and the read API grows a task
  view. v1 of the protocol enums is still unfrozen in the design; this is the
  moment to do it, and it is the last cheap one.
- **Stored counts go stale at a close.** `Turn.tokens` carries `counted_by`, which
  catches a changed counter and not a rewritten history.

## What was rejected

- **Keeping modes alongside tasks.** Two mechanisms for "do not execute yet", and
  a matrix of which wins. The gate belongs to the work.
- **The judge as the authority.** It removes the only free source of labels and
  buys a decision nobody asked it to make.
- **Compacting *only* on task boundaries.** One task can overflow alone; the
  threshold has to survive as the fallback.
- **Auto-approve as a setting, for now.** Cline has an automation policy and a
  track record to justify it. We have neither, and the shadow-mode numbers are
  the precondition for even discussing it.

## Still open

| Question | Precondition |
| --- | --- |
| Does closing on a boundary beat closing on a threshold, in reuse and in tokens? | tools, so a task is long enough to be worth closing |
| Is the deterministic summary enough, or does it need model prose? | a real model, and tasks with something to summarise |
| Judge accuracy against the user's own verdict | thirty closed tasks in shadow mode |
| Sub-tasks and nesting — both prior-art agents have them (`parentAgentId`, `subagent`) | deliberately not now: one level until one level demonstrably hurts |
| What a reopened task does to a prompt already built on its summary | the fold, when closing becomes an event |
