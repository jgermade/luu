# Narrowing: network per plan

**Status:** a proposal and the code it plans. It is item 6 of
[`ROADMAP/2026-09-01`](../ROADMAP/2026-09-01/README.md), unblocked by the container
and the gate probe landing.

[`RECORD/2026-08-30.narrowing.completed.md`](2026-08-30.narrowing.completed.md) established
that an approved plan *is* the sandbox for its task: `files` grants read, `writes`
grants read-write, and `commands` limits executed binaries. But it left `network`
ambient:

```rust
let mut policy = SandboxPolicy {
    paths: Vec::new(),
    commands: Vec::new(),
    network: session.network(),
    enforcement: session.enforcement(),
    limits: session.limits(),
};
```

If the session policy allows network (as `luu.container.toml` does in development
posture to allow cargo downloads), **every command in every task runs with network
access**, even when inspecting a local file or running an offline unit test.

## The problem

The container boundary does not distinguish between a build script that compiles
C code and a build script that curls an external payload. If network is ambiently
available across the session, any `run_command` can reach the internet unless the
outer session explicitly disables network for all tasks.

Conversely, disabling network at the session level breaks tasks that genuinely need
it (`cargo add`, `git fetch`). The choice should belong to the task's plan, subject
to the session policy as an upper bound.

## The proposal

1. **`Plan.network: bool` (default `false`)**:
   A plan must explicitly declare if it wants network access. A plan that names
   nothing regarding network gets none.

2. **Narrowing down**:
   In `Plan::narrow`:
   ```rust
   policy.network = session.network() && self.network;
   ```
   A task can only hold network if both the session policy and the approved plan
   grant it.

3. **Checked at the gate (`Plan::unmet`)**:
   If `self.network && !sandbox.network()`, the gate reports it before running:
   `"network: denied by {authority}"`. A plan cannot ask for what the policy file
   forbids.

4. **Amendment at the gate**:
   `Plan::amend` accepts `network: Option<bool>`. When the person approves a task
   at the gate, they can enable (or disable) network access via
   `ClientMessage::ApproveTask { network, .. }`.

5. **Script directive**:
   Task scripts in `scripts/tasks/` support `## network` or `## network: true`.

6. **Enforcement inside the container**:
   `WireSandbox::of` already derives its `policy` from `sandbox.to_policy()`.
   When `sandbox.network()` is false, `WireSandbox.policy.network` is false.
   The worker resolves this policy and calls `prepare_command`, which installs
   the seccomp filter blocking `AF_INET`, `AF_INET6`, and `AF_PACKET` on Linux.

## What it costs

- Existing recordings and scripts without `network` continue to parse with
  `network: false`.
- Any command expecting network inside a task will fail with `EPERM` unless the
  plan explicitly declared `network: true`. This is the intended behavior.

## What was rejected

- **`docker network connect`/`disconnect`:** Manipulating the container's virtual
  network interface at runtime is racy and coarse. A seccomp filter per-child
  is instant, immutable once installed, and isolated to each command.
- **Network by destination in seccomp:** The Linux kernel cannot filter by hostname
  or destination IP easily in seccomp without userspace interception. Full
  fine-grained domain filtering ("only crates.io") belongs to the userspace egress
  proxy layer.

## Still open

- **Egress proxy:** An HTTP CONNECT proxy running on the host allowing domain-based
  filtering (e.g. allowlisting `crates.io`, `github.com`) when `network: true` is
  active.
