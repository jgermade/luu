# Removing a user, and a week to come back

> sobre los usuarios, al borrar el usuario se borran los datos, pasada una
> semana si no vuelve a iniciar sesión

## The problem

[`users-and-a-code-by-email`](2026-11-03.users-and-a-code-by-email.WIP.md)
left open *what removing a user does with their sessions and their folder*,
and until it was answered `luu user remove` and Settings → Users refused
anyone with a session. Every user who has ever logged in has one: the login
makes it ([`ensure_current`]). So in practice only somebody who never logged
in could be removed, and everybody else could only be suspended, which keeps
everything for ever.

## The proposal

**Removing a user schedules the removal of their data a week out, and
logging in again within that week cancels it.**

- **At once:** every login of theirs ends, and any code waiting for them.
  `users.removed_at` is set. Nothing else is touched yet.
- **Within the week:** they may ask for a code and log in, as before, and
  that login clears `removed_at`: they are a user again with everything they
  had. An admin or an owner may also *Restore* them from Settings → Users,
  and `luu user restore` does the same on the machine.
- **After the week:** `serve` deletes, in this order, their live sessions
  (ended without a checkpoint), their stored sessions and streams, their
  folder `<root>/<user id>`, their SSH keys and passkeys, and the row. Once
  an hour, and once when it starts, so a server that was down for the
  deadline does it when it comes back.

**To keep someone out, suspend them and remove them.** A suspended user
cannot log in, so the week runs out. Removing alone is what the request
asked for: a person who comes back within the week keeps their work.

A removed owner does not count as an owner: `has_owner` and the last-owner
guard ignore them, so the last owner who would be left cannot be removed.

`luu user list` and Settings → Users show *removed* and the date the data
goes. Removing yourself stays refused from the page, as in
[`roles-in-the-page`](2026-11-05.roles-in-the-page.completed.md).

## What it costs

- **`auth.db` schema 4**: `users.removed_at`. Migrated in place, no row
  touched.
- **A task in `serve`** that deletes files under its root. It deletes only
  `<root>/<user id>` for a user whose row says removed and whose week has
  passed, and the id is twelve hex characters the server generated, so the
  path cannot be anything else.
- **The data is gone after the week**, by design. There is no archive.

## Rejected

- **Deleting at once.** That is what the request ruled out.
- **Keeping the data where only the machine reaches it**, the other option
  the users record named. It is a folder nobody owns, kept for ever.
- **A removed user who cannot log in.** That is a suspended one: removing
  would then be suspending with a timer, and the request says a login within
  the week keeps them.

## Still open

- **Whether the week should be a setting.** Seven days, a constant, until
  somebody asks.
- **Telling the user.** A server with mail could send one line saying the
  account goes on a date unless they log in. Not built: nobody asked, and a
  removal an admin made quietly may be meant to stay quiet.

## Built, the same day

As proposed, with one thing the proposal did not say: **a removed user's SSH
keys let nothing in during the week.** `key_user` refuses a removed user as it
refuses a suspended one, so a link from their luu closes with their logins;
the keys stay on the account and come back with a login or a *Restore*, and go
with the purge. A test that said *a user removed takes their key* now says it
keeps it, refused, and loses it when purged.

`luu user list` shows `removed` and when the data goes; `luu user remove`
says how many sessions go with it; `luu user restore` is new.

**Verified:**
- `users`: removed, their login ends, nothing is due before the week, the
  last owner cannot be removed, a login within the week clears it and a
  purge then refuses; backdated eight days, they are due and purged.
- `tests/server_config.rs`, against the binary: an admin removes a user who
  has a folder (`200`, the folder still there) and restores another; and a
  server started after a removed user's week has passed deletes their
  folder and row on its own, while another removed user logs in and is
  kept, folder and all.

**Not verified:** the stored sessions deleted with them. The tests run
`serve --no-store`; the code that deletes them is the store's own `delete`,
filtered by owner.
