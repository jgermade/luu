# Three things the audit left, and none of them need the container

**Status:** plan, then code. Three changes proposed by
[`ROADMAP/2026-09-01/luu_architectural_audit_containerized.md`](../ROADMAP/2026-09-01/luu_architectural_audit_containerized.md)
that survive being checked against the tree. They are grouped in one record
because they share the property that decides their order: **none of them waits
on level 3**, and two of them are enforcement the project already claims in
prose and does not have in code.

## Where they came from, and what the audit is worth

The audit names its sources in its last section: the repository, `loude-design.md`,
`sandbox/mod.rs` and `serve.rs`. It did not read `RECORD/`, `task.rs`, `tools/`
or `linux.rs`, and its shape follows from that — most of it restates decisions
that [`2026-09-01.the-container-decided.WIP.md`](2026-09-01.the-container-decided.WIP.md)
had already taken, on the same day, with the arguments it does not have:

| audit | already |
| --- | --- |
| §18 `writes` should constrain `run_command` — "yes" | done, `Plan::narrow` (`task.rs:123`) grants `Read` for `files` and `ReadWrite` for `writes`, and the narrowed policy is what the child carries |
| §20 one container per session, with a reset op | decided, plus the reason it does not have: memory at 16 GB, and the boundary multi-session will need |
| §35 the image holds the allowed programs | decided, plus "`commands` is the image's manifest" and the *third* failure mode a verdict has to name |
| §37 emit an OCI image, invoke the named runtime | decided, plus containerd rejected (a daemon) and `apple/container` measured (no `--network none`) |
| §8 `/etc` is not a finding | answered in the code it read: `SYSTEM_ROOTS` is subprocess-only and `check_path` ignores it (`sandbox/mod.rs:37`) |

And it has one blind spot, which is the fact that moved the roadmap: **it never
mentions macOS**. Its whole frame is the container as a redundant layer over
Landlock. On the machine this is being built on, level 2 does not exist and the
container is the only boundary there is. An audit that cannot see that cannot
rank anything, which is the second reason to take its findings and not its order.

## 1. `serve` binds where it is told and asks nobody

The hole, precisely. `crates/luu/src/lib.rs:100`:

```rust
#[arg(long, default_value = "127.0.0.1:7878")]
bind: std::net::SocketAddr,
```

Any `SocketAddr` parses. `bind()` in `serve.rs` hands it to
`TcpListener::bind` and builds a router with no middleware, no token and no
check on what it just bound. So `--bind 0.0.0.0:7878` publishes `/ws` to the
LAN, and `/ws` carries `ApproveTask`, `RejectTask`, `CloseTask` and
`ReopenTask` — approval is the authority this whole design is built around, and
it is one `curl` away from anyone on the network.

The design already promised otherwise, at `loude-design.md:429`:

> loopback by default, no auth; require a bearer token when bound to any other
> address

That line is prose. Nothing implements it. It also calls the flag `--http`
where the code calls it `--bind`, so it is drifted as well as unimplemented —
the design doc is rewritten when the change below lands, which is the rule for
any decision that moves.

**The proposal.** In `bind()`, before the listener exists:

```text
address.ip().is_loopback()      → serve, no auth
otherwise, token configured     → serve, every request checked
otherwise                       → Err, naming the flag that would fix it
```

`Serving` is the type that exists once a port is held, so putting the check
*before* `TcpListener::bind` means the unauthenticated non-loopback server is
not a state the program can be in — not a warning printed above one.

**Refuse, not warn**, and the project has already argued this once: `luu.toml`
ships strict on purpose, and "it fails on first run so that a person makes an
informed choice" is the same sentence. A warning above a served port is a
default nobody chose.

**Read and control are not the same surface.** The audit's §27, folded in here
because it is the same edit. `/api/*` is a read side that `luu export` already
mirrors to a static host; `/ws` is authority. The token gates the control
surface. Whether a bearer token should also be required for the read side is
below, in *Still open* — the answer is probably yes, and it is a different
argument (source code and prompts are not public either).

**Cost.** One flag or env var, and the failure path. Tests bind `:0` on loopback
(`crates/luu/tests/serve_ws.rs`), so none of them changes.

## 2. A child has a clock and nothing else

`run_command` holds a subprocess to two things: 30 s of wall clock
(`tools/command.rs:25`) and 8 KiB of output kept (`tools/mod.rs:30`). That is
the whole of it. A `cargo` that forks, allocates or writes without limit is
bounded only by the machine — a fork bomb, a memory bomb and a disk bomb all
run to completion inside the timeout, and the 8 KiB cap trims what is *reported*
about them, not what they did.

**The proposal:** `setrlimit` in the child, in the `pre_exec` that already runs
there.

The finding that decides where it goes: **`setrlimit` is POSIX, not Linux.** So
it does not belong in `kernel::Prepared` — the type behind the
`linux.rs`/`fallback.rs` split — but one level up, in `Restrictions::install`
(`sandbox/mod.rs:432`), which is already the platform-independent seam. It
allocates nothing and is one syscall, which is what that closure allows.

And the consequence that makes it more than hygiene. Today on macOS the verdict
for an allowed command under `best-effort` is:

```text
Applied::Partial { how: "in-process check only",
                   missing: "landlock and seccomp are Linux-only, and this is macos" }
```

With limits installed it becomes `how: "rlimits"` with the same `missing` — the
first thing that has ever actually held a child on the machine every run in this
repository has been made on. The module's own rule is that nothing may say
"sandboxed" without saying by what; this is the first time the macOS answer is
not "nothing".

Which limits, and the one that is dangerous: `RLIMIT_NPROC` (fork), `RLIMIT_FSIZE`
(disk), `RLIMIT_CPU` as a second belt to the wall clock for a child that outlives
its parent, and an address-space or data limit for memory. **The memory one is
where this can break `cargo`**: a Rust toolchain reserves address space far above
what it commits, so `RLIMIT_AS` set to "what a build needs" kills builds that
were fine. That is the reason the numbers are a policy field with defaults, not
constants, and the reason the first run of this is measured against a real
`cargo build` and not against a test.

**Rejected: cgroups.** It is the better mechanism and it is Linux-only, needs a
delegated cgroup, and lands with the container anyway. rlimits are what both
platforms have today, which is the whole point of doing this before level 3.

## 3. `run_command` answers in a paragraph

`tools/command.rs:139` builds the result by concatenation:

```rust
text.push_str(&format!("--- {stream}\n{}", String::from_utf8_lossy(bytes)));
```

`ToolOutcome` then carries `output: String`, `error: Option<String>`,
`truncated`. The exit code exists for one moment, as `{program} exited with
{code}` inside the error string, and is gone. Duration is never captured.

**The nuance the audit missed, and it changes the shape.** `ToolOutcome::render`
is plain text *on purpose* — "a 7B pays for every token of a wrapper it did not
need, and this one is read, never parsed". So the proposal is not "return JSON to
the model". It is: **structure the type and the record; leave the rendering
frugal.** `exit_code`, `stdout`, `stderr` and `duration_ms` as fields; `render`
keeps producing the same short text it produces now.

What that buys, and it is not tidiness. `protocol.rs` says of `CloseTask`:

> The user is the only authority that closes a task today; the ladder above them
> (exit codes, then a judge in shadow mode) is still ahead.

**A task cannot be closed on an exit code that was never a field.** The next rung
of that ladder is blocked on this change, and no other. After it: stdout and
stderr stop being interleaved into one blob a judge has to re-parse, and a
recording carries the number instead of a sentence about the number.

**Cost.** A struct change in `agent-core`, and the record format is versioned —
AGENTS.md pins the protocol/record versions together, so this either fits the
additive rule or bumps the record format, and the record says which before the
code does.

## Order, and why this one

1. **Auth.** It is live, today, on any machine where someone typed a different
   `--bind`. It is the only one of the three where the gap is between what the
   design *says* and what runs.
2. **rlimits.** Holds a child on both platforms now, and is the only kernel
   enforcement macOS can have before the container exists.
3. **Structured results.** Unblocks the exit-code rung of the closing ladder,
   which nothing else does.

None blocks `loude-worker`, and all three are cheaper before it: the worker
inherits the limits, the structured outcome crosses the IPC as a type rather
than a string, and the token is what the IPC's own trust boundary will argue
against.

## What this record rejects from the audit

- **§4, `ExecutionBackend` as the first move.** It calls this its highest-value
  change. The seam it proposes is already decided — all tools inside, context
  manager and model client outside — and the trait is the easy half. The half
  that is open, and that the audit does not see, is the IPC that carries
  approvals across it: a trust boundary inside one machine. Naming a trait
  before that question is answered is naming the part that does not decide.
- **§15, a network namespace instead of per-spawn seccomp.** Argued and settled
  in the container record: the filter is built at every spawn, so its scope is
  exactly the task that declared it, at zero startup cost and with no race
  between tasks. The audit's own §16 then asks for a host-side egress allowlist,
  which that record proposes in more detail — including the reason the kernel
  cannot do it (seccomp cannot dereference the `sockaddr *`). One point of §15
  does survive and is taken: `network = false` should eventually be true at the
  namespace level too, for anything in the worker that does not come through
  `prepare_command`.

## Still open

- Whether the read side (`/api/*`) needs the token as well as `/ws`. Prompts,
  context and source code are not public either, and `luu export` exists
  precisely so a static mirror can be published deliberately.
- Where the token comes from: a flag is greppable in `ps`, an env var leaks into
  children, a file needs a mode check. Probably a file, and this is the same
  question §24 of the audit raises about secrets in general.
- Whether the rlimit numbers are per-policy, per-task or per-command. A task
  declares `files`, `writes` and `commands`; resources are the fourth thing a
  plan could declare and does not.
- Whether structuring `ToolOutcome` is additive under the record format's
  versioning rule, or a bump.
