# One more backend, and the lesson from the first one does not transfer

**Status:** plan, then code. Roadmap item 1 of
[`ROADMAP/2026-09-01/`](../ROADMAP/2026-09-01/README.md), unblocked by nothing and
blocking the measurement that every other row's numbers depend on.

## Why this one first

The roadmap's own correction is the argument: an OpenAI-compatible backend was
listed as unblocking "the CLI and remote web at once — three targets", and with
the hardware in [`machines.md`](../ROADMAP/2026-09-01/machines.md) in play it is
**five of six machines plus two hosted endpoints**, because their serving path is
`llama-server`, Vulkan or a hosted API rather than Ollama. Same item, much larger
payoff.

There is a second reason, and it is about what this repository can currently
*prove*. The two most valuable open questions — the gate probe and relevance
selection's score — both need a model on a machine with a person at it. This one
needs neither: `crates/agent-core/tests/ollama_wire.rs` already binds a stub HTTP
server on an ephemeral port and asserts the bytes `Ollama::stream` puts on the
socket, and an `openai_wire.rs` beside it proves the new backend the same way,
in a plain `cargo test --workspace`.

## The finding that shapes the whole change

**Ollama's lesson does not transfer, and assuming it does would be the bug.**

AGENTS.md states it as a rule, in bold, because it shipped broken once:

> **The window has to be sent, and it is.** `--context-limit` becomes
> `options.num_ctx` on the request. Ollama's own default is a couple of thousand
> tokens and it truncates the prompt to it *silently*.

The OpenAI chat-completions API **has no field for the context window.**
`max_tokens` is a cap on the *output*, not the window, and the two are different
numbers with different consequences. On `llama-server`, vLLM and LM Studio the
window is a property the server was *started* with (`llama-server -c 8192`), not
a property of a request.

So there is nothing to send, and pretending otherwise has two failure modes worth
naming:

- Sending `max_tokens: context_limit` would be the *wrong number in the wrong
  field*: it would cap the answer at the size of the whole window, which is
  neither what `--context-limit` means nor what `--reserve` means.
- Sending nothing and saying nothing leaves a run whose header claims
  `context_limit: 8192` against a server that was started with 4096 — the exact
  situation the Ollama rule exists to prevent, arriving through a different door.

**So the check moves from the request to the response.** `usage.prompt_tokens`
already comes back on every call and this project already compares it against its
own count, per turn, and calls the difference a reading rather than an error. A
server serving a smaller window than we budgeted shows up there. What the backend
owes the user is a sentence saying which of the two situations they are in, once,
at startup — not silence.

## Which makes usage the second decision

`stream_options: {"include_usage": true}` must be on the request. Without it an
OpenAI-compatible server streams **no usage at all** — the field is simply absent
from every chunk — and the backend would report `Usage { prompt_tokens: 0 }`.

A zero there is not a small inaccuracy. It is the number the budget panel plots
against our own count, it is what `RECORD/2026-08-27.the-m4-pro-run.completed.md`
used to find a 1 962-token gap, and reported as zero it would read as "the server
saw an empty prompt". The project already has the rule this falls under — *every
token count carries which counter produced it*, and *nothing may say "sandboxed"
without saying by what* — so:

**`Chunk::Done` carries `usage: Option<Usage>`.** `None` means *not reported*,
which is a different fact from zero, and the whole path above it can already say
so: `TurnEvent::Ended`, `ServerMessage::Ended` and `TurnView` all hold
`Option<Usage>` today, and `store.js` guards with `if (state.budget &&
message.usage)`. The ripple is three call sites and no recorded number changes —
Ollama always reports counts, and the mock keeps reporting its own.

## The rest of the shape

- **SSE, not NDJSON.** `data: ` prefixed lines, blank lines between events, a
  literal `data: [DONE]` terminator, and `:` comment lines some servers send as
  heartbeats. The chunk-boundary handling is the same problem `ollama.rs` solved
  and the same answer: buffer, split on newlines, parse whole lines only.
- **Deltas** at `choices[0].delta.content`, absent on the first and last events.
- **Stop** from `choices[0].finish_reason`: `stop` → `Stop`, `length` →
  `Length`, anything else reported as `Other` rather than guessed at.
- **Errors twice.** A non-2xx with a body, and an `{"error": …}` object arriving
  mid-stream, which `llama-server` does. Both are `BackendError::Rejected`.
- **The API key is a file** — `--api-key-file`, and no header at all when there
  is none, because a local `llama-server` wants no `Authorization` and an empty
  bearer is worse than nothing. Same argument as this morning's
  [`what-the-audit-left`](2026-09-01.what-the-audit-left.completed.md): a flag is
  greppable in `ps`, and an env var is inherited by every child `run_command`
  spawns — which is the one place this repository deliberately runs code it did
  not write. Rejecting `OPENAI_API_KEY` is the part people will find surprising,
  and it is the same trade, made the same way twice.
- **The name carries the host.** `Backend::name()` becomes
  `openai@127.0.0.1:8080` rather than `openai`. The record header's whole job is
  that two runs are comparable, and "openai" cannot tell a run against a 7B on
  `llama-server` from a run against a hosted frontier model. The name is a
  string in a header, not an identifier anything matches on — `model_for`
  matches `"mock"` and nothing else.

## What is rejected

- **The `async-openai` crate.** It models the whole API surface — assistants,
  files, images, embeddings — when this needs one endpoint and one stream, and it
  *owns the request type*. The stable prefix is a wire format here: system text
  and tool definitions have to serialize byte-identically across calls or the
  prompt cache is worth nothing. Handing that to a dependency's derive order is
  the one thing this backend must not do.
- **Pointing the Ollama backend at Ollama's own `/v1`.** Ollama serves an
  OpenAI-compatible endpoint too, so this would "work" and would prove nothing:
  the point is `llama-server`, vLLM, LM Studio and the hosted endpoints, none of
  which are Ollama.
- **Asking `llama-server` for its window.** `GET /props` reports `n_ctx`, which
  would answer the question above exactly — and it is `llama-server`'s own
  endpoint, so a backend that depends on it is not an OpenAI-compatible backend,
  it is a `llama-server` backend wearing the name. If a per-server probe is worth
  having it should be a named thing that says which server it is talking to.

## Cost

One file (`backend/openai.rs`), `Chunk::Done`'s usage becoming optional across
three call sites, two flags on `chat` and `serve`, and `openai_wire.rs`. Nothing
in `agent-core` above the backend trait changes shape, which is the trait doing
its job.

## Still open

- `max_tokens` is not sent, so the answer is bounded by whatever the server
  defaults to. `--reserve` is the number that belongs there and
  `CompletionRequest` does not carry it — adding it would touch Ollama's
  `num_predict` too, and it should be one change with one argument rather than a
  field smuggled in beside this one.
- Tool calling is text-parsed here, as it is for Ollama. Native `tools` /
  `tool_calls` on this API is the obvious next thing and is a different question:
  the fenced block is currently *the* transport, and swapping it is a change to
  what the prefix contains.
- Whether the window mismatch should be an error rather than a sentence. It
  cannot be detected before the first response, and a run that dies on turn 1
  because the server was started smaller is a worse outcome than a run that
  reports the gap it measured.
