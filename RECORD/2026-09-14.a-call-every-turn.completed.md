# A call every turn: `--mock-cycle`

**Status:** a proposal, and the code it plans, both here — the change was small
enough to argue and build the same day. Roadmap item 3b of
[`ROADMAP/2026-09-09`](../ROADMAP/2026-09-09/README.md) names it as "the
missing instrument" for two rows at once —
[`what-a-result-costs`](2026-09-09.what-a-result-costs.completed.md#still-open)
(item 3b, measuring `--prune-results`) and
[`a-grammar-for-tool-calls`](2026-09-06.a-grammar-for-tool-calls.completed.md#the-instrument)
(item 4, the tool-call probe's harness) — and says whoever picks up either row
should build it once rather than work around it twice. This builds it; running
either row against it is not this record's claim.

## The problem

`Mock::replies` is a queue consumed once per model *call*, and once it runs
out the last reply repeats forever. That is exactly right for the ordinary
case — the tool loop end to end, a scripted call then the reply that reads its
result, then plain answers for the rest of the session — and exactly wrong for
a corpus that wants a tool called on *every* turn: after the first call/answer
pair, replies are exhausted and the mock repeats the answer, never the call.
`grounded.txt`, run on the mock, therefore has no tool output in it at all —
found writing `what-a-result-costs`, and true of every scripted corpus in the
tree, because none of them was built to need it before now.

## The proposal

**One boolean, on `Mock`, off by default.** `Mock::cycle(bool)`, threaded to
`--mock-cycle` on `chat`, `serve` and `stdio` beside `--mock-reply`. When set,
the reply queue wraps back to its first element instead of sticking on its
last — so `call, answer` becomes `call, answer, call, answer, …` for as long
as the script runs, and a script with N turns gets a tool call in every one of
them from two `--mock-reply` flags, not `2N`.

Off by default because every existing script depends on the current meaning:
`gate.spec.js`'s `PLAN, CALL, ANSWER` sequence, `store_parity.rs`'s replies,
the coverage and precision probes — none of them wants the tool called twice,
and none of them should have to know this flag exists to keep meaning what
they meant yesterday. A single reply cycled is the same as a single reply
repeated, which is why the "off" and "cycling" paths agree exactly whenever
only one reply was given — there is no discontinuity a caller could trip on by
adding a second reply and forgetting the flag.

## What it costs

- **One field, one match arm.** `Mock::stream` already branched on queue
  length; cycling is a second branch that pops the front and pushes it back
  rather than leaving it, with the empty-queue case (nothing was ever given)
  answering `""` exactly as an empty non-cycling queue does today.
- **Three call sites repeat a flag.** `chat`, `serve` and `stdio` each declare
  their own `--mock-reply`, so each declares its own `--mock-cycle` beside it —
  the existing shape, not a new one; `ModelArgs`/`destination()` is still the
  one place that turns the flags into a backend.

## What was rejected

- **Making the queue cycle by default.** It would silently change what every
  existing `--mock-reply` script means the moment a second reply is added —
  the failure this record's whole design leans away from.
- **A separate flag or constructor for "call every turn" specifically**, e.g.
  `--mock-tool-loop`. Cycling is the general mechanism; a `call, answer` pair
  is one instance of it and a scorer that wants `right, wrong, right, wrong, …`
  for the probe of item 4 is another. Naming the general case once is cheaper
  than naming every corpus that will use it.

## Driven, not just tested

```sh
luu chat --script <(printf 'q1\nq2\nq3\nq4\n') --mock-delay-ms 0 \
  --mock-reply 'looking
```tool
{"name":"read_file","arguments":{"path":"AGENTS.md","max_lines":3}}
```' --mock-reply 'That is what it says.' --mock-cycle --sandbox luu.toml

Four turns, four calls to `read_file`, one per turn — and the same command
without `--mock-cycle` calls it once, in turn one, exactly as before. Three new
tests in `crates/agent-core/src/backend/mock.rs` pin the same three claims at
the unit level: off repeats the last reply, cycling wraps to the first, and a
single reply behaves identically either way. `cargo test --workspace` is
green, clippy under `-D warnings` is clean, `cargo fmt --all --check` is clean.

## Still open

- **Item 3b itself** — running `--prune-results` one flag apart against a
  corpus this instrument can now build. Not done here.
- **Item 4's harness** — the four-way scorer (*parsed* / *drifted* / *no call*
  / *continued past the fence*) that reads what a cycling mock or a real model
  answered. This record builds what it stands on, not the harness itself.
- **`luu serve`'s own mock construction** (`crates/luu/src/serve.rs:3016`,
  used by the debug UI and `gate.spec.js`) was left off this flag — nothing
  there currently wants a call every turn, and adding it unused would be
  exactly the untested code this project keeps warning itself against. Wire it
  up when something does.
