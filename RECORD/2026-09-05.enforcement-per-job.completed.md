# Enforcement per job, and which direction is narrower

**Status:** a proposal and the code it plans, written on 2026-09-05. Item 8 of
[`ROADMAP/2026-09-05`](../ROADMAP/2026-09-05/README.md), and the last line of
`luu-design.md`'s open question about narrowing:

> Narrowing `enforcement` with the rest of the plan. `network` and `egress` are
> now per-job and filtered by host-side proxy; **enforcement remains
> session-wide.**

## The problem

`Plan::narrow` builds the sandbox an approved job runs under, out of what the
session already grants. Paths narrow, commands narrow, `network` and `egress`
narrow. One field is copied across untouched:

```rust
enforcement: session.enforcement(),
```

and the doc comment says so in as many words — *"`network` and `enforcement` are
still the session's: a plan declares neither."* `network` stopped being true in
[`network-per-plan`](2026-09-04.network-per-plan.completed.md). This is the other
half.

## The thing that makes this different from every other narrowing

Every other field in a plan is a **permission**, and narrowing one means asking
for less: fewer files, fewer commands, no network. `enforcement` is not a
permission. It is **what happens when the kernel cannot hold a child**:

| | |
| --- | --- |
| `kernel` | the child does not run, and the denial says what was missing |
| `best-effort` | the child runs, and every verdict carries the gap |

So *narrower* here does not mean "less of something". It means **refusing more**,
and the value that refuses more is `kernel`. Which gives the rule, and it is the
whole design:

> A job may ask for `kernel` where the session says `best-effort`. A job may
> **not** ask for `best-effort` where the session says `kernel`.

The first is a job saying *I would rather not run at all than run unheld* — it
can only make fewer commands run, and no approval is needed to do less. The
second is an approved plan running a command the policy file said must never run
unheld, on a machine where nothing can hold it. That is the gate overruling
`luu.toml`, which is the one thing the gate must never do — the same rule
[`the-gate`](2026-08-30.a-refusal-is-a-message.completed.md) applies to an
amendment, applied to a field nobody had applied it to yet.

`Plan::unmet` is where the refusal goes, beside every other "the plan asks for
what the policy does not grant", so it is refused **before anything runs** rather
than discovered as a denial four turns in.

## Why this is worth having at all

A session on a Linux box with Landlock runs `enforcement = "kernel"` and never
thinks about it. The interesting case is the one this repository actually has:
`luu.container.toml` and macOS, where a person sets `best-effort` **once, for the
session**, because one command needs to run on a machine that cannot hold it —
and every other job in that session silently inherits the loosening. Per-job
enforcement is how the loosening stops being a property of the afternoon and
becomes a property of the one job that argued for it.

## The proposal

```rust
pub struct Plan {
    …
    /// `None` is every plan written before this existed, and reads as "the
    /// session's".
    #[serde(default)]
    pub enforcement: Option<Enforcement>,
}
```

**`Option`, and not a defaulted `Enforcement`.** `Enforcement::default()` is
`Kernel`, so a `#[serde(default)] enforcement: Enforcement` would make every plan
ever written — every recording, every script, every plan block a model has
emitted — start *demanding* the kernel. On a `best-effort` session those plans
would begin to be refused by `unmet`, and the change would look like a
regression in the gate rather than a new field. Absent has to mean absent.

- `Enforcement::strictest(a, b)` is the lattice, one function, so nothing else
  has to remember which of the two is stricter.
- `Plan::unmet` adds one line when the plan would loosen.
- `Plan::narrow` takes the stricter of the two rather than the session's.
- `## enforcement: kernel` in a script, beside `## network:` and `## egress:`,
  because a script's written plan is its approval and it can already say
  everything else a plan can.

### The wire and the record do not move

An additive optional field, the same shape as `ToolOutcome.command`, which is
why the format number did not move then either. Worth naming the one asymmetry:
an older reader that drops the field reads the job as "the session's", which is
the **wider** of the two — so it can under-report how strict a job was, never
over-report it. A reader that showed a job as stricter than it ran would be the
dangerous direction, and this is not that one.

## What it costs

- A third thing a model can put in a plan block that it will almost never put
  there. A 7B does not write `enforcement` unprompted, and that is fine: the
  field exists for the gate and for scripts, which is where `closes_on` lives
  too and for the same reason.
- One more field `unmet` has to be right about, and it is the one whose
  refusal runs the opposite way from every other line in that function — which
  is exactly the kind of thing a reader skims past, so it says so where it is
  written.

## What was rejected

- **Letting a plan loosen it with a louder approval** — a "yes, really" flag at
  the gate. The policy file is the floor for everything else in a plan; carving
  out the one field that decides whether the kernel is involved at all would
  make it the floor for permissions and a suggestion for enforcement.
- **A per-command enforcement.** The plan is the unit of approval, and a job
  whose commands were held by different mechanisms would need a verdict per
  command to stay honest. The verdict already names the mechanism per call, so
  nothing is lost by deciding at the job.
- **Making it narrow silently instead of refusing.** Clamping a `best-effort`
  request up to `kernel` without saying so would leave a plan whose text says one
  thing running under another, and the person at the gate reading the plan is the
  whole point of the gate.

## Still open

- **The gate cannot amend it.** A plan carries `enforcement` from the model or
  from a script; the approve message has no field for it, so a person at the
  gate can widen files, writes, commands, network and egress but cannot tighten
  enforcement. Adding it is a protocol change rather than part of narrowing, and
  it is the obvious next line if anyone wants it.
- **`limits` is still the session's**, and it is the last field of the policy
  that a plan cannot narrow. It is a different argument —
  `RECORD/2026-09-01.what-the-audit-left.completed.md` names it — because a plan
  has no words for what a child may *spend*, and inventing them means inventing
  a unit.
- **Nothing measures whether a model ever uses this.** Like `network`, it is a
  field the gate and scripts will use and a 7B probably will not; unlike
  `network`, no probe asks for it.
