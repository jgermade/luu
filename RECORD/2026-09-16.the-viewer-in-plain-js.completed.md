# The viewer's rows in plain JS, because reactivity is not what they need

Asked, while looking at the file viewer: *would it make sense for the own
editor's content to be handled with plain JS instead of a jq79 component?*

Yes, and the reason is already written down in this repository — it just was
never followed to its conclusion. This file argues it; the section appended at
the bottom carries the code it produced and the numbers that settle it,
including the one place where the argument below turned out to be wrong.

## The problem, in the numbers that are already recorded

[`RECORD/2026-09-16.what-the-debug-ui-does-not-need.completed.md`](2026-09-16.what-the-debug-ui-does-not-need.completed.md)
measured the viewer end to end and found the split that decides everything on
this page:

```
crates/luu/src/serve.rs, 3807 lines, release, loopback
  server: highlight + serialise      20 ms
  browser: build the rows           271 ms
```

**93% of the cost is the browser building rows**, and nothing about how the
bytes arrive can touch it. The three "should we adopt X" questions in that file
— a socket, a service worker, Monaco — were all answered *no* against this
number. This is the fourth question asked against the same number, and it is
the first one that answers *yes*, because it is the only one that proposes to
change the half where the time actually is.

## Where the 271 ms goes: per chunk, not per line

The row template is two nested `:each`es:

```html
<li :each="line in workspace.head"><code
  :each="chunk in line"
  :class="chunk.kind ? `hl-${chunk.kind}` : ''">{{ chunk.text }}</code></li>
```

The inner one is the expensive half and it is easy to miss, because the record
that measured this talked about rows throughout. Per **chunk**, jq79's `:each`
(`_s` in `vendor/jq79.js`) builds:

- a scope object, `Object.create(parentScope)` plus three `defineProperty`
  calls for `chunk`, `$index` and the `at` name,
- a reactive scope, `ce(t)`, which is a disposable node in the effect graph,
- an effect for `:class`, which re-evaluates `chunk.kind ? ... : ''`,
- an effect for the `{{ chunk.text }}` interpolation,

and per **line**, a comment anchor for the inner `:each` on top of the `<li>`.

A 3807-line Rust file at ~5 chunks per line is therefore on the order of
**20 000 live reactive scopes and 40 000 effects** — standing subscriptions,
retained for as long as the tab is open, over data that cannot change. The file
arrives whole and already coloured in one `GET /api/workspace/file`. Nothing in
`lines` is ever written to. Every one of those effects exists to observe a
constant.

That is the whole argument. **Reactivity is a mechanism for tracking what
changes, and these rows never change.** jq79 is the right tool for the chrome
around them — the placeholder, `loading`, `error`, the tab strip, the Monaco
host — which is small and genuinely reactive. It is the wrong tool for 20 000
immutable spans, and the price is not a matter of jq79 being slow: any
reactive renderer charges per bound node, and here every bound node is a
binding to a constant.

## The proposal

**Keep `content-viewer.html` a jq79 component. Make the `<ol>` a plain element
that a module fills.**

```html
<ol :if="!monacoing && shown?.kind === 'file'" id="code-host" class="code"></ol>
```

```js
const esc = s => s.replace(/[&<>]/g, c => ({ "&": "&amp;", "<": "&lt;", ">": "&gt;" }[c]))

export function appendRows(ol, lines) {
  let html = ""
  for (const line of lines) {
    html += "<li>"
    for (const c of line) html += `<code${c.kind ? ` class="hl-${c.kind}"` : ""}>${esc(c.text)}</code>`
    html += "</li>"
  }
  ol.insertAdjacentHTML("beforeend", html)
}
```

**This is not a new escape hatch — it is the one that is already there.**
`content-viewer.html` already attaches Monaco to a plain element by id inside a
`requestAnimationFrame`, and says why in its own comment: *the element is the
one thing both sides can name, and a viewer that needed a framework hook to
exist would be a viewer that broke the day the template moved.* The own viewer
gets the same seam, which makes the two halves of that file consistent rather
than adding a second mechanism to it.

`insertAdjacentHTML` over `createElement` + `textContent` deliberately, and the
tie-break was stated when this was asked for: **performance over bundle
weight.** One parse of one string beats N × 2 node constructions plus N
`textContent` writes, and the escaping it costs is four lines. The alternative
stays correct and is the fallback if the string build ever surprises us.

## What it buys beyond the time

**The item this record's predecessor left open closes.** Phase 8 of
[`RECORD/2026-09-15.a-three-pane-inspector.WIP.md`](2026-09-15.a-three-pane-inspector.WIP.md)
ends with:

> The tail is one block, so a very large file still has one long second render.
> The shape generalises — N blocks, each its own `:each`, appended as they
> arrive, which would be linear rather than quadratic — but the template needs
> one `:each` element per block […]. Two is what the template can say plainly.

With `insertAdjacentHTML` appending, *N blocks* stops being a template problem
and becomes a loop bound. Whether N should be more than two is then a question
the measurement can answer instead of one the renderer forecloses.

**`head`, `tail` and `pending` stop being reactive state.** All three exist in
`workspace.js` only to work around the `:each` — the doc comment says so in as
many words. The rows are painted from `content.lines`, which the store already
holds, and the two-block split becomes a fact about *when the painter is
called* rather than a shape the store has to carry. The spacer stays: a
scrollbar that tells the truth from the first frame is worth an element, and
the identity result that justified it (selection and scroll position surviving
the tail landing) is now free rather than bought.

**A class of bug leaves the subtree.** `picked` rather than `selected`, in this
very file, cost half an hour to a scope variable colliding with a DOM property.
Plain nodes have no scope to collide with.

## What it costs

**`<style scoped>` seals every element the compiler builds with a
`data-jq79` attribute**, and rewrites `.code li` to `.code li[data-jq79="…"]`.
Hand-built `<li>`s do not carry it and would lose the gutter, the monospace and
the line-height. The fix is to move `.code`, `.code li`, `.code li::before` and
`.pending` into `app.css` — which is exactly what was already done for the
`hl-*` classes, for the same reason and with a comment that says so:

> One class per capture `crate::highlight` emits. Global rather than scoped to
> the viewer because the chunks are plain `<code>` elements […]

So this is not a new compromise, it is the existing one extended by four rules.
Forging the hash was rejected: it is an internal of the compiler, and a
stylesheet that hard-codes one breaks silently the day the template's bytes
change.

**Escaping becomes ours.** `{{ }}` sets `textContent` today and is safe by
construction; a string builder is not. Four lines and one place, and the
alternative shape is one commit away if it ever looks like the wrong trade.

## What it does not buy, and this is the part worth being blunt about

**Nothing at 50 000 lines.** The 1.86 MB probe in
[`RECORD/2026-09-15.a-three-pane-inspector.WIP.md`](2026-09-15.a-three-pane-inspector.WIP.md)
found 329 518 DOM nodes and 813 MB of heap against Monaco's 362 and 22.4 MB.
This change keeps one `<code>` per chunk, so the node count stays the same
order and the heap stays dominated by it. **Only virtualising fixes that
regime, and virtualising is rejected on purpose** — it is what costs Monaco the
browser's own Ctrl+F, which was the deciding number in that comparison.

This therefore does **not** argue for raising the 512 KB cap, and any future
reading of this file that uses it to should be treated as a misreading.

## Rejected

- **Replacing jq79 in the component wholesale.** The chrome is reactive and
  small, which is the case jq79 is good at. Rewriting it would trade a real
  win on the 93% for churn on the 7%.
- **Virtualising.** Above: Ctrl+F, and it was already decided.
- **Streaming the payload.** A different axis and already answered: the
  transport is 0.6 ms on loopback, and the reorder that makes `FileView`
  head-first left that door open without needing this one.
- **Keeping `:key="$index"` and hoping.** It was already tried in phase 8 and
  changed nothing measurable.

## A discrepancy found while reading `jq79.js`

Phase 8 states the mechanism as:

> **jq79's `:each` rebuilds the whole list off-DOM and attaches it whole**, so
> N passes cost N rebuilds and the work is quadratic in the number of passes.

**That is not what `vendor/jq79.js` does today.** `_s` keeps the previous
render's items in a `Map` by key, reuses an item when the key matches *and*
`Object.is(prev.item, next)` holds, and reorders the survivors with a longest
increasing subsequence (`Ns`) rather than rebuilding them. With no `:key` the
key is the index, and `lines.slice(0, 400)` then `lines.slice(0, 800)` hands it
the same chunk arrays at the same indices — which should hit the reuse path for
every row already on screen.

So the curve phase 8 measured (47 ms per batch climbing to 125 ms) is real and
reproduced, but **the mechanism it was attributed to does not match the
renderer's code**, and the true cause is still unidentified. This does not
change the proposal — the per-chunk construction cost above is a *first build*
cost and is unaffected by how well reuse works — but it does mean the two-block
shape was adopted against an explanation that may be wrong, and anyone leaning
on that sentence again should re-derive it first.

Not chased here, because plain JS removes the renderer from this path entirely
and the question stops being load-bearing for the viewer. It stays load-bearing
for every other `:each` in the UI.

## Still open

- **The diff is one pass and has never been measured.** It has the same shape —
  `:each` over hunks, `:each` over lines within them — and should use the same
  painter. Whether it needs the two-pass split is a question for after the
  number.
- **Whether two blocks is still the right N.** Append is linear, so the reason
  for exactly two is gone; what the right answer is depends on the measurement
  that follows.
- **`FIRST_ROWS = 200` is unchanged and still not measured against the
  window.** The reasoning for not measuring the viewport stands.

## 2026-09-16, later: built and measured, and one of the answers above is wrong

`crates/luu/ui/rows.js` is the module; `content-viewer.html` keeps the chrome
and hands it an empty `<ol id="code-rows">`; the row rules moved to `app.css`;
`head`, `tail`, `pending` and `showTheRest` are gone from `workspace.js`.

**The instrument.** A `MutationObserver` counting `ol.code > li`, the same shape
phase 8 used, against the **debug** binary — `rust_embed` reads the UI from disk
in debug and bakes it in for release, so all three arms are swapped without a
rebuild and the server's share is inflated identically in every column. Median
of seven opens after a warm-up, Chromium, one machine. The probe is
[`RECORD/runs/2026-09-16.plain-js-rows/probe.mjs`](runs/2026-09-16.plain-js-rows/probe.mjs).

**One trap worth writing down, because it cost the first two runs.** There are
**two** `.col-main` elements — the inspector's and the content column's — and
`document.querySelector(".col-main")` returns the inspector's. The observer was
watching the file tree while the file it was timing rendered in the other
column. Phase 8's warning was that a headless browser does not pace
`requestAnimationFrame` at 60 Hz; this is the neighbouring one, and both come
from instrumenting a page by a selector that is not as unique as it reads.

### The numbers

| | | before | after |
| --- | --- | --- | --- |
| `serve.rs` (3947 lines, 21 652 chunks) | something to read | 204 ms | **191 ms** |
| | the whole file | 969 ms | **512 ms** |
| | JS heap | 444 MB | **13 MB** |
| `store.js` (1036 lines, 6471 chunks) | something to read | 82 ms | **66 ms** |
| | the whole file | 285 ms | **158 ms** |
| | JS heap | 138 MB | **14 MB** |

**The whole file lands in half the time**, and first paint barely moves —
expected, because 200 rows is cheap either way and what dominates that column is
the debug server's own 180 ms.

**Identical where it must be identical:** 25 601 DOM nodes against 25 602 (the
extra one is the spacer, which used to be a `:if` comment), and `scrollHeight`
71 062 in both. The bar still does not move.

### The heap is where the prediction above was wrong

*What it does not buy* says the node count stays the same order so "the heap
stays dominated by it". **It is not dominated by it.** 444 MB → 13 MB over an
unchanged node count says the heap was mostly the *reactive* layer — the scope
objects, the effect graph, the retained closures — and not the DOM at all.

That corrects the section above rather than the decision: the 50 000-line
regime is still one this viewer excludes on purpose, and this is still not an
argument for raising the 512 KB cap. But the reason given for expecting no
memory win was wrong, and the 813 MB in the Monaco comparison should now be
read as *mostly reactivity*, not *mostly nodes* — which means that table
measured jq79 as much as it measured the viewer.

### `insertAdjacentHTML` against `createElement`: a tie, so safety decided

Asked while this was being built: *is `insertAdjacentHTML` faster than a
`DocumentFragment` built with `createElement`?* The proposal above asserted it
was, on the tie-break *performance over bundle weight*. **It is not.**

Both were built and timed over a payload already in memory, into an `<ol>` that
is really in the document so layout is charged, round-robin so neither arm was
always first ([`RECORD/runs/2026-09-16.plain-js-rows/bench.mjs`](runs/2026-09-16.plain-js-rows/bench.mjs), median of 14 after a warm-up):

| | `serve.rs` | `store.js` |
| --- | --- | --- |
| `insertAdjacentHTML` | 189 ms / 213 ms | 54 ms / 52 ms |
| `createElement` + fragment | 191 ms / 208 ms | 48 ms / 52 ms |
| the HTML string alone, escaped | 2.5 ms / 3.2 ms | 0.7 ms |
| the HTML string alone, unescaped | 1.2 ms / 1.3 ms | 0.4 ms |

(Two full runs, so two figures per cell. They straddle each other.)

**Building the entire 700 KB string is 3 ms of a 210 ms job.** The escape pass
inside it is ~1.5 ms, well under 1%. Everything else — 99% — is constructing
elements and laying them out, which both paths pay identically, because
`insertAdjacentHTML` does not skip node construction, it only moves it into the
parser.

A first, non-interleaved run had them 200 ms against 177 ms and looked like a
real difference. It was arm order: whichever ran first paid for JIT warm-up and
whichever ran last inherited the others' garbage. The rotation removed it. **A
24 ms "result" that survives one run and dies under interleaving is the reason
the arms are rotated**, and it is the third measurement trap this viewer has
produced.

So the tie-break moved to the axis that was not tied: **`createElement` +
`textContent` cannot produce an injection bug and has no escape pass to get
wrong** the day the server sends a chunk kind nobody anticipated. `rows.js`
builds nodes. The string builder is recorded here rather than kept as dead
code.

The `heapMB` figures for these two arms are **not** reported, on purpose: the
two runs put `insertAdjacentHTML` at 13 MB then 45 MB and `createElement` at
46 MB then 13 MB — they swapped, which means the number is GC timing and
carries no signal at this sample size. The before/after gap in the table above
is an order of magnitude and survives both runs; this one is noise, and quoting
it would be quoting noise.

Re-run of phase 8's identity checks, now that nothing re-renders

The gutter and the light-theme colour are the two that would have failed
silently if the `<style scoped>` rules had been left where they were: a scoped
selector is rewritten to `[data-jq79="…"]`, and nothing `rows.js` builds carries
that attribute.

### Still open, after the measurement

- **The diff is still a `:each` over hunks and lines.** It is the same shape and
  the same argument, and it is now the only place in the viewer left paying it.
  Not done here because it is a second change with a second set of checks, and
  this one is worth landing on its own. It has still never been measured.
- **Two blocks is still two, and now by choice.** Appending is linear, so the
  tail could be split further; 512 ms for the largest file in this repository
  did not justify it, exactly as 271 ms did not before. The difference is that
  the renderer no longer decides — a loop bound does.
- **`FIRST_ROWS = 200`** is unchanged and still not measured against the window.
- **The `:each` mechanism from phase 8 is still unexplained**, and it now
  matters less here and exactly as much everywhere else in the UI.

### The same thing on the release binary, and a number that must not be compared

`rust_embed` bakes the UI into a release build, so the arms cannot be swapped
there. Two release binaries were built instead — one on each UI — and run on the
same machine, minutes apart ([`RECORD/runs/2026-09-16.plain-js-rows/release-probe.mjs`](runs/2026-09-16.plain-js-rows/release-probe.mjs), median of nine):

| | | before | after |
| --- | --- | --- | --- |
| `serve.rs` (3947 lines) | something to read | 71 ms | **61 ms** |
| | the whole file | 790 ms | **359 ms** |
| | JS heap | 552 MB | **13 MB** |
| `store.js` (1036 lines) | something to read | 39 ms | **24 ms** |
| | the whole file | 243 ms | **118 ms** |
| | JS heap | 722 MB | **12 MB** |

**Do not read the 359 ms against the 271 ms on record.** Phase 8's release
figures were taken on a different machine, and this one is about three times
slower on the same work — its *before* column is 790 ms where phase 8's was
271 ms. The only honest comparison is a column against the column beside it, and
that is why the before binary was built at all rather than quoting the number
already written down. Every ratio in this record — a little over 2× on both
files, on both builds — is within-machine; every absolute in it is this
container's and belongs to nothing else.

That is the fourth trap this viewer has produced, and it is the same family as
the other three: an instrument, a selector, an arm order, and now a baseline,
each of which looked like a result until it was checked.
