# Does the envelope collapse generalize? Two untested tools, probed

Closes the bullet
[`a-grammar-for-tool-calls`](2026-09-06.a-grammar-for-tool-calls.WIP.md) left
open after today's `run_command` fix: *"whether other tools share the
pattern is still untested."*

## The question

`run_command`'s old schema — `{command: string, args: [string], cwd,
timeout_ms}` — collapsed three times across three machine-and-corpus
combinations: a model handed the tool's own argument object straight to the
top level, no `name` field, believing it had already answered. The fix
folded `command`/`args` into one `argv` array and measured 0/24 collapses on
a follow-up run. What that run did not answer: was `run_command` a special
case, or does any tool whose argument object has more than one key carry the
same risk?

## The other four tools, read against the hypothesis

The hypothesis named in the schema-change section above is specific: the
collapse happens when a tool's own argument object has a **name-shaped
string beside an argument list** — a shape that reads as a call in its own
right. Read each of [`fs.rs`](../crates/agent-core/src/tools/fs.rs)'s four
schemas against that:

| tool | schema | reads as a call on its own? |
| --- | --- | --- |
| `read_file` | `{path, start_line, max_lines}` | no — nothing plays `name`'s part; `path` is a value, not an action |
| `list_dir` | `{path}` | no — one key |
| `edit_file` | `{path, old_string, new_string}` | no — three peer strings, none name-shaped |
| `write_file` | `{path, content}` | no — two peer strings |

None has the `command`+`args` shape — a lone identifier-like field next to a
list. `read_file` and `list_dir` had already been exercised, collapse-free,
by every run in
[`the-tool-call-probe-run`](2026-09-14.the-tool-call-probe-run.completed.md)
and the two 14B runs since. `edit_file` and `write_file` had not: **no probe
in this project had ever pointed a tool call at either of them** —
`scripts/tasks/tool-call-probe.txt` only reaches `read_file`, `list_dir` and
`run_command`.

## The instrument

[`scripts/tasks/tool-call-probe-writes.txt`](../scripts/tasks/tool-call-probe-writes.txt) —
eight prompts, four `edit_file` and four `write_file`, each answerable with
exactly one call, engineered against a scratch project
(`greeting.py`, `notes.md`, `config.json`) rather than this repository,
because both tools write. Unlike the read-only corpus, independence between
prompts is not free here — a mutation one prompt makes could change what a
later prompt reads — so
[`runs/2026-09-15.14b-write-tools-probe/run.sh`](runs/2026-09-15.14b-write-tools-probe/run.sh)
restores the scratch project from a template before every prompt, the
write-tool analogue of the read-only corpus's "no shared history." Same
model, machine and settings as every other 2026-09-15 run:
`qwen2.5-coder-14b` over `llama-server`, `--ctx-size 8192 --n-gpu-layers 99
--flash-attn on --temperature 0 --seed 7`, scored by the real
`agent_core::tools::score_call`.

## The result

| verdict | count |
| --- | ---: |
| Parsed | 8 / 8 |
| Drifted | 0 / 8 |
| Continued past the fence | 0 / 8 |
| No call | 0 / 8 |

**Clean on all eight, both tools, first attempt.** Every reply closed the
fence with `{"name": "edit_file"/"write_file", "arguments": {...}}` and
nothing after it — not even the `ContinuedPastFence` habit that still shows
up on two of three `run_command` prompts in the same day's runs. No envelope
collapse, no drift, no trailing prose.

**This does not clear the hypothesis in general — it fails to falsify it in
the one place it predicted nothing would happen.** The hypothesis said the
risk was specific to a name-plus-list shape; `edit_file` and `write_file`
don't have that shape, and they came back clean, which is consistent with
"unique to `run_command`'s old schema" without proving no other schema
anywhere could trigger it. The honest reading: eight prompts, one model, one
seed, is a small sample for a defect that itself only fired 3 times in
several hundred prior tool calls across this project's whole probe history —
absence here is weak evidence, not a proof, but it is the same strength of
evidence `run_command`'s own fix was measured against, and it points the
same way.

## Still open

- **The two tools with the most collision-prone shape were never tried
  because they don't exist yet.** If a future tool takes a `{name, args}`-
  shaped pair for its own reasons — a subprocess-launching tool that is not
  `run_command`, say — this record's evidence does not cover it; the
  hypothesis, not a general clearance, is what should guide that tool's
  schema.
- **Same caveat every number in this file's neighbor carries**: one model,
  one seed, one machine. A 7B or a different seed could still find something
  eight prompts at temperature 0 cannot.
