# The tree renames

Jesús: *"en el árbol de archivos y carpetas, no funciona el botón de editar"*.
Asked what the pencil should do, given that the design said the tree was
read-only: *"quiero habilitar la edición de archivos, el lápiz permitirá
renombrarlo"*.

## The problem

The pencil was built on purpose as half a feature
([`the-tree-makes-room-for-an-icon`](2026-09-16.the-tree-makes-room-for-an-icon.completed.md)):
on a file it opened the file pinned — what a double click already did — and on
a folder it asked the server to read a directory as a file, and the column
said *"Could not read RECORD: is a directory"*. That record left the write half
open because it contradicted a sentence in `luu-design.md`:

> Read-only throughout: the file tree and the git panel are a window onto the
> workspace, not a second way to change it — every write still goes through
> the job gate.

So the button did not work because nothing had been decided for it to do.

## The decision, and the argument with that sentence

**The pencil renames a file or a folder.** That is a write which does not go
through the job gate, and the sentence above is changed to say so.

The gate exists to hold a *model's* actions until a person approves them: a
tool call is proposed by something nobody is watching type, and approving it
is how a person stays in the loop. A rename from the tree is the person
themselves, at the keyboard, typing the name. Routing it through the gate would
mean proposing a job on their behalf and asking them to approve what they just
did — the same reasoning that kept the tree's *reads* outside the gate
(`workspace.rs`'s module note). What the sentence was protecting is that the
model has exactly one way to write, and that is unchanged: no tool, no turn and
no plan reaches this endpoint.

What it does keep from the gate is the sandbox: a rename is checked like a
`write_file`, so a posture that only reads refuses it.

## What a rename may do

- `POST /api/workspace/rename { path, name }` → `{ path }`, the new one.
- **A name, never a path.** `/`, `\`, NUL, `.` and `..` are refused, so a rename
  cannot move anything to another folder. The base itself is not renamed.
- **No overwrite.** A name already taken is a `409` with nothing moved, because
  `rename(2)` replaces a file silently. A case-only rename on a case-insensitive
  disk finds *itself* there and is allowed.
- **Both ends through the sandbox for `read-write`.**
- **From this machine only** — a server bound on loopback, asked by a loopback
  `Host` — as Settings' writes and the engines are. A page on another site that
  rebinds its DNS to 127.0.0.1 is same-origin with this server, and `Host` is
  what it cannot fake.

On the page, the pencil (and F2 on a row, as in an editor) turns the name into
the theme's `TextInput`, with the part before the extension chosen. Enter or
leaving the field renames; ESC puts the name back; a refusal is said under the
row in the server's words, and the field stays open with what was typed. An open
tab on the file, or on anything under the folder, follows it, and a folder that
was open stays open under its new name.

## Rejected

- **Through the job gate.** See above: a person approving their own keystroke.
- **A path rather than a name**, which would make the same endpoint a move: a
  move is a bigger write — it changes where things are, not only what they are
  called — and nothing asked for it.
- **Editing contents from the viewer.** Asked about in the same question and
  not chosen: the pencil is for the name.

## What was checked

- `workspace::tests::an_entry_is_renamed_in_place_and_nothing_else_is`: a file
  and a folder renamed; a taken name, five names that are paths or dots, the
  base, a missing entry and a path outside the sandbox each refused with
  nothing moved; and a posture that only reads refusing it. The first version
  of that last check passed for the wrong reason the other way round — a
  default policy with a `read` rule *added* still grants `read-write` on `.`,
  so the "read-only" posture renamed the file. Its rules are replaced now.
- `serve_ws::the_tree_renames_a_file_from_this_machine_only`: 200 with the new
  path, 409 with both files intact, 400 for `../`, 403 for `Host: evil.example`.
- `workspace.spec.js`, *the pencil renames a file or a folder in place*: the
  field focused with `hello` chosen out of `hello.txt`, the refusal under the
  row, the tab following, F2 and ESC, and a folder staying open with its file
  re-pointed. 3 of 3 in that spec pass.

## Still open

- Editing a file's contents from the viewer, if it is wanted after all — it is
  the larger write, and the same argument would have to be made for it.
- Creating and deleting from the tree.
- A remote host's tree (`/h/<name>/`) cannot rename: that server sees a request
  that did not come from its own machine. Whether a host the person added should
  be trusted to is a question for the hosts record, not this one.
