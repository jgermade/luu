# What Aider does about relevance, and the one place it says we are wrong

**Status:** study, and two decisions it forces. Follows
[`2026-08-27.context-manager.md`](2026-08-27.context-manager.md), which left
*relevance: grep/`tree-sitter` vs. embeddings* open and said that deciding it
before there was a workload to test against is how the wrong index gets built.

Read against Aider at `main` on 2026-08-27: `aider/repomap.py`,
`aider/coders/chat_chunks.py`, `aider/coders/base_coder.py`, `aider/history.py`.
Aider is the closest prior art there is — a coding agent whose whole problem is
fitting a repository into a window — and it has been answering this question in
production for long enough that guessing at it here would be the expensive kind
of laziness.

## What it actually does

### Relevance is a reference graph, not similarity

No embeddings anywhere. The chain is:

1. Per-language `tree-sitter` queries (`.scm`) extract **tags**: definitions and
   references. Where a language has no reference query, Pygments name tokens
   backfill the references.
2. A `networkx` MultiDiGraph, nodes = files, edges = "this file references an
   identifier that file defines".
3. Edge weight is `sqrt(num_refs)`, scaled:
   - ×10 if the identifier was mentioned in the conversation
   - ×10 if it is "well named" (snake/kebab/camelCase, ≥8 characters)
   - ×0.1 if private (leading underscore)
   - ×0.1 if overused (defined in more than five places)
   - ×50 for files already in the chat
4. **PageRank with a personalization vector** pointed at the files in the chat,
   the files mentioned, and files whose path matches a mentioned identifier.

So relevance means *what the current conversation points at, propagated through
the reference graph*. That is a different thing from semantic similarity, and it
is the reading that matters: an embedding says "this text resembles that text";
a reference graph says "you cannot understand this without that".

### The budget is fitted by binary search

Ranked tags are rendered, counted, and the number of them binary-searched until
the rendering lands within 15% of `max_map_tokens`.

### Caching is by mtime, on disk

Tags live in a `diskcache` (SQLite) keyed by filename with the file's mtime,
falling back to an in-memory dict if the cache is corrupt. The rendered map is
cached in memory keyed by the tuple of (chat files, other files, budget,
mentioned files, mentioned identifiers), with refresh modes: `auto`, `manual`,
`always`, `files`.

### Where the map sits in the prompt

```
system + examples + readonly_files + repo + done + chat_files + cur + reminder
```

with `add_cache_control_headers()` marking the last message of system/examples,
of repo/readonly, and of chat_files; `cacheable_messages()` then scans back from
the end to the last marked message.

### Compaction fires late, and in one big step

`ChatSummary` only triggers when the history is over its limit. It walks
backwards accumulating until half the budget, keeps that tail verbatim, and has
a cheap model summarize the whole head into a single message — recursively, if
the result is still too big. The split respects exchange boundaries.

## Decision 1: relevance is `tree-sitter` plus a reference graph. Embeddings stay out.

The open question is closed, and not on Aider's authority — on the reasons its
implementation makes visible:

- **It explains itself.** A graph can say *why* a file was included: something in
  the conversation referenced something it defines. A cosine distance cannot.
  For a project whose thesis is that context decisions must be measurable, a
  selection method that cannot be interrogated is a bad fit on principle.
- **Nothing to ship and nothing to stale.** No embedding model in the binary, no
  vector store on disk, no re-indexing policy. Staleness is `mtime`, which is
  already how everything else on this machine decides whether to redo work.
- **It fits the sandbox story.** Reading files and parsing them is exactly the
  access the sandbox will already have to govern. An embedding index is a second
  store of the user's code, with its own lifetime and its own leak question.

Embeddings are not refuted, they are unmotivated: nothing measurable has asked
for them yet, and per the RECORD's own rule the answer to "which index" comes
after there is a workload, not before.

## Decision 2: our eviction policy is cache-hostile, and Aider is the reason we can see it

This is the finding that cost something, so it gets stated plainly.

Our rule says **what changes most often goes last**. Aider puts its repo map
*above* the history, which looks like a straight contradiction. It is not — the
rule was under-specified, and the correction matters:

> Order blocks by how often a block is **rewritten**. A block that only grows at
> its end is not rewritten.

A prefix cache reuses the longest common prefix. Appending to the history leaves
everything before the new tokens intact, so history-then-map would push a large
map *behind* changed bytes every single turn; map-then-history keeps the map in
the reusable prefix as long as the map itself does not change. Aider then makes
sure it rarely does: the refresh modes exist for exactly that trade, freshness
against prefix stability.

Now turn that lens on what we shipped. Our baseline evicts **the oldest turn,
every turn, once the window is full**. From the first eviction onwards, the
history block is rewritten from its front on every single call — so the reusable
prefix collapses to the system block, permanently. The commitment that the
stable prefix is load-bearing, and the policy that quietly defeats it, are in the
same codebase, written on the same day.

Nothing failed, of course. It just gets slower, which is the failure mode
`AGENTS.md` names as the one to watch for.

**What follows is not a change to the baseline.** The baseline is supposed to be
the dumb thing that later work has to beat, and it is doing its job — it just
exposed the first real thing to beat it with:

> **Strategy 1, to be measured against the recorded baseline: evict in blocks.**
> When the next turn does not fit, drop whole turns down to a low-water mark
> (half the history budget, say) instead of dropping exactly one. The history is
> then rewritten once every N turns rather than every turn, and stays
> byte-stable in between.

The number that decides it is prompt-cache reuse, which we said we would report
and now have a first reason to. Aider's compaction has the same shape — fires
late, cuts deep — and that is not a coincidence: it is what a prefix cache
rewards.

## What this does not change, and one correction to my own reasoning

**Fusing the summary into a turn stays.** Aider does the opposite: its summary is
a standalone `user` message, breaking strict alternation, and it is fine. So the
justification I gave — "chat templates disagree about two user messages in a
row" — was too broad, and Aider is the counter-example.

The narrower reason still holds, and it is the one that should have been written
down the first time: Aider talks to API models that normalize this. We hand a
`messages` array to Ollama, which applies a **local** model's chat template —
ChatML, Llama-3, Mistral — and those are the ones that mis-render or misread
consecutive user turns. The decision stands; the argument for it was wrong.

## What it costs to adopt any of this

- **The per-language `.scm` queries are real work.** Aider carries a set of them.
  Vendoring an existing set versus writing our own is a cost we have not priced,
  and it is the bulk of the effort in decision 1.
- **The magic numbers are Aider's, not ours.** ×10, ×0.1, ×50, "more than five
  definitions", "at least eight characters" — tuned against Aider's workload and
  its models. Adopt the *shape*, measure the constants, and never inherit them as
  truth. A 7B model with 8K of context is not the workload those were tuned on.
- **Decision 1 cannot start yet.** Relevance selection needs to read files, and
  we have no tools and no sandbox. It stays behind them in the order.
- **Decision 2 can start immediately**, and should: it needs nothing that does
  not already exist, and it is the first entry in a comparison table that is
  currently empty.

## Still open

| Question | Precondition |
| --- | --- |
| Block eviction versus per-turn: does it actually buy reuse, and how much? | nothing — this is next |
| Binary-searching the rendering to fit exactly, as Aider does, versus our per-piece counting with boundary error | a case where the boundary error changes a decision |
| Vendor `.scm` queries or write them | decision 1 starting at all, i.e. tools first |
| Whether the personalization signal survives models that name identifiers less reliably than a frontier model does | a real model on a real task set |

# 2026-08-27, later: the `.scm` cost above is wrong

This file says the per-language queries are "the bulk of the effort in decision
1", and prices vendoring versus writing them as an open question. Checked
against the actual crates today, and the premise does not hold for the half that
matters first:

```rust
// tree-sitter-rust 0.24.2, bindings/rust/lib.rs
pub const TAGS_QUERY: &str = include_str!("../../queries/tags.scm");
```

Every `tree-sitter-*` crate exports its tags query as a `pub const`. There is
nothing to vendor and nothing to write: it is a `use`. The Rust query is 60
lines, Python's is 14, and both already capture `@definition.*` **and**
`@reference.call` — so the edges decision 1 needs for a reference graph come from
the same query as the definitions.

Aider carries its own copy because it supports languages whose upstream queries
are missing or inconsistent, and because it reaches them through
`py-tree-sitter-languages` rather than per-language packages. That is a
consequence of its language coverage, not a cost inherent to the approach, and
reading it as one is how this file got the estimate wrong.

What this changes: the cheapest first step is smaller than decision 1 as written
here. A **per-file outline** — definitions with their signatures, bodies elided,
from `TAGS_QUERY` alone — needs no graph, no PageRank, no personalization vector
and no tuned constants, and it is measurable with the budget instrument that now
exists. Aider begins at the graph because it has a large window to fill with a
whole-repository map; at 8K the outline may be the entire answer, and the graph
is what happens if it is not.

The rest of the file stands. Relevance as a reference graph rather than
embeddings, and the correction about why fusion stays, are unaffected.
