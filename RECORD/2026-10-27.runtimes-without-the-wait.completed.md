>

> podrían ir apareciendo según carguen, independientemente.*
>
> *Sobre 'Cannot connect to Podman. Please verify your connection to the
> Linux system using `podman system connection list`, or try `podman machine
> init` and `podman machine start` to manage a new Linux VM': ¿no se podría
> iniciar cuando una sesión lo requiera?*

And, while this was being written:

> *Sobre los programas instalados en una sesión, ¿guardamos un parche de la
> imagen del contenedor vinculado a la sesión?*

Four questions. Three of them change code and one does not.

## 1. Why the image is "not built", and what *build* did

`luu.container.toml` names `image = "luu-worker:dev"`, and Settings asks each
runtime that answers whether **its own store** has it. Podman's store is not
Docker's (see
[`runtimes-and-the-machines-they-run-on`](2026-10-02.runtimes-and-the-machines-they-run-on.WIP.md)),
so an image built under Docker is *not built* under Podman.

*build* ran `podman build -t luu-worker:dev -f Containerfile .` in the base.
Nothing is cloned. The first stage of `Containerfile` copies the checkout
(less `.dockerignore`) into `rust:1-bookworm` and runs
`cargo build --release --bin luu` there. That costs minutes, and it has a
second cost the question did not name: it only works where the base **is**
luu's checkout. Anywhere else the build is refused with *there is no
Containerfile in …*.

**Copying the binary is right, but not the host's binary.**

- On macOS the host's `luu` is a Mach-O. The container is Linux and cannot
  run it.
- On Linux the architecture matches, but the binary is linked against the
  host's glibc. A build on a current distribution wants a newer one than
  bookworm's 2.36, and the worker would die on its first line.

The release already has the binary that fits: `luu-<arch>-unknown-linux-gnu`,
built on the oldest Ubuntu runner (glibc 2.35) for the reason `build.yml`
gives, and listed in the release's `SHA256SUMS`. The image can copy that one.

**Rust stays in the image.** It is no longer there to compile luu. It is
there because this posture's `commands` are `cargo`, `rustc`, `git`, `rg`:
the development posture is for working on a Rust tree, and `commands` is the
image's manifest. A posture for another language swaps that base and that
list together, as `deploy/Containerfile` already says.

### The proposal

A second declared file, `Containerfile.release`, in the tree beside the first:

- a `fetch` stage that downloads `luu-$(uname -m)-unknown-linux-gnu.tar.gz`
  for `v$LUU_VERSION`, checks it with `sha256sum -c` against the release's
  `SHA256SUMS`, and unpacks it;
- the **same final stage** as `Containerfile`, with `COPY --from=fetch`
  instead of `COPY --from=build`. A test pins the two final stages to each
  other, so they cannot drift.

The binary embeds the file. *build* writes it into
`<state dir>/worker-image/` and runs
`<runtime> build -t <image> -f Containerfile.release --build-arg LUU_VERSION=<this build's version> .`
there, so it needs nothing from the base. That works under all five
runtimes: `--build-arg` is in each one's documented `build`.

*from source* stays, as a second action, wherever the base has a
`Containerfile`. That is luu's own checkout, where a person may be changing
the worker. **The handshake already decides when that is needed.** A release
whose protocol differs from this build's answers *the worker speaks protocol N
and this build speaks M: the image is from a different version of luu, so
rebuild it*. No version arithmetic is added on top of that check.

### What it costs

- **The build reaches GitHub.** That is the same trust `setup.sh` places in a
  release, and it is checked the same way, against `SHA256SUMS`. The build
  does it inside the image, so it is a `RUN` line in the build's log and not a
  second downloader in luu.
- **A build between releases fetches the last release**, which is older than
  the code running `serve`. When the worker protocol has not changed, that is
  fine; when it has, the handshake says so.

### Rejected

- **Mounting the binary at run time** (`--mount …,target=/usr/local/bin/luu`)
  instead of baking it into the image. It would remove *build* for a stock
  image, but the mount has to come from somewhere the VM can see (podman's
  machine and colima share only parts of `~`), and the image would stop being
  the thing a recording names. The design says *the image is declared, not
  generated*; this keeps that.
- **Cross-compiling on the host.** A Linux target on macOS needs a linker
  luu cannot assume is installed.
- **One Containerfile choosing its stage by `ARG`** (`FROM ${LUU_FROM}`).
  BuildKit skips the stage it does not use. Whether buildah and Apple's
  builder do the same has not been checked, and two short files that a test
  holds together are easier to read than one clever file.

## 2. The runtimes appear one by one

`GET /api/runtimes` probed all five with `join_all` and answered once, so the
slowest runtime decided when the page saw any of them. A podman machine that
is down takes the whole five-second clock. Postures and the host shell waited
too, and they need no probe at all.

- `GET /api/runtimes` **probes nothing**. Whether a runtime is installed is
  `which`, which starts no process, so every card renders at once with its
  path or how to install it.
- `GET /api/runtimes/{runtime}` probes **one** runtime against the same
  images.
- The page asks each installed runtime separately and fills each card when its
  answer arrives. *Check again*, and a task that ends, do the same.

The rule from
[`runtimes-in-settings`](2026-10-01.runtimes-in-settings.completed.md) still
holds: probes run when the section opens and on *check again*, never on a
timer.

## 3. A runtime that is down is started when a session needs it

Until now a session on a contained posture whose runtime was down failed at
`Worker::start`, with the runtime's own message. The page had a *start it*
button, and the button was only in Settings.

Now, when `Worker::start` fails **and** the runtime does not answer its probe
**and** `start_steps` has a line for it, luu:

1. runs the same lines *start it* runs (`podman machine start`,
   `colima start`, `open -a Docker`, `container system start`);
2. waits until the probe answers, for at most two minutes, because
   `open -a Docker` returns long before the daemon does;
3. starts the worker once more.

Each step is said on stderr and in the log. If the second try fails, the error
names both what was tried and what the worker said.

**It starts and never stops.** A podman machine or a colima VM is shared with
whatever else the person runs in it. Stopping it when the session ends would
be luu deciding about containers it did not start. Engines are stopped with
`serve` because luu is their only user. A runtime is not luu's.

**It never installs.** Installing stays a click in Settings, for the reasons
that record gives.

**One definition of "start it".** The same `start_steps` serve the button and
the session. For podman that includes `podman machine init` when there is no
machine, which is a one-time download of the VM image. Starting from a session
is also a reasonable time to pay that: the person chose a posture on podman.

## 4. What a session installs is not kept

Nothing is kept. The container is `<runtime> run --rm`, and its PID 1 is
`luu worker`. A posture move, a worker replaced after a stuck call, and the
end of the session each start a new container from the image. Two more things
narrow it further:

- the worker runs as the person's uid (`--user`), so `apt-get install` fails
  for lack of root before it fails for lack of persistence;
- the container has `--network none` unless the policy grants the network,
  so there is nothing to download from in the first place.

What survives is the base, because it is bind-mounted. A `cargo build`'s
`target/` survives; a `cargo install` into the image's cargo home does not.

**A per-session snapshot (`<runtime> commit` at the end, resumed from it) is
not proposed.** It would make the image *generated*, so two sessions on one
posture would run on two different images. A recording that says
`docker (luu-worker:dev)` would no longer say what the commands ran on. And a
resume would be resuming onto an image nobody wrote. The declared way already
exists and needs no code: a project's own `Containerfile`,
`FROM luu-worker:dev` plus its `RUN` lines, tagged and named by a policy file
of its own. That makes it a posture, chosen at the start like any other.

## Still open

- **Whether starting on demand should be refusable**, for example
  `[worker] start = "never"` for someone who wants a down runtime to stay an
  error. No one has asked. It is a one-line check if someone does.
- **Settings does not show a start that a session made.** The task list
  belongs to `serve`'s `App`, and the session path builds its agency below
  it. The log and stderr say it. If it matters, the agency builder could be
  handed the `Tasks`.
- **The release build has been run against Docker only.** The `--build-arg`
  spelling is documented for the other four, and has not been run on them
  here.

## Built, the same day

All three, as proposed.

- **`Containerfile.release`**, and `crate::runtimes` carries it
  (`include_str!`). `Tasks::build` takes `BuildFrom::Release` (the default)
  or `BuildFrom::Source`. A release build writes the file into
  `<state dir>/worker-image/` and runs there. `Runtime::build_argv` takes
  `--build-arg`s, with the context kept last. `POST …/build` takes
  `from: "release" | "source"`, and `GET /api/runtimes` says whether the base
  can build from source (`from_source`) and which release a build fetches
  (`release`). The page shows *build* (release) and, where it can,
  *from source*.
- **`GET /api/runtimes`** calls `runtimes::seen_all`, which runs no process.
  **`GET /api/runtimes/{runtime}`** is `runtimes::probe` for one runtime. The
  page asks each installed runtime separately. A card says *comprobando…*
  until its answer arrives, and a card that already had an answer keeps it
  while it is asked again.
- **`runtimes::asleep` and `runtimes::wake`**, called from the agency builder
  only when `Worker::start` has failed. The second failure's message names
  both: *the colima (…) worker: …; starting colima did not help: …*.

**Run here, on Linux with Docker.** The release image built in about two
seconds, with the base image already pulled. Its fetch stage printed
`luu-x86_64-unknown-linux-gnu.tar.gz: OK` against v0.1.4's `SHA256SUMS`, and
`docker run --rm luu-worker:dev luu --version` answered `luu 0.1.4`. `luu tools
--sandbox luu.container.toml`, from a debug build of this branch, then shook
hands with it: `worker docker (luu-worker:dev) — luu 0.1.4, protocol 2`. The
protocol has not moved since the release, which is the case this path is for.

Two caveats, both this machine's and neither the file's. This
environment's outbound proxy re-signs TLS, so the run above added its CA in
a scratch copy of the file. The `apt-get` stage could not resolve
`deb.debian.org` here, so `rg` was left out of that copy, and `luu tools`
reported `absent rg`. That is `absent` doing its job. The file in the tree
is unchanged by both. Through the page, against `luu serve`, *build* wrote
`worker-image/Containerfile.release` into the state directory and ran it with
`LUU_VERSION=0.1.4`, and it failed at the same proxy, as expected here.

In Settings, with Docker answering and the other four not installed, the
five cards were drawn 42 ms after the section opened. Docker's answer
filled its card at 240 ms. Before this change, the whole section waited for
the slowest of the five.

**Tested.**

- `tests/runtime_wake.rs` drives `luu tools` with a stand-in `colima` first on
  `PATH`. The stand-in refuses with `colima is not running` until
  `colima start` has run, then runs the real `luu worker` where a container
  would have been. A runtime that is down gets started, and the worker
  answers the second time. A runtime that answers is not started. A start
  that fails is reported next to the worker's own complaint.
- `the_release_image_is_the_source_image_but_for_the_binary` compares the two
  files' final stages. It failed when the release file was given an extra
  package and passed again once the package was removed.
- `a_release_build_carries_this_version_and_reads_no_checkout` checks the
  line.
- `a_runtime_is_probed_inspected_and_built_by_its_own_words` checks the
  `--build-arg` spelling on colima's `nerdctl --`.
- `settings.spec.js` checks that `/api/runtimes` comes back with every
  `answers` null, that one runtime is asked by name and `host` is refused,
  and that `from` accepts `source` and refuses anything else (`422`). The
  whole spec passes, 23 of 23.

## Appended the same day: *from source* only in luu's own checkout

Jesús, reading the two records together: *"Entiendo que en producción no se
compila el worker, usando la build de la release en su lugar."* That is the
intent, and the code fell short of it in one place. `from_source`, and the
check in `Tasks::build`, asked only whether the base has a `Containerfile`.
A person's project often has one of its own. In that case Settings offered
*from source*, and pressing it would have built **their** image under the
worker's tag and labelled it `source`.

`runtimes::is_luu_checkout` now requires `crates/agent-core/Cargo.toml` next
to the `Containerfile`, which is the crate the worker is compiled from. The
route refuses a source build anywhere else (*not luu's own checkout … build
it from the release*), and the page does not offer one there. The unit test
writes a project `Containerfile` into an empty directory and finds it
refused, and finds this repository accepted.
