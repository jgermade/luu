> what does "decide, then render" forbid doing to the prompt string?

"Decide, then render" forbids **rendering the prompt first and trimming the string afterwards**.

Why that's bad:

1. **Loses attribution** — you can no longer say which bucket each token came from, because the selection was made *after* the tokens already existed as a blob.
2. **Cuts wherever the limit lands** — the trim hits an arbitrary character boundary in the rendered text, not a semantic one. You might slice a code block in half or orphan a header.

The correct order is the reverse:

- **Decide** which items (buckets) fit the token budget first.
- **Render** only those items as a pure function of that selection.

That way every token in the final string maps to a decision, and the cut happens between items, not through them.

> why is there no deny list in this policy?

Because Landlock is **allow-only**. A deny entry (a subtraction) could be honoured in luu's own checks but *not* in the subprocess — and the subprocess is exactly where it would matter. So an apparent deny would give false confidence while the kernel grants access.

The rule that replaces it: **the way to deny is to not grant.** Only what's on the allowlists (`commands`, the trees) is reachable, and nothing else.
