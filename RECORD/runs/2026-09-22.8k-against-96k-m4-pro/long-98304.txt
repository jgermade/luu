The stable prefix survives because every rule in `select` is built to change only the *end* of the prompt, never the middle:

1. **The cached prefix is one message, assembled in one place.** `system_message()` joins `system` + `tools` + `map` (in that order, by rewrite frequency) and it's pushed first, always. Nothing per-turn goes above it — the selected code is fused into the *current* user message, which is rendered last.

2. **History renders oldest-first, new turn appended.** The window is kept from the newest backwards in whole turns, so the retained block always starts on a user message and the new exchange lands at the tail.

3. **The floor only moves forward, and rarely.** Under `Eviction::Block`, when the window no longer fits the cut drops past a low-water mark instead of the minimum — so the history is rewritten once every N turns and stays byte-identical in between. That's exactly what a prefix cache pays for.

4. **`Repeat::Once` picks the oldest owner.** When a later turn re-selects a span already in the window, it's rendered in the *oldest* turn that carries it — so only the newest message changes, which is the one that changes anyway. The alternative (newest owner) would rewrite a turn already inside the prefix.

5. **The prune line is a ratchet.** It moves forward only, and only to the target the eviction policy already computed, so pruning can't oscillate the prompt between calls.

The result is stated in the render loop: "the block above the newest message is byte-identical to the one the previous call sent." And `trace.rs` measures it — `PrefixReuse` reports the longest common prefix with the previous turn's prompt, since a cache reuses a prefix and stops at the first difference.

When the window fills up, `select` runs a two-stage cut, in this order:

**0. The non-negotiable floor.** First it computes `fixed` = system + tools + map + this turn's code + this turn's prompt + `reserve`. These are never trimmed — "nothing here may trim the prompt the user just typed." If they alone exceed the limit, history goes empty and the turn still goes; being over the limit is the backend's error to report, not ours to hide by cutting the question in half. `available = limit − fixed` is what history may spend.

**1. Pruning first (the cheaper half).** If `Prune::Behind` is on and the window still doesn't fit at `available`, the prune line moves forward — but only to `target`, the same number the eviction policy computed, so depth-vs-frequency stays one trade with one knob. Pruned turns keep their question and answer; their code becomes the line that cites it (and under `Results::Cited`/`CitedReads`, their tool output does too). It's a ratchet: the line only moves forward, so the prompt can't oscillate.

**2. Eviction second, and only if pruning the whole window isn't enough.** The floor moves to `fits_from(target, …)` — the oldest turn index from which the window fits. What leaves stays out for the rest of the session; the floor never moves back. The `Evicted` report names the turns and counts the saving as the *difference of two windows*, not the sum of the dropped turns' stored counts — under `Repeat::Once` a span the oldest turn owned passes to the next turn that carries it rather than leaving with it, so summing would report a saving the window didn't get.

**3. The two policies differ only in how deep the cut goes.** `Eviction::Turn` sets `target = available` (drop exactly enough to fit — one turn per turn once full, rewriting the history from the front every call). `Eviction::Block { low_water }` sets `target = available × low_water` — a deeper cut, far less frequent, so the history stays byte-identical between cuts, which is what the prefix cache pays for.

**4. Then it renders.** Decided, then rendered: the selection walks the items oldest-first, applies `Repeat::Once` (a span already shown in the window is dropped from the later turn that re-selects it), and produces `messages` plus `buckets` that describe exactly those messages. The `Selection` carries `evicted`, `pruned`, and `repeating` out to the caller — eviction goes on the protocol (the conversation changed), pruning and repeating go on the trace channel (only the prompt changed).

> which turn gets dropped first, and why that one?

The **oldest turn in the window** — the one sitting at the floor — is what goes first, and it's dropped in whole turns from the front. Several reasons, each load-bearing:

**1. The window is kept from the newest backwards, in whole turns.** `fits_from` returns the index from which the window fits, and the floor moves there. Everything below it — the oldest turns — is what leaves. The newest turns are what the current question is about; the oldest are furthest from the present.

**2. Whole turns, because of the chat template.** "Half a turn would leave an answer to a question nobody asked, and a window starting on an assistant message makes several chat templates continue instead of answering." So the retained block must start on a user message, which is only guaranteed by dropping whole turns from the front. You can't shave the middle.

**3. The floor is a ratchet.** It only ever moves forward, so what leaves stays out for the rest of the session. That's what keeps the prompt from oscillating between calls and lets a prefix survive.

**4. Dropping the oldest turn doesn't actually lose its code.** Under `Repeat::Once` the oldest turn is the one that *owns* the spans — so when it's evicted, each span it carried passes to the next turn that carries it, in the same call. The code stays in the prompt; only the exchange goes. That's why the `Evicted` report counts the saving as the *difference of two windows*, not the sum of the dropped turns' stored counts — summing would report a saving the window didn't get.

**5. It's really the oldest *item*, not turn.** Eviction works over `Item`s, and a closed job folds to a single item worth its summary. So the first thing out can be a whole folded job — which is why eviction and compaction compose instead of cutting each other in half: the job already shrank to one summary before the floor ever reached it.

One caveat worth stating: under `Eviction::Turn` this oldest-first drop happens *every* turn once the window is full, rewriting the history from its front each call — which is exactly why the reusable prefix collapses to the system block, and why `Eviction::Block` exists to make the cut deeper and far less frequent.
