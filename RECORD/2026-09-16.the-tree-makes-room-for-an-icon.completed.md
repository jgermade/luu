# The tree makes room for an icon, and four things it was already getting wrong

Asked: *review the tree's styles, bearing in mind that editing is triggered by
an edit icon shown to the right of each file or folder, only on hover.*

The icon is the constraint rather than the subject. Fitting it turns out to be
impossible without changing what a row **is**, and the review that came out of
trying found four problems that were already there.

`completed` the day it is written: the code is in the same commit and the smoke
test that holds it is beside it.

## First, what the request implies that the row cannot do

The row is a `<button>`:

```html
<button type="button" class="row" @click="…">
  <span class="twist">…</span> <img class="icon"> <span class="name">…</span>
  <span :if="row.status" class="status">…</span>
</button>
```

**A button cannot hold a button**, and the interesting part is that the failure
is not the one you would expect. Chromium disagrees with itself about the
parse, measured three ways:

| how the markup is created | result |
| --- | --- |
| `div.innerHTML = "<button>a<button>b</button></button>"` | stays **nested** |
| `DOMParser().parseFromString(…)` | split into **two siblings** |
| `template.innerHTML = …` | split into **two siblings** |

So "does it nest" depends on how the markup got there — which is not something
to build on either way. And **jq79 uses none of those**: its compiler builds
templates with `document.createElement`, where nesting always succeeds and the
parser never gets a vote. The real failure is one step later:

```
inner.click()  →  ["edit", "row"]
```

One click on the icon, two handlers: the edit action *and* the row's own open.
`@click.stop` would paper over it, and nested interactive controls would still
be wrong for a screen reader.

**So the row stops being a button.** The `<li>` becomes the row — it carries the
hover, the selection and the three controls — and inside it are two sibling
buttons and a span:

```html
<li class="node" :class.on="…" :class.ignored="…" :attrs="{ style: `--depth:${row.depth}` }">
  <button class="row" @click="…">  <!-- twist, icon, name -->
  <span :if="row.status" class="status">
  <button class="edit" @click="…"> <!-- the pencil -->
</li>
```

They are siblings, so there is no bubbling to stop and no `.stop` modifier to
explain.

## The icon cannot simply appear, either

Letting it in and out of the flow reflows the row under the pointer. Measured
on a real row by inserting a 16px box:

```
name width before: 241px
name width after:  221px
```

Twenty pixels, on the one row somebody is pointing at, which also re-runs the
ellipsis — a name that was complete becomes truncated *because* you pointed at
it. **So the slot is always there and only its contents come and go**:
`opacity: 0` on the button, `opacity: 1` on `.node:hover`. The cost is 20px of
name on every row, permanently, which is the trade VSCode makes too.

`opacity` alone is not enough: an invisible button still takes clicks, so a
stray click at the right edge would fire an action nobody can see. It carries
`pointer-events: none` until it is revealed.

And it is revealed by the **keyboard** as well as the pointer
(`.edit:focus-visible`), because an action that exists only on hover is an
action a keyboard cannot find.

## What owned the right edge before, and why it had to move

`.status` — git's letter — claimed the right edge with `margin-left: auto`. An
icon "to the right of each file" would have been fighting it for the same
place. The fix is to stop claiming: `.row` is `flex: 1` and pushes both of them
right, so the order is simply the order they are written in. Measured on a row
that carries both:

```
name   57 → 262
status 267 → 283
edit   283 → 303      the row ends at 303
```

## The three things the review found that had nothing to do with the icon

1. **Hovering the selected row did nothing.** `.row:hover` and `.row.on` have
   the same specificity and `.on` is written second, so it won every time. The
   pointer stopped meaning anything over the one row it is most likely to be
   on. Now `.node.on:hover` mixes 14% of `--fg` into the accent, and the three
   states are measurably distinct:

   ```
   unselected           rgba(0, 0, 0, 0)
   unselected + hover   rgb(20, 22, 26)          --bg
   selected             rgb(122, 162, 247)       --accent
   selected + hover     color(srgb 0.538 0.674 0.963)
   ```

2. **There was no focus style at all.** Tabbing through the tree moved an
   invisible cursor — 21 rows, 21 tab stops, nothing on screen to say where you
   were. `.row:focus-visible` and `.edit:focus-visible` now draw an inset ring,
   in `--on-accent` on the selected row so it is visible against the accent.

3. **`ignored` dimmed the name and not its icon**, which read as a half-loaded
   row rather than as a dimmed one. It now dims the name and the icon together
   and deliberately leaves git's letter alone, because that letter is the one
   thing on an ignored row that is still news.

Also moved, while the file was open: the indent was
`padding-left: ${row.depth * 0.75 + 0.2}rem` recomputed per row into a style
attribute. It is now `--depth` and the arithmetic is one line of CSS.

## A note on the measurement, because it was wrong first

The first reading of the selected-row hover said the colours were identical and
that `color-mix` was not applying. It was the instrument: `page.click()` leaves
the pointer on what it clicked, so both samples were the hover state. The
give-away was in the number itself — the "plain" reading was already the mixed
colour, not `--accent`. Parking the pointer elsewhere before sampling gives the
table above.

That is the fifth instrument error this UI has produced in two days
(`.col-main` matching the wrong column, `requestAnimationFrame` in a headless
browser, arm order in a benchmark, a cross-machine baseline, and now a parked
pointer). They have a shape: **the page is fine and the thing watching it is
not**, and the tell each time was a number that was suspiciously round or
suspiciously equal.

## What this does *not* decide

**What the pencil does.** It opens the file in the content column today, which
is the only half of "edit" this surface can currently deliver. The other half —
whether a write from the tree goes through the job gate or around it —
contradicts a decision `luu-design.md` states in as many words:

> Read-only throughout: the file tree and the git panel are a window onto the
> workspace, not a second way to change it — every write still goes through the
> job gate.

That needs arguing with rather than routing around, and it is a record of its
own. The affordance is built and styled so that the argument is about the write
path and not about the pixels.

## And the thing that was not the styles

Asked alongside this: *the tree's selection changed, it was better before.*
`git blame` says it did not. `.row.on { background: var(--accent) }` has been
that since `c986ce2` on 2026-09-15, and `03ed7c3` touched
`inspector-files.html` by seven lines, five of them a comment, none of them the
selection or the styles. The inspector's own `background: var(--panel)` is
unchanged across that commit too.

**What changed is what `workspace.selected` means.** `03ed7c3` gave the content
column tabs, and `selectedPath` reads the *active tab*:

```js
$: selectedPath = workspace.selected?.kind === "file" ? workspace.selected.path : null
```

So the highlight now follows the tab rather than the last click — and, because
a diff sets `kind === "diff"`, **opening a change in the Git panel clears the
tree's highlight entirely** while the file is still open in a tab beside it.
That is the most likely thing being noticed, it is a behaviour change and not a
style one, and it is not fixed here because the fix is a decision: whether the
tree tracks the active tab, the last thing clicked in the tree, or every open
tab at once.

## Still open

- **The tree spends two tab stops per row now** — 21 rows became 42. The right
  answer is a roving `tabindex` over the tree with arrow-key navigation, which
  is how VSCode does it and is a bigger change than reviewing styles. Making
  the icon unfocusable was rejected instead: it would have made the action
  keyboard-unreachable, which is worse than making it far away.
- **What the pencil does**, above.
- **What the selection should track**, above.
- **The git panel's rows are the same shape and were not touched.**
  `inspector-git.html` has its own `.row` with the same `margin-left: auto`
  habit. It needs no icon today, so it was left alone rather than changed
  speculatively — but the two files now disagree about what a row is.

## 2026-09-16, later: the highlight is a tint, and it stops crossing the scale

Asked, looking at the result above: *softer, and maybe invert the colours
between light and dark.*

`.node.on { background: var(--accent); color: var(--on-accent) }` fills the row
with the accent and flips every child to `--on-accent`. Two problems with that
in a 20rem rail, and the second is the one the request names.

**It is a control's state used on content.** A filled accent means *this button
is pressed*. A selected row is something somebody picked to look at. The page
uses the same fill for both, and a rail of saturated bars reads as a toolbar.

**And `--accent` is the one colour that has to cross the scale.** It is a pale
blue on dark and a deep blue on light — the token's own comment says so about
`--on-accent`: *"the one colour that has to move against the theme"*. So the
selected row was always the brightest thing on a dark rail and the darkest on a
white one: the highlight jumped forward in both themes, in opposite directions.

**Now it is a tint of the accent over `--panel`** — `--selected` and
`--selected-hover`, a pair per theme — and the text stays `--fg`, which is what
lets the glyph, the caret and git's letter keep their own colours instead of all
turning `--on-accent`. Measured with the pointer parked off the rail, the panel
as 1:

| | dark | light |
| --- | --- | --- |
| hover, unselected | 1.08 | 1.09 |
| selected | **1.38** | **1.19** |
| selected + hover | 1.61 | 1.30 |
| text on the selected row | 9.87 | 14.14 |

Monotone in both, all four states distinct in both (asserted, not eyeballed),
and the selected row now lands just off its own panel rather than at the far
end of the scale.

**The comment written for this was wrong first and is corrected here rather
than quietly.** The first version claimed the tint is "darker than nothing on
dark and lighter on light". The measurement says the opposite —
`rgb(44,54,74)` is lighter than the dark panel's `rgb(27,30,36)`, and
`rgb(230,235,247)` is darker than white. What actually inverted is the
*direction relative to the theme*: the highlight stopped being the thing that
crosses to the opposite end, which is what the filled accent could not avoid.
The numbers were in hand and the sentence still went in unchecked, which is the
same failure as the five instrument errors above with none of the excuse.

### The git panel came with it

`inspector-git.html` had the identical `.row.on { background: var(--accent) }`.
It is the same kind of list — rows of content, picked — so it takes the same
two tokens. Leaving one rail soft and its neighbour filled would have been a
worse inconsistency than the one the previous section already noted between
these two files.

**The pressed-control fills were left alone**, deliberately: the settings rail
(`settings-modal.html`), the segmented `.choice` in `app.css` and `.which` in
`app.html` are controls, and a control that is on should say so loudly. The
line this draws is **a pressed control is filled; a selected row is tinted**,
and it is the reason the tokens are named `--selected` rather than something
about lists.

### Still open, after the tint

- **Nothing asserts the contrast ladder.** The numbers above came from a
  scratch probe, not from the suite. A test that pins "all four states
  distinct, and monotone" would catch a palette edit that collapses two of
  them, and it is four lines — not written because the right place for it is a
  palette test that does not exist yet, and inventing one for a single rail
  would be the wrong shape.
- **1.19 on light is deliberately near the floor.** It is stronger than hover
  (1.09) and reads on the screenshots, but it is the value to revisit first if
  anyone finds it too quiet on a bright display.

### One line of the section above is now stale, and this is the correction

*"`.row:focus-visible` and `.edit:focus-visible` now draw an inset ring, in
`--on-accent` on the selected row so it is visible against the accent."* The
second half went with the fill: there is no accent to be visible against any
more, so the ring is `--accent` on every row, selected or not, and the
`.node.on … :focus-visible { outline-color }` override was deleted rather than
re-pointed. The same deletion took `.node.on .glyph`, `.node.on .twist` and
`.node.on .status`, which existed only to undo `--on-accent`.
