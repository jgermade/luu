# The worker and the seam: where level 3 actually cuts in the code

**Status:** a proposal and the code it plans. It is item 3 of
[`ROADMAP/2026-09-01`](../ROADMAP/2026-09-01/README.md) — *level 3 in its
development posture* — and it is now the oldest thing on that list with nothing
in front of it.

[`the-container-decided`](2026-09-01.the-container-decided.WIP.md) settled where
the seam falls in the *design*: all tools inside the container, the context
manager and the model client outside, one enforcement point. It did not say
where that cuts in the tree, and the tree is where the decision either survives
or quietly becomes two enforcement points wearing one config file.

This record answers three questions that file left as prose: **what the seam is
in code**, **what crosses it**, and **what the container is started as**. It
also refines that record's network answer, which was written before the
container had a lifetime.

## The seam is one function

The tool loop touches the tool set in exactly one place:

```rust
// agent.rs:170
let result = tools.call(&call, sandbox).await;
```

Everything else `Tools` is used for — `definitions()`, `names()`, `is_empty()`
— is the *prefix*, not execution. That split is the whole finding:

| | stays on the host | moves into the container |
| --- | --- | --- |
| the tool **definitions** | ✔ they are bytes in the cached prefix | |
| the tool **calls** | | ✔ every one of them |

The definitions have to stay outside for a reason that is not convenience: they
are the second half of the cached prefix, byte-stable across calls and across
processes on purpose (`tools/mod.rs`). A prefix assembled *inside* the image is
a prefix that moves when the image is rebuilt, and nothing would fail — the
prompt cache would just start missing, which is the exact failure mode the
`definitions()` doc comment already warns about. So the host owns what the model
is told, and the container owns what actually runs.

Which makes the seam a trait with one method, and `Tools` its first
implementation:

```rust
pub trait Executor: Send + Sync {
    fn call<'a>(&'a self, call: &'a ToolCall, sandbox: &'a Sandbox) -> ToolFuture<'a>;
}
```

`run_agent_turn` takes `&dyn Executor` instead of `&Tools`. That is the entire
change to the loop, and it is the point: **if adding the container had to touch
the loop, the loop was wrong.**

## What crosses it: the policy, not the sandbox

The worker cannot be handed a `Sandbox`. A `Sandbox` is *resolved* — canonical
paths, open-able roots, the implicit [`SYSTEM_ROOTS`] a child needs to reach its
own libc — and every one of those facts is about the machine it was resolved on.
The container's `/usr` is the image's, not the host's.

What is portable is the thing a `Sandbox` is built *from*, and it already
exists and is already `Serialize`: `SandboxPolicy`, plus the base directory.
`Plan::narrow` is the proof that this is the right shape — narrowing a session's
sandbox for one task is already written as *build a policy, resolve it*:

```rust
Ok(Sandbox::new(&policy, session.base())?.under(Authority::Plan(task)))
```

So the wire carries `{ base, policy, authority }` and the worker runs the same
three lines. One new method makes it possible — `Sandbox::to_policy()`, the
inverse of `Sandbox::new` — and one test keeps it honest, in the same shape as
the store's `fold(record) == load(store, id)`:

```
Sandbox::new(&s.to_policy(), s.base()) grants what s grants
```

**What that inverse loses, stated rather than discovered later:** a `Root`
remembers `source`, the path *as the user typed it*, so a verdict can say
`~/.cargo` rather than `/Users/you/.cargo`. Canonical paths are all that
survives the round trip, so verdicts from inside the worker name resolved paths.
That is a readability cost and not a security one — the grant is identical — and
inside the container the resolved path is the honest name anyway, because `~`
does not mean there what it meant on the host.

**`authority` crosses too**, and it is not decoration. `Authority::Plan(id)` is
what makes a denial say *the approved plan for task 7* rather than *the sandbox
policy*, and [`narrowing`](2026-08-30.narrowing.completed.md)'s whole argument is
that those two are different runs. Dropping it at the seam would make every
denial inside the container read as a policy refusal.

## The mount, and the one decision that keeps runs comparable

**The base directory is mounted inside the container at the same absolute
path.** Not `/workspace`.

The obvious alternative is a fixed mount point with translation at the seam, and
it is wrong here for this project's own reason. Paths appear in verdicts, in
`run_command`'s `cwd`, in the model's prompt, in tool results, and in the record.
Translate them and a container run and a host run of the same script differ in
their *bytes*, which is precisely the thing every probe in `scripts/tasks/` is
built to hold constant. **"One flag apart" is the sentence the whole measurement
discipline rests on**, and a mount point that rewrites every path is a great
deal more than one flag.

The cost is that the container's filesystem has a `/Users/...` or `/home/...`
tree in it that no Linux image would otherwise have. That is a cosmetic oddity
inside a container whose entire filesystem is disposable, and it buys the
property that a probe run inside and outside the container can be diffed.

## The container is started *as* the worker

[`the-container-decided`](2026-09-01.the-container-decided.WIP.md) fixed the
lifetime — long-lived, one per session — and left open what the container's
process actually is. Two shapes:

| | |
| --- | --- |
| **a keep-alive plus `exec`** | start `sleep infinity`, then `docker exec` per tool call |
| **the worker as PID 1** | start `<runtime> run -i --rm <image> luu worker`, and speak to its stdio |

The second, and the reasons compound:

- **The container's lifetime *is* the worker's.** There is no name to allocate,
  no `docker rm` to forget, and no way to leave a container running after the
  session that owned it died. `--rm` plus a closed stdin is the whole of the
  cleanup.
- **No second lifetime to get wrong.** With `exec`, the container and the worker
  are two things that can disagree about being alive, and the failure is a tool
  call that hangs rather than one that fails.
- **stdio is already the transport this project chose.** Item 7 decided stdio,
  spawned per window, for the surface reaching the engine
  ([`how-a-surface-reaches-the-engine`](2026-09-01.how-a-surface-reaches-the-engine.completed.md)).
  This is the same argument pointed the other way — the engine reaching its
  executor — and using one mechanism for both is worth more than either choice
  is on its own. No port, no listener, no token: the pipe's authority is the
  parent's, which is exactly what an approval-carrying channel should have.

So the IPC is JSON, one object per line, strictly request/response, and the
worker is a subcommand of the same binary rather than a second crate. `luu
worker` reads calls on stdin and writes outcomes on stdout, and it is
`Tools::standard()` and `Sandbox::new` on the far side of a pipe — the same
code, not a second copy of it.

## `host`, `direct`, and a runtime by name

`runtime` is a name, not an integration, for the same reason `commands` is an
allowlist of program names rather than a plugin per program:

```toml
[worker]
runtime = "host"          # host | direct | docker | podman | nerdctl | container
image = "loude-worker:dev"
```

- **`host`** — no worker. Tools run in this process, which is every run that has
  ever happened in this repository. The default, so nothing changes for anyone
  who does not type a line.
- **`direct`** — the worker as a plain child process on this machine, with no
  container at all.
- the rest — `docker`, `podman`, `nerdctl` and Apple's `container`, which
  substitute for each other because all this layer does is build an argv.

**`direct` isolates nothing, and it is here on purpose.** It is a mode that
adds a process boundary and no security boundary, which is normally a thing to
refuse to build. The argument for it:

1. It is what makes the seam testable where there is no runtime — which is CI, and
   which is every machine that has not installed one. A seam whose only test
   requires Docker is a seam that is tested nowhere.
2. It isolates the *failure*. When a container run misbehaves, `direct` answers
   "is it the IPC or is it the container" in one flag, and that is the same
   attribution argument the development posture is built on.
3. It is not silently weaker: it isolates nothing and the verdict says so. Every
   run under it reports `worker (direct: no container)` in the same place a
   contained run reports its runtime and image.

The third point is the condition. A mode that quietly looked isolated would not
be worth the first two.

## `commands` is the image's manifest

The finding [`the-container-decided`](2026-09-01.the-container-decided.WIP.md)
named and did not build: a **third** failure mode, distinct from *denied by the
policy* and *the kernel will not hold it* —

> granted by the policy, absent from the image

The worker is the only thing that can answer it, because it is the only thing
standing on the image's `PATH`. So the handshake carries it: on start the worker
reports its protocol version, its `luu` version, and, for every command the
policy allows, whether it resolves. `luu tools` prints the column, and a session
that starts with a gap says so **before** a model finds it:

```
  commands   cargo, rustc, git, rg, ls
  worker     docker — loude-worker:dev, luu 0.1.0, protocol 1
  in image   cargo, rustc, git, ls
  absent     rg   (granted by the policy, absent from the image)
```

The version pair in that line is the other half of it. The image contains a
`luu` that was built at some point; the host is running one built at another.
Everything else in this project treats a version skew a reader cannot see as a
bug (the protocol's `v3`, the record's format `5`), and an image is the easiest
thing in the whole design to leave stale. A protocol mismatch is a refusal that
names both numbers; a `luu` version mismatch is a warning, because it is
ordinary and usually harmless.

## Network, refined

That record's answer was: leave the container's network attached and deny it per
command with seccomp, because `docker network connect`/`disconnect` "would move
by hand what the kernel already decides per call, and its window would not line
up with the task that asked for it".

That argument is about **variation**, and it stands: nothing toggles the
container's network while it is running, ever. But it was written before the
container had a lifetime, and a lifetime introduces a case it does not cover —
a session whose policy says `network = false` for the whole of it. That is not a
window that has to line up with anything. It is fixed before the container
exists and for as long as it exists.

So: **the container is created `--network none` when the session policy denies
the network, and attached when it allows it, and it is never changed
afterwards.** Level 3 draws the coarse, permanent boundary and level 2 makes the
fine cut inside it — which is the earlier record's own sentence, applied to the
one boundary that is genuinely permanent. The per-spawn seccomp filter is
unchanged and is still what denies a *task* the network inside a session that
has it.

Apple's `container` has no documented `--network none`. That is the gap the
earlier record found, and it is why this layer declares what it needs and says
what is missing rather than assuming the flags are uniform: under that runtime
the verdict reports the container as attached, and the seccomp filter is doing
all the work. It is survivable for the reason that record gives — the filter is
what actually denies — and it is *reported*, which is the part that matters.

## The development posture, as a file

The earlier record's three conditions, honoured literally:

1. **Widen `commands` and `network`; leave `enforcement` alone.** Inside a Linux
   container Landlock works, is free, and is the entire reason for the exercise.
2. **Explicit, not ambient.** The loosening is `luu.container.toml`, a separate
   file passed with `--sandbox`, never a default and never an edit to `luu.toml`.
   In three weeks nobody has to tell a default from a leftover: the file's name
   is what it is for.
3. **The trigger is a fact, not a date.** Narrow when `run_command` first runs
   inside the container with a model in the loop. That is item 6, and this
   change does not pre-empt it.

## What this does not do

- **No egress proxy.** That is item 6 and is proposed, not decided.
- **No `network: ["crates.io"]` in a plan.** Same item.
- **The image is declared, not generated.** `Containerfile` is in the tree and a
  person builds it. "The policy is the manifest" points at generating one; the
  manifest *check* is what this change buys instead, and it is the half that
  keeps the two honest without deciding who owns the image.
- **`serve` is still single-session**, so "one container per session" is one
  container. The shape is what makes multi-session safe later; it is not tested
  by anything today, because there is nothing to test it with.

## Still open

- **The IPC carries approvals across a trust boundary inside one machine**, and
  it is unauthenticated because a pipe's authority is its parent's. That is
  correct for a spawned child and is exactly the question signed approvals
  answer for the network. It becomes a real question the day the worker is
  attached to rather than spawned.
- **Whether Apple's kernel has Landlock**, unchanged from the earlier record and
  still one command.
- **A tool call has no timeout at the seam.** `run_command` has its own clock
  inside the worker, but a worker that dies mid-call leaves the host waiting on
  a pipe that will never answer. Today that surfaces as a read of EOF, which is
  an error rather than a hang — but a worker that is *alive and stuck* is not
  covered, and the honest place for that clock is here rather than in each tool.

## What building it found, appended the same day

Two things the proposal above did not have, both discovered by the policy
failing to load rather than by thinking harder.

### `[[worker.paths]]`, because a policy has to resolve on *both* sides

The section above says the policy crosses and the far side resolves it. That is
true and it is not sufficient. The image's toolchain is at `/usr/local/cargo`;
the machine starting the container is a Mac, where there is no such directory —
and `Sandbox::new` **refuses to load a policy naming a path that is not there**,
deliberately, because a rule that silently did nothing is worse than one that
fails.

So the first `luu.container.toml` could not be read by the host that was meant
to start the container. The fix is a third block, and its existence is the
finding:

```toml
[[worker.paths]]        # resolved on the far side only
path = "/usr/local/cargo"
access = "execute"
```

These are added to every sandbox that crosses and are never resolved here. They
are `SYSTEM_ROOTS`' cousins in what they are *for* — the furniture a command
needs in order to run at all — and unlike them in being declared rather than
fixed.

It is also the concrete case for the whole "send the policy, not the sandbox"
argument, which until this point was a claim about portability with no example
attached. `~/.cargo` on a host and `/usr/local/cargo` in a Debian rust image are
**the same grant**, and exactly one of them survives canonicalization. A design
that shipped resolved paths would have had to invent this block anyway, and
would have had to invent it as a translation table.

### The worker runs as whoever started the session

Not in the proposal at all, and it is a correctness bug rather than a nicety.
The base is bind-mounted, so a container running as root writes **root-owned
files into the person's own checkout** — and `writes` in an approved plan is
what the mount is *for*. A gate that grants a write and then hands back a file
its owner cannot edit has granted nothing.

So the spec carries a uid/gid, defaulting to `getuid`/`getgid`. And it is the
second thing this layer has found that is not uniform across runtimes:
`--user uid:gid` for Docker, Podman and nerdctl, `--uid` and `--gid` separately
for Apple's `container`. Two spellings of one idea is exactly the shape this
layer exists to absorb — the first being `--network none`, which Apple's runtime
cannot say at all.

### What is built, and the line the roadmap keeps

The seam, the worker, the IPC, the runtime layer, the manifest check, the image
and the posture file. Every one of them exercised under `direct`, in seven tests
that need no runtime installed — including the one that matters most, that a
contained call and a host call answer the same bytes for an allow, a denial, and
a tool that does not exist.

**No container has been started yet.** `Containerfile` has never been built and
no tool call has run inside the image it describes. That is the same distinction
item 1 of the roadmap keeps about a real `llama-server`, and it is kept for the
same reason: a test against a stub proves we send what we think we send, not
that the other side agrees. The first real `docker build` belongs with the
machines, and the thing to check first is whether Landlock inside the image
reports the ABI the host's VM advertises.
