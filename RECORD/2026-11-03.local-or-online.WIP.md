# Local or online: what setup.sh asks, and `luu setup`

**Status:** proposal, built in the same change; verified as far as a machine
without systemd running reaches, which is said at the end.

> quizá tendría sentido que setup.sh pregunte el modo de instalación
>
> Ok, local o servidor y luu setup, dale
>
> llamémosle local o online, creo que es más coherente

## What is true today

`setup.sh` installs one binary into `~/.local/bin`, with no root. It asks
nothing except *install, reinstall or uninstall* when it finds a binary.
Getting from there to a public server is several steps, all by hand:

- write `[server]` in `config.toml`: `exposure = "public"`, `bind` and
  `origin`, and no `token-file`;
- `luu user add <email> --role owner`, then `luu user code`;
- run `luu serve` as a service, under a user of its own, with a policy file;
- restart it whenever `[server]` changes.

Docker and the chart have the same middle steps, through `docker exec` or
`kubectl exec`.

## The proposal

### Two modes, asked after *install*

```text
How will luu run here?
  [1] local    for you, on this machine: luu serve on 127.0.0.1, no login
  [2] online   for people who log in: a service, exposure = "public", an
               origin, the first owner and their code      (Linux, systemd)
```

- **local** is today's install, unchanged. It is also what the script does
  with nobody to ask, and on any machine without systemd.
- **online** needs root. Like intergate's installer, it runs single steps as
  root (`as_root`: sudo where the script is not root already), so `curl … | sh`
  stays the line. It does five things:
  - installs the binary into `/usr/local/bin`, where a service user can run
    it;
  - creates a system user `luu`, whose home `/var/lib/luu` is the state
    directory (`LUU_HOME`), with `work/` under it as `serve`'s root;
  - writes `/etc/luu/luu.toml`, a policy granting `.` (the session's folder),
    only when there is none;
  - asks for the origin and the owner's email, and runs `luu setup` with them
    as user `luu`;
  - writes `luu.service` (hardened: `ProtectSystem=strict`, `ProtectHome`,
    `PrivateTmp`, `NoNewPrivileges`, writable only in `/var/lib/luu`), then
    enables and starts it.
- `--mode local|online` (`LUU_MODE`), `--origin` and `--owner` say the same
  without asking, which is how CI walks it.
- **An online install is recognised afterwards by its unit.** `reinstall`
  replaces `/usr/local/bin/luu` and restarts the service. `uninstall` stops,
  disables and removes the unit and keeps `/var/lib/luu`. `--purge` deletes it
  and the user as well.
- **No TLS.** luu binds `127.0.0.1:7878`, and the script prints the one line
  that puts Caddy in front: `caddy reverse-proxy --from <host> --to
  127.0.0.1:7878`. Installing a proxy is not this script's business.

### `luu setup`: the step all three ways share

```sh
luu setup                                     # asks, on a terminal
luu setup --origin https://luu.example.com --owner me@example.com [--bind ADDR]
```

1. **Writes `[server]`**: `exposure = "public"`, the origin, and the bind. The
   bind defaults to `127.0.0.1:7878` on a machine and `0.0.0.0:7878` inside a
   container. It drops a `token-file`, which `public` refuses. Everything else
   in `config.toml` is carried through, the way every Settings write carries
   it.
2. **Makes the owner**: added, or raised to owner, or let back in if
   suspended.
3. **Prints a code** for them, and says that `luu serve` reads `[server]` when
   it starts, so it has to be restarted.

The same command is the online step everywhere:

| | install | the first owner |
| --- | --- | --- |
| online | `curl … \| sh`, *online* | the script runs `luu setup`, then starts the service |
| Docker | `docker run …` | `docker exec -it luu luu setup`, then `docker restart luu` |
| Kubernetes | `helm install …` | `kubectl exec -it deploy/luu -- luu setup`, then `kubectl rollout restart deploy/luu` |

On a terminal, `luu setup` asks whatever no flag said. Without one, a missing
answer is an error that names the flag.

## What it costs

- **A script that runs steps as root.** Each one is named before it runs, and
  none is run without the person choosing *online*.
- **A unit file luu now owns**, kept to what systemd guarantees on any distro
  of the last few years.
- **`useradd` and `runuser`**: util-linux and shadow, on every systemd
  distribution.

## Rejected

- **The script driving Docker or Helm.** For Kubernetes it would act on
  whichever context `kubectl` has current, a cluster chosen for the person
  from a pipe. Docker needs root or the `docker` group. And either way it
  wraps one command the landing already shows. The step that is *not* one
  command, the first owner, is what `luu setup` gives all three.
- **`luu setup` reading `/dev/tty` under `runuser`.** The script asks the two
  questions itself, on the terminal it already asks on, and passes flags. A
  child run as another user then needs no terminal of its own.
- **launchd for macOS online.** Nobody asked for it, and a Mac serving people
  is the exception. *online* is Linux with systemd, and macOS is told so.
- **"server" as the name.** Jesús: *local or online*. It names who reaches
  luu, not what kind of process it is.

## Still open

- **A second code without the long line.** On the machine it is
  `sudo -u luu env LUU_HOME=/var/lib/luu luu user code <email>`, which the
  script prints. A `luu` wrapper that knows the service's home would shorten
  it.
- **Email (step 2 of users)** makes the code arrive on its own, and the
  restart after `luu setup` is still needed until `serve` reads `[server]`
  again on its own.

## Built, the same day

All of the above is built. The only names it gained are `--mode`, `--origin`
and `--owner`, beside `LUU_MODE`.

**Found while building:**

- **`as_luu` needs a fallback.** As root it is `runuser -u luu`. As anyone
  else it is `sudo sudo -u luu`: root's sudo, then the user's. A plain
  `sudo -u luu` would ask the person for a password they may not have for that
  user.
- **The binary has to move before anything is downloaded.** The menu asks
  install, reinstall or uninstall against `~/.local/bin`. An online install
  then lands in `/usr/local/bin`, so the mode is asked between the menu and
  the download.

**Verified here:**

- **`tests/server_config.rs`**, through the binary:
  - without a terminal, a missing `--origin` is an error that names it;
  - `luu setup` turns a private `config.toml` public, drops `token-file`, and
    keeps `[sessions] max-live = 2`;
  - its code logs the owner in on the server that file describes;
  - run again for an existing user, it raises them to owner.
- **An online install, walked here.** This container has no systemd running,
  so `systemctl` was a stand-in that logs what it is asked and starts the
  unit's `ExecStart` as its `User`. Everything else was real:
  - the user `luu` and `/var/lib/luu` (`0750`);
  - `/etc/luu/luu.toml`;
  - `luu setup` run as `luu`, so `auth.db` is `0600` and `luu`'s;
  - the unit written, and `serve` answering `{"users":true}`.

  Then `reinstall` replaced the binary and restarted the service, and
  `uninstall --purge --yes` left no unit, binary, `/var/lib/luu`, `/etc/luu`
  or user.
- **`scripts/setup-check.sh`** still passes every local step against a build.
  Its new online steps are skipped here, as they will be anywhere without
  systemd and a sudo that asks nothing.
- **The landing**, at 375 and 1280: each tab shows its commands, nothing is
  wider than the screen, and the console is empty.

**Not verified:**

- **The online steps against a real systemd.** `setup-check.sh` walks them
  wherever systemd runs and sudo asks nothing, which is the `binary` job's
  Ubuntu runners: install, `/api/auth/me.json` answering `users: true`,
  `auth.db` `0600` and `luu`'s, reinstall restarting the service, purge
  leaving nothing. That is CI's first run.
- **The hardening under real systemd**: whether `ProtectSystem=strict` leaves
  `serve`, its engines and its commands everything they need.

## Appended 2026-11-03: CI's first run of online, and what it found

The `binary` job ran `setup-check.sh` on Ubuntu (x86_64 and arm64) with a real
systemd. **luu.service started as written**: `active (running)`, the sandbox
it printed, `users — /var/lib/luu/auth.db (1 of them)`, and serving on
`127.0.0.1:7878`. So `ProtectSystem=strict` and the rest of the hardening
leave `serve` what it needs to start.

**Two failures, both from my own changes:**

- **The check asked `curl -f`**, and `/api/auth/me.json` answers `401` with
  `{"users":true}` when nobody is logged in, which is what this record
  designed. The check now reads the body and ignores the status.
- **A local install created `~/.local/bin` as root**, on macOS too. `in_dir`
  went to root wherever `DIR` and its parent did not exist yet, which is
  every first install. On a runner, sudo asks nothing, so the directory was
  made root's and the cleanup could not delete it. On a laptop, sudo would
  have asked for a password nobody expected. So **local never asks for root**:
  a directory it cannot write is an error, as it always was. Online asks for
  root only where the nearest directory that exists is not the user's to
  write.
