# The floor on 6GB: it doesn't break, it offloads — and 8K was never the number that mattered

Machine 5 from [`machines.md`](../ROADMAP/2026-09-01/machines.md) — i5-9400F, GTX
1660 SUPER, 6 GB VRAM, driver 610.57.04, CUDA 13.3, compute 7.5 — is the only box
in the inventory that can falsify the project's stated target of 7B–32B at
8K–32K. This is that run.

## Setup

`ollama-cuda` 0.33.3 from the CachyOS repo (pulls the system `cuda` package as a
dependency, unlike upstream's binary which vendors its own CUDA libs).
`qwen2.5-coder:7b`, Q4_K_M, 4.7 GB on disk. Tokenizer fetched as AGENTS.md
describes. `luu` built in release. `OLLAMA_KEEP_ALIVE=30m` set before `ollama
serve`.

At server start, before any model loaded, Ollama's own log:

```
inference compute ... library=CUDA compute=7.5 name="NVIDIA GeForce GTX 1660 SUPER"
total="5.6 GiB" available="5.1 GiB"
vram-based default context: total_vram="5.6 GiB" default_num_ctx=4096
```

This machine runs a desktop (Hyprland + noctalia, Wayland) that shares the same
GPU: the compositor alone holds 360–460 MiB of VRAM, and that figure moves
between runs. Ollama's own default context for this card is **4096, not 8192** —
half the project's stated target — computed from VRAM alone, before a single
token of conversation exists.

## The sweep: `--context-limit` against the CPU/GPU split

`luu chat "hola" --backend ollama --model qwen2.5-coder:7b --context-limit N
--tokenizer ...`, reading `ollama ps` after each load (`PROCESSOR` column is
`CPU%/GPU%`):

| `--context-limit` | loaded size | split (CPU/GPU) |
| ---: | ---: | --- |
| 8192 | 5.4 GB | 18% / 82% |
| 4096 | 5.1 GB | 13% / 87% |
| 2048 | 5.0 GB | 13% / 87% |
| 1024 | 4.9 GB | 10% / 90% |
| 512  | 4.9 GB | 10% / 90% |
| 448  | 4.8 GB | 10% / 90% |
| 400  | 4.8 GB | 10% / 90% |
| 384  | 4.5 GB | **100% GPU** |
| 256  | 4.5 GB | 100% GPU |

The cutover sits between 384 and 400 tokens of *configured* window — not actual
conversation length. Re-running the same sweep a second time moved the cutover
by a factor of five (a first pass never reached 100% GPU even at 256): the
desktop compositor's own VRAM footprint is not constant, so **the exact floor is
not a fixed number on this machine, it's a range that depends on what else is
drawn to the screen at load time.**

## The split is fixed at load, not at use

Ran `long-session.txt` (6 turns, designed to grow a real conversation) at
`--context-limit 8192` while polling `ollama ps` and `nvidia-smi` once a second
for the whole run. The split was **18%/82% before the first token and 18%/82%
after the last**, VRAM used flat at 4658 MiB throughout. Ollama reserves the KV
cache for the full `num_ctx` at model load, not incrementally as history grows —
so a session that only ever uses 1 868 of its 8 192 tokens (the actual total by
turn 6) pays the same VRAM cost, and the same split, as one that fills the
window. The number that decides the split is the flag, never the conversation.

## What the split actually costs

The obvious next question — does 18% on CPU mean the turn takes noticeably
longer — turned out to have a boring answer. Same prompt, `ollama run --verbose`:

| config | eval rate |
| --- | ---: |
| ctx 256, 100% GPU | 35.67 tok/s |
| ctx 8192, 18%/82% CPU/GPU | 35.44 tok/s |

Under 1% apart. `llama.cpp`'s layer-wise offload puts the *cheap* layers on the
CPU and keeps the expensive ones on the GPU, and an i5-9400F is fast enough
relative to a 7B at Q4 that offloading a fifth of the layers is inside the
noise. This is specific to *this* ratio — nothing here says a 32B, or a card
offloading 60%+ instead of 18%, behaves the same way, and nothing here measures
prompt-eval (the number that matters for a long attached fragment) rather than
decode.

## The verdict

The stated target — 7B–32B at 8K–32K — does not *fail* on this card at the 7B
end. It degrades gracefully: some layers move to CPU, and on this pairing that
costs nothing measurable. **The number that actually falls is not "does 8K
work", it's "does 8K mean what it means on a card with room to spare"** — no,
because this box can never give a 7B 100% GPU residency at any context length a
real conversation would use for more than a couple of turns, and because it
shares the card with a desktop that changes the available headroom between one
load and the next. A recording made on this machine at `--context-limit 8192`
is a recording made on a partially-offloaded model, silently, unless `ollama ps`
was checked at the time — the same category of problem `AGENTS.md` already
flags for `usage.prompt_tokens` on OpenAI-compatible servers, one layer lower.

## What this cannot answer, whatever it says

- **One model, one quantisation, one card.** Nothing here says where a 14B or a
  32B breaks — the inventory table already expects 6 GB to be `7B at the edge`
  and nothing bigger.
- **Decode only.** Prompt-eval under partial offload — the number that matters
  once a fragment or a map is attached — was not measured here.
- **Not the fold.** This is a hardware capacity question; whether folding still
  loses answers under partial CPU offload is
  [`the-grounded-fold-probe`](2026-08-27.grounded-fold-probe.completed.md)'s
  question, on this machine, unrun, and running the grounded pair here would
  measure the machine rather than the fold — the exact thing
  [`machines.md`](../ROADMAP/2026-09-01/machines.md) says not to do.
- **A desktop machine, not a server.** Every number above has a shared-GPU
  asterisk on it that a headless box would not carry.
