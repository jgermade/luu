# The gate: who proposes, who approves, and the protocol frozen around it

**Status:** plan, then code. Follows
[`2026-08-30.tasks-in-code.md`](2026-08-30.tasks-in-code.md), which built the
task, the fold and the measurement, and left the confirmation itself as a thing
only a script could give. Closes two of its *Still open* rows.

## The problem

A task is confirmed before anything runs — that is the whole design, and today
the only confirmation that exists is a line in a file. `## task:` works for a
recorded baseline and is useless for a person: there is no way to *see* what the
agent is about to do and say no.

Which is also why protocol v1 is still unfrozen. The last record refused to
freeze it around a `ClientMessage::ApproveTask` nobody had ever sent. That
refusal has an expiry date, and this is it.

## Who proposes

The design says the agent does: *the user asks for something → the agent
proposes a plan: steps, files it will touch, commands it will run → CONFIRMATION*.
So a prompt arriving with **no live task** buys one extra model call — the
planning call — whose answer is parsed for a fenced block, exactly the way a
tool call already is:

```plan
{"objective": "add a --dry-run flag",
 "steps": ["read the CLI", "add the flag"],
 "files": ["crates/luu/src/lib.rs"],
 "commands": ["cargo"]}
```

Same shape as `parse_call`, same reason: how a model expresses a plan is a
transport detail — a fenced block today, a GBNF grammar next — and the loop must
not care which.

**Where the instruction goes matters more than what it says.** It is fused into
the current user message, never added to the system block: the prefix is the part
the cache reuses, and a planning instruction that lived up there would be paid
for on every call of every turn, including the ones that never plan.

**A model that proposes nothing still gets a gate.** A 7B will often answer the
planning call with prose. Then the proposal is the user's own prompt as the
objective, with nothing declared, and the panel says the model did not declare
one. It degrades rather than failing — the same posture as the approximate
counter — and the user is still the one who says go.

## Who approves

The client, over the socket: `approve_task`, `reject_task`, `close_task`,
`reopen_task`. Between the proposal and the approval **the prompt is held and
nothing runs** — no turn, no tool, no model call.

A rejection is kept, not erased. `TaskState::Rejected` is a real state and the
task stays in the session with its plan: *this was proposed and refused* is worth
more than a gap, and ids are handed out by position, so removing one would make
the next collide with it. Reopening a closed task and refusing a proposed one are
the two edges of the same commitment — nothing in a session is deleted, only
folded differently.

## What the UI does with it

Two pieces, and the second is the one the design asked for by name:

- **The gate panel**: objective, steps, files, commands, Approve and Reject. The
  composer is disabled while a proposal is pending, because a second prompt
  during a confirmation is a second thing nobody approved.
- **The transcript collapses a closed task to its summary** — the view collapsing
  exactly what the context collapses. Collapsed *by default and expandable*: the
  default view is what the model will see from now on, and opening it shows what
  it no longer does. A debug client that could not show the difference between
  those two would be hiding the one thing this design is about.

## Freezing v1

Now, and here is what makes it different from freezing it last time: every
message below has been watched being sent by a client and answered by the server,
rather than imagined from the shape of the ones next to it. This, over a real
socket, before the freeze went in:

```
<- hello                    -> prompt
<- turn_started (task null) <- ended            the planning call
<- task_proposed            -> approve_task
<- task_approved
<- turn_started (task 1)    <- ended            the work
-> close_task               <- task_closed
```

And in a browser: the gate panel rendering the parsed plan, the composer shut
behind it, a prompt forced past the disabled input changing nothing (the hold is
the server's, not the page's), and the closed task collapsing to its summary with
its turns one click away. `ClientMessage` is
`prompt`, `cancel`, `approve_task`, `reject_task`, `close_task`, `reopen_task`;
`ServerMessage` is the eleven the server emits. A change that breaks a reader
bumps `VERSION` from here on, and the record format bumps with it.

`turn_started` carrying its task is the last field to go in before the freeze,
and it went in with the fold.

## What it costs

- **One model call per task**, before the first turn of it. Prefix-preserving by
  construction — the instruction is in the user message, so the cached prefix
  survives it — but it is a call, and on a local 7B a call is seconds. It buys
  the only thing that makes an approval informed, and it is the same trade Cline
  makes for `createTask`.
- **A gate on a question.** A session is a sequence of tasks, so "what does this
  do?" is a task too, and it costs a planning call and a click. Auto-approving
  the ones that declare nothing was rejected: an empty plan is not a narrow one
  while the plan does not narrow the sandbox, so it still runs with everything
  the policy file grants.
- **A rejection has no reason attached.** The user's next prompt is the feedback,
  and the agent can propose the same plan again. A `reason` on the wire is the
  obvious fix and it waits until someone has been annoyed by it.
- **The planning exchange stays outside the fold** in the transcript: it was
  never in the history either, so folding it under the task would be the view
  claiming a symmetry the context does not have. It also means the raw plan block
  stays visible, which is worth the noise in a client whose job is showing what
  the model actually said.
- **The CLI is still ungated.** `chat "prompt"` runs one turn with the policy
  file as the standing approval, exactly as before — there is no human loop in a
  one-shot to gate. Scripts keep their written approval. Only `serve` has a
  person in it, and that is where the gate went.

## What was rejected

- **Auto-approving a plan that declares nothing.** Rejected above, and it is the
  same argument the tasks plan used against `--auto-approve`.
- **Proposing from a template instead of a model call.** Cheaper, and it makes
  the plan a restatement of the prompt rather than the agent's own reading of it
  — which is the part the user is being asked to check.
- **Approval as an HTTP endpoint** rather than a socket message. The socket is
  the thing every client already speaks, and a second way in is a second thing to
  version.
- **Hiding a closed task's turns outright.** It matches the prompt exactly and
  makes the instrument worse; collapsed-and-expandable is both readings.

## Still open

| Question | Precondition |
| --- | --- |
| The approved plan *narrowing* the sandbox for its task | met: the human who can widen a plan that forgot a file now exists |
| A reason on a rejection, and the agent proposing again in its light | someone being annoyed by retyping |
| Who else may close a task: exit codes first, then a judge in shadow mode | thirty closed tasks, and a real model |
| A follow-up prompt inside a live task that needs a file the plan never named | narrowing, which is what makes it a refusal rather than a nothing |
| The planning call against a real 7B: does it produce a plan worth reading? | a real model |
