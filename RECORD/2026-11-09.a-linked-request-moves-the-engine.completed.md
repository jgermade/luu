## (b) The model a linked request names

### The problem

`/api/infer/<provider>/to/<path>` passes a linked luu's request to one of
this luu's providers, its engine started and its key added. It resolved the
provider with no model, so `engines::for_run` started the engine on its
table's model whatever the request asked for. At home, a session that picks
another GGUF moves the engine onto it; online, picking the same model for
`gpu@casa` sent the request to whatever the engine had loaded, and
llama-server answers with that model, not an error.

### The proposal

Read the body before anything is sent — a model call is JSON, capped at
64 MiB — and take its `model` when the provider's engine may be moved onto it:

| Engine | Moved onto |
| --- | --- |
| llama.cpp, mlx | a catalog reference (`luu:…`, `ollama:…`, `huggingface:…`) |
| Strata | a Strata id, by the same check the engines page uses |
| Ollama | nothing: it serves every model it has |
| none | nothing |

and only one the profile has not switched off (`Profile::offers`). Anything
else resolves as before, on the table's model, and the request still goes
through. `engine_model_named` is that table.

### What it costs

The request body is buffered instead of streamed. A model call's body is
small next to its answer, which is still streamed.

A linked luu can now start this machine's engine on any model the catalog has
and the profile has not switched off. That is what a session here can do from
the picker; a model to keep from peers is switched off on the profile, or the
provider withheld (`offer = false`).

## (a) Links without a restart

### The problem

The SSH listener was decided once: `[server] ssh` read when `serve` started.
Remote access said *set it in `config.toml` and restart `luu serve`*. Four
fields of the router's state — the links, the dial info, the port, the peer
keys — were `Option`s fixed at start, and three things were wired to them
once: the relay socket, the router a peer's channels reach, and the
`/api/infer` router a linked luu's channels reach.

### The proposal

The links always exist, empty until a luu links: a `Listener` holds them, the
peer keys on a luu without users, and the listener's info and port in a
`OnceLock`. The relay, the peer router and the infer router are wired to the
links at start, listening or not. Only the bind is late:

- `start_links` binds and fills the `OnceLock`: at start when `[server] ssh`
  says, and from Remote access.
- `POST /api/peers/listen {ssh}`, behind the same gate as `PUT /api/peers`:
  an address that does not parse is 422; one that cannot be bound is said and
  **nothing is written**; once bound, `[server] ssh` is written so the next
  start does the same. A luu already listening answers 409: moving the port
  would drop every luu linked in.
- Remote access shows the address (`0.0.0.0:2222`) and *Take links* where it
  said *restart*.

`AppRouterState::links()` answers `None` until the listener is on, so every
site that read the old `Option` reads the same thing it did. The one
difference is a message: a relay asked for an unlinked peer on a luu that
takes no links says *no luu named … is linked now* instead of *this luu
accepts no links*.

### What was rejected

- **Restarting the listener on a new address.** Above.
- **Starting it on every config write that adds `[server] ssh`.** A file
  written by hand while `serve` runs is not otherwise read, and a listener that
  appears because of an unrelated save would be a surprise.

## Still open

- **Stopping the listener.** Remote access starts it; removing `[server] ssh`
  still needs a restart to take effect.
- **On a server with users**, *Take links* is the same route and starts the
  relay with it; the page shows the form on a luu without users only, as the
  section it is in always has.
