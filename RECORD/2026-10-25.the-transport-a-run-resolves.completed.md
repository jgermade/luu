# The transport a run resolves

A session sent our fenced preamble and a model copied it into a malformed
call — a ```` ```tool ```` block with one `}` missing — which parsed as
`NoCall`, so nothing ran and the card said *not run*. Settings showed
`· native tools`. Both were true of different things: the file's **profile**
said native; the **model's entry** said fenced, and the entry wins.

## The problem

`provider.rs` resolves a transport with an order the design already states
(`luu-design.md` §*A model's exceptions live under its profile*): a flag, then
the model's entry, then the profile, then the backend's default. `fenced` is
the default for everything but Anthropic.

Two facts made that order invisible:

- **The Models list read the profile's key alone.** `models.html` drew
  `· native tools` from `providers[name]['tool-calls']`, so a per-model entry
  saying `fenced` changed what every turn would send and nothing on the screen
  moved.
- **The form writes those entries for a reason that is not the person's.** A
  model the probe says has no tools gets `tool-calls = "fenced"` written down
  on save — `ModelEntry::tool_calls` says so in its own doc, *"written by the
  provider form from what the server said of the model's tools"* — and the
  profile is set to native whenever *any* listed model takes tools. So the
  file can end up saying native at the provider level and fenced for the model
  a run actually uses, with nobody having chosen either.

That is how a person ends up reading `· native tools`, sending our fenced
preamble, and watching a model reproduce it badly. The malformed call is the
model's; the surprise is the screen's.

## The fix

**The row shows what a run resolves.** `transportOf(name)` is the default
model's entry, else the profile, else the backend's default — the runtime's
own order — and `· native tools` is drawn from that. When any entry disagrees
with the profile, the row says `· per-model tools` in the warning colour with
a title naming `-m` as the thing that resolves it. The list stops summarising
one key and starts reporting the answer.

Nothing about resolution moved: the order is right, and it is what lets a
model that takes no tools ride a profile that does. The context modal's
`tools` row (added the same day) is the per-turn counterpart: it reads what
the turn actually sent, not what any file says.

## What was rejected

- **Removing per-model entries on read.** A view that rewrites the person's
  file is a view that can be wrong loudly; and the entries are load-bearing —
  the next `chat` resolves without asking a server.
- **Hiding the profile key.** A provider-level transport is a real default
  for every model without an entry, and the summary is useful when no entries
  exist. It is only a lie when something overrides it, and that is what the
  marker says.
- **Changing the precedence.** Entry over profile is the whole point of an
  exception table; the bug was that the screen spoke only for the profile.

## Still open

- **The probe can be wrong, and the file remembers it.** A provider whose
  `/models` reports no capabilities — DashScope's compatible mode, in the case
  that produced this — can lead the form to write `fenced` for a model that
  does native calls perfectly well. The row now shows the consequence, not the
  cause; whether the form should stop *persisting* a derived transport (and
  resolve it per run instead) is a decision this record does not take.
- **A session pins its transport when it is created.** A profile edit does not
  move a live session; a new one or *Continue here* re-applies. The Context
  modal's `tools` row answers for the turn in front of you, and the Models row
  now answers for the next run — nothing yet says the two disagree.
- **The settings smoke has no fixture for this.** Its fake server lists model
  names without capabilities, so every model is `unsaid` and no entry is
  written; the marker's own path is exercised by hand, not by a test.
## Same day — the picker says it per model

The Models row fixed the provider; the place a person actually *picks* a model
still spoke only for the profile. `provider-models.html` — the chat's dropup
and the new session's dialog — now draws, beside each model's name, a **plug**
for `native` (the request's own `tools` field) and **braces** for `fenced`
(text in the prompt), resolved per model in the runtime's order. `fenced` is
the default and stays muted; `native` is the exception and takes the tools
bucket's colour. The provider column's summary stopped reading the profile's
key and asks the same function for the profile's default model.

Two symbols joined the page's sprite (`i-tools-native`, `i-tools-fenced`), so
the gate's sprite assertion moved from 28 to 30 — it is a count on purpose, and
a new icon is a thing it should notice.

## Same day — the mixed reply

A fenced session with a model whose training keeps winning produced one reply
that mixed everything: a fenced `list_dir`, then four `<tool_call>` blocks, a
fenced `run_command`, a fenced `list_dir`, and two `<tool_call>` bodies that
had lost characters. Nine blocks; three ran.

**Two independent defects, both in the readers.**

- **`<tool_call>` was not a call form.** The loop found the JSON inside it by
  accident — the bare-object scan looks at every `{` — so it *executed* those
  blocks, while the page's bare scan wants `{"name"` at the start of a line
  and did not, so the tags showed in the chat. The two readers disagreed about
  what a call was, which is the one thing they may not do.
- **The scan took the next fence anywhere, not the next call.** `parse_calls`
  asked for the first fence in the *whole* remaining text, so the fenced
  `run_command` six blocks later shadowed the four tags before it: the scan
  jumped from call 1 to call 6 and never looked in the gap. The page paired
  its own reading of the gap against the three calls that ran, so the cards
  shifted: a `read_file` result drawn on the `run_command` card, and *not run*
  on calls that had never been asked of the loop.

**The fix** is in both readers, and it is one rule: the earliest call of any
form — fenced, tagged, or bare — and a body that does not parse is text, not a
call, and does not consume one that ran. `tools::first_call` is now
`min_by_key` over the three readers; `segments.js` searches for `<tool_call>`
beside its fences and its line-start objects and keeps a malformed block
visible whole.

**What it costs.** Text order lets go of the old fence-first precedence in one
case: a bare object quoted in prose before a fence now runs as well as the
fence, where before only the fence did. That is the same judgement that runs
every fence a reply carries — what the model wrote, in the order it wrote it —
and the probe's `ContinuedPastFence` still counts a call followed by prose as
the waste it is. `score_call` reads a tagged call as `Parsed` through its bare
fallback and stays neutral on text after `</tool_call>`; a malformed body is
still `NoCall`, so it still earns no schema retry — the gap the earlier record
names.

**Verified**: the same reply now runs seven calls in order (`list_dir`,
`read_file` × 2, `list_dir` × 2, `run_command`, `list_dir`) and leaves the two
malformed bodies as text; on the page, seven cards in the same order, the
valid tags gone, the malformed bodies still visible, no console errors.

**And the one denial in it is not this.** `run_command` came back
`denied · the kernel cannot hold this child (landlock and seccomp are
Linux-only, and this is macos); grant it anyway with enforcement =
"best-effort"` — the platform, at the approval or without one. `best-effort`
runs it unheld and says so; Linux and the container posture hold it.
