## The finding: the gate has never met a model

The entire argument for `writes`, and for the gate having *add read* / *add
write* fields at all, is one sentence in
[`2026-08-31.what-a-plan-writes.completed.md`](2026-08-31.what-a-plan-writes.completed.md):

> the first real editing task against a 7B: it will propose a plan with `files`
> and no `writes`, try to edit, and be denied by its own plan.

**Nobody has seen that happen.** Everything verified for the gate, for narrowing
and for `writes` was mock-backed or driven by hand:

```
2026-08-31.what-a-plan-writes.completed.md:152   "all three were run end to end against the mock"
2026-08-30.narrowing.completed.md:96             "against the mock, which is in this change's checks"
```

The one real-model exercise of a *proposed* plan is in
[`2026-08-27.the-m4-pro-run.completed.md`](2026-08-27.the-m4-pro-run.completed.md), on a branch that
was never merged, before narrowing existed.

And unlike the fold, there is nothing that says how to ask it. That asymmetry is
the whole point of this section: the fold question got answered because
[`2026-08-27.grounded-fold-probe.completed.md`](2026-08-27.grounded-fold-probe.completed.md) wrote
down what to run, what a right answer contains, and how to tell two failure modes
apart — *before* anyone ran it. The gate's equivalent question exists,

| The planning call against a real 7B: does it produce a plan worth reading? | a real model |

— in [`2026-08-30.the-gate.completed.md`](2026-08-30.the-gate.completed.md), and has sat there
unmoved while the fold's got answered twice. The difference is not the machine.
It is that one had a protocol and the other has a table row.

A protocol for it has to separate, at minimum:

- **the model never declared a write** from **the model declared one and `narrow`
  refused it wrongly** — the same two-failure-modes discipline the fold probe used
- **a plan naming a file that does not exist yet.** The nearest-existing-ancestor
  rule is the widest thing in #8, and it has only ever been exercised by hand
  against `/tmp`
- **how often a person had to amend a plan before approving it.** The amend rate
  *is* the cost of the gate, and it is the number that says whether a 7B can be
  planned with at all

## Pending, grouped by what blocks it

### Blocked on nothing

Each verified against the code today, not against the record that asked for it.

- **Eviction as a recorded event.** No `Evicted` anywhere in the tree; the floor
  is in-memory and a recording still cannot say what a session forgot. It is now
  the oldest unpaid debt by a wide margin — asked for in
  [`cline-openhands`](2026-08-27.cline-openhands.completed.md) with the precondition
  *"nothing — it is small"*, repeated in
  [`tasks-in-code`](2026-08-30.tasks-in-code.completed.md), repeated again in
  [`state-of-play`](2026-08-30.state-of-play.completed.md).
- **Relevance selection**, `tree-sitter` tags over a reference graph. No
  `tree-sitter` dependency in any `Cargo.toml`. The only unbuilt piece of step 2
  and the project's stated differentiator.
- **Reading the context window from the backend**, instead of `--context-limit`
  being a flag someone has to set right.
- **Sessions in SQLite.** No sqlite dependency; `serve` still loses the
  conversation on restart. Must be derivable from the event stream, not a second
  truth beside it.
- **Pruning tool results** out of the history. No `prune` in `context.rs`.

### Narrowing, what is left of it

- **`network` and `enforcement`.** `Plan` is `steps`, `files`, `writes`,
  `commands` and nothing else, so a task still inherits both from the policy file.
- **Whether `writes` should bound `run_command`.** A child can write whatever the
  task's roots allow, and a plan's `commands` list says nothing about paths.
  Narrower than it was, and still the widest thing a plan can ask for.

### Security debts, named and unpaid

- **`openat2(RESOLVE_BENEATH)`** for the in-process tools. Still what
  `sandbox/mod.rs:312` says it is: a doc comment naming a TOCTOU window that
  canonicalize-then-open leaves open.
- **Level 3**, the container, with level-2 restrictions still applied inside it.
- **Auth**, if `serve` is ever bound off-loopback.

### Smaller, and each becomes folklore if it survives

- `luu chat --record` still sleeps 50 ms before exiting so the writer can drain
  (`crates/luu/src/lib.rs:990`). A race with a delay painted over it.
- `SessionView` still cloned under the mutex on every API read
  (`crates/luu/src/serve.rs:938`, `:946`).
- The replay still caps inter-message gaps at 400 ms
  (`crates/luu/ui/store.js:367`) and nothing in the UI says so.
- `?from=&limit=` on `/turns` still unimplemented.
- `RejectTask { task }` carries no reason, so a refused agent cannot propose again
  in the user's light — the user retypes instead.
- Native function calling and a GBNF grammar, replacing the text parse.
- Sub-tasks and nesting. Still deliberately not now.
- The CLI still has no gate, and whether it should grow one is still undecided.

**Paid since the last list:** *no `busy` reply*. `Refusal::{Busy, Pending, Task,
NotGranted}` is on the wire with `serve_ws` tests for each, and it is why the
protocol is v2. *A test that would have caught `num_ctx`* — `ollama_wire.rs`
asserts the request body against a stub backend, four tests.

## What I would do next, and why

**Eviction tombstones, then the gate protocol.** In that order, and they are
independent enough that the second does not wait on the first.

Tombstones first because they are small, blocked on nothing, and because they are
what makes the *next* run legible. The degenerate 512-token fixtures went
unnoticed for a whole commit for exactly this reason: a recording could show the
history bucket empty and could not say whether that was policy or arithmetic. The
gate run described above will produce recordings nobody has read before, and it
should not produce them through an instrument that cannot say what it dropped.

The gate protocol second because it is the question the last three commits made
askable and nothing else will ask it. Written first, run after — the fold's order,
which is the one that worked.

Relevance selection is the larger piece and comes after both. It is the last thing
step 2 needs, it has to beat a recorded baseline, and the baseline is exactly what
tombstones make trustworthy.
