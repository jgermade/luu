# Narrowing: the approved plan becomes the sandbox for its task

**Status:** plan, then code. It is the design's own sentence —
*make the approved plan be the `SandboxPolicy` for its task, with the file as
its floor* — which has been in `loude-design.md`'s open questions since the
sandbox landed and has been false the whole time. The precondition it was
waiting on ("a human who can widen a plan that forgot a file") was met by the
gate in PR #5; [`2026-08-30.the-gate.completed.md`](2026-08-30.the-gate.completed.md) says so in its
*Still open* table.

## What is true today

`Plan::unmet` checks the plan against the sandbox: every file it names must be
readable and every command it names must be allowed, or the task does not run.
That is the half that cannot be wrong, and it is all there is. Once the task is
approved the agent runs with **everything `luu.toml` grants**, whether the plan
named it or not. The plan is a promise nobody holds it to.

So the permission scope the whole task boundary was argued for — *it is the
scope at which permission is granted* — is not a scope. It is a comment.

## What changes

A task, once approved, carries its own `Sandbox`, built from the plan and
handed to every turn that runs inside it. Outside a task — the CLI's one-shot,
a `serve` session with nothing open — the policy file is still what holds, as
before.

**The file is the floor in the only sense that can be enforced: the plan may
never grant what the file does not.** The narrowed sandbox is the intersection,
built by asking the session's sandbox what it grants for each path the plan
named. A plan cannot invent access; `unmet` already refuses one that tries, and
this is the same rule applied a second time, where it bites.

**Narrowing is on extent, not on level.** A planned file keeps exactly the
access the policy file gives it: a path granted `read-write` there stays
read-write here. The plan has no way to say *read* versus *write* — that is a
separate open item, listed in `2026-08-30.state-of-play.completed.md` — and inventing the
distinction here would answer that question as a side effect of this one. Same
for `network` and `enforcement`: a plan declares neither, so neither narrows.

**A denial names which authority refused.** `Sandbox` gains an `Authority`:
the policy file, or the approved plan for task *n*. It appears in the verdict,
so "no rule grants read on X" becomes "…, under the approved plan for task 1".
Two runs that were refused by different authorities are not the same run, and
the recording is the only thing that could tell them apart — the same argument
as `Applied`, one level up.

## The half that makes it survivable: widening at the gate

Narrowing without this is the reason it was deferred, and nothing about that
argument has changed: *a narrower sandbox with no way to widen it in the moment
turns every under-specified plan into a dead run*. A 7B's first act is to
propose a plan that forgets a file.

So `approve_task` carries an amendment:

```json
{"type": "approve_task", "task": 1, "files": ["luu.toml"], "commands": ["rg"]}
```

Both default to empty, so an approval that widens nothing is the message that
already exists. What the person adds is checked against the policy file exactly
as the model's plan was: the human at the gate can widen the plan up to the
file and not past it. The amended plan is what the task keeps and what
`task_approved` now carries, so the transcript and the recording show what was
actually approved rather than what was proposed.

**Protocol v1 is not bumped.** Both changes are additive fields with defaults;
an older reader that ignores them reads exactly what it read before. The freeze
says a change an older reader *could not make sense of* bumps the version, and
neither of these is one.

## What it costs, and who pays it

- **A follow-up prompt inside a live task that needs a file the plan never
  named is now refused.** That is the point — the gate record lists it as the
  thing narrowing buys — but it is a real behaviour change, and on a small model
  it will happen constantly until plans get better. The refusal names the plan
  and the file, which is what makes it actionable rather than mysterious.
- **A task that declares no files grants no files.** The fourth group of
  `grounded-tasks.txt` is exactly this: it asks the previous three questions
  again from history alone. It attaches nothing and needs no tool, so it runs —
  but a model that decides to read something there is now denied where it used
  to succeed. The probe is a comparison of two scripts and both halves are
  affected identically, so the M4 recipe still measures the fold.
- **A fragment inside a live task is read through the task's sandbox**, not the
  session's. The rule that a path `read_file` would refuse must not become
  readable by spelling it in a flag does not stop applying because a task is
  open. Every `## fragment:` in `scripts/tasks/` sits *before* its `## task:`,
  so nothing in the recipe changes; a fragment inside a task now has to be in
  the plan.
- **The CLI's scripts are approvals, so they narrow too.** A script whose plan
  forgets a file it later reads stops working. The four in `scripts/tasks/` name
  every file their turns touch — verified by running both grounded scripts
  against the mock, which is in this change's checks.

## What was rejected

- **Narrowing at proposal time instead of approval time.** The plan is the
  model's until a person accepts it; a sandbox built from an unapproved plan
  would be a permission the model granted itself.
- **Letting the amendment widen past the policy file.** Then the gate is the
  policy and `luu.toml` is a suggestion. The file is the outer bound, the plan
  the inner one, and the person moves between them.
- **A `--no-narrow` escape flag.** It would be used once by everyone and then
  always, and the design commitment would survive as a default nobody runs.
  Widening the plan at the gate is the escape, and it is one that gets recorded.
- **Narrowing the access level to read unless the plan says otherwise.** It is
  the right end state and it needs the plan to distinguish read from write.
  Doing it now would silently break every task that edits a file it named.
- **Keeping the narrowed sandbox inside `Task`.** `Task` is serialized into the
  view, the record and the summary; a `Sandbox` is a resolved thing with file
  descriptors' worth of meaning behind it and no business in a wire type. The
  runner holds it beside the task id, in `serve` and in the CLI loop.

## Still open after this

- A plan that says what it will *write*, so the check catches a write into a
  read-only root instead of the call catching it.
- Narrowing `network` and `enforcement`, which needs a plan that declares them.
- The verdict of a denial under a plan is a good place to offer *"add this file
  to the task"* as a client action. Not in this change: it is a second gate, and
  the first one should be watched being used before a second is designed.

## 2026-08-30, later: built, and what it looks like from outside

Landed as planned, with one thing the plan did not say and should have.

**A denial now names its authority.** `Sandbox` carries an `Authority` — the
policy file, or the approved plan for task *n* — and every verdict it refuses
with says which. It is the same argument as `Applied` one level up: a run
refused by the file and a run refused by the plan are not the same run. Driven
in the live UI, the tool panel reads:

```
read_file {"max_lines":1,"path":"AGENTS.md"}
denied  no rule grants read on /home/user/luu/AGENTS.md, under the approved plan for task 1
        held by an in-process check · 0 ms
```

Without that clause the message is indistinguishable from a policy file that
never granted the path, which is the mistake a person would then go and make in
`luu.toml`.

**Verified by running, not only by testing.** Both halves were driven through
the real page against a real `luu serve`, in a browser:

- Approving the plan as proposed, then a turn that reads `AGENTS.md` → the
  denial above, and the composer, panel and transcript intact with no console
  errors.
- Typing `AGENTS.md` into the gate's new field, pressing *add file*, then
  *Approve* → `allowed AGENTS.md (read-write)`, and `task_approved` carrying
  the amended plan, which is what the transcript and the read API then show.

The script that drove it is not committed: it needs a debug binary and node, so
CI cannot run it, and a check nobody runs is worse than a note saying what was
checked. What *is* committed are the two socket tests that assert the same two
outcomes against the protocol.

**The M4 recipe still runs.** Both grounded scripts were run end to end against
the mock under narrowing. Every `## fragment:` in them sits before its
`## task:`, so nothing needed changing — and task 4, which declares no files, now
grants none, exactly as this file predicted.

### The one thing the plan got wrong

The amendment's failure mode. The plan said an entry the policy file does not
grant is "dropped rather than approved", which is right, and then said the
feedback is that the client sees it missing from `task_approved`. That is
feedback in the sense that the information is on the wire; it is not feedback in
the sense that anyone notices. A person who types a path into the gate and
presses Approve gets a task that runs, with their path silently absent.

It is the same family as the two silent refusals already listed in
`2026-08-30.ready-for-the-m4-run.completed.md` — `start_turn` refusing while a turn runs,
and a prompt behind the gate — and it wants the same fix: a `busy`-style reply
that says what was refused and why. Not built here, and now there are three
places asking for it rather than two.
