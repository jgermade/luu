# Closing on an exit code: the rung above the person

**Status:** a proposal and the code it plans. The rung it builds is the one
[`what-the-audit-left`](2026-09-01.what-the-audit-left.completed.md) left
unblocked and unbuilt, and the design question it left with it.

`protocol.rs` has said the same sentence since tasks landed:

> Close it: from here its turns are sent as their summary. The user is the only
> authority that closes a task today; the ladder above them (exit codes, then a
> judge in shadow mode) is still ahead.

Yesterday the first half of that stopped being blocked. `CommandResult` gave
`run_command` an `exit_code` field, and the record that landed it said what was
left:

> The closing ladder's next rung is unblocked and not built: nothing yet closes
> a task on an exit code. What "the tests passed" means for a task whose plan
> named three commands is the design question, and it is not this record's.

It is this one's.

## The question, stated so it can come out wrong

A plan declares `commands: ["cargo", "git", "ls"]`. The task runs eleven
commands over four turns. Some exit 0, some do not, and one of them was
`git diff --stat`, which exits 0 whether or not anything works.

**Which exit code, of the eleven, means the work is done?**

Every answer that derives it from the list is wrong, and they are wrong in
different ways:

| Rule | What it does to the case above |
| --- | --- |
| All declared commands exited 0 | `ls` closes the task. So does `git diff`. And a plan whose third command was never run never closes at all — the rule is unreachable exactly when the work went badly |
| The last command exited 0 | Position is not intent. The last thing a task runs is usually the thing it ran to check the thing before it |
| The first command exited 0 | Same, at the other end |
| Any command exited 0 | `ls` |

The common failure is that all four **infer** intent from a list that was
written for a different purpose. `commands` is a *grant* — the set of programs
this task may run — and a grant is deliberately wider than a plan. Reading
"which of these means done" out of "which of these are allowed" is reading an
answer out of a question that was never asked.

## The proposal: the plan says which, and a person writes it

One new field:

```rust
pub struct Plan {
    // ...
    /// The command whose success closes this task. `None` closes nothing.
    pub closes_on: Option<String>,
}
```

`closes_on: Some("cargo test")` and the task closes itself the moment a
`run_command` step belonging to it runs `cargo test` and comes back
`exit_code: Some(0)`. `None` — which is every plan today, and every plan a model
writes — behaves exactly as it behaves now: the person is the only authority.

### The decision this record is actually making: the model is never asked for it

`closes_on` is **not** added to [`session::PLANNING`](../crates/luu/src/session.rs).
The planning prompt keeps its five keys, the model keeps writing the plans it
writes, and the field arrives at the **gate**, in the amendment, beside `files`,
`writes` and `commands`.

Three reasons, and the third is the one that decides it:

1. **The prefix.** `PLANNING` is fused into the current user message on every
   planning call. A sixth key is paid for by every session that never uses it,
   including all of them until someone types one.
2. **The measurement.** [`the-gate-probe`](2026-08-31.the-gate-probe.completed.md)'s
   headline number is how often a 7B produces a plan that is parseable and
   complete enough to run. Adding a field the model may get wrong moves that
   number, and moves it for a reason that has nothing to do with the question
   the probe asks. The probe is written and unrun; changing the prompt it is
   written against before it has ever produced a number would waste the one
   thing it exists for.
3. **It is the person's judgement, and only theirs.** "What would convince me
   this is finished" is not a fact about the code — it is what the human at the
   gate is *for*. A 7B asked to name its own success criterion will name the
   command it was about to run anyway. That is not a closing condition, it is a
   restatement of the plan, and a task that closes on it closes on nothing.

So this is the first thing the gate can add that the model was never asked to
propose, and that asymmetry is the point rather than a gap: `files` and
`commands` are a model's draft a person corrects; `closes_on` is a person's
instruction a model never sees.

**It also means the cached prefix does not move**, so every run recorded before
this change stays comparable with every run after it. That was not a free
choice — it is most of why the field went to the gate rather than into the
prompt.

### What counts as the command running

Narrow on purpose:

- **A step of this task.** `close_task` already gathers the task's own steps;
  the match runs over the same set. Another task's `cargo test` is not this
  task's evidence.
- **`run_command` only.** No other tool has an exit code, and one invented for
  them would be the lie `CommandResult`'s `Option` was chosen to avoid.
- **The rendered command line, matched whole.** `cargo test` matches
  `{"command": "cargo", "args": ["test"]}` and does not match
  `cargo test --no-run`, which compiles the tests and runs none of them. A
  prefix match would close that task, and the difference between those two
  command lines is the entire difference between the work being done and not.
- **`exit_code == Some(0)`.** Not "no error". A child killed by `SIGXCPU` has no
  exit code at all, and `signal: Some(24)` is not success — it is the
  `[sandbox.limits]` rung reporting that the command never finished.

The rendering is the one `summary_text`'s evidence lines already use, lifted out
of `task.rs` as `command_line` and shared. Two renderings of the same command
line, one for the person to read and one to match against, would drift, and the
day they drift a task stops closing for a reason nobody can see.

### Every close says who closed it

```rust
pub enum ClosedBy {
    /// A person, at the gate.
    User,
    /// The task's own `closes_on`, on an exit code of 0.
    ExitCode,
}
```

on `ServerMessage::TaskClosed` and on `TaskView`, both `Option`, both
`#[serde(default)]`.

This is not bookkeeping. The whole reason the ladder is a ladder is that each
rung has to be *counted* before the next one is trusted — how often did the exit
code close a task a person would have left open, and how often did a person
close one the exit code missed. A recording where both closes look identical
cannot answer either question, and by the time anyone wants to ask it the
sessions are already on disk.

`None` is a recording made before the field existed, and it means *user*: that
is what every close in every file to date was.

### The format does not move

`Plan.closes_on`, `ApproveTask.closes_on` and `TaskClosed.by` are all new
optional fields on types that already exist. By the rule
[`what-the-audit-left`](2026-09-01.what-the-audit-left.completed.md) stated when
it added `command` to `tool_result` — *new variant bumps, new optional field does
not* — `record::FORMAT` stays 5 and `protocol::VERSION` stays 3. An older reader
ignores a key it does not know; a newer reader gets `None` from an older file,
which is the truth rather than a default standing in for one.

## What it costs

**A summary can now be written with nobody watching.** `Task::close` lands its
text in the write-once region every later turn is built on, and until now a
person was always present when that happened. After this, a `cargo test` that
exits 0 at 3am folds four turns into one summary and every call for the rest of
the session pays for whatever that summary got wrong.

That cost is why `closes_on` is **opt-in per task** rather than a policy-file
setting or a default. A session-wide "close on green" would apply the rule to
tasks nobody chose it for; a per-task field is chosen by the person who is
already reading that task's plan, at the one moment they are thinking about what
finishing it looks like.

It is also why the field is a command line and not an expression. `closes_on:
"cargo test"` is something the reader of a gate can evaluate in the second they
have. This is the same test `what-the-audit-left` applied to resource limits and
failed them on — "512 MiB" is not judgeable at a gate, so limits stayed in the
policy file — and it is the reason this field passes where those did not.

## What this rejects

**A shadow mode first.** The design stages the ladder as "exit codes and tests
first, then the judge in shadow mode", and the temptation is to give this rung
the same treatment: report what *would* have closed, close nothing, and turn it
on once the reports look right. Rejected, because shadow mode exists to watch a
**judgement** before trusting it, and an exit code is not a judgement — it is the
same fact the person already reads off the transcript before clicking close. A
shadow mode here would measure how often a human agrees with `cargo test`, which
is not a finding. The judge's rung still gets one.

**Deriving the condition from `commands`.** The four rules in the table above.

**Closing on a non-zero exit.** A task whose tests fail is not finished, and it
is also not *nothing* — but "failed" is a state this project does not have, and
inventing one here would be inventing it in the wrong record. A failing
`closes_on` leaves the task open, which is what it is.

**Reopening on a later failure.** A task that closed green and then went red is
a real thing, and undoing a fold on it would rewrite a summary that later turns
have already been built on. Closing is an event; so is reopening; and a machine
that does both on its own is a machine that can loop.

## Still open, after this

- **The 30-second clock makes the obvious case unreachable.**
  `run_command`'s `DEFAULT_TIMEOUT_MS` is 30 000, and a `cargo test` on anything
  real is killed long before it exits. The model can pass `timeout_ms`, so the
  rung *works*; it works on a command whose duration the model chose, which is
  not the same as working. The honest fix is a per-task or per-plan clock, and
  it is the same argument `[sandbox.limits]` had about where a number lives — a
  timeout is judgeable at a gate in a way "512 MiB" is not, so it may belong in
  the plan after all. Not this record's.
- **A turn that fails after its command succeeded.** `cargo test` exits 0, the
  model then errors, the task closes anyway. Arguably right — the criterion was
  met — and arguably a close over a broken turn. Unresolved; the close happens
  after the turn is folded into the context, so today the failure is inside the
  summarised region either way.
- **More than one closing condition.** `closes_on` is one command because one is
  what a person can judge. "`cargo test` and `cargo clippy`" is a real ask and
  wants a list, and a list wants a rule for partial success, which is the door
  this record deliberately did not open.
- **Nothing counts the two authorities yet.** `by` makes the question askable
  and answers nothing. The number wants closed tasks in quantity, which wants
  the store, which is the other half of today's work.

## 2026-09-02 — what building it decided

The proposal above is what landed, with one correction and one finding.

**The correction: a closing condition is checked against the merged plan, not
the amendment.** `permitted` checks what a person adds at the gate against the
policy file, item by item, and the obvious thing was to check `closes_on` there
with the rest. It is wrong, and it is wrong in the ordinary case rather than an
edge one: a person types `cargo test` for a `cargo` the *model* already
declared, and the amendment they are submitting names no commands at all. Read
against the amendment alone, every such condition is refused.

So it is checked against what the plan will be — the model's commands, plus the
gate's, intersected with what the policy file grants. The intersection is the
part that is easy to leave out and the part that matters: `Plan::narrow`
silently drops a declared command the file never granted, so a condition checked
against the *declaration* would be accepted and then never met.

**The finding, and it is larger than this record: the rung does not exist on any
machine where the kernel cannot hold a child.**

Writing the end-to-end test — a plan that declares `sh`, a gate that names
`sh -c exit 0`, a turn that runs it — produced a denial rather than a close:

```
denied: the kernel cannot hold this child (landlock is not available in this
kernel); grant it anyway with enforcement = "best-effort"
```

That is the sandbox module working exactly as designed. Under the default
`enforcement = "kernel"` a `Partial` verdict is a denial, and the closing rung
sits on top of `run_command`, so **wherever `run_command` cannot run, nothing
can close on an exit code**. Which is macOS, which is every machine this is
being built on, and it is the same sentence
[`ROADMAP/2026-09-01`](../ROADMAP/2026-09-01/README.md) already wrote about the
gate probe's command prompts:

> `run_command` has never been observed with a model in the loop anywhere — the
> three command prompts of the gate probe's corpus are unaskable today. The
> container is what makes them askable.

The container makes this askable too. It was item 3 for the probe's sake; it is
now item 3 for two reasons, and the second one is a feature that is *built* and
unreachable rather than a measurement that is unmade. Nothing here should be
believed about a real machine until it has run in one.

The test therefore runs under `best-effort` and says so in a comment. That is
not the rung being weakened — it is the test asserting the thing it is about,
on the kernels CI actually has. A test that only ran where Landlock exists would
assert this nowhere else, macOS included.

### Still open, after building it

- Everything the record already listed, unchanged: the 30-second clock, the turn
  that fails after its command succeeded, more than one condition, and nothing
  counting the two authorities yet.
- **The rung has never closed a task on a machine with a model on it.** The
  end-to-end test is the mock backend and a scripted tool call. What a 7B does
  when it is told a task closed itself is unobserved, and it is the sort of
  thing that reads as the conversation being cut off.
