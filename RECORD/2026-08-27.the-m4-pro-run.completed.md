# 2026-08-27, fourth pass: a real model, and two blind spots it found

The AGENTS.md section for this had never been run. It has been now, following its
own recipe exactly: `ollama serve` with `OLLAMA_KEEP_ALIVE=30m` set before it
started, `qwen2.5-coder:7b` pulled alongside `14b` and `32b`, the HuggingFace
tokenizer fetched to `~/models/qwen2.5-coder-7b/tokenizer.json`, and the same
`steady-state`/`steady-state-tasks` pair the mock measured, run with
`--context-limit 8192 --reserve 512 --tokenizer ...`. `ollama ps` confirmed
`num_ctx` reached the server (`CONTEXT 8192`), and a scripted `run_command` call
on this Darwin box came back denied with the exact verdict text AGENTS.md
describes — nothing in the setup instructions was wrong.

Two things the mock could not have shown turned up anyway.

## The scripts carry no grounding, so "does the answer survive the fold" has no baseline

`steady-state.txt` was written uniform-on-purpose for measuring eviction
mechanics against a mock that echoes fixed text — it injects no file, no
design doc, nothing about this repository. Turn 1, against a real model, asking
"what does the context manager do?":

> A context manager in Python is a way to manage resources such as files,
> locks, and network connections... The primary methods used in a context
> manager are `__enter__` and `__exit__`.

That is a correct answer to a question nobody asked. Every turn in both
recordings is like this: fluent, generic software-consulting prose about
"strategy" and "accountability" that never once names a bucket, a policy, or a
file in this project, because nothing in the prompt ever told the model this
project exists. The planning calls confirm it from the other side: task 1's
plan didn't parse at all (prose steps, one of them a garbled attempt to invent
a `{"steps": ...}` block from scratch); tasks 2–4 parsed cleanly but planned
against files that don't exist — `src/eviction.py`, `src/comparison_logic.py`,
`project_status.md` — Python paths, in a Rust workspace the model was never
shown. `"parsed": true` is a syntax check, not a grounding check, and it will
say yes to a plan that is fiction.

So AGENTS.md's "whether the answers after a fold still refer to what the task
did" is not answerable with this pair, in either direction: there is no
correct, grounded pre-fold answer for a fold to lose. Testing fold fidelity
needs a script that actually fuses real file content into a turn — the `code`
bucket exists for exactly this and neither fixture script uses it.

## A tool call inside a turn is invisible to `prefix_reuse`, the same way a planning call used to be

Turn 12 of `steady-state-tasks` (task 3, still working from a hallucinated
plan) had the model call `read_file` on `src/your_count_system.py` — another
path that doesn't exist, denied by `os error 2`. That call makes turn 12 two
model calls, not one: the first ends in a tool block, the second sees the tool
result and answers. `budget`/`prefix_reuse` recorded only the first: 1 590
tokens, 1 000 shared. `ended.usage.prompt_tokens` — the backend's own count for
the call that actually finished the turn — was **3 552**. Every other turn in
both recordings has our count within 3 tokens of the backend's; turn 12 is off
by 1 962. Nothing crashed and nothing looked wrong in the budget panel, because
the panel only ever heard about the first of the two calls.

This is the exact shape of the gap the planning call left two passes before —
a call that sits between two tracked turns and emits no `prefix_reuse` —
recurring one level down, inside a turn, for the tool-use round trip. The fix
is the same shape too: a trace event for the intermediate call, not just the
one that ends the turn.

## The numbers, with both caveats priced in

Same two recordings, `--context-limit 8192 --reserve 512`, `qwen2.5-coder:7b`,
real tokenizer. Neither run ever evicted — the window is wide enough that 20
short turns fit without either policy firing once, so this pair tests
counting, reuse and grounding, not eviction.

|  | reuse, turns | reuse, all calls | turn prompts (backend) | planning | total |
| --- | ---: | ---: | ---: | ---: | ---: |
| plain · `turn` | 89.5% | — | 66 986 | — | 66 986 |
| tasks · `turn` | 81.3% | 80.7% | 31 879\* | 3 177 | 35 056\* |

\*Turn 12's contribution is the second-call total only, per the blind spot
above — the first call's prompt (~1 590–1 600 tokens by our count, backend
figure unknown) is missing from both the turn-prompts column and the total.
The true total is higher by roughly that much, on both sides equally since the
missing call belongs to the tasks run either way.

**Folding wins on both reuse and tokens here — more than half off, not the ~2%
of the mock's third pass — and the sign of the token result flips from that
pass entirely.** The difference is the window. The third pass fixed
`--context-limit 1024` specifically so the baseline would evict and the two
policies would be comparable; at that width the baseline's history is capped,
so folding could only win on how cheaply eviction happens. At `8192` the
baseline never evicts at all, so its history compounds every one of the 20
turns with nothing pushing back — plain `turn` sends 66 986 tokens total against
tasks' 35 056 (undercounted low) because tasks keeps resetting to a small
history four times and plain never resets. **A window this comfortable relative
to the task is exactly the regime where the naive baseline is at its worst**,
and it is also the regime `luu` targets (7B–32B, 8K–32K) — so the mock's
"folding barely wins on tokens" conclusion holds at the width chosen to force a
fair eviction comparison, and does not hold at the width the tool actually
ships for. State the configuration beside the figure, same rule as before, one
context-limit further in.

Chat-template overhead was the one number that behaved exactly as predicted: on
every plain-run turn (no tool calls, no plan calls to hide a second call inside
one turn number), backend `usage.prompt_tokens` minus our tokenizer count is a
flat **+2**, turn after turn — the stable gap AGENTS.md said a correct chat
template would produce.

# 2026-08-30, landing on this tree: what of the above is now answered

Appended the day this file arrived here, so a reader is not left with a *Still
open* table that three of this repository's commits have since moved.

- **The ungrounded scripts.** Fixed. `## fragment:` and `--fragment` put a real
  file into a turn through the sandbox, and `scripts/tasks/grounded{,-tasks}.txt`
  are the pair that uses it. The fold-fidelity question is now askable, and
  [`2026-08-27.grounded-fold-probe.completed.md`](2026-08-27.grounded-fold-probe.completed.md) is how
  to ask it.
- **The invisible intra-turn call.** Fixed. Every model call a turn makes is
  announced and measured, not just the first.
- **Whether a plan stays grounded.** Partly answered from the other end, and
  differently from the branch this came from: on this tree a script *carries* its
  approved plan rather than asking the model for one, so a scripted run cannot
  hallucinate `src/eviction.py` at all — a plan naming a file the sandbox does not
  grant is refused before the first turn. `serve` still asks the model, and there
  the finding stands untouched.
- **32K, and reuse in seconds.** Still open, both, and both still need only a
  machine with a model on it.
