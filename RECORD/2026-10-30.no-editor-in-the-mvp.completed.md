# No editor in the MVP: the VS Code extension and `luu stdio` retired

> Quién consume `luu stdio`?
>
> Si en un futuro hacemos una extensión para VSCode, no podría hablar
> directamente con `luu serve`?
>
> Ok, descartamos VSCode del MVP entonces

Asked what to do with what there was, the answer was to retire both: the
extension and the subcommand.

## What there was

- **`editors/vscode`**, the chat participant
  ([`vscode-extension`](2026-09-04.vscode-extension.completed.md)). It spawned
  `luu stdio` and spoke the protocol over its stdin and stdout
  ([`protocol-over-stdio`](2026-09-04.protocol-over-stdio.completed.md)).
  **It had stopped working.** It announced protocol 7 and record format 16; luu
  speaks 12 and 26, and answered its `hello` with
  `refused … this host speaks protocol 12 and the client speaks 7`. The last
  commit to touch it was `428e776`. Nothing in CI built or ran it.
- **`luu stdio`**, whose only consumers were that extension and
  `crates/luu/tests/stdio.rs`.

## Why retiring, and not keeping the transport

The reason stdio was chosen for the editor —
[`how-a-surface-reaches-the-engine`](2026-09-01.how-a-surface-reaches-the-engine.completed.md):
no port, no bind, no token, one process per window — was a reason about an
editor. With no editor, `luu stdio` is a second transport carrying the same
protocol to nobody: every protocol change has to be right twice and is tested
once. And an editor that comes back does not need it. `/ws` checks no
`Origin` — only the terminal's socket does — and takes the token as
`Authorization: Bearer`, which a Node client can send; or a webview embeds the
page. What such an editor would have to settle is the server's, not the
transport's: one live session per `serve`, shared with the browser
(concurrency, roadmap row 14), and which folder `serve` works in.

## What went

- `editors/vscode/`, and its lines in `Makefile` (`install`, `build`, `help`),
  `.dockerignore` and the README.
- `Command::Stdio` and its dispatch in `lib.rs`; `serve::stdio`,
  `serve_stdio_stream` and the stdio loop in `serve.rs`.
- `crates/luu/tests/stdio.rs`. Its four tests: *greets and answers*,
  *unparseable lines*, *close and reopen* each have a counterpart over the
  socket in `serve_ws.rs`; **a prompt while a plan is on the table is *more
  changes*** had none, and was moved there as it was, over `/ws`.
- The landing's *VS Code* and *Protocol* cards; its surfaces read *one engine,
  two ways in*.

**Renamed, not removed:** `StdioOptions` was what `serve` built its `App` from
as well, so it is `AppOptions`. The `agency_for: None` path — *this surface
cannot choose a posture* — stays, because tests build an `App` by hand; the
words that said *over stdio* now say that.

**Not touched**: `luu worker` speaks over its stdin and stdout too. That is the
seam between the server and the executor
([`the-worker-and-the-seam`](2026-09-02.the-worker-and-the-seam.completed.md)),
not a client surface, and it stays. VS Code *icon themes* stay as well: the
page reads them, and they have nothing to do with the extension.

`gate.spec`'s folder-folding test used `editors/vscode` as the checkout's one
folder holding only a folder; it uses `tests/smoke` now.

## Still open

- An editor surface, when it comes back: a client of `/ws`, or the page in a
  webview — decided then, with concurrency.
