# A live session moves when it is asked to

## The problem

Reported as *"tengo problemas para cambiar el modelo, específicamente, entre uno
de minimax y uno de ali cloud"*: in a session with turns, choosing the other
provider in the chat's picker closed the menu and changed nothing. The button
kept naming the first one and the next turn went there.

Reproduced without either service: an Anthropic-compatible fake shaped like
MiniMax's `/anthropic` and an OpenAI-compatible fake shaped like DashScope's
`/compatible-mode/v1`, as `[provider.mm]` and `[provider.ali]`, and a driver
that makes a session on `mm`, runs a turn, resumes it on `ali` and runs another.
Before this change:

```
== new session on mm: 201 … "model":"MiniMax-M2"
== turn 1 (mm): ended
== switch to ali: 200 {"model":"MiniMax-M2"}
== settings now: mm MiniMax-M2 anthropic
```

`200`, and nothing moved. Nothing about MiniMax or Alibaba Cloud: any two
destinations do it, once the session has a turn.

## Why

The picker resumes a session that has turns (`resumeSession(state.session,
choice)`), and so does the sessions dialog's *Continue here*. Both are only
ever asked of **the session on screen, which is live**. Since 2026-10-30
(`RECORD/2026-10-30.sessions-side-by-side.WIP.md`, step 3) `resume_session`
answers a live session by attaching to it and **ignores a body naming another
destination**; that record says *"Continue here moves one"*, and nothing did.
No test resumed a live session onto another provider: the picker's smoke test
switches a session with no turns, which is `POST /api/sessions`.

## The proposal

- **A resume of a live session that names another provider or model moves
  it.** `names_another_destination`: a profile or a model in the body that is
  not the one it sends to now. Naming where it already is stays an attach.
- **It moves by the resume that already exists**, run on the session's own
  checkpoint: the destination built by `destination_for`, the history re-folded
  by `store.resume` with the new counter and wrapped in the new tool transport,
  the header `retarget_header` writes where it changed, the hello. The same
  path a stored session takes, so nothing about *what moving means* is
  written twice.
- **Under the posture and the agency it already has.** A destination may move
  under a history and a posture may not; nothing is built, so a container
  running its tools is not ended and started again for a change of model.
- **Between turns.** `409` while a turn runs, a proposal waits at its gate or a
  call is held — the picker already says *Cannot switch* then. Its session lock
  is held from that check until the rebuilt one is live under the same id, so
  nothing starts on the old one mid-move. It takes no room under `max-live`: it
  replaces itself.
- **The sockets follow.** A socket following the current session already
  switches by pointer. One that named the session (`?session=`) now keeps to
  that *id*, so it follows the rebuilt one too; and a message that arrives
  before the notice of the move is handed to the session live now
  (`rebuilt`), not to the one it replaced.
- **An engine only the old destination used is released** after the move, as
  putting a session to sleep releases it.

After it, the same driver:

```
== switch to ali: 200 {"model":"qwen3-max"}
== turn 2 (ali): ended
== settings now: ali qwen3-max openai
== switch back to mm: 200
== turn 3 (mm): ended
```

and the requests each fake received carry the history across the move: `ali`
gets the first prompt and MiniMax's answer before its own; `mm`, back, gets all
three prompts and both answers.

## Cost

The move rebuilds the session (a re-fold from the store and a new
`LiveSession`), which is what resuming a stored session costs; a session
switched every turn pays it every turn. The repository map is rebuilt with the
new counter, as a resume does.

## Rejected

- **Swapping the destination in place**, as `PUT /api/session/posture` swaps a
  posture. The context has to be re-folded with the other counter and the other
  tool transport and the map rebuilt, and `map_rendered` is not behind a lock:
  in place would be a second implementation of a resume. *Built beside, not in
  place* is what the 10-30 record decided for sessions, and this keeps it.
- **Fixing it in the page** — put the session to sleep, then resume. The API
  would still answer `200` to a body it ignored, which is the bug for any
  other client, and the current session cannot be put to sleep anyway.
- **Moving on any body that differs, posture included.** A posture is not
  moved by a resume; the stored-posture check below still refuses one that is
  not the same place.

## Evidence

- The driver above, against the two fakes (`.tmp/`, not kept).
- `tests/smoke/settings.spec.js` *the chat's picker moves a session that has
  turns, and the history comes along*: a turn on the mock, the picker to
  another provider, the same session one turn long on screen and in the list,
  back by the API, and a resume naming where it is answered as an attach.

## Still open

- **What the history carries between two kinds of backend.** Moved from an
  Anthropic-compatible destination to an OpenAI-compatible one, an earlier
  answer goes up with its `<think>…</think>` in its text, because the OpenAI
  backend sends history as it is and the Anthropic one strips it. The other
  way round it is stripped. Whether the OpenAI backend should strip a previous
  turn's thinking — as the Qwen templates do on their own — is a question about
  every OpenAI-compatible server, not this fix.
- **DashScope's thinking is not shown.** Its compatible mode streams a thinking
  model's reasoning in `delta.reasoning_content`, which the OpenAI backend does
  not read; the answer arrives, after a silence as long as the thinking.
