# A three-pane layout for the debug UI: inspector, content viewer, agent chat

**Status:** proposal, no code. Scopes four things asked for in one
conversation — sessions shown on open, a file-tree/git-status panel, a
preferences menu with a theme toggle, and session tabs — as one layout
change rather than four unrelated patches, because three of them only make
sense once the fourth (the column restructure) exists to hold them.

## The problem

`luu serve`'s debug UI (`crates/luu/ui/`) is two columns today: a
chat/timeline on the left and a debug-info sidebar on the right (token
budget, prefix reuse, tool calls, compaction, the exact prompt sent —
`app.html:796+`). It answers "what is the context manager doing," which is
what it was built for
([`2026-08-26.web-debug-client`](2026-08-26.web-debug-client.completed.md)).
It does not answer "what does the workspace look like" or "what changed" —
there is no file tree, no git status, nothing. A person using this page to
watch an agent work has to `cd` to a terminal to see what it touched.

Sessions are a `<select>` dropdown in the header
(`app.html:388-399`) — functional, but it hides how many sessions exist and
which one is live behind a click, rather than showing it.

And the page is dark-only: `app.css:24` hardcodes `color-scheme: dark`, no
light tokens exist, and there is nowhere in the UI to change that or any
other preference.

None of this is a defect in what was built — `luu-design.md:701` scopes the
UI explicitly as "chat, session browser, context inspector," and it does
that. It is scope that was never asked for until now.

## The proposal

Three columns instead of two:

- **Inspector** (left, replaces today's `aside.inspector`) — a mode switch
  between **Files** (a tree of the workspace, gitignored entries dimmed,
  changed entries highlighted — the two states a VSCode file tree already
  distinguishes), **Git** (a VSCode-style changed-files list), and
  **Debug** (today's token-budget/prefix-reuse/tool-calls/compaction panel,
  moved here as a third mode rather than kept as its own column — nothing
  in it changes, only where it lives).
- **Content viewer** (middle, new) — shows whatever the Inspector selected:
  a file's contents, a diff, or an expanded debug detail. Read-only.
- **Agent chat** (right, today's `section.chat`, moved) — the transcript,
  the plan gate, the composer. **Session tabs sit directly above this
  column**, replacing the header dropdown.
- A hamburger button, top-right of the header, opens a preferences modal.
  Its first (only, for now) setting is a light/dark theme toggle.

**Everything stays read-only.** No editing a file from the tree, no
staging or committing from the git panel, no code-editing widget. The UI's
own framing — "context inspector," not an IDE — does not change; it grows
a window onto the workspace it was already implicitly about, not a new
surface for changing it.

### Why tabs over a dropdown

A dropdown answers "which session am I on" only while open. Tabs answer it
at a glance and make "how many sessions exist" visible without a click —
the same reason every browser and editor uses tabs for exactly this. The
underlying state (`store.js:91-92`, `state.sessions` /
`state.currentSessionId`) and the switch/delete functions
(`app.html:41-44`'s `onSwitchSession`, `store.js:982-996`'s `deleteSession`)
do not change — this is a rendering change, not a new state model.

### Why the debug panel moves rather than staying a fourth column

A fourth column was considered and rejected: three panels plus a debug
sidebar is a lot of screen for a window that already collapses the
right-hand panel under 60rem (`app.html:1030-1033`). Folding Debug into the
Inspector's mode switch costs one click to see it and buys back a whole
column's width for content that actually wants it — a file or a diff reads
better wide than the debug panel, which is short label/value pairs, does
not.

### Why the file tree and git panel are new backend endpoints, not the agent's own tools

`luu` already has `list_dir`/`read_file`/`run_command` tools, but every one
of them is a **model's** action, gated by job approval
(`app.html:725-776`'s gate). A person opening the Files tab is not proposing
a job — routing a passive read through the approval flow would either
require rubber-stamping a job nobody asked the model to propose, or
inventing a second read path that bypasses the gate, which is worse: now
there are two ways to read a file and only one is audited. The actual
answer is what the design already does for the *read* side of the session
API (`serve.rs:854-873`, `/api/sessions/*`) — plain, ungated `GET`s, because
the person is not the agent and reading a directory listing is not a tool
call.

New routes, beside the existing table (`serve.rs:840-882`):

- `GET /api/workspace/tree` — walks from the session's `Sandbox::base()`
  (`sandbox/mod.rs:396`), gitignore-aware, merged with `git status
  --porcelain` output by path so the response carries both "ignored" and
  "changed" per entry in one shape the Files component can render directly.
- `GET /api/workspace/file?path=...` — file contents, scoped through
  `Sandbox::check_path` (`sandbox/mod.rs:451`), the same access check every
  other read in this codebase already goes through. No new access model.
- `GET /api/workspace/git-status` — `git status --porcelain`, structured.
- `GET /api/workspace/git-diff?path=...` — a diff, computed server-side
  (see below), not raw text.

### Why the diff is computed in Rust, not diffed in the browser

`luu-design.md:834` already decided this for prompt diffs and never built
it: "compute the prompt diff in Rust (`similar`), and send resolved spans
over the protocol... the server holds both strings anyway." The same
argument applies to a git diff — `git diff` itself already produces one, so
this is really "parse `git diff`'s own output, or compute spans with
`similar` over the two blobs" rather than reinvent diffing; either way nothing
diff-shaped ships to the browser. Reusing `similar` here is also the first
real user of the pattern the design doc named but never needed until now.

### Why the tree/git code is new rather than reused from `repo_map`

`repo_map.rs:205`'s `walk_sources` looks like it should be reusable — it
already walks the sandbox — but it is `.rs`-only and exists to parse tags
for the repository map, not to produce a general file tree, and has no
gitignore awareness. Making it general-purpose would grow a module that has
one job today into one with two unrelated jobs (feeding the model's context
budget vs. rendering a person's file tree) for a savings that is mostly
"a walk exists already," which the `ignore` crate provides more completely
(gitignore semantics included) than adapting `repo_map` would.

### Two new dependencies

- **`ignore`** (the ripgrep author's crate) — gitignore-aware directory
  walking. Nothing in this workspace does this today; `repo_map.rs` walks
  but does not consult `.gitignore`.
- **`similar`** — diff computation, named but never added by
  `luu-design.md:834`.

Both are pure Rust, no build step, consistent with the "cargo build needs
no node" constraint that picked `jq79` over a bundled frontend in the first
place (`luu-design.md:816-820`).

### Why the new panels are separate components, not a bigger `app.html`

`app.html` is 1220 lines today, one monolithic jq79 component. jq79 itself
supports "`.html` files loaded at runtime" as components
(`luu-design.md:819`) — nothing in this repo has used that yet;
`index.html:12-15` only ever mounts `app.html`. Growing the monolith by
another few hundred lines per panel is the path of least resistance and
the wrong one: `inspector-files.html`, `inspector-git.html`, and
`content-viewer.html` as their own components keeps each one readable and
is what the framework was already chosen to support. The exact
parent-to-child mount mechanics are unverified in this codebase (no
existing example) and are the first thing implementation checks, before
committing further to the split.

## What it costs

- **Four new HTTP routes and two new dependencies** for what was previously
  a UI-only tool with a frozen v1 protocol
  (`2026-08-26.web-debug-client.completed.md`'s "the message enums are not
  frozen" resolved since, per `luu-design.md:704`). None of the four routes
  touch the WebSocket protocol or the record format — they are plain reads,
  versioned the same loose way `/api/sessions/*` already is, not folded into
  the frozen `v1` message enums.
- **A layout that is harder to collapse cleanly on narrow screens.** Two
  columns already hide the right one under 60rem
  (`app.html:1030-1033`); three columns needs its own answer, not decided
  here (see Still open).
- **Screen real estate the debug panel used to have alone**, now shared
  with two other modes behind a click. Accepted: the debug panel is used
  less often, per session, than either the ability to see what a session
  touched, or the file tree — but this is a judgment call, not measured.
- **The known-undocumented `git status --short` exit-128 finding from
  machine 4** becomes load-bearing rather than an aside. It was found
  inside the *agent's* sandboxed `run_command` path, and this proposal's
  git endpoint shells directly from `serve.rs`, outside that sandbox
  entirely — plausibly unaffected, not yet confirmed. Phase 4's first step
  is reproducing it directly, not assuming either way.

## Still open

- **Exact column widths**, and what the narrow-screen breakpoint becomes
  with three columns instead of two (`app.html:1030-1033`'s current
  two-column collapse doesn't generalize on its own).
- **Whether the Debug mode's current dense layout survives being one of
  three Inspector tabs** rather than the whole right rail, or wants
  simplifying now that it has less default width.
- **The jq79 parent→child component mount mechanics** — assumed possible
  per `luu-design.md:819`, not yet exercised anywhere in this codebase.
- **Whether `git status --short` still exits 128 on machine 4** from a
  direct `serve.rs` shell-out, separate from the sandboxed path that found
  it.
- **Any editing capability** (write from the tree, stage/commit from the
  git panel) is out of scope by design here, not merely deferred — this
  proposal is read-only throughout; a future one would need its own
  argument for crossing that line, the same way every write in this
  project goes through the job-approval gate today.

## 2026-09-15, later: phase 1 built — the three columns, the modes, the tabs

The layout half of the proposal above, landed. No backend change, no new
dependency: everything here is `crates/luu/ui/`.

**Four new components, and the first time this project has composed two.**
`inspector-debug.html` is the panel that used to be `app.html`'s whole right
column, moved rather than rewritten — it imports `store.js` directly and
recomputes its own `view`/`folds`/budget values, so `app.html` no longer
carries any of them. `inspector-files.html`, `inspector-git.html` and
`content-viewer.html` are stubs that say what they will hold and which phase
holds it; a panel that renders nothing reads as a bug, and these will be on
screen for as long as phases 3 and 4 take.

**The one mechanical thing worth writing down, because the file's own first
comment already warned about it and the warning was still easy to walk
into:** a `:setup` script has no static `import`. `import X from "./x.html"`
parses as a module statement the page cannot run and the whole app fails to
mount with `Cannot use import statement outside a module` — the symptom is a
blank page, not a stack trace pointing at the line. The form that works is
`const X = await import("./x.html")`, which jq79 rewrites to its own loader;
that loader answers an `.html` specifier with **the component itself**, not a
module namespace, so there is no `.default` to destructure. Nothing in the
tree demonstrated either half before this.

**And a build-loop one:** `rust-embed` bakes `ui/` into a release binary, so
a UI edit is invisible until `cargo build --release` runs again. Debug builds
read from disk (`#[cfg(debug_assertions)]`), which is the loop to use while
iterating; a smoke run against a stale release binary tests the old page and
says so nowhere.

**Breakpoints, which the proposal left open.** Three columns above 64rem;
64rem down to 48rem drops the viewer (it is the pane that is empty until
something is selected); below 48rem only the chat survives, since it is the
one being talked into. The first attempt dropped the viewer under 90rem,
which took the middle column away from a 1280px laptop — the common case,
not the narrow one. Caught by the new smoke test, which now pins its own
viewport rather than inheriting Playwright's 1280px default and asserting
whatever that happens to straddle.

**Widths**: 20rem inspector, 30rem chat, the middle flexible. Still a
judgment call rather than a measurement.

`tests/smoke/gate.spec.js` gains one test (the three panes, the mode switch,
the tab strip) and one changed selector: the `+ New` button beside the old
dropdown is now the `+` at the end of the tab strip. Four gate tests pass,
`cargo test --workspace` is green (432 tests), clippy under `-D warnings` and
`fmt --check` clean.

### Still open after phase 1

- Phases 2, 3 and 4 — the preferences menu and theme toggle, the file tree,
  the git panel — are untouched, and the three "Still open" items about
  widths, the Debug mode's density, and the machine-4 `git` exit-128 finding
  stand exactly as written above.
- **The shared module the Files/Git panels will talk to the viewer
  through** is named in `content-viewer.html`'s own comment and does not
  exist: nothing selects anything yet, so nothing has had to.
