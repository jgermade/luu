# A three-pane layout for the debug UI: inspector, content viewer, agent chat

**Status:** proposal, no code. Scopes four things asked for in one
conversation — sessions shown on open, a file-tree/git-status panel, a
preferences menu with a theme toggle, and session tabs — as one layout
change rather than four unrelated patches, because three of them only make
sense once the fourth (the column restructure) exists to hold them.

## The problem

`luu serve`'s debug UI (`crates/luu/ui/`) is two columns today: a
chat/timeline on the left and a debug-info sidebar on the right (token
budget, prefix reuse, tool calls, compaction, the exact prompt sent —
`app.html:796+`). It answers "what is the context manager doing," which is
what it was built for
([`2026-08-26.web-debug-client`](2026-08-26.web-debug-client.completed.md)).
It does not answer "what does the workspace look like" or "what changed" —
there is no file tree, no git status, nothing. A person using this page to
watch an agent work has to `cd` to a terminal to see what it touched.

Sessions are a `<select>` dropdown in the header
(`app.html:388-399`) — functional, but it hides how many sessions exist and
which one is live behind a click, rather than showing it.

And the page is dark-only: `app.css:24` hardcodes `color-scheme: dark`, no
light tokens exist, and there is nowhere in the UI to change that or any
other preference.

None of this is a defect in what was built — `luu-design.md:701` scopes the
UI explicitly as "chat, session browser, context inspector," and it does
that. It is scope that was never asked for until now.

## The proposal

Three columns instead of two:

- **Inspector** (left, replaces today's `aside.inspector`) — a mode switch
  between **Files** (a tree of the workspace, gitignored entries dimmed,
  changed entries highlighted — the two states a VSCode file tree already
  distinguishes), **Git** (a VSCode-style changed-files list), and
  **Debug** (today's token-budget/prefix-reuse/tool-calls/compaction panel,
  moved here as a third mode rather than kept as its own column — nothing
  in it changes, only where it lives).
- **Content viewer** (middle, new) — shows whatever the Inspector selected:
  a file's contents, a diff, or an expanded debug detail. Read-only.
- **Agent chat** (right, today's `section.chat`, moved) — the transcript,
  the plan gate, the composer. **Session tabs sit directly above this
  column**, replacing the header dropdown.
- A hamburger button, top-right of the header, opens a preferences modal.
  Its first (only, for now) setting is a light/dark theme toggle.

**Everything stays read-only.** No editing a file from the tree, no
staging or committing from the git panel, no code-editing widget. The UI's
own framing — "context inspector," not an IDE — does not change; it grows
a window onto the workspace it was already implicitly about, not a new
surface for changing it.

### Why tabs over a dropdown

A dropdown answers "which session am I on" only while open. Tabs answer it
at a glance and make "how many sessions exist" visible without a click —
the same reason every browser and editor uses tabs for exactly this. The
underlying state (`store.js:91-92`, `state.sessions` /
`state.currentSessionId`) and the switch/delete functions
(`app.html:41-44`'s `onSwitchSession`, `store.js:982-996`'s `deleteSession`)
do not change — this is a rendering change, not a new state model.

### Why the debug panel moves rather than staying a fourth column

A fourth column was considered and rejected: three panels plus a debug
sidebar is a lot of screen for a window that already collapses the
right-hand panel under 60rem (`app.html:1030-1033`). Folding Debug into the
Inspector's mode switch costs one click to see it and buys back a whole
column's width for content that actually wants it — a file or a diff reads
better wide than the debug panel, which is short label/value pairs, does
not.

### Why the file tree and git panel are new backend endpoints, not the agent's own tools

`luu` already has `list_dir`/`read_file`/`run_command` tools, but every one
of them is a **model's** action, gated by job approval
(`app.html:725-776`'s gate). A person opening the Files tab is not proposing
a job — routing a passive read through the approval flow would either
require rubber-stamping a job nobody asked the model to propose, or
inventing a second read path that bypasses the gate, which is worse: now
there are two ways to read a file and only one is audited. The actual
answer is what the design already does for the *read* side of the session
API (`serve.rs:854-873`, `/api/sessions/*`) — plain, ungated `GET`s, because
the person is not the agent and reading a directory listing is not a tool
call.

New routes, beside the existing table (`serve.rs:840-882`):

- `GET /api/workspace/tree` — walks from the session's `Sandbox::base()`
  (`sandbox/mod.rs:396`), gitignore-aware, merged with `git status
  --porcelain` output by path so the response carries both "ignored" and
  "changed" per entry in one shape the Files component can render directly.
- `GET /api/workspace/file?path=...` — file contents, scoped through
  `Sandbox::check_path` (`sandbox/mod.rs:451`), the same access check every
  other read in this codebase already goes through. No new access model.
- `GET /api/workspace/git-status` — `git status --porcelain`, structured.
- `GET /api/workspace/git-diff?path=...` — a diff, computed server-side
  (see below), not raw text.

### Why the diff is computed in Rust, not diffed in the browser

`luu-design.md:834` already decided this for prompt diffs and never built
it: "compute the prompt diff in Rust (`similar`), and send resolved spans
over the protocol... the server holds both strings anyway." The same
argument applies to a git diff — `git diff` itself already produces one, so
this is really "parse `git diff`'s own output, or compute spans with
`similar` over the two blobs" rather than reinvent diffing; either way nothing
diff-shaped ships to the browser. Reusing `similar` here is also the first
real user of the pattern the design doc named but never needed until now.

### Why the tree/git code is new rather than reused from `repo_map`

`repo_map.rs:205`'s `walk_sources` looks like it should be reusable — it
already walks the sandbox — but it is `.rs`-only and exists to parse tags
for the repository map, not to produce a general file tree, and has no
gitignore awareness. Making it general-purpose would grow a module that has
one job today into one with two unrelated jobs (feeding the model's context
budget vs. rendering a person's file tree) for a savings that is mostly
"a walk exists already," which the `ignore` crate provides more completely
(gitignore semantics included) than adapting `repo_map` would.

### Two new dependencies

- **`ignore`** (the ripgrep author's crate) — gitignore-aware directory
  walking. Nothing in this workspace does this today; `repo_map.rs` walks
  but does not consult `.gitignore`.
- **`similar`** — diff computation, named but never added by
  `luu-design.md:834`.

Both are pure Rust, no build step, consistent with the "cargo build needs
no node" constraint that picked `jq79` over a bundled frontend in the first
place (`luu-design.md:816-820`).

### Why the new panels are separate components, not a bigger `app.html`

`app.html` is 1220 lines today, one monolithic jq79 component. jq79 itself
supports "`.html` files loaded at runtime" as components
(`luu-design.md:819`) — nothing in this repo has used that yet;
`index.html:12-15` only ever mounts `app.html`. Growing the monolith by
another few hundred lines per panel is the path of least resistance and
the wrong one: `inspector-files.html`, `inspector-git.html`, and
`content-viewer.html` as their own components keeps each one readable and
is what the framework was already chosen to support. The exact
parent-to-child mount mechanics are unverified in this codebase (no
existing example) and are the first thing implementation checks, before
committing further to the split.

## What it costs

- **Four new HTTP routes and two new dependencies** for what was previously
  a UI-only tool with a frozen v1 protocol
  (`2026-08-26.web-debug-client.completed.md`'s "the message enums are not
  frozen" resolved since, per `luu-design.md:704`). None of the four routes
  touch the WebSocket protocol or the record format — they are plain reads,
  versioned the same loose way `/api/sessions/*` already is, not folded into
  the frozen `v1` message enums.
- **A layout that is harder to collapse cleanly on narrow screens.** Two
  columns already hide the right one under 60rem
  (`app.html:1030-1033`); three columns needs its own answer, not decided
  here (see Still open).
- **Screen real estate the debug panel used to have alone**, now shared
  with two other modes behind a click. Accepted: the debug panel is used
  less often, per session, than either the ability to see what a session
  touched, or the file tree — but this is a judgment call, not measured.
- **The known-undocumented `git status --short` exit-128 finding from
  machine 4** becomes load-bearing rather than an aside. It was found
  inside the *agent's* sandboxed `run_command` path, and this proposal's
  git endpoint shells directly from `serve.rs`, outside that sandbox
  entirely — plausibly unaffected, not yet confirmed. Phase 4's first step
  is reproducing it directly, not assuming either way.

## Still open

- **Exact column widths**, and what the narrow-screen breakpoint becomes
  with three columns instead of two (`app.html:1030-1033`'s current
  two-column collapse doesn't generalize on its own).
- **Whether the Debug mode's current dense layout survives being one of
  three Inspector tabs** rather than the whole right rail, or wants
  simplifying now that it has less default width.
- **The jq79 parent→child component mount mechanics** — assumed possible
  per `luu-design.md:819`, not yet exercised anywhere in this codebase.
- **Whether `git status --short` still exits 128 on machine 4** from a
  direct `serve.rs` shell-out, separate from the sandboxed path that found
  it.
- **Any editing capability** (write from the tree, stage/commit from the
  git panel) is out of scope by design here, not merely deferred — this
  proposal is read-only throughout; a future one would need its own
  argument for crossing that line, the same way every write in this
  project goes through the job-approval gate today.

## 2026-09-15, later: phase 1 built — the three columns, the modes, the tabs

The layout half of the proposal above, landed. No backend change, no new
dependency: everything here is `crates/luu/ui/`.

**Four new components, and the first time this project has composed two.**
`inspector-debug.html` is the panel that used to be `app.html`'s whole right
column, moved rather than rewritten — it imports `store.js` directly and
recomputes its own `view`/`folds`/budget values, so `app.html` no longer
carries any of them. `inspector-files.html`, `inspector-git.html` and
`content-viewer.html` are stubs that say what they will hold and which phase
holds it; a panel that renders nothing reads as a bug, and these will be on
screen for as long as phases 3 and 4 take.

**The one mechanical thing worth writing down, because the file's own first
comment already warned about it and the warning was still easy to walk
into:** a `:setup` script has no static `import`. `import X from "./x.html"`
parses as a module statement the page cannot run and the whole app fails to
mount with `Cannot use import statement outside a module` — the symptom is a
blank page, not a stack trace pointing at the line. The form that works is
`const X = await import("./x.html")`, which jq79 rewrites to its own loader;
that loader answers an `.html` specifier with **the component itself**, not a
module namespace, so there is no `.default` to destructure. Nothing in the
tree demonstrated either half before this.

**And a build-loop one:** `rust-embed` bakes `ui/` into a release binary, so
a UI edit is invisible until `cargo build --release` runs again. Debug builds
read from disk (`#[cfg(debug_assertions)]`), which is the loop to use while
iterating; a smoke run against a stale release binary tests the old page and
says so nowhere.

**Breakpoints, which the proposal left open.** Three columns above 64rem;
64rem down to 48rem drops the viewer (it is the pane that is empty until
something is selected); below 48rem only the chat survives, since it is the
one being talked into. The first attempt dropped the viewer under 90rem,
which took the middle column away from a 1280px laptop — the common case,
not the narrow one. Caught by the new smoke test, which now pins its own
viewport rather than inheriting Playwright's 1280px default and asserting
whatever that happens to straddle.

**Widths**: 20rem inspector, 30rem chat, the middle flexible. Still a
judgment call rather than a measurement.

`tests/smoke/gate.spec.js` gains one test (the three panes, the mode switch,
the tab strip) and one changed selector: the `+ New` button beside the old
dropdown is now the `+` at the end of the tab strip. Four gate tests pass,
`cargo test --workspace` is green (432 tests), clippy under `-D warnings` and
`fmt --check` clean.

### Still open after phase 1

- Phases 2, 3 and 4 — the preferences menu and theme toggle, the file tree,
  the git panel — are untouched, and the three "Still open" items about
  widths, the Debug mode's density, and the machine-4 `git` exit-128 finding
  stand exactly as written above.
- **The shared module the Files/Git panels will talk to the viewer
  through** is named in `content-viewer.html`'s own comment and does not
  exist: nothing selects anything yet, so nothing has had to.

## 2026-09-15, later still: phases 2, 3 and 4 — preferences, the tree, the diff

The rest of the proposal, built. Phase 2 (the hamburger, the preferences
modal, the light theme) is described in its own commit and adds no backend.
Phases 3 and 4 are below.

**Four read-only routes, in a new `crates/luu/src/workspace.rs`**:
`/api/workspace/{tree,file,git-status,git-diff}`. Every path goes through
`Sandbox::check_path`, which is what makes them safe — not string handling
here. `..` traversal is refused by the sandbox rather than by a filter
(`../../../etc/passwd` comes back "no rule grants read on
/home/joshua/etc/passwd"), and a leading `/` is stripped so an absolute path
is read as relative to the base rather than as an escape.

**Ignored entries are found by difference**, which is the one design choice
in the tree worth naming. `ignore`'s walker answers "what is *not* ignored
in this directory" and `read_dir` answers "what is there"; the difference is
what git ignores. A matcher built by hand over the root `.gitignore` would
have been fewer moving parts and wrong about nested ignore files, negations
and the global config — the walker already implements all three.

**The diff is parsed, not re-diffed.** `luu-design.md`'s "compute the diff in
Rust and send resolved spans" named `similar`, and `similar` was not added:
git already emits a unified diff, so the server parses that into hunks and
classified lines. Same destination — nothing diff-shaped reaches the browser
— with one less dependency and no second diff implementation to disagree with
git's.

### Two bugs found by running it, both worth the writing down

**Git's `XY` status code was being trimmed, and the two positions are the
whole meaning.** X is the index against `HEAD`, Y the working tree against
the index, so ` M` and `M ` are opposite facts and the space is what says
which. Trimming made every unstaged change look staged, so the Git panel
asked git for the staged side of a file that had nothing staged and rendered
an empty diff with a note explaining why. The bug was invisible in the
endpoint's own output (`"M"` looks like a fine answer) and only showed up as
a panel that did nothing on click.

**A scope variable named `selected` collides with the DOM property of that
name and loops the render effect.** jq79 gives up after 100 passes with
`an effect re-woke itself 100 times in a row (it writes what it reads)` and a
console location inside `jq79.js` — naming neither the variable, nor the
component, nor the file. It was found by bisection: minimal component, add
one line at a time, and the loop appeared with `$: selected =
workspace.selected` and disappeared under any other name. The variables are
`picked` now, with a comment at each site.

That second one is a genuine upstream footgun rather than a mistake this
repo made: the failure mode is a page that silently stops updating, and
nothing in the message points at the cause. `luu-design.md`'s own promotion
rule ("a gap moves upstream when it cannot be expressed in userland") applies
— a userland fix is "know the list of DOM property names", which is not a
thing to know.

### Also worth knowing

- **The smoke tests' first-run dialog is order-dependent.** It opens only
  when the server says it is unconfigured, and the posture test starts a
  session, which configures it — so a test that waits for the dialog passes
  in a full run and fails alone, and one that probes for it with
  `isVisible()` races it and then has every click eaten by its backdrop.
  `dismissFirstRun()` waits up to five seconds and shrugs, which is the only
  honest description of two legitimate states. All six gate tests now pass
  both together and one at a time.
- **`git` here does not go through the tool sandbox**, so the
  `/dev/null` and `~/.gitconfig` findings in
  [`git-could-not-open-dev-null`](2026-09-15.git-could-not-open-dev-null.completed.md)
  do not reach it: this is the server reading its own working directory for
  the person looking at it.

### Still open after phases 2–4

- **File icons and syntax highlighting**, both asked for after this was
  built: VSCode-style icons (ideally by loading a VSCode icon theme rather
  than vendoring one) and `tree-sitter-highlight` for the viewer. Neither is
  started; the highlighting half fits the same "resolved spans from the
  server" shape the diff already uses, and this repo already depends on
  `tree-sitter`.
- The three widths, the Debug mode's density, and the container posture's
  `/dev` are all unchanged from the sections above.
- **Nothing refreshes the tree when the agent writes a file.** The panel has
  a refresh button and uses it; a job that edits three files leaves the tree
  stale until somebody clicks. The turn already emits `tool_result`, so the
  hook exists and is not wired.

## 2026-09-15, the proposal for phases 5 and 6: icons and highlighting

Asked for after phases 3 and 4 landed, and written before the code per this
repo's own rule. Two additions to the panels that now exist.

### Phase 5 — file icons, by loading a VSCode icon theme rather than vendoring one

**The ask was "ideally, apply VSCode icon themes", and that is achievable
literally**, so the design answers the general question instead of shipping
one theme. A VSCode icon theme is a JSON file with `iconDefinitions` (id →
`{iconPath}`) plus `fileExtensions`, `fileNames`, `folderNames` and
`languageIds` maps and a few defaults (`file`, `folder`, `folderExpanded`,
`rootFolder`). An extension points at it from `package.json`'s
`contributes.iconThemes[].path`. Both shapes are two dozen lines to read.

**Rejected: vendoring `vscode-great-icons`.** Measured rather than guessed —
263 icons, 1.5 MB of SVG, 3.0 MB of repository. It would put icons on screen
with nothing configured, and it would put 1.5 MB into a binary whose whole UI
is otherwise "one `jq79.js` plus a handful of `.html` files", tie the page to
one theme's taste, and make this repo a redistributor of someone else's art.
The pattern this project already uses for "a thing that lives on your machine,
not in this repository" is the sandbox's `~/.cargo` line: **the user names
it.**

- `[ui] icon-theme = "<path>"` in `config.toml`, pointing at either an
  extension directory or a theme JSON directly.
- `GET /api/icons/manifest` — the resolved maps, by icon **id**.
- `GET /api/icons/{id}` — that icon's bytes.

**The id is the whole security design.** No path from the client ever reaches
the filesystem: the manifest is read once at startup into an id → absolute
path table, and only ids in that table are servable. A client cannot ask for a
file the theme did not declare, so there is no traversal to get wrong.

**And a fallback, deliberately small**: two inline glyphs, a document and a
folder, in the component itself. Not a second icon set — enough that an
unconfigured tree reads as intentional rather than broken.

### Phase 6 — syntax highlighting with `tree-sitter-highlight`

The same shape as the diff, and for the same reason `luu-design.md` gives:
**resolved spans from the server, never a highlighter in the browser.** This
repo already depends on `tree-sitter`, so this is the crate's second use
rather than a new idea.

- `tree-sitter-highlight`, plus a grammar crate per language. Broad coverage
  was chosen over "only what this repo is written in": Rust, JS/TS, HTML, CSS,
  TOML, Markdown, JSON, Python, Go, C/C++, YAML and shell. The cost is
  compile time for grammars this repository does not itself contain; the
  benefit is that the viewer is useful against any checkout a person points
  `luu` at, which is what it is for.
- One language table, extension → grammar and query, so a thirteenth is one
  line.
- **The wire format is pre-sliced chunks, not offsets.** `FileView` stops
  carrying `text` and carries `lines: Vec<Vec<Chunk>>`, each `Chunk` a
  `{ text, kind }`. Offsets would mean Rust byte indices being read as
  JavaScript UTF-16 indices, which is correct until the first non-ASCII
  character and then silently is not. A file with no grammar is one chunk per
  line with a null kind, so the viewer has one code path.
- Highlighting is capped below the 512 KB read cap: a large file still opens,
  unhighlighted, rather than costing a parse nobody asked for.

### What this does not do

- **No theme for the highlight colours.** The capture names map to the
  palette this page already has, which means highlighting follows the
  light/dark toggle for free and does not acquire a second theme system.
- **No icon theme switching from the page.** One theme, named in the file,
  changed by editing it — the same place the destination and the postures are
  named.

## 2026-09-15, phases 5 and 6 built: icons from a named theme, highlighting from tree-sitter

Both as proposed, and both cheaper than expected.

**The icon loader is about sixty lines and reads any VSCode icon theme.**
Extension directory or theme JSON, `package.json` →
`contributes.iconThemes[0].path` → the theme's maps. Verified against
`vscode-great-icons` itself: 585 extensions, 307 filenames, 63 folders, and
the tree renders its art. With nothing configured the same tree draws its two
glyphs, which the gate suite asserts, because that is the state anybody gets
before they have read this.

**The id table is doing real work, not ceremony.** Two things are dropped at
load: a definition whose file is missing (themes carry entries for art they no
longer ship — dropping the map entry too means the page never asks for a dead
id), and a definition whose `iconPath` canonicalizes outside the theme's own
directory. The second has a test with `../../../etc/hosts` in it. A client
cannot ask for a path at all — `/api/icons/{id}` looks the id up or answers
404, and `..%2f..%2fetc%2fpasswd` as an id is simply an id that is not there.

**Highlighting cost one dependency and thirteen grammars**, and the format
decision was the one that mattered: **pre-sliced chunks rather than offsets.**
The test that would have caught the offset bug is
`the_chunks_join_back_into_the_file`, which uses `"ñ á"` deliberately — Rust
byte indices read as JavaScript UTF-16 indices agree until exactly there.

Two smaller things the shape forced:

- **A span may cross a newline** — a block comment, a multi-line string — and
  a line is what the viewer lays out, so each source span is split on `\n` and
  its pieces pushed onto the lines they belong to. `no_chunk_contains_a_newline`
  is the assertion that keeps that true.
- **Captures nest**, so the highlighter's events are a stack and the innermost
  capture is the one that wins. Adjacent chunks with the same kind are merged,
  or a line of Rust arrives as one span per token the parser felt like emitting.

**Everything funnels into one shape**: an unknown extension, a file over the
256 KB highlight cap, and a parse that failed all return one chunk per line
with no kind, so the viewer has one code path and no special cases. The colours
are the page's own tokens, so the viewer follows the light/dark toggle without
a second theme system.

### Still open after phases 5 and 6

- **`similar` is still not a dependency**, and the prompt-diff feature
  `luu-design.md` named it for is still unbuilt. This record's diff parses
  git's output instead, so nothing here needed it.
- **Nothing refreshes the tree when the agent writes a file** — unchanged from
  the section above, and now slightly more visible: an icon and a status letter
  both go stale.
- **The icon theme is read once at startup.** Editing `config.toml` while the
  server runs changes nothing until it restarts, the same as the postures.
- **No `light`/`highContrast` icon variants.** VSCode themes may declare
  separate art for light backgrounds; this reads only the default set, so a
  theme whose icons assume a dark ground will look wrong under the light theme.
  Not hit with `vscode-great-icons`, not checked with anything else.

## 2026-09-15, phase 7: the page's own chrome, drawn rather than typed

Reported from a screenshot of a tree with no theme configured — *"no veo los
iconos, ¿no había un fallback?"* The fallback was there and working: `▪` and
`▫` at 9px. At 9px a filled small square and a hollow one are two specks, and
two specks read as a rendering failure rather than as a choice. Phase 5 called
that fallback "deliberately small"; the first person to meet it could not tell
it from a bug. The same reading applies to every other symbol this page types
instead of drawing.

### The inventory, because the problem is the set and not one glyph

| symbol | where | doing the job of |
| --- | --- | --- |
| `↻` U+21BB | the Files head, the Git head | refresh |
| `▾` `▸` U+25BE U+25B8 | the tree's twist, the fold head | a disclosure caret |
| `▪` `▫` U+25AA U+25AB | the tree with no theme | a file, a folder |
| `≡` U+2261 | the header | a menu |
| `+` U+002B | the last tab | new session |
| `→` U+2192 | `use →`, the fold's token line | an arrow in running text |

**A text glyph is not a small icon.** Its size, weight, baseline and advance
width belong to whichever font on the machine happens to carry that codepoint,
and nothing about them is the page's to choose: `↻` is a hairline in one family
and a heavy stroke in the next, `≡` is a mathematical operator standing in for
a hamburger, and the two squares are the extreme case — a *font's* idea of
"small", scaled by a `font-size` that was picked for letters. None of them
lands on the 16px box the theme's file icons now occupy, so the column of icons
the theme draws and the column of glyphs the page types do not line up, and the
tree looks like two different programs rendered it.

**The last row stays.** `→` inside `use →`, and inside "1204 tokens of history
→ 96", is prose and not a control. A typographic arrow is the right character
for prose, and an SVG there would be a picture of a word.

### The proposal: one sprite of `<symbol>`s, stroked in `currentColor`

An inline `<svg hidden>` at the top of `app.html` carrying one `<symbol>` per
shape, and `<svg class="ic"><use href="#i-…"/></svg>` at each use site. Six
shapes: caret, refresh, menu, close, plus, and the file/folder pair the
unconfigured tree falls back to.

- **`currentColor` and nothing else.** Every one is a stroke, no fill, so a
  symbol inherits the colour of the control it sits in — `--dim` in a head,
  `--on-accent` on a selected row, `--accent` on the new-session tab — and the
  light theme needs no second set. This is the same rule the highlighter
  already follows: the page's own tokens, never a palette of its own.
- **One caret, rotated.** `▾` and `▸` were two codepoints for one control. The
  sprite has a single chevron and `.ic.open { transform: rotate(90deg) }`, so
  what the screen shows is the same triangle turned. No transition: this page
  has no animation anywhere, and one lone 120ms rotate would be the exception
  that has to be explained.
- **Global, in `app.css`.** The sub-components' `<style scoped>` is rewritten
  per component, so a class shared by four files cannot live in any one of
  them. `app.css` already holds the tokens for the same reason.

**Rejected: an icon font.** A second network request, a `@font-face`, and a
set of private-use codepoints that are exactly as font-dependent as the
characters this is replacing — the failure mode it fixes is the failure mode it
is made of.

**Rejected: vendoring an icon pack.** Phase 5 argued this out for file art and
nothing about the argument changes: this is six shapes of chrome at about 150
bytes each, and a pack would be a dependency, a licence and someone else's
taste for a set that has to match this page's stroke weight and no one else's.
Six hand-drawn paths *are* the small answer.

**Rejected: an inline `<svg>` per use site.** The caret appears in two files
and refresh in two more; copied markup is four places to fix a stroke width.
`<use>` is the platform's own answer and costs one element.

**Rejected: CSS `mask-image` with data URIs.** It gives `currentColor` too, and
in one place — but a URL-encoded SVG in a stylesheet is not readable, and the
shapes are the part of this change a person will want to argue with.

### And the control that was missing: closing a tab

`deleteSession` has been imported into `app.html` since the tabs were built and
wired to nothing — the strip can start sessions and switch between them, and
the only way to remove one is `curl -X DELETE`. The × belongs on the tab, so
it is part of this change rather than a separate one.

- **Only where the server would accept it.** `delete_session_handler` refuses
  the live session and the active one with `cannot delete active session`, so
  the × is not rendered on those two tabs. A control that is only ever refused
  is worse than no control.
- **Two clicks, not a `confirm()`.** Closing a tab here *is* deleting the
  stored session — its stream and its fold, out of SQLite, unrecoverable. The
  first click arms the × (it turns `--bad` and says so in its title), a second
  deletes, and a click anywhere else in the strip disarms it. A browser
  `confirm()` would be one line and would be the only modal dialog in a page
  that already has its own; arming is the smaller of the two.

### What it costs

A sprite in the shell's template, six paths, about thirty lines of CSS, and one
new interaction. No dependency, no request, no build step. The risk worth
naming is jq79's: its compiler rebuilds each node with
`createElementNS(node.namespaceURI, tag)`, so SVG in a template is carried
through correctly — but that had never been exercised in this page before, and
the check is a screenshot of the running server rather than a reading of the
minified runtime.

### Still open after phase 7

- **The `▫` was hiding a second bug.** The fallback's condition is
  `!workspace.icons.loaded`, not `!iconFor(row)`, so a theme that loads without
  declaring a `file`/`folder` default draws neither the theme's icon nor the
  page's own, and the row loses its 16px box. `vscode-great-icons` declares
  both, which is why nothing showed it. Fixed here with the rest.
- **Nothing refreshes the tree when the agent writes a file** — unchanged.

## 2026-09-15, phase 7 built: seven symbols, and the × the tabs never had

Built as proposed. The sprite is at the top of `app.html`, `.ic` and `.sprite`
are in `app.css`, and the use sites are the Files head, the Git head, the
tree's twist and fallback, the fold head, the header's menu, and both tab
controls.

**jq79 carries SVG through, and now it is known rather than assumed.** Its
compiler rebuilds every node with `createElementNS(node.namespaceURI, tag)`,
so a `<svg>` written in a template is parsed by the HTML parser, keeps the SVG
namespace and its `viewBox` casing, and is recreated in that namespace — and
`:attrs` sets attributes with `setAttribute`, so `href` on a `<use>` can be
bound (`row.dir ? '#i-folder' : '#i-file'`) rather than needing two elements
with two `:if`s. Nothing about this page had exercised it before. Checked in
Chrome against the running server, dark and light, themed and unthemed: seven
symbols in the sprite, sixteen `<use>`s on screen, no console errors.

**The refresh was drawn twice.** The first arc was r=8 with a head about four
units long, which reads at 96px and is a nub at 16 — the size the icon is
actually used at. r=7 with a five-unit head is the one that survives the
16px box, and the 12px one the twist uses. The lesson is the obvious one and
was still worth paying for once: an icon is designed at the size it is shown,
and a specimen sheet that only shows it large will approve a shape that does
not work.

**The `+` was in the smoke suite as text.** `gate.spec.js` asserted
`.session-tabs .tab.new` had the text `"+"`, which a drawn plus is not, so the
change broke a test that was right to break. It now asserts the sprite has its
seven symbols and the tab uses `#i-plus` — a sprite that stops rendering blanks
every symbol at once, which is worth one assertion of its own. The unthemed
tree's test kept its `.glyph` locator and gained the two `<use>`s and the
caret.

**The tab close could not be tested there.** The gate server runs with
`--no-store`, and `delete_session_handler` answers `501 session store is
disabled` without one, so the suite cannot exercise the ×. It was driven by
hand instead, against a server with a scratch `LUU_HOME`: arm, disarm with a
click elsewhere in the strip, arm again, delete — four tabs to three, and the
id the server removed is the one the tab named.

**A tab is no longer a `<button>`.** It is a `<span class="tab">` holding two
buttons, because a button inside a button is not markup a browser will parse.
`.tab` keeps its class, its `.on` and the strip's layout, which is what the
smoke suite and the CSS both address it by.

### Still open after phase 7

- **The `→` in `use →` and in the fold's token line is still a text glyph**,
  deliberately: it is prose, not a control.
- **No `light`/`highContrast` icon variants** — unchanged, and now with one
  fewer place it could bite: the page's own symbols are `currentColor` and
  follow the theme, so only a *theme's* art can be wrong on a light ground.
- **Nothing refreshes the tree when the agent writes a file** — unchanged.

## 2026-09-15, phase 8: where the viewer's time actually goes

Proposed from the outside as *"load the file uncoloured as fast as possible,
then colour it progressively with WebAssembly, top to bottom"*. The instinct
about the symptom is right — a big file takes a visible moment to appear — and
the diagnosis was worth checking before building anything, because it
contradicts a decision this document has recorded: **resolved spans from the
server, never a highlighter in the browser.**

### Measured first, on the release binary over loopback

Median of nine, `GET /api/workspace/file`:

| file | bytes | server |
| --- | --- | --- |
| a 6-byte `.toml` | 6 | **0.6 ms** |
| a 13-byte `.rs` | 13 | **15.2 ms** |
| `crates/luu/src/icons.rs` | 12 K | 16.4 ms |
| `crates/luu/ui/store.js` | 37 K | 18.0 ms |
| `crates/luu/src/serve.rs` | 153 K | **40.5 ms** |

Thirteen bytes of Rust cost 15 ms and 153 KB cost 40, so the cost is not the
parse: **~15 ms of it is fixed per request**, and it is
`HighlightConfiguration::new` recompiling `HIGHLIGHTS_QUERY` and
`INJECTIONS_QUERY` from scratch every time `language_for` is called. TOML costs
0.6 ms because TOML's queries are tiny. That is finding one.

Then the same bytes in the browser:

```
crates/luu/src/serve.rs   3807 lines   fetch+parse 40 ms   render+paint 415 ms
```

And the ladder, on generated files with no grammar at all — no colour anywhere
in the picture:

```
  50 lines    28 ms
 250 lines    30 ms
1000 lines    66 ms
2000 lines   119 ms
4000 lines   225 ms
```

About 50 µs a line, and the same file served **with** colour and **without**
it (copied to `.txt`, one chunk per line instead of six) paints in 425 ms and
477 ms — the same, within noise. **The cost is the `<li>` per line, not the
`<code>` per chunk.** That is finding two, and it is the one that decides the
proposal.

### So the proposal is answered by its own measurement

- **Loading it uncoloured first buys nothing**: the uncoloured render costs the
  same ~450 ms, and then the colour pass pays it again.
- **WebAssembly would move the highlighting onto the thread that is already the
  bottleneck**, and would not remove one `<li>`. The server's share is 40 ms
  against the browser's 415.
- The rest of the objection is the one phase 5 already made about art: the whole
  UI is `jq79.js` (56 KB) and a handful of `.html` files embedded in the binary,
  this repo has no bundler on purpose, and `luu export`'s static twin serves
  these same views — so the Rust highlighter would stay anyway and there would
  be two.

**What survives is the shape of the idea, pointed at the right half**: show
something immediately and finish in the background. That is the *render*, not
the colouring.

### What is built instead

**1. The compiled queries are cached.** `language_for` returns a
`&'static HighlightConfiguration` out of a `LazyLock` per language rather than
building one per request. Nothing else changes: same grammars, same `NAMES`,
same output. ~15 ms off every Rust file.

**2. The viewer builds its rows a frame at a time.** The file still arrives
whole and already highlighted — `workspace.shownLines` says how much of it is
in the DOM, starts at what a screen holds, and grows by a batch per
`requestAnimationFrame` until the file is all there. First paint stops
depending on the file's length, and the page answers a click or a scroll while
the tail is still being built.

**Rejected: virtualising the list.** Rendering only the visible window and
spacing the rest with padding is the smaller total, and it breaks the two
things this panel is for: the browser's own find-in-page, and selecting the
whole file to copy it. A debug viewer that cannot be searched is worse than one
that takes 200 ms to finish.

**Rejected: a cap with a "show the rest" button.** It makes the person do the
scheduling, and it answers a question about *this* viewer with a change to what
the viewer means.

**The batch is 400 lines**, which is about 20 ms at 50 µs a line — under one
frame at 60 Hz with room left for the rest of the page. The first batch is the
same number rather than a screen's worth exactly: a screen is a fact about the
window size, and a viewer that reads its own height to decide what to render is
a viewer that has to re-decide on every resize.

### What is *not* built

- **The diff has the same shape and is not batched.** A 4000-line diff builds
  4000 rows the same way. It is left alone because the measurement was taken on
  files and a change nobody measured is a change nobody can defend.
- **No compression.** `serve.rs` is 153 KB of source and 681 KB of JSON, which
  gzips to 59 KB. Over loopback that is a memcpy and worth nothing; the day
  `serve` is reached over a network it is worth more than everything above.

## 2026-09-15, phase 8 built — and the batching plan was wrong

Both halves are in. The first is exactly as proposed; the second is not, and
the measurement that changed it is the useful part of this section.

### The grammars, cached: the number was the number

`language_for` is split in two — `language_of` maps a filename to a grammar's
name, `GRAMMARS` is a `LazyLock<HashMap<&str, HighlightConfiguration>>` built
once — and `serve` calls `highlight::warm()` at startup, beside the icon theme
and for the same reason: a fixed cost belongs where somebody is watching the
process start, not inside the first click.

| file | before | after |
| --- | --- | --- |
| a 13-byte `.rs` | 15.2 ms | **0.6 ms** |
| `icons.rs` (12 K) | 16.4 ms | **2.4 ms** |
| `store.js` (37 K) | 18.0 ms | **6.5 ms** |
| `serve.rs` (153 K) | 40.5 ms | **20.4 ms** |

The fixed cost is gone: a tiny Rust file now costs what a tiny TOML file costs,
which is the round trip and nothing else. `serve serve` boots in 112 ms with
all fifteen grammars compiled, against nothing measurable before.

### The viewer: two passes, because jq79 rebuilds rather than appends

The plan said *a batch of 400 rows per frame*. Built and measured, on a
3807-line file:

```
t=  65.8 ms   rows  400        t=  47 ms per batch at first
t= 113.1 ms   rows  800        …and 125 ms per batch by the end
t= 187.3 ms   rows 1200
   …
t= 983.3 ms   rows 3807
```

First paint went from ~420 ms to 66 ms, and **the total went to 983 ms** — with
the per-batch cost climbing as the list grew. That shape is the answer:
**jq79's `:each` rebuilds the whole list off-DOM and attaches it whole**, so N
passes cost N rebuilds and the work is quadratic in the number of passes. A
`:key="$index"` was tried on the assumption that keying would let it reuse the
rows already built; it changed nothing measurable, so the rebuild is not about
identity.

Given a renderer that rebuilds, the thing to minimise is **the number of
passes, not the size of them**. Two: a screenful now, the whole file on the
next frame. One extra rebuild, and it is the cheapest possible one because it
is the smallest.

| | first rows on screen | whole file |
| --- | --- | --- |
| `store.js`, one pass | 132 ms | 132 ms |
| `store.js`, two passes | **91 ms** | 159 ms |
| `serve.rs`, one pass | 385 ms | 385 ms |
| `serve.rs`, two passes | **162 ms** | 396 ms |

(Debug server, so the server's share is inflated in both columns equally; on
the release binary the same file shows 200 rows at 66 ms and all 3807 at
292 ms.) Something to read arrives in a **third** of the time, and finishing
costs 3% more. `FIRST_ROWS = 200` is a screenful with room to scroll into, and
deliberately not the window's measured height: a viewer that measures itself
has to decide again on every resize.

### Two measurement traps, both worth writing down

**`rust-embed` bakes the UI into a release build.** Half an hour went into
"the viewer does not react to `shownLines`" before noticing the probe was
talking to `target/release/luu`, which was carrying the `.html` from before the
edit. Debug reads from disk; release does not. Behaviour is probed against
debug, timings against release, and neither substitutes for the other.

**A headless browser does not pace `requestAnimationFrame` at 60 Hz.** The
first attempt to watch the growth curve saw every batch collapse into one
frame. The instrument that works is a `MutationObserver` that snapshots the row
count — jq79 attaches the subtree whole, so counting added `<li>` nodes sees
44 rows of the *file tree* and none of the file.

### Still open after phase 8

- **The diff is still one pass.** Same shape, not measured, left alone.
- **Nothing streams.** The file arrives as one JSON body — `serve.rs` is 153 KB
  of source and 681 KB of JSON — and the two passes are over data the page
  already holds. Worth revisiting the day `serve` is reached over something
  slower than loopback, where the 59 KB it gzips to would matter more than
  everything in this section.

## 2026-09-16, phase 8 corrected: two blocks, not two slices

The section above got the count right — two passes — and the mechanism wrong.
It sliced one array in two and handed the viewer a *longer slice* on the second
pass, which means the `:each` is bound to a different array and jq79 rebuilds
the rows already on screen. Proposed from the outside, and it is the better
shape: **render two blocks, each its own `:each` over its own array.** The
first is assigned once and never touched again; the second starts empty and is
filled one frame later.

```html
<ol class="code">
  <li :each="line in workspace.head">…</li>
  <li :each="line in workspace.tail">…</li>
</ol>
```

**One `<ol>`, two groups.** The CSS counter that numbers the rows runs across
both, so the tail numbers itself and there is no offset to keep in step.

**And an empty block has a height.** While `tail` is empty, a spacer stands in
for the rows that have not arrived — `height: calc(var(--rows) * 1lh)`, with
the same font metrics a row has, so `1lh` is exactly one row. The file's line
count is already known when the head renders, so the scrollbar is the length of
the *file* from the first frame rather than the length of its first screen.
Measured, and this is the part that either works exactly or not at all:
`scrollHeight` is 68576 when the 200 head rows land and 68576 when all 3807 are
there. **The bar does not move.**

### What the first block surviving is worth

The identity check, taken while only the head was on screen and read again
after the tail landed:

```
first row still in the document after the tail landed: true
and still the first row: true
```

And the two things a person would actually lose if it were rebuilt under them:

```
selection before the tail landed: "use agent_core::approval::{Approval"
selection after:                  "use agent_core::approval::{Approval"   kept: true
scrolled to 900, after the tail landed 900                                kept: true
```

A selection made in the first screenful survives, and so does the scroll
position. That is the whole argument for two arrays over one growing one, and
it is not a timing argument at all.

### The numbers, one instrument, one build

Debug server, so the server's share is inflated in both columns equally:

| | something to read | whole file |
| --- | --- | --- |
| `store.js` (1002 lines), one pass | 119 ms | 119 ms |
| `store.js`, two blocks | **86 ms** | 153 ms |
| `serve.rs` (3807 lines), one pass | 357 ms | 357 ms |
| `serve.rs`, two blocks | **156 ms** | 385 ms |

On the release binary the same file puts 200 rows up at **53 ms** and finishes
at 271 ms. Finishing costs 8–28% more and that was accepted deliberately —
*"lo prioritario es la experiencia de usuario, si el total tarda más, no me
importa"* — but note what the two-block shape bought against the two-slice one
it replaced: the same first paint, and no rebuild of what is on screen.

### Still open after the correction

- **The tail is one block, so a very large file still has one long second
  render.** The shape generalises — N blocks, each its own `:each`, appended as
  they arrive, which would be linear rather than quadratic — but the template
  needs one `:each` element per block, and a `:each` of blocks containing a
  `:each` of rows would put the outer list back in jq79's rebuild path. Two is
  what the template can say plainly, and 271 ms for the largest file in this
  repository did not justify finding out.
- **Scrolling into the spacer before the tail lands shows blank.** One frame,
  in practice; it is the honest cost of a scrollbar that tells the truth early.
- **The diff is still one pass** — unchanged, still not measured.

## 2026-09-16, the file payload reads head-first

Two questions about `FileView`'s shape, asked after watching the viewer work:
should `language` and `truncated` come before the file, and is the line count
missing? Both were right, for different reasons.

**The order was `path, lines, language, truncated`**, and `serde` writes a
struct's fields in declaration order, so two small facts about the file sat
behind 681 KB of it. Nothing measurable — `JSON.parse` does not care — but it
is wrong twice over: for a person reading the response in devtools, who has to
scroll past the whole file to learn what language it is, and for any reader
that ever consumes this as a stream, for whom "after the body" means "never, in
time to matter". Now `path, language, truncated, total_lines, lines`: the facts
about the file, then the file.

**The count is not redundant, and that is the only reason it is there.** For
the viewer's spacer it would be — `lines.length` is already that number. What
it is for is `truncated`: `file()` reads the whole file and *then* cuts it at
512 KB, so the total is in hand and was being thrown away, leaving the panel
able to say *cut at 512 KB* and not how much of the file that left. It now
reads **`cut at 512 KB — 6255 of 20001 lines`**.

Counted over the whole bytes as `newlines + 1`, which is how the text is split
downstream, and `the_line_count_is_the_one_the_lines_themselves_come_to`
asserts the two agree over the cases where an off-by-one would hide: no
newline at all, a trailing newline, a file of nothing but newlines, and the
empty file.

**The spacer still sizes itself from `lines.length`, not from `total_lines`.**
They differ exactly when the file was cut, and what the scrollbar must measure
is the rows that will be rendered — not the rows the file has. A spacer on
`total_lines` would leave a truncated file with a scrollbar three times longer
than its content.

`total_lines` is an added field on an existing type, so by this repository's own
rule — a new variant bumps, a new optional field does not — nothing moved.

## 2026-09-16, Monaco, measured rather than argued

Asked whether the debug UI should use Monaco. The argument against it can be
made from the recorded decisions alone — read-only panel, no bundler, nothing
vendored, highlighting resolved on the server — but the interesting half is a
number, so it was measured: the same 50 543-line Rust file (1.86 MB, built by
concatenating this repository's own `.rs` files) in Monaco 0.56 and in this
viewer, Chrome, same machine.

### What Monaco costs to have at all

| | raw | gzip |
| --- | --- | --- |
| Monaco, the minimum that boots: core + loader + css + worker host + **one** language | **3.00 MB** | 818 KB |
| `crates/luu/ui` entire — every `.html`, `.js`, `.css`, and `jq79.js` | 0.18 MB | 60 KB |

Seventeen times the whole UI, before a single language service: `ts.worker.js`
alone is 6.4 MB and `min/vs` is 24 MB. Phase 5 rejected vendoring
`vscode-great-icons` at 1.5 MB, and that was optional art with a fallback.

### At 50 543 lines — a regime this viewer excludes

| | this viewer | Monaco |
| --- | --- | --- |
| something readable | 370 ms | 159 ms |
| the whole file | **5 848 ms** | 159 ms (it never builds the rest) |
| DOM nodes | 329 518 | **362** |
| JS heap | **813 MB** | 22.4 MB |
| jump to the last line | 172 ms | 38 ms |
| what the browser's own Ctrl+F can see | 2 178 885 chars | **2 051 chars** |

At this size it is not a contest: virtualising is the right engineering and we
do not do it. The server's share, for the record, was 280 ms to highlight
1.86 MB into 9.0 MB of JSON — still the cheap half.

### At 512 KB — what this viewer actually serves

The caps are the point: `MAX_FILE_BYTES` is 512 KB and `MAX_HIGHLIGHT_BYTES` is
256 KB, so the 1.86 MB file arrives as 13 530 lines **and no colour at all**.
The 50 000-line case is not one this UI can reach, and the two rows above were
taken with both caps temporarily raised to 8 MB and then put back.

| | this viewer | Monaco |
| --- | --- | --- |
| something readable | **38 ms** | 98 ms |
| the whole file | 533 ms | 98 ms |
| DOM nodes | 26 202 | **362** |
| JS heap | 66.3 MB | **21.3 MB** |
| over the network | **0.66 MB** | 4.80 MB |
| Ctrl+F sees | **522 939 chars** | 2 051 chars |
| jump to the end | **21 ms** | 36 ms |

**At the size this panel is actually asked for, this viewer puts text on screen
in a third of Monaco's time, over a seventh of the bytes, and the whole file is
searchable.** Monaco wins on memory and on finishing, and it wins outright the
moment the file is bigger than this UI allows.

### The conclusion, and the one thing the measurement did change

**No.** Monaco buys scaling into a regime the caps deliberately exclude, for
3 MB vendored into a binary whose entire UI is 180 KB, a bundler this repository
removed on purpose, a second highlighter against the recorded "resolved spans
from the server", and an editor in a panel that is read-only by design. And the
project already has an editor surface: `editors/vscode/` is surface #3 and
VSCode *is* Monaco. If the answer to "I want a real editor" is Monaco, it is
already built and it is the extension.

Note also that adopting it would **impose** the cost that virtualising our own
list was rejected for: Ctrl+F sees 2 051 characters of a 13 530-line file.

What the measurement did surface, and it is not about Monaco: **a file between
256 KB and 512 KB is shown with no syntax colour at all**, because the
highlight cap is half the read cap. Nothing in this repository is that big — the
largest is `serve.rs` at 153 KB — so it has never been hit, but the number a
person meets first is a policy number nobody has revisited since it was
written.

### Still open

- **Virtualising our own list** remains the cheap way to get Monaco's DOM and
  memory profile — about forty lines, the same Ctrl+F loss, and none of the
  3 MB. Not built, and not needed while the cap holds.
- **The two caps are unexamined.** 512 KB to read, 256 KB to colour; the second
  being lower than the first is what produces a colourless file rather than a
  refused one.
