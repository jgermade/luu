# A session is a runtime and three lists, the first one included

Row 51 of [`ROADMAP/2026-11-08`](../ROADMAP/2026-11-08/README.md), decided *B*
in [`five-decisions`](2026-11-09.five-decisions.WIP.md) and handed to this
session with one question to ask before building.

## The question, and the answer

**Asked:** `[posture.*]` and `[environment.*]` go. Does the server's own policy
file — the `luu.toml` of the directory `serve` was started in, or `--sandbox` —
go with them? It is what the first session of a `serve` runs under.

> Los permisos se definen por instancia (instalación) de luu, cada sesión hace
> una copia de las elegidas por el usuario

So it goes, and that is the alternative `five-decisions` did not recommend.
The permissions are the instance's — the lists in the state directory's
`config.toml` — and a session is a copy of the ones a person chose. A file in
the working directory is neither.

## The proposal

**In `serve`, nothing is a session's policy but lists.**

| | Before | Now |
| --- | --- | --- |
| `[posture.<name>]`, `[environment.<name>]` | read; the second resolved by name | an unknown table: `config.toml` does not load |
| `POST /api/sessions` with `posture` | a session by name | 400, an unknown field |
| `POST /api/sessions` with no lists | the server's own file | host, three empty lists |
| the first session of a `serve` | the server's own file | host, three empty lists (`--worker` and `--worker-image` move it) |
| `serve --sandbox FILE` | the file every nameless session ran under | refused when `serve` starts |
| `./luu.toml` where `serve` starts | the same, unasked | not read |
| `PUT /api/session/posture` | a live move by name | gone; `PUT /api/session/runtime` is the move |
| resume of a session with no copy of its lists | by name, or the server's file | 409: it is read, and not resumed |
| the image `serve` was started on | `--worker-image`, or its file's `[worker] image` | `--worker-image` |
| Settings → Runtimes' images | `[image.*]`, postures, policy files in the checkout | `[image.*]`, and `--worker-image` |

An empty list allows nothing: the session reads its folder, writes to scratch
and asks the rest (*two zones*,
[`policies-not-postures`](2026-10-22.policies-not-postures.WIP.md)). So a
`serve` started with nothing in `config.toml` asks about every command, and
what a person answers *always in this project* is what it stops asking.

The `--allow-*` flags still add to every session of the `serve` they were
typed on: a flag is typed by whoever starts the instance, and it is in the
header (`Lists` are read back off the sandbox).

**In the code.** `policies::Environment` and `Policies::environments` go;
`compose` builds a `Resolved` from a place and three lists directly, and every
`Resolved` is one. `serve::Chosen` loses `File`. `App::postures`,
`App::environments`, `environments_of` and `provider::Posture` go.
`record::Posture` — *where a session ran* — is untouched, and so is the record
format.

**In the page.** The terminal's place picker and the runtime dialog offer
runtimes and images, never names. Settings → Policies loses the environment
table and `usedBy`; Settings → Runtimes loses the posture table and the
checkout's policy files.

**What ships a policy file today stops**: `deploy/entrypoint.sh`, the Helm
chart's `policy` value and its ConfigMap, `pages/setup.sh`'s
`/etc/luu/luu.toml`. None of them reached a session started from the dialog
already — a composed session never read the server's file.

## What it costs

- **`[sandbox.env]` and `[sandbox.limits]` have no list.** `deploy/luu.toml`
  set `TMPDIR` and `CARGO_HOME` for the first session's commands, and limits
  for them. A composed session has had the default limits and no `env` since
  2026-10-23; now the first one does too.
- **A session recorded on a policy file is not resumed.** No compatibility, by
  72(c)'s answer. It is still listed, read and replayed.
- **The gate's specs started their sessions on `wide`, by name.** They start on
  lists now, which is what a person does.

## Rejected

- **The recommendation** (the server's file stays the default session's):
  answered against, above.
- **A `default` list of each axis for the first session**: a second way to say
  what `prefs.start` already says in the page, and a name with a meaning in a
  table that has none.
- **Reading old tables and warning**: 72(c).

## Still open

- **`luu chat`, `luu tools`, `luu map` and `luu select` still take
  `--sandbox FILE`, and `./luu.toml` where it is.** A one-shot is not a session
  a person composes in a dialog, every recipe in `AGENTS.md` and every run in
  `RECORD/` was made under this repository's `luu.toml`, and
  `scripts/container-check.sh` reads `[worker]` from `luu.container.toml`. By
  the answer above they should name lists of the instance too
  (`--shell NAME --network NAME --files NAME` over `config.toml`). That is row
  50's half of this, and it wants the runs' recipes rewritten with it.
- **Where `env` and `limits` live** once no file carries them: a fourth table,
  or keys of `[image.*]`.

## Appended 2026-11-10: built

As proposed, with these differences and findings.

**A session whose stream names no lists at all is let through, not refused.**
The table above says a resume with no copy is a 409. That holds for a stream
that *names* lists and has no copy of them — a policy file's. One that names
none (from before lists were recorded, or an `App` a test builds by hand) is
made on empty lists instead, the way `Posture::same_place` already reads an
absent side as unknown. Without it every resume in `serve_ws.rs` was a 409,
because the stand-in factory there records no lists.

**`posture` in a body is refused by a sentence, not by serde.** `NewSession`
keeps the field to say what a session is made from; an unknown-field error
would have named the key and nothing else. `PoliciesTables` does take
`deny_unknown_fields`: a page older than the server that still sends
`environment` is told, rather than having it dropped.

**`[approvals]` is read from `config.toml` alone in `serve`.** The fallback
that read it from the working directory's policy file went with the file:
nothing else called it.

**The first session is named.** It was `null` — *the server's own* — and is
`empty` now, as one asked for with nothing is. `scripts/container-check.sh`
asserted the `null`.

**Found: `--worker` moves every place, this machine included.**
`terminal.spec.js` started `serve` on `luu.container.toml` and moved the
session to a posture on the host. With the flag in the file's place that move
is impossible, by a rule already written down
([`the-image-serve-was-started-on`](2026-11-08.the-image-serve-was-started-on.completed.md)).
The spec starts on `[runtimes] default = "docker"` and an `[image.*]` instead.

**What was removed outside the crate**: `deploy/luu.toml`, the chart's
`policy` value and its ConfigMap, `pages/setup.sh`'s `/etc/luu/luu.toml`
(`--purge` still deletes one an older install wrote), and section 6 of
`scripts/container-check.sh` rewritten on an image and lists.

**Verified:**
- `cargo test --workspace`, `clippy -D warnings`, `fmt`. `policies.rs`: lists
  compose, resolve, hash and recompose with no environment. `provider.rs`: a
  `[posture.*]` or an `[environment.*]` is a parse error. `lib.rs`: a place is
  described from flags alone, and `serve --sandbox` is refused. `serve_ws.rs`:
  a body naming a posture is a 400 that changes nothing, on a start and on a
  resume; a list that is not there is a 400 by its table; nothing named is
  `empty`; `/api/postures` offers `runtimes` and no names; `PUT
  /api/session/posture` is gone.
- By hand, on this container (Linux 6.18, Landlock ABI v7): `serve` with an
  `[image.*]` and two lists; the first session `empty` on `host`; moved to
  `direct` by `PUT /api/session/runtime`, its copy with it; a plan naming `ls`
  approved at the gate over empty lists and the call run, held by the kernel;
  a session started from `tools` and `tree`, named `tools · empty · tree`.
  This is section 6 of `container-check.sh` with `direct` for `docker`.

**Not verified, and why:**
- `scripts/container-check.sh` itself, `terminal.spec.js`, and the chart
  (`helm lint`): no container daemon and no helm in this container. CI runs
  the first and the third on the push.
- `luu_config_owner_proves_the_mail_and_the_mailbox_with_one_code` hung once
  under the whole suite and passed alone and with its own binary; nothing here
  touches it.

## Appended 2026-11-10: the page's specs, and what they found

**Found: a `serve` with no lists does not let the person rename a file.** The
tree's rename, new folder and save are held to the session's files list, by
the check `write_file` makes — a rule from before this. Until now the first
session of a `serve` had the working directory's `luu.toml`, or the built-in
policy, and both wrote `.`. On three empty lists it reads, so
`workspace.spec.js`'s *the pencil renames a file* was refused. The spec now
starts its session on a files list that writes. For a person it means: a
fresh install reads until a files list is made and chosen — *always in this
project* covers what a tool asks, and nothing covers what the person does in
the tree. **Not decided here**; it is the first thing in *Still open* below.

**Changed with it**: `gate.spec.js` starts its sessions on three lists called
`wide` in place of the posture; `grants.spec.js` on its lists in place of the
environment; `policies.spec.js` asserts a session is not started or moved by
name, that nothing names a list a rename has to follow, and that one that
names nothing carries empty lists and moves; `terminal.spec.js` as above.

**Verified:** every live-server spec, on this container's Chromium: 89 pass.
The static twin (`site.spec.js`, fixtures made by this binary): 5 pass.

**Failing, and failing before this** (named in
[`five-decisions`](2026-11-09.five-decisions.WIP.md) §*Left open by the three
that were built*): `workspace.spec.js`'s *the tab shows a changed file's diff
in a modal* — its terminal step, with no xterm installed here — and
`policies.spec.js`'s *the lists are edited in Settings*, which passes alone
and with its own file and fails only in the whole run, its *Save* still busy.
`terminal.spec.js` skips itself where no image is built.

## Still open, after building

- **What the person may do in the tree on empty lists.** Either the page's own
  writes stop being the session's (they are the person's, as its terminal on
  this machine is), or the first session starts from what the last one used
  (`prefs.start`, which only the dialog reads today).
- Rows 50, 51 (*Add to the policy*) and 76 of
  [`ROADMAP/2026-11-08`](../ROADMAP/2026-11-08/README.md), as *Still open*
  above says.

## Appended 2026-11-11: what the person does in the page is not a tool's

The first item of *Still open, after building* was put to the person as two
ways out, and answered:

> Una cosa es lo que el modelo puede hacer a través de tools, y otra lo que
> puede hacer el usuario en el IDE que viene siendo luu

**Decided: the first.** A list says what a tool may do. A rename or a new
folder in the tree is the person's, as the page's terminal on this machine
already is, and is held to the session's **folder** and not to its files list.

**Built.** `workspace::rename` and `make_dir` no longer ask the sandbox for
`read-write`; `workspace::inside` resolves the folder an entry is in —
symlinks and `..` — and requires it to be the session's base or under it. The
entry's own name is not followed, so a link is renamed rather than what it
points at. Who may ask is unchanged (`workspace_writable`: a browser on this
machine, or a user, whose base is their own folder), and so is every read,
which still goes through `check_path`.

**Rejected: the first session starting from what the last one used.** It
leaves a new install reading, and `prefs.start` lives in a browser while the
first session is made before there is one.

**What it costs:** a session started on lists that only read no longer stops
the page from renaming in its folder. Nothing a model does changes.

**Verified:** `workspace.rs` — a session whose lists only read renames and
makes a folder; a path through a link that leaves the folder is refused for
both, and nothing outside moves; the link itself is renamed.
`workspace.spec.js` is back on a session with no lists, and *the pencil
renames* and *the picker makes a new folder* pass there. `users.rs` and
`serve_ws.rs` pass; clippy and fmt.
