# The third serving stack: Vulkan on a BC-250

**Status:** run, measured and completed. Answers Machine 6 of
[`ROADMAP/2026-09-04/machines.md`](../ROADMAP/2026-09-04/machines.md): *"neither
Metal nor CUDA — llama.cpp over Vulkan on AMD hardware."* Also closes the
[`an-openai-compatible-backend`](2026-09-01.an-openai-compatible-backend.completed.md)
Still Open item *"nobody has run it against a real server."*

## The machine, corrected

The inventory listed this box as "16 GB GDDR6 → 14b comfortable" on the
assumption that the whole 16 GB is available the way it is on a discrete card.
It is not. The BC-250 is a PS5-derived APU with GDDR6 shared between system RAM
and VRAM by a board-level carve-out, and on this unit:

- `free -h` reports **9.4 GiB** total system RAM, not 16 GiB.
- Vulkan reports two heaps: 3.57 GiB + a 7.14 GiB `DEVICE_LOCAL` heap.
- `llama-server --list-devices` reports the GPU as **10 973 MiB, 9 814 MiB
  free** — the number that actually matters for what fits.

**The ceiling in `machines.md` should read "7B comfortable," not "14b
comfortable," for this specific board's carve-out.** A 14B Q4 model (~8–9 GB of
weights alone) would leave next to nothing for KV cache on a 9.8 GiB budget.
Confirming that number wants an actual 14B pull and load, which is not done
here — see Still open.

## Standing up the stack

`llama-cpp` 0.3.0 is a CachyOS/Arch package, and **the Vulkan backend is not
in it** — `pacman -S llama-cpp` alone produces a CPU-only binary
(`llama-server --list-devices` → `(none)`). The backend is a second package,
`ggml-vulkan`, an optional dependency of `ggml` that is not pulled in
automatically:

```sh
sudo pacman -S llama-cpp ggml-vulkan
```

After both are installed:
```text
$ llama-server --list-devices
Available devices:
  Vulkan0: AMD BC-250 (RADV GFX1013) (10973 MiB, 9814 MiB free)
```

RADV (Mesa's open-source Vulkan driver) is what is driving this — there is no
proprietary AMD stack in play, and no ROCm/HIP installed. This is the intended
third stack: neither Metal nor CUDA, and not even AMD's own compute stack.

## An intermittent hang, and how it was isolated

The first `llama-server -m … -c 8192 -ngl 99` never finished loading:
`load_model` logged and then nothing — no error, no crash. After 15+ minutes:

- All 18 threads at **0% CPU**, main thread parked in `futex_wait`.
- `VmRSS` never grew past ~103 MB — the 4.7 GB of weights never got read.
- `journalctl -k` around the timestamp showed no `amdgpu` reset or fault.

This is a genuine hang, not slow shader compilation (which would burn CPU on
at least one thread). To find out whether it was the Vulkan backend or the
server binary, `llama-cli` (no HTTP layer) was tried directly:

```text
llama-cli -ngl 5  -p "hello" -n 8   → 17.2 t/s prompt / 11.8 t/s gen  (partial offload)
llama-cli -ngl 99 -p "hello" -n 8   → 203.9 t/s prompt / 55.3 t/s gen (full offload)
```

Full GPU offload works, is fast, and the 55 t/s generation figure lines up with
the memory-bound estimate for this board (`~224 GB/s ÷ ~4.5 GB weights ≈ 50
tok/s`), which is itself a sanity check that Vulkan really is doing the work
rather than silently falling back to CPU.

`llama-server -ngl 99` was then retried, unchanged, and it loaded cleanly in
7 seconds. **The hang did not reproduce.** The finding stands as: this specific
combination (`llama-server`, RADV, GFX1013, full offload) has an intermittent
startup hang with no kernel-visible cause and no CPU burn — not a memory-size
problem (full offload works and fits), and not deterministic. A person running
this stack should know a stuck "model loaded" that never prints is worth a
kill-and-retry before assuming something is broken.

## `luu` against a real server, for the first time

With `llama-server` healthy and serving `/v1/chat/completions`:

```sh
cargo run --bin luu -- chat "what does the context manager do?" \
  --backend openai --openai-url http://127.0.0.1:8080/v1 --model qwen \
  --context-limit 8192 --reserve 512
```

```text
note: the window is the server's: --context-limit 8192 is what this run
budgets against and there is no field on this API to send it in. Start the
server with at least 8192 (llama-server -c 8192, vLLM --max-model-len 8192);
the prompt_tokens each turn reports is what actually arrived.
[stop] 455 prompt / 97 completion
```

`usage.prompt_tokens` arrived correctly on the real server (455, not `None`,
not zero), the window caveat printed exactly as designed, and the answer came
back coherent. Every claim in
[`an-openai-compatible-backend`](2026-09-01.an-openai-compatible-backend.completed.md)
was previously proven only against a stub HTTP server this repository wrote;
this is the first time against software this repository did not write.

## No vendor assumptions found

`cargo build --workspace`, `cargo test --workspace`, and `cargo clippy
--workspace --all-targets` were run on this machine (`x86_64`, CachyOS,
kernel 7.2.2). The build required no changes to compile or run — nothing in
`luu` assumes CUDA or Metal, confirming the premise this machine was chosen to
test.

**`cargo test --workspace` did fail once, and not for a Vulkan reason.**
`crates/agent-core/src/sandbox/linux.rs`'s test-only `sandbox_over` helper
built a `SandboxPolicy { .. }` struct literal missing the `egress` and `proxy`
fields added by
[`egress-through-the-host`](2026-09-04.egress-through-the-host.completed.md).
`#[serde(default)]` covers deserialization, not a Rust struct literal, so this
would have failed `cargo test --workspace` on **any** machine — it surfaced
here because this is the first fresh `cargo test --workspace` run since that
record landed. Fixed by adding `egress: Vec::new(), proxy: None,` to the
literal; no test's assertions changed.

## What this changes

- **Machine 6 is answered.** The third serving stack works: RADV Vulkan,
  `llama-server`, `luu`'s OpenAI-compatible backend, end to end, no vendor
  assumptions, no code changes needed in `luu` itself.
- **The size ceiling in `machines.md` is corrected** for this board's actual
  memory carve-out: 7B, not 14B, is what "comfortable" means here.
- **A packaging note worth keeping**: Vulkan support on Arch/CachyOS is a
  second package (`ggml-vulkan`), not implied by installing `llama-cpp`.

## Still open

- **14B was not attempted.** The corrected ceiling above is an estimate from
  the free-memory numbers, not a measured OOM or a measured comfortable run.
- **The hang was not root-caused.** It is recorded as observed and
  non-reproducing, not diagnosed — no `RADV_DEBUG`/`MESA_VK_TRACE` capture was
  taken while it was stuck.
- **The gate probe and repo-map corpus have not been run against this stack.**
  This record only establishes that the wire works; the model-quality
  questions other machines answered remain open here.
