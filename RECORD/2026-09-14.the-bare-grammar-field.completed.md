# Whether a bare `grammar` field works on `/v1/chat/completions` — it does, and not where this project runs

**Status:** completed the day it was written. Answers
[`a-grammar-for-tool-calls`](2026-09-06.a-grammar-for-tool-calls.completed.md)
§Still open's first bullet, verbatim: *"Whether `/v1/chat/completions` accepts
a bare `grammar` field on current `llama-server` builds as an undocumented
extension … This is one curl against a running server … it is the first
thing to do and it is not done here."* It is done here. The WIP record itself
is untouched — `RECORD/` is append-only — and item 5 of
[`ROADMAP/2026-09-09`](../ROADMAP/2026-09-09/README.md) is updated to say so.

## The question, and why it needed two servers, not one

The WIP record's own field table says `llama-server` accepts `grammar` only
on `/completion` / `/v1/completions`, documents `response_format` on
`/v1/chat/completions`, and leaves open whether `grammar` also works there,
undocumented. Machine 1 runs models through **Ollama**, not a bare
`llama-server` — and the same table's last §Still open bullet names the
consequence: *"Ollama is the backend every model run in this repository has
used. If only the grammar arm preserves the alternation, the arm that can be
run on the machine the work happens on is the one that cannot answer the
question."* So the curl was run twice, against two different servers holding
the same weights:

1. **Ollama's own `/v1/chat/completions`** (`127.0.0.1:11434`, the destination
   every record on this machine has used) — three identical requests, one
   with a real constraining GBNF grammar (`root ::= "ONLYTHIS"`), one with a
   string that is not valid GBNF at all, one with no `grammar` field. All
   three returned the same unconstrained text (`"Hi there! How can"`, 5
   tokens, `finish_reason: length`), byte for byte. **Ollama silently ignores
   the field.** Not an error, not a truncation, not a hint in the response —
   the request succeeds as if the key were never sent, which is what the
   field table already implied (Ollama's own constraint field is `format`,
   not `grammar`) but had not been shown, rather than inferred from a table.
2. **`llama-server` itself**, the binary Ollama 0.33.0 bundles at
   `Ollama.app/Contents/Resources/llama-server` (`llama.cpp` build
   `b1-9d77fa172`), run standalone against the same GGUF blob Ollama already
   had on disk for `qwen2.5-coder:7b`
   (`~/.ollama/models/blobs/sha256-60e05f21…`), on port 8090, bypassing
   Ollama's own API layer entirely. Same three requests:
   - Real grammar (`root ::= "ONLYTHIS"`) → the completion **is** `"ONLYTHIS"`,
     `finish_reason: stop`. Enforced, not merely accepted.
   - Invalid GBNF → `400 {"error": {"message": "Failed to initialize
     samplers: failed to parse grammar", …}}`. Validated, not silently eaten.
   - No `grammar` field → ordinary unconstrained completion, same as before.

## What it says

**Yes, as an undocumented extension — on `llama-server` directly, and only
there.** `/v1/chat/completions` takes a bare `grammar` field, parses it as
GBNF, and enforces it, on the exact server binary and exact weights this
project already has on disk. The WIP record's "which field" table listed
`response_format` for that row because that is what the docs say; the field
that answers item 4/5 is also there, one row up from where the table put it,
and reachable without moving to `/v1/completions` or applying a chat template
by hand — the cost the WIP record's §What it costs called *"a template, or a
branch"* does not apply to this path. **Ollama's own OpenAI-compatible
surface is a different, narrower API layered on the same binary, and it does
not forward the field at all.**

**What this changes for item 5, and what it does not.** It removes one of
the two prices the WIP record said item 5 could not avoid — for a
`luu chat --backend openai --openai-url http://127.0.0.1:8090/v1` destination,
against `llama-server` run directly, a grammar arm costs neither a template
nor a branch off `/v1/completions`. It changes nothing for the destination
every record on this machine has actually used: **`--backend ollama` still
cannot get a grammar through**, because the field dies one layer up, in
Ollama's own API translation, before it ever reaches the `llama-server`
process underneath. Whether to *run* against a bare `llama-server` instead of
Ollama on machine 1 is an unmade decision this file does not make — it only
removes the excuse that the answer was unknown.

## What this does not answer

- **vLLM, LM Studio, a hosted endpoint.** One server binary, one build. The
  WIP record's table already gives vLLM its own field
  (`structured_outputs`); nothing here tests it.
- **Whether the compiled grammar for this project's actual tool schemas
  parses.** The WIP record's own §What it costs names a real failure mode
  (llama.cpp #25923: an empty-properties schema compiles to invalid GBNF) —
  this curl used a one-line hand-written grammar to answer the field
  question cheaply, not the five-tool grammar item 5 would actually compile
  and send.
- **Whether running `llama-server` directly instead of through Ollama loses
  anything Ollama's own layer provides** — model management, the `/api/*`
  surface `luu`'s `--backend ollama` may lean on elsewhere. Not investigated;
  this record is scoped to the one field.

## What was rejected

- **Testing only against Ollama.** Would have answered "no" and left the WIP
  record's own documented ambiguity — *undocumented extension on
  `llama-server` builds* — exactly as open as it was. The question named a
  specific server; Ollama wrapping the same weights is not that server.
- **Compiling a real tool-call grammar for this test.** Named above as a
  separate, larger question (item 5's actual build, not its first move) —
  this file answers only whether the field exists and is honoured at all.
